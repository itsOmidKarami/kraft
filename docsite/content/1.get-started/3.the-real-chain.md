**Part 2 of 2.** [Part 1](/get-started/first-work-item) ran a work item on
`quick-task`, which has no gates. This page runs the `default` chain to a merged
pull request. It takes longer, because it waits for your approvals, CI, and the
[forge](/concepts/vocabulary#forge). A [gate](/concepts/vocabulary#gate) is a
node where you decide.

Steps 6 and 7 continue the numbering from Part 1. Start the server and connect
the repo there first (steps 1 and 2).

::note{title="Doing this from Claude Code instead"}
Steps 6 and 7 have slash commands too: `/kraft:handoff` to file work,
`/kraft:board` to see it, `/kraft:gates` to approve. See
[Use Kraft from your agent](/guides/day-to-day/agent-integration).
::

## 6. Try the real chain, and its gates

`default` opens and merges a pull request through your forge. Steps 1 to 5 work
without any of this; before you start `default`, the repo needs:

- **A GitHub or GitLab remote, with `gh` or `glab` logged in.**
- **CI that runs on pull requests.** Kraft waits for the merge request's checks
  to pass. On GitHub, a pull request with no checks at all reads as "no checks
  yet" and stays pending, so `merge_request_feedback` waits until its 90-minute
  cap and then stops and waits for you. A repo with no CI can set
  `ci_checks: false` on its entry in
  [`repos.yaml`](/reference/configuration/repos) to skip both CI waits, before
  and after the merge.
- **A review rule only if you can meet it.** `external_approval` waits while a
  branch rule requires an approving review. GitHub does not let you approve your
  own pull request, so on a solo repo with such a rule it waits until you remove
  the rule or someone else approves. With no such rule it passes straight away,
  so a solo developer needs nothing here.

Check the forge first:

```bash
kraft admin doctor
gh auth status
```

`gh auth status` (or `glab auth status`) reports you as logged in. In the
doctor output, the repo's `forge` row reads like this:

```text
ok    forge my-project  github · gh
```

It fails if `gh` or `glab` is missing, or if the repo had no GitHub or GitLab
`origin` when you connected it. For the second, set `forge: github` or
`forge: gitlab` on the repo in Settings › Repos and **Review & publish** (or in
`repos.yaml`). For a waiting item, see
[Waiting on CI or a review](/troubleshooting/why-did-my-item-stop#waiting-on-ci-or-a-review).

`default` is the chain most work runs on, and the default for `--chain` unless
the repo sets `default_chain`, so you can leave the flag off here. Give `resume`
the new item's ID, not the first one's:

```bash
kraft item create "add a --dry-run flag to the sync command"
kraft item resume ID
```

Before any code is written it stops at three gates, one after another:
`spec_approval`, then `plan_approval`, then `chain_revision_approval`. The last
is about the chain itself: an agent checks the approved spec and plan against
the nodes still to run and proposes changes to them, and when it proposes none,
which is usual, the gate passes without asking you. Each gate shows up under
*Needs you* on the board. Open one to read the document it is about:

![A spec an agent wrote, rendered on the item's review page and waiting for your approval, with Request changes and Approve](/assets/gate.png)

`kraft view artifact ID` reads the document the gate is about, and
`kraft item approve ID` approves it, as **Approve** does at the gate on the
item's page:

```bash
kraft view artifact ID
kraft item approve ID
```

`approve` names the gate it approved and says where the item is now:

```text
approved spec_approval on 9d0ab38ff3c9439b90506df0f6966660; the item is now running
```

To send it back instead, run `kraft item reject ID --note "..."`, or use
**Reject…** at the gate on the item's page. The node that wrote the document
runs again with your note. **Request changes** on the review page, the button in
the picture, sends the gate back the same way, with your summary and review
threads as the note: it is `kraft item review ID request-changes`, and
[Reviewing a change](/guides/day-to-day/review-a-change) covers it.

You know it worked when, after your last approval, the item moves out of
*Needs you* and into *Running*, and the board shows implementation started.
Implementation and tests take a while: the item comes back under *Needs you* at
`local_review`, which is step 7.

## 7. Review before it merges

After implementation and verification, the item stops at `local_review`, and
later at `final_review`. Each comes with a diff to read first.
`kraft view diff ID --stat` shows how big it is, and `kraft view diff ID` shows
the full diff:

```bash
kraft view diff ID --stat
kraft view diff ID
```

Kraft commits after every task, so by a gate the change is already on the
item's branch. The diff opens with **the change under review**: every commit
since the base, the item's spec and plan documents among them. Below it,
**uncommitted** lists whatever an agent left in the worktree without
committing. "(nothing uncommitted)" there is normal, not an empty review.

Approve `local_review` and Kraft opens a draft merge request and runs CI and
automated review on it. Approve `final_review` and it marks the request ready,
waits for the merge request's external approval on your forge, then merges.

Run `kraft item approve ID` at each gate, once you have read the diff, and
`kraft view list` to see the item's status:

```bash
kraft item approve ID
kraft view list
```

Each `approve` prints a line like that, naming the gate it approved. You know it worked
when `kraft view list` shows the item's status as `completed` and the merge
request shows as merged on your forge. If it stays under *Needs you* at a gate
you approved, or at a later one, see [Troubleshooting](/get-started/first-work-item#troubleshooting).

What each gate does, and how caps and waits bound the chain, is in
[How a work item runs](/concepts/how-a-work-item-runs).
