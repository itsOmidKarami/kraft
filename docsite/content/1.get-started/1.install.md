Install Kraft with uv, Homebrew, the install script, or from source. Then run
`kraft` to serve the board at `http://127.0.0.1:8765`.

## Requirements

To install and run Kraft you need:

- macOS or Linux. Windows is not supported, and WSL is untested.
- [uv](https://docs.astral.sh/uv/), or Homebrew. uv uses a Python 3.12 or newer
  already on your machine, or fetches one. To choose the interpreter yourself:
  `uv tool install --python 3.13 kraft-sdlc`.
- `git`, with `user.name` and `user.email` set for the user Kraft runs as
  (`git config --global user.name "Your Name"`, and the same for
  `user.email`), or in each repo you connect. Kraft commits the agents' work
  under that identity, and stops an item before its first task without one.
- Claude Code (`claude`), installed and logged in. Every agent task in the
  shipped chains runs on it. Kraft supports other agent CLIs as
  [harnesses](/reference/harnesses), but using one means editing the chains.

## Installation methods

Pick one. uv is the shortest path.

::tabs{sync="install"}
:::tabs-item{label="uv"}
```bash
uv tool install kraft-sdlc
kraft
```

The package is [`kraft-sdlc` on PyPI](https://pypi.org/project/kraft-sdlc/)
because other tools already use the name `kraft` (Unikraft's CLI, for one). The
command it installs is still `kraft`.
:::

:::tabs-item{label="Homebrew (macOS)"}
```bash
brew tap itsOmidKarami/kraft
brew install kraft
kraft
```
:::

:::tabs-item{label="Install script"}
The script fetches the newest release and installs `uv` first if you do not have
it:

```bash
curl -fsSL https://raw.githubusercontent.com/itsOmidKarami/kraft/main/install.sh | sh
```

[`install.sh`](https://github.com/itsOmidKarami/kraft/blob/main/install.sh) is
short and worth reading before you pipe it to a shell. It says where it put
`kraft`, and when that directory is not on your `PATH` yet (usually after it
installed uv), it says to run `uv tool update-shell` and open a new terminal.
:::

:::tabs-item{label="From source"}
Use this to run an unreleased commit or to work on Kraft itself. Besides uv and
`git`, you need [just](https://just.systems/) and Node 22 to build the board:

```bash
git clone https://github.com/itsOmidKarami/kraft.git
cd kraft
just setup     # Python and frontend dependencies
just install   # builds the board and installs the `kraft` command
kraft
```

To develop Kraft rather than run it, see [Contributing](/project/contributing).
:::
::

## Connect your agent

Kraft talks to agents through its MCP server, the command `kraft admin mcp`.
Register it with the agent you want to drive Kraft from. Pick your agent:

::tabs{sync="agent"}
:::tabs-item{label="Claude Code"}
Install the plugin:

```bash
claude plugin marketplace add itsOmidKarami/kraft
claude plugin install kraft@kraft
```

Then, with the Kraft server running, open a session in your repo, run
`/kraft:onboard`, and follow what it asks. It connects the repo and checks its
setup and test commands. The plugin registers the MCP server itself: do not
also run `kraft admin init`.

Without the plugin, register the server and the `/kraft:*` skills from a
terminal, then connect the repo:

```bash
kraft admin init
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Codex"}
Install the plugin:

```bash
codex plugin marketplace add itsOmidKarami/kraft
codex plugin add kraft@kraft
```

It registers the MCP server and adds the Kraft skills. Without the plugin,
register the server alone with `codex mcp add kraft -- kraft admin mcp`.

Then connect the repo:

```bash
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Cursor"}
Add the Kraft marketplace:

```bash
agent plugin marketplace add https://github.com/itsOmidKarami/kraft
```

Then start `agent`, run `/plugins`, open the Marketplace tab, pick `kraft`, and
install it. It registers the MCP server and adds the Kraft skills.

Without the plugin, add the server to `~/.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "kraft": { "command": "kraft", "args": ["admin", "mcp"] }
  }
}
```

and approve it with `agent mcp enable kraft`.

Then connect the repo:

```bash
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="OpenCode"}
```bash
opencode mcp add --global kraft -- kraft admin mcp
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Amp"}
```bash
amp mcp add kraft -- kraft admin mcp
amp skill add itsOmidKarami/kraft/plugins/kraft/skills --global   # optional: the Kraft skills
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Antigravity"}
Antigravity imports the plugin from a local copy of the repo. The import copies
it, so the clone can go afterwards:

```bash
clone=$(mktemp -d)
git clone --depth 1 https://github.com/itsOmidKarami/kraft.git "$clone"
agy plugin import "$clone/plugins/kraft"
rm -rf "$clone"
```

It registers the MCP server and adds the Kraft skills. Without the plugin,
register the server alone with `agy mcp add kraft kraft admin mcp`.

Then connect the repo:

```bash
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Gemini CLI"}
Since 2026-06-18, Gemini CLI works only with an API key or Gemini Code Assist.
With an individual Google account, use Antigravity instead.

```bash
gemini mcp add --scope user kraft kraft admin mcp
cd ~/code/my-project
kraft repo connect
```
:::
::

The shipped chains run every worker on Claude Code, and Kraft refuses to launch
a Claude worker unless Claude Code knows the `kraft` MCP server: the worker
asks the permission gate through it. So even when you drive Kraft from another
agent, install the Claude Code plugin or run `kraft admin init` as well.

The Kraft plugin, with its skills, installs on Claude Code, Codex, Cursor and
Antigravity. OpenCode and Gemini CLI get the MCP server alone, and Amp adds the
skills with `amp skill add`.

The `kraft` command must be on your `PATH` for every agent.
[Agent integration](/guides/agent-integration) covers each agent in detail,
including what a worker needs when a chain runs on it.

## Verify

`kraft` runs the server in the foreground, so open a second terminal for this:

```bash
kraft --version      # prints the installed version
kraft admin health   # exits 1 if the server is down or degraded
kraft admin doctor   # runs every check; exits 1 if any fails
```

Run `doctor` after you connect a repo: most of its rows are about connected
repos. You know it worked when `http://127.0.0.1:8765` shows the board and
`kraft admin doctor` exits 0. Two rows fail on a repo that is not ready yet:

- `forge <repo>` fails when the repo has no GitHub or GitLab `origin` remote,
  because no forge is recorded for it. `quick-task` does not need one; the
  `default` chain does. If your repo has no remote and you only run
  `quick-task`, expect this one `FAIL` and exit 1; every other row should pass.
- `setup <repo>` fails when the repo has no `setup_command`.

Two more fail when an agent cannot reach Kraft:

- `mcp server` fails when nothing registers Kraft's MCP server with Claude Code,
  so every Claude worker would be refused: install the plugin, or run
  `kraft admin init`. It is a warning instead when a registration exists but
  some connected repos lack one of their own. It does not check other agents.
- `kraft on PATH` fails when the `kraft` command is not on your `PATH`. The
  plugin and every MCP registration run it by name, and workers get the
  server's `PATH`. After a uv install, run `uv tool update-shell`, then start
  `kraft` again from a new terminal.

Next: [Your first work item](/get-started/first-work-item).

## Enable vector search

Search works out of the box in full-text mode. To add vector (semantic) search
to a uv or script install, reinstall with the `vector` extra. It downloads a
model of about 130 MB on the first search.

```bash
uv tool install --force "kraft-sdlc[vector]"
```

If the model cannot be downloaded (offline, or a proxy refuses Hugging Face),
search keeps working as full-text search and says so in a `note`. A search
that asks for `mode=vector` answers 422 with the reason. `kraft admin doctor`
fails its `embeddings` row, and `/api/health` reports the model's `state` as
`failing`.

## Upgrading

Back up the database first. A newer Kraft can migrate `run/orchestrator.db`
forward when it starts, and there is no way back: the version you had then
refuses to start on it (`database schema vN is newer than code vM`). The backup
is what lets you [roll back](#pin-or-roll-back-a-version). This copy is safe
while the server runs:

```bash
sqlite3 ~/.kraft/run/orchestrator.db ".backup '$HOME/kraft-backup.db'"
```

No `sqlite3` command? Python does the same:

```bash
python3 -c "import sqlite3; sqlite3.connect('file:$HOME/.kraft/run/orchestrator.db?mode=ro', uri=True).backup(sqlite3.connect('$HOME/kraft-backup.db'))"
```

Use your `$KRAFT_HOME` in place of `~/.kraft` if you set one. To check the
copy, see [Verify the backup](/guides/operations#verify-the-backup); to
restore one, see [Back up the database](/guides/operations#back-up-the-database).

Kraft also makes a copy of its own. Before it migrates the database, it copies
it to `run/orchestrator.db.pre-v<N>-<time>`, where `<N>` is the new schema
version, and names the file in `run/logs/server.log`. Each upgrade makes a new
copy, so after more than one, restore the newest. Take your own backup anyway:
you know when you made it, and it does not depend on the version you upgrade
to.

Then upgrade:

```bash
kraft admin update             # install the newest release
kraft admin update --restart   # also restart a running server; pause running items first (see below)
```

On a uv or script install, `kraft admin update` runs
`uv tool install --force "kraft-sdlc[vector]==X.Y.Z"`, so the `vector` extra
(when you have it) and a Python you chose with `--python` stay. With no
`--python` recorded, it asks for the minor version Kraft runs on now, such as
`3.13`, so a later `uv python upgrade` still carries Kraft along. uv records
the exact version, so `uv tool upgrade` leaves Kraft where it is: update with
`kraft admin update`. In the few minutes after a release, before PyPI has it, it
installs the release's wheel from GitHub instead. Updates before 1.5 dropped
the extra: if vector search stopped working after one, reinstall it as in
[Enable vector search](#enable-vector-search).

On a Homebrew install, `kraft admin update` runs `brew upgrade kraft` instead of
`uv tool install`. On a pipx or pip install, or a source checkout, it installs
nothing: a uv copy would sit beside the `kraft` you run and change nothing. It
prints the command that updates the install you have instead, such as
`pipx install --force "kraft-sdlc==X.Y.Z"`. A restart ends any agent that is running: see
[A restart ends running agents](#a-restart-ends-running-agents).

Without `--restart`, a running server keeps running the old release until you
restart it with `kraft admin restart`. Unless you update from 1.4 (see
[Upgrading from 1.4](#upgrading) below), the board shows a page saying to
restart instead of the interface until then, and `kraft admin doctor` warns on
its `restart` row.

An upgrade never changes `$KRAFT_HOME/templates/`, with two exceptions:

- An install still on Kraft 0.x's template format (a `registry.yaml`, no
  `library.yaml`) is migrated, after a prompt (see
  [Migrating an older template configuration](/reference/cli/admin#migrating-an-older-template-configuration)).
- The first start of 1.5 or later rewrites `theme.yaml` once if it still has
  `palette`, and keeps the original as `theme.yaml.pre-1.5` beside it (see
  [My theme looks different](/get-started/troubleshooting#where-did-a-page-go-and-why-does-my-theme-look-different)).

To take new shipped chains and library tasks, see
[Upgrade your templates](/guides/upgrading-templates).

**Upgrading from 1.4.** The new release changes some 1.4 behaviour that the
[stability policy](/project/status-and-support#versioning-and-stability) covers, such as `--json`
fields and exit codes. Each change is listed here.

- Update with uv, not with 1.4's `kraft admin update`. That command runs in
  the release you have installed, and 1.4's installs the new release without
  the `[vector]` extra and on uv's default Python, and leaves
  `uv tool upgrade` pointing at a file it has deleted. Instead run
  `uv tool install --force --python 3.X "kraft-sdlc[vector]==<version>"`, with
  the Python you installed Kraft with for `3.X` and the release for
  `<version>` (leave out `[vector]` if you don't use vector search), then
  `kraft admin restart`. That restart is the new release's: it lists running
  items and asks before it ends their agents.
- If you used 1.4's `kraft admin update` anyway, restart right after it.
  With `--restart` (or a service restart), 1.4 restarted the server without
  asking, which ended the agents of running items: pause them first (see
  [A restart ends running agents](#a-restart-ends-running-agents)). Without
  `--restart`, the 1.4 server keeps running and serves the new interface,
  which misreads its board: items show under the wrong heading, and the
  footer names the new release. The board says so in a banner over it (from
  1.5.0; an rc14 or earlier interface did not), and `kraft admin doctor`'s
  `restart` row warns that the server runs a release older than the one
  installed. Run `kraft admin restart` as soon as the update finishes, don't
  act on the board before it, and reinstall `[vector]` with the command above
  if you use vector search.
- The new release replaces the interface, and some pages moved. Old
  addresses still open the right page;
  [Where did a page go](/get-started/troubleshooting#where-did-a-page-go-and-why-does-my-theme-look-different)
  lists where each one went.
- On a network bind, the new release checks the address every browser uses
  to reach the board. 1.4 skipped that check over plain http, so your board
  may have worked at a name that isn't in `allowed_hosts`. After the upgrade,
  such a browser gets a page saying the name isn't allowed. Before you
  upgrade, add each exact name you use (no wildcards) on Settings › Access, or
  to `allowed_hosts` in `access.yaml`. `kraft admin doctor` warns when the
  bind is off loopback and the list is empty.
- Cancel keeps the branch. In 1.4, Cancel in the web interface deleted the
  item's branch and worktree; now it keeps them. To delete them, run
  `kraft item abandon ID --yes`.
- A merge request closed without merging stops its item. In 1.4 the item
  kept waiting. Reopen the merge request from the item's page, retry, or
  cancel.
- You can't disconnect a repo while it has open items. `kraft repo
  disconnect` (and `DELETE /api/repos`) is refused with a 409 until each of
  the repo's items is done, cancelled or abandoned, paused and never-started
  ones included. In 1.4 it went through and left those items stranded.
- A repo entry with `test_command: ""` now means the repo has no tests. In
  1.4 such an entry stopped every item at `verify`; now its items pass
  `verify` without running a test. Before you upgrade, set a real test command
  on any such entry, or `enabled: false` to keep it from running. After the
  upgrade, `kraft admin doctor`'s `tests` row names each such entry.
- `agent_overrides` is now an object, not JSON text, wherever it appears:
  `kraft view show --json`, `kraft item approve --json` and every other
  `--json` answer that carries the item, the MCP tools' results, and
  `GET /api/work-items/{id}`. In the answers to an action, such as
  `kraft item approve --json`, `node_overrides` and `policy_override` are now
  objects too, as `kraft view show --json` already had them. If a script runs
  `json.loads` on one of them, read it as an object instead. Setting the
  override still works as in 1.4: `kraft item set-overrides` and
  `PATCH /api/work-items/{id}` replace the whole override.
- `budget_cap.cap_usd` in `kraft view show --json` is the cap that stops the
  item first: the lower of its own cap and its policy's item-wide
  `budget_usd`. Read `budget_cap.key` to tell which one it is.
  `kraft view events -f --json` prints one JSON object per line from the
  first line on, where 1.4 printed the backlog as an indented array.
- A model override 1.4 stored that is not a model id, such as
  `kraft item set-overrides --model "sonnet 4"`, now stops its item at the
  next launch instead of reaching the agent. The reason names the command
  that clears it.
- `POST /api/triggers` refuses a blank title. A `title` that is empty or only
  whitespace now gets a `422` (`title cannot be empty`), where 1.4 filed an
  item with no title. If a webhook fills the title from a field that can be
  empty, give it a fallback.
- `kraft repo connect` on a repo that is already connected now changes it.
  In 1.4 it did nothing. Now it probes the repo again and saves what its
  entry left undecided: a test command where it has none and no test scopes,
  and a setup command where none is declared. That can enable a repo saved
  disabled for want of a test command. In a terminal it asks first; with
  `-y`, `--json` or no terminal it saves without asking. A script that
  re-runs connect to check a repo should run `kraft repo list` instead. Connect
  also refuses a repo with no commit yet, which 1.4 connected: commit its
  files first. `kraft admin doctor` names each entry 1.4 left without a test
  or setup command where the new release finds one, with the connect command
  that saves it.
- The VS Code extension from the new release works only with a Kraft server
  of the same release. VS Code updates the extension on its own, and against
  a 1.4 server it shows the board but disables every action (its status bar
  reads `Kraft (read-only)`). Update Kraft too.
- `kraft admin restart` with no server running exits 1 (1.4: 0). A script
  that runs it under `set -e` now stops there. `update --restart` is
  unchanged.

**From before the `kraft-sdlc` rename.** An older install can still hold a
`kraft` uv tool next to `kraft-sdlc`. `kraft admin update` then stops and names
the two commands that clear it:

```bash
uv tool uninstall kraft
uv tool install --force --reinstall kraft-sdlc
```

The reinstall is needed because the uninstall removes the `kraft` command both
packages share.

**From a 0.x install.** Read the
[1.0.0 changelog](https://github.com/itsOmidKarami/kraft/blob/main/CHANGELOG.md#100)
first. Finish or abandon in-flight items, and note that harness profile names
and the template layout changed.

### A restart ends running agents

Stopping Kraft stops every agent it is running, whether you run
`kraft admin stop`, `kraft admin restart` or `kraft admin update --restart`,
or restart the service. When Kraft starts again, each item whose agent was
running stops with
`reattach: running session, PID identity unconfirmed, no result (pid N is not alive)`,
and the board shows it as failed.

`kraft admin restart` and `kraft admin update --restart` list the active items
first and, in a terminal, ask before going on (`-y` skips the question).
`kraft admin stop` only lists them. The listing and the question are new in
1.5. `kraft admin update` runs in the release you have installed, so updating
from 1.4 runs 1.4's `update --restart`, which does neither. So upgrade when
nothing is running, or pause the running items first and resume them
afterwards:

```bash
kraft view list --all --status=active   # the items that may have an agent running
kraft item pause ID                     # for each of them
kraft admin update --restart
kraft item resume ID
```

An item that a restart already stopped needs only `kraft item retry ID`.

### Pin or roll back a version

`kraft admin update` only installs the newest release on a channel; it cannot
target a version. Install a specific version with the package manager instead.

**uv or script install.** Name the version:

```bash
uv tool install --force "kraft-sdlc==X.Y.Z"
```

Add the extra if you use vector search: `"kraft-sdlc[vector]==X.Y.Z"`. To
stay on that version, do not run `kraft admin update`; it moves you to the
newest release again.

**Homebrew.** The tap has one formula, which each release rewrites to the
newest version, so Homebrew cannot install an older one. `brew pin kraft` stops
`brew upgrade`, and with it `kraft admin update`, from moving the version you
have. To go back to an older release, `brew uninstall kraft` and install that
version with uv.

**What a rollback does to `$KRAFT_HOME`.** Starting a newer Kraft migrates
`run/orchestrator.db` forward in place, and there is no downgrade migration.
An older Kraft refuses to start on a database a newer one migrated
(`database schema vN is newer than code vM`, in `run/logs/server.log`). So
[back up `run/orchestrator.db`](/guides/operations#back-up-the-database)
before you upgrade, and restore that backup when you roll back. If you have
none, restore the copy Kraft made before migrating,
newest `run/orchestrator.db.pre-v<N>-*` (see
[The copy Kraft makes before an upgrade](/guides/operations#the-copy-kraft-makes-before-an-upgrade)). `run/index.db`
needs nothing: an older Kraft rebuilds a search index it cannot read.
A rollback does not rewrite `templates/`; run `kraft admin templates lint` after
a rollback to check the older version still accepts them. If you install an
older version while the newer server still runs, the web UI says **An older
Kraft is installed** and points here, rather than telling you to restart.

**Rolling back from 1.5 to 1.4.**

1. Stop Kraft with `kraft admin stop`. If Kraft runs as a
   [service](/guides/operations#run-kraft-as-a-service), run
   `kraft admin uninstall-service` instead: the service manager starts a
   stopped server again, and the next step must not run under a live one.
2. Install 1.4: `uv tool install --force "kraft-sdlc==1.4.0"`.
3. Restore the database: put your backup, or Kraft's own
   newest `run/orchestrator.db.pre-v51-*`, in place as `run/orchestrator.db`, and delete
   any `orchestrator.db-wal` and `orchestrator.db-shm` beside it. See
   [Back up the database](/guides/operations#back-up-the-database) for the
   steps.
4. Copy `templates/theme.yaml.pre-1.5` (`theme.yaml.pre-ux2` if you ran
   any of 1.5.0rc5 to rc9) over `templates/theme.yaml`. 1.4's
   interface takes its colours from `palette`, which 1.5 removed, so without
   the copy it shows its default colours. The copy is your theme from the
   first upgrade to 1.5, and is never replaced: if you rolled back before and
   changed the theme on 1.4, set it again in 1.4's Settings.
5. Start Kraft with `kraft admin start --detach`, or
   `kraft admin install-service` if it ran as a service, then run
   `kraft admin templates lint`.

Restoring the backup loses everything done on 1.5 since you took it: items
filed, runs, approvals and their history. It does not remove what those runs
made outside the database. Their worktrees under `run/worktrees/`, their
branches, and any merge requests they opened are still there, and 1.4 knows
nothing about them. `kraft admin doctor`'s `worktrees` row lists a worktree
with no work item; delete the ones you do not need, and close any merge
request yourself. 1.4's row also lists the worktrees of items you cancelled
on 1.4, which its board does not show. A worktree made on 1.5 is one whose id
is not in the database you restored:
`sqlite3 run/orchestrator.db "select id from work_items"` lists those.

## Uninstall

```bash
uv tool uninstall kraft-sdlc   # uv or script install
brew uninstall kraft           # Homebrew install
```

Neither removes `$KRAFT_HOME`. Delete that directory yourself to discard all
Kraft state.

## Where state lives

Kraft keeps state in `$KRAFT_HOME` (default `~/.kraft`):

| Path | Holds |
|---|---|
| `~/.kraft/run/` | `orchestrator.db`, `index.db`, `logs/`, `results/`, `worktrees/`, `attachments/`; `orchestrator.db.pre-v<N>-<time>` after each upgrade that migrated the database |
| `~/.kraft/templates/` | The YAML the Templates and Settings screens edit: `library.yaml`, `chains/`, `harnesses.yaml`, `policy.yaml`, `repos.yaml`, `intake.yaml`; `access.yaml` and `notify.yaml` appear once you save those Settings screens |

`templates/` is seeded from the packaged defaults on first run and never
overwritten after, so an upgrade cannot clobber an edited policy. It is a plain
directory of files, so you can diff it, revert it, or `git init` it.

To reach the board from another device, see [Remote access](/guides/remote-access).

A second, fully separate instance needs its own `KRAFT_HOME` and its own port.
See [Run two instances](/guides/operations#run-two-instances). For backups,
logs and disk use, see [Operate a Kraft server](/guides/operations).
