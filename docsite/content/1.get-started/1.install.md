Install Kraft with uv, Homebrew, the install script, or from source. Then run
`kraft` to serve the board at `http://127.0.0.1:8765`.

## Requirements

To install and run Kraft you need:

- macOS or Linux. Windows is not supported, and WSL is untested.
- [uv](https://docs.astral.sh/uv/), or Homebrew. uv uses a Python 3.12 or newer
  already on your machine, or fetches one. To choose the interpreter yourself:
  `uv tool install --python 3.13 kraft-sdlc`.
- `git`, with `user.name` and `user.email` set for the user Kraft runs as
  (`git config --global user.name "Your Name"`, and the same for
  `user.email`), or in each repo you connect. Kraft commits the agents' work
  under that identity, and stops an item before its first task without one.
- Claude Code (`claude`), installed and logged in. Every agent task in the
  shipped chains runs on it. Kraft supports other agent CLIs as
  [harnesses](/reference/harnesses), but using one means editing the chains.

## Installation methods

Pick one. uv is the shortest path.

::tabs{sync="install"}
:::tabs-item{label="uv"}
```bash
uv tool install kraft-sdlc
kraft
```

The package is [`kraft-sdlc` on PyPI](https://pypi.org/project/kraft-sdlc/)
because other tools already use the name `kraft` (Unikraft's CLI, for one). The
command it installs is still `kraft`.
:::

:::tabs-item{label="Homebrew (macOS)"}
```bash
brew tap itsOmidKarami/kraft
brew install kraft
kraft
```
:::

:::tabs-item{label="Install script"}
The script fetches the newest release and installs `uv` first if you do not have
it:

```bash
curl -fsSL https://raw.githubusercontent.com/itsOmidKarami/kraft/main/install.sh | sh
```

[`install.sh`](https://github.com/itsOmidKarami/kraft/blob/main/install.sh) is
short and worth reading before you pipe it to a shell. It says where it put
`kraft`, and when that directory is not on your `PATH` yet (usually after it
installed uv), it says to run `uv tool update-shell` and open a new terminal.
:::

:::tabs-item{label="From source"}
Use this to run an unreleased commit or to work on Kraft itself. Besides uv and
`git`, you need [just](https://just.systems/) and Node 22 to build the board:

```bash
git clone https://github.com/itsOmidKarami/kraft.git
cd kraft
just setup     # Python and frontend dependencies
just install   # builds the board and installs the `kraft` command
kraft
```

To develop Kraft rather than run it, see [Contributing](/project/contributing).
:::
::

## Connect your agent

Kraft talks to agents through its MCP server, the command `kraft admin mcp`.
Register it with the agent you want to drive Kraft from. Pick your agent:

::tabs{sync="agent"}
:::tabs-item{label="Claude Code"}
Install the plugin:

```bash
claude plugin marketplace add itsOmidKarami/kraft
claude plugin install kraft@kraft
```

Then, with the Kraft server running, open a session in your repo, run
`/kraft:onboard`, and follow what it asks. It connects the repo and checks its
setup and test commands. The plugin registers the MCP server itself: do not
also run `kraft admin init`.

Without the plugin, register the server and the `/kraft:*` skills from a
terminal, then connect the repo:

```bash
kraft admin init
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Codex"}
Install the plugin:

```bash
codex plugin marketplace add itsOmidKarami/kraft
codex plugin add kraft@kraft
```

It registers the MCP server and adds the Kraft skills. Without the plugin,
register the server alone with `codex mcp add kraft -- kraft admin mcp`.

Then connect the repo:

```bash
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Cursor"}
Add the Kraft marketplace:

```bash
agent plugin marketplace add https://github.com/itsOmidKarami/kraft
```

Then start `agent`, run `/plugins`, open the Marketplace tab, pick `kraft`, and
install it. It registers the MCP server and adds the Kraft skills.

Without the plugin, add the server to `~/.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "kraft": { "command": "kraft", "args": ["admin", "mcp"] }
  }
}
```

and approve it with `agent mcp enable kraft`.

Then connect the repo:

```bash
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="OpenCode"}
```bash
opencode mcp add --global kraft -- kraft admin mcp
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Amp"}
```bash
amp mcp add kraft -- kraft admin mcp
amp skill add itsOmidKarami/kraft/plugins/kraft/skills --global   # optional: the Kraft skills
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Antigravity"}
Antigravity imports the plugin from a local copy of the repo. The import copies
it, so the clone can go afterwards:

```bash
clone=$(mktemp -d)
git clone --depth 1 https://github.com/itsOmidKarami/kraft.git "$clone"
agy plugin import "$clone/plugins/kraft"
rm -rf "$clone"
```

It registers the MCP server and adds the Kraft skills. Without the plugin,
register the server alone with `agy mcp add kraft kraft admin mcp`.

Then connect the repo:

```bash
cd ~/code/my-project
kraft repo connect
```
:::

:::tabs-item{label="Gemini CLI"}
Since 2026-06-18, Gemini CLI works only with an API key or Gemini Code Assist.
With an individual Google account, use Antigravity instead.

```bash
gemini mcp add --scope user kraft kraft admin mcp
cd ~/code/my-project
kraft repo connect
```
:::
::

The shipped chains run every worker on Claude Code, and Kraft refuses to launch
a Claude worker unless Claude Code knows the `kraft` MCP server: the worker
asks the permission gate through it. So even when you drive Kraft from another
agent, install the Claude Code plugin or run `kraft admin init` as well.

The Kraft plugin, with its skills, installs on Claude Code, Codex, Cursor and
Antigravity. OpenCode and Gemini CLI get the MCP server alone, and Amp adds the
skills with `amp skill add`.

The `kraft` command must be on your `PATH` for every agent.
[Agent integration](/guides/agent-integration) covers each agent in detail,
including what a worker needs when a chain runs on it.

## Verify

`kraft` runs the server in the foreground, so open a second terminal for this:

```bash
kraft --version      # prints the installed version
kraft admin health   # exits 1 if the server is down or degraded
kraft admin doctor   # runs every check; exits 1 if any fails
```

Run `doctor` after you connect a repo: most of its rows are about connected
repos. You know it worked when `http://127.0.0.1:8765` shows the board and
`kraft admin doctor` exits 0. Two rows fail on a repo that is not ready yet:

- `forge <repo>` fails when the repo has no GitHub or GitLab `origin` remote,
  because no forge is recorded for it. `quick-task` does not need one; the
  `default` chain does. If your repo has no remote and you only run
  `quick-task`, expect this one `FAIL` and exit 1; every other row should pass.
- `setup <repo>` fails when the repo has no `setup_command`.

Two more fail when an agent cannot reach Kraft:

- `mcp server` fails when nothing registers Kraft's MCP server with Claude Code,
  so every Claude worker would be refused: install the plugin, or run
  `kraft admin init`. It is a warning instead when a registration exists but
  some connected repos lack one of their own. It does not check other agents.
- `kraft on PATH` fails when the `kraft` command is not on your `PATH`. The
  plugin and every MCP registration run it by name, and workers get the
  server's `PATH`. After a uv install, run `uv tool update-shell`, then start
  `kraft` again from a new terminal.

## Enable vector search

Search works out of the box in full-text mode. To add vector (semantic) search
to a uv or script install, reinstall the version you run, on the Python it runs
on, with the `vector` extra. It downloads a model of about 130 MB on the first
search.

```bash
uv tool install --force --python 3.X "kraft-sdlc[vector]==X.Y.Z"
```

`kraft --version` prints `X.Y.Z`. Name both: without the version, uv installs
the newest final release, which on a release candidate is an older Kraft that
refuses to start on its database; without `--python`, uv rebuilds Kraft on its
own default Python. `kraft admin doctor`'s `embeddings` row prints this command
filled in for your install. On a pipx or pip install it prints that installer's
command instead; the Homebrew formula does not ship the `vector` extra.

If the model cannot be downloaded (offline, or a proxy refuses Hugging Face),
search keeps working as full-text search and says so in a `note`. A search
that asks for `mode=vector` answers 422 with the reason. `kraft admin doctor`
fails its `embeddings` row, and `/api/health` reports the model's `state` as
`failing`.

On an Intel Mac, or on Apple Silicon before macOS 14, the `vector` extra
installs only on Python 3.12 or 3.13: on 3.14 the package that runs the model,
`onnxruntime`, has no build for those Macs, and the install fails to resolve.
Install Kraft with `--python 3.13` there. A plain `uv tool install` or
`install.sh` can pick 3.14 when the machine has no Python 3.12 or newer.

## Upgrading

Coming from 1.4? [What's new in 2.0](/get-started/whats-new) says what you
get, and [Upgrading from 1.4](#upgrading-from-14) what changes; read both
before you upgrade.

Back up the database first. A newer Kraft can migrate `run/orchestrator.db`
forward when it starts, and there is no way back: the version you had then
refuses to start on it (`database schema vN is newer than code vM`). The backup
is what lets you [roll back](#pin-or-roll-back-a-version). This copy is safe
while the server runs:

```bash
sqlite3 ~/.kraft/run/orchestrator.db ".backup '$HOME/kraft-backup.db'"
```

No `sqlite3` command? Python does the same:

```bash
python3 -c "import sqlite3; sqlite3.connect('file:$HOME/.kraft/run/orchestrator.db?mode=ro', uri=True).backup(sqlite3.connect('$HOME/kraft-backup.db'))"
```

Use your `$KRAFT_HOME` in place of `~/.kraft` if you set one. To check the
copy, see [Verify the backup](/guides/operations#verify-the-backup); to
restore one, see [Back up the database](/guides/operations#back-up-the-database).

Kraft also makes a copy of its own. Before it migrates the database, it copies
it to `run/orchestrator.db.pre-v<N>-<time>`, where `<N>` is the new schema
version, and names the file in `run/logs/server.log`. Each upgrade that
migrates makes a new copy, so after more than one, restore the one whose schema
is the one the release you go back to runs: see
[The copy Kraft makes before an upgrade](/guides/operations#the-copy-kraft-makes-before-an-upgrade)
for how to tell. Take your own backup anyway: you know when you made it, and it
does not depend on the version you upgrade to.

Then upgrade:

```bash
kraft admin update             # install the newest release
kraft admin update --restart   # also restart a running server; pause running items first (see below)
```

On a uv or script install, `kraft admin update` runs
`uv tool install --force "kraft-sdlc[vector]==X.Y.Z"`, so the `vector` extra
(when you have it) and a Python you chose with `--python` stay. With no
`--python` recorded, it asks for the minor version Kraft runs on now, such as
`3.13`, so a later `uv python upgrade` still carries Kraft along (an update
run by 1.5.0rc14 did not: see
[Upgrading from a 1.5.0 release candidate](#upgrading-from-a-150-release-candidate)).
uv records the exact version, so `uv tool upgrade` leaves Kraft where it is: update with
`kraft admin update`. In the few minutes after a release, before PyPI has it, it
installs the release's wheel from GitHub instead. An update run by 1.4 or
earlier, or by a 1.5.0 release candidate before rc14, dropped the extra: if
vector search stopped working after one, reinstall it as in
[Enable vector search](#enable-vector-search).

On a Homebrew install, `kraft admin update` runs `brew upgrade kraft` instead of
`uv tool install`. On a pipx or pip install, or a source checkout, it installs
nothing: a uv copy would sit beside the `kraft` you run and change nothing. It
prints the command that updates the install you have instead, such as
`pipx install --force "kraft-sdlc==X.Y.Z"`. A restart ends any agent that is running: see
[A restart ends running agents](#a-restart-ends-running-agents).

Without `--restart`, a running server keeps running the old release until you
restart it with `kraft admin restart`. Unless you update from 1.4 or from a
1.5.0 release candidate before rc14 (see [Upgrading from 1.4](#upgrading-from-14)
below), the board shows a page saying to restart instead of the interface until
then. `kraft admin doctor` warns on its `restart` row either way.

An upgrade never changes `$KRAFT_HOME/config/`, with three exceptions:

- An install still on Kraft 0.x's template format (a `registry.yaml`, no
  `library.yaml`) is migrated, after a prompt (see
  [Migrating an older template configuration](/reference/cli/admin#migrating-an-older-template-configuration)).
- The first start of 2.0 or later rewrites `theme.yaml` once if it still has
  `palette`, and keeps the original as `theme.yaml.pre-2.0` beside it (see
  [My theme looks different](/get-started/troubleshooting#where-did-a-page-go-and-why-does-my-theme-look-different)).
  A home a 1.5.0 release candidate already converted keeps that candidate's
  `theme.yaml.pre-1.5` (`theme.yaml.pre-ux2` from rc5 to rc9) as its one
  copy, and gets no second one.
- The first start of 2.0 or later renames a 1.4 `templates/` to `config/` and
  moves two keys between `policy.yaml` and `intake.yaml`, rewriting the
  files it moves a key between (see [Upgrading from 1.4](#upgrading-from-14)).

To take new shipped chains and library tasks, see
[Upgrade your templates](/guides/upgrading-templates).

### Upgrading from 1.4

2.0 changes some 1.4 behaviour that the
[stability policy](/project/status-and-support#versioning-and-stability) covers, such as `--json`
fields and exit codes, which is why it is a major release. Each change is
listed here; [What's new in 2.0](/get-started/whats-new) says what you get for
it. Apart from these, your chains, library and other config files carry over
as they are.

- On a uv or `install.sh` install, update with uv, not with 1.4's
  `kraft admin update`. That command runs in the release you have installed,
  and 1.4's installs the new release without the `[vector]` extra and on uv's
  default Python, and leaves `uv tool upgrade` pointing at a file it has
  deleted. Instead run
  `uv tool install --force --python 3.X "kraft-sdlc[vector]==<version>"`, with
  the Python you installed Kraft with for `3.X` and the release for
  `<version>` (leave out `[vector]` if you don't use vector search), then
  `kraft admin restart`. That restart is 2.0's: it lists running items and
  asks before it ends their agents. `"$(uv tool dir)/kraft-sdlc/bin/python" -V`
  prints the Python Kraft runs on, and the `embeddings` line of
  `kraft admin health` says `unavailable (the 'vector' extra is not installed`
  when you don't have the extra.
- On a Homebrew install, run `brew upgrade kraft` once 2.0.0 is in the tap,
  then `kraft admin restart`. 1.4's `kraft admin update` runs the same
  `brew upgrade kraft`, and loses nothing: the formula has no `[vector]`
  extra.
- On a pipx install, run
  `pipx install --force --python python3.X "kraft-sdlc[vector]==<version>"`,
  then `kraft admin restart`. 1.4's `kraft admin update` doesn't update a pipx
  install: it puts a second Kraft beside it with uv.
- If you used 1.4's `kraft admin update` anyway, restart right after it.
  With `--restart` (or a service restart), 1.4 restarted the server without
  asking, which ended the agents of running items: pause them first (see
  [A restart ends running agents](#a-restart-ends-running-agents)). Without
  `--restart`, the 1.4 server keeps running and serves 2.0's interface,
  which misreads its board: items show under the wrong heading, and the
  footer names the new release. The board says so in a banner over it (from
  2.0.0; a 1.5.0rc14 or earlier interface did not), and `kraft admin doctor`'s
  `restart` row warns that the server runs a release older than the one
  installed. If Kraft ran on a Python other than uv's default, the board
  answers `Internal Server Error` instead until the restart: 1.4's update
  moved Kraft to another Python and deleted the files the running server
  serves, though its API still answers. Run `kraft admin restart` as soon as
  the update finishes, don't act on the board before it, and reinstall
  `[vector]` with the command above if you use vector search.
- 2.0 replaces the interface, and some pages moved. Old
  addresses still open the right page;
  [Where did a page go](/get-started/troubleshooting#where-did-a-page-go-and-why-does-my-theme-look-different)
  lists where each one went.
- On a network bind, 2.0 checks the address every browser uses
  to reach the board. 1.4 skipped that check over plain http, so your board
  may have worked at a name that isn't in `allowed_hosts`. After the upgrade,
  such a browser gets a page saying the name isn't allowed. Before you
  upgrade, add each exact name you use (no wildcards) on Settings › Access, or
  to `allowed_hosts` in `access.yaml`. `kraft admin doctor` warns when the
  bind is off loopback and the list is empty.
- **A tunnel or reverse proxy in front of a loopback-bound Kraft must send a
  loopback `Host`.** On a server bound to `127.0.0.1` (the default), 2.0
  answers 403 to every request whose `Host` header isn't `localhost`,
  `127.0.0.1` or `[::1]`, webhooks to `POST /api/triggers` and
  `GET /api/health` included. 1.4 checked only requests from a browser, and
  `allowed_hosts` doesn't apply on a loopback bind. If cloudflared, ngrok,
  Caddy or nginx forwards to Kraft, bind Kraft beyond loopback, with a
  password, and list the name in `allowed_hosts`: that is the one way the
  board works through it. For webhooks and scripts alone, the proxy can
  rewrite `Host` to `localhost` instead, but a loopback-bound Kraft asks a
  request from this machine for no password, so read
  [A proxy in front of a loopback bind](/guides/remote-access#a-proxy-in-front-of-a-loopback-bind)
  first.
- Cancel keeps the branch. In 1.4, Cancel in the web interface deleted the
  item's branch and worktree; now it keeps them. To delete them, run
  `kraft item abandon ID --yes`.
- A merge request closed without merging stops its item. In 1.4 the item
  kept waiting. Reopen the merge request from the item's page, retry, or
  cancel.
- You can't disconnect a repo while it has open items. `kraft repo
  disconnect` (and `DELETE /api/repos`) is refused with a 409 until each of
  the repo's items is done, cancelled or abandoned, paused and never-started
  ones included. In 1.4 it went through and left those items stranded.
- A repo entry with `test_command: ""` now means the repo has no tests. In
  1.4 such an entry stopped every item at `verify`; now its items pass
  `verify` without running a test. Before you upgrade, set a real test command
  on any such entry, or `enabled: false` to keep it from running. After the
  upgrade, `kraft admin doctor`'s `tests` row names each such entry.
- `agent_overrides` is now an object, not JSON text, wherever it appears:
  `kraft view show --json`, `kraft item approve --json` and every other
  `--json` answer that carries the item, the MCP tools' results, and
  `GET /api/work-items/{id}`. In the answers to an action, such as
  `kraft item approve --json`, `node_overrides` and `policy_override` are now
  objects too, as `kraft view show --json` already had them. If a script runs
  `json.loads` on one of them, read it as an object instead. Setting the
  override still works as in 1.4: `kraft item set-overrides` and
  `PATCH /api/work-items/{id}` replace the whole override.
- `budget_cap.cap_usd` in `kraft view show --json` is the cap that stops the
  item first: the lower of its own cap and its policy's item-wide
  `budget_usd`. Read `budget_cap.key` to tell which one it is.
- `kraft view events -f --json` prints one JSON object per line from the
  first line on, where 1.4 printed the backlog as an indented array.
- Action commands print one line. `kraft item approve`, `reject`, `pause`,
  `resume`, `retry`, `raise-budget`, `skip`, `complete`, `cancel`,
  `escalate` and `set-chain`, `kraft item resolve` and `reopen` (one line naming
  the thread), and `kraft item review approve` or `request-changes` at a
  pending gate, print what they did, not the item's fields (or, for a thread,
  its comments). A script that read those fields should use `--json`, which
  is unchanged.
- A review comment names a file inside the repository, and a suggestion goes
  on new-side lines. `kraft item comment`, the MCP tool `add_review_comment`
  and `POST /api/work-items/{id}/threads` refuse an absolute `--file` path, or
  one with `..`, with a `422`, and `kraft item comment --suggest` with
  `--side old` exits 2 (the API answers `422`), where 1.4 stored both.
- A model override that is not a model id is refused. `kraft item
  set-overrides`, `kraft item set-node-override`, `PATCH /api/work-items/{id}`
  and a retry that changes a task's model (`task_config.model`) answer one,
  such as `--model "my model"`, with a `422`, where 1.4 stored any text. One
  1.4 already stored now stops its item at the next launch instead of
  reaching the agent, and the reason names the command that clears it.
- Escalating an item a spend cap stopped is refused, and so is raising a cap
  to what the item has already spent. `kraft item escalate` (and `POST
  /api/work-items/{id}/escalate`) on an item any spend cap stopped, the daily
  cap included, answers `409` and points to the cap to raise, where 1.4 started
  an escalation that the same cap then stopped. `kraft item raise-budget`
  with a cap at or below what the item has spent answers `422`, where 1.4
  saved it and the item stopped again at once.
- A work item title is one line of plain text, and not blank. `kraft item
  create`, the MCP tool `create_work_item`, `POST /api/triggers` and `PATCH
  /api/work-items/{id}` refuse a title that is empty, only whitespace, holds a
  line break (a trailing one included), or holds a tab, an escape or another
  control character, with a `422`, where 1.4 filed or saved it (only a blank
  `PATCH` title was refused). If a webhook or script builds the title from
  text that can be empty or run over several lines, give it a fallback and
  send its first line, with the rest in `description`. A schedule's title (a
  `policy.yaml` cron trigger in 1.4), and **Duplicate** of an item 1.4 filed
  with one, is cleaned up instead of refused: the first line is the title and
  the rest goes to the top of the description, a tab becomes a space, other
  control characters are dropped, and a blank title takes the description's
  first line (a schedule with neither is skipped). `kraft view list` shows the
  first line of a title 1.4 stored with a line break, without its control
  characters.
- `kraft repo connect` on a repo that is already connected now changes it.
  In 1.4 it did nothing. Now it probes the repo again and saves what its
  entry left undecided: a test command where it has none and no test scopes,
  and a setup command where none is declared. That can enable a repo saved
  disabled for want of a test command. In a terminal it asks first; with
  `-y`, `--json` or no terminal it saves without asking. A script that
  re-runs connect to check a repo should run `kraft repo list` instead. Connect
  also refuses a repo with no commit yet, which 1.4 connected: commit its
  files first. `kraft admin doctor` names each entry 1.4 left without a test
  or setup command where 2.0 finds one, with the connect command
  that saves it.
- The 2.0 VS Code extension needs Kraft 2.0 or a later 2.x. VS Code updates
  the extension on its own, and against a 1.4 server it shows the board but
  disables every action: its status bar reads `Kraft (read-only)`, and it says
  "This extension (2.0.0) needs Kraft 2.0 or later; this server runs 1.4.0."
  when it connects. Update Kraft too. It works the other way as well: a 1.4
  extension, one with updates turned off or pinned, is read-only against a 2.0
  server. It says "Kraft 2.0.0 does not match this extension (1.4.0); actions
  are disabled until they match." when it connects, and "Kraft is read-only:
  the daemon's version does not match this extension" when you try an action,
  so update both.
- `kraft admin restart` with no server running exits 1 (1.4: 0). A script
  that runs it under `set -e` now stops there. `update --restart` is
  unchanged.
- The config directory is `$KRAFT_HOME/config/`, not `templates/`. The first
  start renames yours, every file in it as it was, once it holds the server's
  lock: started while the 1.4 server is still up, it exits "already running"
  and touches nothing. `templates` is left as a link to `config`, so a 1.4
  process still running (an MCP server under an agent) and a path in a
  script keep working. `KRAFT_CONFIG_DIR` names it; `KRAFT_TEMPLATES_DIR` is
  still read when the new one is unset, and one pointing at the old default
  is renamed with it, so a service unit or a shell written for 1.4 keeps
  working. Change it when you next touch that unit. A `config/` you made
  before the first start, such as the harness guide's `config/harnesses`,
  gets what it lacks moved in (an empty directory in `templates/` is
  removed); whatever both hold stays in `templates/`, and
  `kraft admin doctor`'s `config` row names both until you merge them. If a
  service unit or a shell sets `KRAFT_TEMPLATES_DIR` to the old default and
  you also made a `config/`, 2.0 refuses to start until you merge
  `templates/` into `config/` and remove it. A directory you point at
  anywhere else is never renamed. A `templates` that is a link to another
  directory (a dotfiles repo) is not renamed or merged either, and its files
  are not read, except a `harnesses/` directory in it, which stays read
  until a `config/harnesses` exists: the start prints a warning naming the target, and the `config`
  row warns the same, so set `KRAFT_CONFIG_DIR` to that target. `kraft admin
  doctor --json` names the row `config`, not `templates`.
- Three keys moved. The first start carries two of them, in the renamed home
  or in one you point at by hand: `policy.yaml`'s `triggers:` become
  `schedules:` in `intake.yaml`, and an `intake.yaml` `max_concurrent` moves
  to `policy.yaml` unless it already sets one. Each file a key moves between
  is rewritten, readable by you alone (`0600`); the rest of it keeps its
  comments and layout. A moved trigger takes its comments with it: the
  lines above it and the ones on its own lines. A comment line above
  `triggers:` itself stays in `policy.yaml`, even once every trigger has
  moved, when it sits over the next key: delete it by hand. A comment on
  the `max_concurrent` line is dropped. If keeping a file's comments would
  leave it unreadable, the start writes it without them, and its log says
  so. A trigger 2.0's schedule refuses (1.4 ignored an extra key such
  as `enabled: false`) stays in `policy.yaml`, still read and fired, and the
  rest move; doctor's `moved keys` row names the key that keeps each one there
  (the start's log names only the first). One whose `cron` names a value outside its field
  (`0 24 * * *`, `0 9 * * 8`), which 1.4 loaded and never ran, or a number
  in digits other than 0-9 (`²`, which 1.4 never ran, or `٣`, which it ran
  as 3), stays too and is skipped, with a warning,
  rather than refusing the file. Settings ›
  Auto-intake edits the schedules there, and `max_concurrent` is on
  Settings › Policy › Housekeeping. A repo entry's `default_chain_template`
  is `default_chain`, and `theme.yaml`'s `board.group_by: template` reads
  as `chain`. Every old place is still read, so a hand-written file stops
  nothing, except `max_concurrent` in `intake.yaml`: the server ignores it,
  with a warning, until the next start moves it to `policy.yaml`. `kraft
  admin doctor`'s `moved keys` row names each old place you still have.
- A schedule's day of week `7` is Sunday, as in cron. 1.4 accepted `7` and
  never fired it: a `0 9 * * 7` trigger that never ran in 1.4 fires every
  Sunday after the upgrade. Change or remove it first if that is not what
  you want. Ranges (`1-5`) and steps (`*/15`) work since 2.0.
- `kraft item set-chain` takes `--chain`; `--template` still works. The MCP
  tool `set_chain_template` is `set_chain`, with `chain` for `template`, and
  the old tool name no longer exists: an agent prompt or skill that names it
  needs the new one. `create_work_item` takes `chain` for `chain_template`.
  `POST /api/triggers` takes `chain`, and still reads `chain_template`. `POST`
  and `PATCH /api/repos` take `default_chain`, and still read
  `default_chain_template`. `kraft repo list --json`, `kraft repo connect
  --json`, the MCP tool `ensure_repo` and `GET /api/repos` answer
  `default_chain`, not `default_chain_template`.
- A `steering/` directory of `.md` files, which 0.x read and 1.x folded into
  `library.yaml` at the first start, is no longer read. Every 1.x start
  already folded it; a directory left over is only files. A 0.x home
  updated straight to 2.0 loses those files as steering: copy their text
  into `library.yaml`'s `steering:` by hand.
- Four `repos.yaml` keys an older Kraft wrote are not read: `default_model`
  (set a model per harness profile under `models:`), `submodules` (connect
  each submodule as an entry of its own), `default_root_merge_policy` (a
  workspace's `root_pointer_default`) and `allow_cross_repo`. A repo still
  carrying one loads, the server log names it once, and `kraft admin
  doctor`'s `keys` row warns, naming what replaced it. `gitlab_project` is
  still read as `forge: gitlab` and `project:`.
- `harnesses.yaml` agent profiles are written as `providers:` (per provider,
  `{model, effort}`), the shape Settings › Harnesses edits. The older `model:`
  map with one `effort` still loads.

### Upgrading from a 1.5.0 release candidate

The 1.5.0 release candidates, `1.5.0rc1` to `1.5.0rc14`, were the
pre-releases of 2.0; no 1.5.0 was released.

- On 1.5.0rc14, `kraft admin update` follows the release-candidate channel,
  so it moves to 2.0's candidates, and to 2.0.0 once that is out, and keeps
  `[vector]` and your Python. `kraft admin update --channel stable` waits for
  2.0.0.
- On 1.5.0rc13 it follows the release-candidate channel too, but installs
  without `[vector]` and on uv's default Python, as 1.4's does. Use the
  `uv tool install` command from [Upgrading from 1.4](#upgrading-from-14)
  instead, naming the release you want (such as `2.0.0`). Then run
  `kraft admin restart`.
- On an earlier candidate it compares against stable releases and says you
  are up to date. Use the same `uv tool install` command. Its
  `kraft admin update --channel rc` installs the candidate too, but drops
  `[vector]` and the Python as rc13's does.
- An update run by rc14 keeps the extra, but where uv had recorded no Python
  for Kraft (an install without `--python`, `install.sh`, or one that 1.4 or
  an earlier candidate updated), it records the exact interpreter it ran on,
  one Python patch release (`…/cpython-3.13.12-…/bin/python3.13`). Every later
  `kraft admin update` keeps it, so `uv python upgrade` leaves Kraft behind,
  and removing that patch release breaks `kraft`.
  `grep python "$(uv tool dir)/kraft-sdlc/uv-receipt.toml"` shows what uv
  recorded. If it is a path, run the `uv tool install --force --python 3.X …`
  command once to tie Kraft to the minor version.
- The VS Code extension on the Marketplace stays at 1.4 until 2.0.0 ships, and
  is read-only against a 2.0 release candidate. Install the
  `kraft-<version>.vsix` attached to the candidate's GitHub release with
  `code --install-extension kraft-<version>.vsix`.

What a candidate already did stays done. 2.0 migrates the database from the
schema the candidate left, copying it first as any upgrade does (every
candidate's schema, 51 at most, is older than 2.0's 52, so each one makes a
copy), and a
theme the candidate converted keeps its `theme.yaml.pre-1.5`
(`theme.yaml.pre-ux2` from rc5 to rc9). To roll back to 1.4 from there, you
need the database as 1.4 left it, schema 44: your own backup, or the copy Kraft
made when you first left 1.4, which is not the newest one. See step 3 of
[Rolling back from 2.0 to 1.4](#pin-or-roll-back-a-version).

### Upgrading from older releases

**From before the `kraft-sdlc` rename.** An older install can still hold a
`kraft` uv tool next to `kraft-sdlc`. `kraft admin update` then stops and names
the two commands that clear it:

```bash
uv tool uninstall kraft
uv tool install --force --reinstall kraft-sdlc
```

The reinstall is needed because the uninstall removes the `kraft` command both
packages share.

**From a 0.x install.** Read the
[1.0.0 changelog](https://github.com/itsOmidKarami/kraft/blob/main/CHANGELOG.md#100)
first. Finish or abandon in-flight items, and note that harness profile names
and the template layout changed.

### A restart ends running agents

Stopping Kraft stops every agent it is running, whether you run
`kraft admin stop`, `kraft admin restart` or `kraft admin update --restart`,
or restart the service. When Kraft starts again, each item whose agent was
running stops with
`reattach: running session, PID identity unconfirmed, no result (pid N is not alive)`,
and the board shows it as failed.

`kraft admin restart` and `kraft admin update --restart` list the active items
first and, in a terminal, ask before going on (`-y` skips the question).
`kraft admin stop` only lists them. The listing and the question are new in
2.0. `kraft admin update` runs in the release you have installed, so updating
from 1.4 runs 1.4's `update --restart`, which does neither. So upgrade when
nothing is running, or pause the running items first and resume them
afterwards:

```bash
kraft view list --all --status=active   # the items that may have an agent running
kraft item pause ID                     # for each of them
kraft admin update --restart
kraft item resume ID
```

An item that a restart already stopped needs only `kraft item retry ID`.

### Pin or roll back a version

`kraft admin update` only installs the newest release on a channel; it cannot
target a version. Install a specific version with the package manager instead.

**uv or script install.** Name the version, and the Python you run Kraft on
(`"$(uv tool dir)/kraft-sdlc/bin/python" -V` prints it):

```bash
uv tool install --force --python 3.X "kraft-sdlc==X.Y.Z"
```

Without `--python`, uv moves Kraft to its default Python. Add the extra if
you use vector search: `"kraft-sdlc[vector]==X.Y.Z"`. To stay on that
version, do not run `kraft admin update`; it moves you to the newest release
again.

**Homebrew.** The tap has one formula, which each release rewrites to the
newest version, so Homebrew cannot install an older one. `brew pin kraft` stops
`brew upgrade`, and with it `kraft admin update`, from moving the version you
have. To go back to an older release, `brew uninstall kraft` and install that
version with uv.

**What a rollback does to `$KRAFT_HOME`.** Starting a newer Kraft migrates
`run/orchestrator.db` forward in place, and there is no downgrade migration.
An older Kraft refuses to start on a database a newer one migrated
(`database schema vN is newer than code vM`, in `run/logs/server.log`). So
[back up `run/orchestrator.db`](/guides/operations#back-up-the-database)
before you upgrade, and restore that backup when you roll back. If you have
none, restore the copy Kraft made before migrating, the newest
`run/orchestrator.db.pre-v<N>-*` whose schema is the older version's (see
[The copy Kraft makes before an upgrade](/guides/operations#the-copy-kraft-makes-before-an-upgrade)). `run/index.db`
needs nothing: an older Kraft rebuilds a search index it cannot read.
A rollback does not undo what a newer version changed in the config
directory: what 2.0 moved, you move back by hand (the steps below), and
`kraft admin templates lint` after a rollback checks the older version still
accepts the chains. If you install an older version while the newer server
still runs, the web UI says **An older Kraft is installed** and points here,
rather than telling you to restart.

**Rolling back from 2.0 to 1.4.**

1. Stop Kraft with `kraft admin stop`. If Kraft runs as a
   [service](/guides/operations#run-kraft-as-a-service), run
   `kraft admin uninstall-service` instead: the service manager starts a
   stopped server again, and the next step must not run under a live one.
2. Install 1.4 with the Python you run Kraft on and the extra you have:
   `uv tool install --force --python 3.X "kraft-sdlc[vector]==1.4.0"` (leave
   out `[vector]` if you don't use vector search).
3. Restore the database: put your backup, or the copy Kraft made when you
   first left 1.4, in place as `run/orchestrator.db`, and delete any
   `orchestrator.db-wal` and `orchestrator.db-shm` beside it. Kraft's copy is
   the newest `run/orchestrator.db.pre-v*` whose schema is 44, 1.4's. If you
   went straight from 1.4 to 2.0 that is the newest `pre-v52-*`, but if you
   ran a release candidate on the way it is an older one (`pre-v49-*`,
   `pre-v50-*` or `pre-v51-*`, from the first candidate you ran), and the
   newest holds the candidate's schema, which 1.4 refuses. If the first
   candidate you ran was 2.0.0rc9 or later, it already ran schema 52, so its
   `pre-v52-*` copy is 1.4's and 2.0 made none. Print each
   copy's schema (both commands read `$KRAFT_HOME` when you set one):

   ```bash
   for f in "${KRAFT_HOME:-$HOME/.kraft}"/run/orchestrator.db.pre-v*; do echo "$(sqlite3 "$f" 'PRAGMA user_version') $f"; done
   ```

   No `sqlite3` command? Python prints the same:

   ```bash
   python3 -c 'import glob, os, sqlite3; home = os.environ.get("KRAFT_HOME") or os.path.expanduser("~/.kraft"); [print(sqlite3.connect(f"file:{f}?mode=ro", uri=True).execute("PRAGMA user_version").fetchone()[0], f) for f in sorted(glob.glob(os.path.join(home, "run", "orchestrator.db.pre-v*")))]'
   ```

   No copy prints `44` when you upgraded to a candidate before rc12, which
   made none: only a backup you took yourself rolls back then. See
   [Back up the database](/guides/operations#back-up-the-database) for the
   steps.
4. Check the config directory: 1.4 reads `~/.kraft/templates` (under
   `$KRAFT_HOME` if you set one). 2.0's first start renamed it to `config`
   and left `templates` as a link to it, which 1.4 follows, so there is
   nothing to do while that link is there. If it is gone, rename the
   directory back, `mv ~/.kraft/config ~/.kraft/templates`: when 1.4 finds no
   `templates/` it seeds a fresh default home beside yours, with no repos, a
   default policy and no `access.yaml`. If `templates` is a directory, not a
   link, 2.0 found a `config/` you had made and could not merge the two
   (`kraft admin doctor`'s `config` row named both): move what `templates/`
   still holds into `config/`, keeping the copy you want of each, then
   `rm -r ~/.kraft/templates && ln -s config ~/.kraft/templates`. A
   directory you point `KRAFT_CONFIG_DIR` at was never renamed; point 1.4's
   `KRAFT_TEMPLATES_DIR` at it instead.
5. Move the schedules back. 1.4 reads them as `triggers:` in `policy.yaml`,
   not `schedules:` in `intake.yaml`; the entries have the same shape, so
   cut the list from `intake.yaml` and paste it under a `triggers:` key in
   `policy.yaml`. Add the key yourself: 2.0 removed it once every trigger had
   moved, and the `# triggers:` in a seeded file is a commented example, so
   pasting under that line breaks the file (1.4 then refuses every new item).
   If some triggers stayed in `policy.yaml`, paste under the key that is
   there. 1.4 reads a `cron` field only as `*` or a comma list of
   numbers: before you paste, write a range or a step as that list (`1-5` as
   `1,2,3,4,5`, `*/15` as `0,15,30,45`), or 1.4 refuses the whole
   `policy.yaml` and then every new item; and write a day of week `7` as `0`,
   or 1.4 loads it and never fires it. Then delete the `schedules:` key
   itself from `intake.yaml`, even an empty `schedules: []`: 1.4 refuses an
   `intake.yaml` that has one, and its auto-intake then stays off while
   `kraft admin health` says ok.
   Delete `forge_poll_s` from `policy.yaml` too, if you set it: 1.4 rejects
   the file and then refuses every new item (`policy config invalid,
   refusing work`). `max_concurrent` in `policy.yaml` needs nothing: 1.4
   reads it there.

   In `repos.yaml`, 1.4 reads a repo's chain only as
   `default_chain_template`. It skips `default_chain`, so the repo files on
   `default` and doctor's `keys` row fails. Rename each `default_chain:` to
   `default_chain_template:`. Where an entry has both keys (2.0 can save the
   new one beside the old), put `default_chain`'s value, the one 2.0 used, in
   `default_chain_template`, then delete the `default_chain` line, so no
   entry ends with both.

   In `harnesses.yaml`, a profile saved on 2.0's Settings › Harnesses is
   written as `providers:`, which 1.4 refuses, and with it the whole file.
   Rewrite each such profile in 1.4's shape, one `model:` map by provider
   and one `effort:` for all of them:

   ```yaml
   # 2.0
   strong:
     providers:
       claude: { model: sonnet, effort: high }
       codex: { model: gpt-5.6-terra, effort: high }
   # 1.4
   strong:
     model: { claude: sonnet, codex: gpt-5.6-terra }
     effort: high
   ```

   1.4 has one `effort` per profile: where the providers set different ones,
   pick one. A profile already in the `model:` shape needs nothing.
6. Copy `~/.kraft/templates/theme.yaml.pre-2.0` over
   `~/.kraft/templates/theme.yaml` (under `$KRAFT_HOME` if you set one). If a
   1.5.0 release candidate converted the theme first, the copy is
   `theme.yaml.pre-1.5` instead (`theme.yaml.pre-ux2` if that was any of
   rc5 to rc9). 1.4's interface takes its colours from `palette`, which 2.0
   removed, so without the copy it shows its default colours. The copy is your
   theme from the first upgrade past 1.4, and is never replaced: if you rolled
   back before and changed the theme on 1.4, set it again in 1.4's Settings.
   With no copy, check `theme.yaml` for `group_by: chain`, which 2.0 writes
   when the board is grouped by chain, and change it to `group_by: template`.
   Also look for an `editor:` line, which 2.0 writes when you pick a Default
   editor in Settings › Appearance, and delete it. Or delete the file. 1.4
   refuses both, and its board then loads no theme.
7. Start Kraft with `kraft admin start --detach`, or
   `kraft admin install-service` if it ran as a service, then run
   `kraft admin templates lint`.

Restoring the backup loses everything done on 2.0 since you took it: items
filed, runs, approvals and their history. It does not remove what those runs
made outside the database. Their worktrees under `run/worktrees/`, their
branches, and any merge requests they opened are still there, and 1.4 knows
nothing about them. `kraft admin doctor`'s `worktrees` row lists a worktree
with no work item; delete the ones you do not need, and close any merge
request yourself. 1.4's row also lists the worktrees of items you cancelled
on 1.4, which its board does not show. A worktree made on 2.0 is one whose id
is not in the database you restored:
`sqlite3 run/orchestrator.db "select id from work_items"` lists those.

## Uninstall

```bash
uv tool uninstall kraft-sdlc   # uv or script install
brew uninstall kraft           # Homebrew install
```

Neither removes `$KRAFT_HOME`. Delete that directory yourself to discard all
Kraft state.

## Where state lives

Kraft keeps state in `$KRAFT_HOME` (default `~/.kraft`):

| Path | Holds |
|---|---|
| `~/.kraft/run/` | `orchestrator.db`, `index.db`, `logs/`, `results/`, `worktrees/`, `attachments/`; `orchestrator.db.pre-v<N>-<time>` after each upgrade that migrated the database |
| `~/.kraft/config/` | The YAML the Templates and Settings screens edit: `library.yaml` and `chains/` (the templates), `harnesses.yaml`, `policy.yaml`, `repos.yaml`, `intake.yaml`; `access.yaml` and `notify.yaml` appear once you save those Settings screens. `templates/` before 2.0 |

`config/` is seeded from the packaged defaults on first run and never
overwritten after, so an upgrade cannot clobber an edited policy: 2.0's
first start only moves the keys [Upgrading from 1.4](#upgrading-from-14)
lists. It is a plain
directory of files, so you can diff it, revert it, or `git init` it.

To reach the board from another device, see [Remote access](/guides/remote-access).

A second, fully separate instance needs its own `KRAFT_HOME` and its own port.
See [Run two instances](/guides/operations#run-two-instances). For backups,
logs and disk use, see [Operate a Kraft server](/guides/operations).
