Questions that come up before and after a first [work item](/concepts/vocabulary#work-item).

## Does Kraft work only with GitHub?

No. Kraft opens and merges changes on GitHub through `gh` and on GitLab
through `glab`. A GitHub or GitLab repo can instead use a `client: api` account in
[forges.yaml](/reference/configuration/forges), which needs no `gh` or `glab`. A repo's
[forge](/concepts/vocabulary#forge) is recorded when you connect it, from its `origin`.

## Can I use it without Claude Code?

Partly. Kraft ships seven [harnesses](/reference/harnesses): Claude, Codex,
Cursor, OpenCode, Gemini, Antigravity and Amp. Every agent task in the shipped
chains names Claude, so to run without it you change each task's `harness:`.
See [Switch a task to another harness](/guides/harnesses/switch-harness).

Any agent that speaks MCP can drive Kraft with `kraft admin mcp`, and any shell
can use the `kraft` command.

## What does it cost?

Kraft is free and Apache-2.0 licensed. Your agent provider bills you for the
sessions Kraft runs, and a fresh install caps that spend per work item and per
day. [The default caps](/reference/configuration/policy#the-default-caps) has the
amounts.

## Does it run on Windows?

No. Kraft supports macOS and Linux. WSL is untested. See
[Supported platforms](/project/status-and-support#supported-platforms).

## What makes a good spec?

Start with a good description: it is the brief the spec is written from, and
the title is only a label. A good spec names:

- the problem, in the repo's own terms;
- the approach, and the options you rejected;
- what is out of scope;
- the tests that prove it.

If you already have a spec or plan, attach it with
`kraft item create --spec PATH --plan PATH`, and Kraft skips writing and
approving it again. The rules for `PATH` are in
[Attach a spec or plan](/reference/cli/item#attach-a-spec-or-plan).

A spec kept outside the repo, such as in `~/notes`, is refused with
`attachment path escapes the repo`. Copy it in, for example to
`.engineering/specs/`, and give that path.

## How do I share my chains with my team?

_Added in 2.1_

Publish them as a [Kraft add-on](/concepts/vocabulary#add-on) in a git
repository. Each person adds that repository as a
[collection](/concepts/vocabulary#collection) with
`kraft admin addon collection add owner/repo`, then installs the add-on with
`kraft admin addon install ADDON@COLLECTION`. Kraft prints what the add-on
changes and installs it only after you accept. [Share chains with
add-ons](/guides/customize/share-chains-with-addons) covers both sides.

For anyone else's add-on, ask whoever published it for its address. Kraft's
own repository is a collection too, with its shipped chains and variants of
them: see [Install Kraft's own add-ons](/guides/customize/share-chains-with-addons#install-krafts-own-add-ons).
A [collection](/concepts/vocabulary#collection) is a git repository or directory
with a `.kraft/collection.json`.

## Is it safe to install an add-on?

_Added in 2.1_

An [add-on](/concepts/vocabulary#add-on) can't run a command, grant
a permission or define a harness, and Kraft refuses one that tries.
It does decide what the agent is told and which gates, models and limits its
chains have, so read the review before you accept an install or an update.
Auto-update is off unless you turn it on.
[Security](/project/security-in-depth#kraft-add-ons) says what an add-on can and can't
change.

## Kraft or Kraft Lite?

Use Kraft when work should run without you watching, in its own [worktree](/concepts/vocabulary#worktree),
across sessions and restarts, with a board and caps. Use
[Kraft Lite](/guides/kraft-lite) when you want the same chain and gates inside
one agent session, with no server to run.

## Can I approve each tool call myself?

No. A [worker](/concepts/vocabulary#worker) runs unattended, and Kraft's [permission gate](/reference/permissions)
answers each tool call from the task's [policy](/concepts/vocabulary#policy), never by asking a person. To
control what a worker may do:

- set `allowed_tools`, `deny_tools` and `grants`;
- run it in a [sandbox](/reference/configuration/sandbox);
- review its work at the gates between nodes.

## How do I uninstall Kraft?

Uninstalling removes the `kraft` command and nothing else, so stop what runs
first, while the command exists. Stop a running server:

```bash
kraft admin stop
```

If you installed a service, remove it too:

```bash
kraft admin uninstall-service
```

`uninstall-service` deletes the launchd agent or the systemd unit, and a systemd
drop-in you made stays. [Run Kraft as a service](/guides/run/run-as-a-service#remove-the-service)
says what to save before you remove it. Then remove Kraft with the command for
how you installed it:

| Installed with | Run |
|---|---|
| uv or the script | `uv tool uninstall kraft-sdlc` |
| Homebrew | `brew uninstall kraft` |

Two things are left:

- **Claude Code's registration.** Remove the plugin with
  `claude plugin uninstall kraft`. If you ran `kraft admin init` instead, remove
  its registration with `claude mcp remove --scope user kraft`, and delete the
  skill files it wrote under `~/.claude/skills/kraft/`. Another agent you
  registered keeps its registration: [Use Kraft from your agent](/guides/day-to-day/agent-integration)
  covers each one.
- **`$KRAFT_HOME`** (default `~/.kraft`), where Kraft keeps its state. Delete that
  directory yourself to discard it.

uv itself, and a Python it fetched for Kraft, stay too: they are uv's, and
`uv python uninstall` removes a Python.

`config/` holds the YAML you edit, a plain directory you can diff, revert or
`git init`: see [Configuration](/reference/configuration). `run/` holds the
databases, logs, [worktrees](/concepts/vocabulary#worktree) and attachment
copies: see [Secrets and state](/project/data-and-privacy#secrets-and-state). A
second, fully separate instance needs its own `KRAFT_HOME` and its own port: see
[Run two instances](/guides/run/run-as-a-service#run-two-instances).
