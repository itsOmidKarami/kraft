title: Your first work item
description: Start Kraft, connect a repo, run a work item end to end, and approve its gates.

Start Kraft, connect a repo, run a work item end to end, and approve the gates
that stand in its way. A
[work item](/concepts/vocabulary#work-item) runs through a
[chain](/concepts/vocabulary#chain) of nodes, and some nodes are
[gates](/concepts/vocabulary#gate) where you decide.

Steps 1 to 5, on the `quick-task` chain, take about fifteen minutes, most of it
spent waiting on an agent. Steps 6 and 7 run the `default` chain to a merged
pull request. They take longer, because they wait for your approvals, CI, and
the [forge](/concepts/vocabulary#forge).

## Before you start

You need:

- Kraft installed, with a git identity set and Kraft registered with Claude Code
  (the plugin, or `kraft admin init`), and Claude Code logged in. See
  [Install](/get-started/install).
- A git repo to work on, with at least one commit (`git log -1` shows it: a work
  item's branch starts from one) and a committed `.gitignore` covering build
  output and caches (`__pycache__/`, `node_modules/`, `target/` and the like).
  After each agent task, Kraft commits every file the agent left in the [worktree](/concepts/vocabulary#worktree)
  that git does not ignore.
- A git identity in that repo: `git config user.name` and
  `git config user.email` both print a value there. If the repo overrides the
  identity [Install](/get-started/install#before-you-start) checked, check it
  again here.
- A test command for the repo. Step 2 has Kraft propose one.

::note{title="Doing this from Claude Code instead"}
Step 2 recommends `/kraft:onboard`. Steps 3 to 7 have slash commands as well:
`/kraft:handoff` to file work, `/kraft:board` to see it, `/kraft:gates` to
approve. See [Use Kraft from your agent](/guides/day-to-day/agent-integration).
::

## 1. Start the server

If the server you started in [Install](/get-started/install#start-the-server)
is still running, go to step 2. Otherwise:

```bash
kraft
```

```text
kraft: http://127.0.0.1:8765
```

Leave that running: it is the server, in the foreground. Open that address. With
no repo connected yet, the board shows **Nothing on the board yet** and three
setup steps. [The setup wizard on first start](/guides/day-to-day/first-run) describes them; step 2
does the same job from a terminal or your agent. Open a second terminal for
everything that follows.

You know it worked when the address opens the board. If `kraft` refuses to start,
see [Kraft won't start: port already in use](/troubleshooting/starting-and-reaching-kraft#kraft-wont-start-port-already-in-use).

## 2. Connect a repo

Connect it from your coding agent, or from a terminal.

### From your agent (recommended)

Open a Claude Code session in the repo you want Kraft to work on. This needs the
Kraft plugin from [Install](/get-started/install#claude-code):

```bash
cd ~/code/my-project
claude
```

Then, in the session:

```text
/kraft:onboard
```

Follow what it asks. It connects the repo and makes sure Kraft knows how to set
it up and run its tests, so your first work item doesn't stop on a wrong guess.
The plugin also registers Kraft's MCP server with Claude Code, so there is no
`kraft admin init` step on this path.

### From a terminal

Without the plugin, register Kraft with Claude Code once, then connect the repo
from the repo's directory:

```bash
kraft admin init   # once per machine; required without the plugin
cd ~/code/my-project
kraft repo connect
```

Kraft reads the repo's own task runner, lockfiles and CI config to propose two
commands: how to prepare a fresh checkout (`setup_command`) and how to run the
tests (`test_command`). It says which commit it read, prints each command with
the file it came from, and lists the other candidates it found:

```text
connected: /home/you/code/my-project
  read from origin/main, where work items start
test command: uv run pytest (from uv.lock)
setup command: uv sync (from uv.lock)
```

The `read from` line names `HEAD` instead when the repo has no `origin`. In a
terminal, Kraft asks first, before it prints anything else, when it found more
than one candidate for a command or none:

- Enter keeps the proposal (or leaves the command unset).
- A number picks a candidate.
- `-` means none.

You know it worked when `kraft repo list` shows the repo, with `enabled` in the
STATE column and a `*` in the first column when you are standing in it:

```bash
kraft repo list
```

```text
   NAME        STATE    CHAIN    PATH
*  my-project  enabled  default  /home/you/code/my-project
```

To check the two commands before your first item does, run
`kraft repo connect --verify`. It runs both once in a throwaway worktree, and
ends with `verify: passed`, or with
`verify: failed -- fix the entry in repos.yaml and run again` and exit 1.

Change them in Settings › Repos, then **Review & publish** (or in
`~/.kraft/config/repos.yaml`). If the repo needs no preparation, tick
**No setup needed** there, then **Review & publish** (or set
`setup_command: ""`). See [repos.yaml](/reference/configuration/repos) for every
field.

### If connect finds no test or setup command

`kraft repo connect` says so when it does. Neither stops the connect, and each
stops a work item later if you leave it.

- **No test command.** Kraft saves the repo with `enabled: false` (see
  [`enabled`](/reference/configuration/repos#enabled)), and an item on it stops
  at its test node (`verify` on `quick-task`, `verification` on `default`) with
  nothing to run. Run `kraft repo connect --test-command "..."`, or `--no-tests`
  for a repo with none (`""`). Or set it in Settings › Repos and **Review &
  publish**: an edit there is a draft until you do.
- **No setup command.** The repo's first work item stops at once, before its
  first node, and the stop names the missing `setup_command`. Set one in
  Settings › Repos, or tick **No setup needed**.
- **A `pyproject.toml` with no lockfile** gets no guess: see
  [A Python project with no lockfile](/reference/configuration/repos/connect-proposals#a-python-project-with-no-lockfile).

[When connect finds no command](/reference/configuration/repos/connect-proposals#when-connect-finds-no-command)
has the full case list. A stopped item is in
[`no setup_command declared`](/troubleshooting/why-did-my-item-stop#no-setup_command-declared)
and [`declares neither test_scopes nor test_command`](/troubleshooting/why-did-my-item-stop#declares-neither-test_scopes-nor-test_command).
How Kraft proposes the commands is in
[How connect proposes commands](/reference/configuration/repos/connect-proposals).

## 3. File your first work item

The `quick-task` chain has no gates, which makes it good for confirming the
pipes are connected:

```bash
kraft item create "fix the flaky import test" --chain quick-task \
  --description "It's the datetime import, not the fixture."
```

It prints the new item. Copy its `id`:

```text
id            9d0ab38ff3c9439b90506df0f6966660   <- the ID
status        paused
title         fix the flaky import test
bead_warning  bd is not installed: [Errno 2] No such file or directory: 'bd'
```

You can list IDs again any time with `kraft view list`.

`bead_warning: bd is not installed` means Kraft could not file a matching
[beads](https://github.com/gastownhall/beads) issue. Beads is optional; the work
item is filed and runs the same without it, so you can ignore the line.

The item lands **paused**, because `item create` starts nothing unless you add
`--autostart`. Nothing has spent a token yet.

You know it worked when the item's status is `paused`. If the command is
refused because the repo is not connected, run step 2 first.

## 4. Start it, and watch

Replace `ID` with the one you copied. `resume` takes the item's ID, which you
can leave off only when you run the command inside that item's worktree.

```bash
kraft item resume ID   # the CLI twin of Start in the board's side panel
```

`resume` answers with the item it started:

```text
started 9d0ab38ff3c9439b90506df0f6966660
```

To watch it work, open the board in your browser, or run `kraft view watch` in a
third terminal. `watch` takes no ID, redraws a live board on every event, and
holds its terminal until you press Ctrl-C. The web board looks like this:

![The Kraft board: work items grouped by Needs you, Running, Not started, and Done](/assets/board.png)

The [Web UI](/reference/web-ui) reference describes each screen in the picture.

`quick-task` runs `implementation`, then `verify`, with no gate. If the agent's
fix is good, the item reaches **Done** on its own. `verify` runs the repo's own
`test_scopes` or `test_command` from `repos.yaml`. If a test fails, the item
stops and waits for you. Its stop reason names the failing command and its
scope, and `kraft view logs ID` shows that command's output.

When it is done, `kraft view list` shows the item with the status `completed`
(the NODE column is the last node it entered):

```text
ID                                STATUS     GATE  NODE    TITLE
9d0ab38ff3c9439b90506df0f6966660  completed  -     verify  fix the flaky import test
```

You know it worked when the board shows the item under **Done**, and
`kraft view list` shows its status as `completed`. A failure shows as
`needs_human`, under **Needs you**: see [Troubleshooting](#troubleshooting)
below.

## 5. Where is my change?

`quick-task` opens no pull request: the change stays on the item's own branch,
in its worktree. To see it:

```bash
kraft view diff ID     # the change, against the base branch
kraft repo path ID     # the worktree's path; cd "$(kraft repo path ID)" to go there
kraft repo open ID     # open the worktree in your default editor (Settings, else $KRAFT_EDITOR, else the OS default app); --editor code|cursor|zed|obsidian|system picks one
```

Merge the branch yourself, or run the next piece of work on `default`, which
opens and merges a pull request for you.

You know it worked when `kraft view diff ID` prints the agent's change.

## 6. Try the real chain, and its gates

`default` opens and merges a pull request through your forge. Steps 1 to 5 work
without any of this; before you start `default`, the repo needs:

- **A GitHub or GitLab remote, with `gh` or `glab` logged in.**
- **CI that runs on pull requests.** Kraft waits for the merge request's checks
  to pass. On GitHub, a pull request with no checks at all reads as "no checks
  yet" and stays pending, so `merge_request_feedback` waits until its 90-minute
  cap and then stops and waits for you. A repo with no CI can set
  `ci_checks: false` on its entry in
  [`repos.yaml`](/reference/configuration/repos) to skip both CI waits, before
  and after the merge.
- **A review rule only if you can meet it.** `external_approval` waits while a
  branch rule requires an approving review. GitHub does not let you approve your
  own pull request, so on a solo repo with such a rule it waits until you remove
  the rule or someone else approves. With no such rule it passes straight away,
  so a solo developer needs nothing here.

Check the forge first:

```bash
kraft admin doctor
gh auth status
```

`gh auth status` (or `glab auth status`) reports you as logged in. In the
doctor output, the repo's `forge` row reads like this:

```text
ok    forge my-project  github · gh
```

It fails if `gh` or `glab` is missing, or if the repo had no GitHub or GitLab
`origin` when you connected it. For the second, set `forge: github` or
`forge: gitlab` on the repo in Settings › Repos and **Review & publish** (or in
`repos.yaml`). For a waiting item, see
[Waiting on CI or a review](/troubleshooting/why-did-my-item-stop#waiting-on-ci-or-a-review).

`default` is the chain most work runs on, and the default for `--chain` unless
the repo sets `default_chain`, so you can leave the flag off here:

```bash
kraft item create "add a --dry-run flag to the sync command"
kraft item resume ID   # use the new item's ID, not the first one
```

Before any code is written it stops at three gates, one after another:
`spec_approval`, then `plan_approval`, then `chain_revision_approval`. The last
is about the chain itself: an agent checks the approved spec and plan against
the nodes still to run and proposes changes to them, and when it proposes none,
which is usual, the gate passes without asking you. Each gate shows up under
*Needs you* on the board. Open one to read the document it is about:

![A spec an agent wrote, rendered on the item's review page and waiting for your approval, with Request changes and Approve](/assets/gate.png)

```bash
kraft view artifact ID     # read the document the gate is about
kraft item approve ID      # or Approve at the gate, on the item's page
```

`approve` names the gate it approved and says where the item is now:

```text
approved spec_approval on 9d0ab38ff3c9439b90506df0f6966660; the item is now running
```

To send it back instead, run `kraft item reject ID --note "..."`, or use
**Reject…** at the gate on the item's page. The node that wrote the document
runs again with your note. **Request changes** on the review page, the button in
the picture, sends the gate back the same way, with your summary and review
threads as the note: it is `kraft item review ID request-changes`, and
[Reviewing a change](/guides/day-to-day/review-a-change) covers it.

You know it worked when, after your last approval, the item moves out of
*Needs you* and into *Running*, and the board shows implementation started.
Implementation and tests take a while: the item comes back under *Needs you* at
`local_review`, which is step 7.

## 7. Review before it merges

After implementation and verification, the item stops at `local_review`, and
later at `final_review`. Each comes with a diff to read first:

```bash
kraft view diff ID --stat   # how big it is
kraft view diff ID          # the full diff
```

Kraft commits after every task, so by a gate the change is already on the
item's branch. The diff opens with **the change under review**: every commit
since the base, the item's spec and plan documents among them. Below it,
**uncommitted** lists whatever an agent left in the worktree without
committing. "(nothing uncommitted)" there is normal, not an empty review.

Approve `local_review` and Kraft opens a draft merge request and runs CI and
automated review on it. Approve `final_review` and it marks the request ready,
waits for the merge request's external approval on your forge, then merges.

```bash
kraft item approve ID   # at each gate, once you have read the diff
kraft view list         # shows the item's status
```

Each `approve` prints a line like that, naming the gate it approved. You know it worked
when `kraft view list` shows the item's status as `completed` and the merge
request shows as merged on your forge. If it stays under *Needs you* at a gate
you approved, or at a later one, see [Troubleshooting](#troubleshooting).

What each gate does, and how caps and waits bound the chain, is in
[How a work item runs](/concepts/how-a-work-item-runs).

## Troubleshooting

An item that stops shows under **Needs you** with a reason. Read it with
`kraft view show ID`, then the log of the session that stopped it with
`kraft view logs ID`, then check the install with `kraft admin doctor`. In
Claude Code, `/kraft:triage` does this for you, and offers to retry, raise a cap,
or hand the item back to you.

[Troubleshooting](/troubleshooting) maps every stop reason to its fix. These four
are the ones a first run most often hits:

| It stops with | The fix is in |
|---|---|
| `... nothing registers it for Claude Code ...`, at its first agent step with 0 tokens spent. | [A task Kraft would not launch](/troubleshooting/why-did-my-item-stop#a-task-kraft-would-not-launch) |
| `no setup_command declared for <repo> in repos.yaml ...`, before its first node runs. | [`no setup_command declared`](/troubleshooting/why-did-my-item-stop#no-setup_command-declared) |
| A config error at its test node: the repo declares neither `test_scopes` nor `test_command`. | [`declares neither test_scopes nor test_command`](/troubleshooting/why-did-my-item-stop#declares-neither-test_scopes-nor-test_command) |
| `kraft admin doctor` fails its `agent: claude` row. | [The agent row and the service PATH](/troubleshooting/doctor-failures#the-agent-row-and-the-service-path) |
