title: Your first work item
description: Start Kraft, connect a repo, and run a work item on the quick-task chain until it lands on the board.

**Part 1 of 2.** A [work item](/concepts/vocabulary#work-item) runs through a
[chain](/concepts/vocabulary#chain) of nodes. Here you run one on `quick-task`,
the shortest chain: it has no gates, and takes about fifteen minutes, most of
it spent waiting on an agent. [Part 2](/get-started/the-real-chain) runs the
`default` chain to a merged pull request.

## Before you start

You need:

- Kraft installed, with a git identity set and Kraft registered with Claude Code
  (the plugin, or `kraft admin init`), and Claude Code logged in. See
  [Install](/get-started/install).
- A git repo to work on, with at least one commit (`git log -1` shows it: a work
  item's branch starts from one) and a committed `.gitignore` covering build
  output and caches (`__pycache__/`, `node_modules/`, `target/` and the like).
  After each agent task, Kraft commits every file the agent left in the [worktree](/concepts/vocabulary#worktree)
  that git does not ignore.
- A git identity in that repo: `git config user.name` and
  `git config user.email` both print a value there. If the repo overrides the
  identity [Install](/get-started/install#before-you-start) checked, check it
  again here.
- A test command for the repo. Step 2 has Kraft propose one.

::note{title="Doing this from Claude Code instead"}
Step 2 recommends `/kraft:onboard`. Steps 3 to 5 have slash commands as well:
`/kraft:handoff` to file work and `/kraft:board` to see it. See
[Use Kraft from your agent](/guides/day-to-day/agent-integration).
::

## 1. Start the server

The server you started in [Install](/get-started/install#start-the-server)
must still be running, in its own terminal. If it is not, start it again with
`kraft`, which prints `kraft: http://127.0.0.1:8765`, and leave it running. With no repo connected yet, the board shows three
setup steps: [the setup wizard on first start](/guides/day-to-day/first-run)
describes them, and step 2 does the same job from a terminal or your agent. Do
everything that follows in a second terminal.

You know it worked when `http://127.0.0.1:8765` opens the board. If `kraft` refuses to start,
see [Kraft won't start: port already in use](/troubleshooting/starting-and-reaching-kraft#kraft-wont-start-port-already-in-use).

## 2. Connect a repo

Connect it from your coding agent, or from a terminal.

### From your agent (recommended)

Open a Claude Code session in the repo you want Kraft to work on. This needs the
Kraft plugin from [Install](/get-started/install#claude-code):

```bash
cd ~/code/my-project
claude
```

Then, in the session:

```text
/kraft:onboard
```

Follow what it asks. It connects the repo and makes sure Kraft knows how to set
it up and run its tests, so your first work item doesn't stop on a wrong guess.
The plugin also registers Kraft's MCP server with Claude Code, so there is no
`kraft admin init` step on this path.

### Or from a terminal

<!-- renamed from: From a terminal -->

No agent session? Connect from a terminal instead. The rest of this page works
the same either way.

Registered Kraft with Claude Code in [Install](/get-started/install#claude-code)?
Skip that: it is once per machine. If not, do it there first. Then connect the
repo from the repo's directory:

```bash
cd ~/code/my-project
kraft repo connect
```

Kraft reads the repo's own task runner, lockfiles and CI config to propose two
commands: how to prepare a fresh checkout (`setup_command`) and how to run the
tests (`test_command`). It says which commit it read, prints each command with
the file it came from, and lists the other candidates it found:

```text
connected: /home/you/code/my-project
  read from origin/main, where work items start
test command: uv run pytest (from uv.lock)
setup command: uv sync (from uv.lock)
```

The `read from` line names `HEAD` instead when the repo has no `origin`. In a
terminal, Kraft asks first, before it prints anything else, when it found more
than one candidate for a command or none:

- Enter keeps the proposal (or leaves the command unset).
- A number picks a candidate.
- `-` means none.

To check the two commands before your first item does, run
`kraft repo connect --verify`. It runs both once in a throwaway worktree, and
ends with `verify: passed`, or with
`verify: failed -- fix the entry in repos.yaml and run again` and exit 1.
A test that fails in the repo itself ends the same way, with the entry
right.

Change them in Settings › Repos, then **Review & publish** (or in
`~/.kraft/config/repos.yaml`). If the repo needs no preparation, tick
**No setup needed** there, then **Review & publish** (or set
`setup_command: ""`). See [repos.yaml](/reference/configuration/repos) for every
field.

#### If connect finds no test or setup command

`kraft repo connect` says so when it finds no test command or no setup command.
Neither stops the connect, and each stops the repo's first work item if you leave it. With no test command Kraft saves the repo with `enabled: false`, so `kraft repo list` shows it as `disabled` below. See
[`declares neither test_scopes nor test_command`](/troubleshooting/stop-reasons-in-detail#declares-neither-test_scopes-nor-test_command)
and [`no setup_command declared`](/troubleshooting/stop-reasons-in-detail#no-setup_command-declared).
[When connect finds no command](/reference/configuration/repos/connect-proposals#when-connect-finds-no-command)
has the cases, including a `pyproject.toml` with no lockfile.

### Check that the repo is connected

On either path, you know it worked when `kraft repo list` shows the repo, with `enabled` in the
STATE column and a `*` in the first column when you are standing in it:

```bash
kraft repo list
```

```text
   NAME        STATE    CHAIN    PATH
*  my-project  enabled  default  /home/you/code/my-project
```

## 3. File your first work item

The `quick-task` chain has no gates, which makes it good for confirming the
pipes are connected:

```bash
kraft item create "fix the flaky import test" --chain quick-task \
  --description "It's the datetime import, not the fixture."
```

It prints the new item. Copy its `id`:

```text
id            9d0ab38ff3c9439b90506df0f6966660   <- the ID
status        paused
title         fix the flaky import test
bead_warning  bd is not installed: [Errno 2] No such file or directory: 'bd'
```

You can list IDs again any time with `kraft view list`.

`bead_warning: bd is not installed` means Kraft could not file a matching
[beads](https://github.com/gastownhall/beads) issue. beads is optional; the work
item is filed and runs the same without it, so you can ignore the line.

The item lands **paused**, because `item create` starts nothing unless you add
`--autostart`. Nothing has spent a token yet.

You know it worked when the item's status is `paused`. If the command is
refused because the repo is not connected, run step 2 first.

## 4. Start it, and watch

Replace `ID` with the one you copied. `resume` takes the item's ID, which you
can leave off only when you run the command inside that item's worktree. It is
the CLI twin of **Start** in the board's side panel.

```bash
kraft item resume ID
```

`resume` answers with the item it started:

```text
started 9d0ab38ff3c9439b90506df0f6966660
```

While it runs, `kraft view list` shows its status and node. To watch it work,
open the board in your browser, or run `kraft view watch` in a third terminal. `watch` takes no ID, redraws a live board on every event, and
holds its terminal until you press Ctrl-C. The web board looks like this:

![The Kraft board in the dark graphite look: work items grouped by Needs you (a paused item with Resume, a failed one with Retry, and two waiting at a gate, each with its one button), Running, Not started, and Done, the unstarted items marked created paused, with a Select all link on every group and a ? shortcuts button in the toolbar](/assets/board.png)

The [Web UI](/reference/web-ui) reference describes each screen in the picture.

`quick-task` runs `implementation`, then `verify`, with no gate. If the agent's
fix is good, the item reaches **Done** on its own. `verify` runs the repo's own
`test_scopes` or `test_command` from `repos.yaml`. If a test fails, the item
stops and waits for you. Its stop reason names the failing command and its
scope, and `kraft view logs ID` shows that command's output.

When it is done, `kraft view list` shows the item with the status `completed`
(the NODE column is the last node it entered):

```text
ID                                STATUS     GATE  NODE    TITLE
9d0ab38ff3c9439b90506df0f6966660  completed  -     verify  fix the flaky import test
```

You know it worked when the board shows the item under **Done**, and
`kraft view list` shows its status as `completed`. A failure shows as
`needs_human`, under **Needs you**: see [Troubleshooting](#troubleshooting)
below.

## 5. Where is my change?

`quick-task` opens no pull request: the change stays on the item's own branch,
in its worktree. To see it, run one of these with the item's ID:

| Command | What it does |
|---|---|
| `kraft view diff ID` | Prints the change, against the base branch. |
| `kraft repo path ID` | Prints the worktree's path. `cd "$(kraft repo path ID)"` goes there. |
| `kraft repo open ID` | Opens the worktree in your default editor: the one set in Settings, else `$KRAFT_EDITOR`, else the OS default app, which needs a desktop session. `--editor code`, `cursor`, `zed`, `obsidian` or `system` picks one. |

Merge the branch yourself, or run the next piece of work on `default`, which
opens and merges a pull request for you.

You know it worked when `kraft view diff ID` prints the agent's change.

## Troubleshooting

An item that stops shows under **Needs you** with a reason. Read it with
`kraft view show ID`, then the log of the session that stopped it with
`kraft view logs ID`, then check the install with `kraft admin doctor`. In
Claude Code, `/kraft:triage` does this for you, and offers to retry, raise a cap,
or hand the item back to you.

[Troubleshooting](/troubleshooting) maps every stop reason to its fix. These four
are the ones a first run most often hits:

| It stops with | The fix is in |
|---|---|
| `... nothing registers it for Claude Code ...`, at its first agent step with 0 tokens spent. | [A task Kraft would not launch](/troubleshooting/why-did-my-item-stop#a-task-kraft-would-not-launch) |
| `no setup_command declared for <repo> in repos.yaml ...`, before its first node runs. | [`no setup_command declared`](/troubleshooting/stop-reasons-in-detail#no-setup_command-declared) |
| A config error at its test node: the repo declares neither `test_scopes` nor `test_command`. | [`declares neither test_scopes nor test_command`](/troubleshooting/stop-reasons-in-detail#declares-neither-test_scopes-nor-test_command) |
| `kraft admin doctor` fails its `agent: claude` row. | [The agent row and the service PATH](/troubleshooting/doctor-failures#the-agent-row-and-the-service-path) |
