---
title: Inbound triggers
description: Starting a chain from a cron schedule or a webhook instead of typing into kraft item create.
---


Start a chain from an event instead of typing `kraft item create` each time.
There are two doors, a cron schedule and an HTTP call. Both always file the
item `paused`, exactly like manual intake: an agent can't start work from a
trigger any more than from your own `kraft item create`. You start the item
from the board.

## A cron schedule

Add a `triggers:` entry to `policy.yaml`:

```yaml
triggers:
  - cron: "0 9 * * 1,2,3,4,5"  # 9:00 UTC on weekdays
    repo: /path/to/repo
    chain: default
    title: "Nightly dependency check"
    description: "Filed by the 9am weekday trigger"
```

| Field | Required | Meaning |
|---|---|---|
| `cron` | yes | Five fields: minute, hour, day of month, month, day of week (0 is Sunday). Each field is `*` or a comma-separated list of integers. Ranges (`1-5`) and steps (`*/15`) aren't supported. |
| `repo` | yes | Path of a repo you connected with `kraft repo connect`. An unconnected repo is skipped, and Kraft logs a warning. |
| `chain` | yes | A chain template id from `templates/`. |
| `title` | yes | The work item's title. |
| `description` | no | The work item's description. Defaults to `""`. |

Kraft evaluates the schedule in UTC, not in the server's local time zone. It
checks once a minute. A minute missed while the server is down isn't
backfilled. The poller runs for the life of the server, whether or not any
trigger existed at boot, so a trigger you add later starts firing without a
restart. Add it through Settings, or edit `policy.yaml` and run
`kraft admin reload`.

## An HTTP call

`POST /api/triggers` is the HTTP twin of a cron entry, for anything that can
fire a webhook (CI, an external scheduler, a script watching a queue) and can't
wait for the next minute tick. The request body is JSON:

| Field | Required | Meaning |
|---|---|---|
| `title` | yes | The work item's title. |
| `repo` | yes | Path of a connected repo. |
| `chain_template` | no | A chain template id. Defaults to `default`. |
| `description` | no | The work item's description. Defaults to `""`. |

The chain field is named `chain` in `policy.yaml` and `chain_template` in the
HTTP body.

Request from the machine running Kraft, where no login is needed:

```bash
curl -s -X POST http://127.0.0.1:8765/api/triggers \
  -H 'Content-Type: application/json' \
  -d '{"title": "Nightly dependency check", "repo": "/path/to/repo", "chain_template": "default"}'
```

From another machine, send the MCP bearer token, which lives in
`$KRAFT_HOME/run/mcp-token`, and use your tunnel's address. A browser session
cookie works too. See [Remote access](/reference/remote-access).

```bash
curl -s -X POST https://<your-tunnel-hostname>/api/triggers \
  -H "Authorization: Bearer $(cat ~/.kraft/run/mcp-token)" \
  -H 'Content-Type: application/json' \
  -d '{"title": "Nightly dependency check", "repo": "/path/to/repo"}'
```

On success Kraft answers `201` with the work item as JSON. Its `id` field is
the new item's id, and `status` is `paused`:

```json
{"id": "<work-item-id>", "title": "Nightly dependency check", "status": "paused", "...": "..."}
```

The `repo` must already be connected. A path Kraft hasn't seen is refused with
a 422 that names `kraft repo connect`. A cron entry goes through the same
check, but no request is there to answer: Kraft skips that trigger, logs a
warning naming `kraft repo connect`, and still fires the other triggers due in
the same tick.

## Verify a trigger

List the board and look for the new item, filed paused:

```bash
kraft view list --status=paused
```

The item shows as *Waiting to start*. For a cron trigger, wait for the next
matching UTC minute first. If nothing appears, check the server log for a
skipped-trigger warning.
