---
title: Reviewing a change
description: Approve or reject the gate a Kraft work item waits at, or comment on the change at any point in its life, in the web UI or from the CLI.
---

A gate holds a work item until you decide. Approving lets it run on, and rejecting sends the work back with your note. Comments reach the next agent whether or not a gate is open.

## Approve a gate

You need a work item at a gate: the board shows it under **Needs you**. For the CLI, also its ID from `kraft view list` (add `--all` outside the repo's directory). Left without an ID, a verb acts on the item whose [worktree](/concepts/vocabulary#worktree) you stand in, which a reviewer rarely is.

### Decide in the web UI
<!-- not new: merged from "Approve or reject in the web UI" -->

![The gate's review page headed Approve final review: Request changes and Approve buttons in the header, a Waiting for you mark, a line saying Approving starts release with no gate after it and the spend, the review brief an agent wrote rendered below, and the files on the branch beside it](/assets/gate.png)

1. On the board, select **Review** on the item's row, or open the item and select the waiting gate in its chain. The review page opens at the gate.
2. Read the document and the diff.
3. Decide:
   - **Approve** passes the gate at once. An open must-fix thread refuses it with `must-fix review threads are not resolved`.
   - **Request changes** sends the work back. Write what is wrong, because the next agent reads your note and threads.
   - With drafts pending, **Approve** in the bottom bar opens **Finish your review** first, so no comment goes out with an approval unseen.

[A waiting gate](/reference/web-ui/item-page#a-gate-that-is-waiting) and [Finish review](/reference/web-ui/review-page#finish-review) describe each button and the bar. Approving on the review page shows **Approved · *gate* passed** and returns you to the item's page.

### Decide from the CLI
<!-- not new: merged from "Approve or reject from the CLI" -->

```bash
kraft item approve ID
kraft item approve ID --head <head>
kraft item reject ID --note "the plan skips migrations"
```

Each acts on the gate the item waits at, and prints what it did and where the
item stands:

```text
approved spec_approval on <id>; the item is now running
```

At the final review, which merges the work, the approval names the head you
read: `kraft view show ID` prints it as `head`, and `--head <head>` sends it
back. `reject` needs a note, which the next agent reads. [Item verbs](/reference/cli/item) has `--gate`, `--node` and the rest.

Either way, you know it worked when the CLI prints `approved <gate> on <id>`, or the review page shows **Approved · *gate* passed**. The item leaves **Needs you** and runs on, until it reaches the next gate or stops.

### If approve is refused
<!-- not new: the refusals of approve, moved after the check -->

- `must-fix review threads are not resolved`: a must-fix thread is open. Resolve
  or reopen it first, as [Block approval with a must-fix](#block-approval-with-a-must-fix) says.
- `409`: the gate you named with `--gate` isn't the one pending.
- A refusal at the final review: the approval was sent without `--head`, or a
  commit has reached the branch since you looked. Read `head` again with
  `kraft view show ID` and send it back.

To comment without deciding, see [Comment and finish a review in the web UI](#comment-and-finish-a-review-in-the-web-ui). You can comment while the item runs, stopped or at a gate. Only `request-changes` interrupts an agent, and only the node it targets.

`kraft item review` makes the same decisions together with your drafted comments, as [Comment and send a review](#comment-and-send-a-review-from-the-cli) shows.

## Comment and finish a review in the web UI

![The review page: the file tree on the left, a diff of kraft/progress.py, and a comment being written on the removed line and its replacement (Old 2 to new 2) with Must fix selected, above the review bar with Request changes and Approve](/assets/review.png)

The item's review page does everything the comment verbs below do: select
**Review changes** on the item's page, or open `/work-items/<id>/review`. Each
part of the page does what one CLI verb does:

| On the review page | From the CLI |
|---|---|
| **Compare** and **All nodes ▾** | `kraft view compare --from T --to T [--nodes a,b]` |
| **+** on a line, or dragged down a range | `kraft item comment --body "..." --file P --lines A-B [--side old\|new]`; across sides, `--start-side` names line A's side (`--lines 3-2 --start-side old --side new`) |
| **Comment on this file** | `kraft item comment --body "..." --file P` |
| **Must fix**, **Question** and **Nit** | `--label must-fix`, `--label question`, `--label nit` |
| **± Suggest change** | `--suggest "..."` |
| **Reply** | `kraft item comment --reply THREAD --body "..."` |
| **Resolve** and **Reopen** | `kraft item resolve THREAD`, `kraft item reopen THREAD` |
| **Finish review**, then **Comment only**, **Request changes** or **Approve**, with the overall note | `kraft item review comment`, `request-changes` or `approve`, with `--summary "..."` |

A comment you add on the page is a draft until you finish the review.
**Viewed**, which marks a file as read, has no CLI equivalent.

## Comment and send a review from the CLI

1. Comment on the lines you mean:

   ```bash
   kraft item comment ID --body "this leaks the connection" --file src/db.py --lines 40-46 --label must-fix
   ```

   It files a draft and prints where the thread sits, the lines it quotes, and
   what happens next:

   ```text
   drafted thread <thread-id> on src/db.py:+40 to +46
       | <the quoted lines>
   it goes out with your next kraft item review
   ```

2. Read your drafts:

   ```bash
   kraft view threads ID
   ```

   Each thread is a line with its ID, where it sits and its tags, then its
   comments. A draft carries the tag `draft` and `(draft)` after its author:

   ```text
   <thread-id>  src/db.py:+40 to +46  [must_fix open draft]
     you (draft): this leaks the connection
   ```

3. Send them with one outcome:

   ```bash
   kraft item review ID comment --summary "a few notes, nothing blocking"
   ```

   No agent sees a draft until you send it. The outcome is one of three:

   | Outcome | What it does |
   |---|---|
   | `comment` | Queues your drafts for the next agent that runs. It never stops anything, and it works whether or not a gate is pending. Agents answer questions in the thread, and at a gate the gate stays open. |
   | `approve` | Needs a pending gate: it clears it, the same as `kraft item approve`. |
   | `request-changes` | Redoes work now. See [Request changes](#request-changes). |

   For `comment` with no gate pending, the CLI prints the review's ID and
   outcome:

   ```text
   review_id    <review-id>
   outcome      comment
   gate         -
   reply_agent  False
   ```

## Block approval with a must-fix

A comment labelled `--label must-fix` blocks every gate approval on the item
until it is resolved, no matter which gate it was filed at or whether one was
pending at all. `kraft item resolve THREAD` clears it. `kraft item reopen
THREAD` puts it back if the fix didn't hold up.

## Comment while it runs

Every agent dispatch carries the item's unanswered threads: the next
implementation run, every verify reviewer, every fix-loop round.

- A working agent (no review skill) is told to address each thread and reply
  with `kraft item reply`.
- A reviewer agent is told to judge the change against the threads, and reports
  an unaddressed must-fix as a finding.

A thread drops off that list the moment an agent replies or you resolve it.

## Request changes

```bash
kraft item review ID request-changes --summary "please address the must-fix"
kraft item review ID request-changes --node implementation --summary "redo this part"
```

Where the work restarts is `--node` when you give it. Without `--node`, at a
pending gate it is the gate's reject target. With no gate pending, Kraft derives
it from your threads: the earliest node, at or before the one now running, that
wrote what a thread is about (a thread's own `file_path`, or the node it
names). A whole-change comment falls back to the current working node.

What happens next depends on the item:

| The item | What happens |
|---|---|
| At a pending gate | Rejects that gate, the same decision as `kraft item reject` or **Request changes…** on the item's page, with your summary and threads as the note instead of a note you type. The chain re-enters at the target. |
| Running, target is the running node | The node stops and re-runs now, with your review as its note. |
| Running, target is an earlier node | Nothing running is touched. The rewind is queued and takes effect the moment the running node finishes, or on your next `kraft item resume` or `kraft item retry`. |
| Stopped and waiting for you (`needs_human`), nothing else running | Retries at the target immediately. |
| Paused | Only the rewind is queued. Resuming a paused item is your call, so `request-changes` doesn't do it for you. |

The response says which of these happened, and the CLI prints it:
`request-changes -> implementation (threads on src/db.py), rerun`.

A gate you already approved between the target and where the item stood asks
you again when the re-run reaches it, since your approval was of the work
before. Approved again, it lets the walk on.

## A gate with a must-fix doesn't open
<!-- renamed from: A gate with a must-fix does not open -->

Reaching a gate with an unanswered `must-fix` bounces it back to the reject
target instead of opening, the same as if you had rejected it yourself. The
gate's own reject-loop limit caps the bounces, so an agent that never answers
can't loop forever.

When one more bounce would pass that limit, the gate opens for you, and
approving it still answers `409` until you resolve the must-fix. A gate with only unanswered questions or nits opens as
usual, with the reply agent already launched to answer them.

## Compare attempts

```bash
kraft view compare ID --from attempt:1 --to attempt:2 --stat
```

[Compare two review targets](/reference/cli/view#compare-two-review-targets) has the targets and flags. On the review page, **Compare** does the same.

## For agents

A [worker](/concepts/vocabulary#worker) replies to a thread it was handed with `kraft item reply <thread-id>
--body "..." --claim fixed|answered|should_fix`. Every other review verb
above is refused from inside a worker's own worktree. Reviewing is a person's
job, or an assistant acting on a person's behalf from outside the item.

## Check a sent review

After you send a review, run `kraft view threads ID` again. The sent threads no longer carry `draft`: `[must_fix open]`.
