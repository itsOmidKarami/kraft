---
title: Use Kraft from your agent
description: Register Kraft with Claude Code, Codex, Cursor, OpenCode, Amp, Antigravity or Gemini CLI, then drive it from that agent.
---

Register Kraft with your coding agent and connect a repo, then file work, read
the board, and approve or reject gates from the agent's session without
switching to the browser. At the end the agent answers "what is waiting on me in
Kraft?" from the board.

Every agent reaches Kraft through its MCP server, the command `kraft admin mcp`.
With the Kraft plugin, Claude Code, Codex, Cursor and Antigravity also get
Kraft's skills.

Registering lets you drive Kraft from the agent. The agent CLI that runs a work
item's tasks is a separate choice: [Switch a task to another
harness](/guides/harnesses/switch-harness) moves tasks to another, and [Give a
worker its login](/guides/harnesses/give-a-worker-its-login) gives that CLI the
login a headless worker needs.

## Before you start

- Kraft installed, with `kraft` on your `PATH`, and the server running
  (`kraft`). See [Install](/get-started/install).
- A git checkout of the repo you want Kraft to work on.
- One of the agents below, signed in.

## Register Kraft with your agent

Pick your agent. Each tab ends with the command that lists the registration.

::tabs{sync="agent"}
:::tabs-item{label="Claude Code"}
Add the Kraft marketplace and install the plugin:

```bash
claude plugin marketplace add itsOmidKarami/kraft
claude plugin install kraft@kraft
```

The plugin registers Kraft's MCP server with Claude Code and adds the
[`/kraft:*` skills](#the-skills). You do not need `kraft admin init` as well.

`claude plugin update kraft` picks up new skills. `claude plugin uninstall kraft`
removes them.

To use plain files instead of a managed plugin, see
[Set up without the plugin](#set-up-without-the-plugin).
:::

:::tabs-item{label="Codex"}
Codex installs the same plugin from the same marketplace:

```bash
codex plugin marketplace add itsOmidKarami/kraft
codex plugin add kraft@kraft
```

The plugin registers Kraft's MCP server (`codex mcp list` shows `kraft`) and
adds the Kraft skills. Start a new Codex session to load them. `/skills` lists
them as `kraft:board`, `kraft:handoff` and so on. Type `$` to pick one, or
describe the task and let Codex choose. `codex plugin remove kraft@kraft`
uninstalls it.

Without the plugin, register the server alone:

```bash
codex mcp add kraft -- kraft admin mcp
```

This writes the server to `~/.codex/config.toml`:

```toml [~/.codex/config.toml]
[mcp_servers.kraft]
command = "kraft"
args = ["admin", "mcp"]
```

To register it for one repo only, put the same table in that repo's
`.codex/config.toml` instead. `codex mcp list` shows it.
:::

:::tabs-item{label="Cursor"}
Add the Kraft marketplace to your Cursor account:

```bash
agent plugin marketplace add https://github.com/itsOmidKarami/kraft
```

Then install the plugin. In an `agent` session, run `/plugins`, open the
Marketplace tab, pick `kraft`, and choose user scope (every project) or project
scope (this repo). Its details list the Kraft skills and the `kraft` MCP
server. Once installed, `/mcp` in a session lists `Kraft (plugin)`; the
`agent mcp list` command shows only servers from `mcp.json` files, so it does
not list it. `agent plugin marketplace remove kraft` drops the marketplace.

Without the plugin, register the server alone. Cursor's CLI has no command that
adds a server. Add it to `~/.cursor/mcp.json` for every project, or to
`.cursor/mcp.json` in one repo:

```json [~/.cursor/mcp.json]
{
  "mcpServers": {
    "kraft": { "command": "kraft", "args": ["admin", "mcp"] }
  }
}
```

The CLI loads a new server only once you approve it. Until then,
`agent mcp list` shows `kraft: not loaded (needs approval)`. Approve it with:

```bash
agent mcp enable kraft
```

The Cursor editor reads the same file.
:::

:::tabs-item{label="OpenCode"}
```bash
opencode mcp add --global kraft -- kraft admin mcp
```

`--global` writes your user config. Without it, the server goes into
`opencode.json` in the current directory, for that project only.
`opencode mcp list` shows `kraft connected` once OpenCode can start it.
:::

:::tabs-item{label="Amp"}
```bash
amp mcp add kraft -- kraft admin mcp
```

This writes `amp.mcpServers` in `~/.config/amp/settings.json`. With
`--workspace` it writes the repo's `.amp/settings.json` instead, and Amp runs a
workspace server only after you approve it: `amp mcp approve kraft`.
`amp mcp list` shows it.

Amp has no plugin route that carries an MCP server, but it installs the Kraft
skills straight from the repo:

```bash
amp skill add itsOmidKarami/kraft/plugins/kraft/skills --global
```

`--global` copies them into `~/.config/agents/skills/`. `amp skill list` shows
them. To update, run the same command with `--overwrite`.
:::

:::tabs-item{label="Antigravity"}
Antigravity's CLI (`agy`) imports a Claude Code plugin from a local directory,
so clone the repo and import the plugin from it:

```bash
clone=$(mktemp -d)
git clone --depth 1 https://github.com/itsOmidKarami/kraft.git "$clone"
agy plugin import "$clone/plugins/kraft"
rm -rf "$clone"
```

The import copies the plugin, so the clone is not needed afterwards. It
registers Kraft's MCP server and adds
the Kraft skills; `agy plugin list` shows `kraft` with `skills` and
`mcpServers`. To update, clone again and run the import with `--force`.
`agy plugin uninstall kraft` removes it.

Without the plugin, register the server alone:

```bash
agy mcp add kraft kraft admin mcp
```

`agy mcp list` shows it.
:::

:::tabs-item{label="Gemini CLI"}
Gemini CLI needs an API key or Gemini Code Assist. With an individual Google
account, use the Antigravity tab instead. The
[harness table](/reference/harnesses) says why.

```bash
gemini mcp add --scope user kraft kraft admin mcp
```

`--scope user` writes `~/.gemini/settings.json`. Without it, Gemini CLI writes
the project's `.gemini/settings.json`, and connects a project's servers only in
a folder you have trusted. `gemini mcp list` shows it.
:::
::

Kraft's skills reach Claude Code, Codex, Cursor and Antigravity through the
plugin, and Amp through `amp skill add`. OpenCode and Gemini CLI get the MCP
server alone: ask for what you want in plain words ("what is waiting on me in
Kraft?") and the agent calls the [MCP tools](/reference/mcp-tools). The `kraft` command gives a
hook or an agent without MCP the same surface.

## Connect the repo

Kraft works on repos it has connected. In the repo's directory, run:

```bash
cd ~/code/my-project
kraft repo connect
```

The first line it prints is `connected:` and the repo's path. After it, in
order: a `read from` line naming the branch Kraft reads, the `test command:` and
`setup command:` lines, an `also found` or `not installed here` line where Kraft
has more to say, and, when it found no test command, a final `saved disabled:`
line that says how to enable the repo.

Where the skills are installed, `/kraft:onboard` in a session of that agent
does the same and then checks the two commands. Run it before the first work
item starts: the commands Kraft proposed are saved unconfirmed, and an item
that runs against wrong ones stops.

## Check it worked

1. The list command in your agent's tab shows `kraft` (Cursor's plugin shows in
   `/mcp`, as its tab says).
2. In a new session of that agent, ask: "what is waiting on me in Kraft?" The
   agent answers from the board: your items, or that nothing is waiting. Where
   the skills are installed, `/kraft:board` lists the [work items](/concepts/vocabulary#work-item) of every
   connected repo, not only the one you are in.
3. For Claude Code, `kraft admin doctor` has an `mcp server` row. It passes once
   Kraft is registered, and names the permission tool Claude workers use. The
   row checks Claude Code's registration only, not Codex, Cursor, OpenCode, Amp,
   Antigravity or Gemini CLI. For those, use the list command in the agent's
   tab.

If the agent cannot reach Kraft, check that the server is running
(`kraft admin health`) and that `kraft` is on the `PATH` of the shell the agent
starts. [Troubleshooting](/troubleshooting) lists the rest.

## Set up without the plugin

Use this when you want plain files instead of a managed plugin. For Claude Code
without the plugin, this step is required: without a registered `kraft` MCP
server, Kraft refuses to launch a Claude worker.

For Claude Code, run one of:

```bash
kraft admin init          # for every repo you open
kraft admin init --repo   # for this repo only
```

- The first registers Kraft with Claude Code for your user
  (`claude mcp add --scope user kraft -- kraft admin mcp`) and writes the skills
  to `~/.claude/skills/kraft/`. It needs the `claude` command; without it, it
  prints that command for you to run.
- The second writes a `.mcp.json` and `.claude/skills/kraft/` into the current
  repo, where other tools can read them too. Commit the `.mcp.json`: each work
  item runs in a fresh checkout of the repo, and an uncommitted file is not in it.

Either way you get the same `/kraft:*` commands. To remove them, delete the
skills directory.

`kraft admin init` registers Kraft with Claude Code only. For another agent, use
its tab in [Register Kraft with your agent](#register-kraft-with-your-agent).
An agent not listed there needs an MCP server that runs the command
`kraft admin mcp` over stdio.

### Refresh the skills

The user-scope form fails on a second run. `claude mcp add` refuses a name that
is already registered, so `kraft admin init` prints "could not register" and
writes no skills. The same happens when you run the command it printed first.
To refresh the skills after upgrading Kraft, or to write them after running the
printed command, remove the registration and run it again:

```bash
claude mcp remove --scope user kraft
kraft admin init
```

`kraft admin init --repo` registers nothing with `claude`, so you can re-run it
as often as you like. The plugin route has no such step: `claude plugin update
kraft` refreshes its skills.

## The skills

Claude Code runs these as slash commands. In Codex they have the same names
without the slash (`kraft:board`), picked with `$`.

| Skill | Use it to |
|---|---|
| `/kraft:onboard` | Connect the repo you are in and check its setup and test commands. |
| `/kraft:board` | See what is running, blocked, or waiting on a person, or search specs and plans. |
| `/kraft:prepare` | Write a spec (and a plan, if you ask), then decide whether the work runs in this session or in Kraft. |
| `/kraft:handoff` | File work with Kraft, with any agreed spec and plan attached. |
| `/kraft:status` | Report where a work item has reached, or watch it until it ends. |
| `/kraft:gates` | Approve or reject the gate a work item is waiting on, leave review threads and submit a review, or pause and resume it. |
| `/kraft:review` | Read what a gate is about and recommend approve or reject, with reasons. Reasons tied to specific lines become review threads. It acts only after you answer. |
| `/kraft:steer` | Redirect a work item that is heading the wrong way. |
| `/kraft:triage` | Find out why a work item stopped, and retry it, raise a cap, or hand it to you. |
| `/kraft:check` | Report where a repo's Kraft config has drifted from this Kraft version. |
| `/kraft:doctor` | Diagnose an unhealthy Kraft server and fix what it can. |

### Example: hand work to Kraft

Say you and your agent have settled what to build, and you want Kraft to build
it. Ask for `/kraft:handoff`, with the work in your own words:

1. The skill connects the repo if Kraft has not seen it. If it newly connected
   it, it tells you and runs `/kraft:onboard` before the item can start.
2. It files the work with `create_work_item`, putting your intent in the
   description, which is the brief the spec node writes its design from. A spec
   and a plan you already wrote are attached, and the item skips the node and
   gate each one satisfies.
3. It reads the board back (`kraft view list --status=paused`) to check the item
   is there under the title you gave.
4. It reports the work as filed, not running: the item is paused under **Not
   started**, and nothing spends tokens until you start it. Click its row, then
   [**Start**](/reference/web-ui/item-page) in the side panel or on the item's
   own page, or ask your agent to resume it (`/kraft:gates`).

### What an agent is refused

The MCP tools have no autostart option, and the server refuses
`kraft item create --autostart` from a session Kraft started or a request tagged
as the MCP client. It cannot tell a coding agent that runs the command in your
own shell from you, so that call starts the item.

A worker is refused every item verb on its own work item (approve, reject,
pause, resume, skip, abandon, retry, complete, cancel and escalate), and any
change to its attachments, overrides or [policy](/concepts/vocabulary#policy), because a gate is where a
person decides.

These are checks on the
client and on the API, and none is a boundary against a worker that is not
sandboxed. [Who may call what](/reference/mcp-tools#who-may-call-what) lists
every refusal, and [Agents and gates](/project/security#agents-and-gates) says
what each one does and does not stop.
