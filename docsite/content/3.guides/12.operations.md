The day-to-day care of a Kraft install: backups, logs, disk space, a second
instance, and running Kraft as a service.

## Before you start

- Everything below lives under `$KRAFT_HOME`, which is `~/.kraft` unless you
  set it. `run/` holds the state, `config/` holds the YAML you edit. See
  [Data and privacy](/project/data-and-privacy#secrets-and-state) for what each
  file holds.
- The commands assume the default home. Put your own path in place of
  `~/.kraft` if you moved it.
- If Kraft runs as a [service](#run-kraft-as-a-service), `kraft admin stop`
  does not keep it stopped: the service manager starts it again. Where a step
  says to stop the server, run `kraft admin uninstall-service` instead, and
  `kraft admin install-service` when you are done.

## Back up the database

`run/orchestrator.db` holds every work item, event, session and review
thread. Kraft runs SQLite in WAL mode, so recent writes can sit in
`orchestrator.db-wal` beside it. Copying `orchestrator.db` alone while the
server runs can give you a copy that is missing them, or one that does not
open.

Use SQLite's online backup, which is safe while the server runs:

```bash
sqlite3 ~/.kraft/run/orchestrator.db ".backup '$HOME/kraft-backup.db'"
```

No `sqlite3` command? Python does the same:

```bash
python3 -c "import sqlite3; sqlite3.connect('file:$HOME/.kraft/run/orchestrator.db?mode=ro', uri=True).backup(sqlite3.connect('$HOME/kraft-backup.db'))"
```

Or stop the server first, then copy the file:

```bash
kraft admin stop
cp ~/.kraft/run/orchestrator.db ~/kraft-backup.db
kraft admin start --detach
```

Back up `config/` too. It is your config, and it is small. See
[Keep your templates in git](/guides/upgrading-templates#keep-your-templates-in-git).

You do not need to back up `run/index.db`. It is the search index, and
`kraft admin reindex` rebuilds it.

To restore, stop the server, put the backup in place as
`run/orchestrator.db`, delete any `orchestrator.db-wal` and
`orchestrator.db-shm` beside it, and start the server again.

### The copy Kraft makes before an upgrade

When a newer Kraft starts on an older database, it migrates the database
forward, and the older version cannot open the result. So before it migrates,
Kraft copies the database to `run/orchestrator.db.pre-v<N>-<time>`, where `<N>`
is the schema version it is about to migrate to and `<time>` is when it made
the copy. `server.log` names the file:

```text
database schema v44 -> v51: backed up the old database to /home/you/.kraft/run/orchestrator.db.pre-v51-20261002-093015
```

The copy is consistent even while the WAL holds recent writes, and only you
can read it (`0600`). Each migration makes a new copy and never overwrites an
older one. If you upgrade, roll back and upgrade again, the newest
`orchestrator.db.pre-v51-*` is the one that holds what you did in between.

The `v<N>` in the name is the schema Kraft migrated to, not the one the copy
holds. After more than one upgrade, the newest copy can hold a schema the
release you go back to refuses: going from 1.4 through a 1.5.0 release
candidate to 2.0 leaves 1.4's database in a `pre-v50-*` copy, and the
candidate's in the newest `pre-v51-*`. Each copy's own schema is its
`PRAGMA user_version`; 1.4's is 44.

The copy needs about as much free space as the database, beside it in `run/`.
If Kraft cannot write it, it does not migrate: the server does not start, the
database is left unchanged, and the error names the copy and the space it
needs. Free the space and start again.

Restore the newest copy whose schema is the one the release you go back to
runs, the same way as your own backup. If Kraft runs as a
[service](#run-kraft-as-a-service), run `kraft admin uninstall-service` in place
of `kraft admin stop`, or the service manager starts it again under you:

```bash
kraft admin stop
for f in ~/.kraft/run/orchestrator.db.pre-v*; do echo "$(sqlite3 "$f" 'PRAGMA user_version') $f"; done
cp ~/.kraft/run/orchestrator.db.pre-v51-20261002-093015 ~/.kraft/run/orchestrator.db   # the newest that printed 44, for 1.4
rm -f ~/.kraft/run/orchestrator.db-wal ~/.kraft/run/orchestrator.db-shm
```

The loop prints each copy's schema, then its name; names sort by schema, then
by time. Without the `sqlite3` command, Python prints the same:

```bash
python3 -c 'import glob, os, sqlite3; [print(sqlite3.connect(f"file:{f}?mode=ro", uri=True).execute("PRAGMA user_version").fetchone()[0], f) for f in sorted(glob.glob(os.path.expanduser("~/.kraft/run/orchestrator.db.pre-v*")))]'
```

Then start the version you upgraded from. The copy loses everything done since
the upgrade. It is no substitute for a backup you take yourself: make one
before every upgrade. Once you are sure you will stay on the new version,
you can delete the copies. Kraft never deletes them itself.

### Verify the backup

```bash
sqlite3 ~/kraft-backup.db "PRAGMA integrity_check; SELECT count(*) FROM work_items;"
```

Or, without the `sqlite3` command:

```bash
python3 -c "import sqlite3; db = sqlite3.connect('$HOME/kraft-backup.db'); print(db.execute('PRAGMA integrity_check').fetchone()[0]); print(db.execute('SELECT count(*) FROM work_items').fetchone()[0])"
```

Either prints `ok`, then the number of work items.

## Find the logs

All logs are in `run/logs/`.

| File | Holds |
|---|---|
| `server.log` | The server's own output: startup, shutdown and its reason, errors. A foreground `kraft` writes here as well as to the terminal. Kraft moves it to `server.log.1` at start once it passes about 8 MB, replacing the last one. |
| `<session id>.log` | One worker session: everything an agent or command printed. Kraft never deletes these. |
| `<session id>.times.jsonl` | When each line of that session's log was written, one JSON object per line: `{"n": <line number>, "t": <timestamp>}`. `kraft view logs` and the item page's log take a line's time from it when the line carries none of its own. |

Read a session's log through Kraft rather than by file name:

```bash
kraft view logs ID                    # the item's latest session
kraft view logs ID --session SESSION  # one session
kraft view logs ID -f                 # follow a running session
```

`kraft view events ID --type worker_session_created --json` lists the item's
session ids.

## Reclaim disk space

Each work item gets a git worktree in `run/worktrees/<item id>/`, a full
checkout of its repo, plus any dependencies its setup command installed. That
adds up.

A worktree is removed when the item is abandoned or archived:

- **Abandon** a work item you no longer want: `kraft item abandon ID --yes`.
  It removes the worktree, and deletes the item's local branch and its
  attachment copies in `run/attachments/`. Uncommitted work is lost, and so
  are commits you never pushed.
- **Archive** a completed or abandoned item from the board's Done group, or
  with `POST /api/work-items/ID/archive`. It removes the worktree and keeps
  the item's record and its attachment copies, so you can still duplicate
  it. It deletes the local branch only when every commit on it is somewhere
  else too: another branch such as the base, a remote-tracking branch, a
  tag, or what Kraft pushed. Otherwise the branch stays, and the archive
  event says how many commits it kept. Commits on a detached HEAD in the
  worktree are kept on a new branch, `kraft/rescued/<item id>`. If Kraft
  cannot make that branch, it archives the item but leaves the worktree, and
  the archive event's `worktree_kept` says why. Uncommitted
  changes in the worktree are lost: commit them, or copy them out from
  `kraft repo open ID`, before you archive.
- **Auto-archive.** `archive.after_days` in `policy.yaml` archives completed
  and abandoned items that old. The shipped file sets `30`. Lower it to
  reclaim space sooner. See [Policy](/reference/configuration/policy).

`kraft item complete` and `kraft item cancel` keep the worktree until the
item is archived. A cancelled item that never pushed keeps its branch after
that too. Delete it by hand once you are done with it:
`git branch -D <branch>`.

Session logs in `run/logs/` and result files in `run/results/` stay after
archiving. Delete old ones by hand if they grow, with the server stopped.

To see what uses space:

```bash
du -sh ~/.kraft/run/*
```

## Run two instances

Two instances need separate homes and separate ports. A second server on the
same port refuses to start and names the one already there.

Start the second instance once on a free port. The first start seeds its
`config/`. This example uses 8767, since 8765 is the default and 8766 is
where a contributor's `just dev` runs:

```bash
KRAFT_HOME=~/kraft-staging KRAFT_PORT=8767 kraft admin start --detach
```

Then write the port into that home's `access.yaml`, so the server and the
`kraft` command find it without `KRAFT_PORT`. A port given only as `KRAFT_PORT`
or `--port` is not saved, and every other command would still dial 8765:

```bash
printf 'port: 8767\n' >> ~/kraft-staging/config/access.yaml
```

You can also make `config/` yourself before the first start, to write its
`access.yaml` or a `sandbox.yaml` first. The first start then adds each default
file the directory lacks, and keeps the files you wrote.

Run every command for that instance with the same `KRAFT_HOME`:

```bash
KRAFT_HOME=~/kraft-staging kraft view list
KRAFT_HOME=~/kraft-staging kraft admin stop
```

Workers inherit their instance's `KRAFT_HOME`, so their own `kraft` calls
reach the instance that started them. An agent you run yourself reaches the
instance its environment names, so start it with the same `KRAFT_HOME` to use
the second one.

## Run Kraft as a service

A service starts Kraft at login and restarts it if it exits:

```bash
kraft admin stop
kraft admin install-service
```

On macOS this writes a launchd agent,
`~/Library/LaunchAgents/com.kraft.daemon.plist`, and loads it. On Linux it
writes a systemd user unit, `~/.config/systemd/user/kraft.service`, and enables
it. `install-service` refuses while a server is running, so stop it first.

The service gets the environment of the shell you ran `install-service` from:
`PATH`, and `KRAFT_HOME`, `KRAFT_RUN_DIR`, `KRAFT_CONFIG_DIR`,
`KRAFT_SKILLS_DIR`, `KRAFT_HOST` and `KRAFT_PORT` when set. Run it from a shell
where `claude`, `git`, `gh` and your other tools are on `PATH`. To pick up a
changed `PATH` later, run `kraft admin uninstall-service`, then
`install-service` again.

Nothing else from that shell reaches the service. A repo's
[`env_passthrough`](/reference/configuration/repos) copies a variable from the
server's own environment, so under a service it finds only the ones above. A
key you export in your shell, such as `GEMINI_API_KEY` or a forge token, does
not reach the workers. Set it in the service instead, then run
`kraft admin restart`:

- **systemd:** run `systemctl --user edit kraft` and add the variable to the
  drop-in it opens:

  ```ini
  [Service]
  Environment="GEMINI_API_KEY=..."
  ```

  The drop-in is a separate file from the unit Kraft writes, so it survives
  `uninstall-service` and `install-service`.
- **launchd:** add it to the agent's `EnvironmentVariables`:

  ```bash
  plutil -replace EnvironmentVariables.GEMINI_API_KEY -string "$GEMINI_API_KEY" \
    ~/Library/LaunchAgents/com.kraft.daemon.plist
  ```

  `-replace` adds the key or changes it, so it is safe to run again.
  `install-service` rewrites that file, so do this again after you reinstall
  the service.

Both files are usually readable by other accounts on the machine, and so is a
key written into them. On systemd, keep keys in a file only you can read, such
as `~/.config/kraft/secrets.env` after `chmod 600`, and point the drop-in at
it with `EnvironmentFile=%h/.config/kraft/secrets.env` instead of
`Environment=`.

There is one service per user. Its launchd label and systemd unit name are
fixed, so run a second instance by hand.

To remove it:

```bash
kraft admin uninstall-service
```

### Verify the service

```bash
kraft admin restart
kraft admin health
```

`restart` goes through the service manager when a service is installed.
`health` exits 0 once the server is back, and its `version` row names the
release it runs. Before the restart, after an update, it also prints the
installed release with `restart pending`.
