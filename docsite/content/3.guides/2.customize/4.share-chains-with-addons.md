_Added in 2.1_

Each instance pins a [Kraft add-on](/concepts/vocabulary#add-on) from a
[collection](/concepts/vocabulary#collection) to a commit and changes it only
through an update you review.

This guide installs the add-on `release` from the collection `acme`, uses what it ships and keeps it current. To write and publish an add-on, see [Publish an add-on](/guides/customize/publish-an-add-on).

| To | Run |
|---|---|
| [Add a collection](#install-an-add-on) | `kraft admin addon collection add SOURCE` |
| [Install an add-on from it](#install-an-add-on) | `kraft admin addon install ADDON@COLLECTION` |
| [See what is installed](#install-an-add-on) | `kraft admin addon list` |
| [Take a new version](#update-by-hand) | `kraft admin addon update` |
| [Remove an add-on](#remove-an-add-on) | `kraft admin addon uninstall ADDON@COLLECTION` |

## Before you start

- A running Kraft server, and `git`.
- The instance defines every [harness](/concepts/vocabulary#harness) and
  [agent profile](/concepts/vocabulary#agent-profile) the add-on requires. The
  example needs the shipped `claude` harness and `strong` profile.
- The address of the collection, from whoever published it.

## Install an add-on

### Bound what an add-on's agents may do

An add-on's prompts, steering and skills are instructions an agent follows with
whatever tools your instance allows it. An add-on cannot widen what a run may
do, but with nothing set on the instance an agent may already run any command.
Before you install an add-on from people you do not fully trust, set these on
the instance:

- `maxima:` in [`policy.yaml`](/reference/configuration/policy#defaults-and-maxima),
  so no add-on sets a time, attempt or budget limit above yours;
- [`allowed_tools`](/reference/configuration/policy#tool-lists), so the
  [permission gate](/reference/permissions) answers from your list;
- a [sandbox](/reference/configuration/sandbox) on each repo the add-on's chains
  run in.

[Security](/project/security#kraft-add-ons) explains why an add-on carries
limits and never permissions.

### 1. Add the collection

Kraft ships no collection and has no directory of them, so ask whoever
published the add-on for its address. Then add it:

```bash
kraft admin addon collection add acme/kraft-addons
```

```text
added collection acme
```

`owner/repo` is a GitHub repository. An https URL, an `ssh://` URL, a
`user@host:path` address or a `file:///` URL works too, and `--ref` picks a
branch, tag or commit. This installs nothing.
`kraft admin addon collection list` shows what the collection publishes.

### 2. Install the add-on

```bash
kraft admin addon install release@acme
```

Kraft fetches the add-on, checks it against your instance, and prints a
review. **Reach** lists what decides how far a run goes: gates, merge steps,
harnesses, models and limits. **Content** lists the rest, with every prompt and
skill in full. On a first install everything is new:

```text
release@acme new, 1.0.0
Reach:
  - release:ship.nodes[implementation].tasks[implement]: harness set to 'claude'
  - release:ship.nodes[implementation].tasks[implement].policy: limit time_cap_minutes set, set to 90
  ...
Content:
  - release:ship.nodes[implementation].tasks[implement]: prompt new:
Implement the approved plan, then write the release notes.
  ...
Apply release@acme? [y/N]
```

Read it, then answer `y`. Nothing is installed until you do. `-y` accepts without
asking. A running server loads the add-on at once.
[Add-on problems](/troubleshooting/addon-problems#adding-installing-updating-and-removing)
covers a refused or declined install.

If another add-on or a repository already uses the name `release`, install it
under another namespace with `--as`:

```bash
kraft admin addon install release@acme --as acme-release
```

### 3. Check it worked

```bash
kraft admin addon list
```

```text
release@acme  release  1.0.0  f4a11422cc83
```

The columns are the add-on id, its namespace, its version and the commit it is
pinned to. Then read a chain it ships:

```bash
kraft admin templates show release:ship
```

The output starts with `# release:ship (release@acme 1.0.0)`.
`kraft admin doctor` shows `1 add-on(s) load` on its `add-ons` row.

## Install an add-on that builds on another

_Added in next_

An add-on can [build on another](/guides/customize/publish-an-add-on#build-on-another-add-on),
its parent, and accept a range of the parent's versions. Install the child and
Kraft fetches the parents it lacks from their collections, so you name only the
add-on you want:

```bash
kraft admin addon install team-payments@payments
```

The install is one review and one answer for the whole tree. It starts with a
line for each parent Kraft pulls in, then the review of each add-on, parent
first:

```text
pulls in platform-dept@platform 2.0.0 from collection platform: team-payments@payments builds on it
```

Answer `n` and nothing is installed, the parents included. A parent that is
already installed is used as it is.

- **The parent's collection must be added.** If it is not, the install is
  refused with `its parent platform-dept@platform comes from collection
  platform, which this instance has not added; add it first: kraft admin addon
  collection add <its git URL or directory>`. Add the collection, then install
  again. Ask whoever published the child for its address.
- **`--as` names only the add-on you install.** `--as` and `--auto-update`
  apply to the child alone; a pulled-in parent installs under its own name. If
  that name is taken, the refusal says `install it first with its own --as` and
  gives the command: install the parent with an alias, then the child.
- **A parent outside the child's range is refused**, with both ways out, in
  [An update is held by a range](/troubleshooting/addon-problems#an-update-is-held-by-a-range).

The review of a child's install or update lists its chain changes as they
resolve with its parent.

While an enabled child builds on it, `uninstall` and `disable` refuse to remove
the parent, and name each child:

```text
cannot uninstall platform-dept@platform: something installed builds on it
  team-payments@payments builds on it (requires.addons)
```

Disable or uninstall the child first; that is always allowed. `enable` on a child
is refused while its parent is not installed, not enabled or outside its range.
When a parent is left out at load, its children are left out with it, each
saying `its parent <id> is not loaded:` and the parent's reason.

## Use what an add-on ships

Everything an add-on declares is named `<namespace>:<name>` from outside it.

- **Run its chain.** Name it when you file an item, or make it a repo's
  `default_chain` in [`repos.yaml`](/reference/configuration/repos#default_chain):

  ```bash
  kraft item create "Cut the 4.2 release" --chain release:ship
  ```

- **Extend a component.** A chain or library component of your own takes an
  add-on's with `extends:` and changes what it needs. An update to the add-on
  reaches your chain too, and its review shows the change:

  ```yaml [config/chains/mine.yaml]
  id: mine
  nodes:
    - id: implementation
      kind: exec
      tasks:
        - id: implement
          extends: release:implementer
          policy:
            time_cap_minutes: 60
  ```

- **Select its skill, steering profile or agent profile.** Set
  `skill: release:release-notes`, `steering: [release:house-style]` or
  `profile: release:careful` on a task in your own chain or library. The add-on
  must ship the one you name. The example add-on ships only the skill. An add-on
  declares a steering profile in the `steering:` section of its `library.yaml`,
  and an agent profile in its `profiles.yaml`.
  [Names](/reference/configuration/addons#names) lists every qualified
  reference.

- **Copy it.** An add-on's chains and components are read-only. In the web UI,
  open the chain under **Templates › Chains**, or the component under
  **Templates › Library**, and click **Copy to my library**. Kraft asks for a
  name and opens a draft that is yours to edit. A copy no longer follows the
  add-on's updates. The phone layout has no copy button.

## Build on a shared chain

_Added in 2.2_

Copying an add-on's chain gives you a snapshot that misses its later fixes. To
change a few things and keep the rest current, write a chain that extends it.
This one adds a sign-off gate to `release:ship` and gives its implementer less
time:

```yaml [config/chains/team.yaml]
id: team
extends: release:ship
description: acme's release chain, with our own sign-off.

add:
  - after: verify
    node:
      id: sign_off
      kind: gate
      chain_finalized: true
      message: The team lead signs off.
      reject_to: implementation

overrides:
  implementation.main.implement: { policy: { time_cap_minutes: 60 } }
```

Check what it resolves to:

```bash
kraft admin templates show team --resolved
```

The output starts with where each node came from, then the whole chain:

```text
# extends release:ship
#   implementation: overridden (implementation.main.implement)
#   verify: inherited
#   sign_off: added
id: team
```

Run it like any chain of your own: `kraft item create "..." --chain team`. When
the add-on updates, your chain gets the new version, and the update's review
lists what `team` will run differently. An update that drops or renames a node
your edits name is refused, so your chain never breaks silently; see
[Add-on problems](/troubleshooting/addon-problems#installing-and-updating).
While `team` extends it, `uninstall` and `disable` refuse to remove the add-on.

You can start one on the Templates screen too: open the add-on's chain, press
**Add to my library** and keep **Extend**, then edit it on the canvas. Each change you make there is written as
one of these edits, never as a copy of what the chain inherits; see
[An extending chain](/reference/web-ui/templates-and-settings#an-extending-chain).

A repository can do the same in its own `.kraft/chains/`: list the add-on under
`addons:` in `.kraft/library.yaml`, and name it by its own name. See
[Building on an add-on's chain](/reference/configuration/repo-libraries#building-on-an-add-ons-chain).

[Extending a chain](/reference/configuration/library-and-chains#extending-a-chain)
has every edit and rule.

## Keep it current

### Update by hand

```bash
kraft admin addon update --check
```

```text
release@acme 1.0.0 -> 1.1.0
Reach:
  - release:ship.nodes[implementation].tasks[implement].policy: limit time_cap_minutes raised, 90 -> 120
Content:
  - component tasks.implementer changed
release@acme: update waiting
```

`--check` prints each review and changes nothing. It exits 0 when every add-on
is current, 1 when an update is waiting, 2 when one would be refused and 3
when a collection could not be checked, so a scheduled job can watch for one. `kraft admin addon update` shows the same reviews and asks about each
add-on in turn.

An item that is already running keeps the add-on version it started with. It keeps the versions of the add-on's whole tree, its parent and theirs. A revision that would bring in a child built on another version of a parent is refused.

### When an update is held

_Added in next_

Add-ons that build on each other move as a set. Kraft drops every move that
would leave an installed add-on outside its parent's range, offers the dropped
ones again, and applies what is then consistent. A dropped move is **held**:
the add-on keeps its version and the rest of the update goes ahead.

```text
company@corp: held: company@corp 2.0.0 is outside team@payments's range 1 (needs 1.x)
```

- **One review and one answer per tree.** The add-ons that move together are
  shown in one review, parent first, and you accept or decline them whole.
  Add-ons in other trees are asked separately.
- **A named add-on takes its relatives.** `kraft admin addon update ADDON`
  also takes the waiting moves of its installed parents and children. If a
  relative's move would break a chain and the add-ons you named do not need it,
  that relative is held and the rest apply. If the named moves themselves break
  a chain, every member is refused.
- **`--check` exits 1 for a held move**, like a waiting update, and 2 for one
  that would be refused, which includes a relative held because its own move
  breaks a chain.
- **Auto-update never moves a relative.** It updates only add-ons whose
  auto-update is on, each by itself. A move that needs one whose auto-update is
  off is held, and `kraft admin doctor` shows it on its `add-on updates` row.
  Run `kraft admin addon update` to move the tree.

To get a held move out of the way, see
[An update is held by a range](/troubleshooting/addon-problems#an-update-is-held-by-a-range).

### Let an add-on update itself

```bash
kraft admin addon auto-update release@acme on
```

After each server start, and once a day while the server runs, Kraft checks
the add-on and applies an update whose
review has no **Reach** line: a new version that changes only content, such as
a prompt or a skill. It holds every other update for you and keeps the
installed version running. `kraft admin doctor` shows a held or failed update
on its `add-on updates` row.

`kraft admin addon collection auto-update acme on` does the same for every
add-on installed from the collection.
[Auto-update](/reference/configuration/addons#auto-update) lists what is held.

### Put the same add-ons on another machine

Copy `addons.yaml` and `addons.lock` from `config/` to the other machine's
`config/`, then start Kraft or run `kraft admin reload`. Kraft fetches each
add-on at its locked commit in the background, so both machines run the same
files. The other machine needs git access to the collection's URL.

## Remove an add-on

```bash
kraft admin addon uninstall release@acme
```

Kraft refuses while one of your own files still names the add-on's namespace,
and lists each reference. Change those first. It also refuses while another
add-on [builds on it](#install-an-add-on-that-builds-on-another).
`kraft admin addon disable release@acme` keeps the add-on installed and stops
loading it, under the same rule. Items that are running finish on the version
they started with.
