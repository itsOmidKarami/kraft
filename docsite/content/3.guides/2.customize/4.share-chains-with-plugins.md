---
title: Share chains with plugins
description: Publish chains, library components, skills and agent profiles as a Kraft plugin in a collection, then install, use and update it on another instance.
---

Publish your chains as a [Kraft plugin](/concepts/vocabulary#kraft-plugin) in a
[collection](/concepts/vocabulary#collection), and install it on every instance
that should run them. Each instance pins the plugin to a commit and changes it
only through an update you review.

This guide builds a collection `acme` with one plugin, `release`, then installs
it. If you only install someone else's plugin, start at
[Bound what a plugin's agents may do](#bound-what-a-plugins-agents-may-do).

A Kraft plugin is not the Kraft plugin for Claude Code that
[Use Kraft from your agent](/guides/day-to-day/agent-integration) installs. That
one puts `/kraft:*` commands in your coding agent. This one adds chains to a
Kraft instance.

## Before you start

- A running Kraft server, and `git`.
- A git repository to publish the collection from, if other machines will
  install it.
- The instance defines every [harness](/concepts/vocabulary#harness) and
  [agent profile](/concepts/vocabulary#agent-profile) the plugin requires. The
  example needs the shipped `claude` harness and `strong` profile.

## Publish a collection

### 1. Lay out the collection

A collection is a directory with `.kraft/collection.json` at its root and one
directory per plugin:

```text
acme-kraft/
  .kraft/collection.json
  plugins/
    release/
      .kraft/plugin.json
      library.yaml
      chains/ship.yaml
      skills/release-notes/SKILL.md
```

`collection.json` names the collection and lists its plugins:

```json [acme-kraft/.kraft/collection.json]
{
  "$schema": "https://itsomidkarami.github.io/kraft/schemas/collection.schema.json",
  "name": "acme",
  "description": "ACME's Kraft chains and review methods",
  "owner": { "name": "ACME Platform", "email": "platform@acme.dev" },
  "plugins": [
    { "name": "release", "source": "./plugins/release", "description": "Release chains" }
  ]
}
```

`plugin.json` names the plugin, its version, and what it needs from an
instance. `"kraft": "2"` means any Kraft 2.x:

```json [acme-kraft/plugins/release/.kraft/plugin.json]
{
  "$schema": "https://itsomidkarami.github.io/kraft/schemas/plugin.schema.json",
  "name": "release",
  "version": "1.0.0",
  "description": "Release chains",
  "requires": { "kraft": "2", "harnesses": ["claude"], "profiles": ["strong"] }
}
```

### 2. Write the plugin's files

The files have the same shape as the ones in your own `config/`. Inside a
plugin, a bare `extends:`, `steering:` or `skill:` names the plugin's own
declaration. A bare `harness:` or `profile:` names the instance's.

```yaml [acme-kraft/plugins/release/library.yaml]
tasks:
  implementer:
    kind: agent
    harness: claude
    profile: strong
    prompt: Implement the approved plan, then write the release notes.
    skill: release-notes
    policy:
      time_cap_minutes: 90

  test_changed_scopes:
    kind: builtin
    ref: kraft.verify_changed_test_scopes
    scope: each_repository
```

```yaml [acme-kraft/plugins/release/chains/ship.yaml]
id: ship
description: Implement, write release notes, run the tests for what changed.

nodes:
  - id: implementation
    kind: exec
    tasks:
      - id: implement
        extends: implementer

  - id: verify
    kind: exec
    tasks:
      - id: test_changed_scopes
        extends: test_changed_scopes
```

```markdown [acme-kraft/plugins/release/skills/release-notes/SKILL.md]
---
name: release-notes
description: Write release notes for the change in this worktree.
---

Add one line to `RELEASES.md` for each user-visible change, newest first.
```

A plugin cannot use a component of your local library or of another plugin: it
carries everything its chains extend. It also cannot carry a `subprocess` task
or a permission. [What a plugin may set](/reference/configuration/plugins#what-a-plugin-may-set)
has the list.

### 3. Validate it

```bash
kraft admin plugin validate ./acme-kraft
```

```text
release 1.0.0  sha256:f915f6266d319e9c0bc2bb2483683d74f307839138258901919e7d071fd37da4
```

`validate` runs the checks an install runs and installs nothing. It prints one
line per plugin, then each problem as `error: <file>: <message>`, and exits 1 on
any problem.

- On a machine with a Kraft home, it also checks the plugin against that
  instance: its `requires`, its namespace, and your own chains.
- With no Kraft home, as in CI, it prints a `skipped:` line that names the
  checks it left out. Run it on every push to the collection.

### 4. Try it from the directory

Add the directory itself as a collection, and install from it:

```bash
kraft admin plugin collection add ./acme-kraft
kraft admin plugin install release@acme
```

A plugin from a directory collection has an update whenever its files change,
whatever its version. Edit a file, then run `kraft admin plugin update` and
accept the review. Before you add the published collection in step 5, remove
this one: `kraft admin plugin uninstall release@acme`, then
`kraft admin plugin collection remove acme`.

A directory collection exists on one machine only, and never auto-updates.

### 5. Publish it

Commit the collection and push it to a git host. To release a change later,
raise `version` in `plugin.json` and push. An installed instance sees an update
only when the version changes, so a push without a new version changes nothing
for the people who installed it.

## Install a plugin

### Bound what a plugin's agents may do

A plugin's prompts, steering and skills are instructions an agent follows with
whatever tools your instance allows it. A plugin cannot widen what a run may
do, but with nothing set on the instance an agent may already run any command.
Before you install a plugin from people you do not fully trust, set these on
the instance:

- `maxima:` in [`policy.yaml`](/reference/configuration/policy#defaults-and-maxima),
  so no plugin sets a time, attempt or budget limit above yours;
- [`allowed_tools`](/reference/configuration/policy#tool-lists), so the
  [permission gate](/reference/permissions) answers from your list;
- a [sandbox](/reference/configuration/sandbox) on each repo the plugin's chains
  run in.

[Security](/project/security#kraft-plugins) explains why a plugin carries
limits and never permissions.

### 1. Add the collection

```bash
kraft admin plugin collection add acme/kraft-plugins
```

```text
added collection acme
```

`owner/repo` is a GitHub repository. Any https, ssh or `file:///` git URL
works too, and `--ref` picks a branch, tag or commit. This installs nothing.
`kraft admin plugin collection list` shows what the collection publishes.

### 2. Install the plugin

```bash
kraft admin plugin install release@acme
```

Kraft fetches the plugin, checks it against your instance, and prints a
review. **Reach** lists what decides how far a run goes: gates, merge steps,
harnesses, models and limits. **Content** lists the rest, with every prompt and
skill in full. On a first install everything is new:

```text
release@acme new, 1.0.0
Reach:
  - release:ship.nodes[implementation].tasks[implement]: harness set to 'claude'
  - release:ship.nodes[implementation].tasks[implement].policy: limit time_cap_minutes set, set to 90
  ...
Content:
  - release:ship.nodes[implementation].tasks[implement]: prompt new:
Implement the approved plan, then write the release notes.
  ...
Apply release@acme? [y/N]
```

Read it, then answer `y`. Nothing is installed until you do. `-y` accepts without
asking. A running server loads the plugin at once.

If another plugin or a repository already uses the name `release`, install it
under another namespace with `--as`:

```bash
kraft admin plugin install release@acme --as acme-release
```

### 3. Check it worked

```bash
kraft admin plugin list
```

```text
release@acme  release  1.0.0  f4a11422cc83
```

The columns are the plugin id, its namespace, its version and the commit it is
pinned to. Then read a chain it ships:

```bash
kraft admin templates show release:ship
```

The output starts with `# release:ship (release@acme 1.0.0)`.
`kraft admin doctor` shows `1 plugin(s) load` on its `plugins` row.

## Use what a plugin ships

Everything a plugin declares is named `<namespace>:<name>` from outside it.

- **Run its chain.** Name it when you file an item, or make it a repo's
  `default_chain` in [`repos.yaml`](/reference/configuration/repos#default_chain):

  ```bash
  kraft item create "Cut the 4.2 release" --chain release:ship
  ```

- **Extend a component.** A chain or library component of your own takes a
  plugin's with `extends:` and changes what it needs. An update to the plugin
  reaches your chain too, and its review shows the change:

  ```yaml [config/chains/mine.yaml]
  id: mine
  nodes:
    - id: implementation
      kind: exec
      tasks:
        - id: implement
          extends: release:implementer
          policy:
            time_cap_minutes: 60
  ```

- **Copy it.** A plugin's chains and components are read-only. In the web UI,
  open the chain under **Templates › Chains**, or the component under
  **Templates › Library**, and click **Copy to my library**. Kraft asks for a
  name and opens a draft that is yours to edit. A copy no longer follows the
  plugin's updates. The phone layout has no copy button.

## Keep it current

### Update by hand

```bash
kraft admin plugin update --check
```

```text
release@acme 1.0.0 -> 1.1.0
Reach:
  - release:ship.nodes[implementation].tasks[implement].policy: limit time_cap_minutes raised, 90 -> 120
Content:
  - component tasks.implementer changed
release@acme: update waiting
```

`--check` prints each review and changes nothing. It exits 0 when every plugin
is current, 1 when an update is waiting, 2 when one would be refused and 3
when a collection could not be checked, so a scheduled job can watch for one. `kraft admin plugin update` shows the same reviews and asks about each
plugin in turn.

An item that is already running keeps the plugin version it started with.

### Let a plugin update itself

```bash
kraft admin plugin auto-update release@acme on
```

After each server start, and once a day while the server runs, Kraft checks
the plugin and applies an update whose
review has no **Reach** line: a new version that changes only content, such as
a prompt or a skill. It holds every other update for you and keeps the
installed version running. `kraft admin doctor` shows a held or failed update
on its `plugin updates` row.

`kraft admin plugin collection auto-update acme on` does the same for every
plugin installed from the collection.
[Auto-update](/reference/configuration/plugins#auto-update) lists what is held.

### Put the same plugins on another machine

Copy `plugins.yaml` and `plugins.lock` from `config/` to the other machine's
`config/`, then start Kraft or run `kraft admin reload`. Kraft fetches each
plugin at its locked commit in the background, so both machines run the same
files. The other machine needs git access to the collection's URL.

## Remove a plugin

```bash
kraft admin plugin uninstall release@acme
```

Kraft refuses while one of your own files still names the plugin's namespace,
and lists each reference. Change those first.
`kraft admin plugin disable release@acme` keeps the plugin installed and stops
loading it, under the same rule. Items that are running finish on the version
they started with.

## Serve Claude Code from the same directory

A plugin directory can also be a Claude Code plugin. Kraft reads `.kraft/`,
`library.yaml`, `profiles.yaml`, `chains/` and `skills/`, and nothing else in
the directory:

```text
plugins/release/
  .kraft/plugin.json
  .claude-plugin/plugin.json
  library.yaml
  chains/ship.yaml
  skills/release-notes/SKILL.md
  hooks/hooks.json
  .mcp.json
```

- `skills/` has the layout Claude Code uses, so both tools read the same
  `SKILL.md`. The skill is `release:release-notes` in both.
- `.claude-plugin/`, `hooks/` and `.mcp.json` never reach Kraft. It does not
  install the Claude Code half: do that in Claude Code.
- An alias changes the name on Kraft's side only. A plugin installed with
  `--as acme-release` has `acme-release:release-notes` in Kraft and
  `release:release-notes` in Claude Code.
- A chain of yours that already says `skill: release:<name>` hands that skill to
  the agent. Once a Kraft plugin holds the namespace `release`, Kraft reads the
  skill from the plugin, and the install review lists each such reference.
