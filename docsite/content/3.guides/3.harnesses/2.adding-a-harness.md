description: Add an agent CLI to Kraft with a YAML file, override a shipped harness, and set up Amp, Cursor or Antigravity credentials.
---

Add a new agent CLI to Kraft, or change how a shipped one is launched, by dropping a YAML file into a directory. No Python change and no Kraft release are involved. At the end, a chain task runs on your harness.

## Before you start

- The CLI is installed, on the `PATH` of the shell that starts Kraft, and you can run it headless by hand.
- You know its flags for a prompt, and for each option you want Kraft to set (a model, an effort, a permission mode).
- You know how it reports tokens: in a log one of [Kraft's readers](/reference/harnesses/harness-files#log-readers) parses, or in a file the agent writes.

## Add a harness

1. Create `$KRAFT_HOME/config/harnesses/mytool.yaml` (`~/.kraft/config/harnesses/` by default). Make the directory if it does not exist. The file name without `.yaml` must equal the `id`.
2. Start with the three required capabilities:

   ```yaml
   id: mytool          # must match the file name without .yaml
   kind: cli           # the only kind implemented
   command: [mytool]   # the command and its fixed arguments
   capabilities:
     prompt:  { cli: ["-p", "{value}"] }
     context: { channel: prompt }       # or: { channel: system_prompt, cli: [...] }
     usage:   { source: result_file }   # or: { source: envelope, reader: <parser name> }
   ```

   [Capabilities](/reference/harnesses/harness-files#capabilities) defines each one and the `channel`, `source` and `reader` keys.

3. Add each optional capability the CLI supports, with the `cli:` fragment that sets it. Leave out what the CLI cannot do. A task that asks for a capability you left out is rejected at load, pointing at this file. For a CLI with `--model` and `--effort` flags, add these two lines under `capabilities:`:

   ```yaml
     model:   { cli: ["--model", "{value}"] }
     effort:  { cli: ["--effort", "{value}"], values: [low, high] }
   ```

4. Add a harness profile for the harness in `~/.kraft/config/harnesses.yaml`. The profile's `provider` is your harness `id`. See [the harnesses file](/reference/configuration/harnesses-file) for every profile field.

   ```yaml
   harnesses:
     mytool:
       provider: mytool
       enabled: true
       executable: mytool
   ```

5. In `library.yaml`, set `harness: mytool` on a task that should run on it.
6. Reload so a running server rereads `library.yaml`:

   ```bash
   kraft admin reload
   ```

   Kraft reads `harnesses.yaml` and the harness file again at every agent launch, so those two need no reload.

## Override a shipped harness

Use the same steps, with a file named after a shipped harness: `claude.yaml`, `codex.yaml`, `cursor.yaml`, `opencode.yaml`, `gemini.yaml`, `antigravity.yaml`, or `amp.yaml`.

Your file replaces the shipped one entirely. Copy the shipped definition from [`src/kraft/harnesses/`](https://github.com/itsOmidKarami/kraft/tree/main/src/kraft/harnesses) (one file per harness) and change only what you need. For example, edit `claude.yaml` to change which `effort` values it allows.

## Set up harness credentials

A worker has no one to answer a login prompt, so give each CLI credentials it can use without one. [Run workers on your agent](/guides/day-to-day/agent-integration#run-workers-on-your-agent) lists each harness's login. This section covers the steps it leaves out for Amp, Cursor and Antigravity.

### Pass an API key to a worker

1. Name the variable in the repo's `env_passthrough`, because a worker's environment is an allowlist:

   ```yaml
   # repos.yaml
   repos:
     - path: /path/to/repo
       env_passthrough: [AMP_API_KEY]
   ```

2. Export the variable in the shell that starts the Kraft server.
3. Restart the server.

### Amp

1. On a machine where you ran `amp login`, do nothing more. The login lives under your home directory, which a worker keeps. A [sandboxed](/reference/configuration/sandbox) repository never sees it: its workers get a home of their own, so use step 2.
2. Elsewhere, create an access token (`sgamp_...`) at ampcode.com/settings and pass it as `AMP_API_KEY`, as above.

### Cursor

1. On a machine where you ran `agent login`, do nothing more. The login lives in the OS keychain, which a [sandboxed](/reference/configuration/sandbox) worker cannot reach.
2. With an API key instead (the only way under a sandbox), pass `CURSOR_API_KEY`, as above.

### Antigravity

1. On the machine that runs Kraft, run `agy` once in a terminal and sign in with your Google account. A headless run never signs in by itself: it needs that cached sign-in.
2. The tokens live in the OS keychain, and the CLI's state under `~/.gemini/antigravity-cli/`. A worker keeps both. A [sandboxed](/reference/configuration/sandbox) worker reaches neither, and Kraft has not run Antigravity in a sandbox.
3. Untested in Kraft: with a Gemini API key instead, set `"modelProvider": "gemini"` in `~/.gemini/antigravity-cli/settings.json`, and pass `GEMINI_API_KEY`, as above.

### Check that a worker can log in

File a small work item with a task on the harness. Or run the CLI's own headless command by hand as the same user: `amp -x "say hi"`, `agent -p --trust -- "say hi"` or `agy -p "say hi"`.

Without credentials, Amp prints a device-login prompt and waits about five minutes for a browser before it exits 1. A hang on that prompt means the credentials did not reach the worker.

## Check it worked

```bash
kraft admin doctor
```

Once a chain selects your harness profile, the output has an `agent: mytool` row that gives the path where Kraft found the executable. Kraft pads the name column to the widest check name:

```text
ok    agent: mytool  /usr/local/bin/mytool
```

- A failing `harness: mytool` row means your file did not load. Its detail names the file and the field to fix.
- `kraft admin harnesses` lists the library tasks that select each harness profile.
- File a small work item on a chain that selects the harness profile, and confirm the task runs on it.
