---
title: Switch a task to another harness
description: Run some or all of a chain's agent tasks on Codex, Cursor, OpenCode, Gemini, Antigravity or Amp instead of Claude Code, and what changes when you do.
---

Every agent task Kraft ships runs on Claude Code. This guide moves tasks to
another agent CLI, which Kraft calls a [harness](/reference/harnesses). The
examples use Codex. The steps are the same for the other shipped harnesses.

The harness is a property of the task in your templates. There is no
per-item harness switch: `kraft item set-overrides` changes the model and
effort only. To run one item on another harness, give it a chain that sets the
harness, as in step 2.

## Before you start

- The CLI is installed, on the `PATH` of the shell that starts Kraft, and
  logged in. A worker has nobody to answer a login prompt. For Amp, Cursor and
  Antigravity, see [Set up harness credentials](/guides/harnesses/adding-a-harness#set-up-harness-credentials).
- For Gemini models on an individual Google account, use `antigravity`, not
  `gemini`: Gemini CLI stopped serving free, Google AI Pro and Ultra accounts
  on 2026-06-18. `gemini` still works with a Gemini API key or Gemini Code
  Assist.
- Read the harness's row in the [harness table](/reference/harnesses). It lists
  what that CLI cannot do.

## 1. Check the harness profile

A task names a **profile** from `$KRAFT_HOME/config/harnesses.yaml`, not a
CLI. The shipped file has two profiles, `claude` and `codex`:

```yaml
harnesses:
  codex:
    provider: codex
    enabled: true
    executable: codex
    defaults:
      effort: medium
```

For another shipped harness, add a profile the same way, with `provider` set
to its id (`cursor`, `opencode`, `gemini`, `antigravity` or `amp`). See
[Harnesses file](/reference/configuration/harnesses-file).

A task with `profile: strong` gets its model from the `profiles:` section of
the same file, keyed by provider. The shipped `strong` and `deep` tiers name a
Codex model. `fast` does not, so a `fast` task on Codex cannot start.
`kraft admin templates lint` reports it:

```text
chains/codex-fast.yaml:1:1: chain 'codex-fast' task 'implementation.main.implement': profile 'fast' has no model for provider 'codex' (harness 'codex')
```

No shipped tier names a model for the other harnesses. Add the provider to
each tier a moved task uses before you move it. The shipped `implementer`
uses `strong`, so moving it to Antigravity needs, for example, one more line in
the tier's shipped `providers:` block:

```yaml
profiles:
  strong:
    providers:
      claude: { model: sonnet, effort: high }
      codex: { model: gpt-5.6-terra, effort: high }
      antigravity: { model: gemini-3.8-flash, effort: high }
```

Keep the `providers:` shape. A `model:` or `effort:` beside `providers:` is
refused, and an unreadable `harnesses.yaml` stops every agent task. See
[Agent profiles](/reference/harnesses/agent-profiles).

Amp takes no model, so a task on Amp sets `effort:` itself instead of a
profile.

## 2. Pick which tasks move

List the tasks each profile runs:

```bash
kraft admin harnesses
kraft admin harnesses claude
```

Then choose how far the change reaches.

**Every chain.** Change `harness: claude` to `harness: codex` on the tasks you
want to move in `library.yaml`. Every chain that extends them follows.

**One chain.** Leave the library alone and override the task in the chain
file. A key set next to `extends` wins over the library's:

```yaml
# chains/codex-impl.yaml
id: codex-impl
nodes:
  - id: implementation
    kind: exec
    tasks:
      - id: implement
        extends: implementer
        harness: codex
```

**One item.** File it on a chain like that one, with
`kraft item create "title" --chain codex-impl`, or switch an item that has not
started with `kraft item set-chain ID --chain codex-impl`.

Kraft's own `kraft:` skills, such as `kraft:code-review`, are sent to the agent
in its instructions, so they work on any harness. A skill from another plugin
(`plugin:skill`) needs that plugin installed for the new CLI. If it cannot
load, the task stops and asks for it.

## 3. Allow the profile

Skip this step if nothing in your policy sets `allowed_harnesses`.

`allowed_harnesses` can appear in `policy.yaml` under `defaults:` or
`maxima:`, in a repo's `policy:` in `repos.yaml`, or in a chain, node or task
`policy:`. When it is set, it must include the new profile. Otherwise Kraft
refuses the item when you file it:

```text
kraft: 422: policy.allowed_harnesses: implementation.main.implement: harness 'codex' is not in its allowed_harnesses ['claude']
```

## 4. Check tool lists

An `allowed_tools` list in the task's policy can stop the new harness from
launching:

- `gemini` and `antigravity` have no way to restrict tools, so they refuse to
  launch under any `allowed_tools` or `deny_tools` list.
- `codex` enforces the list through Kraft's permission hook, which never sees
  its web search. It refuses a list that leaves out `WebSearch`.
- `cursor` refuses a list that leaves out `WebFetch` and `WebSearch`, for the
  same reason.

The refusal happens at launch. The item stops for you, and the stop reason
names the harness and the missing tools. Add the tools to the list, or keep
that task on Claude. See [Policy fields](/reference/configuration/policy#policy-fields)
and the [Permission gate](/reference/permissions).

## 5. Decide where escalation runs

An escalation turn runs on `claude` unless policy says otherwise. To move it
too, set `escalation_harness` in `policy.yaml`:

```yaml
defaults:
  escalation_harness: codex   # or `item`: the harness the item's last agent task ran on
```

See [Fallback and escalation](/reference/harnesses/fallback-and-escalation).

## 6. Load it

```bash
kraft admin templates lint
kraft admin reload
```

## Cost reporting changes

Codex, Cursor, Amp and Antigravity report tokens but no cost. Kraft estimates
it from `prices.json` when it can price the model:

- Codex on the model it launched with.
- Amp and Antigravity on the model their log names (Antigravity names one only
  when launched with a base model id, such as `gemini-3.8-flash` with `effort`
  set).

These can't be priced:

- Cursor unless it is launched with a model the table lists.
- A Codex task that passes no model.
- Any model the table lacks.

For those:

- `budget.work_item_usd`, `budget.daily_usd` and `kraft item create --budget`
  count their sessions as $0 and warn once on the item's timeline.
- A per-scope `budget_usd` treats their spend as unknown and stops the next
  launch in that scope for you. No higher cap passes that stop; see
  [Raising a cap](/concepts/caps-and-budgets#raising-a-cap-on-a-stuck-item)
  for `budget_usd=none`, the way past it.
- The board shows their tokens, with no dollar figure.

`kraft admin doctor` warns about each such harness. Use `token_budget` to
bound them. See
[Harnesses that report no cost](/concepts/caps-and-budgets#harnesses-that-report-no-cost).

## Verify

```bash
kraft admin harnesses
kraft admin templates show codex-impl --resolved
kraft admin doctor
```

- `kraft admin harnesses` lists the moved library tasks under the new profile,
  and in its CHAINS column every chain that selects it, a chain-level
  override included.
- `show --resolved` prints `harness: codex` on each task you moved.
- `kraft admin doctor` has an `agent: codex` row once a chain selects the
  profile. It fails when the executable is not on `PATH`, naming the chains
  that cannot run without it.

File a small item on the chain. `kraft view show ID` shows its token count and
no dollar figure once a Codex session has run.
