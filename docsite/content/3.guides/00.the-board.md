---
title: The board and the web UI
description: A tour of Kraft's web UI, desktop and phone, for a new user. It covers the board, an item's page, the review page, filing an item, the first-run setup, Templates and Settings.
---

Kraft's web UI is the server's own page: start `kraft` and open
`http://127.0.0.1:8765`. Most of what the CLI does to a work item, you can
also do here. Three verbs are CLI-only: `kraft item abandon`,
`kraft item set-attachments` and `kraft item mr-label`. This page walks
through each screen and names the buttons you will see. For what a work item, chain, node and gate are, see
[Vocabulary](/concepts/vocabulary).

The sidebar on the left reaches every page. **Search** (**⌘K**, or **Ctrl+K**)
opens a search box over any page that finds work items, documents, beads and
pages. An item waiting at a gate shows there as **Review** and the gate's name,
and opens straight onto that gate's review. A document opened from a search
shows the search's matches in it, with **↑**/**↓** to step through them.
**Filters** at the right of the tabs narrows the documents. Below Search are
**Board** and **Analytics**, then **Templates** (Chains, Library) and
**Settings** (Repos, Harnesses, Policy, Auto-intake, Notifications, Access,
Appearance). The foot of the sidebar shows the version, and **update** beside
it when a newer Kraft is available or an update waits on a restart; it opens
**About**. The sidebar starts pinned open. The button at the top right of the
sidebar (**⌘\\**, or **Ctrl+\\**) unpins it: it then takes no room, and
opens over the page while the pointer is at the left edge of the window or
over the sidebar, closing shortly after the pointer leaves. Keyboard focus
opens it too. Your choice is kept in the browser.

In any box you write a steer, an answer, a note, a reason or a comment in,
**⌘↵** (**Ctrl+Enter**) sends it, as its button would. **Enter** starts a new
line.

## The first run

With no repo connected, the board shows **Nothing on the board yet** and three
setup steps. The header's **+ New work item** is there too, so you can file
work without finishing them; filing one ends the setup.

1. **Connect a repo.** Type the path to a local git checkout and click
   **+ Add repo**. When the server was started inside a checkout that is not
   connected yet, a **Try** line under the field offers its path: click it to
   fill the field. Before you add anything, the panel beside the step lists
   what Kraft will probe (`.gitmodules`, `.beads/`, the test command and the
   forge remote), each marked **after you add**. Kraft then probes the repo and
   lists what it found: those, the setup command and more. Check them, then
   click **Add repo**. It does what `kraft repo connect` does. A repo with no
   commit yet cannot be added: the wizard says so beside **Add repo**. Commit
   its files, then click **Check again**. **Skip to chain →** moves on to step
   2 without a repo; the step is not marked done until one is added.
2. **Chain and policy.** Shows the chain every item uses unless it names
   another (`default`) and the policy's fix attempts and dollar cap. **Open
   Chains** takes you to the chain; **Continue** moves on.
3. **First work item.** **+ New work item** opens the composer described below.
   This step also says what Claude workers need before you start an item:
   Kraft's MCP server, from the Kraft plugin or from `kraft admin init`, not
   both. **Copy commands** copies the plugin install commands. **Go to the
   board** leaves the wizard without filing anything.

The wizard first shows while no repo is connected. Once you add one, it stays
on the board until you leave its last step, with **+ New work item** or **Go
to the board**, or until the first work item exists, wherever it was filed:
an item filed from the CLI while the wizard is open ends it, and the board
shows the item. If you reload the page, or follow a link to another page and
come back, it opens at the step you were on. This browser remembers it.

A repo where Kraft found no test command is connected disabled. The wizard
says so (**No test command: connected disabled. In Settings › Repos, set its
test command and Enable it, then publish.**), and step 3 reminds you that
**New work item** cannot file to it yet: the composer and the new-item page
list only enabled repos. Before you file work on it, open **Settings ›
Repos**, select the repo, set its **test command**, click **Enable**, then
**Review & publish**.

A repo where Kraft found no setup command is connected without one, enabled or
not. The wizard says so too: **No setup command found: its first work item
stops before it starts until you set one, or tick No setup needed, in
Settings › Repos**. An item on it stops at once, before its first node runs,
and its stop names the missing `setup_command`. In **Settings › Repos**, select
the repo and set its **setup command** (such as `npm ci` or `uv sync`), or tick
**No setup needed** for a repo with nothing to install. Then **Review &
publish**.

When the tests are in subdirectories, the wizard names them: **No setup
command: web has tests and nothing found prepares it.** It lists each
directory that has tests and nothing to prepare them. Set a setup command that
covers them, in **Settings › Repos**.

## The board

![The Kraft board: work items grouped by Needs you, Running, Not started, and Done](/assets/board.png)

The board lists every work item in four groups:

- **Needs you**: a gate waits for your approval, an agent asked a question,
  the item stopped on a failure or a cap, or a person paused it mid-chain. It
  always comes first, and the header shows how many with **N NEED YOU**. The
  sidebar's **Board**, an item page's **N others need you** and the phone's
  **Board** tab count the same items.
- **Running**: an agent or a check is working on it.
- **Not started**: filed paused and never started.
- **Done**: completed and cancelled items. It shows the five most recent;
  **show all N** shows the rest.

Each row shows the title, then the repo, the item's ID, its chain, how long
ago it changed, and why it is where it is (`approve spec`,
`failed at implementation`, `created paused`). The ticks on the right are the
chain's nodes, filled in as the item moves along it. A row that needs
something carries one button:

| The row says | It does |
|---|---|
| **Review to approve** | opens the item's review page at the waiting gate, with the gate's brief open beside the diff |
| **Answer** | opens the side panel at the agent's question |
| **Raise cap** | for a time or attempts cap: opens the side panel's Config tab, where the cap is |
| **Retry…** | for a failed item or a stuck fix loop: opens the side panel, where Retry is |
| **Resume** | resumes a paused item that has already started |
| **Raise budget** | for a dollar or token budget stop. If the stop was a policy `budget_usd` cap, opens the side panel's Overview with the **Raise budget cap** dialog open. If it was the item's own cap, opens the Config tab with the budget editor open. When the item cannot raise it (the day's cap, say), the panel stays on Overview, whose banner says so; the panel's main button is then **Retry** |
| **Open** | opens the side panel for any other stop |

A row that has not started has no button. Start it from the side panel.

### Filter, Group and Sort

- **Filter by title or id** narrows every group as you type. Press **/** from
  anywhere on the board to jump to it.
- **Chain ▾** shows only items on one chain.
- The **all repos ▾** menu beside **Board** at the top shows only one repo.
- **Group** sorts the rows into groups by **Status** (the default), **Repo**
  or **Chain**. **Needs you** comes first in all three.
- **Sort** orders the rows within a group: **Needs attention**, **Recently
  updated**, **Created** or **Title**.

The filter, group and sort are kept in the page address, so a link you share
opens the same view.

### Selecting several items

Tick a row's checkbox (or press **Space** on a row) to select it. A bar
appears at the bottom with what you can do to the selection:

- **‖ Pause N** pauses the selected items that are running.
- **Cancel N…** cancels every selected item that has not ended. It asks for a
  reason first, and the reason goes into each item's run log. For a few
  seconds after you confirm, **Undo** in the message at the bottom takes it
  back.
- **Archive N** archives the selected items that are completed or cancelled.
  It is greyed out until you select one of those.
- **Clear** drops the selection.

**Select all** on the **Done** header selects every finished item, so
**Archive** clears them off the board in one go. If some of the items refuse
the action, the bar lists each one with its reason and keeps them selected.

### Archived items

The **Done** header carries a link, **completed and cancelled · auto-archive
after 30 days** (the number is `archive.after_days` in
[`policy.yaml`](/reference/configuration/policy)). It opens **Archived**, at
`/archived`, which lists every archived item. Filter it, sort it by
**Recently archived**, **Created** or **Title**, and click **Restore** on a
row to put it back on the board. Tick several rows for **Restore N**. On a
phone, **Archived** is under **More**: open an item there to restore it.

### The side panel

Click a row and a panel opens on the right, over the list, without leaving
the board. Its heading shows the item's title, and under it the item's ID,
its group and why it is there. It
has three tabs:

- **Overview**: the item's state card with what it is waiting on and the
  buttons to act on it (approve, answer, retry, raise a cap, escalate), and a
  short view of the chain with the node it is at. A stuck fix loop's card
  gives its reason, **Retry from** the task, and **Escalate…**.
- **Activity**: every event on the item, newest first. **Show earlier** loads
  more. Click an event about a node to open that node.
- **Config**: the limits the item runs under (its budget, tokens, the day's
  spend across all items) and anything changed for this item alone. The pencil
  beside **Budget** edits the item's dollar cap.

The bottom of the panel holds the item's main action, the same as the item
page's header (below). **Open item ↗** and **Focus** both open the item's
full page.

To skip the panel, **⌘-click** (**Ctrl-click**) or double-click a row. Set
**Settings › Appearance › Board › Open items in** to **Full page** to make a
plain click do that too. **↑** and **↓** move between rows. **Esc**, the
button at the panel's top right, or a click anywhere outside it closes the
panel. While it is open, **Tab** from the selected row goes into the panel and
on to the next row after it. The row buttons the panel covers are skipped, as
a pointer cannot reach them either.

## An item's page

![An item's page: the chain drawn as a graph with the spec_approval gate selected, and the inspector on the right showing the gate's files, open threads, and Approve and Reject buttons](/assets/item.png)

An item's page, at `/work-items/<id>`, is under **Board › repo › item** in
the header: **Board** goes back to the board, and the repo opens the board
filtered to that repo. The page has its title and brief at the top
(**edit** changes the brief), then the size of the change so far with a
**Review changes** link, and a banner when the item needs you, such as
**Waiting for your approval at `spec_approval`** with **Review changes**, which
opens the review page at that gate with the gate's brief beside the diff.

The header at the top right shows how long ago the item was created (or how
long it ran, once it has ended), its status, and the main action, which is
always one the item can take:

| The item | Main action |
|---|---|
| never started (**NOT STARTED**, here and on the phone, never **Paused**) | **Start** |
| running or waiting | **‖ Pause** |
| paused | **Resume** |
| at a gate | **Open gate**, which selects the gate (on the review page, opens its document) |
| asking a question | **Answer**, which goes to the answer box |
| stopped at a cap or a budget it can raise | **Raise cap**, which opens the cap's editor on Config |
| stuck, failed, or with an escalation running | **Retry** |
| stopped on a rebase conflict | **Review conflicts** |
| stopped because its MR was closed | **Reopen MR** |
| done or cancelled | **Archive** |
| archived | **Restore** |

Clicking the main action's name runs it. Its **▾**, or the pointer resting on
it, opens a menu over it with the main action first and then the others that
fit the item's state: **Escalate…**, **Mark complete…**, **Archive** and
**Cancel…**. Each of those that asks for more opens a card under the button.
The **⋮** menu holds **Review changes**, **Item settings**, **Open worktree in
editor**, **Copy ID**, **Copy link**, and **Escalate…** and **Cancel…** (or
**Duplicate as new item** once the item has ended). **Escalate…** is offered
only on an item stopped or paused, and not while an escalation is already
running. Click the title to rename the item: **Enter** or clicking away saves,
**Esc** cancels. The line under the brief counts the changed files and, when
there are any, the open review threads.

### The chain graph

The middle of the page draws the item's chain, frozen when the item was filed,
node by node. A box is an agent or a command (an exec node); a diamond is a
gate. Each node shows how it went and how long it took, and a gate that sends
work back draws a **reject** arc to the node it reruns.

- Click a node to show it in the inspector.
- Double-click a node, or press **Enter** on it, to open its own view at
  `/work-items/<id>/nodes/<node>`, which draws the tasks inside the node.
  **← chain** goes back.
- Drag to pan. The controls at the bottom right zoom in and out, fit the
  chain to the window, and centre on the current node. An item that has not
  started opens at a readable size, never under 80%, starting from its first
  node; pan to see the rest.

### The inspector

The panel on the right of the graph shows whatever you selected: the chain,
a node, a gate or a task. Its heading names it, and **Focus** opens it on its
own. The button at the top right folds the panel away.

- **The chain**: **Overview** has the item's status, progress, the node it is
  at, the spec or plan attached when it was filed, what it has spent, and its
  recent events. Click an attachment's name to read it, even before the item
  starts. **Config** has its limits and overrides, as in the side panel.
- **A node**: **Overview** has its progress, what runs next, what it spent and
  its steps, with **Retry** to rerun it once the item has stopped. A paused
  item offers **Resume** there instead, and a running or waiting one no
  Retry. **Config** has its settings. Clicking
  a step, or a step's task, opens the node's own view with it selected, as
  **Focus** does.
- **A task**: **Overview**, **Input**, **Output**, **Log** and **Config**.
  **Overview** names the harness and model the attempt ran on. **Log** is the
  agent session's own log; **full screen** spreads it over the whole window,
  and **Esc** brings it back. When a task ran more than once, **‹ attempt n of m ›**
  above the tabs picks the attempt every tab shows. The tabs follow the newest
  attempt as it starts. Pick an earlier one and they stay on it, while the
  count shows the newer ones; step back to the newest to follow again. A task
  that asked you a question also has a **Thread** tab, which shows the
  conversation up to the turn you picked. On the escalation the switcher
  counts turns, **‹ turn n of m ›**, as its **Thread** tab does.
- **Before the item starts**, each Config row shows the value that applies
  and a chip naming where it comes from: **chain** (this item's chain),
  **policy** or **policy maximum**, **item policy** (the item's own
  `kraft item set-policy`), **item-wide** or **node** (an item-wide or node
  override), **profile** (the task's agent profile), **repo** (the repo's
  `models:`) or **harness** (the harness's default). ✎ sets it for this item
  and ↺ drops that. The chain's Config sets the model and effort of every agent
  task. An exec node's Config sets its agents' model and effort, its fix
  loop's attempts, whether it auto-escalates when stuck, and an extra prompt
  for its agents. These save at once, like `kraft item set-overrides` and
  `kraft item set-node-override`. A task's own fields and the time and spend
  caps go into the item's draft, which **Review & apply** applies. Their chip
  reads **draft** until then. A cap set on a node is that node's own: the
  item's budget still applies. **Changed for this item**, under the chain's
  Config, lists all of it: the item-wide and node overrides, and each draft
  change, marked as not applied yet. **Start** never applies a draft on its own: with
  one, it asks first, with **Apply and start** and **Start without them**.
  **Start** in the board's side panel opens the item's page to ask the same,
  and the phone asks in a sheet. Once
  the item starts, the item-wide and node rows are gone. Later nodes still take
  draft overrides. A draft edit on a node the run has already reached can no
  longer apply, and **Review & apply** offers to take it out of the draft.
  **Review & apply** lists the exact change and checks the draft against the
  policy before it applies. An override above a policy maximum is shown as a
  problem, and **Apply** stays off until you fix it. Each node the draft adds
  shows which harnesses it may use and what it is estimated to cost, from the
  average of that node's earlier runs, or "no estimate yet". **Start** on an
  item with unapplied changes opens the same dialog first.
- **A gate that is waiting**: the files changed so far, the open review
  threads, the document it decides on, and where a rejection sends the work.
  At the bottom, **Read** followed by the document's name opens it in a panel
  on the right (**full screen** widens it),
  **Review changes** opens the review page, and **Approve** and **Reject…**
  decide the gate.

## The review page

![The review page: the file tree on the left, a diff of calc.py, and a comment being written on lines −2 to +2 (the removed line and its replacement) with Must fix selected, above the Your review bar with Finish review](/assets/review.png)

**Review changes** opens the review page at `/work-items/<id>/review`. You can
open it at any point in the item's life, not only at a gate. The file tree is
on the left, the diff on the right, and a bar along the bottom holds your
review.

### Compare

The toolbar reads **Compare** *from* **and** *to*:

- **Compare from**: **base**, the item's starting point; an earlier
  attempt; or **your last review**, to see only what changed since you last
  submitted one.
- **Compare to**: **latest (attempt N)**, the current state of the branch, or
  an earlier attempt.

Attempts are listed while a gate waits for you.

**All nodes ▾** limits the diff to the files chosen nodes touched. On the
right, the toolbar collapses or expands every file, and the list button holds
the diff settings: **Side-by-side** or **Inline**, whitespace changes, changed
words, line wrapping, and one file at a time.

### Viewed

Each file's header has **Viewed**. Tick it once you have read the file: the
tree marks it, and the foot of the tree counts how many you have viewed out of
the total. Each header also has a button to comment on the whole file, and a
**⋮** menu with **Copy diff** and **Copy path**.

### Commenting on a line

Hover a line and click the **+** that appears at the left of its number. To
comment on a few lines, drag the **+** down to the last one you want; the
lines shade as you go. A drag stays inside one hunk of the diff. For a longer
range, click the first line's **+** or number, then **Shift**-click the last
one's. Dragging down the numbers picks a range too. **c** or **Enter** also
opens the box on a pick.

Each side has its own lines. In **Side-by-side**, each half has its own **+**.
In **Inline**, an unchanged line has two numbers. To comment on the old file's
line, click the left number, then **+**. To comment on the new file's line,
click the right number, then **+**.

A range can run across sides, as GitLab's and GitHub's do. Drag from a removed
line's **+** down to the line that replaced it, or **Shift**-click it. In
**Side-by-side**, drag or **Shift**-click across to the right half. The range
then covers every line between its two ends.

A comment box opens under the last line. Its header names the lines, marked as
the diff marks them: **Line +5**, **Lines +5 to +7**, **Lines −2 to +2**. The
thread it makes is headed the same way. While the box is open, the shaded
range has a small handle on its first and last rows. Drag one to move that end,
even past the other end, which flips the range. **Shift**-click another line, or press
**Shift+↑** or **Shift+↓**, to move the end too. The box keeps what you wrote,
and **×** next to the lines goes back to the last line alone. A suggested change you typed moves with the range, and the
box says which lines it was written for; on a range across sides it is set
aside, and not sent, until the start is back on the new side.
Once you add the comment, its thread stays under the last line, headed with
the lines it covers. A thread on no file, such as one from `kraft item comment
--body` alone, is listed above the files under **On the whole change**. A range's lines stay shaded and are quoted in the thread,
and the agent that reads the thread gets the same quote, as it does for one
made with `kraft item comment` or an agent's `add_review_comment`, which Kraft
quotes from the diff. The pick clears when
the box closes.

In the comment box:

- Pick a label: **No label**, **Must fix**, **Question** or **Nit**. A
  **Must fix** comment blocks every gate approval on the item until it is
  resolved.
- Write the comment. Markdown works, and **Preview** shows it rendered.
- **± Suggest change**, on lines of the new side, adds the lines you picked,
  for you to edit into the code you want. Left as it was, it is not sent. It
  is off for a range that runs across lines the diff doesn't show, and a range
  across sides has none.
- **Add to review**, or **⌘↵** (**Ctrl+Enter**), keeps it as a draft. Drafts
  reach no agent until you finish the review. **Cancel** or **Esc** asks
  before it throws away what you wrote.

From the keyboard, focus a file's lines and use **↑** and **↓** to pick a
line, **Shift+↑** and **Shift+↓** to extend the pick, **c** or **Enter** to
comment, and **n** and **p** to move to the next or previous file. **Tab**
from the lines reaches the picked line's **+**. **Shift** with the arrows keeps
to one side, so a range that crosses sides is made with the mouse: the handles
or **Shift**-click.

### Finish review

The bar at the bottom reads **Your review** with your drafts counted:
**N pending, N must fix, N unlabeled**. **Finish review** opens **Finish your
review**, which lists the drafts it will send, takes an optional overall note,
and offers three outcomes:

- **Request changes** sends the threads back to the node that wrote the code
  they are about. It says which node that is and which fix round this would
  be, before you submit.
- **Comment only** sends the threads without stopping anything. Agents answer
  questions in the thread; at a gate, the gate stays open.
- **Approve** passes the pending gate, the same as Approve on the gate. It is
  only offered at a gate, and stays greyed out while a must-fix thread is
  open.

**Submit review** sends it. Once a review has gone out, the bar reads **N of M
resolved** and offers **Request changes** and **Approve** directly. A comment
you add after that shows there as pending, **Finish review** comes back beside
them, and **Approve** opens **Finish your review** first, so a new comment is
never sent with an approval unseen. [Reviewing a change](/guides/review-a-change#in-the-web-ui)
lists the CLI verb behind each of these.

### At a gate

**Review changes** from a waiting gate opens the review page with the gate's
document first, rendered, and the gate along the top: its name, **WAITING FOR
YOU**, how many comments are pending, and **Request changes** and **Approve**.
The changed files are listed on the right; **Review changes** below them
switches to the diff.

## Filing a work item

**+ New work item**, at the top right of the board, opens a composer at the
top of the list:

- **Title**, and a line of brief that every node reads.
- The **repo** and the **chain**, each a menu. The repo menu lists only
  enabled repos; with none, the composer says so, links **Settings ›
  Repos**, and creates nothing. The chain menu shows each chain's node and
  gate count, and marks the repo's default.
- **+ spec** and **+ plan** attach a document: search the repo's specs or
  plans, or paste a path relative to the repo. The file must be inside the
  repo, since it is committed on the item's branch: copy one kept elsewhere
  into the repo first, for example to `.engineering/specs/`. A chain that starts by writing
  a spec or a plan skips that node and its gate when you attach one.
- **N of N nodes run · N gates** says what will run, as the server works it
  out from what you attached.

**Create paused** files the item without starting it, so nothing spends
tokens until you start it from the side panel. The **▾** beside it holds
**Create and start**. **⌘↵** (**Ctrl+Enter**) also creates and starts.

**More options ⤢** carries the draft to the full new-item page at
`/work-items/new`. It adds a larger brief, **Start from existing** with the
**+ spec** and **+ plan** slots, and the chain drawn as a graph. Click a node
to look at it or skip it for this item, and set overrides for this item alone
in the inspector's **Config** tab. Its **Create paused ▾** works the same
way. Nothing is created until you click it, and **Cancel** discards the
draft.

## Templates

**Templates** holds the two files an item is copied from, the chains and the
library, as screens. Each one edits a draft: your changes take effect when
you click **Review & publish**, which shows what changed and checks it first.
**YAML** shows the file itself. Open items, every one not done or cancelled,
keep the chain they were filed with. The screens count them as **open**, not
running: the board's **Running** group is only the ones an agent or a check
is working on now. Repos, Harnesses, Policy and Auto-intake edit a draft the
same way, under **Settings**.

- **Chains** draws a chain as a graph, picked from the menu beside
  **Chains**. Click a node to see and change its settings in the inspector;
  double-click it to open its own view of steps and tasks. The pencil opens
  the chain's own settings. Click the name at the top of the inspector to
  rename it in place: **Enter** renames it, **Esc** keeps it. Renaming the
  chain itself shows as `old → new` beside **Chains** until you publish, and
  **Review & publish** lists it as a change: publishing moves its file to the
  new name, and new items name the new id. A task's
  **Config** tab leaves out the agent settings a command or merge-request task
  never uses, unless its on-failure recovery runs under them, and a yes/no
  setting is a switch. **Duplicate** copies the chain under a new name. See
  [Write your own chain](/guides/write-your-own-chain).
- **Library** lists the components chains are built from, under **Nodes**,
  **Steps**, **Tasks** and **Steering**, each with how many chains use it.

## Settings

- **Harnesses** lists the agent CLIs Kraft can drive and whether each is
  available, and the profiles tasks pick a model by. **+ Profile** adds one.
  See [Switch a task to another harness](/guides/switch-harness).
- **Repos** lists the connected repos with each one's chain, steering, test
  command and state. **Connect repo** adds one. Given a repo already
  connected, it offers **Update** instead, which saves only what the repo's
  entry left undecided, as `kraft repo connect` does. A repo with no commit
  yet cannot connect: **Check again** reads it once you have committed. Select a repo to change its
  fields; **No setup needed**, beside its **setup command**, says that a fresh
  checkout needs nothing installed (`setup_command: ""`). **No tests**, beside
  its **test command**, says the repo has no tests (`test_command: ""`): its
  items pass verify without running any, and the list shows
  `no tests (passes verify)`. Untick it and the test command is not set, which
  stops each item at verify. See [Repos](/reference/configuration/repos).
- **Policy**: time, token and dollar caps for each scope: the whole install,
  the work item, and each node. See [Caps and budgets](/concepts/caps-and-budgets).
- **Auto-intake**: whether Kraft picks up ready beads by itself, and its
  schedules (**Add schedule**), both in `intake.yaml`. How many items run at
  once is Policy › Housekeeping. See
  [Schedule or webhook work](/guides/schedule-and-webhook-work).
- **Notifications**: where Kraft tells you it has stopped for you: a
  **Webhook**, and **This browser**. **Send a test** checks each one.
- **Access**: who can reach the board. **This machine only** (`127.0.0.1`,
  no password) or **Local network** (`0.0.0.0`, password required), the port,
  the allowed hosts and the password. A change takes effect on restart. See
  [Remote access](/guides/remote-access).
- **Appearance**: **Light**, **Dark** or **System**; how much colour; the
  surface and accent colours; and, further down, the board (**Open items in**:
  **Peek** or **Full page**), the review diff's layout and syntax
  highlighting, and the **Default editor** that **Open in editor** uses (the
  editors found on this machine, or **Not set**: `KRAFT_EDITOR`, else the
  system's default app). It is saved in
  `theme.yaml`.
- **About**, from the version line at the foot of the sidebar: the version,
  whether an update is available or waits on a restart, the command to install
  it, the release channel, and this instance's address, run directory and
  health.
  **Copy diagnostics** copies them for a bug report.

## On a phone

![The board at a 390px phone viewport, with bottom tab navigation](/assets/mobile.png)

On a screen narrower than 768 pixels Kraft shows its phone layout at the same
address. Widen the window to get the desktop back.

The phone has no first-run wizard. With no repo connected, the board says
"No repository is connected": connect one from a computer, or run
`kraft repo connect` in the repo on the machine Kraft runs on.

- A bar at the bottom holds **Board**, **Search**, **Analytics** and **More**.
  **More** lists Templates (Chains, Library), Settings (Repos, Harnesses,
  Policy, Auto-intake, Notifications, Access, Appearance, About), Analytics
  and **Archived**.
- The board filters by **All**, **Needs you**, **Running**, **Not started** and
  **Done**, the desktop board's groups. A card
  that needs you carries its own buttons, such as **Approve** and **Reject…**
  for a gate, or **Retry…** for a failed item. The **+** button files a new
  work item.
- An item opens as its chain, node by node: tap a node for its tasks, a task
  for its log.
- A stopped item has an action bar at the bottom with two buttons chosen by why
  it stopped: **Reject…** and **Review and decide** at a gate, **Escalate** and
  **Retry** for a failure, and so on.
  [Remote access](/guides/remote-access#on-the-phone) lists every stop and
  its buttons, and how to reach Kraft from your phone.
