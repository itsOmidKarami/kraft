Kraft Lite starts no server, port or database. It reads the same chain files
Kraft reads, and walks the same ordered nodes, gates and fix-loop caps. It is
the attended half of Kraft: the chain runs in front of you and resumes across
sessions, but it doesn't outlive your terminal. Lite is a Claude Code plugin.
The repository also ships manifests for Cursor, Gemini CLI and Antigravity, and
Amp and OpenCode load its skills from a folder.

Unlike the [`kraft` plugin](/guides/day-to-day/agent-integration), Lite needs neither
the `kraft` binary nor an MCP server.

## Before you start

- Python 3.10 or newer, and nothing else. Check with `python3 --version`.
- Claude Code, or one of the [other harnesses](#other-harnesses).

## Install

Lite ships in the same plugin marketplace as the `kraft` plugin:

```bash
claude plugin marketplace add itsOmidKarami/kraft
claude plugin install kraft-lite@kraft
```

Add `--scope project` to either command to keep it to one repo. Update with
`claude plugin update kraft-lite`.

### Other harnesses
_Added in 2.3_

On the harnesses below, two things differ from Claude Code:

- Skills aren't namespaced. `/kraft-lite:next` is the skill `next`, and where a
  skill's text says `kraft-lite:<name>`, the agent uses `<name>`.
- There is no plugin-root variable, so each skill finds `kl.py` two directories
  above its own file. Keep the plugin folder whole: a copy of `skills/` alone
  leaves `kl.py` behind.

Each install reads a local clone of the Kraft repository. The commands below
call its path `<kraft>`; clone it first:

```bash
git clone https://github.com/itsOmidKarami/kraft
```

#### Gemini CLI

Install the folder as an extension, then restart the CLI:

```bash
gemini extensions install <kraft>/plugins/kraft-lite
```

`gemini skills list` then lists the seven skills. To update, pull the clone,
then run `gemini extensions update kraft-lite`. Installing from the GitHub URL isn't
covered: the extension sits in a subfolder of the repository.

#### Antigravity

Install the folder as a plugin:

```bash
agy plugin install <kraft>/plugins/kraft-lite
```

`agy plugin list` shows it. The skills become slash commands by their own
names, such as `/next`. That the install copies `kl.py` along with the skills
isn't checked yet: if a skill can't find it, that is why.

#### Amp

Point Amp's skills path at the folder's `skills/`, in `~/.config/amp/settings.json`
or a repo's `.amp/settings.json`:

```json
{ "amp.skills.path": "<kraft>/plugins/kraft-lite/skills" }
```

`amp skills list` then lists them. Pull the clone to update.

#### OpenCode

Add the folder's `skills/` to `opencode.json`. Slices need OpenCode 2.0.0 or
newer. On 2.x:

```json
{ "skills": ["<kraft>/plugins/kraft-lite/skills"] }
```

On 1.x the key is `{"skills": {"paths": [...]}}`. Use the absolute path, and
don't symlink single skill folders into `~/.config/opencode/skills`: the agent
then looks for `kl.py` next to the link. Pull the clone to update.

A skill elsewhere with the same name can win over Lite's. Gemini CLI has a
built-in `/init`, and your own or a workspace's skills override an extension's.
Amp searches `~/.claude/plugins/cache/` before `amp.skills.path`, so a Claude
Code install of Lite there is the one Amp finds.

## Run your first chain

In a session in the repo:

1. Run `/kraft-lite:init`, once per repo. It detects the test command, the CI
   command, and which installed skills can run a task, and writes an editable
   `.kraft-lite/bindings.yaml` of the choices that differ from the defaults.
   You can skip it: every task has a default.
2. Run `/kraft-lite:start` and say what the work is. It makes a chain from the
   default chain, unless you name another chain or a chain file, and runs the
   first node. It reports the chain's ID, which chain it froze and where that
   came from, and where its state lives: `bd`, or a file under `.kraft-lite/`.
3. Run `/kraft-lite:next` to run the next node. It also resumes a node after a
   gate, a new session or a cleared context.
4. At a gate, run `/kraft-lite:gate`. It presents what the gate needs decided,
   then records your approval or rejection.
5. Run `/kraft-lite:status` at any time to see which node is live, what blocks
   it, and how many fix attempts are spent.

## Check it worked

After the install, run `/kraft-lite:init` in a repo, then `/kraft-lite:status`.
Status reports that no chain exists yet. After you start one, it names the
chain's first node (`spec`, in the shipped chain).

## How Lite works

- **Nodes.** The shipped chain is Kraft's `default`: nineteen nodes, from spec and plan through implementation and verification to opening a merge request, checking it, review by a person, merge and a check of the merged branch's CI. Five are gates, where a person decides.
- **Freezing.** A chain freezes when it starts, resolved, in `.kraft-lite/chains/<chain-id>.json`. You can't reorder, add or remove its nodes, and editing the chain file later doesn't retarget a run in flight.
- **State.** Lite keeps state in [beads](/concepts/vocabulary#beads) (`bd`) when the repo has it, and otherwise in `.kraft-lite/chain.jsonl`. The format is the same `bd export` format either way, so adopting `bd` later is `bd import`.
- **Several chains.** One directory can hold several chains. With two or more unfinished chains, each command needs `--chain-id <id>`.

## Where chains come from

Lite reads the files Kraft reads: a `library.yaml` and its `chains/*.yaml`. With no `--chain`, `start` runs the repo's `repo:default` when `.kraft/chains/default.yaml` exists, and `default` otherwise: your Kraft home's entry, which on a stock home extends the bundled one.

To run another chain, name it when you start: a chain ID such as `repo:ship`, or the path of a chain file (`--chain PATH`).

Run `kl.py chains --available` to list every chain ID Lite can see, with the library it came from. Lite loads no add-ons other than Kraft's own `kraft-default`, so `acme:ship` is refused. The [reference](/reference/kraft-lite#chain-sources) has the four sources and how they rank.

## What runs each task

Lite supplies the order, the gates and the caps. A task runs on its default, or on the skill, instruction or command you bind to it in `.kraft-lite/bindings.yaml`. A task with nothing of yours to run follows Kraft's own method for it, the spec writer and the planner included: see [Kraft's methods](/reference/kraft-lite#krafts-methods).

The file is optional, and so is every entry in it. `/kraft-lite:init` writes one listing only the entries that differ from the defaults. Edit it and commit it. Lite reads it again on every dispatch, so rebinding a task corrects a chain already in flight.

An entry has a `kind`: `skill`, `prompt`, `subprocess` or `skip`. This one runs a skill for the spec, skips the code review and runs `just test` for the changed-scope tests:

```yaml
tasks:
  spec_author:
    kind: skill
    skill: superpowers:brainstorming
    prompt: Agree requirements and write a spec before any code.
  verification.review.code_review:
    kind: skip
    why: the merge request review covers it
builtins:
  kraft.verify_changed_test_scopes:
    kind: subprocess
    command: [just, test]
```

A `skill` entry needs a `prompt` too, which runs if the skill isn't installed. A `skip` needs a `why`. `start` checks every entry before it writes anything, and lists a `tasks` key that names no task under `unused_bindings`. The [reference](/reference/kraft-lite#bindings) has the sections, which binding wins and the defaults.
