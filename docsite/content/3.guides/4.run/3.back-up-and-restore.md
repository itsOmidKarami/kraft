title: Back up and restore the database
description: Back up Kraft's database while the server runs, restore it, check the backup, and find the copy Kraft makes before an upgrade.
---

How to copy Kraft's database safely, put a copy back, and tell which copy
Kraft made for you. Read [Before you start](/guides/run/operations#before-you-start) first.

## Back up the database

`run/orchestrator.db` holds every work item, event, session and review
thread. Kraft runs SQLite in WAL mode, so recent writes can sit in
`orchestrator.db-wal` beside it. Copying `orchestrator.db` alone while the
server runs can give you a copy that is missing them, or one that does not
open.

Use SQLite's online backup, which is safe while the server runs:

```bash
sqlite3 ~/.kraft/run/orchestrator.db ".backup '$HOME/kraft-backup.db'"
```

No `sqlite3` command? Python does the same:

```bash
python3 -c "import sqlite3; sqlite3.connect('file:$HOME/.kraft/run/orchestrator.db?mode=ro', uri=True).backup(sqlite3.connect('$HOME/kraft-backup.db'))"
```

Or stop the server first, then copy the file:

```bash
kraft admin stop
cp ~/.kraft/run/orchestrator.db ~/kraft-backup.db
kraft admin start --detach
```

Back up `config/` too. It is your config, and it is small. See
[Keep your templates in git](/guides/customize/upgrading-templates#keep-your-templates-in-git).

You do not need to back up `run/index.db`. It is the search index, and
`kraft admin reindex` rebuilds it.

To restore, stop the server, put the backup in place as
`run/orchestrator.db`, delete any `orchestrator.db-wal` and
`orchestrator.db-shm` beside it, and start the server again.

## The copy Kraft makes before an upgrade

When a newer Kraft starts on an older database, it migrates the database
forward, and the older version cannot open the result. So before it migrates,
Kraft copies the database to `run/orchestrator.db.pre-v<N>-<time>`, where `<N>`
is the schema version it is about to migrate to and `<time>` is when it made
the copy. `server.log` names the file:

```text
database schema v44 -> v52: backed up the old database to /home/you/.kraft/run/orchestrator.db.pre-v52-20261002-093015
```

The copy is consistent even while the WAL holds recent writes, and only you
can read it (`0600`). Each migration makes a new copy and never overwrites an
older one. If you upgrade, roll back and upgrade again, the newest
`orchestrator.db.pre-v52-*` is the one that holds what you did in between.

The `v<N>` in the name is the schema Kraft migrated to, not the one the copy
holds. After more than one upgrade, the newest copy can hold a schema the
release you go back to refuses:

- Going from 1.4 through 2.0.0rc1 to rc8 (schema 51) to 2.0 leaves 1.4's
  database in a `pre-v51-*` copy, and the candidate's in the newest `pre-v52-*`.
- From rc9 on the candidates already run schema 52, so the `pre-v52-*` copy the
  candidate made holds 1.4's database, and going on to 2.0 makes no new copy.

Each copy's own schema is its `PRAGMA user_version`; 1.4's is 44.

The copy needs about as much free space as the database, beside it in `run/`.
If Kraft cannot write it, it does not migrate: the server does not start, the
database is left unchanged, and the error names the copy and the space it
needs. Free the space and start again.

Restore the newest copy whose schema is the one the release you go back to
runs, the same way as your own backup. If Kraft runs as a
[service](/guides/run/run-as-a-service#run-kraft-as-a-service), run `kraft admin uninstall-service` in place
of `kraft admin stop`, or the service manager starts it again under you:

```bash
kraft admin stop
for f in ~/.kraft/run/orchestrator.db.pre-v*; do echo "$(sqlite3 "$f" 'PRAGMA user_version') $f"; done
cp ~/.kraft/run/orchestrator.db.pre-v52-20261002-093015 ~/.kraft/run/orchestrator.db   # the newest that printed 44, for 1.4
rm -f ~/.kraft/run/orchestrator.db-wal ~/.kraft/run/orchestrator.db-shm
```

The loop prints each copy's schema, then its name; names sort by schema, then
by time. Without the `sqlite3` command, Python prints the same:

```bash
python3 -c 'import glob, os, sqlite3; [print(sqlite3.connect(f"file:{f}?mode=ro", uri=True).execute("PRAGMA user_version").fetchone()[0], f) for f in sorted(glob.glob(os.path.expanduser("~/.kraft/run/orchestrator.db.pre-v*")))]'
```

Then start the version you upgraded from. The copy loses everything done since
the upgrade. It is no substitute for a backup you take yourself: make one
before every upgrade. Once you are sure you will stay on the new version,
you can delete the copies. Kraft never deletes them itself.

## Verify the backup

```bash
sqlite3 ~/kraft-backup.db "PRAGMA integrity_check; SELECT count(*) FROM work_items;"
```

Or, without the `sqlite3` command:

```bash
python3 -c "import sqlite3; db = sqlite3.connect('$HOME/kraft-backup.db'); print(db.execute('PRAGMA integrity_check').fetchone()[0]); print(db.execute('SELECT count(*) FROM work_items').fetchone()[0])"
```

Either prints `ok`, then the number of work items.
