---

You will run a newer Kraft release, with a backup of your database taken first,
and `kraft admin health` names the new version. The page also says how to go
back to the version you had.

Coming from 1.4? Do not follow the steps on this page: 1.4's own
`kraft admin update` mishandles the install. Follow
[Upgrade from 1.4](/guides/run/upgrade-from-1-4#update-from-14)
instead. [What's new in 2.0](/project/whats-new) says what you get.

## Before you start

- You know how Kraft was installed: with uv or `install.sh`, with Homebrew, with
  pipx or pip, or from a source checkout. The update step differs for each.
- You can pick a moment when no agent is running, or you will pause the running
  items first. Step 4 restarts the server, which ends the agents of items that
  run in place. Across a major version `kraft admin restart` refuses and
  `kraft admin update --restart` waits while anything runs, so only
  `kraft admin update --now`, or `kraft admin stop --now` then a start, ends
  the rest.
- `sqlite3` or `python3` is on your `PATH`, for the backup.

## Upgrade

1. Back up the database. A newer Kraft can migrate `run/orchestrator.db`
   forward when it starts, and there is no way back: the version you had then
   refuses to start on it (`database schema vN is newer than code vM`). The
   backup is what lets you [roll back](#pin-or-roll-back-a-version).

   This copy is safe while the server runs. The file is named for the second you
   run the command, so a backup taken at another time never replaces this one,
   and a rollback to 1.4 needs the backup from before the first upgrade. The
   command prints the name: write it down, and keep the file.

   `-readonly` opens the database you copy from read-only, so a wrong path fails
   instead of making an empty backup. `run` follows `KRAFT_RUN_DIR`, then
   `KRAFT_HOME`, as Kraft does:

   ```bash
   run="${KRAFT_RUN_DIR:-${KRAFT_HOME:-$HOME/.kraft}/run}"
   backup="$HOME/kraft-backup-$(date +%Y%m%d-%H%M%S).db"
   sqlite3 -readonly "$run/orchestrator.db" ".backup '$backup'" && chmod 600 "$backup" && echo "$backup"
   ```

   ```text
   /home/you/kraft-backup-20261002-093015.db
   ```

   The `chmod` keeps the copy readable by you alone, as the database is.

   [Back up and restore the database](/guides/run/back-up-and-restore) has the
   form for a machine without `sqlite3`, and how to check the copy and put it
   back. Kraft also copies the database itself before it migrates it, as
   [The copy Kraft makes before an upgrade](/guides/run/back-up-and-restore#the-copy-kraft-makes-before-an-upgrade)
   says. Take your own anyway: you know when you made it, and it does not depend
   on the version you upgrade to.

2. Pause the running items, or wait until none run. The restart in step 4 ends
   the agents of in-place items; across a major version it waits or refuses
   while anything runs. The commands are in
   [A restart leaves local steps running](/guides/run/restart-kraft#a-restart-leaves-local-steps-running).

3. Install the newest release. On 1.4, do not run this command: follow
   [Update from 1.4](/guides/run/upgrade-from-1-4#update-from-14).

   ```bash
   kraft admin update
   ```

   It prints the release it installs:

   ```text
   kraft 2.0.0 -> v2.0.1
   kraft v2.0.1 installed.
   Restart a running server: kraft admin restart
   ```

   What it runs depends on how Kraft was installed:
   - **uv or script install:** `uv tool install --force --python 3.X "kraft-sdlc[vector]==X.Y.Z"`.
     The `vector` extra (when you have it) and a Python you chose with
     `--python` stay. With no `--python` recorded, it asks for the minor version
     Kraft runs on now, such as `3.13`, so a later `uv python upgrade` still
     carries Kraft along.
   - **Homebrew:** `brew upgrade kraft`.
   - **pipx, pip or a source checkout:** nothing, because a uv copy would sit
     beside the `kraft` you run and change nothing. It prints the command that
     updates the install you have instead, such as
     `pipx install --force --python /path/to/python "kraft-sdlc==X.Y.Z"`.

   On a uv install, uv records the exact version, so `uv tool upgrade` leaves
   Kraft where it is: update with `kraft admin update`. In the few minutes after
   a release, before PyPI has it, `kraft admin update` installs the release's
   wheel from GitHub instead.

   A [Kraft add-on](/concepts/vocabulary#add-on) runs on one major version
   of Kraft. Before `kraft admin update` installs a release of another major, it
   lists the loaded add-ons that release would leave out, and asks:

   ```text
   kraft 3.0.0 would stop loading these add-ons until each publishes a version for it:
     release@acme 1.0.0 needs Kraft 2.x
   Install it anyway? [y/N]
   ```

   A no installs nothing. After a yes, or `-y`, each listed add-on stays
   installed and stops loading, and a chain that extends it stops resolving.
   `kraft admin addon update` brings it back once its author publishes a
   version for the new major.

4. Restart the server so it runs the new release. Either run
   `kraft admin restart`, or give step 3 `--restart` (`kraft admin update --restart`)
   to do both.

   Within a major version the restart leaves the local steps of worktree items
   running: the new server starts a local worker of its own and takes the steps
   over. The old worker exits once it has finished its processes.

   `kraft admin update --restart` to a new major version does not restart at
   once. It marks the release for [when Kraft is free](#update-when-kraft-is-free)
   and says so, since the new major cannot take over the old one's steps. With
   no server running it only installs.

   `kraft admin update --now` installs and restarts at once, ending every step.
   `kraft admin restart` onto a new major with an item active exits 1 and names
   `--when-free` and `kraft admin stop --now`.

   Without a restart, a running server keeps running the old release, the board
   shows a page saying to restart instead of the interface, and
   `kraft admin doctor` warns on its `restart` row. The page does not appear
   when you update from 1.4 or from a 1.5.0 release candidate before rc14: see
   [If you used 1.4's update anyway](/guides/run/upgrade-from-1-4#if-you-used-14s-update-anyway).

5. Check the result:

   ```bash
   kraft --version
   kraft admin health
   ```

   `--version` prints `kraft` and the release, such as `kraft 2.0.1`. `health`
   prints the same release on its `version` row, and no `installed` row that says
   `restart pending`:

   ```text
   status         ok
   version        2.0.1
   ```

   The `restart` row of `kraft admin doctor` reads
   `the server (pid N) runs the installed version (2.0.1)`.

## Update when Kraft is free

_Added in 2.3_

Kraft can take a release for you, at a moment when it costs no running work. You mark a release, or turn on auto-update, and Kraft installs it and restarts once nothing is going on. Nothing is held while it waits: items still start, and Kraft tries again a minute later.

Kraft is free when no agent session is running and no work item is `active`, `waiting`, `queued` or `rate_limited`. An item waiting for a person (`needs_human`), `paused`, `blocked`, `completed` or `abandoned` does not hold it back. If you set [allowed hours](/reference/configuration/update), Kraft also waits for them. Once it is free and has decided to go ahead, it starts no new walk or agent session until it has installed and restarted, about a minute, so nothing is cut off while starting.

If the restart never happens, that hold lapses after 15 minutes and Kraft looks again.

1. Open Settings › About. On a release install made with uv, an available version has an **Install when free** button, and a marked one has **Don't**. The CLI does the same:

   ```bash
   kraft admin update --when-free
   kraft admin update --when-free v2.3.0
   kraft admin update --cancel-when-free
   ```

   The mark works whatever the switches say, and stays across a restart. A new major version is offered beside the newest release of your major, and installs only when you mark it.

2. To have Kraft mark releases itself, turn on **Update automatically**. It marks each new minor or patch release on your channel. Both switches are off until you turn them on. **Restart when free** also restarts a dev install or a settings change when it is free. A release Kraft installed itself always finishes with its restart.

3. Optionally, add **Allowed hours**, such as `01:00-06:00`, in the server's local time. Kraft updates and restarts only inside them, and only when free. A person's mark waits for them too.

About says what is waiting and why it is not done yet: `waiting for 1 running item`, `outside 01:00-06:00`, `attached to a terminal`. It also keeps how the last attempt ended.

### What Kraft does when it is free

1. It claims the moment, and checks that it is still free.
2. It installs the marked release, after the checks `kraft admin update` makes. Kraft installs nothing that would ask a question by hand: a configuration migration, add-ons the release would drop, a leftover `kraft` uv tool. It refuses, says why on About, and leaves the old version running. Run `kraft admin update` yourself.
3. It checks that the new install can start: it imports the server, reads every configuration file, and checks the bind address and port, without starting anything.
4. It copies the configuration directory and the databases, then restarts. The new server comes up on probation: it answers, and starts no walk, poller or loop until a helper has seen it come up as a new process, of the new version for a release.
5. If it does not come up in time, the helper puts back what changed: it reinstalls the previous version, restores the configuration and the databases, and starts that version. About shows the failure. The same version is not tried again until you mark it again.

A dev install, installed from a checkout, has no release to look for. Install it yourself with `just install`; its restart then waits for a free moment, if you turned on **Restart when free**. If the old server cannot start on what is installed, Kraft is left down, and About says so.

Which servers can restart themselves:

- **A service** (launchd or systemd) and **a server started with `--detach`** can. They restart through their own manager, or by stopping and starting in the background.
- **A server started in a terminal** cannot. About shows the update and says it is attached to a terminal. Restart it there.

A failed or refused attempt, and each one that works, is written to `run/logs/server.log` and shown on About. Kraft's notifications carry events of work items, which an update does not belong to, so they do not carry it.

## What an upgrade leaves in config

An upgrade never changes `$KRAFT_HOME/config/`, with three exceptions:

- An install still on Kraft 0.x's template format (a `registry.yaml`, no
  `library.yaml`) is migrated, after a prompt. See
  [Migrating a home from 0.x](/guides/run/upgrade-from-0-x-or-a-release-candidate#migrating-a-home-from-0x).
- The first start of 2.0 or later rewrites `theme.yaml` once if it still has
  `palette`. See [Your theme](/reference/changes-from-1-4#your-theme).
- The first start of 2.0 or later renames a 1.4 `templates/` to `config/` and
  moves two keys between `policy.yaml` and `intake.yaml`, rewriting the files it
  moves a key between. See
  [Config directory and files](/reference/changes-from-1-4#config-directory-and-files).

To take new shipped chains and library tasks, see
[Upgrade your configuration](/guides/run/upgrade-your-configuration).

## Pin or roll back a version

`kraft admin update` only installs the newest release on a channel; it cannot
target a version. Install a specific version with the package manager instead.

To go back to 1.4 after an upgrade, see [Roll back to 1.4](/guides/run/roll-back).
To go back to an earlier 2.x release, pin it, as below, then follow
[Roll back to an earlier 2.x release](#roll-back-to-an-earlier-2x-release).

### Pin a version

- **uv or script install.** Name the version, and the Python you run Kraft on
  (`"$(uv tool dir)/kraft-sdlc/bin/python" -V` prints it):

  ```bash
  uv tool install --force --python 3.X "kraft-sdlc==X.Y.Z"
  ```

  Without `--python`, uv moves Kraft to its default Python. Add the extra if you
  use vector search: `"kraft-sdlc[vector]==X.Y.Z"`. To stay on that version, do
  not run `kraft admin update`; it moves you to the newest release again.
- **Homebrew.** The tap has one formula, which each release rewrites to the
  newest version, so Homebrew cannot install an older one. `brew pin kraft` stops
  `brew upgrade`, and with it `kraft admin update`, from moving the version you
  have. To go back to an older release, `brew uninstall kraft` and install that
  version with uv.

### Roll back to an earlier 2.x release

Pinning the older release is not enough when the upgrade migrated the database.
A migration is one way: an older release refuses a database a newer one
migrated, and Kraft copied the database before it migrated it.

1. Stop the server: `kraft admin stop`, or as
   [Stop a service](/guides/run/run-as-a-service#stop-a-service) says when Kraft
   runs as a service. That removes the service: run `kraft admin install-service`
   once the older release runs, as the restore in
   [Back up and restore the database](/guides/run/back-up-and-restore#restore-a-backup)
   does.
2. Pin the earlier release, as above.
3. Start it with `kraft admin start --detach`. If it starts, the upgrade changed
   no schema, so Kraft made no copy and the database needs no restore.
4. If it exits with `database schema vN is newer than code vM`, which
   `kraft admin start --detach` prints and `run/logs/server.log` records, the
   earlier release runs schema `M`, and going back loses everything done since
   the upgrade. Restore the newest of Kraft's copies whose own schema is `M`:
   [Find the copy to restore](/guides/run/back-up-and-restore#find-the-copy-to-restore)
   shows how to read it, and
   [Restore a backup](/guides/run/back-up-and-restore#restore-a-backup) puts it in
   place, with `backup` set to that copy's path.
5. If no copy holds schema `M`, check the backup you took in step 1 of the
   upgrade, the file that step printed. Set `backup` to it; the command prints
   its schema, as
   [Find the copy to restore](/guides/run/back-up-and-restore#find-the-copy-to-restore)
   does for Kraft's copies:

   ```bash
   backup="$HOME/kraft-backup-20261002-093015.db"
   sqlite3 -readonly "$backup" 'PRAGMA user_version'
   ```

   If it is `M`, restore it the same way. If it is not `M` either, there is no
   way back to that release: pin the newer release again and stay on it.
