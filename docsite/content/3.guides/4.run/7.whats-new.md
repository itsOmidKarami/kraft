---
title: What's new in 2.0
description: Kraft 2.0's new interface, code-host review, a repo connect that reads more of the repo, and safer sharing, and what to check before you upgrade from 1.4.
---

Kraft 1.0 shipped the engine: chains that take your coding agent from spec to
merge request and stop only where a decision is yours. 2.0 is built around
those decisions. Most of what changed since 1.4 is what you see and touch.

If you are upgrading, read [Upgrading from 1.4](/guides/run/upgrade-kraft#upgrading-from-14)
first. It lists every change that can affect a script or a habit, and how to
upgrade without ending a running agent.

## A new interface, built around what needs you

Open Kraft at the same address and you get the redesigned interface; the old
one is gone.

- The board keeps 1.4's four groups (needs you, running, not started and
  done), its one button per row and its side panel.
- Select several items in any group and pause, cancel or archive them at
  once. 1.4 could only archive, and only from Done.
- An item's page draws its chain as a graph, where 1.4 showed a row of
  node names, and each node opens its own view of its steps and tasks. Click
  a node, step or task to see its log, documents and settings in place.
- ⌘K (Ctrl+K) search and the phone layout come along, redesigned to match.

[The board and the web UI](/guides/day-to-day/the-board) tours every screen. If you
can't find a page you used in 1.4, see
[Where did a page go?](/troubleshooting#where-did-a-page-go-and-why-does-my-theme-look-different)

## Review the way you would on a code host

The review threads that `kraft item comment` and the VS Code extension have
had since 1.2 now have a page of their own in the web interface.

- Each item has a **Review** page with the diff, the comment threads and the
  gate decision.
- Comment on one line or on a range, even one that runs from a removed line
  to its replacement, as on GitLab. The range stays shaded, and the agent
  gets its lines quoted.
- Suggest a change in place, and send a whole round of comments at once with
  **Finish review**.

See [Reviewing a change](/guides/day-to-day/review-a-change).

## Shape the work from its page

- Read the spec and plan an item was filed with before you start it.
- Set the item's and its nodes' model, effort and limits on the item's page,
  beside the values its chain would use. The CLI could already; now the page
  shows what you are overriding.
- Change a running item's chain; the change applies from its next node.
- **Start** asks first when the item has draft changes you haven't applied.
- When a cap or budget stops an item, its page names the limit that stopped
  it, whether the item's own, its policy's or its chain's, and where the item
  can raise it, lets you raise it and retry from the same place. 1.4 offered
  that only for the item's own dollar cap. See
  [Raising a cap on a stuck item](/guides/day-to-day/raise-a-cap).
- Chains, the library, harnesses, repos and policy are edited as a draft that
  you review, then publish. See [Templates](/reference/web-ui/templates-and-settings#templates).

## One config directory, named for what it holds

`$KRAFT_HOME/config/` holds every YAML Kraft runs from, and the first start
renames a 1.4 `templates/` to it. Only two of its files are templates, the
library and the chains, and those are what the **Templates** screens hold;
repos, harnesses, policy and auto-intake are **Settings**.

Each Settings screen edits one file: schedules moved from `policy.yaml` to
`intake.yaml` beside the rest of auto-intake, and `max_concurrent` is set in
one place.

Where a chain is named, the word is `chain`: a repo's `default_chain`,
`kraft item set-chain --chain`, the `set_chain` tool. Every old name and
place is still read, and `kraft admin doctor` lists the ones you still have.

## Repo connect reads more of the repo

`kraft repo connect` now bases the setup and test commands it proposes on
much more of the repo: its own task runner (just, make, Taskfile, mise and
others), its toolchain's files (40 detectors across 17 language ecosystems
and build systems) and its CI, where 1.4 looked at a justfile and a few
manifests and lockfiles. It explains each choice, and rehearses the commands
with `--verify`. See
[Connecting a repo](/reference/configuration/repos/detectors#connecting-a-repo) and
[Detectors](/reference/configuration/repos/detectors).

## Safer to share

- No other site can frame the board, and an image from another site in a
  document or review thread loads only when you click it, so a worker can't
  send data out through your browser.
- Off loopback, Kraft answers a browser only at a name you listed, on every
  request and on the live-update socket. See
  [Remote access](/guides/run/remote-access).

## Why 2.0 so soon after 1.0

Because Kraft keeps its
[stability promise](/project/status-and-support#versioning-and-stability).
Making the interface and the API consistent changed some `--json` fields and
exit codes, and the database moves to a schema 1.4 can't open. A minor
version would have hidden that, so this is a major one.

Apart from what [Upgrading from 1.4](/guides/run/upgrade-kraft#upgrading-from-14)
lists, your chains, library and repos carry over as they are. If you ran a
1.5.0 release candidate, those were 2.0's pre-releases: see
[Upgrading from a 1.5.0 release candidate](/guides/run/upgrade-kraft#upgrading-from-a-150-release-candidate).

## Looking ahead

The sandbox backend that has run tasks under Docker and Podman since 1.2, and
the [Docker Sandbox Kits](/guides/harnesses/worker-kit) added in 1.4, are what richer
sandboxes and remote workers are meant to build on during 2.x.
