By the end you run the current release, coming from 1.4, and you have acted on each change that needs something from you. An update between 2.x releases needs only [Upgrade Kraft](/guides/run/upgrade-kraft). A 1.5.0 release candidate or a 0.x home follows [From a release candidate or 0.x](#from-a-release-candidate-or-0x).

- **On 1.4:** follow [Update from 1.4](#update-from-14), then read [Changes that need action](#changes-that-need-action).
- **Already ran 1.4's own update:** go to [If you used 1.4's update anyway](/guides/run/coming-from-1-4#if-you-used-14s-update-anyway).
- **Update went wrong:** go to [Roll back to 1.4](#roll-back-to-14).

## Before you start

- You know how Kraft was installed: with uv or `install.sh`, with Homebrew, or with pipx. Step 4 differs for each.
- On uv or pipx, you know the Python Kraft runs on and whether you use vector search. `"$(uv tool dir)/kraft-sdlc/bin/python" -V` prints the Python. The `embeddings` line of `kraft admin health` says `unavailable (the 'vector' extra is not installed` when you don't have the extra.
- `sqlite3` or `python3` is on your `PATH`, for the backup in step 1.
- You can pick a moment when no agent runs, or you pause the running items first (step 3).

## Update from 1.4

Don't update with 1.4's own `kraft admin update`. That command runs in the release you have installed, and 1.4's mishandles a uv install and a pipx install, as step 4 says. Use your package manager:

1. Back up the database, as step 1 of [Upgrade](/guides/run/upgrade-kraft#upgrade) says. 1.4 can't open the database the new release migrates. Keep the file name that step prints: a rollback to 1.4 needs it, and a later upgrade's backup never replaces it.
2. Do what has to come first. Each item names its change below:
   - On a network bind, add each name you use to `allowed_hosts` ([Network access](#network-access)).
   - Behind a tunnel or reverse proxy on a loopback bind, make it send a loopback `Host` ([Network access](#network-access)).
   - On a repo entry with `test_command: ""`, set a real test command or `enabled: false` ([Items and repos](#items-and-repos)).
   - On a repo whose `sandbox:` has no `network:`, add one, or set `unrestricted_network: true` ([Items and repos](#items-and-repos)).
   - On a schedule with day of week `7`, change or remove it unless you want it to fire on Sundays ([Config directory and files](#config-directory-and-files)).
3. Pause the running items, or wait until none run: 1.4 ends its agents when it stops. See [A restart leaves local steps running](/guides/run/restart-kraft#a-restart-leaves-local-steps-running).
4. Install the newest release with the tool you installed Kraft with:
   - **uv or `install.sh`:** run `uv tool install --force --python 3.X "kraft-sdlc[vector]==<version>"`, with the Python you installed Kraft with for `3.X` and the release for `<version>`: the number without the `v`, as the newest tag on the [releases page](https://github.com/itsOmidKarami/kraft/releases/latest) shows it (tag `v2.5.0` is `2.5.0`). For example, `uv tool install --force --python 3.13 "kraft-sdlc[vector]==2.5.0"`. Leave out `[vector]` if you don't use vector search.

     1.4's update installs the new release without the `[vector]` extra and on uv's default Python, and leaves `uv tool upgrade` pointing at a file it has deleted.
   - **Homebrew:** run `brew update`, then `brew info kraft`. It shows the version the tap offers, and `brew info` alone doesn't refresh the tap.
     - If it still shows 1.4, the tap has no newer release yet, and `brew upgrade kraft` changes nothing: wait, or run `brew uninstall kraft` and install with uv as above.
     - Otherwise run `brew upgrade kraft`. 1.4's `kraft admin update` runs the same command, and loses nothing: the formula has no `[vector]` extra.
   - **pipx:** run `pipx install --force --python python3.X "kraft-sdlc[vector]==<version>"`, with `<version>` as above. 1.4's `kraft admin update` doesn't update a pipx install: it puts a second Kraft beside it with uv.
5. Restart the server with `kraft admin restart`. With an item still active, a restart onto a new major version exits 1 and names `--when-free` and `kraft admin stop --now`: wait for the item, or end its steps with the second. Otherwise it asks before it ends agents.

## Check it worked

- `kraft --version` and `kraft admin health` print the release you installed, as step 5 of [Upgrade](/guides/run/upgrade-kraft#upgrade) shows.
- `kraft admin doctor` has a `keys`, `moved keys`, `tests` and `config` row. Each names what the new release found in your files: [Changes that need action](#changes-that-need-action) says what to do about it.

## If you used 1.4's update anyway

On a uv install, an update run by 1.4 drops the `vector` extra and moves Kraft to uv's default Python. Restart right after it, and don't act on the board before:

1. Run `kraft admin restart` as soon as the update finishes.
2. Reinstall `[vector]` with the uv command above, if you use vector search. Without it, vector search stops working: see [Add vector search](/guides/run/upgrade-kraft#add-vector-search).
3. If you reinstalled the extra, run `kraft admin restart` once more, to be safe. The reinstall replaced files under the server you just restarted, as any update does, and a restarted server reads them fresh. The `embeddings` line of `kraft admin health` then says `available`.

Before the restart you may see:

- Items under the wrong heading, and a footer that names the new release. 1.4's server keeps running and serves the new interface, which misreads its board.
- A banner over the board saying so. `kraft admin doctor`'s `restart` row warns that the server runs a release older than the one installed.
- `Internal Server Error` instead of the board, if Kraft ran on a Python other than uv's default. 1.4's update moved Kraft to another Python and deleted the files the running server serves, though its API still answers.

If you ran `kraft admin update --restart` (or restarted a service), 1.4 restarted the server without asking, which ended the agents of running items. Pause them first next time.

## Changes that need action
<!-- not new: the changes from 1.4 moved here from the reference page -->

The new release changes some 1.4 behaviour that the [stability policy](/project/status-and-support#versioning-and-stability) covers, such as `--json` fields and exit codes, which is why it is a major release. Apart from the changes here, your chains, library and other config files carry over as they are. Each item says what is true now, what 1.4 did, and what to do.

### Network access

- **The Host check on a network bind.** The server checks the address every browser uses to reach the board. 1.4 skipped that check over plain HTTP, so your board may have worked at a name that isn't in `allowed_hosts`. Such a browser now gets a page saying the name isn't allowed.
  - Do: before you update, add each exact name you use (no wildcards) on Settings › Access, or to `allowed_hosts` in `access.yaml`.
  - `kraft admin doctor` warns when the bind is off loopback and the list is empty.
- **A tunnel or reverse proxy in front of a loopback-bound Kraft must send a loopback `Host`.** On a server bound to `127.0.0.1` (the default), every request whose `Host` header isn't `localhost`, `127.0.0.1` or `[::1]` gets 403, webhooks to `POST /api/triggers` and `GET /api/health` included. 1.4 checked only requests from a browser, and `allowed_hosts` doesn't apply on a loopback bind. See [Who may call](/reference/http-api#who-may-call).
  - Do, for the board: bind Kraft beyond loopback, with a password, and list the name in `allowed_hosts`. That is the one way the board works through cloudflared, ngrok, Caddy or nginx. What a proxy you run must pass is in [Behind a reverse proxy you run](/guides/run/remote-access#behind-a-reverse-proxy-you-run).
  - Do, for webhooks and scripts alone: have the proxy rewrite `Host` to `localhost`. Read [Put a proxy in front of Kraft](/guides/run/put-a-proxy-in-front-of-kraft) first, because it also changes who has to sign in.

### Items and repos

- **A sandbox with no `network:` is refused.** Every agent launch into it stops the item as a configuration error, whatever the harness. 1.4 already refused a Claude task there, and a Codex or Cursor task with a tool policy. It ran every other one with the worker's network unrestricted and no channel to Kraft, so gates weren't enforced. A repo that runs only Claude needs nothing done.
  - Do: add a [`network:` policy](/reference/configuration/sandbox/network-policy) to the sandbox, or set `unrestricted_network: true` on it to run as 1.4 did, knowing that. The two keys together are refused when `repos.yaml` loads. `kraft admin doctor` fails the `egress` row of each such repo.
- **Cancel keeps the branch.** Cancel in the web interface keeps the item's branch and [worktree](/concepts/vocabulary#worktree). 1.4 deleted them. Do: to delete them, run `kraft item abandon ID --reason "..." --yes`.
- **A merge request closed without merging stops its item.** In 1.4 the item kept waiting. Do: reopen the merge request from the item's page, retry or cancel.
- **A repo with open items can't be disconnected.** `kraft repo disconnect` (and `DELETE /api/repos`) is refused with a 409 until each of the repo's items is done, cancelled or abandoned, paused and never-started ones included. 1.4 let it through and left those items stranded. Do: finish, cancel or abandon the items first.
- **`test_command: ""` means the repo has no tests.** Its items pass `verify` without running a test. In 1.4 such an entry stopped every item at `verify`. Do: before you update, set a real test command on any such entry, or `enabled: false` to keep it from running. Afterwards, the `tests` row of `kraft admin doctor` names each one.
- **`kraft repo connect` on a repo that is already connected changes it.** 1.4 did nothing. Now it probes the repo again and saves what its entry left undecided: a test command where it has none and no test scopes, and a setup command where none is declared.
  - That can enable a repo saved disabled for want of a test command. In a terminal it asks first; with `-y`, `--json` or no terminal it saves without asking.
  - Do: a script that re-runs connect to check a repo should run `kraft repo list` instead.
- **`kraft repo connect` refuses a repo with no commit yet.** 1.4 connected it. Do: commit its files first. `kraft admin doctor` names each entry 1.4 left without a test or setup command where the new release finds one, with the connect command that saves it.

### Scripts, JSON output and the API

- **`agent_overrides` is an object, not JSON text,** wherever it appears: in `kraft view show --json`, in `kraft item approve --json` and every other `--json` answer that carries the item, in the MCP tools' results, and in `GET /api/work-items/{id}`.
  - In the answers to an action, such as `kraft item approve --json`, `node_overrides` and `policy_override` are objects too, as `kraft view show --json` already had them.
  - Do: if a script runs `json.loads` on one of them, read it as an object instead.
  - Setting the override works as in 1.4: `kraft item set-overrides` and `PATCH /api/work-items/{id}` replace the whole override.
- **`budget_cap.cap_usd` in `kraft view show --json` is the cap that stops the item first:** the lower of its own cap and its [policy](/concepts/vocabulary#policy)'s item-wide `budget_usd`. Do: read `budget_cap.key` to tell which one it is.
- **`kraft view events -f --json` prints one JSON object per line** from the first line on. 1.4 printed the backlog as an indented array. Do: read it line by line.
- **An event has a `node_id` of its own,** from the payload's `node_id` or `node` key. A gate's events from before the update keep `null`: they named their node under `gate`. Do: a script that reads an old gate event takes the node from `gate`.
- **Action commands print one line.** `kraft item approve`, `reject`, `pause`, `resume`, `retry`, `raise-budget`, `skip`, `complete`, `cancel`, `escalate` and `set-chain`, `kraft item resolve` and `reopen` (one line naming the thread), and `kraft item review approve` or `request-changes` at a pending gate, print what they did, not the item's fields (or, for a thread, its comments). Do: a script that read those fields should use `--json`, which is unchanged.
- **`kraft admin restart` with no server running exits 1.** 1.4 exited 0. `update --restart` is unchanged. Do: a script that runs it under `set -e` stops there, so start the server first.
- **A review comment names a file inside the repository, and a suggestion goes on new-side lines.** `kraft item comment`, the MCP tool `add_review_comment` and `POST /api/work-items/{id}/threads` refuse an absolute `--file` path, or one with `..`, with a `422`, and `kraft item comment --suggest` with `--side old` exits 2 (the API answers `422`). 1.4 stored both. Do: use a repository-relative path, and `--side new` for a suggestion.
- **A model override that isn't a model ID is refused.** `kraft item set-overrides`, `kraft item set-node-override`, `PATCH /api/work-items/{id}` and a retry that changes a task's model (`task_config.model`) answer one, such as `--model "my model"`, with a `422`. 1.4 stored any text. One 1.4 already stored now stops its item at the next launch, and the reason names the command that clears it. Do: run that command.
- **Escalating an item a spend cap stopped is refused, and so is raising a cap to what the item has already spent.**
  - `kraft item escalate` (and `POST /api/work-items/{id}/escalate`) on an item any spend cap stopped, the daily cap included, answers `409` and points to the cap to raise. 1.4 started an escalation that the same cap then stopped.
  - `kraft item raise-budget` with a cap at or below what the item has spent answers `422`. 1.4 saved it and the item stopped again at once.
  - Do: raise the cap above the spend.
- **A [work item](/concepts/vocabulary#work-item) title is one line of plain text, and not blank.** `kraft item create`, the MCP tool `create_work_item`, `POST /api/triggers` and `PATCH /api/work-items/{id}` refuse a title that is empty, only whitespace, holds a line break (a trailing one included), or holds a tab, an escape or another control character, with a `422`. 1.4 filed or saved it (only a blank `PATCH` title was refused).
  - Do: if a webhook or script builds the title from text that can be empty or run over several lines, give it a fallback and send its first line, with the rest in `description`.
  - A schedule's title, and **Duplicate** of an item 1.4 filed with one, is cleaned up instead of refused: the first line is the title and the rest goes to the top of the description, a tab becomes a space, other control characters are dropped, and a blank title takes the description's first line (a schedule with neither is skipped).

**Chains are named `chain`, not `template`, in commands, tools and the API.**

| Before | Now | What to do |
|---|---|---|
| `kraft item set-chain --template` | `--chain`; `--template` still works | Nothing. |
| The MCP tool `set_chain_template` | `set_chain`, with `chain` for `template`; the old tool name no longer exists | Change an agent prompt or skill that names `set_chain_template`. |
| `chain_template` in the MCP tool `create_work_item` | `chain` | Use `chain`. |
| `chain_template` in `POST /api/triggers` | `chain`; `chain_template` is still read | Nothing. |
| `default_chain_template` in `POST` and `PATCH /api/repos` | `default_chain`; `default_chain_template` is still read | Nothing. |
| `default_chain_template` in the answers of `kraft repo list --json`, `kraft repo connect --json`, the MCP tool `ensure_repo` and `GET /api/repos` | `default_chain` | Read `default_chain` in a script that uses the key. |

### Config directory and files

- **The config directory is `$KRAFT_HOME/config/`, not `templates/`.** Do: nothing for a default home; the first start renames it.
  - The first start renames yours, every file in it as it was, once it holds the server's lock. Started while the 1.4 server is still up, it exits "already running" and touches nothing. `templates` is left as a link to `config`, so a 1.4 process still running (an MCP server under an agent) and a path in a script keep working.
  - `KRAFT_CONFIG_DIR` names it. `KRAFT_TEMPLATES_DIR` is still read when the new one is unset, and one pointing at the old default is renamed with it. Change it when you next touch that unit.
  - A `config/` you made before the first start, such as the [harness](/concepts/vocabulary#harness) guide's `config/harnesses`, gets what it lacks moved in. Whatever both hold stays in `templates/`, and `kraft admin doctor`'s `config` row names both until you merge them.
  - If a service unit or a shell sets `KRAFT_TEMPLATES_DIR` to the old default and you also made a `config/`, the server refuses to start until you merge `templates/` into `config/` and remove it.
  - A directory you point at anywhere else is never renamed. A `templates` that is a link to another directory (a dotfiles repo) isn't renamed or merged either, and its files aren't read, except a `harnesses/` directory in it, which stays read until a `config/harnesses` exists. The start prints a warning naming the target, and the `config` row warns the same. Do: set `KRAFT_CONFIG_DIR` to that target.
  - `kraft admin doctor --json` names the row `config`, not `templates`.
- **A schedule's day of week `7` is Sunday, as in cron.** 1.4 accepted `7` and never fired it. Ranges (`1-5`) and steps (`*/15`) work now. Do: a `0 9 * * 7` trigger that never ran in 1.4 fires every Sunday after the update, so change or remove it first if that isn't what you want.
- **A `steering/` directory is no longer read.** Every 1.x start folded it into `library.yaml`, so a directory left over is only files. Do: on a 0.x home updated straight to the new release, copy those files' text into `library.yaml`'s `steering:` by hand.
- **Three keys moved.** Every old place is still read, so a hand-written file stops nothing, except `max_concurrent` in `intake.yaml`: the server ignores it, with a warning, until the next start moves it to `policy.yaml`. `kraft admin doctor`'s `moved keys` row names each old place you still have.

| Before | Now | What to do |
|---|---|---|
| `triggers:` in `policy.yaml` | `schedules:` in `intake.yaml`, edited on Settings › Auto-intake | Nothing: the first start moves it. |
| `max_concurrent` in `intake.yaml` | `max_concurrent` in `policy.yaml`, on Settings › Policy › Housekeeping | Nothing: the first start moves it, unless `policy.yaml` already sets one. |
| `default_chain_template` in a repo entry | `default_chain` | Nothing: the old key is still read. |
| `board.group_by: template` in `theme.yaml` | `board.group_by: chain` | Nothing: the old value reads as `chain`. |

Unless the notes below apply, there is nothing to do:

- Each file a key moves between is rewritten, readable by you alone (`0600`); the rest of it keeps its comments and layout. A moved trigger takes its comments with it. A comment line above `triggers:` itself stays in `policy.yaml` when it sits over the next key: delete it by hand. A comment on the `max_concurrent` line is dropped.
- A trigger that the schedule format refuses (1.4 ignored an extra key such as `enabled: false`) stays in `policy.yaml`, still read and fired, and the rest move. Doctor's `moved keys` row names the key that keeps each one there.
- A trigger whose `cron` names a value outside its field (`0 24 * * *`, `0 9 * * 8`), which 1.4 loaded and never ran, or a number in digits other than 0-9, stays in `policy.yaml` and is skipped, with a warning, rather than refusing the file.

**Four `repos.yaml` keys an older Kraft wrote aren't read.** A repo still carrying one loads, the server log names it once, and `kraft admin doctor`'s `keys` row warns, naming what replaced it. `gitlab_project` is still read as `forge: gitlab` and `project:`.

| Before | Now | What to do |
|---|---|---|
| `default_model` | A model per [harness profile](/concepts/vocabulary#harness-profile) under `models:` | Replace the key. |
| `submodules` | Each submodule as an entry of its own | Replace the key. |
| `default_root_merge_policy` | A [workspace](/concepts/vocabulary#workspace)'s `root_pointer_default` | Replace the key. |
| `allow_cross_repo` | Nothing | Remove it. |

### The interface

- **The new interface replaced the old one, and some pages moved.** Old addresses still open the right page, and keep their query string. No action. An address that began with `/ng` drops that prefix, and an old tab address (`/work-items/ID#tab=changes`) opens the item's review page.
- **The theme file changes once.** The first start rewrites `theme.yaml` so the look you had stays, and keeps the original as `theme.yaml.pre-2.0`. No action: [`palette` is legacy](/reference/configuration/theme#palette-is-legacy) says what each old palette becomes. If it looks wrong, pick the surface, accent and amount of colour on Settings › Appearance.
- **The VS Code extension needs the same major version.** VS Code updates the extension on its own. Against a 1.4 server it shows the board but disables every action, and a 1.4 extension is read-only against a newer server. Do: update Kraft and the extension together; the messages are in [VS Code](/reference/vscode-extension#if-the-extension-is-read-only).
- **The phone layout** shows on a screen narrower than 768 pixels. No action: see [Kraft on a phone](/guides/day-to-day/kraft-on-a-phone).

Three more changes need nothing. Cursor's hook entry runs Kraft's Python with `-I`, and the server adds it to each existing worktree. [Agent profiles](/concepts/vocabulary#agent-profile) in `harnesses.yaml` are written as `providers:`, and the older `model:` map still loads. `kraft admin restart` and `update --restart` list the running items first, and ask in a terminal.

## Roll back to 1.4

Starting a newer Kraft migrates `run/orchestrator.db` forward in place, and there is no downgrade migration: 1.4 refuses a database a newer release migrated (`database schema vN is newer than code vM`, in `run/logs/server.log`). A rollback puts back the release, the database as 1.4 left it (schema 44) and the config files the newer release changed. It loses everything done since that backup: items filed, runs, approvals and their history.

You need the database as 1.4 left it: a [backup you took before the update](/guides/run/back-up-and-restore#back-up-the-database), or the copy Kraft made when you first left 1.4. That copy isn't always the newest, because a later upgrade adds a newer one that 1.4 refuses. A 1.5.0 release candidate before 1.5.0rc12 made no copy, and only your own backup rolls back.

The commands that name your Kraft home set `home` or `run` themselves, so each block works in a new terminal. Step 1 only checks: if it finds no database you stop there and stay on the new release.

1. Pick a database that prints schema 44, before you stop anything. For Kraft's copy, follow [Find the copy to restore](/guides/run/back-up-and-restore#find-the-copy-to-restore) and take the newest one that prints 44. For your own backup, set `backup` to its path and read its schema (a backup taken after the update doesn't print 44). [Back up without sqlite3](/guides/run/back-up-and-restore#back-up-without-sqlite3) has a Python form for a machine without `sqlite3`:

   ```bash
   backup="$HOME/kraft-backup-20261002-093015.db"
   sqlite3 -readonly "$backup" 'PRAGMA user_version'
   ```

   ```text
   44
   ```

   Write down the path: step 4 uses it. If no copy prints 44 and you have no backup of your own, stop here.
2. Stop Kraft with `kraft admin stop`, or as [Stop a service](/guides/run/run-as-a-service#stop-a-service) says when Kraft runs as a service: the service manager starts a stopped server again. Go on only when it prints `kraft: stopped (pid N)` or `kraft: no server running`. If it prints `kraft: pid N did not stop within 15s` and exits 1, the server still runs: don't touch the database.
3. Install 1.4 with the Python you run Kraft on and the extra you have. On Homebrew, which can't install an older release, see [Pin a version](/guides/run/upgrade-kraft#pin-a-version). Leave out `[vector]` if you don't use vector search:

   ```bash
   uv tool install --force --python 3.X "kraft-sdlc[vector]==1.4.0"
   kraft --version
   ```

   ```text
   kraft 1.4.0
   ```

   If it prints another version, 1.4 isn't what your shell runs: read the error the install printed, and run `command -v kraft` to see which `kraft` comes first on `PATH`. If you skipped step 2, the web UI says **An older Kraft is installed** and points to [Pin or roll back a version](/guides/run/upgrade-kraft#pin-or-roll-back-a-version).
4. Restore the database from step 1: follow steps 2 and 3 of [Restore a backup](/guides/run/back-up-and-restore#restore-a-backup), with `backup` set to the file from step 1. Skip its step 1, because step 2 here stopped Kraft, and its steps 4 and 5, because steps 5 and 6 here handle the config directory and start Kraft. Then check the restored database:

   ```bash
   run="${KRAFT_RUN_DIR:-${KRAFT_HOME:-$HOME/.kraft}/run}"
   sqlite3 -readonly "$run/orchestrator.db" 'PRAGMA user_version'
   ```

   ```text
   44
   ```

   If it prints another number, repeat steps 1 and 4 with a copy that prints 44. If it prints an error, no database is in place: read the message the restore printed, and run it again.
5. Put the config files back as 1.4 reads them. A rollback doesn't undo what the newer release changed in `$KRAFT_HOME/config/`. Do the first row's commands, then edit each file in the table:

   | File | What to change for 1.4 | If you skip it |
   |---|---|---|
   | The directory | Rename `config/` back to `templates/`, as below | 1.4 seeds a fresh default home beside yours, with no repos |
   | `intake.yaml` | Write each schedule's `cron` as `*` or a comma list of numbers: `1-5` as `1,2,3,4,5`, `*/15` as `0,15,30,45`, day `7` as `0` | A `cron` with day `7` never fires |
   | `intake.yaml` and `policy.yaml` | Move the `schedules:` list under a `triggers:` key in `policy.yaml`, then delete the `schedules:` key, even `schedules: []` | Auto-intake stays off while `health` says `ok` |
   | `policy.yaml` | Add the `triggers:` key yourself: a seeded `# triggers:` is a comment, so pasting under it breaks the file. Delete `forge_poll_s`. `max_concurrent` needs nothing | Every new item is refused (`policy config invalid, refusing work`) |
   | `repos.yaml` | Rename each `default_chain:` to `default_chain_template:`. Where an entry has both, keep the value of `default_chain` and delete that line | Doctor's `keys` row fails and the repo files on `default` |
   | `harnesses.yaml` | Rewrite each `providers:` profile as one `model:` map by provider and one `effort:`, as below | 1.4 refuses the whole file |
   | `theme.yaml` | Restore the theme, as below | The board shows default colours, or no theme |

   Check the directory. 1.4 reads `templates` under `$KRAFT_HOME`, which is `~/.kraft` unless you set it:

   ```bash
   home="${KRAFT_HOME:-$HOME/.kraft}"
   ls -ld "$home/templates"
   ```

   - **A link (`templates -> config`):** nothing to do.
   - **`No such file or directory`:** the link is gone. This moves nothing if `templates` exists, because `mv` would put `config/` inside it:

     ```bash
     home="${KRAFT_HOME:-$HOME/.kraft}"
     if [ -e "$home/templates" ] || [ -L "$home/templates" ]; then
       echo "$home/templates exists: nothing moved"
     else
       mv "$home/config" "$home/templates"
     fi
     ```

   - **A real directory, not a link:** the first start found a `config/` you had made and couldn't merge the two (`kraft admin doctor`'s `config` row named both). Move what `templates/` still holds into `config/`, keeping the copy you want of each, then set `templates/` aside and link it. Nothing is deleted: delete `templates.old-<time>` once 1.4 runs and [Check the rollback](#check-the-rollback) passes:

     ```bash
     home="${KRAFT_HOME:-$HOME/.kraft}"
     old="$home/templates.old-$(date +%Y%m%d-%H%M%S)"
     if [ -L "$home/templates" ] || [ ! -d "$home/templates" ]; then
       echo "$home/templates is not a real folder: nothing moved"
     elif [ ! -d "$home/config" ]; then
       echo "$home/config is not a folder: nothing moved"
     elif [ -e "$old" ]; then
       echo "$old is already there: run this again"
     else
       mv "$home/templates" "$old" && ln -s config "$home/templates" && ls -ld "$home/templates"
     fi
     ```

   - **`KRAFT_CONFIG_DIR` points elsewhere:** the directory was never renamed. Point 1.4's `KRAFT_TEMPLATES_DIR` at it instead.

   Rewrite a `providers:` profile in 1.4's shape. 1.4 has one `effort` per profile: where the providers set different ones, pick one. A profile already in the `model:` shape needs nothing:

   ```yaml
   # newer release
   strong:
     providers:
       claude: { model: sonnet, effort: high }
       codex: { model: gpt-5.6-terra, effort: high }
   # 1.4
   strong:
     model: { claude: sonnet, codex: gpt-5.6-terra }
     effort: high
   ```

   Restore the theme. 1.4 takes its colours from `palette`, which the newer release removed. Copy the file kept beside `theme.yaml` over it: `theme.yaml.pre-2.0`, or the copy a 1.5.0 release candidate made (`theme.yaml.pre-1.5`, or `theme.yaml.pre-ux2` from rc5 to rc9) if one converted the theme first. The block moves the current `theme.yaml` aside as `theme.yaml.before-rollback-<time>` and copies only when the source exists. Delete the dated file once 1.4 shows the theme you want:

   ```bash
   home="${KRAFT_HOME:-$HOME/.kraft}"
   copy="$home/templates/theme.yaml.pre-2.0"
   saved="$home/templates/theme.yaml.before-rollback-$(date +%Y%m%d-%H%M%S)"
   if [ ! -f "$copy" ]; then
     echo "$copy is not a file: nothing changed. Set copy to the right file, or edit theme.yaml by hand"
   elif [ -e "$saved" ]; then
     echo "$saved is already there: run this again"
   elif [ -e "$home/templates/theme.yaml" ] && ! mv "$home/templates/theme.yaml" "$saved"; then
     echo "could not move theme.yaml aside: nothing changed"
   else
     cp "$copy" "$home/templates/theme.yaml" && ls -l "$home/templates/theme.yaml" || echo "the copy failed: the theme you had is at $saved, if there was one"
   fi
   ```

   With no copy, open `theme.yaml`, change `group_by: chain` to `group_by: template` and delete an `editor:` line, or delete the file. 1.4 refuses both, and its board then loads no theme.
6. Start Kraft with `kraft admin start --detach`, or with `kraft admin install-service` if it ran as a service.

### Check the rollback

Run `kraft --version`, then `kraft admin templates lint` and `kraft admin doctor`. It worked when `--version` prints `kraft 1.4.0`, the board loads, `templates lint` exits 0, and `doctor` shows no failing `templates` row (1.4's name for the config directory row) or `keys` row. Each row of the table in step 5 names its symptom: a `database schema vN is newer than code vM` line means the database isn't the one 1.4 left, so repeat steps 1 and 4.

### What the restore leaves behind

Restoring loses everything done on the newer release since the backup. It doesn't remove what those runs made outside the database: their worktrees under `run/worktrees/`, their branches, and any merge requests they opened. 1.4 knows nothing about them.

- `kraft admin doctor`'s `worktrees` row lists a worktree with no work item. Delete the ones you don't need, and close any merge request yourself. 1.4's row also lists the worktrees of items you cancelled on 1.4, which its board doesn't show.
- A worktree made after the update is one whose ID isn't in the database you restored. This lists the IDs that are, and `-readonly` makes a wrong path an error, not an empty database where Kraft is about to start:

  ```bash
  run="${KRAFT_RUN_DIR:-${KRAFT_HOME:-$HOME/.kraft}/run}"
  sqlite3 -readonly "$run/orchestrator.db" "select id from work_items"
  ```

## From a release candidate or 0.x

An update between 2.x releases needs only [Upgrade Kraft](/guides/run/upgrade-kraft). Back up the database first in each case below, as step 1 of [Upgrade](/guides/run/upgrade-kraft#upgrade) says, and keep the file name: a rollback to 1.4 needs it.

### A 1.5.0 release candidate

The 1.5.0 release candidates, `1.5.0rc1` to `1.5.0rc14`, were pre-releases of 2.0. Pause the running items first, or wait until none run. Which command updates you depends on the candidate:

- **1.5.0rc14:** `kraft admin update` follows the release-candidate channel and keeps `[vector]` and your Python. `kraft admin update --channel stable` waits for the next stable release.
- **1.5.0rc13:** `kraft admin update` installs without `[vector]` and on uv's default Python, as 1.4's does. Use the `uv tool install` command from [Update from 1.4](#update-from-14), then `kraft admin restart`.
- **An earlier candidate:** `kraft admin update` compares against stable releases and says you are up to date. Use the same `uv tool install` command.

Restart the server with `kraft admin restart` unless the update did, then check `kraft --version` and `kraft admin health`. After an update run by rc14 or earlier, vector search may have stopped: reinstall the extra as in [Add vector search](/guides/run/upgrade-kraft#add-vector-search).

Where uv had recorded no Python for Kraft, an update run by rc14 records one Python patch release, so `uv python upgrade` leaves Kraft behind. Run `grep python "$(uv tool dir)/kraft-sdlc/uv-receipt.toml"`, and if it shows a path, run the `uv tool install --force --python 3.X …` command once to tie Kraft to the minor version.

A `uv.lock` that an open item's setup command wrote under 1.5.0rc14 was recorded without a digest, so the item's rebase can stop on it: see [Git wouldn't start the rebase](/troubleshooting/worktree-and-git-stops#git-wouldnt-start-the-rebase). Items started on a stable release are recorded with a digest.

### An install from before the `kraft-sdlc` rename

An older install can still hold a `kraft` uv tool next to `kraft-sdlc`. `kraft admin update` then stops and names the two commands that clear it. The reinstall is needed because the uninstall removes the `kraft` command both packages share:

```bash
uv tool uninstall kraft
uv tool install --force --reinstall kraft-sdlc
```

### A 0.x home

A Kraft home from 0.x holds a `registry.yaml` and no `library.yaml`. Kraft doesn't convert it: the server starts degraded and refuses new work until `kraft admin update` replaces the configuration. Harness profile names and the template layout changed in 1.0: read the [1.0.0 changelog](https://github.com/itsOmidKarami/kraft/blob/main/CHANGELOG.md#100) first.

1. Finish or abandon in-flight items, then stop the old server with `kraft admin stop`. It prints `kraft: stopped (pid N)`, or `kraft: no server running` when none runs. On an install from before 0.6.0, stop the server in the terminal it runs in. Back up the database as above: the update keeps the old configuration whole in a backup folder of its own.
2. Install the newest release with the tool you installed Kraft with, as [Install](/get-started/install#installation-methods) shows.
3. Run `kraft admin update`. It says what changes, then asks `Replace it? [y/N]`. Answer `y`; `-y` asks nothing, and with no terminal and no `-y` it prints `kraft admin update: nothing changed. Answer y, or pass -y, to replace it.` and exits 1.
4. Start the server with `kraft admin start --detach`, or run `kraft admin restart` if one is running: a server that came up before the update still holds its degraded state. `kraft admin reload` loads the new library, chains, `policy.yaml` and `intake.yaml` with no restart.
5. Run `kraft --version` and `kraft admin health`. It worked when `--version` prints a 2.x release and `status` says `ok`. A `degraded` server with an `invalid template` row that names the 0.x configuration hasn't read the new one yet: do step 4.

The update moves the old configuration, whole, to `config.pre-v1-<time>` beside the directory it replaces (`templates.pre-v1-<time>` when no 2.x server has started yet). Then:

- `access.yaml`, `notify.yaml`, `theme.yaml`, `repos.yaml`, `intake.yaml` and `harnesses/` carry across.
- `policy.yaml` starts from the shipped default and keeps your value for every key the current format still has. Kraft prints each key it drops, with its old value.
- A `steering/` directory and your old chains and registry stay only in the backup. There is no migration helper: copy the steering text into `library.yaml`'s `steering:` by hand.
- When the release feed is unreachable, the command exits 1 after the configuration was replaced. Running it again changes no configuration. An update interrupted mid-swap is finished by the next start or the next `kraft admin update`.
