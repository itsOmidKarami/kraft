---
title: Back up and restore the database
description: Back up Kraft's database while the server runs, check the backup, restore it, and find the copy Kraft makes before an upgrade.
---

You will have a private, dated copy of Kraft's database that you have checked,
and the steps that put it back. Kraft also makes a copy of its own before an
upgrade migrates the database, and this page says how to find it.

## Before you start

- `$KRAFT_HOME` is `~/.kraft` unless you set it; see
  [Environment variables](/reference/configuration/environment-variables). The
  commands assume the default home: put your own path in place of `~/.kraft` if
  you moved it.
- The commands use the `sqlite3` command. Each one has a Python form for a
  machine without it.
- A backup needs no stop. A restore does: see
  [Restore a backup](#restore-a-backup).

## Back up the database

`run/orchestrator.db` holds every [work item](/concepts/vocabulary#work-item), event, session and review
thread. Kraft runs SQLite in WAL mode, so recent writes can sit in
`orchestrator.db-wal` beside it. Copying `orchestrator.db` alone while the
server runs can give you a copy that is missing them, or one that does not
open.

1. Use SQLite's online backup, which is safe while the server runs. Every form
   below names the file for the second you run it and prints the name. Write the
   name down: verify and restore need it, and it is the file to keep. A backup
   taken at another time never replaces an earlier one, so the copy you took
   before an upgrade is still there after the next one.

   `-readonly` opens the database you copy from read-only, so a wrong path fails
   instead of creating an empty database and an empty backup of it:

   ```bash
   backup="$HOME/kraft-backup-$(date +%Y%m%d-%H%M%S).db"
   sqlite3 -readonly ~/.kraft/run/orchestrator.db ".backup '$backup'" && chmod 600 "$backup" && echo "$backup"
   ```

   ```text
   /home/you/kraft-backup-20261002-093015.db
   ```

   The backup holds everything the database holds, and `.backup` makes it
   readable by other accounts under the usual umask. The `chmod` keeps it at
   `600`, like the database.

   No `sqlite3` command? Python does the same:

   ```bash
   backup="$HOME/kraft-backup-$(date +%Y%m%d-%H%M%S).db"
   python3 -c "import sqlite3, sys; sqlite3.connect('file:$HOME/.kraft/run/orchestrator.db?mode=ro', uri=True).backup(sqlite3.connect(sys.argv[1]))" "$backup" && chmod 600 "$backup" && echo "$backup"
   ```

   Or stop the server first, then copy the file. Use this form only for a
   server that stops cleanly: a server that crashed can leave a `-wal` file
   beside `orchestrator.db` that a copy of the `.db` alone misses, and the
   `.backup` form above is the safe one.

   The lines are chained with `&&`, so
   nothing is copied unless `kraft admin stop` succeeded. It prints
   `kraft: stopped (pid N)` or `kraft: no server running`, and the copy goes on.
   If it prints `kraft: pid N did not stop within 15s` and exits 1, the server is
   still running and the chain ends there.

   Stopping ends the agents of running items: pause them first, as
   [A restart ends running agents](/guides/run/restart-kraft#a-restart-ends-running-agents)
   says. The last line starts a detached server, even if yours ran in a terminal
   or none ran. If `cp`, `chmod` or `echo` fails, the server stays stopped: start
   it with `kraft admin start --detach`. If `stop` fails, nothing was copied and
   the server is still running.

   ```bash
   backup="$HOME/kraft-backup-$(date +%Y%m%d-%H%M%S).db"
   kraft admin stop &&
     cp ~/.kraft/run/orchestrator.db "$backup" &&
     chmod 600 "$backup" &&
     echo "$backup" &&
     kraft admin start --detach
   ```

   ```text
   kraft: stopped (pid 48213)
   /home/you/kraft-backup-20261002-093015.db
   kraft: http://127.0.0.1:8765 (pid 48390, detached - kraft admin stop)
   ```

   If Kraft runs as a service, `kraft admin stop` is not enough: the service
   manager starts the server again in the middle of the copy. Stop it as
   [Stop a service](/guides/run/run-as-a-service#stop-a-service) says, and run
   this block only after `kraft admin stop` printed `kraft: stopped (pid N)` or
   `kraft: no server running`. Then bring the service back with
   `kraft admin install-service`:

   ```bash
   backup="$HOME/kraft-backup-$(date +%Y%m%d-%H%M%S).db"
   cp ~/.kraft/run/orchestrator.db "$backup" &&
     chmod 600 "$backup" &&
     echo "$backup"
   ```

2. Copy `config/` and `run/attachments/` too. A database restore brings back
   neither. Copy `config/` whole: `access.yaml` holds your password hash,
   `notify.yaml` a webhook URL, and `repos.yaml` any `env:` values, so the copy
   stays private.

   The folder is named for the second you run the command, and
   `mkdir` stops the command if the name is already there, so an earlier copy is
   never overwritten. Write down the name it prints: the restore needs it. Use
   your `$KRAFT_HOME` in place of `~/.kraft` if you set one:

   ```bash
   files="$HOME/kraft-files-$(date +%Y%m%d-%H%M%S)"
   mkdir -m 700 "$files" && cp -R ~/.kraft/config ~/.kraft/run/attachments "$files"/ && echo "$files"
   ```

   ```text
   /home/you/kraft-files-20261002-093015
   ```

   [Keep your configuration in git](/guides/run/upgrade-your-configuration#keep-your-config-in-git)
   leaves `access.yaml` and `notify.yaml` out on purpose, so a git copy alone is
   not a complete backup.

`run/attachments/` holds the spec and plan copy of each item filed with one.
After a restore, an item that has not started needs its copy: without it the
item stops when its worktree is made, and the message names the missing file.

You do not need to back up `run/index.db`. It is the search index, and
`kraft admin reindex` rebuilds it.

## Verify the backup

Open the copy and count its work items. Each block sets `backup` to the file
your backup step printed, so it works in a new terminal. `-readonly` makes a
wrong name fail instead of creating an empty file:

```bash
backup="$HOME/kraft-backup-20261002-093015.db"   # the file your backup step printed
sqlite3 -readonly "$backup" "PRAGMA integrity_check; SELECT count(*) FROM work_items;"
```

Without the `sqlite3` command:

```bash
backup="$HOME/kraft-backup-20261002-093015.db"   # the file your backup step printed
python3 -c "import sqlite3, sys; db = sqlite3.connect('file:' + sys.argv[1] + '?mode=ro', uri=True); print(db.execute('PRAGMA integrity_check').fetchone()[0]); print(db.execute('SELECT count(*) FROM work_items').fetchone()[0])" "$backup"
```

Both print two lines:

```text
ok
42
```

You know it worked when the first line is `ok` and the second is the number of
work items you expect.

## Restore a backup

A restore replaces the database, so everything done since the backup is lost.
Do the steps in order. Each block sets the shell variables it uses, so each
works in a new terminal, and `run` follows your `$KRAFT_HOME` when you set one.

1. Stop the server with `kraft admin stop`. If Kraft runs as a
   [service](/guides/run/run-as-a-service#run-kraft-as-a-service), read the
   warning in [Stop a service](/guides/run/run-as-a-service#stop-a-service)
   first, run `kraft admin uninstall-service`, then run `kraft admin stop`
   anyway: `uninstall-service` does not wait for the server, which can take up
   to 10 seconds to finish and still holds the database until it does.

   Go on only when `kraft admin stop` prints `kraft: stopped (pid N)` or
   `kraft: no server running`. If it prints `kraft: pid N did not stop within 15s`
   and exits 1, the server is still running: do not touch the database.
2. Move the current database aside, with the files SQLite keeps beside it. Kraft
   runs SQLite in WAL mode, and `orchestrator.db-wal` holds writes that belong to
   the file it sits beside, so the three move together and none stays behind for
   the restored database to meet. The directory name carries the time, so a
   second restore never touches the first one's copy, and `mv -n` never
   overwrites:

   ```bash
   run="${KRAFT_HOME:-$HOME/.kraft}/run"
   safe="$run/before-restore-$(date +%Y%m%d-%H%M%S)"
   mkdir "$safe" && for f in orchestrator.db orchestrator.db-wal orchestrator.db-shm; do
     if [ -e "$run/$f" ]; then mv -n "$run/$f" "$safe"/; fi
   done && ls "$safe"
   ```

   The `ls` lists `orchestrator.db`, and `orchestrator.db-wal` and
   `orchestrator.db-shm` when the server left them. If `mkdir` reports an error,
   or `ls` lists nothing, stop: nothing was moved, or the database was not where
   this command looked. Run twice, this step leaves an empty `before-restore-*`
   folder: the one that holds `orchestrator.db` is the one that matters.

   Delete `$safe` once you have checked the restored database in step 5 and no
   longer need what the old one held. Until then it is the only copy of that
   work.
3. Put the backup in place as `orchestrator.db`, readable by you alone (`0600`,
   as Kraft makes it). Put the path of the file your backup step printed in
   `backup`, or of the copy you chose in
   [Find the copy to restore](#find-the-copy-to-restore). The block refuses to
   run while `orchestrator.db`, `orchestrator.db-wal` or `orchestrator.db-shm` is
   in `run/`, so a second run cannot replace a database Kraft has written since,
   or put the backup beside a leftover WAL file that SQLite would replay into it:

   ```bash
   backup="$HOME/kraft-backup-20261002-093015.db"   # the file your backup step printed
   run="${KRAFT_HOME:-$HOME/.kraft}/run"
   if [ -e "$run/orchestrator.db" ] || [ -e "$run/orchestrator.db-wal" ] || [ -e "$run/orchestrator.db-shm" ]; then
     echo "a database file is already in $run: do step 2 first, unless step 3 is already done"
   else
     cp "$backup" "$run/orchestrator.db" && chmod 600 "$run/orchestrator.db"
   fi
   ```

   It prints nothing when it works. If `cp` prints an error, do not start
   Kraft: it would create an empty database and show an empty board. Fix the
   path, do step 2 again (it moves a half-written copy aside), then run this
   block again.
4. Put `config/` and `run/attachments/` back, if you lost them or they are
   wrong. Do it while the server is still stopped from step 1. A database
   restore does not touch them. This overwrites each file of
   the same name with the copy from step 2 of
   [Back up the database](#back-up-the-database), so move aside anything newer
   first. Set `files` to the folder that step printed, and use your
   `$KRAFT_CONFIG_DIR` in place of `$home/config` if you set one:

   ```bash
   files="$HOME/kraft-files-20261002-093015"   # the folder your files copy printed
   home="${KRAFT_HOME:-$HOME/.kraft}"
   mkdir -p "$home/config" "$home/run/attachments" &&
     cp -R "${files:?set files to the folder your copy printed}/config/." "$home/config/" &&
     cp -R "$files/attachments/." "$home/run/attachments/"
   ```

   It prints nothing when it works, and running it again copies the same files
   again. `ls "$home/config"` shows the files that are back.
5. Start the Kraft release that wrote the backup, with `kraft admin start --detach`
   (or `kraft admin install-service` if you removed the service in step 1). To
   go back a release first, see
   [Pin or roll back a version](/guides/run/upgrade-kraft#pin-or-roll-back-a-version).

`kraft admin start --detach` prints the address and the server's process id:

```text
kraft: http://127.0.0.1:8765 (pid 48213, detached - kraft admin stop)
```

You know it worked when `kraft view list --all` shows the items the backup held.
`run/index.db` needs no restore: the server rescans repo documents when it
starts, and `kraft admin reindex` rescans them on demand.

### If the restore went wrong

If the board is empty or shows the wrong items, put the old database back. The
copy in `$safe` is untouched.

1. Stop the server, as in step 1.
2. Move the restored files into a new directory, so nothing is overwritten:

   ```bash
   run="${KRAFT_HOME:-$HOME/.kraft}/run"
   bad="$run/restored-$(date +%Y%m%d-%H%M%S)"
   mkdir "$bad" && for f in orchestrator.db orchestrator.db-wal orchestrator.db-shm; do
     if [ -e "$run/$f" ]; then mv -n "$run/$f" "$bad"/; fi
   done && ls "$bad"
   ```

3. Move the old files back. This block sets both variables itself, so it is
   safe in a new terminal. List the copies, then put the name of the one that
   holds `orchestrator.db`, which step 2 of the restore made, in place of
   `before-restore-20261002-093015`. The block moves nothing while a database
   file is in `run/`:

   ```bash
   run="${KRAFT_HOME:-$HOME/.kraft}/run"
   ls -d "$run"/before-restore-*
   safe="$run/before-restore-20261002-093015"
   if [ -e "$run/orchestrator.db" ] || [ -e "$run/orchestrator.db-wal" ] || [ -e "$run/orchestrator.db-shm" ]; then
     echo "a database file is still in $run: do step 2 here first"
   elif [ ! -d "$safe" ]; then
     echo "$safe is not a directory: check the name against the ls above"
   else
     for f in orchestrator.db orchestrator.db-wal orchestrator.db-shm; do
       if [ -e "$safe/$f" ]; then mv -n "$safe/$f" "$run"/; fi
     done && ls "$run"/orchestrator.db*
   fi
   ```

   A message means nothing was moved: act on it. Otherwise the last `ls` lists
   `orchestrator.db` back in `run/`. If it lists nothing, `$safe` was an empty
   folder: pick the one that holds `orchestrator.db` and run the block again.

4. Start Kraft as in step 5 of the restore.

## The copy Kraft makes before an upgrade

When a newer Kraft starts on an older database, it migrates the database
forward, and the older version cannot open the result. So before it migrates,
Kraft copies the database to `run/orchestrator.db.pre-v<N>-<time>`, where `<N>`
is the schema version it is about to migrate to and `<time>` is when it made
the copy. `run/logs/server.log` names the file:

```text
database schema v44 -> v52: backed up the old database to /home/you/.kraft/run/orchestrator.db.pre-v52-20261002-093015
```

The copy is consistent even while the WAL holds recent writes, and only you
can read it (`0600`). Each migration makes a new copy and never overwrites an
older one. If you upgrade, roll back and upgrade again, the newest
`orchestrator.db.pre-v52-*` is the one that holds what you did in between.

The copy needs about as much free space as the database, beside it in `run/`.
If Kraft cannot write it, it does not migrate: the server does not start, the
database is left unchanged, and the error names the copy and the space it
needs. Free the space and start again.

The copy loses everything done since the upgrade, and it is no substitute for
your own backup: make one before every upgrade. Once you are sure you will stay
on the new version, delete the copies. Kraft never deletes them itself.

### Find the copy to restore

The `v<N>` in the name is the schema Kraft migrated to, not the one the copy
holds. After more than one upgrade, the newest copy can hold a schema the
release you go back to refuses. Restore the newest copy whose own schema is the
one that release runs, and 1.4's schema is 44.

1. Print each copy's schema, then its name, one line per copy. This only reads
   the copies: `-readonly` makes a missing file an error instead of an empty
   file named like a copy. Names sort by schema, then by time:

   ```bash
   run="${KRAFT_HOME:-$HOME/.kraft}/run"
   for f in "$run"/orchestrator.db.pre-v*; do echo "$(sqlite3 -readonly "$f" 'PRAGMA user_version') $f"; done
   ```

   Without the `sqlite3` command, Python prints the same:

   ```bash
   run="${KRAFT_HOME:-$HOME/.kraft}/run"
   python3 -c 'import glob, sqlite3, sys; [print(sqlite3.connect(f"file:{f}?mode=ro", uri=True).execute("PRAGMA user_version").fetchone()[0], f) for f in sorted(glob.glob(sys.argv[1] + "/orchestrator.db.pre-v*"))]' "$run"
   ```

   ```text
   44 /home/you/.kraft/run/orchestrator.db.pre-v52-20261002-093015
   ```

   An error naming `orchestrator.db.pre-v*`, or no lines, means Kraft made no
   copy.
2. Pick the newest line that starts with the schema you are going back to, such
   as `44`.
3. Restore that file as in [Restore a backup](#restore-a-backup), with `backup`
   set to its path.

For 1.4's database, the first release you ran after 1.4 decides which copy
holds it, and a 1.5.0 release candidate may have made none: see
[Upgrading from a 1.5.0 release candidate](/guides/run/upgrade-from-1-4#upgrading-from-a-150-release-candidate).
