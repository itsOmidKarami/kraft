title: Back up and restore the database
description: Back up Kraft's database while the server runs, check the backup, restore it, find the copy Kraft makes before an upgrade and roll back to an earlier 2.x release.
---

You get a private, dated copy of Kraft's database that you have checked,
and the steps that put it back. Kraft also makes a copy of its own before an
upgrade migrates the database, and this page says how to find it.

## Before you start

Run this block first, in every terminal you use for the steps below:

```bash
run="${KRAFT_RUN_DIR:-${KRAFT_HOME:-$HOME/.kraft}/run}"
config="${KRAFT_CONFIG_DIR:-${KRAFT_TEMPLATES_DIR:-${KRAFT_HOME:-$HOME/.kraft}/config}}"
config="${config%/}"
stopped() { [ -n "$run" ] && [ -n "$config" ] || { echo "run the Before you start block first" >&2; return 1; }; [ ! -e "$run/kraft.pid" ] || { echo "$run/kraft.pid exists: a server may be running. If a service runs Kraft, follow Stop a service on the Run Kraft as a service page. Otherwise run kraft admin stop, which also clears a stale pid file."; false; }; }
```

It finds `run/` and `config/` as Kraft does: `run` from `$KRAFT_RUN_DIR`, then
`$KRAFT_HOME` (`~/.kraft` unless you set it; see
[Environment variables](/reference/configuration/environment-variables)), and
`config` from `$KRAFT_CONFIG_DIR`, then `$KRAFT_TEMPLATES_DIR`, then
`$KRAFT_HOME`.

A 1.4 home that no 2.0 start has renamed keeps its configuration in
`templates/`: put that folder in the `config=` line.

`stopped` is the guard the steps that change files in `run/` or `config/` use.
It prints a message and fails while `kraft.pid` is there. In a terminal where
you haven't run the block, `stopped` isn't found and the step does nothing.

- The commands use the `sqlite3` command. [Back up without sqlite3](#back-up-without-sqlite3)
  has a Python form for a machine without it.
- A backup needs no stop. A restore does: see
  [Restore a backup](#restore-a-backup).

## Back up the database

`run/orchestrator.db` holds every [work item](/concepts/vocabulary#work-item), event, session and review
thread. Kraft runs SQLite in WAL mode, so recent writes can sit in
`orchestrator.db-wal` beside it. A plain copy of `orchestrator.db` while the
server runs isn't a backup: it can miss them, or not open.

1. Use SQLite's online backup, which is safe while the server runs. The command
   names the file for the second you run it and prints the name. Write the name
   down: verify and restore need it, and it is the file to keep. A backup taken at
   another time never replaces an earlier one, so the copy you took before an
   upgrade is still there after the next one.

   `-readonly` opens the database you copy from read-only, so a wrong path fails
   instead of creating an empty database and an empty backup of it:

   ```bash
   backup="$HOME/kraft-backup-$(date +%Y%m%d-%H%M%S).db"
   sqlite3 -readonly "$run/orchestrator.db" ".backup '$backup'" && chmod 600 "$backup" && echo "$backup"
   ```

   ```text
   /home/you/kraft-backup-20261002-093015.db
   ```

   The backup holds everything the database holds, and `.backup` makes it
   readable by other accounts under the usual umask. The `chmod` keeps it at
   `600`, like the database. With no `sqlite3` command, use
   [Back up without sqlite3](#back-up-without-sqlite3).
2. Copy `config/`, `run/items/` and `run/attachments/` too. A database
   restore brings back none of them. Copy `config/` whole: `access.yaml` holds your password hash,
   `notify.yaml` a webhook URL, and `repos.yaml` any `env:` values, so the copy
   stays private.

   `config/` also holds `addons.yaml` and `addons.lock`, which are all a
   backup needs of your installed
   [Kraft add-ons](/concepts/vocabulary#add-on) from git collections.
   `run/addons/` needs no copy. An add-on from a directory collection comes
   back only while that directory still holds the same files.

   The folder is named for the second you run the command, and `mkdir` stops the
   command if the name is already there, so an earlier copy is never overwritten.
   Write down the name it prints: the restore needs it.

   `cp -RH` follows a `config`, `items` or `attachments` that is itself a
   symbolic link, so the copy holds the files, not a link that dangles without
   the original. A link inside them is copied as a link:

   ```bash
   files="$HOME/kraft-files-$(date +%Y%m%d-%H%M%S)"
   mkdir -m 700 "$files" && cp -RH "$config" "$files/config" && cp -RH "$run/items" "$files/items" && cp -RH "$run/attachments" "$files/attachments" && echo "$files"
   ```

   ```text
   /home/you/kraft-files-20261002-093015
   ```

   [Keep your configuration in git](/guides/run/upgrade-your-configuration#keep-your-config-in-git)
   leaves `access.yaml` and `notify.yaml` out on purpose, so a git copy alone
   isn't a complete backup.

`run/items/` holds each item's documents, session logs and the spec and plan
copy it was filed with; `run/attachments/` holds that copy for an item filed
before Kraft kept one folder per item. After a restore, an item that hasn't
started needs its copy: without it the item stops when its worktree is made,
and the message names the missing file. A sandboxed item's `sandbox-home/` in
its folder is only a cache, and can be left out of the copy.

You don't need to back up `run/index.db`. It is the search index, and
`kraft admin reindex` rebuilds it.

### Back up without sqlite3

Python does the same as step 1, and prints the same name:

```bash
backup="$HOME/kraft-backup-$(date +%Y%m%d-%H%M%S).db"
python3 -c "import sqlite3, sys; sqlite3.connect('file:' + sys.argv[1] + '?mode=ro', uri=True).backup(sqlite3.connect(sys.argv[2]))" "$run/orchestrator.db" "$backup" && chmod 600 "$backup" && echo "$backup"
```

## Verify the backup

Open the copy and count its work items. Set `backup` to the file your backup step
printed, so the block works in a new terminal. `-readonly` makes a wrong name
fail instead of creating an empty file:

```bash
backup="$HOME/kraft-backup-20261002-093015.db"
sqlite3 -readonly "$backup" "PRAGMA integrity_check; SELECT count(*) FROM work_items;"
```

Without the `sqlite3` command, set `backup` the same way:

```bash
backup="$HOME/kraft-backup-20261002-093015.db"
python3 -c "import sqlite3, sys; db = sqlite3.connect('file:' + sys.argv[1] + '?mode=ro', uri=True); print(db.execute('PRAGMA integrity_check').fetchone()[0]); print(db.execute('SELECT count(*) FROM work_items').fetchone()[0])" "$backup"
```

Both print two lines:

```text
ok
42
```

You know it worked when the first line is `ok` and the second is the number of
work items you expect.

## Restore a backup

A restore replaces the database, so everything done since the backup is lost.
Do the steps in order, with the [shell variables](#before-you-start) set. Each
block that changes files in `run/` or `config/` refuses to run while `kraft.pid`
is there, and says to stop Kraft first. If a block says
`stopped: command not found`, run the [Before you start](#before-you-start)
block again in this terminal.

1. Stop the server with `kraft admin stop`. If Kraft runs as a
   [service](/guides/run/run-as-a-service#run-kraft-as-a-service), read the
   warning in [Stop a service](/guides/run/run-as-a-service#stop-a-service)
   first, run `kraft admin uninstall-service`, then run `kraft admin stop`
   anyway: `uninstall-service` doesn't wait for the server, which can take up
   to 10 seconds to finish and still holds the database until it does.

   Go on only when `kraft admin stop` prints `kraft: stopped (pid N)` or
   `kraft: no server running`. If it prints `kraft: pid N did not stop within 15s`
   and exits 1, the server is still running: don't touch the database.

   While a server is undoing a `git rebase` it was cut off in, or finishing one
   in an in-place item's checkout, `kraft admin stop` says
   `still stopping: a git rebase is being finished or undone` and waits up to
   about 80 seconds in all.
2. Move the current database aside, with the files SQLite keeps beside it. Kraft
   runs SQLite in WAL mode, and `orchestrator.db-wal` holds writes that belong to
   the file it sits beside, so the three move together and none stays behind for
   the restored database to meet. The directory name carries the time, so a
   second restore never touches the first one's copy, and `mv -n` never
   overwrites:

   ```bash
   safe="$run/before-restore-$(date +%Y%m%d-%H%M%S)"
   stopped && mkdir "$safe" && for f in orchestrator.db orchestrator.db-wal orchestrator.db-shm; do
     if [ -e "$run/$f" ]; then mv -n "$run/$f" "$safe"/; fi
   done && ls "$safe"
   ```

   The `ls` lists `orchestrator.db`, and `orchestrator.db-wal` and
   `orchestrator.db-shm` when the server left them. If `mkdir` reports an error,
   or `ls` lists nothing, stop: nothing was moved, or the database wasn't where
   this command looked. A message about `kraft.pid` means nothing was moved: stop
   Kraft, then run the block again. Run twice, this step leaves an empty
   `before-restore-*` folder: the one that holds `orchestrator.db` is the one that
   matters.

   Delete the `before-restore-*` folder that holds `orchestrator.db` once you have
   checked the restored database and no longer need what the old one held. Until
   then it is the only copy of that work.
3. Put the backup in place as `orchestrator.db`, readable by you alone (`0600`,
   as Kraft makes it). Set `backup` to the path of the file your backup step
   printed, or of the copy you chose in
   [Find the copy to restore](#find-the-copy-to-restore).

   The block refuses to run while a server may be running, or while
   `orchestrator.db`, `orchestrator.db-wal` or `orchestrator.db-shm` is in `run/`.
   That means a second run can't replace a database Kraft has written since, or put the
   backup beside a leftover WAL file that SQLite would replay into it:

   ```bash
   backup="$HOME/kraft-backup-20261002-093015.db"
   stopped && if [ -e "$run/orchestrator.db" ] || [ -e "$run/orchestrator.db-wal" ] || [ -e "$run/orchestrator.db-shm" ]; then
     echo "a database file is already in $run: move the old database aside first, unless the backup is already in place"
   elif [ ! -f "$backup" ]; then
     echo "$backup is not a file: set backup to the file your backup step printed"
   else
     cp "$backup" "$run/orchestrator.db" && chmod 600 "$run/orchestrator.db" && ls -l "$run/orchestrator.db"
   fi
   ```

   When it works it prints one line for the restored file, which starts with
   `-rw-------`. If a message appears, nothing was copied: act on it and run the
   block again. If `cp` prints an error, don't start Kraft: it
   would create an empty database and show an empty board. Move the half-written
   copy aside as step 2 does, then run this block again.
4. Put `config/`, `run/items/` and `run/attachments/` back, if you lost them
   or they are wrong. Do it while the server is still stopped from step 1. A database
   restore doesn't touch them.

   The block overwrites each file of the same name in `config/` with the copy from
   step 2 of [Back up the database](#back-up-the-database), so it first copies the
   `config/` you have to a dated folder beside it and prints the name. It stops,
   restoring nothing, if that copy can't be made. Set `files` to the folder that
   step printed:

   ```bash
   files="$HOME/kraft-files-20261002-093015"
   saved="$config.before-restore-$(date +%Y%m%d-%H%M%S)"
   stopped && if [ ! -d "$files/config" ]; then
     echo "$files/config is not a folder: set files to the folder your files copy printed"
   elif [ -e "$saved" ]; then
     echo "$saved is already there: run this again"
   elif [ -d "$config" ] && ! cp -RH "$config" "$saved"; then
     echo "could not copy $config to $saved: nothing was restored. Delete $saved if it is there, fix the cause, and run this again"
   else
     if [ -d "$saved" ]; then echo "the config you had is kept at $saved"; fi &&
       mkdir -p "$config" "$run/items" "$run/attachments" &&
       cp -R "$files/config/." "$config/" &&
       if [ -d "$files/items" ]; then cp -R "$files/items/." "$run/items/"; fi &&
       if [ -d "$files/attachments" ]; then cp -R "$files/attachments/." "$run/attachments/"; fi &&
       ls "$config"
   fi
   ```

   It names the folder that keeps the config you had, then lists the files that are
   back. If `cp` prints an error after that name, the restore stopped partway: the
   named folder still holds everything you had. Any other message means nothing was
   restored: act on it and run the block again.

   Each run makes a new dated folder, so the oldest one holds what you had before
   the first run. Delete it once Kraft runs on the restored config and you no
   longer need what the old files held. Until then it is the only copy of them.

   `items/` and `attachments/` are only added to: `cp -R` replaces a file of the
   same name and removes none, so what an item wrote since the backup stays.
5. Start the Kraft release that wrote the backup, with `kraft admin start --detach`
   (or `kraft admin install-service` if you removed the service in step 1). To
   go back a release first, see
   [Pin or roll back a version](/guides/run/upgrade-kraft#pin-or-roll-back-a-version).

`kraft admin start --detach` prints the address and the server's process id:

```text
kraft: http://127.0.0.1:8765 (pid 48213, detached - kraft admin stop)
```

You know it worked when `kraft view list --all` shows the items the backup held.
`run/index.db` needs no restore: the server rescans repo documents when it
starts, and `kraft admin reindex` rescans them on demand.

`run/addons/` needs none either. When the restored `config/` holds
`addons.lock`, the server fetches each installed add-on again at its locked
commit after it starts, in the background, and loads it once its files match
the locked digest. The same happens when you copy `config/` to a new machine.
The machine needs git access to each collection's URL. `kraft admin doctor`
names an add-on that isn't back on its `add-ons` row. See
[Restoring a store](/reference/configuration/addons#restoring-a-store).

### If the restore went wrong

If the board is empty or shows the wrong items, put the old database back. The
copy in the `before-restore-*` folder is untouched.

1. Stop the server, as in step 1.
2. Move the restored files into a new directory, so nothing is overwritten:

   ```bash
   bad="$run/restored-$(date +%Y%m%d-%H%M%S)"
   stopped && mkdir "$bad" && for f in orchestrator.db orchestrator.db-wal orchestrator.db-shm; do
     if [ -e "$run/$f" ]; then mv -n "$run/$f" "$bad"/; fi
   done && ls "$bad"
   ```

3. Move the old files back. The first line lists the `orchestrator.db` each
   `before-restore-*` folder holds. Put the name of the right folder, which step 2
   of the restore made, in place of `before-restore-20261002-093015`. The block moves nothing while a server may be
   running or a database file is in `run/`:

   ```bash
   ls -d "$run"/before-restore-*/orchestrator.db
   safe="$run/before-restore-20261002-093015"
   stopped && if [ -e "$run/orchestrator.db" ] || [ -e "$run/orchestrator.db-wal" ] || [ -e "$run/orchestrator.db-shm" ]; then
     echo "a database file is still in $run: move the restored files aside first"
   elif [ ! -d "$safe" ]; then
     echo "$safe is not a directory: check the name against the ls above"
   else
     for f in orchestrator.db orchestrator.db-wal orchestrator.db-shm; do
       if [ -e "$safe/$f" ]; then mv -n "$safe/$f" "$run"/; fi
     done && ls "$run"/orchestrator.db*
   fi
   ```

   A message means nothing was moved: act on it. Otherwise the last `ls` lists
   `orchestrator.db` back in `run/`. If it lists nothing, the folder was an empty
   one: pick the one the first line listed and run the block again.

4. Start Kraft as in step 5 of the restore.

## The copy Kraft makes before an upgrade

When a newer Kraft starts on an older database, it migrates the database
forward, and the older version can't open the result. Before it migrates,
Kraft copies the database to `run/orchestrator.db.pre-v<N>-<time>`, where `<N>`
is the schema version it is about to migrate to and `<time>` is when it made
the copy. Two copies in the same second get `-2`, `-3` and so on after the time. `run/logs/server.log` names the file:

```text
database schema v44 -> v52: backed up the old database to /home/you/.kraft/run/orchestrator.db.pre-v52-20261002-093015
```

The copy is consistent even while the WAL holds recent writes, and only you
can read it (`0600`). Each migration makes a new copy and never overwrites an
older one. If you upgrade, roll back and upgrade again, the newest
`orchestrator.db.pre-v52-*` is the one that holds what you did in between.

The copy needs about as much free space as the database, beside it in `run/`.
If Kraft can't write it, it doesn't migrate: the server doesn't start, the
database is left unchanged, and the error names the copy and the space it
needs. Free the space and start again.

The copy loses everything done since the upgrade, and it is no substitute for
your own backup: make one before every upgrade. Once you are sure you stay
on the new version, delete the copies. Kraft never deletes them itself.

### Find the copy to restore

The `v<N>` in the name is the schema Kraft migrated to, not the one the copy
holds. After more than one upgrade, the newest copy can hold a schema the
release you go back to refuses. Restore the newest copy whose own schema is the
one that release runs, and 1.4's schema is 44.

1. Print each copy's schema, then its name, one line per copy. This only reads
   the copies: `-readonly` makes a missing file an error instead of an empty
   file named like a copy. Names sort by schema, then by time:

   ```bash
   for f in "$run"/orchestrator.db.pre-v*; do echo "$(sqlite3 -readonly "$f" 'PRAGMA user_version') $f"; done
   ```

   Without the `sqlite3` command, Python prints the same:

   ```bash
   python3 -c 'import glob, sqlite3, sys; [print(sqlite3.connect(f"file:{f}?mode=ro", uri=True).execute("PRAGMA user_version").fetchone()[0], f) for f in sorted(glob.glob(sys.argv[1] + "/orchestrator.db.pre-v*"))]' "$run"
   ```

   ```text
   44 /home/you/.kraft/run/orchestrator.db.pre-v52-20261002-093015
   ```

   An error naming `orchestrator.db.pre-v*`, or no lines, means Kraft made no
   copy.
2. Pick the newest line that starts with the schema you are going back to, such
   as `44`.
3. Restore that file as in [Restore a backup](#restore-a-backup), with `backup`
   set to its path.

For 1.4's database, a 1.5.0 release candidate before 1.5.0rc12 made no copy, so only your own backup rolls back: see
[Roll back to 1.4](/guides/run/coming-from-1-4#roll-back-to-14).

### The copy an update makes

_Added in next_

`kraft admin update` also copies the configuration and every database in `run/`
before it installs a release. It prints where:

```text
kraft: backed up the configuration and databases to /home/you/.kraft/run/update-snapshot-20261113-114345
```

The folder holds `config/`, a copy of the configuration directory, `db/`, one
file per database, and `version`, the Kraft release that wrote them: the
running server's, or the installed one's when no server answers. The
copies are consistent while the server runs. If Kraft can't make them, it
installs nothing and says why.

An update that Kraft installs [when it is free](/guides/run/upgrade-kraft#update-when-kraft-is-free)
makes the same copy before it restarts.

Kraft keeps the copy of the last update that went through until the next one
does, and deletes older ones then. An update that fails, or installs nothing,
leaves the earlier copy in place, and so does one run while another update is
still being confirmed.

The first upgrade onto the release that added this makes no copy, because the
`kraft admin update` that runs is the previous release's. Back up by hand for
that one, as [Back up the database](#back-up-the-database) says.

To go back to the version before the update:

1. Pin the release that `version` names, as
   [Pin a version](/guides/run/upgrade-kraft#pin-a-version) says.
2. Restore `db/orchestrator.db` with steps 1 to 3 of
   [Restore a backup](#restore-a-backup), with `backup` set to its path: stop
   the server, move the current database aside, then copy the backup in.
   `db/index.db` needs no restore: Kraft rebuilds the search index when its
   schema doesn't match.
3. If you want the configuration as it was too, replace the contents of your
   configuration directory with the files under `config/`, with the server
   still stopped.
4. Go on from step 5 of [Restore a backup](#restore-a-backup) to start Kraft
   and check it.

## Roll back to an earlier 2.x release

Pin the older release first, as [Pin a version](/guides/run/upgrade-kraft#pin-a-version) says. That isn't enough when the upgrade migrated the database. A migration is one way: an older release refuses a database a newer one migrated, and Kraft copied the database before it migrated it.

1. Stop the server: `kraft admin stop`, or as [Stop a service](/guides/run/run-as-a-service#stop-a-service) says when Kraft runs as a service. That removes the service: run `kraft admin install-service` once the older release runs, as the restore [above](#restore-a-backup) does.
2. Pin the earlier release.
3. Start it with `kraft admin start --detach`. If it starts, the upgrade changed no schema, so Kraft made no copy and the database needs no restore.
4. If it exits with `database schema vN is newer than code vM`, which `kraft admin start --detach` prints and `run/logs/server.log` records, the earlier release runs schema `M`, and going back loses everything done since the upgrade. Restore the newest of Kraft's copies whose own schema is `M`: [Find the copy to restore](#find-the-copy-to-restore) shows how to read it, and [Restore a backup](#restore-a-backup) puts it in place, with `backup` set to that copy's path.
5. If no copy holds schema `M`, check the backup you took before the upgrade, the file its step 1 printed. Set `backup` to it; the command prints its schema:

   ```bash
   backup="$HOME/kraft-backup-20261002-093015.db"
   sqlite3 -readonly "$backup" 'PRAGMA user_version'
   ```

   If it is `M`, restore it the same way. If it isn't `M` either, there is no way back to that release: pin the newer release again and stay on it.

To go back to 1.4 instead, see [Roll back to 1.4](/guides/run/coming-from-1-4#roll-back-to-14).
