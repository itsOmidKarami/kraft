title: Run a step on another machine

_Added in next_

A [work item](/concepts/vocabulary#work-item)'s steps run on the machine the Kraft server runs on. This guide moves one of them to another computer you already have: a build box, a GPU machine, a Linux host. The board, gates, repos and the item's branch stay where they are.

You need `kraft` on the other machine, the agent CLIs it should run installed and logged in there, and `git`. Kraft installs nothing and sends no credential.

## Register the machine

On the server's machine, add it. For one the server can reach over ssh:

```bash each
kraft admin worker add gpu-box --ssh gpu-box --capacity 2
```

It saves the machine, connects once and prints `connected`, or why not. For a machine that can reach the server but not the other way round, leave out `--ssh`. The command prints a token once and the command to run on the machine:

```bash each
kraft admin worker add home-server
```

Then run the printed `kraft admin worker serve --server URL --token TOKEN` on the machine. See [workers.yaml](/reference/configuration/workers) for the two ways to connect.

## Check the machine

On the machine itself:

```bash each
kraft admin worker check
```

It lists git, each agent CLI with its login and, for dial-in, whether the server answers with a valid token. It exits 1 on any failure. `kraft admin worker list` on the server shows whether the machine is online and why not.

## Put a node on it

In a chain file, add `runner:` to a node:

```yaml [config/chains/default.yaml]
nodes:
  - id: implementation
    runner: gpu-box
```

The value is a machine's name, `any` (the first connected machine that may work on every repo of the item and has a free slot, never the server) or `local`. A step's own `runner:` beats its node's, and a node's beats its chain's. See [Placing a step on a machine](/reference/configuration/library-and-chains#placing-a-step-on-a-machine).

## Place one item without editing a chain

```bash each
kraft item create "tidy the parser" --runner gpu-box
kraft item set-overrides --runner gpu-box
kraft item set-node-override --node verify --runner local
```

The first files an item whose steps all run on `gpu-box`. The second changes it for the whole item. The third overrides one node and wins over both. A change takes effect at the next step launch, even on a node that has started. Kraft refuses, with a 422, a machine that is not in `workers.yaml` or not allowed for the repo, and an item that is in place, sandboxed or has workspace members, submodules or Git LFS.

## Read a waiting item

An item whose machine is offline or full shows `waiting for gpu-box`. It holds no slot on the server and its time cap does not run. It starts when the machine is back or a slot frees. Kraft never runs the step on the server instead. See [Waiting for a machine](/troubleshooting/why-did-my-item-stop#waiting-for-a-machine).

## What comes back

The log streams to the server as the step writes it, so `kraft view logs -f` works as for a local step, and pause and cancel reach the machine.

After the step, its new commits, `result.json`, `summary.md` and changed documents are taken in before the server looks at the step. The next step, or a gate, sees them wherever it runs. If the branch moved meanwhile, the commits are kept at `refs/kraft/unsynced/...` and the item records `sandbox_branch_not_synced`. See [If something goes wrong](/reference/configuration/workers#if-something-goes-wrong).
