description: What a rollback does to the database and the config directory, and the steps that take an upgraded install from 2.0 back to 1.4.
---

Go back from 2.0 to 1.4 when an upgrade went wrong. A rollback needs the database as 1.4 left it, so take a backup before you upgrade.

## What a rollback does to `$KRAFT_HOME`

Starting a newer Kraft migrates `run/orchestrator.db` forward in place, and
there is no downgrade migration. An older Kraft refuses to start on a database a
newer one migrated (`database schema vN is newer than code vM`, in
`run/logs/server.log`).

So [back up `run/orchestrator.db`](/guides/run/back-up-and-restore#back-up-the-database)
before you upgrade, and restore that backup when you roll back. If you have
none, restore the copy Kraft made before migrating: see
[Find the copy to restore](/guides/run/back-up-and-restore#find-the-copy-to-restore).
`run/index.db` needs nothing: an older Kraft rebuilds a search index it cannot
read.

A rollback does not undo what a newer version changed in the config directory.
What 2.0 moved, you move back by hand (the steps below), and
`kraft admin templates lint` after a rollback checks the older version still
accepts the chains.

If you install an older version while the newer server still runs, the web UI
says **An older Kraft is installed** and points here, rather than telling you to
restart.

## Roll back from 2.0 to 1.4

1. Stop Kraft with `kraft admin stop`. If Kraft runs as a service, stop it as
   [Stop a service](/guides/run/run-as-a-service#stop-a-service) says instead:
   the service manager starts a stopped server again, and the next steps must not
   run under a live one.
2. Install 1.4 with the Python you run Kraft on and the extra you have:

   ```bash
   uv tool install --force --python 3.X "kraft-sdlc[vector]==1.4.0"
   ```

   Leave out `[vector]` if you don't use vector search.
3. Restore the database, using your backup or the copy Kraft made when you
   first left 1.4. Follow steps 2 and 3 of
   [Restore a backup](/guides/run/back-up-and-restore#restore-a-backup): Kraft is
   already stopped, and you start it in step 9 here. To find Kraft's copy, see
   [Find the copy to restore](/guides/run/back-up-and-restore#find-the-copy-to-restore):
   it is the newest one that prints 44, and none does when you upgraded to a
   candidate before rc12, which made none, so only a backup you took yourself
   rolls back then.
4. Check the config directory. 1.4 reads `~/.kraft/templates` (under
   `$KRAFT_HOME` if you set one). 2.0's first start renamed it to `config` and
   left `templates` as a link to it, which 1.4 follows, so there is nothing to do
   while that link is there. Otherwise:
   - If the link is gone, rename the directory back,
     `mv ~/.kraft/config ~/.kraft/templates`. When 1.4 finds no `templates/` it
     seeds a fresh default home beside yours, with no repos, a default policy and
     no `access.yaml`.
   - If `templates` is a directory, not a link, 2.0 found a `config/` you had made
     and could not merge the two (`kraft admin doctor`'s `config` row named both).
     Move what `templates/` still holds into `config/`, keeping the copy you want
     of each, then `rm -r ~/.kraft/templates && ln -s config ~/.kraft/templates`.
   - A directory you point `KRAFT_CONFIG_DIR` at was never renamed: point 1.4's
     `KRAFT_TEMPLATES_DIR` at it instead.
5. Move the schedules back. 1.4 reads them as `triggers:` in `policy.yaml`, not
   `schedules:` in `intake.yaml`. The entries have the same shape, so cut the
   list from `intake.yaml` and paste it under a `triggers:` key in `policy.yaml`.
   - Add the key yourself: 2.0 removed it once every trigger had moved, and the
     `# triggers:` in a seeded file is a commented example, so pasting under that
     line breaks the file (1.4 then refuses every new item). If some triggers
     stayed in `policy.yaml`, paste under the key that is there.
   - 1.4 reads a `cron` field only as `*` or a comma list of numbers. Before you
     paste, write a range or a step as that list (`1-5` as `1,2,3,4,5`, `*/15` as
     `0,15,30,45`), or 1.4 refuses the whole `policy.yaml` and then every new
     item. Write a day of week `7` as `0`, or 1.4 loads it and never fires it.
   - Delete the `schedules:` key itself from `intake.yaml`, even an empty
     `schedules: []`: 1.4 refuses an `intake.yaml` that has one, and its
     auto-intake then stays off while `kraft admin health` says ok.
   - Delete `forge_poll_s` from `policy.yaml` too, if you set it: 1.4 rejects the
     file and then refuses every new item (`policy config invalid, refusing work`).
     `max_concurrent` in `policy.yaml` needs nothing: 1.4 reads it there.
6. Rename the chain key in `repos.yaml`. 1.4 reads a repo's chain only as
   `default_chain_template`. It skips `default_chain`, so the repo files on
   `default` and doctor's `keys` row fails. Rename each `default_chain:` to
   `default_chain_template:`. Where an entry has both keys (2.0 can save the new
   one beside the old), put `default_chain`'s value, the one 2.0 used, in
   `default_chain_template`, then delete the `default_chain` line, so no entry
   ends with both.
7. Rewrite the profiles in `harnesses.yaml`. A profile saved on 2.0's
   Settings › Harnesses is written as `providers:`, which 1.4 refuses, and with
   it the whole file. Rewrite each such profile in 1.4's shape, one `model:` map
   by provider and one `effort:` for all of them:

   ```yaml
   # 2.0
   strong:
     providers:
       claude: { model: sonnet, effort: high }
       codex: { model: gpt-5.6-terra, effort: high }
   # 1.4
   strong:
     model: { claude: sonnet, codex: gpt-5.6-terra }
     effort: high
   ```

   1.4 has one `effort` per profile: where the providers set different ones, pick
   one. A profile already in the `model:` shape needs nothing.
8. Restore the theme. Copy `~/.kraft/templates/theme.yaml.pre-2.0` over
   `~/.kraft/templates/theme.yaml` (under `$KRAFT_HOME` if you set one), or the
   candidate's copy named in [Your theme](/guides/run/upgrade-from-1-4#your-theme) if a 1.5.0 release
   candidate converted it first. 1.4's interface takes its colors from `palette`,
   which 2.0 removed, so without the copy it shows its default colors.
   - The copy is your theme from the first upgrade past 1.4, and is never
     replaced: if you rolled back before and changed the theme on 1.4, set it
     again in 1.4's Settings.
   - With no copy, check `theme.yaml` for `group_by: chain`, which 2.0 writes when
     the board is grouped by chain, and change it to `group_by: template`. Also
     look for an `editor:` line, which 2.0 writes when you pick a Default editor
     in Settings › Appearance, and delete it. Or delete the file. 1.4 refuses
     both, and its board then loads no theme.
9. Start Kraft with `kraft admin start --detach`, or `kraft admin install-service`
   if it ran as a service, then check it:

   ```bash
   kraft --version
   kraft admin templates lint
   kraft admin doctor
   ```

   You know it worked when `--version` prints `kraft 1.4.0`, the board loads,
   `templates lint` exits 0, and `doctor` shows no failing `templates` row (1.4's
   name for the config directory row) or `keys` row.

### What the restore leaves behind

Restoring the backup loses everything done on 2.0 since you took it: items filed,
runs, approvals and their history. It does not remove what those runs made
outside the database. Their worktrees under `run/worktrees/`, their branches, and
any merge requests they opened are still there, and 1.4 knows nothing about them.

- `kraft admin doctor`'s `worktrees` row lists a worktree with no work item.
  Delete the ones you do not need, and close any merge request yourself. 1.4's
  row also lists the worktrees of items you cancelled on 1.4, which its board does
  not show.
- A worktree made on 2.0 is one whose id is not in the database you restored:
  `sqlite3 run/orchestrator.db "select id from work_items"` lists those.
