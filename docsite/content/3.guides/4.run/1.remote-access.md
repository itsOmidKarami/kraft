Reach the Kraft board from a phone or another machine by binding it off
loopback and turning on password auth. You get the real board, with the same
auth, at an address you choose.

## Before you start

- A password. Kraft refuses any bind off loopback until one is set.
- The hostname or address you will type in the other device's browser. It goes
  in `allowed_hosts`.
- A non-loopback bind: [choose one](#choose-a-bind) first.
- The port. It is 8765 unless you set `port` in `access.yaml` or pass `--port`.
  Use your port wherever this page says 8765.
- `access.yaml`, which lives in `$KRAFT_HOME/config/` (by default
  `~/.kraft/config/`).

## Choose a bind

Kraft binds `127.0.0.1` by default and skips auth for local clients. Any other
bind makes Kraft require the password from every client, local ones included,
and check browser Host headers against `allowed_hosts`.

Pick the narrowest bind that works:

- **Tailscale (recommended).** Bind the machine's Tailscale address. Only
  devices on your tailnet can reach the board, and your LAN cannot. See
  [Over Tailscale](#over-tailscale).
- **Local network.** Bind `0.0.0.0`, which listens on every network this
  machine is on. Use it only on a network you trust. See
  [On your local network](#on-your-local-network).
- **Cloudflare Quick Tunnel.** Put the board on the public internet. Use it
  only if you cannot use Tailscale. See
  [Over a Cloudflare Quick Tunnel](#over-a-cloudflare-quick-tunnel).

## Set a password

Kraft refuses any bind off loopback until a password is set, both at
`kraft admin start` and on the Settings › Access screen. On `127.0.0.1` the
screen lists the password under **Not used on 127.0.0.1**, and picking
**Local network** asks for one: **Set and switch** saves the password and the
`0.0.0.0` bind in one step (on a phone, a **Set a password** sheet does the
same).

Once the bind is off loopback, every browser signs in, including one on the
machine itself. Kraft stores only the password's hash, in `access.yaml`. The
Access screen's **Password** card changes it once Kraft is off loopback.

To set a password and leave the bind alone, send it by itself while Kraft is
still on `127.0.0.1`, with your password in place of `...`:

```bash
curl -X PUT http://127.0.0.1:8765/api/access \
  -H 'Content-Type: application/json' -d '{"password": "..."}'
```

## On your local network

1. Open Settings › Access and choose **Local network** (`0.0.0.0`). The screen
   asks for what is missing: a password if none is set yet, and the name or
   address your phone will type, filled in with this machine's LAN address
   (`192.168.1.20`).
2. Click **Set and switch**. The bind, the password and the host are saved at
   once, and the bind waits for a restart. The **Allowed hosts**, **Password**
   and **Sessions** cards appear.
3. Under **Allowed hosts**, add any other name or address you will type in the
   phone's browser. The list is for the names other devices use: on the machine
   itself the board keeps working at `http://127.0.0.1:8765`, behind the same
   sign-in. An empty list refuses every other device's browser, and the card
   then offers this machine's address.
4. [Restart Kraft](#restart-kraft) so it binds the new address.
5. From the phone, open `http://192.168.1.20:8765/` and log in. The traffic is
   plain HTTP, so anyone on the network can read it.

## Over Tailscale

The Access screen offers only `127.0.0.1` and `0.0.0.0`, so set a Tailscale
bind in `access.yaml` by hand. Start Tailscale before Kraft: the Tailscale
address does not exist until Tailscale is up, and the bind fails without it.

Keep to this order, and mind two things on the way:

- **Stay off the Access screen between steps 3 and 4.** A save there rewrites
  `access.yaml` from what the running server holds, which reverts a hand-edited
  `bind` and `allowed_hosts`.
- **Pause any active item before step 3.** From then until the restart the
  `kraft` CLI dials the new address, where nothing listens yet, so
  `kraft admin restart` cannot list the agents it is about to end.

1. Set a password with the `curl` command in [Set a password](#set-a-password).
   It leaves the bind on `127.0.0.1`. Picking **Local network** on the Access
   screen would also set one, but it writes `bind: 0.0.0.0` with it.
2. Find the machine's Tailscale address and name:

   ```bash
   tailscale ip -4        # e.g. 100.101.102.103
   tailscale status       # the first line names this machine
   ```

3. In `access.yaml`, set `bind` to that address and add the machine's tailnet
   name to `allowed_hosts`:

   ```yaml [config/access.yaml]
   bind: 100.101.102.103
   allowed_hosts:
     - mybox.tailnet-name.ts.net
   ```

   Setting `bind` in the file, rather than passing `--host`, keeps the `kraft`
   CLI in your other shells pointed at the same address, and keeps the bind
   across a restart. Run `kraft admin doctor` and read its `access.yaml` row to
   confirm the file parses. Its `server` row fails until the restart.
4. [Restart Kraft](#restart-kraft) so it reads the new bind.
5. From a device on your tailnet, open `http://mybox.tailnet-name.ts.net:8765/`.
   Tailscale encrypts the traffic between your devices.

After the restart the Access screen shows **Local network** as chosen, since the
bind is off loopback. Do not click it: that writes `0.0.0.0` over your Tailscale
address.

## Over a Cloudflare Quick Tunnel

::warning
A Quick Tunnel puts the board on the public internet. Anyone who finds the
`*.trycloudflare.com` URL reaches the login page, and the password is the
barrier.

Kraft locks an address out for 15 minutes after 5 failed logins, but
if the tunnel does not pass on the visitor's address, every visitor counts as
one address and a stranger's guesses can lock you out too. See
[Login](/project/security#login).

Open only the tunnel's `https://` URL, so the
session cookie is marked `Secure`. The tunnel also needs a `0.0.0.0` bind,
which listens on every interface, your LAN included. If your LAN is
untrusted, block the port at your firewall for other interfaces.
::

1. Run `cloudflared tunnel --url http://localhost:8765`. It prints a
   `*.trycloudflare.com` URL. The URL changes every time `cloudflared` starts:
   after the first time, add each new hostname under **Allowed hosts**, where it
   applies at once, with no restart.
2. On the Access screen, choose **Local network**, setting the password if it
   asks. The phone's host field is pre-filled with the machine's LAN address:
   replace it with the tunnel's hostname. Or, with a password already set, write
   `bind: 0.0.0.0` and the hostname under `allowed_hosts` in `access.yaml`.
3. [Restart Kraft](#restart-kraft) so it binds the new address.

Keep the bind in `access.yaml`, not in `kraft admin start --host 0.0.0.0`.
`kraft admin restart` starts the server from `access.yaml` alone, so a bind you
passed with `--host` is gone after a restart. The tunnel then reaches a server
on `127.0.0.1`, which skips auth for local clients. Only the hostname check
stands between it and the internet: Kraft refuses a request addressed to any name
but `127.0.0.1`, `localhost` or `[::1]`.

## Restart Kraft

Kraft binds a new address only after a restart. Pick the way that matches how it
runs:

- When Kraft runs as a service, the Access screen offers **Restart Kraft**.
- Otherwise run `kraft admin restart`, which reads the new bind from
  `access.yaml`.
- A server running in a terminal only stops, so start it again there with
  `kraft`.

A restart ends the agent of every active item, and each stops as failed until
you retry it. The dialog says how many are active. Pause them first to avoid
that: see [A restart ends running agents](/guides/run/restart-kraft#a-restart-ends-running-agents).

## Check it worked

1. From the phone or other machine, request the health endpoint, which needs no
   login:

   ```bash
   curl -s https://<your-tunnel-hostname>/api/health
   ```

   Over Tailscale, use `http://mybox.tailnet-name.ts.net:8765/api/health`. A JSON
   status confirms the request reaches Kraft.
2. Open the same address without `/api/health` in a browser. You should see the
   login page. Log in with your password.
3. On a computer, the sidebar reads **live** next to **Kraft** once the board's
   event connection is open, and the board updates without a reload. If it stays
   on **reconnecting…**, check that anything between the browser and Kraft, such
   as a reverse proxy, passes WebSocket connections through and keeps the `Host`
   header the browser sent.

### The browser says Kraft does not answer to the name you opened

The hostname is missing from `allowed_hosts`. The page names it.

- The list is held to browsers only: `curl`, the `kraft` CLI and MCP are not
  checked against it.
- Add the name in `access.yaml` and restart, or on the Access screen from an
  address already on the list, where it applies at once.
- Enter the name alone, as `mybox.tailnet-name.ts.net`. Kraft drops a port or an
  `http://` you type with it, and refuses a wildcard.

## A proxy in front of a loopback bind

A tunnel or reverse proxy on this machine that passes on the name its clients
used gets a 403 for every request. On a loopback bind (`127.0.0.1`, the
default), Kraft answers only a request addressed to `localhost`, `127.0.0.1` or
`[::1]`. Any other `Host` gets a 403, `unexpected Host for a server bound to
127.0.0.1`, scripts and webhooks included, and `allowed_hosts` is not read.
[Who may call](/reference/http-api#who-may-call) has the rule. Coming from 1.4,
see [Network access](/guides/run/upgrade-from-1-4#network-access).

Choose the fix by what has to reach Kraft:

- **The board:** bind Kraft beyond loopback, with a password, and list the name
  in `allowed_hosts`, as in the sections above. A loopback-bound Kraft behind a
  proxy serves webhooks and scripts only, never the board: a browser's sign-in,
  every change it makes on the board and the live-update socket carry the name
  it used as their `Origin`, and Kraft refuses those as cross-site.
- **Webhooks and scripts only:** have the proxy send `Host: localhost`, as
  below.

### Send `Host: localhost` from the proxy

| Proxy | Setting |
|---|---|
| cloudflared | `httpHostHeader: localhost` in the ingress rule's `originRequest`, or `--http-host-header localhost` on the command line |
| ngrok | `--host-header=rewrite` |
| Caddy | `header_up Host localhost` in the `reverse_proxy` block |
| nginx | `proxy_set_header Host localhost;` |

Before you rewrite `Host`, know what it does to sign-in. A loopback-bound Kraft
asks a request from this machine for no password, and a request through a proxy
on this machine is one, unless the proxy names its client in `X-Forwarded-For`.
So:

1. First set a password (`PUT /api/access` with `{"password": "..."}`).
2. Make sure the proxy sends that header: nginx does not unless you add
   `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`.

Kraft then asks every request through the proxy to sign in, or for the
[trigger token](/guides/customize/schedule-and-webhook-work#file-a-work-item-from-a-webhook)
on `POST /api/triggers`, and refuses them all while no password is set. Without
the header, everyone who reaches the proxy has the whole API, with no sign-in,
password or not.

Kraft takes the client from the last `X-Forwarded-For` address that is not
loopback (it reads the header only from `127.0.0.1` and `::1`). So a proxy that
is itself fed from loopback, such as an `ssh -R` endpoint or a second proxy on
this machine, passes every request on as local, and Kraft asks it for no
password even with one set. Put nothing like that in front of a loopback-bound
Kraft.
