The ops a draft takes in each area, and the ops of a [work item](/concepts/vocabulary#work-item)'s own draft; the routes that carry them are on [Drafts](/reference/http-api/drafts). Like those routes they can change in any release, and routes written here without the `/api` prefix are relative to it, as [the HTTP API overview](/reference/http-api#in-this-section) explains.

## Draft ops


An op edits the chain's model rather than its text, so it writes the whole
file back: the file's comments are dropped, and `warnings` says so until a
`PUT` of that file. A path is a component's canonical path
(`draft_merge_request.open.open`, `verification.fix_loop.judge`), and a
container is a node or one of its handlers (`spec`, `spec.on_failure`).

On the `library` draft, a path starts with the component's section:
`nodes.<name>[.<step>[.<task>]]`, `steps.<name>[.<task>]`, `tasks.<name>`,
`steering.<name>`. Every op below but `add_node`, `new_chain`, `delete_chain`,
`move_to_library` and a chain `rename` applies there, plus `add_component`.
`rename` of a component (`path: tasks.implementer`) also rewrites every
`extends:` or `steering:` entry naming it, in the library and in each chain
file, which joins the draft, and answers `{updated: [{file, path, field}]}`.
`remove` of one leaves its uses as problems and answers them as
`{broken: [{file, path, field}]}`.

| Op | Fields | Does |
|---|---|---|
| `add_node` | `at, id, kind` | Inserts an `exec` or `gate` node at position `at`. An exec node starts with no step, a problem until it has one. |
| `add_step` | `container, at, id?` | Inserts an empty step. The default id is `step_<n>`; a container holding only `main` renames it `step_1` first. |
| `add_task` | `container, step, kind \| extends, id?` | Appends a task of a `kind`, or one extending a library task. The default id is the kind or the library name, made unique with `_2`, `_3`…. |
| `add_task` | `slot, node, kind \| extends` | Fills a named slot: `judge` (the node needs a [fix loop](/concepts/vocabulary#fix-loop)), `escalation` or `auto_review`, with the id `judge`, `escalate` or `reviewer`. |
| `add_handler` | `path, kind` | Adds an `on_failure`, `fix_loop` or `on_conflict` handler holding one empty step `main`. |
| `remove_handler` | `path, kind` | Removes it: written `null` when the node's library base supplies one, deleted otherwise. |
| `move` | `path, to, to_step?` | Moves a node, a step, or a task (to `to_step` beside its own) to position `to`. |
| `remove` | `path` | Removes a node, gate, step, task, `fix_loop`, `judge`, `escalation` or `auto_review`. Answers `{broken: [{path, field}]}`, the `reject_to` and `restart_from` references left naming a removed node; they stay as problems. |
| `extend` | `node, base` | Makes the node extend library node `base`, dropping its own `kind`, steps, `on_failure` and `fix_loop`. Answers `{dropped}`. |
| `change_base` | `node, base` | Changes the base, keeping each override the new base can take. Answers `{kept, dropped: [{key, why}]}`; with `?preview=1`, what a change would drop. |
| `new_chain` | `from?` | Starts the key's chain, empty or as a copy of chain `from` under this id. Only for a key with no file and no draft. |
| `delete_chain` | none | Deletes the chain on publish. A repo whose default it is makes that a problem. |
| `set_field` | `path, field, value` | Sets one field (`path: ""` is the chain). See [The `set_field` op](#the-set_field-op). |
| `reset_field` | `path, field?` | Removes the key so the inherited or default value applies. With no `field`, removes every override of a component that extends a library one except `id`, `extends`, `icon` and `on_failure`. |
| `rename` | `path, id` | A node or gate also rewrites every `reject_to` and `on_base_changed.restart_from` naming it, and answers `{updated: [{path, field}]}`. See [The `rename` op](#the-rename-op). |
| `set_fragment` | `path, yaml` | Replaces the component at `path` with the YAML mapping, as the component's YAML tab writes it. |
| `move_to_library` | `path, name` | Moves the exec node or task at `path` into `library.yaml` as `nodes.<name>` or `tasks.<name>`, leaving `{id, extends: <name>}` in the chain. `library.yaml` joins the draft. A `name` its section already has is refused. Answers `{path}`, the component's. |
| `add_component` | `section, name, kind?` | Library only. Adds an empty component to `nodes` (an `exec` node with no step, or a `gate`), `steps`, `tasks` (of `kind`, when given) or `steering`, whose empty `instructions` are a problem until written. Answers `{path}`. |

An op that cannot apply (an id that is taken, reserved or malformed, a move that
puts a `reject_to` or `restart_from` target after the node naming it, or a gate
before the node producing its document, a task moved beside one of its name) answers `422`
`{detail, op}`, `op` being its index, and nothing is saved.

A fragment that
changes its component's id answers "rename it with rename"; one that does not
parse adds `line` and `col`, counted in the fragment. A draft with a
`yaml_error` answers `409` "fix the YAML first".

### The `set_field` op

- `field` is dotted: `policy.max_attempts`, `on_base_changed.restart_from`, `wait.polling.initial_interval`.
- `null` or `""` removes the key, and so does a value equal to the one the component inherits.
- Setting `profile` removes `model` and `effort`, and setting either removes `profile`.
- An empty `on_base_changed.restart_from` removes `on_base_changed` (written `null` when inherited), an empty `artifact` removes `artifact_required` with it, and `artifact_required: false` removes it.
- `icon` is set like any other field.
- `id` is refused: use `rename`.

### The `rename` op

- A step, task, judge, escalation or reviewer changes its id only.
- The chain (`path: ""`) moves to `chains/<id>.yaml`, its old file deleted on publish; a repo whose default is the old id makes that a problem.
- A gate's `artifact` names a document kind, not a node, so a rename never changes it.


## Harnesses ops

On the `harnesses` draft (`harnesses.yaml` and `policy.yaml`), each [harness](/concepts/vocabulary#harness) is
`available`, `override` or `never`. That is two `allowed_harnesses` lists in
`policy.yaml`:

- `available` is in `defaults` and `maxima`.
- `override` only in `maxima`.
- `never` in neither.

An absent list means no bound. A list is written
again only when one was there to begin with, or when it leaves a harness out.

A task that selects a `never` harness, or falls back to one, is a problem that
names it, so the draft cannot publish until the task or the state changes. An
`override` harness is allowed only for a task whose own `policy:` widens it.

| Op | Fields | Does |
|---|---|---|
| `set_access` | `harness, state` | Moves the harness to `available`, `override` or `never`. |
| `set_allowed_tools` | `tools` | `maxima.allowed_tools`, or removes it with `null`. |
| `set_escalation` | `harness, grants` | `defaults.escalation_harness` and `escalation_grants`; `null` removes each. |
| `set_harness` | `id, patch` | A harness's own fields in `harnesses.yaml`. See [The `set_harness` op](#the-set_harness-op). |
| `add_profile` | `name, copy_from?` | A new [agent profile](/concepts/vocabulary#agent-profile), empty or a copy of another. |
| `rename_profile` | `name, to` | Renames it and retargets the `fallback:` entries of `harnesses.yaml` that name it. A library or chain task that names it is left dangling, a problem, and answers `{broken: [{chain, path}]}`. |
| `remove_profile` | `name` | `422` while a task or another profile's `fallback:` names it. |
| `set_profile` | `name, patch` | `patch` may hold `providers` (per [provider](/concepts/vocabulary#provider) `{model, effort?}`, `null` removes one, and an older profile becomes this shape), or `model` and `effort` for an older profile, and `fallback` (replaces the list, or `null`). Both shapes in one patch is `422`. |

### The `set_harness` op

- `patch` may hold `enabled` (a boolean), `executable` (`null` clears it) and `defaults`, which merges per option (`null` or an empty text removes one).
- An option the provider does not accept is a problem, not a refusal.
- Any other key is `422`.

### The `resolved` answer for harnesses

The answer's `resolved` lists:

- `harnesses` (`id`, `state`, `executable_found`,
and from `harnesses.yaml` its `provider`, `enabled`, `executable` and
`defaults`, plus `tasks`: the agent tasks that select it, `{chain, path,
profile, fallback: false}`, and those whose `fallback:` list lands on it, with `fallback: true`).
- `allowed_tools`.
- `escalation` (what the file says).
- `escalation_effective` (`{harness, set}`: the harness a launch uses, `claude`
when the key is unset).
- `profiles` (their providers and the tasks that use
  them).

`impact` counts the tasks whose harness changed state.

A problem about a
task of a chain carries that task's `path` where the message names one, and
escalation running on a `never` harness is a problem at
`defaults.escalation_harness` in `policy.yaml`.

## Repos ops

On the `repos` draft (`repos.yaml`). `PATCH /repos` is unchanged. `DELETE /repos?path=` answers `409`, naming the count, while any work item that has not ended (any status but completed or abandoned) uses the repo, as `remove_repo` reports it as a problem.

| Op | Fields | Does |
|---|---|---|
| `add_repo` | `path, fields?` | A new entry, disabled and managed, with `fields` on top. The path is not probed; a path that is not a git repository is a problem. |
| `set_repo` | `path, patch` | Any entry field; `null` clears it. Like `PATCH /repos`, it marks the entry managed. |
| `remove_repo` | `path` | Drops the entry. A problem while the repo has items that have not ended. |
| `connect_detected` | `path` | A detected (`managed: false`) entry becomes `managed: true`. |

The answer's `resolved` has `repos` and `detected`. Each carries `resolved` and
`sources` for `steering`, `deny_tools`, `models` and each `policy` key. `steering`
is `repo` or `library` (the chains' steering), the rest are `repo` or `default`.
Problems name the repo: a `policy:` that relaxes the instance's safety layer
(the same refusal a run gives), a path that is not a git repository, and a
`default_chain` that is no chain. `impact.running` is the count of
items not ended, per repo path.

## Policy ops

On the `policy` draft (`policy.yaml`). `PUT /policy` is unchanged.


| Op | Fields | Does |
|---|---|---|
| `set_value` | `scope, key, value` | One setting, by dotted `key`. See [The `set_value` op](#the-set_value-op). |
| `set_loop` | `key, max_attempts?, wall_clock_s?` | The `loops:` entry for a loop (`<node id>.fix_loop`), starting from `default:`. A key naming no loop is kept and shown as a problem. |
| `remove_loop` | `key` | Drops the entry. `422` when it is not there. |

`GET /api/policy` also answers `active_count` (items running now), and its
`max_concurrent` is the value the loaded policy runs under. A body sent back
to `PUT /api/policy` may keep `active_count`; it is ignored.

### The `set_value` op


Each `key` is its dotted path in `policy.yaml`, by `scope`:

| `scope` | Keys |
|---|---|
| `limits` | `budget.work_item_usd`, `budget.daily_usd`, `defaults\|maxima.max_attempts`, `defaults\|maxima.timeout_minutes` and `defaults\|maxima.<level>.<cap>`. |
| `escalation`, `retries` | Their named keys. |
| `loops` | `default.attempts` and `default.wall_clock_s` (the `default:` block). |
| `housekeeping` | `max_concurrent` and `archive.after_days`. |
| `findings` | `findings.loop_severities` (a list of `critical`, `important`, `minor`). |

`null` removes it and any section it leaves empty. Any other key, and the `harnesses` scope, is `422`.

### The `resolved` answer

The answer's `resolved` has `limits`, `loops`, `escalation`, `retries`,
`housekeeping` (`max_concurrent`, `archive_after_days`), `findings`
(`loop_severities`), `harnesses` (read-only) and `other` (read-only). Each value is
`{value, source}`: `policy` or `default`; a cap's `source` is the level
(`work_item`, `nodes`, `steps`, `tasks`) that sets it, and an unset maximum is
`{value: null, source: null}`.

Each cap also has `below`: every scope of the
published library's chains that sets that cap itself, `{layer, chain, path, via,
value, exceeds}`:

- `layer` is `chain` (the chain file) or `library` (a
  component it extends, named in `via`).
- `path` is the scope's canonical path (the
  chain's id for the chain itself).
- `exceeds` is whether `value` is past the
  draft's maximum at that level.

`below` is `[]` when nothing sets it.

`limits.work_item_usd` also has `binding`, the
lower of the dollar caps (`budget.work_item_usd`, `maxima.work_item.budget_usd`,
`defaults.work_item.budget_usd`) and the key that sets it.

`loops.live` lists every
fix loop in the library with its `attempts` and `wall_clock_s` and the layer that
wins (`loop`, `node`, `chain`, `defaults` or `maxima`, `loops`, `default`; a wall
clock has no `loop` layer). A work item's own override is not in it.

Problems
carry `scope` (the group) and, for a cap, `level`; a `loops:` key naming no
loop in the library, and a limit a chain already exceeds (naming the `chain`),
are problems.



## Intake ops

On the `intake` draft (`intake.yaml`, its `schedules:` included).
`GET /api/intake` and `PUT /api/intake` are unchanged.

| Op | Fields | Does |
|---|---|---|
| `set_intake` | `patch` | Any of `enabled`, `interval_s` (at least 30), `priority_ceiling` (0 to 4) and `repos`, written to `intake.yaml`, which gets its defaults for any key it did not have. Any other key is `422`; `max_concurrent` is the `policy` draft's. |
| `add_schedule` | `cron, repo, chain, title, description?` | Appends a `schedules:` entry. |
| `set_schedule` | `index, patch` | Changes fields of the entry at `index`. `422` for an index that is not there or a key that is no schedule field. |
| `remove_schedule` | `index` | Drops the entry. |

The answer's `resolved` is `{enabled, interval_s, priority_ceiling, repos, schedules}`,
each schedule `{index, cron, repo, chain, title, description}`. A schedule whose `repo` is not
connected or whose `chain` is not in the library is a problem carrying its `schedule` index. A
publish applies without a restart: the poller is replaced, and the new interval and
schedules are live.

`GET /api/intake/checks?limit=` answers what each recent poll found, newest first:
`[{id, at, ready, started, skipped}]`. `limit` defaults to 20 and is at most 100;
the newest 500 polls are kept.

`ready` is how many beads were ready, `started` the
work item ids it filed, and `skipped` the beads it left alone, each
`{bead, reason}` (`bead` is `null` for the single `invalid_config` entry of a
poll that could not read its configuration) with `reason` one of `above_priority_ceiling`, `already_item`, `epic`,
`max_concurrent`, `daily_budget` or `invalid_config`. A check is not a work item event.

## Item drafts

A work item's own chain has one draft too: a list of ops a person has not
applied yet, kept until it is applied or discarded. A worker cannot read or
change its own item's draft (`403`), and an ended item's answers `409`.

| Route | Answers |
|---|---|
| `GET /api/work-items/{id}/draft` | `{ops, problems, checks, nodes, base_seq, updated_at}`. With no draft, `ops` is `[]` and `nodes` is the item's chain. |
| `PUT /api/work-items/{id}/draft` | Body `{ops: [{op, ...}]}`. Replaces the whole list and answers as `GET /api/work-items/{id}/draft` does. An empty list deletes the draft. A malformed op answers `422`. |
| `DELETE /api/work-items/{id}/draft` | Discards the draft: `204`, or `404` with no draft. |
| `POST /api/work-items/{id}/draft/apply` | No body. Applies every op at once, in one transaction, and answers as `GET /api/work-items/{id}/draft` does with the draft gone. |

| Op | Fields | Does |
|---|---|---|
| `override` | `path, task_config?, policy?` | Sets what a retry's override may set at that path, within the same bounds: no structural field, policy only tightened or kept under the maxima, a harness inside `allowed_harnesses`. |
| `add_node` | `after, node` | Adds a node built from library components only, as a chain revision adds one: `node` is `{id, extends}`, or `{id, tasks}` or `{id, steps}` of library tasks. |
| `remove_node` | `node` | Takes the node out of the chain. A gate, a node that is not skippable, or a node that lands the merge request cannot be removed. |
| `skip` | `path` | Skips a step or a task: applying records it as `scope_skipped`, so the [walk](/concepts/vocabulary#walk) passes it. |

In the answer, each op carries `passed`: `true` once the item has reached the
node it acts on (for `add_node`, gone past the node it follows). A passed op is
not applied, and `nodes` (the chain in the `chain_definition` node shape) has
every other op applied.

`problems` is `[{op, message}]`, `op` being the op's
index.

`checks` is `{budget, added}`:

- `budget` is `{spent_usd, cap_usd}`, the item's
spend against its cap, as `budget_cap` on `GET /api/work-items/{id}` reports it.
- `added` has one `{op, node, harnesses, estimate_usd, estimate_runs}` for each `add_node` that is
not passed and has no problem:
  - `harnesses` are the harnesses its agent tasks run
on (one outside the policy's `allowed_harnesses` is a problem on that op, so these
are allowed).
  - `estimate_usd` is what a node of that id has cost per item, averaged over `estimate_runs` items of the
instance; both are `null` when none has run.

The estimate is information and blocks nothing. An `override` outside its
policy maximum is a `problems` entry on its op whose message starts with the field.

An apply re-reads the item inside its transaction. If any op is passed by
then, it answers `409` and writes nothing:

```json
{"detail": "the item has moved past some of this draft's ops; remove them or move them after the current node",
 "passed": [0]}
```

Any problem answers `422` `{detail, problems}`. Otherwise the revised chain
replaces the item's, recorded as `chain_revised` with `source: "draft"`, each
`skip` is recorded, and the draft is deleted. On a running item it takes effect
at the next node boundary; the node running finishes as it started. Nothing is
moved for you: drop a passed op from the list, or change it to act after the
current node.
