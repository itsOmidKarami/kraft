The board's routes for a [work item](/concepts/vocabulary#work-item)'s budget, the dry run of a create, its events and its run summary; like the other board routes they can change in any release, as [Work items](/reference/http-api/work-items) says. Routes written here without the `/api` prefix are relative to it, as [the HTTP API overview](/reference/http-api#in-this-section) explains.

## Daily total and dry run

### Daily total

`GET /budget/today` answers the instance's spend since local midnight against
`policy.budget.daily_usd`:

```json
{"spent_usd": 3.4, "cap_usd": 20.0}
```

`cap_usd` is `null` when `policy.budget.daily_usd` is unset. `GET
/work-items/{id}`'s `budget_cap` gains the same two numbers under `daily`
(`{spent_usd, cap_usd}`). Its `spent_usd` is unchanged: the item's own,
all-time spend.

`budget_cap.cap_usd` is whichever cap stops the item first: the lower of its own cap and the item-wide `budget_usd` of its policy. This holds in the API and in `kraft view show --json`.

- `key` says which cap it is, and the `PATCH` field that changes it: `budget_usd` for the item's own cap, `policy.budget_usd` for the policy one.
- `source` is `item` when the item itself set the reported cap, by its own `budget_usd` or by its own `policy` override, and `policy` when it comes from `policy.yaml` or the chain.
- So `source: item` with `key: policy.budget_usd` means the item's policy override.

Before 2.0, `cap_usd` was always the item's own cap (its `budget_usd`, else `budget.work_item_usd`), and `source` said which of those two set it.

`POST /work-items/{id}/budget/raise` (`kraft item raise-budget`) raises
whichever of the two stopped the item.

Beside the dollars, `running_time` is the item's time budget:
`{running_s, cap_minutes}`. `running_s` is what its item-wide
`time_cap_minutes` measures, the seconds any of its sessions ran since the
last `/retry` a person made, and `cap_minutes` is that cap, `null` when it has
none. It is `null` for an item with no frozen chain.

### Dry run

`POST /work-items?dry_run=1` runs every check `POST /work-items` runs, up to
and including validating `node_overrides`, then answers `200` without filing
anything: no row, no bead, no attachment copy, no spawn. A body that would
answer `422` or `503` on an ordinary create answers the same on a dry run.

```json
{
  "dry_run": true,
  "nodes": [...],
  "skipped": [{"node": "spec", "why": "covered_by", "kind": "spec"}, {"node": "...", "why": "skip"}],
  "gates": ["spec_approval", "..."],
  "caps": {
    "budget_usd": 5.0,
    "budget_source": "item",
    "daily_usd": 20.0,
    "nodes": {"implement": {"attempts": 3, "wall_clock_s": 7200}}
  }
}
```

- `nodes` is the chain that would be filed, in `chain_definition`'s own node
  shape.
- `skipped` lists every node the attachments or `skip_nodes` dropped:
`covered_by` names the attachment kind that made it redundant, `skip` is an
  operator's own choice.
- `gates` is the ids of the gate nodes left in the chain.
- `caps.budget_usd`/`budget_source` mirror the create route's own cap
resolution (`"item"` for the body's own `budget_usd`, else `"policy"`).
- `caps.nodes` is each fix-loop node's `attempts`/`wall_clock_s`, resolved the
same way the [walk](/concepts/vocabulary#walk) resolves them at run time: the node's own `policy`,
`node_overrides` entry and any item-wide override each layered on in the same
order, so a node's own override and an item-wide value each show where they
apply.

## Events paging and the run summary

### Events paging

`GET /work-items/{id}/events` normally returns every event after `after_seq`
(`0` by default). `before_seq` pages backward instead: it returns the last
`limit` events with `seq < before_seq`, oldest first, in the same row shape --
100 when `before_seq` is given with no `limit`. `limit` alone bounds
`after_seq`'s own forward window to the first `limit` events after it (1-500;
outside that range, or passing both cursors at once, answers `422`). Every
event row carries a `node_id` (see [Events](/reference/events)).

### The run summary

`GET /api/work-items/{id}` adds `summary`, a run's progress at a glance:

```json
{"nodes_done": 3, "nodes_total": 8, "gates_passed": 1, "step": {"index": 2, "count": 2} | null}
```

`nodes_done`/`nodes_total` count against the frozen chain; `gates_passed` is
how many of the completed nodes were gates. `step` is the current node's step
(1-based) out of its own steps, read from its latest non-escalation session's
task, when the node declares more than one, and `null` otherwise.

`GET /api/work-items` rows carry two more fields the detail already has or
derives, so the board can draw "2 of 3 · review › code_review" and "merged !139"
without a request per row. `mr_ref` is `{number, url}` or `null`, the same
value as the detail's. `step` is `{index, count, name, task}` or `null`:
`index` and `count` as in `summary.step`, `name` the step's id and `task` the
latest non-escalation session's task id within it.

### Worktree, plan and scope runs

`GET /api/work-items/{id}` carries `worktree_exists`: whether `worktree_path` is a
directory on disk. It is `false` before the item first runs and after its
[worktree](/concepts/vocabulary#worktree) was reclaimed or deleted.

The routes that need the directory
(`diff`, `compare`, `open-worktree`, `mr-labels`) answer 404 in that case, with
"this work item has not started, so it has no worktree yet" for an item that
never ran and "this work item's worktree was removed from disk" for one that
did. A retry or resume recreates the directory.

The detail also carries what a node's view draws its plan and its scopes from:

- `progress` is `{current, total, title, tasks}` or `null` when the item has no
  plan to follow. Each task is `{n, title, state, sha}`: `state` is `done`,
  `current` or `pending`, and `sha` is the short hash of the newest commit on
  the item's branch that names the task, or `null`. Board rows carry only
  `current`, `total` and `title`.
- `worker_sessions[].repository` is the workspace member a session ran in, or
  `null` for the item's own repository.
- `scope_runs` lists every command a changed-test-scope task ran in its node's current pass, in the order each started, across rounds and repositories:
  `{session_id, repository, round, command, passed, exit_code?, scope?, area?,
  setup?, order?, selected?, pending?, node_id, hook_point}`.
  - `passed` is `null` until the command finishes.
  - A command its round picked that has not
    started yet comes last, `pending: true` with no `session_id`, while the node
    is still running.
  - `round` is the session's fix-loop round, `0` for the first
    pass; `-1` is the repair an `on_failure` recovery runs inside a fix-loop
    node, and the re-measure after it.
  - A retry starts a new pass, so the list
    keeps only the newest one.
  - It is empty for a chain with no such task.

### Diff, compare, fix target and review digest

`GET /api/work-items/{id}/diff` and `GET /api/work-items/{id}/compare` take an
optional `ignore_whitespace=true`, like `git diff -w`. A file whose only change
is whitespace then drops out of `files`, the per-file counts and `diff` together,
so the three never disagree; `touched_by` and `untracked` do not follow it. Both
answers carry `ignore_whitespace`, the value they used.

`GET /api/work-items/{id}` carries `fix_target` while a gate is pending: the
`node` a request-changes review restarts at, the nodes `then` that run before it
returns to the `gate`, and the `round` (`n` of `max`) a rejection now would start,
counted against the cap the gate's reject loop already snapshotted. It is `null`
with no gate pending.

`GET /api/work-items/{id}/fix-target?node=&gate=` answers
for a target the reviewer picked; with no gate pending it gives what a gateless
`request_changes` would target, with `reason` one of `requested` (you named the
node), `threads on <path or node>`, `current node`, or `gate`. It answers `400`
for a node that is not before the gate, `409` for a gate that is not pending or an
ended item, and does git work per thread, so call it on demand.

A review submitted with `outcome: approve` takes an optional `digest`, passed to
the gate approval as `POST /api/work-items/{id}/gates/{gate}/approve` takes it. A chain revision gate
needs it (the one `GET /artifact` returned) and answers `409` without it or with a
stale one; any other gate ignores it.

### Attachments and artifacts

`GET /api/work-items/{id}/attachments/{kind}` reads the spec or plan attached
at intake (`kind` is `spec` or `plan`) from the copy Kraft keeps under
`run/attachments/<id>/`, the one the worktree gets when the item starts. It
answers `{work_item_id, kind, path, title, content, truncated}`, `path` being
where the worktree puts it, `404` when the item has no such attachment or
its copy is gone, and `422` for a `kind` that is neither.

Before the item starts nothing is indexed, so this is how the
board and the phone open one, as do `kraft view docs --attachment` and the MCP
tool `get_attachment`.

`GET /api/work-items/{id}/documents` lists the same
copy, until the item has a worktree, as `attachment:<id>:<kind>`, which
`GET /api/documents/{id}` reads.

`GET /api/work-items/{id}/artifacts/{kind}` reads the document of `kind` a task
wrote (its `produces`), whether or not a gate is pending on it: what the task's
**Output** opens. `kind` must be one the item's chain names, as a task's
`produces` or a gate's `artifact`, else `404`.

It reads the item's worktree, as
`GET /artifact` does, with a chain revision rendered as its gate shows it, and
answers `{work_item_id, kind, path, absolute_path, title, content, truncated}`.

A
file there that is refused (a symlink, an unreadable file) is a `404` with the
reason, recorded on the item's timeline as `artifact_refused`. With no file in
the worktree it reads the copy the gate's approval indexed, answering the same
fields with `origin` in place of `absolute_path`, and `404` when there is neither.

### Viewed marks

`GET /api/work-items/{id}/compare` marks each file `viewed`. `PUT` and
`DELETE /api/work-items/{id}/viewed?file=<path>&to=<target>` set and clear the
mark and answer `{file, to, viewed}`; `to` is a compare target (default `latest`)
and `file` a repository-relative path.

A mark belongs to the file's content at
`to`, not to the `from` side, so a file that has not changed since you ticked it
stays ticked in any other comparison and a new attempt that edits it clears the
tick. `DELETE` clears the mark on that content wherever it was made.

The routes
answer `404` for a target the item does not have and `400` for a path outside the
repository.
