The routes that decide a gate, pause, resume, skip, escalate, end and retry an item are on [Gates, run control, ending and retry](/reference/http-api/gates-run-control-and-ending). The shapes the routes answer with are on [The work item object](/reference/http-api/work-item-object).

Every route under `/api/` except the [stable routes](/reference/http-api#stable-routes), and the `/api/ws/events` WebSocket, exists for the board and can change in any release. For those, prefer the `kraft` command with `--json`, which is stable.

| Route | What it does |
|---|---|
| [`POST /api/work-items`](#post-apiwork-items) | Files a work item, paused unless the body starts it. |
| [`POST /api/one-off-chain/ops`](#post-apione-off-chainops) | Applies editor ops to a one-off chain's text and answers what it resolves to, storing nothing. _Added in 2.5_ |
| [`POST /api/work-items/{id}/duplicate`](#post-apiwork-itemsidduplicate) | Files a fresh paused item from an existing one. |
| [`GET /api/work-items`](#get-apiwork-items) | Lists the items on the board. |
| [`GET /api/work-items/{id}`](#get-apiwork-itemsid) | Answers one item in full. |
| [`GET /api/work-items/{id}/one-off`](#get-apiwork-itemsidone-off) | Answers what a person reads before starting an item with a one-off chain. _Added in 2.5_ |
| [`POST /api/work-items/{id}/one-off/approve`](#post-apiwork-itemsidone-offapprove) | Approves the custom content of an item's one-off chain. _Added in 2.5_ |
| [`PATCH /api/work-items/{id}`](#patch-apiwork-itemsid) | Changes an item's title, description, chain, overrides, budget, policy or attachments. |
| [`POST /api/work-items/bulk`](#post-apiwork-itemsbulk) | Pauses, cancels, archives or restores several items. |

Routes that read an item's budget, events, diff and documents are on [Budget, events, diff and documents](/reference/http-api/budget-and-events).

## Filing a work item

### `POST /api/work-items`

Files a work item. The item is paused unless the body sets `autostart: true`, like `kraft item create` without `--autostart`. `POST /api/work-items?dry_run=1` runs the same checks and files nothing: see [Dry run](/reference/http-api/budget-and-events#post-apiwork-itemsdry_run1).

| Field | Type | Default | Meaning |
|---|---|---|---|
| `title` | string | required | One line of plain text, up to 500 characters, with no tab, escape or other control character. |
| `description` | string | `""` | The brief: prose the spec node writes a design from. |
| `repo` | string | required | The absolute path of a connected repo. |
| `chain` | string | the repo's `default_chain` | The chain to run. The pre-2.0 name `chain_template` is still read, by `PATCH` too. |
| `one_off_chain` | string or object | `null` | A chain for this item alone, as a chain file's text or its mapping, never saved to the library. Not with `chain`. Custom content in it waits for a person's approval. _Added in 2.5_ |
| `approve_one_off` | string | `null` | The `review_digest` the editor (`POST /api/one-off-chain/ops`) answered as `digest`, not `GET …/one-off`'s `digest`. Sent by the web UI. Refused (`403`) from a Kraft worker or an MCP session. _Added in 2.5_ |
| `workspace`, `members`, `root_pointer_policy` | string, list, string | `null`, `[]`, `null` | A workspace item: the workspace `repo` is the root of, the members it selects, and `ignore` or `bump`. An unset policy is the workspace's `root_pointer_default`. |
| `base_branch` | string | `null` | The branch the work starts from and the merge request targets: the repo's default branch when `null`. Refused unless `origin` has it. |
| `in_place` | boolean or `null` | `null` | `true` runs the item in the repo's own checkout, `false` in a worktree of its own; `null` follows the repo's [`worktrees`](/reference/configuration/repos#worktrees). Frozen at filing. _Added in 2.1_ |
| `attachments` | list | `[]` | Existing documents, `{kind, path}` with `kind` `spec` or `plan` and `path` inside the repo. At most one per kind. They trim the gates they satisfy. |
| `cwd` | string | `null` | The caller's working directory, sent only with attachment paths. A path is also read from another working tree of the same repo there. |
| `autostart` | boolean | `false` | Start the item now instead of filing it paused. A one-off chain whose custom content nobody approved is filed paused all the same. _Added in 2.5_ |
| `auto_gate` | boolean | `true` | Arms agent review for the item's `auto_escalate` gates. |
| `implements_beads` | list | `[]` | Bead ids the item implements, closed when it completes. |
| `depends_on` | list | `[]` | Work item ids this item comes after, or a unique start of each. Started while one is unfinished, the item is `blocked` and starts when they complete. Set here only: `POST /api/work-items/{id}/unblock` drops them, nothing adds them. |
| `skip_nodes` | list | `[]` | Node ids to drop from the chain. An id that is no node of the chain is refused. |
| `budget_usd` | number or `null` | the policy default | The item's own dollar cap. Omitted uses the policy default, `null` means no cap. |
| `runner` | string | `null` | Where the item's steps run: a machine or group from `workers.yaml`, `any` or `local`. Stored as `agent_overrides.runner`. `422` for an unknown name, one not allowed for the repo, an in-place item, or one with workspace members. _Added in 2.4_ |
| `node_overrides` | object | `{}` | `{node_id: {field: value}}`, as `PATCH` takes it. |
| `policy` | object | `null` | The item's own [policy override](/reference/cli/item#a-work-items-own-policy). |

A `POST` or `PATCH` body naming two different chains under `chain` and `chain_template` is refused with `422`, its `detail` one sentence naming both. The same chain twice is fine.

The answer is `201` with `{"id": "...", "status": "paused"}` for an item filed paused, `"status": "queued"` when `autostart: true` found every slot busy, and `"status": "blocked"` when it also named an unfinished item in `depends_on`. These keys appear only when they apply:

| Key | When |
|---|---|
| `slots` | `autostart: true` was sent but every slot (`max_concurrent`) was busy, so the item was filed `queued`: `{"busy": 3, "limit": 3}`. |
| `why`, `held_by`, `held_by_title` | `autostart: true` found another in-place item using the checkout, so the item was filed `queued` behind it: `why` is `checkout`, and the others name that item. _Added in 2.1_ |
| `waiting_on` | `autostart: true` with an unfinished item in `depends_on`, so the item was filed `blocked`: `[{"id", "title", "status"}]` for each item it waits on. |
| `repo_warning` | The repo declares no setup command, or no test command nor test scopes. It says where the item will stop. A disabled repo is warned of too: check its commands before starting the item. |
| `duplicate_warning` | Another open item has the same title or implements a bead the body names. |
| `bead_warning` | Why no bead was filed for the item. |
| `one_off` | For a `one_off_chain`: `{"custom", "approved", "digest", "review_digest"}`: how many custom parts, whether a person approved them at filing, the authored chain's digest, and the value `approve_one_off` must equal. _Added in 2.5_ |

An item that starts at once answers `201` with `bead_id`, `chain_definition`, `materialized_chain` and `current_node_id` beside `id` and `status`.

| Status | When |
|---|---|
| `503` | `policy.yaml` does not load. It is checked first, before the `403`. Kraft refuses new work until the file loads. |
| `403` | `autostart: true` came on a request that carries `X-Kraft-Session-Id` (a worker session) or `X-Kraft-Client: mcp` (the MCP server). An agent files work paused, and you start it. |
| `403` | `approve_one_off` came from a worker session or the MCP server: only a person approves a one-off chain's custom content. _Added in 2.5_ |
| `403` | A `node_overrides` entry sets `extra_prompt`, from a worker session, an escalation turn or the MCP server. See below the table. _Added in 2.5_ |
| `403` | The repo is disabled, and the request came from a worker session, an escalation turn or the MCP server, `dry_run` included. See below the table. _Added in 2.5_ |
| `409` | `approve_one_off` does not match what will run: the `one_off_chain` sent differs, or a library reload changed its custom parts since the review. Nothing is filed. _Added in 2.5_ |
| `503` | The library or a chain does not load. |
| `422` | A field is refused: a relative or unconnected `repo`, an unknown chain, a bad title or description, a missing attachment, an unknown or abandoned `depends_on` id, an unknown `skip_nodes` id, an unknown `base_branch`, or a refused override. |
| `422` | A `depends_on` value is the start of several work item ids. `detail` names them. |
| `422` | The item would run in place and sandboxed, naming the setting that turns each on, or a workspace item would run in place. _Added in 2.1_ |
| `422` | The chain reads another repository's [repo library](/reference/configuration/repo-libraries#who-can-name-it): `chain 'my-repo:ship': it reads my-repo's repo library, visible only to items in my-repo`. |
| `502` | Filing the item failed after the checks passed. |

The server cannot tell a coding agent that runs `kraft item create --autostart` in its own shell from a person, so that call starts the item.

An agent files no work on a disabled repo, or on a workspace that selects a disabled member, and does not start a never-started item on one (`POST /api/work-items/{id}/resume` answers the same `403`): `<repo> is disabled: a person enables it in Settings › Repos before an agent files or starts work on it, since its commands run for every item` (`an assistant` from the MCP server).

For a repo with no test command, it reads `a person sets its test command and enables it`. A repo is disabled when an agent connected it with its own commands, until a person has read them and enabled it, or when it has no test command. A person can still file on a disabled repo by hand.

A node's `extra_prompt` is a person's to set: `node '<id>': an extra_prompt is a person's to set, not an agent's; it reaches the node's tasks with nobody reviewing it` (`an assistant's` from the MCP server). A request that carries `X-Kraft-Session-Id` or `X-Kraft-Client: mcp` gets that `403`, on any item. `PATCH` refuses it the same way. Dropping one (`"extra_prompt": null`), clearing the node (`{}`) and the node's other fields stay open to an agent.

Every repo path you send must be absolute: the server would read a relative one against its own directory, not yours. `POST /api/work-items`, `POST /api/repos` and `POST /api/triggers` refuse a relative path with `422`, and `PATCH` or `DELETE /api/repos?path=` answer `404`.

### `POST /api/one-off-chain/ops`

_Added in 2.5_

The editor behind a one-off chain: applies the Templates screen's [chain ops](/reference/http-api/draft-ops#chain-and-library-ops) to a chain file's text and answers the result. It writes nothing, to the library or anywhere else. The body is `{"text": "...", "ops": [...], "preview": false}`; `preview` is the web UI's own flag, and the server stores nothing either way.

The answer is the [draft view](/reference/http-api/drafts#get-apidraftsareakey) of the edited chain, with its new `text`, plus:

| Key | Meaning |
|---|---|
| `digest` | The review digest: the value `approve_one_off` must equal to approve this chain at filing. `null` while the text is not YAML. |
| `custom` | Each custom part, as `GET /api/work-items/{id}/one-off` answers it. |
| `custom_nodes` | The ids of the nodes a custom part names, or every node when the chain extends no library chain. |
| `added` | For each added node, `node`, `harnesses`, `estimate_usd` and `estimate_runs`. |
| `nodes` | The resolved chain's nodes. |

A text with a YAML syntax error is answered `200` with its error and no op applied. `custom`, `custom_nodes`, `added` and `nodes` are empty while the chain does not resolve.

| Status | When |
|---|---|
| `422` | An op would change the library or another chain (`new_chain`, `delete_chain`, `move_to_library`, `add_component`, `copy_component`, or renaming the chain): `a one-off chain can't change the library or other chains`. |
| `422` | `text` is over 256 KiB (`a one-off chain is at most 256 KiB`), or expands to more than 20,000 YAML nodes (`chain YAML is too large: …`). |
| `422` | The chain's id is a library chain's or not a chain id, or an op cannot apply (`op` names its index). |
| `422` | `text` is not a mapping of plain values (`a chain file is a mapping`, `a one-off chain holds only plain YAML values: …`), or holds a value that can't be read (`not YAML: …`). |

### `POST /api/work-items/{id}/duplicate`

Files a fresh, paused item from the item `{id}`: its title, description, repo, chain, workspace selection and attachments, snapshotted again under the new item's own id. Any source status is accepted, archived and cancelled included. No run state, override, policy override, budget or bead link carries over. This is a fresh intake, not a clone of the row. Agent review of the item's `auto_escalate` gates is armed, as for an ordinary create, whatever the source had. The body is empty.

A copy of an item with a one-off chain resolves that chain again from what was authored, as at a fresh filing, and is filed unapproved.

```json
{"id": "...", "status": "paused", "duplicate_warning": "..."}
```

`duplicate_warning` is present only when another open item looks like a duplicate, the same check `POST /api/work-items` makes.

| Status | When |
|---|---|
| `403` | The source's repo is disabled, and the request came from a worker session, an escalation turn or the MCP server. See [`POST`'s](#post-apiwork-items). _Added in 2.5_ |
| `404` | There is no such item. |
| `409` | The source's stored attachment copy has gone missing, as it does when the source is abandoned. The answer names it, before anything is filed. |
| `422` | The chain or workspace the source used is gone (for a one-off chain, the library chain it extends), the chain reads another repository's [repo library](/reference/configuration/repo-libraries#who-can-name-it), or its title is empty. |
| `502` | Filing the item failed after the checks passed. |
| `503` | `policy.yaml`, the library or a chain does not load. |

## Reading work items

### `GET /api/work-items`

Answers the board: `{"items": [...], "cursor": N}`. `cursor` is the highest event `seq` at the time of the read. Each row is [the list row](/reference/http-api/work-item-object#the-list-row): a short subset of the item's fields, with `display_status`, `stop` (without `facts`, `task` and `attempt`), `step`, `mr_ref` and `progress` (without `tasks`) in place of the detail's per-row lookups. It carries no `agent_overrides`, `node_overrides` or `policy_override`.

| Query | Meaning |
|---|---|
| `archived=true` | Only archived items. Without it, archived items are left out. An archived item that was cancelled or abandoned also needs `include_abandoned=true`. |
| `include_abandoned=true` | Include cancelled and abandoned items. Without it they are left out, archived or not. |

### `GET /api/work-items/{id}`

Answers one item as [the detail object](/reference/http-api/work-item-object#the-detail-object), and `404` for an id that names no item.

### `GET /api/work-items/{id}/one-off`

_Added in 2.5_

Answers what a person reads before starting an item with a one-off chain: `extends`, the `authored` chain, each `custom` part (`path`, `what`, `value`) and the `provenance` recorded when the item was filed.

It also answers its `digest` (covering the chains that will run, so a draft applied after you read it makes it stale), the `approval` (or `null`), `needs_review`, and two lists:

- `added`: for each added node, `node`, `harnesses`, `estimate_usd` and `estimate_runs`;
- `redrafted`: each draft that revised the chain since filing.

It answers `404` for an item filed with a library chain.

### `POST /api/work-items/{id}/one-off/approve`

_Added in 2.5_

Approves the custom content of an item's one-off chain. The body is `{"digest": "...", "door": "web"}`, where `door` is `web` or `phone` and the digest is the one `GET` answered.

Nothing is approved on a refusal:

| Status | When |
|---|---|
| `403` | A Kraft worker or an MCP session sent it. |
| `404` | The item has no one-off chain. |
| `409` | The chain is library-only: `nothing to approve: this one-off chain is library-only`. |
| `409` | The item has ended (`work item has ended; there is nothing to approve`) or started (`work item has already started`). |
| `409` | The chain is already approved: `this one-off chain is already approved`. |
| `409` | The chain changed since the digest was read: `the one-off chain changed since it was reviewed; review it again`. |

An approval of an item stopped because its one-off chain changed before it started puts it back to `paused`; a person then starts it.

## Forge reads

_Added in 2.5_

These routes read an item's merge request and CI through the forge, so a worker needs no forge login. The server derives the project and merge request from the item. Each takes an optional `repo`: a workspace member's mount path. Without it the route reads the root repository. Host workers call them unscoped, like every loopback route.

| Route | Answers |
|---|---|
| `GET /api/work-items/{id}/forge/mr` | The merge request: `number`, `url`, `state`, `title`, `body`, `draft`, `labels`, `source_branch`, `target_branch`, `head_sha`. |
| `GET /api/work-items/{id}/forge/pipelines` | The item's pipelines: `id`, `kind`, `ref`, `sha`, `status`, `url`, `created_at`. |
| `GET /api/work-items/{id}/forge/pipelines/{pid}/jobs` | One pipeline's jobs: `id`, `name`, `stage`, `status`, `failure_reason`, `url`. |
| `GET /api/work-items/{id}/forge/pipelines/{pid}/jobs/{jid}/log` | `{"log", "truncated"}`: the last `lines` lines (1 to 5000, default 200). |
| `GET /api/work-items/{id}/forge/merged` | Recent merges into the base branch; `limit` is 1 to 100, default 20. |
| `GET /api/work-items/{id}/forge/labels` | The project's labels: `name`, `description`, `color`. |

`status` is the forge's own word. A pipeline or job the item does not own, a missing `repo` member and an item with no merge request yet (`/forge/mr` only) answer `404`. Only the newest 20 pipelines are listed (GitHub: 20 branch runs and 20 merge-queue runs), and only those can be read. A `lines` or `limit` out of range answers `422`. A rate limit answers `429` with `Retry-After`, and any other forge failure `502`.

## Changing a work item

### `PATCH /api/work-items/{id}`

Changes the fields the body names and leaves the rest. A body naming none is refused with `422`. The write is one transaction, so a body that changes several fields never lands half.

| Field | Type | Meaning |
|---|---|---|
| `title` | string | The new title. It cannot be empty and is one line. |
| `description` | string | The new brief. `""` clears it. |
| `chain` | string | Switches a not-yet-started item onto that chain. |
| `one_off_chain` | string or object | Gives a not-yet-started item a chain of its own, as `POST /api/work-items` takes it, and drops any approval of the chain it replaces. Not with `chain`. _Added in 2.5_ |
| `agent_overrides` | object | Replaces the item's whole model and effort override. See below. |
| `node_overrides` | object | Merges per node. See below. |
| `budget_usd` | number or `null` | The item's own dollar cap. `null` sets no cap, and leaving the field out leaves the cap alone. |
| `policy` | object | Replaces the item's [policy override](/reference/cli/item#a-work-items-own-policy). `{}` clears it. A change applies from the next node the item enters and the next time it observes a wait. |
| `attachments` | object | `{"spec": PATH}` snapshots that kind again, `{"spec": null}` drops it and puts back the gate it trimmed. A kind not named keeps its copy. |
| `cwd` | string | The caller's working directory, as at create. |

`agent_overrides` replaces the override as a whole. A field you leave out, or send as `null`, is dropped, and `{}` clears the override. The exception is `runner`, a machine or group, `any` or `local`: a replacement that does not name it keeps the stored one. A node's override takes `runner` too, and a started node accepts a `runner` change alone, because it takes effect at the next step launch.

`node_overrides` merges per node. `{"plan": {"effort": "high"}}` sets that field and keeps the node's others, `{"plan": {"effort": null}}` drops one field, and `{"plan": {}}` drops the node's overrides. `{}` resets every node. A node's `reviewers` is a list of `{"bot": LOGIN}` or `{"check": NAME}`, the automated reviewers its `mr.automated_review` wait reads; `[]` expects none, and a node with no such task answers `422`.

The answer is `{"id": "...", ...}` with each field you sent. A `chain` you sent is echoed as `chain_template`. A `one_off_chain` is echoed as `chain_template: "@one-off"` and a `one_off` summary (`extends`, `custom`, `needs_review`, `approval`), never the YAML you sent. `agent_overrides` and `node_overrides` are echoed as stored: `{}` once an override is cleared, and for `node_overrides` only the nodes you named.

| Status | When |
|---|---|
| `403` | A worker session sent `attachments`, an override, a `policy` or a `budget_usd` for its own item. An escalation turn is refused `policy` and `budget_usd` too. |
| `403` | A `node_overrides` entry sets `extra_prompt`, on any item, from a worker session, an escalation turn or the MCP server. See [`POST`'s](#post-apiwork-items). _Added in 2.5_ |
| `404` | There is no such item, or `chain` names a chain that does not exist. |
| `409` | The item has ended: `work item is <status>; its chain does not run again`. |
| `409` | `chain`, `one_off_chain` or `attachments` was sent for an item that has started or is running: its chain and documents are fixed for its life. Another write changed them meanwhile. |
| `409` | `chain` or `one_off_chain` sent for an item claimed to run that has not loaded its first node: `work item is starting; its chain and documents can't change now`. _Added in 2.5_ |
| `409` | `attachments` sent then: the same text, ending `; nothing was changed`. _Added in 2.5_ |
| `409` | `node_overrides` names a node that has started, or is `{}` for an item that has. |
| `422` | The body names no field to change. |
| `422` | `chain` names a chain that reads another repository's [repo library](/reference/configuration/repo-libraries#who-can-name-it): `chain 'my-repo:ship': it reads my-repo's repo library, visible only to items in my-repo`. |
| `422` | A field is refused, and `detail` says which: an unknown node id or field, a model or effort the harness refuses, a limit above the policy's `maxima`, or a path that is not a file in the repo. |
| `422` | `auto_escalate: true` on a gate that declares no `auto_review`. |

A started node accepts one exception. On an item stopped at that node because its stored `model` or `escalate_model` is not a model id, clearing that node (`{"<node>": {}}`) and changing `model`, `escalate_model` or `effort` alone are accepted, so the stop can be repaired.

### `POST /api/work-items/bulk`

Applies one action to several items, each through the single-item route, in `ids` order, each in its own write.

```json
{"action": "pause", "ids": ["...", "..."], "reason": "..."}
```

| Field | Type | Meaning |
|---|---|---|
| `action` | string | `pause`, `cancel`, `archive` or `restore`. |
| `ids` | list | From 1 to 200 item ids. |
| `reason` | string | Required when `action` is `cancel`, and checked before anything is touched (`422` otherwise). The other actions ignore it. |

The answer is one result per id, in order:

```json
{"results": [{"id": "...", "ok": true, "status": "paused"}, {"id": "...", "ok": false, "error": "..."}]}
```

An id whose action raises, an item in the wrong status for example, becomes `{id, ok: false, error, status}`, and the rest of the batch still runs. An id that names no item answers `{id, ok: false, error: "not found"}` with no `status`. `status` is the item's stored status after the action ran.

An id may be the start of one, as in a [path](/reference/http-api#work-item-ids-in-a-path): its result's `id` is the whole id. A start shared by several ids is its own result, `{id, ok: false, error}`, with `error` naming them.

| Status | When |
|---|---|
| `422` | `action` is none of the four, `ids` holds fewer than `1` or more than `200` ids, or `action` is `cancel` and `reason` is blank. Nothing is touched. |
