This page lists the board's routes for a [work item](/concepts/vocabulary#work-item) and the object they return. Every route under `/api/` except the [stable routes](/reference/http-api#stable-routes), and the `/api/ws/events` WebSocket, exists for the board and can change in any release. For those, prefer the `kraft` command with `--json`, which is stable.

| Route | What it does |
|---|---|
| [`POST /api/work-items`](#post-apiwork-items) | Files a work item, paused unless the body starts it. |
| [`POST /api/work-items/{id}/duplicate`](#post-apiwork-itemsidduplicate) | Files a fresh paused item from an existing one. |
| [`GET /api/work-items`](#get-apiwork-items) | Lists the items on the board. |
| [`GET /api/work-items/{id}`](#get-apiwork-itemsid) | Answers one item in full. |
| [`PATCH /api/work-items/{id}`](#patch-apiwork-itemsid) | Changes an item's title, description, chain, overrides, budget, policy or attachments. |
| [`POST /api/work-items/bulk`](#post-apiwork-itemsbulk) | Pauses, cancels, archives or restores several items. |
| [`GET /api/work-items/{id}/cancel-preview`](#get-apiwork-itemsidcancel-preview) | Shows what a cancel would do, without doing it. |
| [`POST /api/work-items/{id}/cancel`](#post-apiwork-itemsidcancel) | Ends an item and keeps its worktree and branch. |
| [`POST /api/work-items/{id}/archive`](#post-apiwork-itemsidarchive) | Archives a completed or cancelled item and reclaims its worktree. |
| [`POST /api/work-items/{id}/abandon`](#post-apiwork-itemsidabandon) | Ends an item and deletes its worktree and branch. |
| [`POST /api/work-items/{id}/retry`](#post-apiwork-itemsidretry) | Reruns the node an item stopped on. |
| [`POST /api/work-items/{id}/reopen-mr`](#post-apiwork-itemsidreopen-mr) | Reopens a merge request closed on the forge, then retries. |

Routes that read an item's budget, events, diff and documents are on [Budget, dry run and events](/reference/http-api/budget-and-events).

## Filing a work item

### `POST /api/work-items`

Files a work item. The item is paused unless the body sets `autostart: true`, like `kraft item create` without `--autostart`. `POST /api/work-items?dry_run=1` runs the same checks and files nothing: see [Dry run](/reference/http-api/budget-and-events#post-apiwork-itemsdry_run1).

| Field | Type | Default | Meaning |
|---|---|---|---|
| `title` | string | required | One line of plain text, up to 500 characters, with no tab, escape or other control character. |
| `description` | string | `""` | The brief: prose the spec node writes a design from. |
| `repo` | string | required | The absolute path of a connected repo. |
| `chain` | string | the repo's `default_chain` | The chain to run. The pre-2.0 name `chain_template` is still read. |
| `workspace`, `members`, `root_pointer_policy` | string, list, string | `null`, `[]`, `null` | A workspace item: the workspace `repo` is the root of, the members it selects, and `ignore` or `bump`. An unset policy is the workspace's `root_pointer_default`. |
| `base_branch` | string | `null` | The branch the work starts from and the merge request targets: the repo's default branch when `null`. Refused unless `origin` has it. |
| `attachments` | list | `[]` | Existing documents, `{kind, path}` with `kind` `spec` or `plan` and `path` inside the repo. At most one per kind. They trim the gates they satisfy. |
| `cwd` | string | `null` | The caller's working directory, sent only with attachment paths. A path is also read from another working tree of the same repo there. |
| `autostart` | boolean | `false` | Start the item now instead of filing it paused. |
| `auto_gate` | boolean | `true` | Arms agent review for the item's `auto_escalate` gates. |
| `implements_beads` | list | `[]` | Bead ids the item implements, closed when it completes. |
| `skip_nodes` | list | `[]` | Node ids to drop from the chain. An id that is no node of the chain is refused. |
| `budget_usd` | number or `null` | the policy default | The item's own dollar cap. Omitted uses the policy default, `null` means no cap. |
| `node_overrides` | object | `{}` | `{node_id: {field: value}}`, as `PATCH` takes it. |
| `policy` | object | `null` | The item's own [policy override](/reference/cli/item#a-work-items-own-policy). |

A body naming two different chains under `chain` and `chain_template` is refused, its `detail` one sentence naming both. The same chain twice is fine.

The answer is `{"id": "...", "status": "paused"}` for an item filed paused. These keys appear only when they apply:

| Key | When |
|---|---|
| `slots` | `autostart: true` was sent but every slot (`max_concurrent`) was busy, so the item was filed paused: `{"busy": 3, "limit": 3}`. |
| `repo_warning` | The repo declares no setup command, or no test command nor test scopes. It says where the item will stop. |
| `duplicate_warning` | Another open item has the same title or implements a bead the body names. |
| `bead_warning` | Why no bead was filed for the item. |

An item that starts at once answers `201` with `bead_id`, `chain_definition`, `materialized_chain` and `current_node_id` beside `id` and `status`.

| Status | When |
|---|---|
| `403` | `autostart: true` came from an agent: a worker or an assistant over MCP. An agent files work paused, and you start it. |
| `422` | A field is refused: a relative or unconnected `repo`, an unknown chain, a title or description that fails its check, a missing attachment, an unknown `skip_nodes` id, an unknown `base_branch`, or an override the chain or policy refuses. |
| `503` | `policy.yaml` or the template library does not load. Kraft refuses new work until it does. |
| `502` | Filing the item failed after the checks passed. |

Every repo path you send must be absolute: the server would read a relative one against its own directory, not yours. `POST /api/work-items`, `POST /api/repos` and `POST /api/triggers` refuse a relative path with `422`, and `PATCH` or `DELETE /api/repos?path=` answer `404`.

### `POST /api/work-items/{id}/duplicate`

Files a fresh, paused item from the item `{id}`: its title, description, repo, chain, workspace selection and attachments, snapshotted again under the new item's own id. Any source status is accepted, archived and cancelled included. No run state, override, policy override, budget or bead link carries over. This is a fresh intake, not a clone of the row. The body is empty.

```json
{"id": "...", "status": "paused", "duplicate_warning": "..."}
```

`duplicate_warning` is present only when another open item looks like a duplicate, the same check `POST /api/work-items` makes.

| Status | When |
|---|---|
| `404` | There is no such item. |
| `409` | The source's stored attachment copy has gone missing, as it does when the source is abandoned. The answer names it, before anything is filed. |
| `422` | The chain or workspace the source used is gone, or its title is empty. |
| `503` | `policy.yaml` or the template library does not load. |

## Reading work items

### `GET /api/work-items`

Answers the board: `{"items": [...], "cursor": N}`. `cursor` is the highest event `seq` at the time of the read. Each row is a [work item object](#the-work-item-object) with the fields that need no per-row lookup: `display_status`, `stop` (without `facts`, `task` and `attempt`), `step`, `mr_ref` and `progress` (without `tasks`).

| Query | Meaning |
|---|---|
| `archived=true` | Only archived items. Without it, archived items are left out. |
| `include_abandoned=true` | Include cancelled and abandoned items. Without it they are left out. |

### `GET /api/work-items/{id}`

Answers one item as [the work item object](#the-work-item-object), and `404` for an id that names no item.

## Changing a work item

### `PATCH /api/work-items/{id}`

Changes the fields the body names and leaves the rest. A body naming none is refused with `422`. The write is one transaction, so a body that changes several fields never lands half.

| Field | Type | Meaning |
|---|---|---|
| `title` | string | The new title. It cannot be empty and is one line. |
| `description` | string | The new brief. `""` clears it. |
| `chain` | string | Switches a not-yet-started item onto that chain. `chain_template` is read too. |
| `agent_overrides` | object | Replaces the item's whole model and effort override. See below. |
| `node_overrides` | object | Merges per node. See below. |
| `budget_usd` | number or `null` | The item's own dollar cap. `null` sets no cap, and leaving the field out leaves the cap alone. |
| `policy` | object | Replaces the item's [policy override](/reference/cli/item#a-work-items-own-policy). `{}` clears it. A change applies from the next node the item enters and the next time it observes a wait. |
| `attachments` | object | `{"spec": PATH}` snapshots that kind again, `{"spec": null}` drops it and puts back the gate it trimmed. A kind not named keeps its copy. |
| `cwd` | string | The caller's working directory, as at create. |

`agent_overrides` replaces the override as a whole. A field you leave out, or send as `null`, is dropped, and `{}` clears the override.

`node_overrides` merges per node. `{"plan": {"effort": "high"}}` sets that field and keeps the node's others, `{"plan": {"effort": null}}` drops one field, and `{"plan": {}}` drops the node's overrides. `{}` resets every node.

The answer is `{"id": "...", ...}` with each field you sent. `agent_overrides` and `node_overrides` are echoed as stored: `{}` once an override is cleared, and for `node_overrides` only the nodes you named.

| Status | When |
|---|---|
| `403` | A worker session sent `attachments`, an override, a `policy` or a `budget_usd` for its own item. |
| `404` | There is no such item, or `chain` names a chain that does not exist. |
| `409` | The item has ended. |
| `409` | `chain` or `attachments` was sent for an item that has started: its chain and documents are fixed for its life. Another write changed them meanwhile. |
| `409` | `node_overrides` names a node that has started, or is `{}` for an item that has. |
| `422` | The body names no field to change. |
| `422` | A field is refused, and `detail` says which: an unknown node id or field, a model or effort the harness refuses, a limit above the policy's `maxima`, or a path that is not a file in the repo. |
| `422` | `chain` and `chain_template` name different chains. |

A started node accepts one exception. On an item stopped at that node because its stored `model` or `escalate_model` is not a model id, clearing that node (`{"<node>": {}}`) and changing `model`, `escalate_model` or `effort` alone are accepted, so the stop can be repaired.

### `POST /api/work-items/bulk`

Applies one action to several items, each through the single-item route, in `ids` order, each in its own write.

```json
{"action": "pause", "ids": ["...", "..."], "reason": "..."}
```

| Field | Type | Meaning |
|---|---|---|
| `action` | string | `pause`, `cancel`, `archive` or `restore`. |
| `ids` | list | From 1 to 200 item ids. |
| `reason` | string | Required when `action` is `cancel`, and checked before anything is touched (`422` otherwise). The other actions ignore it. |

The answer is one result per id, in order:

```json
{"results": [{"id": "...", "ok": true, "status": "paused"}, {"id": "...", "ok": false, "error": "..."}]}
```

An id whose action raises, an item in the wrong status for example, becomes `{id, ok: false, error, status}`, and the rest of the batch still runs. An id that names no item answers `{id, ok: false, error: "not found"}` with no `status`. `status` is the item's stored status after the action ran.

## Ending a work item

### `GET /api/work-items/{id}/cancel-preview`

Shows what `POST /api/work-items/{id}/cancel` would do, without doing it. It answers `409` once the item has ended, as `/cancel` does.

```json
{
  "running": {"node": "mr_checks", "task": "mr_checks", "attempt": 1, "started_at": "2026-10-03T10:00:00+00:00"} | null,
  "kept": {"branch": "kraft/...", "worktree": "/path", "findings": 0, "threads": 1},
  "mr": {"ref": 54, "url": "https://...", "state": "open"} | null,
  "spend": {"spent_usd": 1.2, "cap_usd": 5.0},
  "beads": ["kraft-ab1"]
}
```

| Field | Meaning |
|---|---|
| `running` | The item's running session, if any, and when it started. |
| `kept` | What cancel leaves behind. Cancel never removes the [worktree](/concepts/vocabulary#worktree) or the branch. Archive later removes the worktree but keeps a branch with commits nowhere else. |
| `mr` | The item's merge request and its live state, or `null` before one was ever opened. `state` is `null` when the forge cannot answer. |
| `spend` | The item's spend and its own cap. |
| `beads` | Every bead `POST /api/work-items/{id}/complete` closes when asked with `close_beads`. See below. |

`beads` holds the item's own bead, the beads it implements, and those a `Fixes` or `Closes` trailer on its commits names (an id starting `Kraft-`, any case). An item filed while `bd` was down has none yet, and `close_beads` files one for it and closes that.

### `POST /api/work-items/{id}/cancel`

Ends the item, with a reason, and stops whatever is running. The worktree and the branch stay.

| Field | Type | Default | Meaning |
|---|---|---|---|
| `reason` | string | required | Why it ended. A blank reason answers `422`. |
| `close_mr` | boolean | `false` | Close the item's merge request on the [forge](/concepts/vocabulary#forge) once the cancel has landed, if it is open. |

The answer is the item, as [the work item object](#the-work-item-object). With `close_mr: true` it also carries `close_mr: {"ok": true}`, or `{"ok": false, "error": "..."}` when there was no open merge request or the forge call failed. A failed close never undoes the cancel. The key is absent when `close_mr` was not asked for.

A worker session cannot cancel its own item (`403`). An item that has already ended answers `409`.

### `POST /api/work-items/{id}/archive`

Archives a completed or cancelled item and reclaims its worktree. The item still reads as completed or cancelled. It answers `{"id", "archived_by", "worktree_removed"}`, and `409` for an item in any other status. An item already archived answers the same shape with `worktree_removed: false`.

Archive never deletes a commit, and keeps the attachment copies. These keys appear only in the cases below.

| Key | When |
|---|---|
| `kept_branch`, `unpushed_commits` | The branch was kept because some of its commits are on no other branch, remote-tracking branch or tag, and not in what Kraft pushed. |
| `rescued_branch`, `rescued_commits` | The worktree's HEAD was detached on commits no branch has. Kraft saved them as `kraft/rescued/<id>`. |
| `worktree_kept` | That branch could not be made, as `rescue failed: <reason>`. The item is still archived but its worktree stays. |
| `repo_missing` | The item's repository was moved or deleted. Archive removed the worktree directory directly and did nothing to the branch: if you only moved the repository, it is still there. |

### `POST /api/work-items/{id}/abandon`

Ends the item and deletes its worktree, branch and attachment copies. It answers `{"id", "status": "abandoned", "worktree_removed"}`.

When the item's repository has been moved or deleted, abandon removes the worktree directory directly and adds `repo_missing`, the repository path it could not find. It does nothing to the branch.

| Status | When |
|---|---|
| `403` | A worker session abandons its own item. |
| `409` | The item is active. Pause it first. |

An item that is already abandoned, a cancelled one included, is reclaimed again without a second event. A second call finds nothing left and answers `worktree_removed: false`.

## Retrying a work item

### `POST /api/work-items/{id}/retry`

Reruns the node an item stopped on, with steer text if you give it, and clears a breached loop cap if there was one. It is the only way back onto an item stopped by a task failure, and `kraft item retry` calls it.

| Field | Type | Default | Meaning |
|---|---|---|---|
| `steer` | string | `null` | Text carried into the rerun. |
| `path` | string | the stopped node | What to rerun, by canonical path: `node`, `node.step` or `node.step.task`. A path after the node the item stands on answers `409`. |
| `restart` | boolean | `false` | Rerun the whole chain from its first node. It cannot be combined with `path`, `task_config` or `policy`. |
| `task_config` | object | `null` | Task fields to change for the retried task, validated against the chain and its policy bounds. |
| `policy` | object | `null` | The retried scope's policy, validated the same way. |

```json
{"id": "...", "node_id": "implement", "path": null, "loop": null, "steer": null, "attempt": 2}
```

`attempt` is the attempt number the task it relaunches will run as: the count of that task's own sessions so far, plus one. A `path` naming a task counts only that task's sessions. A `path` naming a step takes the highest next attempt over the step's tasks.

A `path`-less retry, or a `restart`, takes the highest over all of the node's own tasks, since a [walk](/concepts/vocabulary#walk) may enter at any one of them. A retry that stops at once answers the item itself, as [the work item object](#the-work-item-object).

| Status | When |
|---|---|
| `403` | A worker session retries its own item. |
| `409` | The item is not stopped, has ended, or has no current node. Every slot is busy. A walk is already running. `steer` is text no agent task downstream of the node would read. |
| `422` | `path`, `task_config` or `policy` is refused. |

### `POST /api/work-items/{id}/reopen-mr`

Reopens the item's merge request on the forge and retries the stopped node, the same as `POST /api/work-items/{id}/retry` with no `path`. Use it on an item that stopped because its merge request was closed there without merging.

A poller checks every `waiting` or `needs_human` item parked at a merge-request node against the forge every `policy.forge_poll_s` seconds (default `300`). When the merge request was closed without merging, it stops the item with `stop.kind: "mr_closed"` and `facts: {ref, url}`. See [Events: work_item_needs_human](/reference/events#work_item_needs_human).

There are three ways out: this route, `POST /api/work-items/{id}/retry` with the merge request node's path to open a new merge request, and `POST /api/work-items/{id}/cancel`. Cancelling leaves the closed merge request and the worktree as they are. [MR closed externally](/reference/statuses#mr-closed-externally) lists the board's button for each.

The answer is `/retry`'s own.

| Status | When |
|---|---|
| `409` | The item is not stopped with `stop.kind: "mr_closed"`, or has no merge request to reopen. |
| `502` | The forge call failed, with the forge's own message. The item stays stopped. |

## The work item object

`GET /api/work-items/{id}` answers the work item object: the item's stored columns plus the fields below. Every answer that hands back the item itself carries the stored columns too: a gate's approve or reject, `complete`, `cancel`, `skip`, and a `retry` or `resume` that stops at once. The [schema](/reference/http-api#the-schema) lists every field. This table lists the ones that need an explanation.

| Field | Meaning |
|---|---|
| `display_status` | List and detail. The board's status badge, one of `archived`, `done`, `cancelled`, `paused`, `running`, `waiting`, `needs_you`, `escalated`, `failed`. Read-only and computed on read rather than stored: see [Displayed status](/reference/statuses#displayed-status). |
| `stop` | List and detail. `null` unless the item is `needs_human`, `waiting` or `rate_limited`. See [The `stop` field](#the-stop-field). |
| `test_result` | Detail only. The latest changed-test-scope verification run. See [The `test_result` field](#the-test_result-field). |
| `budget_cap` | Detail only. The item's effective dollar cap and spend. See [The `budget_cap` field](#the-budget_cap-field). |
| `running_time` | Detail only. `{running_s, cap_minutes}`: the seconds any session ran since the last `/retry` a person made, against the item-wide `time_cap_minutes` (`null` for none). The whole field is `null` for an item with no frozen chain. |
| `summary` | Detail only. A run's progress at a glance. See [The `summary` field](#the-summary-field). |
| `step` | List only. `{index, count, name, task}` or `null`, which lets the board draw a row. `index` and `count` are as in `summary.step`. `name` is the step's id, and `task` is the latest non-escalation session's task id in it. |
| `mr_ref` | List and detail. The item's merge request, `{number, url}`, or `null`. The board draws "merged !139" from it. |
| `progress` | The item's place in its plan. See [The `progress` field](#the-progress-field). |
| `worktree_exists` | Detail only. See [The `worktree_exists` field](#the-worktree_exists-field). |
| `worker_sessions` | Detail only. One entry per session. `repository` is the workspace member the session ran in, or `null` for the item's own repository. |
| `scope_runs` | Detail only. Every command a changed-test-scope task ran. See [The `scope_runs` field](#the-scope_runs-field). |
| `fix_target` | Detail only. Where a request-changes review restarts, while a gate is pending. See [The `fix_target` field](#the-fix_target-field). |
| `agent_overrides`, `node_overrides`, `policy_override` | The item's overrides. `agent_overrides` and `policy_override` are `null` when the item has none, and `node_overrides` is `{}`. `PATCH` sets them: see [Changing a work item](#patch-apiwork-itemsid). |

### The `stop` field

`stop` is `{kind, node, resume_at, reason}` on the list. The detail adds `task`, `attempt` and `facts`. On a `cap` or `budget` stop it adds `limit`, and on a `budget` stop `scope`.

`facts.cause` names why an `infra` stop happened, when Kraft knows. [The `facts` field](/reference/events#the-facts-field) lists the values. The failed card chooses its action from it, and an `infra` stop without one reads as a generic infrastructure stop.

A `rate_limit` stop's `facts` also carries `fallback` and `fallback_allowed`: the stopped task's declared fallback [harnesses](/concepts/vocabulary#harness), and which of those its resolved policy still allows.

### `stop.kind`

`stop.kind` is one of twelve values: `gate`, `question`, `cap`, `budget`, `failed`, `conflict`, `mr_closed`, `config`, `infra`, `stuck`, `wait` and `rate_limit`. [Stop kinds](/reference/events#stop-kinds) says what each means, and [Why did my item stop?](/troubleshooting/why-did-my-item-stop#why-did-my-item-stop) gives each stop's reason with its fix.

A `needs_human` item stopped on 1.4.0 or earlier has no recorded kind. It reads `question`, `budget` or `cap` where its stop event carries one, else `failed`. A `waiting` row reads `wait` and a `rate_limited` one `rate_limit`.

### `stop.limit`

A `cap` or `budget` stop on the detail also carries `limit: {path, key, value, maximum}` when a `PATCH` of the item's `policy` can raise what stopped it, and omits it when none can.

| `key` | What it caps | `path` |
|---|---|---|
| `max_attempts`, `timeout_minutes` | A [fix loop](/concepts/vocabulary#fix-loop)'s attempts or its clock. | The node id. |
| `time_cap_minutes`, `total_time_cap_minutes` | The work item's own cap. | `""` |
| `budget_usd` | On a `budget` stop, the item-wide policy dollar cap. | `""` |

`value` is the limit that stopped it, in attempts, minutes or dollars. `maximum` is the `maxima` ceiling or `null`.

Raise it with `PATCH /api/work-items/{id}` `{policy: {<key>: N}}` (item-wide) or `{policy: {paths: {<path>: {<key>: N}}}}`, then `POST /api/work-items/{id}/retry`.

There is no `limit` for:

- a `budget` stop on the item's own cap (`POST /api/work-items/{id}/budget/raise` raises that one), on a node, step or task's `budget_usd`, a `token_budget`, the daily cap or spend a harness never reported;
- a node, step or task's time cap;
- a gate's or wait's timeout;
- a `loops:` cap in `policy.yaml`;
- exhausted rate-limit retries;
- a fix loop whose bound the older `node_overrides` set.

### `stop.scope`

A `budget` stop on the detail also carries `scope`, the cap that stopped it:

| `scope` | The cap |
|---|---|
| `work_item` | The item's own dollar cap. |
| `usd` | A `budget_usd`, item-wide or on a node, step or task, or spend a harness never reported. `POST /api/work-items/{id}/budget/raise` takes `work_item` and an item-wide `usd`. |
| `tokens` | A `token_budget`. |
| `daily` | `budget.daily_usd`. |

### The `test_result` field

`test_result` is `{scopes: [{command, scope, passed, exit_code, session_id}], passed}`, or `null` when no scope has finished.

- One entry per scope, passed or failed. `scope` is `null` when the repo's table no longer declares the command, and `exit_code` when none was recorded. `passed` is true when every scope passed.
- An area's setup appears only when it failed.
- A scope still running is left out.
- No test counts.
- `session_id` is the scope's session. Read its log with `GET /api/worker-sessions/{id}/log`.

### The `budget_cap` field

`budget_cap` is `{cap_usd, source, key, spent_usd, daily}`.

- `cap_usd` is whichever cap stops the item first: the lower of its own cap and the item-wide `budget_usd` of its policy. It is `null` when neither is set. This holds in the API and in `kraft view show --json`.
- `key` says which cap it is, and the `PATCH` field that changes it: `budget_usd` for the item's own cap, `policy.budget_usd` for the policy one.
- `source` is `item` when the item itself set the reported cap, by its own `budget_usd` or by its own `policy` override, and `policy` when it comes from `policy.yaml` or the chain. So `source: item` with `key: policy.budget_usd` means the item's policy override.
- `spent_usd` is the item's own, all-time spend.
- `daily` is `{spent_usd, cap_usd}`: the instance's spend since local midnight against `policy.budget.daily_usd`, the same two numbers as `GET /api/budget/today`.

`POST /api/work-items/{id}/budget/raise` (`kraft item raise-budget`) raises whichever of the two caps stopped the item.

Before 2.0, `cap_usd` was always the item's own cap (its `budget_usd`, else `budget.work_item_usd`), and `source` said which of those two set it.

### The `summary` field

`summary` is a run's progress at a glance:

```json
{"nodes_done": 3, "nodes_total": 8, "gates_passed": 1, "step": {"index": 2, "count": 2} | null}
```

`nodes_done` and `nodes_total` count against the frozen chain. `gates_passed` is how many of the completed nodes were gates. `step` is the current node's step (1-based) out of its own steps, read from its latest non-escalation session's task, when the node declares more than one, and `null` otherwise.

### The `progress` field

`progress` is `{current, total, title, tasks}`, or `null` when the item has no plan to follow. Each task is `{n, title, state, sha}`. `state` is `done`, `current` or `pending`, and `sha` is the short hash of the newest commit on the item's branch that names the task, or `null`. Rows on the list carry only `current`, `total` and `title`.

### The `worktree_exists` field

`worktree_exists` is whether `worktree_path` is a directory on disk. It is `false` before the item first runs and after its worktree was reclaimed or deleted.

The routes that need the directory (`diff`, `compare`, `open-worktree`, `mr-labels`) answer `404` in that case. The message is "this work item has not started, so it has no worktree yet" for an item that never ran, and "this work item's worktree was removed from disk" for one that did. A retry or resume recreates the directory.

### The `scope_runs` field

`scope_runs` lists every command a changed-test-scope task ran in its node's current pass, in the order each started, across rounds and repositories. Each entry is `{session_id, repository, round, command, passed, exit_code?, scope?, area?, setup?, order?, selected?, pending?, node_id, hook_point}`. The node's view draws its scopes from it.

- `passed` is `null` until the command finishes.
- A command its round picked that has not started yet comes last, `pending: true` with no `session_id`, while the node is still running.
- `round` is the session's fix-loop round, `0` for the first pass. `-1` is the repair an `on_failure` recovery runs inside a fix-loop node, and the re-measure after it.
- A retry starts a new pass, so the list keeps only the newest one.
- It is empty for a chain with no such task.

### The `fix_target` field

`fix_target` is `{gate, node, then, round}` while a gate is pending, and `null` with none pending.

| Key | Meaning |
|---|---|
| `gate` | The pending gate. |
| `node` | The node a request-changes review restarts at. |
| `then` | The nodes that run from there before the work returns to the gate. |
| `round` | The round a rejection now would start, `{n, max}`, counted against the cap the gate's reject loop already snapshotted. |

`GET /api/work-items/{id}/fix-target` answers the same shape for a target the reviewer picked: see [Fix target](/reference/http-api/budget-and-events#get-apiwork-itemsidfix-target).
