title: The work item object
description: The fields a work item answers carry, from its status and stop to its budget cap and plan progress.
---

`GET /api/work-items/{id}` answers the work item object: the item's stored columns plus the fields below. Every answer that hands back the item itself carries the stored columns too: a gate's [approve](/reference/http-api/work-items#post-apiwork-itemsidgatesgateapprove) or [reject](/reference/http-api/work-items#post-apiwork-itemsidgatesgatereject), `complete`, `cancel`, `skip`, and a `retry` or `resume` that stops at once. The [schema](/reference/http-api#the-schema) lists every field. This page explains the ones that need it.

## Fields that need an explanation

| Field | Meaning |
|---|---|
| `display_status` | List and detail. The board's status badge, one of `archived`, `done`, `cancelled`, `paused`, `running`, `waiting`, `needs_you`, `escalated`, `failed`. Read-only and computed on read rather than stored: see [Displayed status](/reference/statuses#displayed-status). |
| `stop` | List and detail. `null` unless the item is `needs_human`, `waiting` or `rate_limited`. See [The `stop` field](#the-stop-field). |
| `test_result` | Detail only. The latest changed-test-scope verification run. See [The `test_result` field](#the-test_result-field). |
| `budget_cap` | Detail only. The item's effective dollar cap and spend. See [The `budget_cap` field](#the-budget_cap-field). |
| `running_time` | Detail only. `{running_s, cap_minutes}`: the seconds any session ran since the last `/retry` a person made, against the item-wide `time_cap_minutes` (`null` for none). The whole field is `null` for an item with no frozen chain. |
| `summary` | Detail only. A run's progress at a glance. See [The `summary` field](#the-summary-field). |
| `step` | List only. `{index, count, name, task}` or `null`, which lets the board draw a row. `index` and `count` are as in `summary.step`. `name` is the step's id, and `task` is the latest non-escalation session's task id in it. |
| `mr_ref` | List and detail. The item's merge request, `{number, url}`, or `null`. The board draws "merged !139" from it. |
| `progress` | The item's place in its plan. See [The `progress` field](#the-progress-field). |
| `worktree_exists` | Detail only. See [The `worktree_exists` field](#the-worktree_exists-field). |
| `worker_sessions` | Detail only. One entry per session. `repository` is the workspace member the session ran in, or `null` for the item's own repository. |
| `scope_runs` | Detail only. Every command a changed-test-scope task ran. See [The `scope_runs` field](#the-scope_runs-field). |
| `fix_target` | Detail only. Where a request-changes review restarts, while a gate is pending. See [The `fix_target` field](#the-fix_target-field). |
| `agent_overrides`, `node_overrides`, `policy_override` | The item's overrides. `agent_overrides` and `policy_override` are `null` when the item has none, and `node_overrides` is `{}`. `PATCH` sets them: see [Changing a work item](/reference/http-api/work-items#patch-apiwork-itemsid). |

## Why the item stopped

### The `stop` field

`stop` is `{kind, node, resume_at, reason}` on the list. The detail adds `task`, `attempt` and `facts`. On a `cap` or `budget` stop it adds `limit`, and on a `budget` stop `scope`.

`facts.cause` names why an `infra` stop happened, when Kraft knows. [The `facts` field](/reference/events#the-facts-field) lists the values. The failed card chooses its action from it, and an `infra` stop without one reads as a generic infrastructure stop.

A `rate_limit` stop's `facts` also carries `fallback` and `fallback_allowed`: the stopped task's declared fallback [harnesses](/concepts/vocabulary#harness), and which of those its resolved policy still allows.

### `stop.kind`

`stop.kind` is one of twelve values: `gate`, `question`, `cap`, `budget`, `failed`, `conflict`, `mr_closed`, `config`, `infra`, `stuck`, `wait` and `rate_limit`. [Stop kinds](/reference/events#stop-kinds) says what each means, and [Why did my item stop?](/troubleshooting/why-did-my-item-stop#find-your-reason) gives each stop's reason with its fix.

A `needs_human` row saved before database migration 45 has no recorded kind. It reads the `kind` of its stop event, else `question` for a reason that starts `needs_context:`, `budget` where the event carries `budget`, `cap` where it carries `capped`, else `failed`. A `waiting` row with none reads `wait` and a `rate_limited` one `rate_limit`.

### `stop.limit`

A `cap` or `budget` stop on the detail also carries `limit: {path, key, value, maximum}` when a `PATCH` of the item's `policy` can raise what stopped it, and omits it when none can.

| `key` | What it caps | `path` |
|---|---|---|
| `max_attempts`, `timeout_minutes` | A [fix loop](/concepts/vocabulary#fix-loop)'s attempts or its clock. | The node id. |
| `time_cap_minutes`, `total_time_cap_minutes` | The work item's own cap. | `""` |
| `budget_usd` | On a `budget` stop, the item-wide policy dollar cap. | `""` |

`value` is the limit that stopped it, in attempts, minutes or dollars. `maximum` is the `maxima` ceiling or `null`.

Raise it with `PATCH /api/work-items/{id}` `{policy: {<key>: N}}` (item-wide) or `{policy: {paths: {<path>: {<key>: N}}}}`, then `POST /api/work-items/{id}/retry`.

There is no `limit` for:

- a `budget` stop on the item's own cap (`POST /api/work-items/{id}/budget/raise` raises that one), on a node, step or task's `budget_usd`, a `token_budget`, the daily cap or spend a harness never reported;
- a node, step or task's time cap;
- a gate's or wait's timeout;
- a `loops:` cap in `policy.yaml`;
- exhausted rate-limit retries;
- a fix loop whose bound the older `node_overrides` set.

### `stop.scope`

A `budget` stop on the detail also carries `scope`, the cap that stopped it:

| `scope` | The cap |
|---|---|
| `work_item` | The item's own dollar cap. |
| `usd` | A `budget_usd`, item-wide or on a node, step or task, or spend a harness never reported. `POST /api/work-items/{id}/budget/raise` takes `work_item` and an item-wide `usd`. |
| `tokens` | A `token_budget`. |
| `daily` | `budget.daily_usd`. |

## Tests and spend

### The `test_result` field

`test_result` is `{scopes: [{command, scope, passed, exit_code, session_id}], passed}`, or `null` when no scope has finished.

- One entry per scope, passed or failed. `scope` is `null` when the repo's table no longer declares the command, and `exit_code` when none was recorded. `passed` is true when every scope passed.
- An area's setup appears only when it failed.
- A scope still running is left out.
- No test counts.
- `session_id` is the scope's session. Read its log with `GET /api/worker-sessions/{id}/log`.

### The `budget_cap` field

`budget_cap` is `{cap_usd, source, key, spent_usd, daily}`.

- `cap_usd` is whichever cap stops the item first: the lower of its own cap and the item-wide `budget_usd` of its policy. It is `null` when neither is set. This holds in the API and in `kraft view show --json`.
- `key` says which cap it is, and the `PATCH` field that changes it: `budget_usd` for the item's own cap, `policy.budget_usd` for the policy one.
- `source` is `item` when the item itself set the reported cap, by its own `budget_usd` or by its own `policy` override, and `policy` when it comes from `policy.yaml` or the chain. So `source: item` with `key: policy.budget_usd` means the item's policy override.
- `spent_usd` is the item's own, all-time spend.
- `daily` is `{spent_usd, cap_usd}`: the instance's spend since local midnight against `policy.budget.daily_usd`, the same two numbers as `GET /api/budget/today`.

`POST /api/work-items/{id}/budget/raise` (`kraft item raise-budget`) raises whichever of the two caps stopped the item.

## Progress and the worktree

### The `summary` field

`summary` is a run's progress at a glance:

```json
{"nodes_done": 3, "nodes_total": 8, "gates_passed": 1, "step": {"index": 2, "count": 2} | null}
```

`nodes_done` and `nodes_total` count against the frozen chain. `gates_passed` is how many of the completed nodes carry a gate after them (`gate_after`). `step` is the current node's step (1-based) out of its own steps, read from its latest non-escalation session's task, when the node declares more than one, and `null` otherwise.

### The `progress` field

`progress` is `{current, total, title, tasks}`, or `null` when the item has no plan to follow. Each task is `{n, title, state, sha}`. `state` is `done`, `current` or `pending`, and `sha` is the short hash of the newest commit on the item's branch that names the task, or `null`. Rows on the list carry only `current`, `total` and `title`.

### The `worktree_exists` field

`worktree_exists` is whether `worktree_path` is a directory on disk. It is `false` before the item first runs and after its worktree was reclaimed or deleted.

`open-worktree`, `mr-labels` and the `viewed` routes answer `404` when the directory is missing. The message is "this work item has not started, so it has no worktree yet" for an item that never ran, and "this work item's worktree was removed from disk" for one that did. A retry or resume recreates the directory.

`diff` and `compare` check the item's `base_ref` first. Before the first run it is unset: `diff` answers `200` with an empty diff and `base_ref: null`, and `compare` answers `409`. With a `base_ref` set and the directory gone, both answer `404`.

### The `scope_runs` field

`scope_runs` lists every command a changed-test-scope task ran in its node's current pass, in the order each started, across rounds and repositories. Each entry is `{session_id, repository, round, command, passed, exit_code?, scope?, area?, setup?, order?, selected?, pending?, node_id, hook_point}`. The node's view draws its scopes from it.

- `passed` is `null` until the command finishes.
- A command its round picked that has not started yet comes last, `pending: true` with no `session_id`, while the node is still running.
- `round` is the session's fix-loop round, `0` for the first pass. `-1` is the repair an `on_failure` recovery runs inside a fix-loop node, and the re-measure after it.
- A retry starts a new pass, so the list keeps only the newest one.
- It is empty for a chain with no such task.

### The `fix_target` field

`fix_target` is `{gate, node, then, round}` while a gate is pending, and `null` with none pending.

| Key | Meaning |
|---|---|
| `gate` | The pending gate. |
| `node` | The node a request-changes review restarts at. |
| `then` | The nodes that run from there before the work returns to the gate. |
| `round` | The round a rejection now would start, `{n, max}`, counted against the cap the gate's reject loop already snapshotted. `null` when no cap applies. |

`GET /api/work-items/{id}/fix-target` answers the same shape for a target the reviewer picked: see [Fix target](/reference/http-api/budget-and-events#get-apiwork-itemsidfix-target).
