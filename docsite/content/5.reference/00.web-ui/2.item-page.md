An item's page shows one [work item](/concepts/vocabulary#work-item): its brief, its [chain](/concepts/vocabulary#chain) drawn as a graph, and an inspector for whatever you select. This page names the header's actions, the graph and the inspector's tabs, one heading for each part.

![An item's page: a banner reading Waiting for you to approve final review with a Review button, the chain drawn as a graph of named nodes with the final_review gate selected, the chain overview above it (a glyph per node, framed on the part in view), and the inspector on the right showing the gate's files, an open thread, and the Read kraft-cb59-review.md, Review gate, Approve and Request changes buttons](/assets/item.png)

## The page

An item's page, at `/work-items/<id>`, is under **Board › repo › item** in
the header: **Board** goes back to the board, and the repo opens the board
filtered to that repo. The page has:

- its title and brief at the top (**edit** changes the brief);
- the size of the change so far, with a **Review changes** link;
- a banner when the item needs you, such as **Waiting for you to approve
  spec** with **Review**, which opens the review page at that
  [gate](/concepts/vocabulary#gate) with the gate's brief beside the diff.

The line under the brief counts the changed files and, when there are any, the
open [review threads](/concepts/vocabulary#review-thread).

## The main action

Each state has one main action, and it sits next to the words that explain the
state: in the banner or the card under the brief. Only a state with no banner
or card keeps its main action in the header, as a button.

The header at the top right also shows the item's status, the **⋮** menu, and
how long the item has been going since its chain's first node started, so a
wait behind a dependency doesn't count. Before that it counts from the
filing, and once the item has ended it shows how long it ran.

| The item | Main action | Where |
|---|---|---|
| never started | **Start** | header |
| running or waiting | **Pause** | header |
| paused | **Resume**, which becomes **Resume with steer** once a steer is typed | the paused card |
| at a gate | **Review**, which opens the review page at the gate | banner |
| asking a question | **Send & resume**, or **Open thread** | the question card |
| stopped at a [cap](/concepts/vocabulary#cap) or a budget it can raise | **Raise cap**, which opens the editor for the limit the stop names, or Config's budget editor for the item's own dollar cap. A cap that names no limit offers **Open config**. [Which stop offers what](/reference/web-ui/cap-stops-and-raises#which-cap-stopped-the-item) | banner |
| a budget it can't raise, or an escalation running | **Retry** | header |
| [stuck](/concepts/vocabulary#stuck) or failed | **Retry from** the stopped task, with a steer box and a line saying what it restarts. A failed card lists the stop's causes or the last lines of the task's log | the state card |
| stopped on a rebase conflict | **Review the conflicts** | the state card |
| stopped because its MR was closed | **Reopen !N** | the state card |
| cancelled | **Duplicate as new item**, and **Archive** | the state card |
| done | **Archive**, under the outcome: the merge request, the changed files, spend against the cap and the time taken | the state card |
| archived | **Restore** | header |

The line under the brief counts the changed files and doesn't repeat the
**Review changes** link where the banner already offers the review.

An item that never started reads **NOT STARTED**, here and on the phone, never **Paused**.

### Folding a card

_Added in 2.1_

The state card, the paused card and the card listing what the item comes after
fold to their title line when you select it, and open the same way, here and in
[the board's side panel](/reference/web-ui/board#the-side-panel). In a node's
view they start folded, as the brief is hidden there, so the graph keeps the
room. A card you fold or open stays that way for the session, until the item
stops somewhere new.

## What an item comes after

_Added in 2.1_

An item filed to come after others lists them in a card under the brief while
any of them is unfinished: each one's status and its title, which opens that
item. On a [blocked](/reference/statuses) item the card is titled **Blocked**,
and Kraft starts the item when they have all completed.

**Unblock** stops the item waiting for the unfinished ones. The card offers it
on a blocked item, and on a paused or not-started one. A blocked item then
joins the queue within seconds. The same card is in
[the board's side panel](/reference/web-ui/board#the-side-panel).

## Header actions

The header has two menus, and some actions that ask before they act.

### The menus

A header button, where the state keeps one (**Start**, **Pause**, **Retry** after
a budget stop or an escalation, **Archive**, **Restore**), runs when you select
its name. Its **▾**, or the pointer resting on it, opens a menu over it with
that action first and then the others that fit the item's state:
**Escalate…**, **Mark complete…**, **Archive** and **Cancel…**.

Where the banner or card carries the main action, the header has no button and
the **⋮** menu ends with those same items. Each of them that asks for more
opens a card under the header.

The **⋮** menu holds **Review changes**, **Item settings**, **Open [worktree](/concepts/vocabulary#worktree) in
editor**, **Copy ID** and **Copy link**, and **Duplicate as new item** once
the item has ended.

Select the title to rename the item: **Enter** or moving focus away saves, **Esc**
cancels.

### Escalate…

**Escalate…** is offered only on an item stopped or paused after it started.
It isn't offered at a stop on a dollar or token budget (raise the cap first),
nor while an agent session is running on the item's pending gate, nor while an
escalation is already running.

Once the item has an escalation thread, it offers **Start a new thread** and
says what it changes: it continues the last thread, which remembers its earlier
turns, or starts a fresh one that doesn't see it.

### Mark complete… and Cancel…

Both say, before you confirm:

- what they stop (when something runs: the running attempt and how long it has
  run, whose work is lost);
- what they keep (the branch, the worktree, findings and the run log);
- what the status becomes.

## The chain graph

The middle of the page draws the item's chain, frozen when the item was filed,
[node](/concepts/vocabulary#node) by node. A box is an agent or a command (an exec node); a diamond is a
gate. Each node shows how it went and how long it took, and a gate that sends
work back draws a **reject** arc to the node it re-runs.

A node that ran more than once carries a **×N** badge: the most times any one
of its tasks ran, whether by a retry or a fix-loop round. A changed-test-scope
task counts its rounds, not the scopes in them. The badge is red on a node
stopped at its cap.

A task whose Claude Code agent has sub-agents carries a badge in the box's
top-left corner: how many run now, such as **2**, and a red **×** when one
failed, was stopped or was cut off.

Hover or focus the task, or select it, and a row
of marks comes out under it, one per sub-agent: a dot while it runs, a tick once it
finished, a cross when it didn't. Hover a mark for its name. Select it, or press
**↓** from the task and then **Enter**, to open [the sub-agent](#a-sub-agent)
in the inspector.

- Select a node to show it in the inspector.
- Double-click a node, or press **Enter** on it, to open its own view at
  `/work-items/<id>/nodes/<node>`, which draws the tasks inside the node.
  Above it, the whole chain is drawn small, as on
  [the chain overview](#the-chain-overview), with the node you are in ringed;
  select another node there to go to it. **← chain** goes back.
- Drag or scroll to pan. A chain no taller than the graph scrolls along, so a
  mouse wheel walks it left and right, and no pan takes the chain off the
  graph. Pinch or **⌘**-scroll zooms at the pointer. The controls at the bottom
  right zoom in and out, **Fit** the whole chain to the window (down to 30%: a
  longer chain than that still pans), and centre on the current node.
- The graph ends where the inspector starts, so no node is drawn under it. When a
  chain runs past an edge, a node the edge would cut through isn't drawn, and a
  button there counts the nodes past it, such as **+9**; select it to slide them
  into view.

### A slice group

_Added in next_

When a plan is [sliced](/concepts/how-a-work-item-runs#slices), the chain draws
its implementation and the nodes after it as one **slices** node, a box with a
second edge behind it. The words under it say where the group is: **shared
groundwork** while the item builds the tasks in no slice itself, how many slices
are done while they run, with one that needs you or failed on its own amber
line, and which slice the **join** replays.

Its own view, at `/work-items/<id>/nodes/slices`, draws the group's path:

- **groundwork**: the group's nodes, as the item runs them on the shared
  groundwork. Select one to show it in the inspector; double-click it, or press
  **Enter**, to open its own view, such as `/work-items/<id>/nodes/slices.implementation`.
- **slices**: one box per slice, in its own item's state. Double-click one, or
  press **Enter**, to open that item.
- **join**: the slices' commits replayed onto the item's branch, in slice order.

A plan with no shared groundwork draws none, and a group that runs without
splitting draws its nodes alone. The inspector gives the group's phase, its
groundwork tasks, each slice by name with its item's state, and the node after
the group. In the strip above a node view the group is one box like any other,
ringed while you are in it or in one of its nodes.

### The chain overview

_Added in 2.1_

A chain too long to read whole, wider than 800px at 100%, has the chain overview
above it: the whole chain drawn small on one line, always as wide as the graph or
less. Each node is a small box, a gate a small diamond, with no label and its
state shown: done, running, waiting on you in amber, failed or not started. A
frame marks the part of the chain the graph below shows.

- Select a node on the overview, or anywhere along it, to centre the graph there.
  Drag along it to slide the graph with you.
- The graph below takes the rest of the pane and draws every node at full
  size, by name, such as **approve spec**, not by ID. An edge with more of the
  chain past it fades.
- With the keyboard, **Tab** reaches the overview on the node the item is at,
  **←** and **→** move along it, **Enter** centres the graph on that node, **↓**
  moves to the node on the graph, and **↑** comes back up to the overview.
- **Fit** still fits the whole chain.

A chain that fits whole, such as `quick-task`, has no overview. The
[Chains](/reference/web-ui/templates-and-settings#chains) editor draws a long
chain the same way, with node IDs instead of names.

### Where the graph opens

Every item opens with its chain fitted to the graph, never smaller than 95%. A
chain too long for that opens on the node the run is at, with as much of what
comes next beside it as fits whole: up to the gate after the next one, else up
to the next gate, else the next node.

A finished item opens on its last node, and one that hasn't started opens from
its first node. Under the chain overview the edges fade; without it, the buttons
at the edges count the rest.

## The inspector

The panel on the right of the graph shows whatever you selected: the chain,
a node, a gate or a task. Its heading names it. **Collapse pane** at the top
right, or **Esc**, folds it away. **Esc** leaves it open while the cursor is in
a box that holds text, so the text isn't thrown away.

A [gate that is waiting](#a-gate-that-is-waiting) has a heading of its own.
The Config values [before the item starts](/reference/web-ui/config-before-start)
have a page of their own, as do a [node's fix loop](/reference/web-ui/fix-loops-and-test-scopes#a-node-with-a-fix-loop)
and a [changed-test-scope task](/reference/web-ui/fix-loops-and-test-scopes#a-changed-test-scope-task).

### The chain

| Tab | What it shows |
|---|---|
| **Overview** | the item's status, progress, the node it is at, the spec or plan attached when it was filed, what it has spent, the checkout an [in-place item](/guides/run/run-items-in-place) runs in, and its recent events |
| **Config** | its limits and overrides, as in the side panel on [The board](/reference/web-ui/board#the-side-panel). While the item can still take a draft, it says where to add a node or gate: the **+** on a connector in the chain |

While Claude Code sub-agents run, Overview adds a **sub-agents** row under **current**:
how many run, with their descriptions on a line below. Select the count to open the task that runs them.

In Overview, select an [attachment](/concepts/vocabulary#attachment)'s name to
read it, even before the item starts.

An item with a [one-off chain](/guides/day-to-day/file-a-work-item#file-with-a-one-off-chain)
that holds custom content shows a row, `one-off chain`, saying who approved it,
through which door and when, or that nobody has yet.

### A node

| Tab | What it shows |
|---|---|
| **Overview** | its progress, what runs next, what it spent and its steps, with **Retry** to re-run it once the item has stopped (not on the node a failed item stopped on: the state card has it) |
| **Config** | its settings |

A paused item offers **Resume** in Overview instead of Retry, and a running or
waiting one has no Retry. **Focus**, at the top right of a node's panel on the
chain, opens the node's own view. Selecting a step, or a step's task, opens that
view with it selected.

### A task

A task has the tabs **Overview**, **Input**, **Output**, **Log** and **Config**. The escalation task has a sixth, **Thread**, before them.

| Tab | What it shows |
|---|---|
| **Thread** | on the escalation task, first of its tabs: the conversation up to the turn you picked |
| **Overview** | the [harness](/concepts/vocabulary#harness) and model the attempt ran on, and the tokens and cost it spent. Claude Code sub-agents get a **Sub-agents** list by state, **Finished** folded; a row opens [that sub-agent](#a-sub-agent). _Added in next_ |
| **Input** | what the API keeps of what went in: the head commit, the fix-loop round it carries findings from (or "first pass"), the escalation thread, and a pending [steer](/concepts/vocabulary#steer) |
| **Output** | the session's own summary note, led by **wrote** on a task that writes a document |
| **Log** | the agent session's own log; **full screen** spreads it over the whole window, and **Esc** brings it back. With sub-agents, an **agent** menu shows one's lines; `?agent=` opens the log filtered. Colour codes aren't shown. _Added in next_ |
| **Config** | the attempt's own values, read-only: its path, model, attempt number and head commit. Before the item starts, [the draft's overrides](/reference/web-ui/config-before-start) |

A token figure reads as two parts when the run read from the prompt cache, such
as `40k new + 900k cached`. **cached** is what was read back from the cache,
which costs a fraction of fresh input; **new** is everything else: uncached
input, cache writes and output. Hover the figure for all four counts; the phone shows the two parts only.

Output is only known once a session ends, so **new** grows when it does. The same figure
is on a node's **Overview** and on the item's **Config** tab.

Two tabs show more on some tasks:

- **Overview on the task that implements the plan** also shows how far through
  the plan's sub-tasks (its `## Task N` headings) the work is, with the commit
  that finished each one and a link to the plan.
- **Output on a task that writes a document** (its `produces`, such as the work
  brief) leads with **wrote**, which opens that document, above the session's own
  summary note. It is on the newest attempt only, once that attempt is done,
  since each attempt rewrites the one file, and not on an escalation, a gate's
  `auto_review` or a [fix loop](/concepts/vocabulary#fix-loop)'s repair and judge.

### A sub-agent
_Added in next_

A Claude Code sub-agent opens a level under its task: from its mark on the
graph, its row in the task's **Overview**, or the **agent** menu on the
**Log**. The crumb trail ends at the task, and the subtitle gives the
sub-agent's type, status and how long it ran.

- **Overview** shows its tokens and tool uses, what it is running now or its
  answer once it finished, and the prompt it was given.
- **Log** shows only its lines of the task's log.

The task's crumb, **Esc** or **All** in the Log's menu goes back to the task.
The URL carries the sub-agent as `?agent=<id>`.

### A task that ran more than once

The subtitle under its name reads **attempt n of m ▾**. Select it for a menu of
every attempt, newest first, each with how it went and how long it ran, and pick
the one every tab shows.

The tabs follow the newest attempt as it starts. Pick an earlier one and they
stay on it, while the count shows the newer ones; pick the newest again to
follow.

On the escalation the menu counts turns, **turn n of m ▾**, as its **Thread**
tab does.

### What Esc does on the page

One **Esc** steps the page back one level, in this order:

1. Whatever is open over the page takes it first: the review, a picker, the
   escalation card, the full-screen log or a document.
2. Then the inspector folds.
3. Then a node's own view goes back to the chain.

A box that holds text, and an open menu or dialog, keep their own **Esc**. In a
[changed-test-scope task](/reference/web-ui/fix-loops-and-test-scopes#stepping-back-and-closing),
**Esc** first steps back from a scope to its task, and from the task to its box.
On [a sub-agent](#a-sub-agent), it first steps back to the sub-agent's task.

## A gate that is waiting

The panel of a waiting gate shows:

- the files changed so far;
- the open review threads;
- under **Concerns**, what a task said it doubted about its own work when it
  finished, since the last gate you decided;
- the document it decides on;
- where a rejection sends the work.

The facts under them are rows. **tests** appears once the item has a test
result, at any gate: `✓ 3 scopes` when every scope passed, or `✗ 1 of 3 scopes`
followed by each red scope as a link to its session's log. It sits above
**decides on**, **reject to** and **status**.

At the bottom:

- **Read** followed by the document's name opens it in a panel on the right
  (**full screen** widens it).
- **Review gate** opens the review page at this gate.
- **Approve** and **Request changes…** decide the gate.

### The gate's reviewer

_Added in 2.5_

A gate with an [`auto_review`](/guides/customize/add-review-agents) reviewer
draws it on the chain beside the gate, with a chip for its latest outcome:
**approve**, **reject**, **ready for you** or **could not decide**. A gate the
item hasn't reached yet reads **runs first when reached**.

When Kraft left a note on that outcome, the gate's panel shows it under
**Reviewer: ready for you** or **Reviewer: could not decide**, such as the
files a reviewer that checks first changed, which void its verdict.

## A failed item's card

_Added in 2.1_

The state card of a failed item gives the stop's reason, then up to three fact
rows, then its actions. **Retry from** and **Escalate…** come with every
failure, when the item admits them. What else the card offers depends on the
stop's `facts.cause`:

| The stop | The card adds |
|---|---|
| `forge_auth`, a refused forge login | Words, no button: sign the forge CLI in on the server's machine (`gh auth login`, or `glab auth login`), check git's credentials, then **Retry**. No setting in Repos can fix it. [The numbered fix](/troubleshooting/stop-reasons-in-detail#forge-authentication-fails) |
| `forge_auth` naming an API account (`facts.account`, `facts.source`) | Words, no button, by source: set the variable and restart Kraft (`env`), put a new token in the file, or fix the command or credential helper. Check with `kraft admin forge test`, then **Retry**. _Added in 2.5_ |
| `stranded`, a run a restart left behind, or any stop that isn't an infrastructure one | **Retry from** alone |
| any other infrastructure stop: `forge_unreachable`, `ci_infra`, `crash`, or one naming no cause | **Check the repo settings**, which opens the repo's entry under Settings › Repos, next to **Retry from** |

When a `forge_auth` stop carries `sso_url`, the forge wants the token authorised for single sign-on; on an API account the card names the account. The card ends its words with the address as a link: open it, authorise the token, then **Retry**. No fact row repeats it. The phone's card does the same, and the terminal console's banner prints the address.

A stop that names no cause and gives no reason of its own shows the last lines
of the task's log under the reason, with a link to the full log.

The fact rows:

- **work kept** answers "do I lose anything?": the branch, the number of files
  changed on it, and `tests passing` when the item's tests passed.
- **tests failed** lists each red scope's command with its scope and exit code.
- **why** says a cause in words: the forge couldn't be reached, the run was
  left behind by a restart, CI itself failed rather than the change, or the
  server stopped while it ran.
- **spent**, when the item has a dollar cap.
