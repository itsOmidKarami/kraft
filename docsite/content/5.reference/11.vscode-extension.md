## The status bar and the connection

The status bar shows a check mark beside `Kraft` while the extension is
connected and nothing waits on you, and `Kraft (read-only)` when the versions don't
match or the workspace is in [Restricted Mode](#in-restricted-mode).

While connected, the status bar also shows how many items in scope wait on you,
such as `Kraft 2`, the same count as the Needs you group. When something waits,
it shows a bell in place of the check mark on VS Code's warning background. It
leaves the number out when nothing waits.

While connected, hovering `Kraft` shows what Kraft has spent today against its daily cap, such
as "Today: $1.20 of $20.00" or "Today: $0.500 (no daily cap)". It reads the
figure on connect and again at most every 30 seconds while the board changes,
and leaves the line out when the server doesn't answer.

Select `Kraft` in the status bar for **Show Log**, **Open Web UI**, **Start
Kraft** (only while it is disconnected, and never when you are
[signed in to another machine](#signing-in-to-a-remote-kraft)), **Sign in to a
server…** and **Retry Now**. **Kraft: Show Log**
in the Command Palette opens the same log: it records each connect, disconnect
and retry with its delay, every request Kraft refused, and every command that
failed.

While the extension can't connect, hovering `Kraft` says why, and an empty
Kraft view shows one row:

| Row | Meaning | Selecting it |
| --- | --- | --- |
| `Kraft isn't running — Start` | Nothing answers at `kraft.url`. | Starts Kraft in the background: `kraft admin start --detach`, from `kraft.path`. |
| `Kraft refused the token — check kraft.url` | Kraft answered but rejected the token: `kraft.url` points at another Kraft, or the token changed. | Opens the `kraft.url` setting. |
| Kraft: sign in again | Kraft answered 401 to a session: it was signed out, or the password changed. | Runs **Kraft: Sign in to a server…**; the stored session is deleted. |
| `Kraft error: … — Show log` | Kraft answered with another error. | Opens the log. |

The extension retries on its own, waiting 1 second, then 2, 4 and so on up to
30 seconds between tries. **Retry Now** tries again at once.

**Start Kraft** runs from your home folder and shows "Starting Kraft…" until
Kraft answers, then connects. A Kraft that is already running is said so, and
the extension reconnects to it. When the binary isn't found, **Get Kraft**
opens the [install page](/get-started/install) and **Open Settings** opens `kraft.path`. Any other failure shows Kraft's own error, with the full
output in **Show Log**. Selecting it again while one start runs says `Kraft is already starting.`

## Which items the board shows

_Added in 2.1_

The board, the count on its icon and the notifications cover the repos of the
window's folders. A folder matches its repo the way Kraft matches it, so these
all show the repo's items:

- A subfolder of the repo.
- A symlinked path to it.
- A linked worktree of it.
- A submodule or nested repo under a connected repo.

A window opened on an item's worktree shows that item's repo.

Archived items sit under **Archived**, the last group, collapsed. Expand it to
list them, then right-click one, or select several, and run **Restore** to put
them back under Done. The group reads its items from Kraft when you expand it,
when the extension connects, and after an item is archived or restored. If that
read fails, the group shows one row saying why.

**Archived** shows only while the board has other items. When it has none,
restore from the Command Palette with **Kraft: Restore**, which lists the
archived items to pick from, or from the web UI.

**Show All Repos**, in the view's title bar, widens the board, the count and the
notifications to every repo Kraft has work in. **Show This Repo**, in the same
place while all repos show, goes back to this window's repos. Both are also in
the Command Palette.

The view's description says which it shows, "This repo" or "All repos", where
VS Code shows a description (not in a sidebar that holds only the board). While
Kraft is disconnected, the rows are the last it knew, and a line above them says
"Not connected · last known".

The choice is kept per workspace: reopen the folder, or reload the window, and
the board shows the repos it showed when you left it.

When this window's repos have no Kraft work, the view says "No Kraft work in
this repo." with **File Work Item…** and **Show all repos** links. With all
repos shown and no work in any, it says "No Kraft work yet, in any repo." with
the **File Work Item…** link.

When a folder's repo isn't connected to Kraft at all, the view says "This repo
isn't connected to Kraft." instead, after one sentence on what Kraft is and what a
gate is, with a **What is Kraft?** link to the docs and a **Connect this repo** link (also
**Kraft: Connect This Repo** in the Command Palette). It connects the repo with
the commands Kraft detects, and the board then reads the connected repos again.

To set the test or setup command yourself, connect from the web UI or with
`kraft repo connect`. Connecting from VS Code needs Kraft on this machine: when
`kraft.url` points elsewhere, neither the link nor the command is offered, and
you connect the repo from the web UI or with `kraft repo connect` on Kraft's
machine. A read-only window doesn't offer them either.

To work in an item's worktree, right-click the item and run **Open Worktree in
New Window**. It appears only while the item's worktree is on disk: not before
the item has run, and not once its worktree is reclaimed.

## Gate notifications and approval

_Added in 2.1_

When a gate opens, the notification names the item by its title and says what
the gate asks, such as "Design the caching layer: approve spec". A notification
for an item that failed or hit a cap or budget is a warning; a question or a
gate isn't.

When two or more arrive at once, as on startup or after a reconnect, one
notification says "3 items need you" instead, with **Next Gate** when a gate is
among them and **Show Board** to reach the rest.

Approving a gate whose document you haven't opened opens it instead ("Read the
spec on `<title>` first: the document is open."). A message then says what was
approved ("Approved: `<title>` · approve spec"), and where the item went when
Kraft already knows.

A gate that is followed by a merge or a push asks first ("Approve and merge
`<title>` into the target branch?", with an **Approve and Merge** or **Approve and
Push** button), whether you approve from the gate or by **Submit Review** with
the Approve outcome; every other gate is one step. Kraft sends no flag for
this, so the extension reads the item's chain: a `merge` or `push` node or task
between this gate and the next.

## Opening the config

_Added in 2.4_

**Open Config…**, the gear in the board's title bar or **Kraft: Open Config…**
in the Command Palette, lists the files in `$KRAFT_HOME/config` that exist,
each with a line on what it holds: configuration first (`policy.yaml`,
`harnesses.yaml`, `repos.yaml` and the rest), then templates (`library.yaml`
and each chain by its file name). Typing matches the file names and those lines, so
`budget` finds `policy.yaml`.

Pick one to open it; in a trusted workspace a chain opens with the **Show
resolved chain** lens above its first line.

`sandbox.yaml` and `detectors.yaml`, the two files only you write, are listed
under **Not created yet** until they exist. Picking one opens an unsaved editor
at its path, with a header linking its reference page and schema completion
already on; saving creates the file.

Other missing files aren't offered: the web UI's Settings writes most of
them, `kraft admin addon` writes `addons.yaml`, `kraft admin worker add`
writes `workers.yaml`, and `kraft admin forge add` writes `forges.yaml`. The last entry, **Open Config Folder in New Window**,
opens the folder. The whole command works in Restricted Mode, because it only
opens files.

## Signing in to a remote Kraft

_Added in next_

To use the board of a Kraft on another machine, run **Kraft: Sign in to a
server…** from the Command Palette or the status bar menu. It asks for the
server's address, filled in from `kraft.url`, then for its password.

- **The address.** `http` or `https`, with the host and port and nothing
  after: a path prefix such as `https://proxy/kraft/` is refused. The host is
  lower-cased and the port made explicit, so `HTTPS://Box/` and
  `https://box:443` are one server. A zone ID such as `%eth0` is refused.
- **An unencrypted password.** For an `http://` address to a host that isn't
  this machine, the extension first warns that the password crosses the network
  unencrypted and asks whether to go on. It asks on every sign-in, a Tailscale
  address included.
- **What it keeps.** The session goes in VS Code's secret storage under that
  address, and `kraft.url` is set to it in your user settings. The window then
  reloads and the board is the server's.
- **What the server shows.** The web UI lists the session as `Kraft for VS Code
  on <hostname>`. Sign it out there. It also ends when the password changes and
  expires after `session_expiry_days`.
- **The token stays home.** With a session the extension sends the session's
  cookie and never the `mcp-token`, including on the live-updates socket, and
  it follows no redirect.
- **A self-signed `https` server.** The error says the server's certificate isn't
  trusted. Set `NODE_EXTRA_CA_CERTS` to the file holding its certificate
  authority and restart VS Code.

When the server ends the session, the extension deletes it, shows "The server
ended this session." with **Sign in again**, and the status bar row reads **Kraft:
sign in again**. A refusal that the extension finds isn't the session's, such
as a proxy's, is retried as any failed connection is.

A user-level `kraft.url` that names another machine and holds no session keeps
working with the token, as before. The status bar tooltip then adds "Sign in to
use a session instead."

## What a signed-in window leaves out

_Added in next_

Some actions read or change this machine, and a window signed in to another
machine's Kraft refuses them, naming the server:

- **Start Kraft**, which would start a Kraft here.
- **Open Worktree in New Window** and **Review Changes**, which read the item's
  worktree on the server's machine. Review the diff in the web UI.
- Connecting a repo, and filing work from a file or selection.
- Config checks, schema completion, **Show Resolved Chain** and **Lint Template
  Library**, and **Open Config…**, which read config files on the server's
  machine.
- Repo scoping: no folder here belongs to the server's repos, so the board shows
  every repo and **Show All Repos** is hidden.

The documents, previews, gates, worker logs, search and the live board need
nothing local, and work as on the same machine. **Remote - SSH** is unchanged: a
window on a remote machine whose Kraft is on that machine needs no sign-in.

## Settings

| Setting | What it does |
|---|---|
| `kraft.url` | Where Kraft listens. Empty reads `KRAFT_HOST` and `KRAFT_PORT`, then `bind` and `port` from `access.yaml`. Set in your user or Remote settings only. **Kraft: Sign in to a server…** sets it to the address you signed in to. |
| `kraft.path` | The `kraft` binary **Start Kraft** runs. Empty runs `kraft` on your `PATH`; a leading `~` means your home folder. Set in your user or Remote settings only. |
| `kraft.notifications` | `all`, `gates` or `off`: `all` notifies when an item needs you or fails, `gates` only when a gate opens. Pausing an item yourself never notifies. |

## In Restricted Mode

_Added in 2.1_

In a workspace you haven't trusted, the extension runs read-only. The board,
gate documents and **Review Changes** work. Every action, from Approve to
**Submit Review** and **Start Kraft**, shows "Kraft is read-only in Restricted
Mode: trust this workspace to act." The status bar item reads
`Kraft (read-only)`, with the reason in its tooltip.

Config checks, schema completion, **Show Resolved Chain** and **Lint Template
Library** start once you trust the workspace, with no reload.

## If the extension is read-only

The extension works with a Kraft of its own major release and at least its
minor: the 2.0 extension needs Kraft 2.0 or a later 2.x. Against any other, it
turns read-only. The board still updates, every action is disabled, and its
status bar item reads `Kraft (read-only)`.

| The extension | The server | The fix |
|---|---|---|
| 2.0 | 1.4 | [Upgrade from 1.4](/guides/run/upgrade-from-1-4#update-from-14). |
| 1.4 | 2.0 | Update the extension. |

### An extension newer than Kraft

- When it connects, it shows a warning that says which to update, and the status
  bar item's tooltip repeats it: against a 1.4 server, "This extension (2.0.0)
  needs Kraft 2.0 or later; this server runs 1.4.0. Update Kraft. Actions are
  disabled until they match."
- When you then try an action, it shows "Kraft is read-only: this server's
  version doesn't work with this extension. Hover Kraft in the status bar to see
  which one to update."

VS Code updates the extension on its own, so after a new major release this is
what you see until you [update Kraft from 1.4](/guides/run/upgrade-from-1-4#update-from-14).

### An extension older than Kraft

The rule holds the other way too: an extension from 1.4, one whose updates are
off or that you pinned, is read-only against a 2.0 server. The 1.4 extension
has no tooltip and says less. When it connects, it shows `Kraft 2.0.0 does not
match this extension (1.4.0); actions are disabled until they match.` When you
try an action, it shows `Kraft is read-only: the daemon's version does not match
this extension.` Update the extension as well.
