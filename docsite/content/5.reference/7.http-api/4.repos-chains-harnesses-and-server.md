The board's routes for connecting a repo, chain templates, harnesses, changes saved but not applied, the update check and editors; like the other board routes they can change in any release, as [Work items](/reference/http-api/work-items) says. Routes written here without the `/api` prefix are relative to it, as [Other routes](/reference/http-api#other-routes) explains.

## Connecting a repo

- `GET /api/repos` answers the connected `repos` and `workspaces`, and `suggested`: the git checkout the server was started in, when it is one and not connected yet, else `null`. The first-run board offers it as the path to connect.
- `POST /api/repos/probe` (`{path, detect?}`) reads a repository and changes nothing. With `detect: false` it answers only what needs no detector table: the resolved `path`, `name`, `branch`, submodules, beads and forge.
- `POST /api/repos` connects it, answering `409` for a repo already connected before reading anything else, and `422` for a repository with no commit yet.

The probe takes a `test_command` too, and answers the proposal connecting with it would save. A `test_command` or `setup_command` in the body
replaces the proposal, and `""` declares none (a `test_command` of `""` is a repo
with no tests, which may be enabled). Both answer with the proposal's
evidence beside the entry. None of it is stored in `repos.yaml`:

| Field | Meaning |
|---|---|
| `candidates` | Every command the evidence supports: `{dir, role, command, tier, source, marker, detector, family, corroborated, chosen}`. `role` is `test` or `setup`; `tier` is `runner`, `ci`, `toolchain` or `devenv`; `dir` is `""` for the root; `chosen` marks the proposal. |
| `scopes` | One `{dir, test, setup}` per directory the proposal covers, root first, with commands as they run from inside that directory. |
| `missing_setup` | Directories with a test command and nothing to prepare them (`.` for the root), so `setup_command` is left undeclared. |
| `test_markers` | The file each proposed test command came from. |
| `read_from` | The commit read: `refs/remotes/origin/HEAD`'s target, `refs/remotes/origin/main` or `HEAD`, or `null` for a repo with no commit (read from its working copy). |
| `missing_tools` | Programs a proposed command runs that the server's `PATH` does not have, one `{dir, tool}` each: a work item fails on them until they are installed. |
| `stopped` | Why no test command was proposed, one `{dir, reason, detector}` per directory that stopped it (`.` for the root): a `pyproject.toml` with no lockfile, or a root project with no test command found beside nested ones. Empty when nothing stopped. |

A `detectors.yaml` that does not load answers `400`, naming it, and so does a probe that runs past two minutes. The probe runs in a process of its own with that limit, so a repository's files cannot stall the server. A few probes run at once; `POST /api/repos/probe` past that answers `429`. `POST /api/repos` given both a `test_command` and a `setup_command` connects a repo the probe fails on, with those, and says why in `probe_failed`. See
[Detectors](/reference/configuration/repos/detectors).

## Chain templates

These board routes read the chains the Templates editor shows.

| Route | Answers |
|---|---|
| `GET /api/templates/chains` | Every chain: `id`, `description` (or `null`), `nodes`, `gates`, `error` and `uses`. A chain that does not resolve still has its `description`, with `nodes` empty and `error` saying why. |
| `GET /api/templates/chains/{id}/resolved` | `{id, chain, task_paths, steering, nodes, documents}`. `documents` maps each gate id to the document kinds the exec nodes before it produce, in chain order: what that gate's `artifact` can name. |
| `GET /api/templates/library` | `{file, text, components}`. See [The library answer](#the-library-answer). |
| `GET /api/templates/library/{ref}` | One component, shaped as in [the library answer](#the-library-answer), by its `id` or a bare name no other section shares. `404` when nothing matches; `409` naming each `id` when two sections share the bare name. |
| `GET /api/templates/steering/preview?chain=&task=&repo=` | `{sections: [{kind, source, text}]}`: what the agent task at canonical path `task` of chain `chain` reads at launch in the repository whose `name` or `path` is `repo`, section by section in launch order. See [The steering preview answer](#the-steering-preview-answer). |

Each entry of `nodes` carries `icon`, the node's own [icon](/reference/chain-nodes#icons)
name, or `null` when it sets none (always for a gate).

### The library answer

`GET /api/templates/library` answers `{file, text, components}`. Each component has:

- `id` (`tasks.implementer`).
- `kind` (its section).
- `name`.
- `definition` as written.
- `issues`.
- `used_by` (the ids of the chains that use it).
- `used_by_paths: [{chain, path, overrides, via?}]`: each component of a chain that extends or selects it. `path` is that component's canonical path, `overrides` whether it sets any key besides `id`, `extends` and `kind`, and `via` the library node it reaches the chain through, when it sits in that node's own definition (`{chain: "default", path: "verification.review.code_review", overrides: false, via: "verification"}`).

### The steering preview answer

`kind` is one of:

- `contract`.
- `document` (`source` is the kind it produces).
- `review_package`.
- `skill` (`source` is the skill).
- `intent` (`source` is the repository's `intent_dir`).
- `steering`.
- `usage`.

There is one `steering` section per profile: the repository's first, then the task's, with `source` `repo:<profile>` or `task:<profile>`.

Joined, the texts are the launch's context. Per-launch values are placeholders (`<work item id>`, `<session id>`, `<title>`, `<task instruction>`), and nothing launches.

An unknown chain, task or repository answers `404`, and a task that is not an agent task answers `422`, as does a task whose harness, skill or steering cannot resolve. A `repos.yaml` that does not load answers `503`.


## Harnesses

The harness routes. The web UI edits harnesses through a draft (`/api/drafts/harnesses/...`); these read the published state.

| Route | Answers |
|---|---|
| `GET /api/harnesses/profiles` | `{profiles, agent_profiles, file, error}`. See [The harness profiles answer](#the-harness-profiles-answer). |
| `GET /api/harnesses` | One entry per provider: `{id, label, executable, executable_found, efforts, models, capabilities}`. `executable_found` is whether the command is on `PATH` now. There is no `version`. |
| `GET /api/harnesses/providers` | Each provider's capability surface. A provider also lists `efforts` and `models`: the plain-word values it limits that option to, `[]` when it takes any string or a pattern. |

### The harness profiles answer

- Each entry of `agent_profiles` has `id`, `used_by`, `chains`, `fallback`, `model` (provider → model id) and `providers` (provider → `{model, effort}`). `effort` is the one effort every provider shares, or `null` when they differ: read `providers` then.
- `problems` is the list of messages, and `problem_details` the same list as `{profile, provider, field, message}`, where `field` is `model`, `effort`, or `null` for a profile that isn't defined.
- Each `fallback` entry has its own `problems` and `problem_details`.

## Saved but not applied

`GET /api/apply` answers what is saved and not running yet:
`{restart: [{id, file, text}], reload: [{id, file, text, problem?}], managed}`, both lists empty when
nothing is pending. `managed` is true when a service manager started this server, the only case
`POST /api/apply/restart` can restart it.

- A `restart` item is `access.bind` or `access.port`: `access.yaml` names an address the server is not bound to.
  It is left out when `KRAFT_HOST` or `KRAFT_PORT` is set, since the environment wins and a restart would change nothing.
- A `reload` item is `disk:<file>` for `library.yaml`, `chains/*.yaml`, `policy.yaml` or `intake.yaml` whose bytes
  differ from the ones last loaded. A file rewritten with the same bytes is no change. `problem` is the first
  problem found in the file as it is on disk.

`POST /api/apply/reload` rereads the library, `policy.yaml` and `intake.yaml` (and replaces the intake poller),
and answers the new `GET /api/apply`. `POST /api/templates/reload` does the same. A policy or an
`intake.yaml` that does not load is refused and stays pending, with its `problem`, and the
running one is kept. `POST /api/templates/reload` answers `{valid, invalid_templates,
refused_policy, refused_intake}`, the last two each the refusal's reason or `null`; `kraft admin
reload` prints them and exits 1 on either.

`POST /api/apply/restart` restarts the server when a service manager started it (the
launchd or systemd unit `kraft admin install-service` writes). It answers `202` and runs
`kraft admin restart` detached.

A server started from a terminal answers `409`
`{"detail": "started from a terminal: restart it there"}`. Nothing restarts the server
unless this is called.

The restart ends the agent of every active item, and each stops as
failed until it is retried, as `kraft admin restart` warns: see
[A restart ends running agents](/guides/run/upgrade-kraft#a-restart-ends-running-agents). The web
UI counts the active items from `GET /api/work-items` (the rows whose `status` is `active`) and
shows the number in its confirmation.

The `apply_changed` live message says when this list changes.

## Update check

`GET /api/update?channel=` answers `{installed, latest, channel, python, behind, checked_at}`; `python` is the interpreter the server runs on, as `3.14`.
`channel` is one of `stable`, `rc`, `beta` and `alpha` (`400` otherwise) and defaults to
the installed version's own; it is not stored. The answer comes from the daily
cached check. `POST /api/update/check?channel=` skips the cache and asks the
release feed now, and answers the same shape.

When the feed cannot be reached, `latest` and `behind` are `null`: unknown, not "up
to date". `checked_at` is the time of the last check that succeeded on that channel
(`null` when there has been none), so it can be old while `latest` is `null`. Installing
the update is `kraft admin update`; the server never does it.

## Editors

`GET /api/editors` answers `{available, system, default}`:

- `available` lists
  the editors (`code`, `cursor`, `zed`, `obsidian`) whose executable this
server's machine has on its `PATH`, or, on macOS, whose app is installed in
`/Applications` or `~/Applications` (it is then opened with `open -a`).
- `system` says whether the system opener
(`open`, `xdg-open`) is there.
- `default` is `editor` from `theme.yaml`,
else `KRAFT_EDITOR`, else `null`.

It is loopback only, as
`POST /api/documents/{id}/open` is: any other caller gets `403`.

`POST /api/work-items/{id}/artifact/open` opens the pending gate's document in the item's worktree (`GET /api/work-items/{id}/artifact` carries its `absolute_path`), and `POST /api/work-items/{id}/artifacts/{kind}/open` a task's document of that kind, with the same rule.

These routes and `POST /api/work-items/{id}/open-worktree` take `{editor}`: a name from `available`, `"system"` for the system opener, or `null` (or nothing) for the `default` above, else the system opener.
