title: Events
description: Every event type on a work item's timeline, its key payload fields, and the notification webhook that sends them.
---

Kraft records what happens to a [work item](/concepts/vocabulary#work-item) as a list of events, its timeline. This page lists every event type, grouped as the contents list shows, and the notification webhook that sends them.

Every event has these fields:

| Field | Meaning |
|---|---|
| `seq` | The event's number on the timeline. |
| `work_item_id` | The item it belongs to. |
| `type` | One of the types below. |
| `payload` | A JSON object. Each type's key fields are in its row. |
| `node_id` | The [node](/concepts/vocabulary#node) the event is about, or `null` for an item-level event (filing, a pause, a bulk action). It comes from the payload's `node_id` or `node` key. A [gate](/concepts/vocabulary#gate)'s own events carry it under `gate`. |
| `created_at` | When it happened. |

Before 2.0, an event carried no `node_id` of its own. The upgrade filled it only from a payload's `node_id` or `node` key, so a gate's older events in an upgraded database keep `null`: they named their node under `gate`.

Read the events with `kraft view events`:

| Command | What it shows |
|---|---|
| `kraft view events ID` | The whole timeline. |
| `kraft view events ID --type gate_requested` | Only the events of that type. |
| `kraft view events ID --after 120 -f` | Only the events after `seq` 120, then follows the timeline. |
| `kraft view events ID --json` | The raw events. |

The tables list each type and the payload fields you are most likely to use.
A payload can carry more fields than these. Event types and payloads are not a
[stable interface](/project/status-and-support#versioning-and-stability): a
release can add, rename or reshape them.

| `work_item_attachments` | The item is filed with a spec or plan. | `attachments` |
| `work_item_resumed` | A paused item starts or restarts. | `steer` |

| `work_item_storage_held` | A start was queued because worktrees are over `storage.worktrees.limit`, not because a slot was busy. Written once each time the item is queued. | `used_bytes`, `limit_bytes` |

| `paused_by_broken_base` | Another item broke the [base branch](/concepts/vocabulary#base-branch), so this one paused. | `broken_by`, `follow_up_bead` |
| `work_item_needs_human` | The item stopped for a person. See [below](#work_item_needs_human). | `node_id`, `reason`, `kind` |
| `work_item_waiting` | The item is parked on an external wait. | `node_id`, `retry_at` |
| `work_item_rate_limited` | The agent hit a rate limit; the item retries on its own. | `node_id`, `retry_at` |
| `work_item_retried` | Someone retried the item. | `node_id`, `steer`, `escalated` (an [escalation turn](/concepts/vocabulary#escalation-turn) retried it) |

| `work_item_title_edited` | The title changed. | `title` |
| `work_item_description_edited` | The description changed. | `description` |
| `plan_progress` | A [worker](/concepts/vocabulary#worker) started a plan task. | `node_id`, `task`, `total`, `title` |
| `steer_context_set` | A [steer](/concepts/vocabulary#steer) was stored for the next agent. | `steer` |
| `steer_undelivered` | A steer was stored but no agent received it. | `steer` |

### `work_item_archived`

| Field | Meaning |
|---|---|
| `by` | `you` or `auto`. |
| `reason` | `storage` when automatic clean-up archived it for the worktree limit. Absent otherwise. |
| `kept_branch`, `unpushed_commits` | Present when the branch stayed because it has commits nowhere else. |
| `rescued_branch`, `rescued_commits` | Present when commits on a detached HEAD were kept on a new branch. |
| `worktree_kept` | The reason, when that branch could not be made and the [worktree](/concepts/vocabulary#worktree) stayed. |

### `work_item_needs_human`

This is the event behind `stop_reason` in `kraft view show --json`, and behind
"why did it stop" on the board. Its fields:

| Field | Meaning |
|---|---|
| `node_id` | The node the item stopped on. |
| `reason` | What stopped it, in words. A reason that starts `needs_context:` is a question from the agent. |
| `kind` | Why, as one of nine values. See [Stop kinds](#stop-kinds). |
| `session_id` | The last session of that node, when it failed or asked a question. `kraft view logs` reads its log. |
| `capped` | `{cycles, attempts}` when a [fix loop](/concepts/vocabulary#fix-loop) spent its attempts. |
| `budget` | `{scope, spent_usd, cap_usd}` when a spend [cap](/concepts/vocabulary#cap) stopped the item. |
| `stuck` | `true` when the item stopped in a way an escalation turn can answer. |
| `bundle` | What Kraft gathered about a [stuck](/concepts/vocabulary#stuck) item when it gave up. |
| `suggested_action` | `{action, reason}`, the next step Kraft suggests. |
| `facts` | Detail that depends on the stop, when there is any. See [The `facts` field](#the-facts-field). |

### Stop kinds

`kind` is also the value `stop.kind` takes on the [HTTP API](/reference/http-api/work-item-object#stopkind). [Why did my item stop?](/troubleshooting/why-did-my-item-stop) gives each stop's fix.

| Kind | Meaning |
|---|---|
| `question` | An agent asked for context it needs (`needs_context:`). |
| `cap` | A loop or time cap ran out: a fix loop's attempts, a time cap, a gate's rejection cycles, a wait's timeout, or rate-limit retries. |
| `budget` | A spend cap, in dollars or tokens, refused the next launch. |
| `failed` | A task failed, a changed-test scope ran red, or a read-only node changed the worktree. |
| `conflict` | A merge or rebase conflict the conflict handler could not clear. |
| `mr_closed` | Someone closed the item's merge request. |
| `config` | The chain, the repo's configuration or a gate's document cannot run as it stands: a task that could not start, a missing base branch, a chain that changed under the [walk](/concepts/vocabulary#walk). |
| `infra` | Kraft or what it depends on failed: a crash, git, the [forge](/concepts/vocabulary#forge), CI infrastructure. `facts.cause` says which. |
| `stuck` | A loop stopped making progress: the same findings across cycles, a [judge](/concepts/vocabulary#judge)'s ruling to stop, or a repair that doubts itself. An escalation turn can answer it. |

`stop.kind` takes three more values. They come from the item's status, not from this event:

| Kind | Meaning |
|---|---|
| `gate` | The item waits at a pending gate (a `gate_requested` event). |
| `wait` | The item is parked on an external wait: CI or a review. |
| `rate_limit` | An agent rate limit holds the item, and it retries on its own. |

### The `facts` field

What `facts` carries depends on the stop:

| Stop | `facts` carries |
|---|---|
| A `conflict` stop | `resolved` and `unresolved`: the files the handler cleared and the ones still conflicted (`git diff --diff-filter=U` in the worktree). |
| A closed MR | Its ref and url. |
| A `failed` stop on a red changed-test-scope run | The first failed command's `command`, `scope`, `exit_code` and `session_id` (`area`, and `setup: true` for an area's setup), and every failed one under `failed_scopes` when more than one went red. |
| A stop whose cause Kraft can name | `cause`: see below. |

On an `infra` stop, `cause` is one of:

- `crash`: the executor task crashed.
- `stranded`: a claim that no walk took over.
- `ci_infra`: CI infrastructure failed and retrying did not recover it.
- `git`: the worktree refresh failed.
- `forge_auth`: the forge refused the credential.
- `forge_unreachable`: the forge could not be reached.

For `forge_auth` and `forge_unreachable`, the git or forge error says so. A forge task's own failure carries one of these two the same way, on its `failed` stop, or on its `infra` one in a node with a fix loop. Other `infra` stops name no cause.

| `beads_left_open` | The item completed but its issues in [beads](/concepts/vocabulary#beads) stayed open. | `beads`, `reason` |

### `sweep_failed`

Kraft could not commit the work because:

- the commit failed;
- the worktree was not on the item's branch;
- the worktree held a git operation Kraft did not start; or
- the worktree held a repository Kraft did not create.

### `sweep_left_out`

After an agent task, Kraft commits the work the task left, but not the installs the repo's setup made. The event names the paths it left out. It is written only when that set differs from the item's last `sweep_left_out`, not after every task.

Kraft leaves out:

- a lockfile the repo's setup command wrote and nobody changed since (`uv sync` in a repo that commits no `uv.lock`);
- a virtualenv or `node_modules` the repo does not ignore. A `node_modules` the setup command made counts whatever is in it: bun leaves no marker.

Kraft commits, as the agent's work:

- a lockfile the agent writes, or an edit it makes to the setup's;
- a `node_modules` the setup did not make with no package manager's marker in it (`.package-lock.json`, `.modules.yaml`, `.pnpm`, `.yarn-integrity`, `.yarn-state.yml`), even beside a `package.json`;
- a `pyvenv.cfg` with no `python` beside it.

## Reading events as they happen

### `WS /api/ws/events`

Streams every work item's events as they are stored. The board and `kraft view watch` read it. Unlike [`GET /api/work-items/{id}/events`](/reference/http-api/budget-and-events#get-apiwork-itemsidevents), it is not limited to one item. It first replays the stored events after `after_seq`, then sends each new event once, with none lost or repeated between the two.

| Query | Type | Default | Meaning |
|---|---|---|---|
| `after_seq` | integer | `0` | Replay every stored event with a greater `seq` first. `0` replays the whole timeline of every item, so reconnect with the last `seq` you saw. |
| `live` | boolean | `false` | `1` or `true` also sends [live messages](#live-messages). |

Each frame is one JSON text message. An event frame has the fields in the table above, `{seq, work_item_id, type, payload, node_id, created_at}`. A live message has `{"frame": "live", "type", "payload", "created_at"}` and no `seq`.

A client authenticates as for the HTTP routes: [who may call](/reference/http-api#who-may-call). A peer on this machine needs nothing while Kraft is bound to loopback. Otherwise send the MCP bearer token as `Authorization: Bearer <token>`, or the session cookie from the login page. The trigger token is not accepted. The `Host` and `Origin` rules of the HTTP routes apply too.

| Refusal or close | When |
|---|---|
| `403` on the handshake | Kraft refused the connection before accepting it. See below. |
| Close code `1011` | The client fell behind: more than 1000 messages were waiting for it. Reconnect with `after_seq` set to the last `seq` you read. |

A refused connection closes before it is accepted, so a real client sees the handshake fail with HTTP `403`, not a close frame. A test client reports it as close code `1008`. The causes are no valid credential, a remote caller while no password is set, a `Host` that is not allowed, and an `Origin` from another site.

## Live messages

A client of [`WS /api/ws/events`](#ws-apiwsevents) that connects with `live=1` also receives messages
that are not events. They are `{"frame": "live", "type", "payload", "created_at"}`,
have no `seq`, are sent once to whoever is connected and are neither stored nor
replayed after a reconnect. A client that does not ask for them never sees one.

| Type | When | Key fields |
|---|---|---|
| `intake_checked` | An [intake](/concepts/vocabulary#intake) poll found a bead ready, started an item or left one alone. A poll that found nothing sends none. | `id`, `at`, `ready`, `started`, `skipped` |
| `apply_changed` | What is saved but not applied changed: a draft was published, a reload or an access save ran, or a file was edited on disk (checked every 5 seconds). Not sent when the pending items are the same. | `restart`, `reload` (how many of each; see `GET /api/apply`) |

## Notifications

`notify.yaml` sends an HTTP `POST` to a webhook when an event you name
happens. Set it on the Settings screen, or edit the file:

```yaml [config/notify.yaml]
enabled: true
url: https://hooks.example.com/abc123   # a secret; Kraft never shows it back
base_url: https://kraft.example.com     # where links in the message point
events: [gate_requested, work_item_needs_human]
```

[notify.yaml](/reference/configuration/notify) lists the fields, and what `events` accepts. [Get notified when an item needs you](/guides/day-to-day/notifications) sets it up.

The body is JSON:

```json
{
  "work_item_id": "<work-item-id>",
  "title": "Fix the flaky login test",
  "type": "gate_requested",
  "gate": "spec_approval",
  "url": "https://kraft.example.com/work-items/<work-item-id>"
}
```

`gate` is `null` for an event that is not about a gate.

- Kraft sends at most one message per work item every 10 seconds. A second
  matching event in that window sends nothing.
- A send that times out after 5 seconds, errors, or gets a status of 400 or
  more is tried once more after 2 seconds. If that fails too, Kraft records a
  `notification_failed` event on the item.
- Events that happen while the server is down send nothing when it comes back.
- The Settings screen's **Send a test** posts `"type": "test"` with a `null`
  `work_item_id` and `gate`.
