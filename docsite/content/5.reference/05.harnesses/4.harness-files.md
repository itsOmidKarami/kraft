title: Harness definition files
description: "The YAML file that describes one harness: the capabilities it declares, argv fragments, constraints and allowlists."
---

A [harness](/concepts/vocabulary#harness) file maps Kraft's capabilities onto one CLI's flags. This page lists the fields of that file and the sixteen capabilities it can declare.

```yaml [config/harnesses/mytool.yaml]
id: mytool
kind: cli
command: [mytool]
capabilities:
  prompt:  { cli: ["-p", "{value}"] }
  context: { channel: prompt }
  usage:   { source: result_file }
  model:   { cli: ["--model", "{value}"] }
  effort:  { cli: ["--effort", "{value}"], values: [low, high] }
```

A file in `$KRAFT_HOME/config/harnesses/` with the same name as a shipped harness overrides it. A file with a new name adds a harness. That directory isn't seeded on first run, so it exists only once you put a file in it. To write one, follow [Add or override a harness](/guides/harnesses/adding-a-harness).

## Required fields

| Field | Type | Default | Meaning |
|---|---|---|---|
| `id` | string | required | Must match the file name without `.yaml`. |
| `kind` | string | required | `cli` or `acp`. _Added in next_ |
| `command` | string or list of strings | required | The argv prefix, such as `[mytool]`. |
| `capabilities.prompt` | mapping | required | A `cli:` argv fragment. |
| `capabilities.context` | mapping | required | `channel: prompt`, or `channel: system_prompt` with a `cli:` fragment. |
| `capabilities.usage` | mapping | required | `source: result_file`, or `source: envelope` with the name of a `reader:`. |

## Capabilities

Every capability other than `prompt`, `context` and `usage` is optional. A task or a `harnesses.yaml` [harness profile](/concepts/vocabulary#harness-profile) that sets an option whose capability the file omits is rejected when the chain or `harnesses.yaml` loads (`kraft admin templates lint` shows it). A repository's `models:` entry that does is refused at launch, naming this file.

A task's YAML never names a CLI flag. It asks for a capability, and the harness file maps it to whatever the CLI calls it.

| Capability | Kind | Meaning | Shipped on |
|---|---|---|---|
| `prompt` | Required, sent | The task's instruction. | all seven |
| `context` | Required, sent | Kraft's context for the session. `channel: system_prompt` is out of band; `channel: prompt` folds it into the prompt text. | all seven; `system_prompt` on `claude` and `codex` |
| `usage` | Required, read back | The session's tokens and cost, from the result file or from the log. | all seven |
| `structured_log` | Sent | The flag that makes the CLI write the log a `reader:` parses. | all seven |
| `model` | Sent | The model. | all but `amp` |
| `effort` | Sent | The reasoning effort. On `amp`, its mode (`-m`). | `claude`, `codex`, `antigravity`, `amp` |
| `permission_mode` | Sent | The CLI's approval or [sandbox](/concepts/vocabulary#sandbox) mode: `--permission-mode` on Claude, `-c sandbox_mode=` on Codex, `--approval-mode` on Gemini, `--auto-review` or `--force` on Cursor. | all but `amp` |
| `deny_tools`, `allowed_tools` | Sent, or enforced by a hook or rules | The task's tool lists. See [Constraints and alternate bindings](#constraints-and-alternate-bindings). | all but `gemini` and `antigravity` |
| `restrict_tools` | Sent | The CLI's own flag for which built-in tools exist. See [Allowlists](#allowlists). | `claude` |
| `approval_channel` | Sent | Hands the CLI's permission asks to Kraft's MCP permission tool. | `claude` |
| `resume` | Sent | Continues an earlier session by ID. | all but `gemini` |
| `autocompact` | Filled by Kraft | The CLI's own context auto-compaction. Kraft sets it on an [escalation turn](/concepts/vocabulary#escalation-turn). | `claude` |
| `rate_limit_signal` | Read back | Tells Kraft a launch was rate-limited. See [Fallback and escalation](/reference/harnesses/fallback-and-escalation). | `claude`, `codex`, `opencode`, `antigravity` |
| `writable_dirs` | Filled by Kraft | Directories outside the [worktree](/concepts/vocabulary#worktree) that the [worker](/concepts/vocabulary#worker) must write. See [`writable_dirs`](#writable_dirs). | `codex` |
| `mcp_config` | Filled by Kraft | The CLI's MCP servers for a sandboxed launch with `network:`. See [`mcp_config`](#mcp_config). | `claude` |
| `extra_mcp_config` | Filled by Kraft | MCP servers added to the CLI's own, for an in-place agent working in a copy of your checkout. See [`mcp_config`](#mcp_config). _Added in 2.5_ | `claude` |

Two capabilities need no argv: `usage` and `rate_limit_signal` describe what Kraft reads back, so they are legal with no `cli:` binding.

### writable_dirs

Kraft fills `writable_dirs` for a launch, and a task never sets it. It lists the directories outside the worktree that a worker must write:

- the session's `out/` folder, which holds the launch's `$KRAFT_RESULT_PATH` and its summary (`$KRAFT_HOME/run/items/<work item id>/sessions/<session id>/out`). Never the session folder itself, which holds the log and exit code Kraft trusts;
- the item's `docs/` folder, where it writes a document it was asked for (`$KRAFT_DOCS_DIR`);
- the worktree's git common dir, where every commit writes. For a linked worktree that is the main checkout's `.git`. Kraft asks git for it (`git rev-parse --git-common-dir`) and leaves it out when git has none.

`{value}` is one JSON array of absolute paths, such as `["/home/me/.kraft/run/items/ID/sessions/SID/out","/home/me/.kraft/run/items/ID/docs","/home/me/src/app/.git"]`, with the work item's ID for `ID` and the session's for `SID`. A harness that doesn't declare `writable_dirs` gets nothing extra.

Only Codex confines its writes to a list it can be given, so only it declares `writable_dirs`. Every other shipped harness writes the result file, its summary and `docs/` outside the worktree the way it always wrote the result file: Claude through the [permission gate](/reference/permissions), OpenCode through its `external_directory` ask, which `--auto` approves, and the rest under a permission mode that doesn't confine a path.

An escalation thread started before one folder per item keeps the grant it started with, `$KRAFT_HOME/run/results`, until it ends.

Codex binds it to `-c sandbox_workspace_write.writable_roots={value}`. Its `workspace-write` sandbox writes only the workspace and `/tmp`, so without the grant a Codex worker on a default install (`~/.kraft`) could write neither its result file, its documents nor a commit. Kraft grants these directories outright, because Codex's automatic reviewer isn't relied on for any of them.

### mcp_config

Kraft fills `mcp_config` only for a [sandboxed](/reference/configuration/sandbox) launch with `network:`. It is the CLI's MCP servers as one JSON object:

```json
{"mcpServers": {"kraft": {"type": "http", "url": "http://kraft/mcp"}}}
```

That is Kraft's own server for the session, reached through the sandbox's route out, because the MCP server registered on your machine is out of the container's reach. Claude binds it to `--strict-mcp-config --mcp-config {value}`, so that server is its only one and its `approval_channel` tool is answered there.

Kraft fills `extra_mcp_config` for an [in-place](/guides/run/run-items-in-place) agent that works in a throwaway copy of your checkout. It holds the servers Claude keys by your checkout's folder, which the copy's folder doesn't get: your local-scope servers for it, and `kraft` from its `.mcp.json`.

`{value}` is the path of a file holding them in the same shape, which only your user can read, because a server's settings can hold a token. Claude binds it to `--mcp-config {value}`, so they load beside the servers that load anywhere.

A harness file of your own that lacks `extra_mcp_config` can't hand the copy anything. When `kraft` is registered for the repo (at local scope or in its `.mcp.json`), Kraft refuses that launch and says what to add. With `kraft` registered anywhere else, the launch goes ahead without your local-scope servers.

## ACP entries
_Added in next_

A harness with `kind: acp` is an agent that speaks the [Agent Client Protocol](https://agentclientprotocol.com) over its stdin and stdout. It has no `capabilities:`, because the agent tells Kraft what it offers when a session starts. The file goes in `$KRAFT_HOME/config/harnesses/`, like any other harness file. Kraft never installs an agent or a bridge: the agent's program must already be on the worker's `PATH`.

[Claude over ACP, compared](/reference/harnesses/claude-over-acp) shows two example entries, `claude-acp` and `opencode-acp`, to copy. [`kraft admin acp-probe`](/reference/cli/admin#probe-an-acp-agent) runs one session against an entry and checks what it declares.

| Field | Meaning |
|---|---|
| `command` | The agent's argv in ACP mode, **a list** such as `[opencode, acp]`. A bare string is one word and doesn't run. `kraft admin doctor` and `min_version` target this command. |
| `reports` | What the agent sends: `tokens`, `cost`, both or neither. A cap Kraft can't count against it refuses the launch. See [ACP agents](/reference/harnesses/cost-reporting#acp-agents). |
| `options` | Maps Kraft's `model` and `effort` to the agent's session config option ID (`model: { config: model }`). |
| `asks_everything` | How to make the agent ask before every tool call: `env` (set for the agent only), `config` (session config options) or `mode`. Kraft applies it on **every** launch, with or without a tool policy. |
| `tool_names` | Maps the agent's tool `name`, else its `kind`, to Kraft's bare tool names. A name it doesn't list passes through as itself; a kind it doesn't list, and `other`, name no tool. |
| `always_deny` | Tools the client rejects whatever the task's policy. They count as a tool policy. |
| `settles_itself` | Kraft tool names the agent runs without asking. A task whose policy denies one refuses to start. |
| `network`, `credentials`, `min_version` | As for a `kind: cli` file. |

At `initialize` Kraft learns the rest from the agent: whether it can resume a session or load one, whether it takes a system prompt, and which config options it offers. `kraft admin doctor` shows them in an `acp: <id>` row.

### What a launch on an ACP harness refuses

This release runs an ACP agent on the server's own machine, with no sandbox. A launch that asks for more stops before the agent starts, as `could not start ...`.

| The reason says | Why | Remove |
|---|---|---|
| `permission_mode` | A `permission_mode` is a `kind: cli` harness's own mode. An ACP agent's asking is its entry's `asks_everything`. | The mode, at the layer that sets it. |
| `named grant(s)` | The task holds a grant *and* a limit that denies `Bash`. A grant matches a shell call's text, which over ACP is only the agent's description. | The grant or the limit. A grant with no such limit isn't refused: an escalation turn, which carries the default git grants, still runs unless the task's limit denies `Bash`. |
| `declares no asks_everything` | The task holds a tool policy, and Kraft can't make this agent ask before each call. | The policy, or add `asks_everything` to the entry. |
| `cannot tell them apart` | One `tool_names` key covers several Kraft tools that the policy treats differently. | Treat them alike, or map each by its own `name`. |
| `runs <tool> without asking` | The entry's `settles_itself` names a tool that the policy denies or leaves out of an allowlist. | The denial, or the tool from the allowlist. |
| `ACP part 3` | The launch is in a sandbox or on a remote machine. | The sandbox, or the remote machine. |

An ACP harness can't be a `fallback:` target, so a rate limit never switches to one.

### How a tool limit is held over ACP
_Added in next_

A task's `allowed_tools` and `deny_tools` hold on an ACP harness, or the launch refuses with a reason (the table above).

- Kraft makes the agent ask before every tool call, by `asks_everything`.
- Every ask goes to Kraft's permission gate as this session, on Kraft's tool names, resolved through `tool_names`.
- The client answers `allow_once` or `reject_once`, never an `always` option.
- A gate that can't be reached, or can't read the task's policy, rejects.
- Under an allowlist, an ask Kraft can't name (a `kind: other` call with no `name`) is rejected.
- A deny list holds only for tools the entry's `tool_names` maps, or that the agent already names in Kraft's terms (`Bash`, `Read`). A name the entry doesn't map passes through as itself, so `deny_tools: [Bash]` doesn't stop an agent whose shell tool is called `shell` until `tool_names` maps `shell` to `Bash`.
- An agent may end its turn when Kraft rejects a tool (OpenCode does). Kraft then prompts the same session again, naming the tool and the gate's reason and saying it isn't available, and the task goes on without it. It does this up to three times per launch, and a pause still ends the launch at once. Past that the launch ends `config_error` with `the agent ended its turn after Kraft rejected <tool> (<limit>) <N> times`.
- Without a tool policy, the client answers `allow_once` and logs it.

The **backstop** is detection after the fact, not prevention. A call that completes, or ends `failed`, without an allowing ask, and that the policy doesn't allow, ends the session as `config_error` with `tool policy violated: ...`. A tool the entry lists under `settles_itself` isn't flagged.

While an ask waits, the log gets a `heartbeat` line every minute, so `idle_s` doesn't fire. The gate's 5 s cap means it rarely does.

### How a launch ends

A **pause** signals the whole process group. The agent gets the interrupt as well as Kraft's `session/cancel`, and may exit before it answers. The pause still lands, and the usage the log already holds is counted.

A refused option, a missing agent program and a missing login stop as `config_error` or `failed`, as the client logs them. A call that completed without an allowing ask, and that the policy doesn't allow, ends the session `config_error`, with the reason `... stopped: tool policy violated: ...`, never `done`. An agent that dies on a bad flag before any session exists ends `failed` with its own exit code.

A session adopted after a server restart shows `failed` where it would have shown `config_error`.

## Capability keys

These keys sit under a capability.

| Key | Type | Default | Applies to | Meaning |
|---|---|---|---|---|
| `cli` | list of strings | `[]` | any invocable capability | The argv fragment. See [Argv fragments and placeholders](#argv-fragments-and-placeholders). |
| `via` | string | unset | `resume`, `deny_tools`, `allowed_tools` | Binds the capability to something other than a flag: `command_resume`, `permission_hook` or `permission_rules`. See [Constraints and alternate bindings](#constraints-and-alternate-bindings). |
| `values` | list of strings | `[]` | any capability with a value | A closed vocabulary the CLI itself would reject, as `re.fullmatch` patterns. Codex's `effort` is `minimal, low, medium, high, xhigh`; Claude's is `low, medium, high, xhigh, max`. |
| `always` | string or list of strings | unset | any capability | The value Kraft uses when nothing else is supplied. Gemini's `permission_mode` is `yolo`, since a headless worker has nobody to answer an approval prompt. |
| `under_allowlist` | string | unset | `permission_mode` | The mode a launch runs in under `allowed_tools`. See [Allowlists](#allowlists). |
| `channel` | string | unset | `context` | `prompt` or `system_prompt`. |
| `source` | string | unset | `usage` | `envelope` or `result_file`. |
| `reader` | string | unset | `usage`, `rate_limit_signal` | The name of one of Kraft's [log readers](#log-readers). |

## Optional top-level keys

| Key | Type | Default | Meaning |
|---|---|---|---|
| `command_resume` | string or list of strings | `[]` | The argv prefix for a resume, when it differs from `command` (see [below](#constraints-and-alternate-bindings)). |
| `permission_hook` | string | unset | The translator (`cursor` or `codex`) for a capability bound `via: permission_hook`. |
| `tool_names` | mapping | `{}` | Maps the CLI's tool names to Kraft's (`Shell: Bash`). |
| `unhooked_tools` | list of strings | `[]` | Kraft tool names that never reach the hook (`[WebFetch, WebSearch]`). A launch whose policy would have to deny one is refused. |
| `permission_rules` | string | unset | The renderer (`opencode` or `amp`) for a capability bound `via: permission_rules`. |
| `config_dir` | mapping of `env` and `files` | unset | The CLI's config-directory variable (`env:`) and the JSON files Kraft writes into that directory before each launch (`files:`). |
| `launch_env` | mapping of strings | `{}` | Variables set on every launch of the CLI, over a repository's `env:`. The shipped `claude` sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS: "1"`, so neither a Bash command nor a sub-agent runs in the background. _Added in next_ |
| `network.requires` | list of strings | `[]` | The hosts the CLI itself reaches (`[api.anthropic.com]`). Kraft adds them to the `runtime` allow list of a sandbox with a [network policy](/reference/configuration/sandbox/network-policy), but not to a [Kit](/reference/configuration/sandbox/kits), which lists its own. Checked as network-policy hosts when the file loads. |
| `proxy_aware` | boolean | `true` | `false` for a CLI that ignores `HTTP(S)_PROXY`. Under a network policy its only route is Kraft's proxy, so Kraft refuses such a harness before launch. |
| `credentials` | list of mappings | `[]` | How Kraft's egress proxy can hold each credential the CLI reads. See [credentials](#credentials). |
| `min_version` | string | unset | The oldest release (`N.N.N`) of the CLI this file's argv works with. See [min_version](#min_version). |
| `container_permission_mode` | string | unset | The `permission_mode` a launch gets under Kraft's [Docker sandbox](/reference/configuration/sandbox), unless it chose a mode other than the capability's `always:`. For a CLI whose own sandbox can't start in a container (`codex`: `danger-full-access`). Checked against `permission_mode`'s `values:` at load. |

### credentials

The shipped `claude`, `codex` and `gemini` files declare credentials:

| Harness | Variable | Header | Host |
|---|---|---|---|
| Claude | `ANTHROPIC_API_KEY` | `x-api-key` | `api.anthropic.com` |
| Claude | `CLAUDE_CODE_OAUTH_TOKEN` | `Authorization: Bearer` | `api.anthropic.com` |
| Codex | `CODEX_API_KEY` | `Authorization: Bearer` | `api.openai.com` |
| Gemini | `GEMINI_API_KEY` | `x-goog-api-key` | `generativelanguage.googleapis.com` |

Codex's variable is `CODEX_API_KEY` because `codex exec` doesn't send an `OPENAI_API_KEY`. The `ANTHROPIC_API_KEY`, `CODEX_API_KEY` and `GEMINI_API_KEY` pairings work in a Docker and a Podman sandbox. Kraft hasn't confirmed the `CLAUDE_CODE_OAUTH_TOKEN` pairing.

Each credential declares:

- `env`
- `service`
- `sentinel`: the value the container sees instead (shaped like a real key where the CLI may check).
- `inject`: a list of `domain`, `header` and optional `format` (`Bearer %s`).

The rules:

- Each `domain` must be one of `network.requires`.
- `phase` and `source` are a repository's to set, and refused here.
- Kraft uses a declaration only for a variable a repository lists under [`sandbox.credentials`](/reference/configuration/sandbox/credentials).

### min_version

Each launch runs `<command> --version` (in the image, when sandboxed) and refuses an older one by name. An answer with no version in it lets the launch go ahead.

The shipped `opencode` needs `2.0.0`: npm's `opencode-ai` 1.x refuses `--standalone` and `--log-level error`, so install 2.x from opencode.ai or Homebrew's `anomalyco/tap/opencode-v2`.

### Log readers

The `reader:` in a `usage` or `rate_limit_signal` capability names one of Kraft's log readers: `claude-stream-json`, `codex-json`, `cursor-stream-json`, `opencode-json`, `amp-stream-json` or `antigravity-stream-json`. A reader reads the log, so the file must also declare `structured_log`.

## Argv fragments and placeholders

A capability needs a `cli:` argv fragment unless it is `usage` or `rate_limit_signal`, or it is `context` with `channel: prompt`, which Kraft folds into the prompt text. `{value}` and `{csv}` are the whole placeholder language: `{value}` is one substituted string and `{csv}` a comma-joined list.

Kraft builds the command line in the order the capabilities are declared. A capability whose fragment is a bare `{value}` (a positional argument) must be declared last.

## Constraints and alternate bindings

- `values:` is a list of `re.fullmatch` patterns. A value outside them fails at load, not at launch.
- `always:` is the value Kraft uses when a binding supplies none. For a list capability, Kraft merges it with what a binding supplies. Kraft checks it against `values:` too.
- `resume` can bind `via: command_resume` instead of `cli:`, when a resume needs its own command prefix. `codex.yaml` uses `command_resume: [codex, exec, resume, "{value}"]`.
- `deny_tools` and `allowed_tools` can bind `via: permission_hook`: no flag, and Kraft's pre-tool hook enforces the lists. This needs a top-level `permission_hook:` naming the translator (`cursor` or `codex`), and `tool_names:` mapping the CLI's tool names to Kraft's (`Shell: Bash`).
- The same two capabilities can bind `via: permission_rules`, for a CLI with no hook. A top-level `permission_rules:` names the renderer (`opencode` or `amp`) that writes the tool lists into the CLI's own permission config at launch. A policy name that no CLI tool maps to refuses the launch.

## Allowlists

A launch whose policy sets `allowed_tools` (an empty list included) must not let a tool outside the list run. A harness meets that in one of three ways:

- It declares `restrict_tools` (the CLI's own flag for which built-in tools exist, such as Claude's `--tools`) and a `permission_mode` with an `under_allowlist:` mode that asks the approval channel about everything else (Claude's `manual`). A harness missing either refuses to launch under an allowlist, and so does a launch whose own `permission_mode` differs from that mode.
- It has a `permission_hook`, which denies every tool the list doesn't name, fail-closed.
- It has `permission_rules`, which deny every tool the list doesn't name.

## Checking harness files

`kraft admin doctor` runs one `PATH` check per harness profile that the live library's chains select, not every declared one. It adds a failure row for any harness file that failed to load. For an ACP harness it adds an `acp:` row and an `acp-cost:` row: see [Doctor failures](/troubleshooting/doctor-failures#agents-and-registration).
