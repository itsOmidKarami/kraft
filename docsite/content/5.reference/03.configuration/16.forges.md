_Added in next_

`forges.yaml` names forge accounts. An account records which forge a host runs and its web address, so `kraft repo connect` stops asking about a self-hosted host whose name does not say which forge it is. The file does not exist until you write it, and without it nothing changes.

```yaml [config/forges.yaml]
accounts:
  corp-gitlab:
    forge: gitlab                 # github | gitlab
    web_url: https://code.corp.example/gitlab
    default_for_host: true        # repos on this host use it unless they name another
  acme-gh:
    forge: github
    web_url: https://github.com
```

An account that talks to the forge's API names where its token comes from:

```yaml [config/forges.yaml]
accounts:
  corp-gitlab:
    forge: gitlab
    client: api                   # api | cli
    web_url: https://code.corp.example/gitlab
    ca_file: /etc/ssl/corp-ca.pem # optional
    default_for_host: true
    token: { from: git-credential, kind: unknown }
  acme-gh:
    forge: github
    client: api
    web_url: https://github.com
    token: { from: file, file: ~/.kraft/secrets/acme-gh, kind: pat }
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `forge` | `github` or `gitlab` | required | The forge the account is on. It must agree with the `forge` of each repo that uses it. |
| `client` | `cli` or `api` | `cli` | How Kraft talks to the forge. `cli` keeps the sign-in of `gh` and `glab`, and refuses `token` and `ca_file`. `api` reads a token from the source `token` names. |
| `web_url` | `https://` address | required | The forge's web address. A trailing `/` is dropped. `http://` is refused. |
| `api_url` | `https://` address | derived | The API address. It must have `web_url`'s origin (host and port), except `api.github.com` for `github.com` and `api.SUBDOMAIN.ghe.com` for `SUBDOMAIN.ghe.com`. |
| `token` | mapping | `from: git-credential` | An `api` account only. Where the token comes from, and its kind. See the tables below. A bare string is refused: the file never holds a token. |
| `ca_file` | path | none | An `api` account only. A PEM file of certificate authorities to trust for the forge, for a private CA. |
| `default_for_host` | `true` or `false` | `false` | Repos on this web host use the account unless their entry names another. Only one account may be the default for a host. |

An unset `api_url` is `https://api.github.com` for github.com, `https://api.SUBDOMAIN.ghe.com` for a `ghe.com` host, `https://HOST/api/v3` for another GitHub host, and `WEB_URL/api/v4` for GitLab.

## Where the token comes from

`token.from` names one source, and the one key that source needs. Any other key is refused.

| `from` | Key | What it stores and where it runs |
|---|---|---|
| `git-credential` | none | Nothing. Kraft runs `git credential fill`, asked by host only, and never prompts. It reuses what your git helper holds. |
| `command` | `command` | Nothing. Set only with `kraft admin forge` or connect's option [3] on the server's machine, or by hand: never over HTTP. The command runs without a shell and its stdout is the token. Wrap a pipe in `sh -c`. |
| `env` | `env` | Nothing. The variable is taken out of the server's environment when it starts, so a change needs a restart. |
| `file` | `file` | The token, in one file only you can read. The path starts with `/`, `~/` or `$`. A pasted token (`--token-stdin`) goes to `secrets/NAME` under Kraft's home. |

A `file` path may use `~` and `$VAR`; an unset variable is refused, naming it. The file is refused when it is a symlink, is not owned by the user the server runs as, or has any group or other permission bit. It is also refused inside a connected repo, a worktree, a `sandbox.expose` root, `/etc`, or a system directory every sandbox mounts.

A sandboxed worker never sees the file. A host (unsandboxed) worker runs as the same user as the server, so it can read the file.

An `env` name may not be one Kraft needs: `KRAFT_*`, `GIT_*`, `PATH` and the other variables every child gets, or `ANTHROPIC_API_KEY` and the other credentials Kraft passes to agents.

`token.kind` says what the token is. Every kind is sent as `Authorization: Bearer`.

| `kind` | Meaning |
|---|---|
| `pat` | A personal or project access token. |
| `oauth` | An OAuth access token. |
| `unknown` | The default. Kraft does not say what it is. |

## The origin rule

`api_url` must be on `web_url`'s origin: the same host and the same port, where no port means 443. An `api_url` on another port is refused. The two exceptions are `api.github.com` for `github.com` and `api.SUBDOMAIN.ghe.com` for `SUBDOMAIN.ghe.com`, where both addresses must be on 443.

## Git push and fetch over HTTPS

On an account with `client: api` and a `command`, `env` or `file` token, git push, fetch and the git-lfs upload to an `https://` remote at the account's address send the token in a header set for that one call. It is never written to `.git/config` and no hook sees it. The user name is `x-access-token` on GitHub and `oauth2` on GitLab.

`git-credential` accounts and SSH remotes are unchanged: git asks its own credential. So do `addons/repo_library.py` and the git-lfs downloads at checkout.

A push follows the account the item is pinned to. A fetch follows the account configured now. A push URL on another address is refused, and so is a push when any one of several push URLs is. Kraft never sends the token there.

A base fetch the token cannot authenticate stops the item and names the account, instead of starting from a stale base. Redirects are never followed with the header: a redirect stops the item, and the fix is to point `origin` at the new address. The stop card still shows the token hint.

For these calls `http.sslVerify` is forced on and `GIT_SSL_NO_VERIFY` is ignored. `ca_file` does not apply: git's own `http.sslCAInfo` does, so a gitconfig with `sslVerify false` needs the CA there instead. `GIT_TRACE` variables are removed and trace2 is switched off.

Kraft pins the header, redirects, `sslVerify`, proxy and resolve settings for the exact URL git dials as well as for the origin. A key scoped to that URL in `.git/config` does not override them, but one scoped to a deeper path would.

## Which account a repo uses

A repo uses the account its `repos.yaml` entry names with `forge_account`. Otherwise it uses the account marked `default_for_host` for the host of its `origin` remote, when that account's `forge` is the repo's `forge`; a default for another forge is skipped, and doctor says so. Otherwise it uses the CLI as before.

Hosts compare in lowercase, without a port or a trailing dot. An SSH alias such as `github-work` is not the account's host, so a repo with one names its account itself.

## A file that does not load

A file that does not load is refused when the server rereads it: the running accounts are kept, `/health` reports `degraded` with `invalid_forges`, and `kraft admin doctor` names the file and the key, or for a file that is not valid YAML, the line and column. `kraft admin reload` rereads it.

A file that does not load when the server starts leaves no accounts to keep. Items already pinned keep their pins.

Every repo not yet pinned stops at its next forge node, until the file loads and a person retries it: with ``forges.yaml does not load (<why>); fix it, then a person's `kraft item retry` ``, or for a repo that names an account, `forge_account <name>: forges.yaml does not load (<why>)`. Its forge reads, labels and merge request calls are refused the same way. A missing file is not this case: it means no accounts.

`invalid_forges` also names a repo whose `forge_account` names no account, or an account on another forge. A save that fixes it clears it.

## How Kraft talks to GitLab over the API

On a `client: api` GitLab account, Kraft runs every forge node and forge read over GitLab's REST API with the account's token. It does not run `glab`. It works on gitlab.com and on a self-hosted GitLab on any domain or path.

The project comes from the repo's push URL as configured: `remote.origin.pushurl`, else `remote.origin.url`, before any `insteadOf` rewrite. An `https://` URL loses the path prefix of `web_url`, so `https://code.corp.example/gitlab/group/sub/app.git` is the project `group/sub/app`. An SSH URL keeps its path. An `https://` push URL on another host than the account's is refused, without quoting it.

Kraft reads each account's token once and keeps it in the server's memory. A request answered `401` reads the token again and retries once, only if it changed. An `env` source is never read again, so a new value needs a restart. `kraft admin reload` clears the cache, and so does saving an account in Settings.

Each item uses the backend and account its first forge node pinned, and each repo of a workspace is run from its own pin. A repo pinned to `glab` keeps running `glab` under a workspace root on an API account.

A failed job's log is read as its last part: a log past the size cap keeps its end. A very large log can still time out, and the item's log route then answers 502. Jobs of a pipeline are read a page at a time, so one with up to 1,000 jobs is no longer cut short, on either backend.

## GitLab versions

Kraft reads the server's version for the last two calls. For recent merged merge requests it does not: it asks for `merged_at` and, on a `400`, asks again sorted by `updated_at`.

| Call | Newer GitLab | Older GitLab | Version unreadable |
|---|---|---|---|
| Recent merged merge requests | `order_by=merged_at`, from 17.2. | Sorts by `updated_at`, after a `400`. | Same as either, by the answer. |
| Merge when the pipeline passes | `auto_merge`, from 17.11. | `merge_when_pipeline_succeeds`. | `auto_merge`, as `glab` sends it. |
| Cancel an auto-merge | `cancel_auto_merge`, from 19.5. | The deprecated cancel endpoint. | The deprecated endpoint. |

## How Kraft talks to GitHub over the API

On a `client: api` GitHub account, Kraft runs every forge node and forge read over GitHub's REST and GraphQL APIs with the account's token. It does not run `gh`. It works on github.com, on GitHub Enterprise Server and on `ghe.com`.

The repository comes from the repo's push URL as configured, before any `insteadOf` rewrite, and is exactly `owner/name`. Any other path, such as `a/b/c`, or an `https://` URL on another host than the account's, is refused without quoting the URL.

On Enterprise Server, GraphQL is at `https://HOST/api/graphql`.

A job log lives in GitHub's storage, so GitHub answers its request with a redirect. Kraft follows that one `https` redirect without the token or GitHub's headers, and refuses a second. A failure there names the storage's host, never the signed address, and is not read as a token problem. The redirect and the download share one timeout, so a log read takes no longer than a single call.

The download trusts the system's certificate authorities and the account's CA together: its `ca_file`, else git's `http.sslCAInfo`.

### What the token needs

A classic personal access token needs the `repo` scope. A fine-grained one needs access to the repository, with the permissions GitHub lists for the REST endpoints Kraft calls: see [Permissions required for fine-grained personal access tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens). Kraft reads and writes pull requests, labels, check runs, commit statuses and Actions job logs.

An organization with single sign-on refuses a token until you authorize it. The stop names the account and carries the address of GitHub's authorize page; open it, authorize the token, then retry.

A workflow's `GITHUB_TOKEN` or a GitHub App installation token can run items, but it is not a supported kind. The probe asks `GET /user`, which GitHub answers `403` to such a token, so `kraft admin forge test` reports it as forbidden and `/health` stays `degraded`.
