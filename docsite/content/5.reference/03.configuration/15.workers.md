_Added in next_

`workers.yaml` lists the machines Kraft may run steps on. A machine is another computer with the agent CLIs installed and `kraft` on its `PATH`. A connected machine runs the steps that work items place on it.

```yaml [config/workers.yaml]
workers:
  gpu-box:
    ssh: gpu-box              # ssh mode: a host or an ~/.ssh/config alias
    capacity: 2               # sessions at once; default 1
    repos: [kraft, infra]     # optional; left out means every connected repo
    give_up_after: 2h         # default 2h; "never" turns the limit off
  home-server:
    token_sha256: "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
```

`kraft admin worker add` writes this file for you. The file does not exist until the first machine is added.

| Field | Type | Default | Meaning |
|---|---|---|---|
| `ssh` | string | unset | Ssh mode. A host, `user@host` or an ssh config alias that Kraft's server dials. |
| `token_sha256` | string | unset | Dial-in mode. The SHA-256 of the machine's token, as 64 lowercase hex characters. `worker add` writes it; the token itself is never stored. |
| `capacity` | integer, 1 or more | `1` | How many sessions the machine may run at once. |
| `repos` | list of names | every connected repo | Limits the machine to these repos. See [Naming a repo](#naming-a-repo). |
| `give_up_after` | `30s`, `90m`, `2h`, `1d` or `never` | `2h` | How long a step waits for the other side before it is given up, on the server and on the machine. See [When the server is gone](#when-the-server-is-gone). |

Each machine sets exactly one of `ssh` and `token_sha256`.

## Names

A machine's name is 1 to 39 lowercase letters, digits, `-` or `_`, starting with a letter or digit. `local` and `any` are refused: they are placement words, not machines.

## Naming a repo

An entry in `repos` matches a connected repo by its `id`, its `name`, or the last part of its `path`. A name that matches no connected repo is refused when you save the file in Settings or add the machine with `worker add`. A hand edit that names one is shown as a problem on the pending reload.

## Two ways to connect

### Dial-in

The machine opens a connection to the server, so it works behind a NAT and needs no inbound port. This is the default mode: `kraft admin worker add NAME` with no `--ssh` registers one.

1. Run `kraft admin worker add home-server`. It prints a token once, and the command to run on the machine.
2. On the machine, run `kraft admin worker serve --server URL --token TOKEN`. It redials by itself after a drop, a refusal or an unreachable server, until you stop it.

The server must be reachable from the machine. That means binding it beyond loopback with a password, as in [Remote access](/guides/run/remote-access).

The connection route is `/api/workers/connect`. It is exempt from the login cookie: the machine proves itself with its token and nothing else. It still obeys the rest of the perimeter, so a server with no password refuses a peer that is not local, token or not.

Kraft speaks plain WebSocket, so TLS is your reverse proxy's job. Put the `https://` address in `--server`.

The token appears in the process list on the machine, because it is on the command line. Treat that machine as trusted with it. To rotate, remove the machine and add it again.

### Ssh

The server dials the machine with `ssh HOST kraft admin worker serve --stdio` and redials when the connection ends. Nothing runs on the machine until the server connects.

Kraft uses the server process's own `ssh` and its own `~/.ssh/config`. A server started by `launchd` or `systemd` may not reach your SSH agent, so give it a key file with no passphrase prompt, or an agent socket it can see. The connection runs with `BatchMode=yes`, so it never asks for a password. `kraft` must be on the remote machine's non-interactive `PATH`.

`kraft admin worker add NAME --ssh HOST` saves the machine, connects once and prints the result. A failed connect leaves the machine saved and exits 1, because a machine that is asleep or not yet reachable is still worth registering.

A machine that connects over ssh keeps its state in a small background process, the machine daemon, so a step outlives the ssh session that started it. The first connection starts it, detached, and later ones reuse it. It listens on a unix socket in `$KRAFT_HOME/remote`, which only the machine's user can enter, and logs to `$KRAFT_HOME/remote/daemon.log`.

The daemon exits after ten minutes with no connection and no unfinished step. After an upgrade, the first connection from the newer Kraft retires the older daemon as soon as it holds no step. A dial-in machine does not use it: `serve --server` is already a long-running process.

## When a machine is offline

`kraft admin worker list` shows `offline:` and the reason.

| Reason | What it means |
|---|---|
| `never connected` | Nothing has dialled in, or the server has not connected yet since it started. |
| `refused: invalid token` | The token does not belong to any machine. It was removed, rotated or mistyped. |
| `refused: incompatible protocol: ...` | The machine and the server speak different protocol versions. The reason names both, with each side's Kraft version. Update the older one. |
| `disconnected: ...` | The connection ended, or the other side was silent for 60 seconds. |
| `ssh: ...` | The server's `ssh` ended before the machine answered. The reason is the last of what `ssh` printed, such as `Permission denied (publickey)`. |
| `could not run ssh: ...` | The server could not start `ssh` at all. |

`kraft admin doctor` shows each offline machine as a warning with the same reason. For an ssh machine it is the server's own attempt, not your shell's, so a failure there that your terminal does not show points to the SSH agent.

A second connection from a machine replaces the first. A machine that is removed, or whose `ssh` or `token_sha256` changes, loses its connection at once.

## How Kraft reads the file

- Kraft reads the file at startup and again on `kraft admin reload`. A hand edit shows in Settings as waiting to be reloaded.
- A file that does not load is not used: at startup no machine is connected, and on a reload the running set is kept. `kraft admin doctor` names the problem.
- `kraft admin worker add` and `remove` write the file themselves and apply it at once.
- A Kraft session cannot add, list or remove a machine. Only a person, or an assistant a person is working with, can.

## When the server is gone

_Added in next_

A step keeps running when the server goes away: the laptop sleeps, ssh drops, the server restarts. The agent's calls to Kraft wait for the connection and are answered after it comes back. A call already sent when the connection dropped fails with a 503 saying so, because sending it again could act twice.

A step that finishes while the connection is down keeps its log, commits and documents on the machine and hands them in when it reconnects. Its log carries on from the byte the server has.

`give_up_after` is how long either side waits:

- The machine stops the step it is running once it has had no connection for `give_up_after`, and writes `kraft: stopped on this machine after 2h without Kraft` at the end of the step's log.
- The server ends the step as `unknown`, the status a process that vanished gets, once the machine has been out of reach for `give_up_after`. It records `remote_step_given_up`, and tells the machine to stop the step if it comes back. Whatever the machine hands in after that is thrown away.
- Only time the server was awake counts. A laptop that sleeps for a night does not give up on a machine: the clock starts again on wake.
- `never` turns both off for that machine. Its steps run to the end and wait, however long, to hand in. The board shows the step as unreachable since the time the connection dropped, until the machine returns or you cancel the step.

Removing a machine gives up every step on it at once, without waiting for `give_up_after`.

The time cap and the idle-output limit of a step are enforced on the machine as well as on the server, since a sleeping laptop enforces nothing. Whichever side fires first stops the step with the same `time_cap_reached` event.

A machine drops its copy of an item, its working files and its job folders, when the item is archived or abandoned, and on reconnect for every item the server no longer lists. It keeps the copy of an item while one of the item's steps is still running there.

## Running a step on a machine

_Added in next_

Name a machine in a chain's `runner:` (see [Placing a step on a machine](/reference/configuration/library-and-chains#placing-a-step-on-a-machine)) or give one item its own with `kraft item create --runner NAME`. A step placed there runs on the machine; the board, gates, repos and the item's branch stay on the server.

Before every step the server sends the commits the machine lacks as a git bundle, the item's `docs/` folder, earlier sessions' results and summaries, and the job. The machine runs the repo's `setup_command` in its own copy first.

The log streams home as it is written. After the step the machine's new commits, `result.json`, `summary.md` and changed documents come back, and only then does the server look at the step.

The machine uses its own login for the agent CLI. No credential or environment variable leaves the server: `env:` values from `repos.yaml` travel, and `env_passthrough:` names are read from the machine's own environment.

A step's own calls to Kraft (`kraft item progress`, a reply to a review thread, a read of its own item) cross the same connection. The server answers only what a worker session may call, for its own work item.

The session MCP endpoint (`/mcp`) is not forwarded, so use the `kraft` command on a machine. An escalation turn, a review reply or a gate review that runs on a machine gets the same worker rights and nothing wider.

## Waiting and capacity

_Added in next_

A step whose machine is offline or full waits: the item shows `waiting for gpu-box`, holds no slot on the server, and its time cap does not run. It never runs anywhere else. `any` means the first connected machine that may work on every repo the item uses and has a free slot; it never means the server. A machine runs at most `capacity` sessions at once. Pause, skip and cancel work as usual.

A step that was resumed with the agent CLI's `--resume` (a paused session, an escalation thread's later turns) goes back to the machine that ran its first turn, because the CLI's resume state lives there.

## What a machine refuses

_Added in next_

Kraft refuses, with a 422 when the item is filed or overridden and `config_error` at launch, an item that names a machine not in `workers.yaml` or not allowed for its repo; an in-place item; a sandboxed item; and an item with workspace members, submodules or Git LFS, which a single bundle does not carry. A machine without the agent CLI the step needs, or whose `setup_command` fails, stops the step with the reason in its log.

## If something goes wrong

_Added in next_

A bundle that does not fetch, adds a nested git repository, or does not continue from the head it was sent fails the step with the reason in its log and leaves the branch alone.

If the branch moved while the step ran, the commits are kept at `refs/kraft/unsynced/...` and `sandbox_branch_not_synced` is recorded. A document you edited while the step ran keeps your version; the step's copy is saved in the session's folder and `remote_docs_conflict` names it.

When the server restarts, a running step carries on and its log resumes without a gap.
