A [sandboxed](/concepts/vocabulary#sandbox) [worker](/concepts/vocabulary#worker) reaches Kraft through a channel of its own, and a sandbox puts limits on its container's CPU, memory and processes. This page covers both.

## Callbacks from a sandbox

Under a [network policy](/reference/configuration/sandbox/network-policy) a sandboxed worker reaches Kraft through its session's own channel, the one its proxy runs on. Every such container has Kraft's `kraft` shim, a `sh` and `curl` script, mounted read-only at `/opt/kraft/bin` and first on its `PATH` (the image's own `PATH` after it).

The shim has only the verbs a worker needs, each for the worker's own item only:

- `kraft item progress K`
- `kraft item reply THREAD --body ...`
- `kraft item retry`
- `kraft view show|threads`
- `kraft view events [--after N] [--type T]`
- `kraft admin permission-hook HARNESS`

`view events` answers the item's history as JSON (all of it, or the part `--after` and `--type` keep). The history holds what a person wrote in a steer or a gate note, and every permission decision. There is no `-f` inside.

There is no `kraft view diff` or `compare` inside: Kraft reads no git in a [worktree](/concepts/vocabulary#worktree) while a sandboxed session runs in it, and the worker has `git` itself.

The shim sends each call to `http://kraft` through the proxy, which answers it in the Kraft server itself, never forwarded anywhere.

A call acts as the session whose channel it came in on, whatever headers or token the worker sends. It acts only on that session's own [work item](/concepts/vocabulary#work-item): its progress and retry, replies on its own item's threads, its own permission asks, and reads of its own item.

Anything else is answered `403` and recorded as a `sandbox_egress_refused` event, like a refused host. No allow list entry is needed for any of this.

Permission checks under `network:`:

- **Codex.** Its hook is the shim's `admin permission-hook codex`.
  - The hash Codex needs to trust the hook is asked of the image's own `codex`, in a short container with no network, since Codex silently skips a hook it does not trust and runs the call.
  - When that cannot be done (the image's Codex does not start, or does not trust the hook), the task is refused.
  - When the shim gets no answer from Kraft, it prints Codex's own deny.
- **Claude.** Launched with Kraft's MCP server at `http://kraft/mcp` and no other (`--strict-mcp-config`), which answers its permission tool for that session alone.
- **Cursor** ignores a proxy, so it is refused under a network policy.

### Without `network:`

Kraft sets up no channel to itself: the container has no `kraft` command and no Kraft MCP server. Kraft does not restrict the container's network either, so do not rely on this configuration to keep a worker away from the host: see [Security](/project/security).

A sandboxed Claude task is refused before it starts (its permission tool would be missing and the CLI would exit), as is a Codex or Cursor task with a tool policy (`allowed_tools`, `deny_tools` or a grant other than `git-commit`). For a task that does start:

- Prompts do not tell the worker to run `kraft`: it tags its commits with the task number instead of reporting progress, and says what it did about each review thread in its result.
- No reply agent is launched for review threads: a `comment` review answers `reply_agent: false`, and the item records a `reply_agent_skipped` event saying why.
- An [escalation turn](/concepts/vocabulary#escalation-turn) cannot resume the chain itself: you retry it.

## Resource limits

```yaml [config/repos.yaml]
repos:
  - path: /home/you/code/my-service
    sandbox:
      kind: docker
      image: ghcr.io/acme/agent:1
      resources: {cpu: 2, memory: 4g, pids: 512}
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `cpu` | number | unset | CPUs the container may use (`--cpus`), fractions allowed: `0.5`, at least `0.01`. |
| `memory` | string | unset | A hard memory limit: a whole number with an optional unit `b`, `k`, `m` or `g` (binary, as Docker reads them), at least `6m`. See [Memory and swap](#memory-and-swap). |
| `pids` | integer | `4096` | Processes and threads at once (`--pids-limit`), which bounds a fork bomb. At least `1`. |

### Memory and swap

Swap is held to the same limit (`--memory-swap`) wherever the runtime can limit swap. Where it cannot, the container may swap as much again, and doctor says `memory (swap unbounded)`.

### How the limits bind

The limits bind every sandboxed launch of the item, its setup command included, and they are part of the sandbox: a chain, node or task cannot loosen, tighten or drop them. `resources: {}` sets none, and is the same sandbox as no `resources` at all.

### When a limit cannot be enforced

A limit is applied or the task does not start. Two runtimes would otherwise drop a limit silently:

- Docker runs a container without a limit whose cgroup controller is missing, with only a warning.
- Rootless Podman on cgroup v1 ignores every limit.

Kraft therefore asks the runtime what it can enforce (Docker's `info`, Podman's cgroup controllers). A task that sets a limit the runtime cannot enforce stops as a configuration error that names the limit.

The fix is cgroup v2 and, for a rootless runtime, delegating the controllers to your user (systemd `Delegate=cpu memory pids` for `user@.service`).

A runtime whose `info` gives no answer Kraft can read (a daemon still starting) enforces nothing as far as Kraft knows. A task that sets a limit stops, and the next launch asks again. The default `pids` is left out, never refused, where the runtime cannot limit processes.

`kraft admin doctor` names the limits the runtime enforces on each sandboxed repository's row, and fails a row whose limits it cannot.

### Out of memory

A session container is kept after it exits, so Kraft can ask the runtime whether the memory limit killed it, then removes it by name.

- The container has no log of its own (`--log-driver=none`); Kraft reads the output as it runs.
- The `docker run` client runs in a directory of Kraft's under `$KRAFT_HOME/run/sandbox-client/`, never the worktree.

When a process in the sandbox was killed by its memory limit, Kraft records a `sandbox_oom_killed` event (`{session_id, memory, confirmed}`). The item stops and waits for you as a configuration error naming the limit: the same limit would kill a retry the same way, so no [fix loop](/concepts/vocabulary#fix-loop) runs. A session that still reported a result of its own (something it ran was killed and it got past it) keeps that result, with the event recorded.

A kill is confirmed by the runtime's own word: Docker's out-of-memory flag, and on Podman also the `oom` file its conmon writes where the client runs, since Podman on cgroup v1 never sets the flag. The runtime can set its flag a moment after the container exits, so for a container that exited 137 under a memory limit Kraft asks again for up to two seconds.

Docker on cgroup v2 can drop the flag altogether ([moby#41929](https://github.com/moby/moby/issues/41929)). Kraft counts a container as an unconfirmed kill when all three hold:

- it exited 137 under a memory limit
- Kraft did not stop it itself (a pause, a time cap, a cancel)
- the flag is still missing after those two seconds

The event then has `confirmed: false`, and the stop says the runtime did not confirm it was the limit.

Exit 137 from a container with no memory limit is never counted. A setup command the limit killed stops the item the same way.
