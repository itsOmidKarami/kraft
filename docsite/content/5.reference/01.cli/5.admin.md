Bare `kraft` is the same as `kraft admin start`.

## Verbs at a glance

| Verb | What it does |
|---|---|
| [`admin start`](#start-the-server) | Runs the server; bare `kraft` does the same. |
| [`admin stop`](#stop-the-server) | Stops the running server. |
| [`admin restart`](#restart-the-server) | Stops the server, then starts it the same way. |
| [`admin health`](#what-health-prints) | The server's state; exits 1 when degraded. |
| [`admin doctor`](#what-doctor-checks) | Checks the whole install, one line per check. |
| [`admin update`](#update-kraft) | Installs the newest release. |
| [`admin reload`](#reload-the-configuration) | Rereads the library, `policy.yaml`, `intake.yaml` and `workers.yaml`. |
| [`admin reindex`](#commands) | Rescans documents into the search index. |
| [`admin install-service`](/guides/run/run-as-a-service) | Registers Kraft as an OS service; `admin uninstall-service` removes it. |
| [`admin templates`](#inspect-templates-and-harnesses) | Lints the library's chains, shows one, or lists components. |
| [`admin harnesses`](#inspect-templates-and-harnesses) | The harness profiles and the tasks that select each. |
| [`admin addon`](#install-and-update-add-ons) | Installs, updates and removes add-ons and collections. _Added in 2.1_ |
| [`admin worker`](#machines) | Registers, lists and removes machines, and runs the machine's side. _Added in 2.4_ |
| [`admin init`](/guides/day-to-day/agent-integration) | Registers Kraft's MCP server and skills with an agent. |
| [`admin mcp`](#commands) | Serves the MCP tools over stdio. |
| [`admin permission-hook`](#commands) | A Cursor or Codex worker's pre-tool hook; not run by hand. |

```bash each
kraft admin start --port 9000

kraft admin reload

kraft admin update --cancel-when-free
kraft admin restart --when-free
kraft admin install-service
kraft admin uninstall-service
kraft admin templates lint

kraft admin templates show ID
kraft admin templates show ID --resolved
kraft admin templates library
kraft admin templates library ID
kraft admin harnesses
kraft admin harnesses ID
kraft admin addon validate PATH [--with DIR ...]
kraft admin addon collection add SOURCE [--ref REF] [--auto-update] [--replace]
kraft admin addon collection list
kraft admin addon collection update [NAME]

kraft admin addon collection remove NAME
kraft admin addon install ADDON@COLLECTION [--as ALIAS] [--auto-update] [--re-install] [-y]

kraft admin addon auto-update ADDON@COLLECTION on|off
kraft admin addon enable ADDON@COLLECTION

kraft admin addon uninstall ADDON@COLLECTION

kraft admin worker add NAME [--ssh HOST] [--capacity N] [--repos A,B] [--group G ...] [--give-up-after 2h|never] [--disabled]
kraft admin worker edit NAME [--capacity N|none] [--give-up-after 2h|never] [--group G ... | --no-groups] [--repos A,B | --every-repo] [--ssh HOST]

kraft admin worker local --run-dir DIR [--install ID]
kraft admin init --repo
kraft admin mcp
kraft admin permission-hook cursor --fail-closed
```

| Command | Effect |
|---|---|
| `admin start` | Runs the server in the foreground; the same as bare `kraft`. See [Start the server](#start-the-server). |
| `admin stop` | Sends SIGTERM to the server; local steps of worktree items keep running, and `--now` stops them. See [Stop the server](#stop-the-server). |
| `admin restart` | Stops, then starts again the same way it was running. See [Restart the server](#restart-the-server). |
| `admin health` | Prints the server's state and exits 1 when it is degraded, with the reasons on stdout. See [What health prints](#what-health-prints). |
| `admin doctor` | Runs every check in one pass. Exits 1 if any fails. See [What doctor checks](#what-doctor-checks). |
| `admin reindex` | Rescans documents into the search index. `--repo` limits it to one repo. |
| `admin reload` | Rereads the [library](/concepts/vocabulary#library), the [chains](/concepts/vocabulary#chain), `policy.yaml`, `intake.yaml` and `workers.yaml` from disk, with no restart. See [Reload the configuration](#reload-the-configuration). |
| `admin update` | Installs the newest release. See [Update Kraft](#update-kraft). |
| `admin install-service`, `admin uninstall-service` | Register or remove Kraft as an OS service (a launchd agent on macOS, a systemd user unit on Linux) that restarts if it exits. Stop a running server first. |
| `admin templates lint` | Checks every chain in the library and exits 1 on any error. See [Lint the templates](#lint-the-templates). |
| `admin templates show ID` | One chain as written. `--resolved` expands its library components. See [Show a chain](#show-a-chain). |
| `admin templates library [ID]` | Every library component, its kind and the chains using it. With an ID, one component. See [Show a chain](#show-a-chain). |
| `admin harnesses [ID]` | Every [harness profile](/concepts/vocabulary#harness-profile) in `harnesses.yaml`, its [provider](/concepts/vocabulary#provider), and the library tasks and chains selecting it (a chain's own `harness:` on a task included), then the [agent profiles](/concepts/vocabulary#agent-profile). With an ID, one [harness](/concepts/vocabulary#harness) profile in detail. |
| `admin addon validate PATH` | Checks a collection or a single add-on directory and installs nothing. Exits 1 on any problem. See [Check an add-on](#check-an-add-on). `--with DIR` names a collection or add-on directory to find a child add-on's parent in. |
| `admin addon collection add SOURCE` | Adds a collection from `owner/repo` (GitHub), a git URL or a directory. Installs nothing. `--replace` moves one already added from another source. See [Install and update add-ons](#install-and-update-add-ons). |
| `admin addon collection list` | Each collection, its source and the add-ons it published when last fetched. No network. |
| `admin addon collection update [NAME]` | Fetches the newest catalogue. Installed add-ons do not change. |
| `admin addon collection auto-update NAME on\|off` | Sets whether every add-on installed from the collection updates itself. |
| `admin addon collection remove NAME` | Forgets a collection. Refused while one of its add-ons is installed. |
| `admin addon install ADDON@COLLECTION` | Installs an add-on, and any of its ancestors that is not installed, after one review. `--re-install` takes the newest commit of an installed one. |
| `admin addon update [ADDON@COLLECTION ...]` | Updates the named add-ons, with their installed relatives' waiting updates, or all of them, after one review per tree of related add-ons. `--check` changes nothing. |
| `admin addon auto-update ADDON@COLLECTION on\|off` | Sets one add-on's auto-update. Refused when its collection already auto-updates. |
| `admin addon enable\|disable ADDON@COLLECTION` | Loads an installed add-on, or keeps it installed and not loaded. |
| `admin addon uninstall ADDON@COLLECTION` | Removes an add-on. Refused while your own config still references its namespace. |
| `admin addon list` | Every installed add-on: namespace, version and commit, with its auto-update setting, why it is not loaded, and a pending alias, `ref` or collection URL change. |
| `admin worker add NAME` | Registers a machine. Without `--ssh` it prints a token once and the command to run on the machine. See [Machines](#machines). _Added in 2.4_ |
| `admin worker edit NAME` | Changes a machine, or `local`: only the flags you give. See [Machines](#machines). _Added in 2.4_ |
| `admin worker enable\|disable NAME` | Lets a machine take new steps, or stops it: running steps finish, nothing new starts. _Added in 2.4_ |
| `admin worker rotate-token NAME` | A new token for a dial-in machine, printed once; the old one stops working at once. _Added in 2.4_ |
| `admin worker list` | Each machine: mode, online or offline and why, slots, groups, repos, last seen and Kraft version. _Added in 2.4_ |
| `admin worker remove NAME` | Forgets a machine and ends its connection. Refused while a step runs on it. _Added in 2.4_ |
| `admin worker serve` | On a machine: connects to a server. `--stdio` is what the server's ssh runs. See [Machines](#machines). _Added in 2.4_ |
| `admin worker check` | On a machine: reports what it has for running steps, sandbox backends included. Exits 1 on a failure. _Added in 2.4_ |
| `admin worker attach` | Run by Kraft, not by hand: the local process of a step that runs on a machine. See [Machines](#machines). _Added in 2.4_ |
| `admin worker local` | Run by the server, not by hand: the local worker that starts every local session. See [The local worker](/reference/configuration/workers#the-local-worker). _Added in 2.4_ |
| `admin init [--repo]` | Registers the MCP server and skills with an agent. `--repo` installs into this repo, not your user config. See [Use Kraft from your agent](/guides/day-to-day/agent-integration). |
| `admin mcp` | Serves the MCP tools over stdio. |
| `admin permission-hook HARNESS` | What a Cursor or Codex [worker](/concepts/vocabulary#worker)'s pre-tool hook runs. You do not run it by hand. `--fail-closed` denies rather than giving no opinion when Kraft cannot answer. See [Permission gate](/reference/permissions). |

## Run the server

### Start the server

| Flag | What it does |
|---|---|
| `--host`, `--port` | Override `KRAFT_HOST` and `KRAFT_PORT`, which override `access.yaml`. |
| `--detach`, `-d` | Forks the server into its own session and returns once it is up. |

Kraft refuses to start when:

- the address is not loopback and no password is set;
- a server is already running against the same run directory.

The foreground server stops on Ctrl-C, which, like `kraft admin stop`, leaves the local steps of worktree items running. Use `kraft admin stop` for one you started elsewhere.

The flags are not saved: other commands still dial the host and port in `KRAFT_HOST` and `KRAFT_PORT`, or in `access.yaml`. When `--host` or `--port` differs from that value, `start` prints the `KRAFT_HOST=H` or `KRAFT_PORT=N` line they need. A wildcard `--host` such as `0.0.0.0` needs none.

With `--detach`, if the server exits instead, `start` prints the error (such as `RuntimeError: database schema vN is newer than code vM`), the end of that start's output, and the path of `server.log`.

### Stop the server

`kraft admin stop` sends SIGTERM to the process in `run/kraft.pid`, once it has checked that the process is this Kraft server. The local steps of worktree items keep running in the local worker, and the next start picks them up. `stop` says how many keep running, and that until Kraft is back nothing answers their permission prompts or enforces their caps.

A step of an item that runs in place stops with the server, and that item stops with a `reattach:` failure when Kraft starts again; it does not resume by itself. See [A restart leaves local steps running](/guides/run/restart-kraft#a-restart-leaves-local-steps-running).

| Flag | What it does |
|---|---|
| `--now` | Stops every step, the local steps of worktree items included. Each of those items stops with a `reattach:` failure when Kraft starts again. _Added in 2.4_ |

- A pidfile naming any other process is stale: `stop` removes it, says so, and signals nothing.
- It lists the items it stops, without asking. A server that does not list them within 2 seconds is stopped anyway.
- A repo's setup command that is running is ended too, with everything it started, so it never runs beside the next server's own run of it. A server that is killed (SIGKILL) cannot end it.

### Restart the server

`kraft admin restart` stops the server, then starts it again the way it was running: through the service manager if one is installed, back into the background if it was detached.

Like `stop`, `restart` leaves the local steps of worktree items running; the new server picks them up. It ends the step of an item that runs in place: pause those items first, and retry any item it stopped. It lists those items and, in a terminal, asks before going on; with none, it asks nothing. `-y` skips the question.

| When | Then |
|---|---|
| The server runs attached to a terminal | It is stopped, with a note that only that terminal can bring it back, and `restart` exits 1, since no server is running after it. |
| You answer no | It exits 1 and says nothing was restarted. |
| No server is running | It starts nothing: it says so and exits 1. Start one with `kraft admin start`. |
| The installed Kraft is a new major version and an item is active | It exits 1 before stopping anything, naming `--when-free` and `stop --now`. _Added in 2.4_ |

| Flag | What it does |
|---|---|
| `-y` | Does not ask about running in-place steps. |
| `--when-free` | Asks for one restart at the next free moment instead, whatever `restart_when_free` says. See [Update when Kraft is free](#update-when-kraft-is-free). _Added in 2.3_ |

## Update and reload

### Update Kraft

`kraft admin update` installs the newest release with uv, keeping the `vector` extra and the Python it runs on, or runs `brew upgrade` if you installed with Homebrew. On a pipx or pip install, or a source checkout, it installs nothing and prints the command that updates that install.

It warns when another install of `kraft` sits ahead of this one on `PATH`, since MCP servers and hooks run the first one.

Before it installs a release of another major version, it lists each loaded [Kraft add-on](/concepts/vocabulary#add-on) whose `requires.kraft` that release does not meet, and asks `Install it anyway? [y/N]`. Those add-ons stop loading until each publishes a version for the new major. Answering no, or running with no terminal, installs nothing and exits 1.

| Flag | What it does |
|---|---|
| `--force` | Installs even when current. |
| `--restart` | Also restarts a running server, as `restart` does. It lists the in-place items and asks before installing anything; answering no exits 1. Across a major version it marks the release for [when Kraft is free](#update-when-kraft-is-free) instead. |
| `--now` | Installs and restarts at once, ending every running step, including those an update to a new major version would wait for. Implies `--restart`. _Added in 2.4_ |
| `--channel CHANNEL` | Takes releases from that channel. See [Channels](#channels). |
| `-y` | Accepts the [template migration](/guides/run/upgrade-from-0-x-or-a-release-candidate#migrating-a-home-from-0x) without asking, skips `--restart`'s question, and installs a major release that leaves add-ons out. |
| `--when-free [TAG]` | Marks the newest release on the channel, or `TAG`, to install and restart once nothing is running. See [Update when Kraft is free](#update-when-kraft-is-free). _Added in 2.3_ |
| `--cancel-when-free` | Drops a release marked with `--when-free` or on the About page. _Added in 2.3_ |

A Kraft home from 0.x holds a `registry.yaml` and no `library.yaml`: the server starts degraded and refuses new work until you run `kraft admin update`. See [Migrating a home from 0.x](/guides/run/upgrade-from-0-x-or-a-release-candidate#migrating-a-home-from-0x) for what the update changes.

### Update when Kraft is free

_Added in 2.3_

`kraft admin update --when-free` and `kraft admin restart --when-free` ask the running server to do it once nothing is going on: no agent session is running, and no item is `active`, `waiting`, `queued` or `rate_limited`. They answer at once; the server installs and restarts later, inside any [allowed hours](/reference/configuration/update). A mark survives a restart.

- Without a tag, `update --when-free` marks the newest release on the channel, `--channel` choosing it. With a tag, it marks that release, a new major version included. It marks nothing when the install is already current.
- Both need a running server to hold the request. With none, they say so, exit 1 and name the command that works without one: `kraft admin update` installs now. `--cancel-when-free` needs one too.
- Allowed hours apply to a mark and to `restart --when-free`: they ask for "when free", not "now". `kraft admin update` and `kraft admin restart` without the flag stay immediate.
- A dev install, and an install not made with uv, cannot be marked: the server refuses and says why.
- `update --restart` across a major version marks the newest release the same way instead of restarting, and says so. `update --now` installs and restarts at once.

[Update Kraft when it is free](/guides/run/upgrade-kraft#update-when-kraft-is-free) says what the server does when it gets there and what a failed update puts back.

#### Channels

`--channel` takes one of four values:

| `--channel` | Takes |
|---|---|
| `stable` | Final releases only. It is how an rc or beta install goes back to finals. |
| `rc` | Release candidates and finals. |
| `beta` | Betas, release candidates and finals. |
| `alpha` | Anything. |

Without `--channel`, the install follows the channel of the release it is:

| Install | Follows |
|---|---|
| A release candidate | `rc` |
| A beta | `beta` |
| An alpha | `alpha` |
| A final release | `stable`, which never takes a pre-release |

Homebrew installs only track stable.

### Reload the configuration

`kraft admin reload` rereads the library, the chains, `policy.yaml`, `intake.yaml` and `workers.yaml`. A `policy.yaml`, `intake.yaml` or `workers.yaml` that does not load is refused and the running one is kept. Reload names it and exits 1, as it does for a chain that does not resolve.

It also rereads `addons.yaml` and `addons.lock`, and restores in the background any add-on store the lock names and this machine lacks. An add-on file that does not read is refused, and the server keeps the add-ons it has. See [What loads](/reference/configuration/addons#what-loads).

## What health prints

`kraft admin health` prints the server's state as `key  value` lines, and exits 1 unless `status` is `ok`. The line after `version` and the lines after `embeddings` appear only when they apply:

- `installed` names the installed version with `restart pending`, after an update the server has not restarted for. It is not degraded.
- `invalid template`, `invalid policy` and `invalid intake` name each file that does not load, with the reason.
- `storage` shows worktree usage against `storage.worktrees.limit`, and appears only when a limit is set. `held` makes the status `degraded`, so the command exits 1. With `auto_cleanup` set, the line also says how many finished items ended too recently to clean up.
- `index error`, `reattached` and `orphaned sessions` report the search index and the agent sessions found at startup.

```text
status         ok
version        2.0.0
bind           127.0.0.1
documents      214
repos scanned  3
last scan      4m ago
embeddings     available
```

`--json` prints the [`GET /api/health`](/reference/http-api#get-apihealth) answer.

## What doctor checks

`kraft admin doctor` runs every check in one pass, one line per check, and exits 1 if any fails. `--json` prints the rows. `kraft admin health` checks only the server.

Each line starts with `ok`, `warn`, `FAIL` or `skip`, then the check's name and what it found. With `storage.worktrees.limit` set, a `storage` row says how much the worktrees use of the limit: `ok` under the quota, `warn` over it, and over the limit a failing `health` row. A row about one repository carries its name, such as `setup my-repo`. The last line counts them.

```text
ok    server            http://127.0.0.1:8765
ok    health            ok
...
ok    restart           the server (pid 4242) runs the installed version (2.0.0)
ok    config            /Users/you/.kraft/config
ok    access.yaml       parses
...
ok    spa bundle        /usr/lib/kraft/_bundled/web
...
ok    repo app          /Users/you/code/app
ok    forge app         github · gh
ok    worktrees         /Users/you/.kraft/run/worktrees
ok    review bots       no review bot silent across 3 items

all 26 checks passed
```

The excerpt cuts the rows marked `...`. The count is for a running server, the shipped chains with `claude` on `PATH`, and one connected repo, `app`, with its commands declared. It grows with each connected repo and each harness profile the chains select. With no repo connected, a `repos  none connected` row stands in for the repo rows.

[Doctor failures](/troubleshooting/doctor-failures#doctor-rows) lists every row with its fix.

## Inspect templates and harnesses

### Lint the templates

`kraft admin templates lint` checks every chain in the library, including that `harnesses.yaml` can launch each agent task (a task's `profile:` naming an agent profile with no model for its harness's provider is an error). It exits 1 on any error, printing each as `file:line:column: message`.

`--dir PATH` checks that directory in-process, with no server and no `$KRAFT_HOME`.

### Show a chain

`kraft admin templates show ID` asks the running server. A chain file you just added shows only after `admin reload`, and `--resolved` expands the version the server last loaded.

For a chain that [extends](/reference/configuration/library-and-chains#extending-a-chain) another, `--resolved` heads the YAML with comment lines: `# extends <parent>`, then each node as `inherited`, `added` or `overridden` (with its override paths), then each parent node it removes. Without `--resolved`, the chain prints as written.

A chain that comes from an add-on is headed `# <id> (<addon> <version>)`, with or without `--resolved`, and a [child add-on's](/guides/customize/share-chains-with-addons) chain ends the parenthesis with `; <mark>`: `inherited from <parent>`, `overridden here` or `added here`. A root add-on's `--resolved` output starts with that header, then `# extends`.

```text
# team-payments:default (team-payments@acme 1.0.0; overridden here)
# extends plat:default
#   verification: inherited
#   pci_review: added; pci_review added here
#   scan: inherited; security_scan overridden here
```

A node line ends with `<component> overridden here` or `<component> added here` when it is built from a component the child overrides or adds. The parent is named as this instance serves it, here `plat`.

`kraft admin templates library ID` takes a component id such as `tasks.implementer`, or a unique bare name. A bare name two sections share is refused with each full id. It prints the component's definition, its users and its lint issues. Without an ID, the `ID` column of a child add-on's component ends its parenthesis with `; inherited from company`, `; overridden here` or `; added here`, and a single component's `id` row does the same.

## Install and update add-ons

_Added in 2.1_

### Add a collection and install from it

`kraft admin addon collection add SOURCE` records a collection in `addons.yaml` under the name its `collection.json` declares. `owner/repo` is written as its full GitHub URL. `kraft admin addon install ADDON@COLLECTION` then fetches the add-on, checks it against this instance, and prints a review: what can change how far a run reaches first, then the rest. Nothing is installed until you accept it. `-y` accepts without asking; with no terminal and no `-y` the install is declined.

Any ancestor the add-on builds on that is not installed is installed with it, in the same review; a disabled one is refused with the `kraft admin addon enable` to run.

`--as ALIAS` installs the add-on under another namespace. `--re-install` takes the commit the collection's ref names now, even when the add-on's version has not changed.

### Move a collection to another source

_Added in next_

`kraft admin addon collection add SOURCE --replace` moves a collection already added under the same name to another repository or directory: a fork, a mirror or a local checkout. It writes the new source to `addons.yaml`, and changes neither the lock nor the store.

The installed add-ons keep what they locked until `kraft admin addon update` shows the move, as `collection URL changed: <old> -> <new>`, and you accept it. From one directory to another, the update shows only what changed in the add-ons' files.

The move takes the new source whole: the old `--ref` is dropped, `auto_update` is kept from one git source to another, and a directory never auto-updates. Without `--replace`, adding a taken name from another source is refused. To follow another branch of the same repository, `collection add SOURCE --ref REF` is enough.

### Update add-ons

`kraft admin addon update` reviews every installed add-on that has an update: its version changed (its files, for a directory collection), or you changed its alias, `ref` or collection URL by hand. Add-ons that build on each other share one review.

An add-on that fails a check is reported and the others go on. A change that would break one of your own chains, a `default_chain` in `repos.yaml` or an `intake.yaml` schedule is refused and names the reference.

`update` exits 0 only when everything asked for was applied or current, and 1 when an update was refused, declined, held or failed, a held relative's included.

`--check` prints the reviews and changes nothing. It exits 0 when every add-on is current, 1 when an update is waiting or held by a range, 2 when an update would be refused (a relative's that breaks a chain included) and 3 when it could not check, so a scheduled job can tell them apart.

An add-on set to auto-update is checked after each server start and once a day while the server runs. `kraft admin addon list` marks it `auto-update (collection)` or `auto-update (addon)`; its last outcome is on the `add-on updates` row of `kraft admin doctor` and in [`GET /api/health`](/reference/http-api#get-apihealth). See [Auto-update](/reference/configuration/addons#auto-update).

### Remove an add-on

`kraft admin addon uninstall` and `disable` are refused while your library, a chain, `repos.yaml`, `intake.yaml`, `policy.yaml` or `harnesses.yaml` still names the add-on's namespace. The refusal lists each reference.

A [worker](/concepts/vocabulary#worker) cannot run the verbs that change add-ons.

## Machines

_Added in 2.4_

`kraft admin worker` manages the machines that may run work item steps, listed in [`workers.yaml`](/reference/configuration/workers). A connected machine runs the steps that work items place on it. Kraft runs `admin worker attach` itself, as the local process of a step on a machine; you do not run it.

`add`, `edit`, `enable`, `disable`, `rotate-token`, `list` and `remove` ask the running server, which owns the file. `serve` and `check` run on the machine itself.

### Add, edit, list and remove a machine

```bash each
kraft admin worker add home-server --capacity 2
kraft admin worker add gpu-box --ssh gpu-box --repos kraft,infra
kraft admin worker edit gpu-box --capacity 3 --group gpu
kraft admin worker disable gpu-box
kraft admin worker enable gpu-box
kraft admin worker rotate-token home-server
kraft admin worker list
kraft admin worker remove home-server
```

| Verb | Effect |
|---|---|
| `add NAME` | Registers a machine. A dial-in one prints its token once, then the command to run on it. With `--ssh HOST` the server connects once and exits 1 if it cannot; the machine stays registered. |
| `edit NAME` | Changes only the flags you give and applies from the next step; with none it exits 2. `local` takes only `--capacity` and the groups. _Added in 2.4_ |
| `enable NAME` | Lets a machine, or `local`, take new steps again. _Added in 2.4_ |
| `disable NAME` | Stops new steps starting on a machine, or on `local`; running steps finish. See [Disabling a machine](/reference/configuration/workers#disabling-a-machine). _Added in 2.4_ |
| `rotate-token NAME` | A new token for a dial-in machine, printed once with the `serve` command. The old one stops working at once. _Added in 2.4_ |
| `list` | Columns `NAME MODE STATE SLOTS GROUPS REPOS LAST SEEN VERSION`. `STATE`: `online`, `offline:` and why, or `disabled`. `SLOTS`: `1 of 2`, `(machine)` for a lower own limit, `2 · no limit` for `local`. `--json` prints the [`GET /api/workers`](/reference/http-api/repos-chains-harnesses-and-server#get-apiworkers) answer. |
| `remove NAME` | Forgets the machine. Its token or ssh entry stops working and its connection ends. Refused while a step runs on it. _Added in 2.4_ |

A disabled machine that is also out of reach reads `disabled · offline:` and the reason.

`rotate-token` ends the machine's connection; steps running on it wait for it, up to its `give_up_after`, until `serve` runs with the new token. An ssh machine and `local` have no token, and the server refuses.

`remove` is refused while a step runs on the machine: the message names the items, and says to disable the machine and remove it once they end. A step held by an offline machine is freed by pausing or cancelling its item. `local` cannot be removed.

| Flag of `add` | Meaning |
|---|---|
| `--ssh HOST` | A host or ssh config alias for the server to dial. Left out, the machine dials in. |
| `--capacity N` | The most sessions it may run at once. Left out, the machine's own [limit](/reference/configuration/workers#the-machines-own-limit) is used, else 1. The lower of the two applies. |
| `--group G` | Put it in group G, which a step's `runner:` can name. Repeat it for several groups. See [Groups](/reference/configuration/workers#groups). _Added in 2.4_ |
| `--repos A,B` | Limit it to these connected repos, by id, name or directory name. |
| `--give-up-after D` | How long a vanished machine's work is waited for: `2h`, `30m`, `1d` or `never`. |
| `--disabled` | Register it taking no new steps, until `enable`. _Added in 2.4_ |

| Flag of `edit` | Meaning |
|---|---|
| `--capacity N\|none` | The most sessions it may run at once. `none` drops the cap: the machine's own limit applies (for `local`, no limit). |
| `--give-up-after D` | As for `add`. The machine learns the new value the next time it connects; the server uses it at once. |
| `--group G` | Its groups become exactly these; repeat it for several. |
| `--no-groups` | Take it out of every group. Not with `--group`. |
| `--repos A,B` | Limit it to these connected repos. |
| `--every-repo` | Lift the repo limit. Not with `--repos`. `--repos all` would name a repo called `all`, so this is a flag of its own. |
| `--ssh HOST` | A new host for a machine Kraft dials. Refused for a dial-in machine, and while a step runs on it, since a new host drops the connection. |

A Kraft session cannot run `add`, `edit`, `enable`, `disable`, `rotate-token`, `list` or `remove`: the server answers `403`.

### Run the machine's side

```bash each
kraft admin worker serve --server https://kraft.example --token kwt_...
kraft admin worker check --server https://kraft.example --token kwt_...
```

`serve --server URL --token TOKEN` dials the server and stays connected, redialling after a drop until you press Ctrl-C. It prints one line per outcome to stderr: `connected as NAME`, `refused: ...`, `disconnected: ...` or `cannot connect: ...`. `serve --stdio` speaks on standard input and output instead; the server runs it over ssh, and you do not run it by hand. Exactly one of `--server` and `--stdio` is required.

`check` prints one line per finding, as [`doctor`](#what-doctor-checks) does. It fails, and exits 1, when `git` is missing, when none of Kraft's agent CLIs is on `PATH`, or when `--server` is given and the handshake fails. A missing credential variable or sandbox runtime is a warning only, because an agent CLI can keep its login in a store this check cannot see.

## Check an add-on

_Added in 2.1_

### Validate a collection or an add-on

`kraft admin addon validate PATH` checks a collection or a single add-on directory and installs nothing. `PATH` is a directory holding `.kraft/collection.json`, or one holding `.kraft/addon.json`.

It checks each add-on's files against the size and content limits, both manifests, the Kraft version the add-on requires, and that every chain the add-on ships resolves.

When the config directory holds a `library.yaml`, it also checks the add-on as an install into that instance: its `requires.harnesses` and `requires.profiles`, its namespace, and your own chains. With none, it prints a `skipped:` line naming those checks.

It prints one line per add-on with its version and digest, then each problem with its file, then warnings: a manifest key Kraft does not read, and a file that looks like part of the add-on layout and is not.

It exits 0 when every add-on passes and 1 otherwise, so a collection's CI can run it on every push; [Run validate in CI](/guides/customize/publish-an-add-on#run-validate-in-ci) shows a job. `--json` prints the report as an object with `addons`, `problems`, `warnings` and `skipped`.

### Validate a child add-on

_Added in 2.3_

An add-on that builds on another (`requires.addons`) is checked together with its parent and every ancestor above it. Validate looks for each one, in order:

1. in `PATH`, when it is a collection that publishes the parent
2. in each `--with DIR`, a collection directory or a single add-on directory; repeat `--with` for more than one. A `--with` directory that holds neither manifest is a problem
3. on this instance, as installed
4. on this instance, as the current version of a collection added in `addons.yaml`, which validate fetches into a temporary directory, so the instance is not changed

```bash
kraft admin addon validate ./payments-addons --with ./company-addons
```

When none of them has the parent, validate still checks the child's own files, then exits 1 with `its parent <id> could not be found in PATH, --with or this instance; pass its collection with --with`, alongside any other problem it finds. A tree that is a cycle, or deeper than 8 add-ons, is reported the same way. In `--json`, each entry of `addons` carries `parent`, the parent's id or `null`.
