This page defines the words Kraft's docs use. Each entry is a sentence or two
and a link to the page that explains the term in full. For the keys a chain
file accepts, see [Chain file keys](/reference/chain-nodes). To see the words at
work, follow one item through [How a work item runs](/concepts/how-a-work-item-runs).

## Work items and chains

### Work item

A **work item** is one unit of work, and it produces one merge request. You
file one from the web UI, the CLI (`kraft item create`), or an agent. It always
lands **paused**, so nothing spends a token until you start it. See
[Starting an item](/concepts/how-a-work-item-runs#starting-an-item) for the
one way to skip the pause.

The item's repo must already be connected (`kraft repo connect`). Kraft refuses
one that is not, and names that command. For an item that spans several
repositories, see [Workspaces](/reference/configuration/repos/workspaces).

### Base branch

The **base branch** is the branch an item starts from and merges into. It is
the repository's default branch unless the item names another with
`--base-branch`.

That branch is where the worktree is cut from, what every rebase is applied
onto, and what the merge request and post-merge CI use. It must already exist
on the repository's origin, or Kraft refuses the item. It is fixed when you
file the item.

### Attachment

An **attachment** is a spec or plan you file with an item (`--spec`, `--plan`).
The item starts without the node that would write that document and the gate
that approves it.

Kraft stores its own copy when you file the item, and the item's worktree gets
that copy, so editing your original changes nothing. Until the item starts,
`kraft item set-attachments` replaces a document, or drops one, which puts its
node and gate back. After the item starts, its documents are fixed.

### Intake

**Intake** is the moment Kraft accepts a filed work item. It checks the repo,
base branch, chain, and policy, freezes the chain and policy onto the item, and
stores a copy of any [attachment](#attachment). Intake refuses a problem it
finds, so you see it then and not hours into a run.

### Beads

**Beads** are an optional issue tracker (`bd`) that Kraft can link a work item
to. `kraft item create --implements BEAD` records the bead an item implements
and closes it when the item completes. Kraft works without beads.

### Forge

A **forge** is the code host a repo's merge requests live on: GitHub or
GitLab. Kraft reaches it through `gh` or `glab`, signed in as the user the
server runs as, and holds no forge token. A repo's `forge` field says which;
`kraft repo connect` sets it from the remote's host. See
[Repos](/reference/configuration/repos).

### Chain

A **chain** is the ordered list of **nodes** a work item runs. It writes the
stages of your process down once, in a file you can read and diff, so an agent
does not decide them afresh each time.

You pick the chain with `--chain` (`kraft item create "..." --chain
quick-task`). Without one, the item gets the repo's `default_chain` from
`repos.yaml`, or `default` if the repo sets none. That holds for every way of
filing work, including [auto-intake](/reference/configuration/intake). To build
a chain of your own, see
[Write your own chain](/guides/customize/write-your-own-chain). The two chains
Kraft ships are listed under [The shipped chains](#the-shipped-chains).

### Chain revision

A **chain revision** is the change an agent proposes to the rest of a chain
once its spec and plan are approved: skip a node, add one, or adjust a limit.
It runs in the `chain_revision` node. See
[Chain revision](/concepts/how-a-work-item-runs#chain-revision) for how it is
proposed and approved.

### Node

A **node** is one stage of a chain. It is either an **exec** node, which runs
work, or a **gate** node, which waits for you. An exec node can carry
[recovery](#recovery), a [fix loop](#fix-loop), and an [escalation](#escalation),
all bounded by [caps](#cap).

### Step

A **step** is a group of tasks inside an exec node. Tasks in one step run in
parallel. Steps run in order, so a later step sees what an earlier one left
behind, and is skipped if the earlier one fails.

### Task

A **task** is one unit of execution. There are four kinds, and the split lets
Kraft treat an agent's judgment differently from its own bookkeeping:

- **agent** runs a headless coding agent in the item's worktree, on a
  [harness profile](#harness-profile). Its model comes from an
  [agent profile](#agent-profile) or from its own settings.
- **subprocess** runs a literal command.
- **builtin** is work Kraft does itself, such as running the repo's tests or
  rebasing onto the item's base branch before a draft merge request opens.
- **forge** is a merge-request action on GitHub or GitLab (open a draft, watch
  CI, merge), resolved from the `forge` recorded in the repo's `repos.yaml`
  entry.

### Worker session

A **worker session** is one run of a task, recorded with its status, log,
result file, tokens, and cost. See
[Inside a node](/concepts/how-a-work-item-runs#inside-a-node).

### Canonical path

Every task, step, and node has a **canonical path**, such as `spec.main.author`.
It is how you point Kraft at one piece of work, for example with
`kraft item retry --path`. The path format is in
[Chain file keys](/reference/chain-nodes).

### Library

The **library** is the set of reusable tasks, steps, and nodes Kraft ships in
`library.yaml`. A chain component reuses one with `extends`, which keeps a fix
to a shared piece in one place. See
[Library and chains](/reference/configuration/library-and-chains), and run
`kraft admin templates lint` to check every chain.

### Templates

In these docs, **templates** means `library.yaml` and the files in `chains/`,
and nothing else. Kraft copies a chain onto each item when you file it, so
editing a template changes no item already filed. The directory that holds them
and the rest of Kraft's configuration is the config directory. See
[Configuration](/reference/configuration).

## Decisions, notes, and limits

### Gate

A **gate** is where your decision belongs. When the chain reaches a gate node it
stops. The work item's status becomes `needs_human`, and the board shows it
under *Needs you*. From there you can:

- **Approve.** The chain continues to the node after the gate.
- **Reject**, with a note. The chain re-enters at the gate's `reject_to` node,
  carrying the note as a steer, so the node that produced the document tries
  again with your feedback. On the review page the same decision is **Request
  changes**: it rejects the gate with your summary and review threads as the note.

### Review thread

A **review thread** is a line-level comment on the change. You can leave one at
any point, gate or not. Every agent that runs next reads the ones still waiting
on an answer, and working agents reply in the thread.

A `must-fix` thread blocks every approval until you resolve it. A gate reached
with one still unanswered sends the work back instead of asking you again. See
[Reviewing a change](/guides/day-to-day/review-a-change).

### Steer

A **steer** is a note to the next agent Kraft launches for an item. The first
agent task that runs reads it once, and then Kraft drops it. See
[Steering](/concepts/how-a-work-item-runs#steering) for the four ways to give
one.

### Cap

A **cap** is a limit on a scope's time, tokens, or dollars. A scope is the work
item, a node, a step, or a task. A **wait**, such as CI, an automated review,
an approval, or a merge landing, has its own time limit. A
[fix loop](#fix-loop) stops at its attempt limit and wall clock.

Hitting any of these stops the chain and hands the item to you, naming the
scope, so a defect the agent cannot fix ends with you seeing the full trace and
not a loop that never finishes. See
[Caps and budgets](/concepts/caps-and-budgets) for how the bounds combine, and
[Configuration](/reference/configuration/policy) for the values.

### Recovery

**Recovery** (`on_failure`) is a node's optional repair steps, run once per
entry into the node when a task fails, before the whole node runs again. See
[Inside a node](/concepts/how-a-work-item-runs#inside-a-node).

### Fix loop

A **fix loop** (`fix_loop`) is a node's optional repair cycle: an agent fixes
the failure, then Kraft measures the whole node again, until it passes or the
loop runs out of attempts or time. See
[Fix loop and judge](/reference/chain-nodes/fix-loop).

### Judge

A **judge** is the task a fix loop runs before each repair cycle after the
first, to rule whether another attempt is worth it. Its verdict is `continue`,
`stop_needs_human` or `stop_downgrade`. See
[Fix loop and judge](/reference/chain-nodes/fix-loop#the-judge).

### Stuck

A node is **stuck** when its fix loop cannot go on: the attempts or the wall
clock ran out, the same findings came back, or the [judge](#judge) stopped it.
Kraft then tries an [escalation](#escalation), and the item stops and waits
for you if that does not clear it. See
[Fix loop and judge](/reference/chain-nodes/fix-loop#one-cycle).

### Escalation

**Escalation** (`escalation`) is the third thing a node can try when a task
fails. It runs once the node is stuck. If it succeeds, the node gets a fresh
entry from its first step. If it does not, the item stops and waits for you. A
node with none of its own gets a generic one, which runs as an
[escalation turn](#escalation-turn).

### Apply chip

The **apply chip** is the button in the web UI's header that appears while
saved configuration is not running yet. It offers a reload for files Kraft can
reread, and a restart where a service manager started the server. See
[Saved but not applied](/reference/http-api/repos-chains-harnesses-and-server#saved-but-not-applied).

## Agents and where they run

### Worktree

A **worktree** is the work item's own git checkout, cut from its
[base branch](#base-branch) onto a branch of its own. Agents edit it, and
archiving the item removes it. See
[Starting an item](/concepts/how-a-work-item-runs#starting-an-item).

### Harness

A **harness** is one agent CLI that Kraft can run a task on, described as data
and not code. Kraft ships seven. See [Agent harnesses](/reference/harnesses).

### Harness profile

A **harness profile** is an entry in `harnesses.yaml` that names a harness (its
`provider`) and the options to start it with. An agent task's `harness:` field
names one. It is not an [agent profile](#agent-profile). See
[harnesses.yaml](/reference/configuration/harnesses-file).

### Agent profile

An **agent profile** is a named model tier (`deep`, `strong`, `fast`) that a
task selects with `profile:` instead of spelling out `model:` and `effort:`. A
tier means the same on every harness. It is not a
[harness profile](#harness-profile). See
[Agent profiles](/reference/harnesses/agent-profiles).

### Sandbox

A **sandbox** is the container a repository's workers run in, set by `sandbox:`
in `repos.yaml` or a policy. Without one, workers run directly on your machine,
as your user. See [Sandboxed workers](/reference/configuration/sandbox).

### Kit

A **Kit** is an image that carries a descriptor of what its workload may reach
and hold. As a repository's sandbox, it is the whole sandbox. See
[Kits](/reference/configuration/sandbox/kits).

### Provider

A **provider** is one of the seven agent runtimes Kraft knows: `claude`,
`codex`, `cursor`, `opencode`, `gemini`, `antigravity` or `amp`. A
[harness profile](#harness-profile) configures one provider, and an
[agent profile](#agent-profile) spells its model and effort once per provider.
See [Harnesses file](/reference/configuration/harnesses-file).

### Ref store

A **ref store** is the private copy of a repository's branches and tags that a
sandboxed worker's container sees in place of the real ones. Kraft moves only
the item's own branch back to your repository when the session ends. See
[Repository refs](/reference/configuration/sandbox#repository-refs).

### Sentinel

A **sentinel** is the stand-in value a sandboxed worker holds for a credential.
Kraft's egress proxy swaps the real value in on requests to the host that
credential is for, so the container never holds it. See
[Credentials](/reference/configuration/sandbox/credentials).

### Classifier mode

A harness's **classifier mode** is its own automatic judge of which tool calls
need approval, such as Claude Code's `auto` mode or Cursor's `--auto-review`.
Kraft runs each CLI in it where the CLI has one. See
[Unattended runs](/reference/harnesses/unattended-runs).

## How a run proceeds

### Walk

A **walk** is one pass of Kraft's executor through an item's chain, from the
node it enters until the item finishes or stops at a gate, a wait, or a stop.
Starting the item again begins a new walk. See
[Architecture](/project/architecture).

### Run fork

A **run fork** is the new run a retry starts. It keeps what the earlier run
did, reruns the node or step you name and everything after it, or only the
task you name, and reopens every gate it has to rerun. See
[Addressing work by path](/reference/cli/item#addressing-work-by-path).

### Span

A **span** is the stretch of a chain that runs again: from the node, step, or
task a retry names, or from a node's `restart_from` when the base branch moves.
A retry you ask for starts the fix-loop counts inside its span afresh. See
[Caps and budgets](/concepts/caps-and-budgets#two-kinds-of-bound).

### Escalation turn

An **escalation turn** is an agent session Kraft opens on a stopped item to
help. It reads the stop and may retry the item. Kraft starts one itself on a
stuck stop, or you start one with `kraft item escalate`. See
[Fallback and escalation](/reference/harnesses/fallback-and-escalation#escalation-turns).

## The shipped chains

Kraft ships two chains: `default`, the full process, and `quick-task`, the
smallest.

### The default chain

The `default` chain has these nodes, in order. A node marked *gate* waits for
you.

| Node | What it does |
|---|---|
| `spec` | An agent writes the specification. |
| `spec_approval` (gate) | You approve it. A reject sends the item back to `spec`. |
| `plan` | An agent writes the implementation plan. |
| `plan_approval` (gate) | You approve it. A reject goes back to `plan`. |
| `chain_revision` | An agent reads the spec and plan against the nodes still to run and proposes changes. |
| `chain_revision_approval` (gate) | You approve the proposal. It passes without asking you when nothing was proposed. A reject goes back to `chain_revision`. |
| `implementation` | An agent implements the approved plan. |
| `verification` | The changed test scopes run, then a code review, inside a fix loop. |
| `work_brief` | An agent writes the brief you read before the merge request exists. |
| `local_review` (gate) | You approve creating a draft merge request. A reject goes back to `implementation`. |
| `describe_merge_request` | An agent writes the merge request's title, labels, reviewers, and description. |
| `draft_merge_request` | Kraft rebases onto the base branch, then opens a draft merge request. |
| `merge_request_feedback` | Kraft waits for CI and the automated review, inside a fix loop. If the base branch moves, the chain restarts from `verification`. |
| `work_item_summary` | An agent writes the summary and review brief. |
| `final_review` (gate) | You review the whole item and its summary. A reject goes back to `implementation`. |
| `mark_ready` | Kraft marks the merge request ready. |
| `external_approval` | Kraft waits for an approving review if the forge requires one. |
| `merge` | Kraft merges the merge request. |
| `post_merge_ci` | Kraft waits for the post-merge pipeline. |

How long each wait lasts and how many attempts each fix loop gets are in
[The default caps](/concepts/caps-and-budgets#the-default-caps).

`kraft admin templates show default --resolved` prints the chain with every
library component expanded.

### The quick-task chain

The `quick-task` chain is two nodes with no gates: `implementation`, then
`verify`. `verify` runs the repo's own `test_scopes` or `test_command` from
`repos.yaml`. On a repo that declares neither, the item stops and waits for you
with a config error, and Kraft guesses no command.
