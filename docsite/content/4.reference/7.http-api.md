The Kraft server serves its board, and the JSON API behind it, on one port
(`127.0.0.1:8765` by default). The `kraft` command and the MCP server are
clients of that API.

## Stable routes

Only two routes are meant for other programs, and only these keep their shape
between minor releases. See
[Versioning and stability](/project/status-and-support#versioning-and-stability).

| Route | Use |
|---|---|
| `POST /api/triggers` | File a work item from a webhook or script. See [Inbound triggers](/reference/triggers#post-apitriggers). |
| `GET /api/health` | Check that the server is up. Answers `status` (`ok` or `degraded`), the reasons it is degraded (`invalid_templates`, `invalid_policy`, and `invalid_intake`: why `intake.yaml` does not load, else `null`), whether auto-intake and `intake.yaml`'s schedules are off for it (`intake_off`: `true` when the server started on that file, though a trigger left in `policy.yaml` still fires; `false` when a reload refused it and the running ones are kept), which instance this is (`run_dir`, `pid`, `uptime_s`, `bind`, `port`), the version it runs (`version`), and the version installed on disk (`installed`), which differs until a restart finishes an update. Needs no login. |

Every other route under `/api/`, and the `/api/ws/events` WebSocket, exists
for the board and can change in any release. For those, prefer the `kraft`
command with `--json`, which is stable.

`POST /api/work-items`, the board's create route, files the item paused unless
the body sets `autostart: true`, like `kraft item create` without
`--autostart`. With every slot busy (`max_concurrent`), an `autostart: true`
item is filed paused anyway, and the answer carries
`"slots": {"busy": 3, "limit": 3}` to say why. On a repo that declares no setup command, or no test
command nor test scopes, the answer carries `repo_warning`, saying where the item will stop. The chain is `chain`; `chain_template`,
the pre-2.0 name, is still read, on `PATCH` too, and an unknown one is
refused. A body naming two different chains under the two names is
refused (`422`, its `detail` one sentence naming both); the same one twice
is fine. A body with neither gets the
repo's `default_chain`. Every repo path you send must be absolute: the
server would read a relative one against its own directory, not yours.
`POST /api/repos`, `POST /api/work-items` and `POST /api/triggers` refuse it
with a `422`, and `PATCH` or `DELETE /api/repos?path=` answer `404`.

## Work item status

`GET /api/work-items` and `GET /api/work-items/{id}` both carry two read-only fields
on every item, computed on read rather than stored (see
[Displayed status](/concepts/how-a-work-item-runs#displayed-status)):

| Field | Meaning |
|---|---|
| `display_status` | The board's status badge: one of `archived`, `done`, `cancelled`, `paused`, `running`, `waiting`, `needs_you`, `escalated`, `failed`. |
| `stop` | `null` unless the item is `needs_human`, `waiting` or `rate_limited`. On the list, `{kind, node, resume_at, reason}`; on the detail, also `task`, `attempt` and `facts`. `facts.cause` names why an `infra` stop happened when Kraft knows: `forge_auth`, `forge_unreachable`, `git`, `ci_infra`, `stranded` or `crash` (a `failed` stop of a forge task carries the first two as well); the failed card chooses its action from it, and an `infra` stop without one reads as a generic infrastructure stop. A `cap` or `budget` stop on the detail also carries `limit: {path, key, value, maximum}` when a `PATCH` of the item's `policy` can raise what stopped it, and omits it when none can. A `budget` stop on the detail also carries `scope`, the cap that stopped it: `work_item` (the item's own dollar cap), `usd` (a `budget_usd`, item-wide or on a node, step or task, or spend a harness never reported; `POST /work-items/{id}/budget/raise` takes the first and an item-wide `usd`), `tokens` (a `token_budget`) or `daily` (`budget.daily_usd`). `key` is `max_attempts` or `timeout_minutes` (a fix loop's attempts or its clock, `path` the node id) or `time_cap_minutes` or `total_time_cap_minutes` (the work item's own cap, `path` `""`) or, on a `budget` stop, `budget_usd` (the item-wide policy dollar cap, `path` `""`); `value` is the limit that stopped it, in attempts, minutes or dollars, and `maximum` the administrator ceiling or `null`. Raise it with `PATCH /work-items/{id}` `{policy: {<key>: N}}` (item-wide) or `{policy: {paths: {<path>: {<key>: N}}}}`, then `POST /work-items/{id}/retry`. No `limit` for a `budget` stop on the item's own cap (`POST /work-items/{id}/budget/raise` raises that one), on a node, step or task's `budget_usd`, a `token_budget`, the daily cap or spend a harness never reported, nor for a node, step or task's time cap, a gate's or wait's timeout, a `loops:` cap in `policy.yaml`, exhausted rate-limit retries, or a fix loop whose bound the older `node_overrides` set. |
| `test_result` | Detail only. The latest changed-test-scope verification run, `{scopes: [{command, scope, passed, exit_code, session_id}], passed}`, or `null` when no scope has finished. One entry per scope, passed or failed (`scope` is `null` when the repo's table no longer declares the command, `exit_code` when none was recorded); `passed` is true when every scope passed. An area's setup appears only when it failed. A scope still running is left out. No test counts. `session_id` is the scope's session; read its log with `GET /api/worker-sessions/{id}/log`. |

`stop.kind` is one of `gate`, `question`, `cap`, `budget`, `failed`,
`conflict`, `mr_closed`, `config`, `infra`, `stuck`, `wait`, `rate_limit` (see
[Events → work_item_needs_human](/reference/events#work_item_needs_human) for
what each means). A `needs_human` item stopped on 1.4.0 or earlier, before kinds were
recorded, reads its kind off its stop event: `question`, `budget` or `cap` where
the event carries one, else `failed`; only a `waiting` row reads `wait` and a
`rate_limited` one `rate_limit`. A `rate_limit` stop's `facts` also carries `fallback` and
`fallback_allowed` -- the stopped task's declared fallback harnesses, and
which of those its resolved policy still allows.

## Overrides

`agent_overrides`, `node_overrides` and `policy_override` are objects in
`GET /api/work-items/{id}` and in every answer that hands back the item itself:
a gate's approve or reject, `complete`, `cancel`, `skip`, and a `retry` or
`resume` that stops at once. `agent_overrides` and `policy_override` are
`null` when the item has none, and `node_overrides` is `{}`. 1.4 sent
`agent_overrides` as JSON text in all of these, and the other two as text in
the action answers.

`PATCH /api/work-items/{id}` with `agent_overrides` replaces the item's whole
model and effort override, as in 1.4. A field you leave out, or send as
`null`, is dropped, and `{}` clears the override. The answer echoes the
override as stored: `{}` once it is cleared. `node_overrides` merges per node
instead: `{"plan": {"effort": "high"}}` sets that field and keeps the node's
others, `{"plan": {"effort": null}}` drops one field, and `{"plan": {}}` drops
the node's overrides. The answer echoes each node you named, as stored:
`{"plan": {}}` once you clear it. A node that has started answers `409`,
except on an item stopped at that node because its stored `model` or
`escalate_model` is not a model id: there `{}`, and a change to `model`,
`escalate_model` or `effort` alone, are accepted.

## Cancelling

`GET /work-items/{id}/cancel-preview` shows what `POST /work-items/{id}/cancel`
would do, without doing it: `409` once the item has already ended, same as
`/cancel` itself.

```json
{
  "running": {"node": "mr_checks", "task": "mr_checks", "attempt": 1, "started_at": "2026-10-03T10:00:00+00:00"} | null,
  "kept": {"branch": "kraft/...", "worktree": "/path", "findings": 0, "threads": 1},
  "mr": {"ref": 54, "url": "https://...", "state": "open"} | null,
  "spend": {"spent_usd": 1.2, "cap_usd": 5.0},
  "beads": ["kraft-ab1"]
}
```

`running` is the item's running session, if any, and when it started; `kept` is what cancel leaves
behind (cancel never removes the worktree or the branch, and archive later
removes the worktree but keeps a branch with commits nowhere else); `mr` is
the item's merge request and its live state, or `null` before one was ever
opened; `beads` is every bead `POST /work-items/{id}/complete` closes when
asked with `close_beads`: the item's own bead, those it implements, and those
a `Fixes` or `Closes` trailer on its own commits names (an id starting
`Kraft-`, any case). An item filed while `bd` was down has none yet, and
`close_beads` files one for it and closes that.

`POST /work-items/{id}/cancel` takes an optional `close_mr: bool = false`.
When set and the item's merge request is open, cancel closes it on the forge
once the cancel itself has landed and the response gains `close_mr: {ok:
true}` (or `{ok: false, error}` when there was no open merge request or the
forge call failed -- a failed close never undoes the cancel). The key is
absent when `close_mr` was not asked for.

`POST /work-items/{id}/archive` answers `{"id", "archived_by",
"worktree_removed"}`. It adds `kept_branch` and `unpushed_commits` when it
kept the item's branch because some of its commits are on no other branch,
remote-tracking branch or tag, and not in what Kraft pushed. It adds
`rescued_branch` (`kraft/rescued/<id>`) and `rescued_commits` when the
worktree's HEAD was detached on commits no branch has. If that branch cannot
be made, the item is still archived but its worktree stays, and the answer
has `worktree_kept: "rescue failed: <reason>"`. Archive keeps the
attachment copies.

When the item's repository has been moved or deleted, archive and
`POST /work-items/{id}/abandon` remove the worktree directory directly and
add `repo_missing`, the repository path they could not find. Nothing is done
to the branch: if you only moved the repository, it is still there.

## Retrying, duplicating, acting in bulk

`POST /work-items/{id}/retry`'s response gains `attempt`: the attempt number
the task it relaunches will run as -- the count of that (item, node, task)'s
own sessions so far, plus one. A `path` naming one task counts only that
task's sessions; a `path`-less retry (the whole stopped node, or `restart`'s
whole chain) takes the highest next-attempt over all of the node's own tasks,
since a walk may enter at any one of them.

`POST /work-items/{id}/duplicate` files a fresh, paused item from `{id}`'s own
title, description, repo, chain, workspace selection and
attachments (re-snapshotted under the new item's own id). Any source status is
accepted, archived and cancelled included. No run state, override, policy
override, budget or bead link carries over -- this is a fresh intake, not a
clone of the row.

```json
{"id": "...", "status": "paused", "duplicate_warning": "..."}
```

`duplicate_warning` is present only when another open item looks like a
duplicate, the same check `POST /work-items` makes. A source whose stored
attachment copy has gone missing, as it does when the source is abandoned,
answers `409` naming it, before anything is filed.

`POST /work-items/bulk` applies one action to several items at once:

```json
{"action": "pause", "ids": ["...", "..."], "reason": "..."}
```

`action` is one of `pause`, `cancel`, `archive`, `restore` -- the same door
each one's own single-item route already has, called once per id, each in its
own write, in `ids` order. `reason` is required, and checked before anything
is touched, when `action` is `cancel` (`422` otherwise); the other three
ignore it. The response is one result per id, in order:

```json
{"results": [{"id": "...", "ok": true, "status": "paused"}, {"id": "...", "ok": false, "error": "..."}]}
```

An id whose action raises (an item in the wrong status, say) becomes `{id,
ok: false, error}` and the rest of the batch still runs; an id naming no work
item answers `{id, ok: false, error: "not found"}`. `status` is the item's
stored status after the action ran.

## MR closed externally

A poller checks every `waiting`/`needs_human` item parked at a merge-request
node against the forge every `policy.forge_poll_s` seconds (default 300). When
the merge request was closed there without merging, it stops the item with
`stop.kind: "mr_closed"` and `facts: {ref, url}` (see [Events →
work_item_needs_human](/reference/events#work_item_needs_human)).

`POST /work-items/{id}/reopen-mr` reopens that merge request on the forge and
retries the stopped node, the same as `POST /work-items/{id}/retry` with no
`path` -- it answers `409` unless the item is actually stopped with
`stop.kind: "mr_closed"`, and `502` with the forge's own message when the
forge call fails (the item stays stopped). Its response is `/retry`'s own
response shape. "Open a new MR" instead is `/retry` with the MR node's path;
cancelling the item instead is `/cancel`.

## Daily total and dry run

`GET /budget/today` answers the instance's spend since local midnight against
`policy.budget.daily_usd`:

```json
{"spent_usd": 3.4, "cap_usd": 20.0}
```

`cap_usd` is `null` when `policy.budget.daily_usd` is unset. `GET
/work-items/{id}`'s `budget_cap` gains the same two numbers under `daily`
(`{spent_usd, cap_usd}`). Its `spent_usd` is unchanged: the item's own,
all-time spend.

`budget_cap.cap_usd` and `budget_cap.source` changed meaning in 2.0, in the
API and in `kraft view show --json`:

- In 1.4, `cap_usd` was always the item's own cap (its `budget_usd`, else
  `budget.work_item_usd`), and `source` said which of those two set it.
- Now `cap_usd` is whichever cap stops the item first: the lower of its own
  cap and the item-wide `budget_usd` of its policy.
- Read the new `key` to know which cap it is, and the `PATCH` field that
  changes it: `budget_usd` for the item's own cap, `policy.budget_usd` for
  the policy one.
- `source` is `item` when the item itself set the reported cap, by its own
  `budget_usd` or by its own `policy` override, and `policy` when it comes
  from `policy.yaml` or the chain. So `source: item` with
  `key: policy.budget_usd` means the item's policy override, not the cap
  1.4's `source: item` named.

`POST /work-items/{id}/budget/raise` (`kraft item raise-budget`) raises
whichever of the two stopped the item.

Beside the dollars, `running_time` is the item's time budget:
`{running_s, cap_minutes}`. `running_s` is what its item-wide
`time_cap_minutes` measures, the seconds any of its sessions ran since the
last `/retry` a person made, and `cap_minutes` is that cap, `null` when it has
none. It is `null` for an item with no frozen chain.

`POST /work-items?dry_run=1` runs every check `POST /work-items` runs, up to
and including validating `node_overrides`, then answers `200` without filing
anything -- no row, no bead, no attachment copy, no spawn. A body that would
answer `422` or `503` on an ordinary create answers the same on a dry run.

```json
{
  "dry_run": true,
  "nodes": [...],
  "skipped": [{"node": "spec", "why": "covered_by", "kind": "spec"}, {"node": "...", "why": "skip"}],
  "gates": ["spec_approval", "..."],
  "caps": {
    "budget_usd": 5.0,
    "budget_source": "item",
    "daily_usd": 20.0,
    "nodes": {"implement": {"attempts": 3, "wall_clock_s": 7200}}
  }
}
```

`nodes` is the chain that would be filed, in `chain_definition`'s own node
shape. `skipped` lists every node the attachments or `skip_nodes` dropped:
`covered_by` names the attachment kind that made it redundant, `skip` is an
operator's own choice. `gates` is the ids of the gate nodes left in the chain.
`caps.budget_usd`/`budget_source` mirror the create route's own cap
resolution (`"item"` for the body's own `budget_usd`, else `"policy"`);
`caps.nodes` is each fix-loop node's `attempts`/`wall_clock_s`, resolved the
same way the walk resolves them at run time -- the node's own `policy`,
`node_overrides` entry and any item-wide override each layered on in the same
order, so a node's own override and an item-wide value each show where they
apply.

## Events paging and the run summary

`GET /work-items/{id}/events` normally returns every event after `after_seq`
(`0` by default). `before_seq` pages backward instead: it returns the last
`limit` events with `seq < before_seq`, oldest first, in the same row shape --
100 when `before_seq` is given with no `limit`. `limit` alone bounds
`after_seq`'s own forward window to the first `limit` events after it (1-500;
outside that range, or passing both cursors at once, answers `422`). Every
event row carries a `node_id` (see [Events](/reference/events)).

`GET /api/work-items/{id}` adds `summary`, a run's progress at a glance:

```json
{"nodes_done": 3, "nodes_total": 8, "gates_passed": 1, "step": {"index": 2, "count": 2} | null}
```

`nodes_done`/`nodes_total` count against the frozen chain; `gates_passed` is
how many of the completed nodes were gates. `step` is the current node's step
(1-based) out of its own steps, read from its latest non-escalation session's
task, when the node declares more than one -- `null` otherwise.

`GET /api/work-items` rows carry two more fields the detail already has or
derives, so the board can draw "2 of 3 · review › code_review" and "merged !139"
without a request per row. `mr_ref` is `{number, url}` or `null`, the same
value as the detail's. `step` is `{index, count, name, task}` or `null`:
`index` and `count` as in `summary.step`, `name` the step's id and `task` the
latest non-escalation session's task id within it.

`GET /api/work-items/{id}` carries `worktree_exists`: whether `worktree_path` is a
directory on disk. It is `false` before the item first runs and after its
worktree was reclaimed or deleted. The routes that need the directory
(`diff`, `compare`, `open-worktree`, `mr-labels`) answer 404 in that case, with
"this work item has not started, so it has no worktree yet" for an item that
never ran and "this work item's worktree was removed from disk" for one that
did. A retry or resume recreates the directory.

`GET /api/work-items/{id}/diff` and `GET /api/work-items/{id}/compare` take an
optional `ignore_whitespace=true`, like `git diff -w`. A file whose only change
is whitespace then drops out of `files`, the per-file counts and `diff` together,
so the three never disagree; `touched_by` and `untracked` do not follow it. Both
answers carry `ignore_whitespace`, the value they used.

`GET /api/work-items/{id}` carries `fix_target` while a gate is pending: the
`node` a request-changes review restarts at, the nodes `then` that run before it
returns to the `gate`, and the `round` (`n` of `max`) a rejection now would start,
counted against the cap the gate's reject loop already snapshotted. It is `null`
with no gate pending. `GET /api/work-items/{id}/fix-target?node=&gate=` answers
for a target the reviewer picked; with no gate pending it gives what a gateless
`request_changes` would target, with `reason` one of `requested` (you named the
node), `threads on <path or node>`, `current node`, or `gate`. It answers `400`
for a node that is not before the gate, `409` for a gate that is not pending or an
ended item, and does git work per thread, so call it on demand.

A review submitted with `outcome: approve` takes an optional `digest`, passed to
the gate approval as `POST /gates/{gate}/approve` takes it. A chain revision gate
needs it (the one `GET /artifact` returned) and answers `409` without it or with a
stale one; any other gate ignores it.

`GET /api/work-items/{id}/attachments/{kind}` reads the spec or plan attached
at intake (`kind` is `spec` or `plan`) from the copy Kraft keeps under
`run/attachments/<id>/`, the one the worktree gets when the item starts. It
answers `{work_item_id, kind, path, title, content, truncated}`, `path` being
where the worktree puts it, `404` when the item has no such attachment or
its copy is gone, and `422` for a `kind` that is neither. Before the item starts nothing is indexed, so this is how the
board and the phone open one, as do `kraft view docs --attachment` and the MCP
tool `get_attachment`. `GET /api/work-items/{id}/documents` lists the same
copy, until the item has a worktree, as `attachment:<id>:<kind>`, which
`GET /api/documents/{id}` reads.

`GET /api/work-items/{id}/compare` marks each file `viewed`. `PUT` and
`DELETE /api/work-items/{id}/viewed?file=<path>&to=<target>` set and clear the
mark and answer `{file, to, viewed}`; `to` is a compare target (default `latest`)
and `file` a repository-relative path. A mark belongs to the file's content at
`to`, not to the `from` side, so a file that has not changed since you ticked it
stays ticked in any other comparison and a new attempt that edits it clears the
tick. `DELETE` clears the mark on that content wherever it was made. The routes
answer `404` for a target the item does not have and `400` for a path outside the
repository.

## Connecting a repo

`GET /api/repos` answers the connected `repos` and `workspaces`, and `suggested`: the git checkout the server was started in, when it is one and not connected yet, else `null`. The first-run board offers it as the path to connect.
`POST /api/repos/probe` (`{path, detect?}`) reads a repository and changes nothing. With `detect: false` it answers only what needs no detector table: the resolved `path`, `name`, `branch`, submodules, beads and forge.
`POST /api/repos` connects it, answering `409` for a repo already connected before reading anything else, and `422` for a repository with no commit yet.
The probe takes a `test_command` too, and answers the proposal connecting with it would save. A `test_command` or `setup_command` in the body
replaces the proposal, and `""` declares none (a `test_command` of `""` is a repo
with no tests, which may be enabled). Both answer with the proposal's
evidence beside the entry. None of it is stored in `repos.yaml`:

| Field | Meaning |
|---|---|
| `candidates` | Every command the evidence supports: `{dir, role, command, tier, source, marker, detector, family, corroborated, chosen}`. `role` is `test` or `setup`; `tier` is `runner`, `ci`, `toolchain` or `devenv`; `dir` is `""` for the root; `chosen` marks the proposal. |
| `scopes` | One `{dir, test, setup}` per directory the proposal covers, root first, with commands as they run from inside that directory. |
| `missing_setup` | Directories with a test command and nothing to prepare them (`.` for the root), so `setup_command` is left undeclared. |
| `test_markers` | The file each proposed test command came from. |
| `read_from` | The commit read: `refs/remotes/origin/HEAD`'s target, `refs/remotes/origin/main` or `HEAD`, or `null` for a repo with no commit (read from its working copy). |
| `missing_tools` | Programs a proposed command runs that the server's `PATH` does not have, one `{dir, tool}` each: a work item fails on them until they are installed. |
| `stopped` | Why no test command was proposed, one `{dir, reason, detector}` per directory that stopped it (`.` for the root): a `pyproject.toml` with no lockfile, or a root project with no test command found beside nested ones. Empty when nothing stopped. |

A `detectors.yaml` that does not load answers `400`, naming it, and so does a probe that runs past two minutes. The probe runs in a process of its own with that limit, so a repository's files cannot stall the server. A few probes run at once; `POST /api/repos/probe` past that answers `429`. `POST /api/repos` given both a `test_command` and a `setup_command` connects a repo the probe fails on, with those, and says why in `probe_failed`. See
[Detectors](/reference/configuration/repos/detectors).

## Chain templates

These board routes read the chains the Templates editor shows.

| Route | Answers |
|---|---|
| `GET /api/templates/chains` | Every chain: `id`, `description` (or `null`), `nodes`, `gates`, `error` and `uses`. A chain that does not resolve still has its `description`, with `nodes` empty and `error` saying why. |
| `GET /api/templates/chains/{id}/resolved` | `{id, chain, task_paths, steering, nodes, documents}`. `documents` maps each gate id to the document kinds the exec nodes before it produce, in chain order: what that gate's `artifact` can name. |
| `GET /api/templates/library` | `{file, text, components}`. Each component has `id` (`tasks.implementer`), `kind` (its section), `name`, `definition` as written, `issues`, `used_by` (the ids of the chains that use it) and `used_by_paths: [{chain, path, overrides, via?}]`: each component of a chain that extends or selects it. `path` is that component's canonical path, `overrides` whether it sets any key besides `id`, `extends` and `kind`, and `via` the library node it reaches the chain through, when it sits in that node's own definition (`{chain: "default", path: "verification.review.code_review", overrides: false, via: "verification"}`). |
| `GET /api/templates/library/{ref}` | One component, shaped as in the list above, by its `id` or a bare name no other section shares. 404 when nothing matches; 409 naming each `id` when two sections share the bare name. |
| `GET /api/templates/steering/preview?chain=&task=&repo=` | `{sections: [{kind, source, text}]}`: what the agent task at canonical path `task` of chain `chain` reads at launch in the repository whose `name` or `path` is `repo`, section by section in launch order. `kind` is `contract`, `document` (`source` is the kind it produces), `review_package`, `skill` (`source` is the skill), `intent` (`source` is the repository's `intent_dir`), `steering` or `usage`. There is one `steering` section per profile: the repository's first, then the task's, with `source` `repo:<profile>` or `task:<profile>`. Joined, the texts are the launch's context. Per-launch values are placeholders (`<work item id>`, `<session id>`, `<title>`, `<task instruction>`), and nothing launches. An unknown chain, task or repository answers `404`, and a task that is not an agent task answers `422`, as does a task whose harness, skill or steering cannot resolve. A `repos.yaml` that does not load answers `503`. |

Each entry of `nodes` carries `icon`, the node's own [icon](/reference/chain-nodes#icons)
name, or `null` when it sets none (always for a gate).

## Harnesses

The harness routes. The web UI edits harnesses through a draft (`/api/drafts/harnesses/...`); these read the published state.

| Route | Answers |
|---|---|
| `GET /api/harnesses/profiles` | `{profiles, agent_profiles, file, error}`. Each entry of `agent_profiles` has `id`, `used_by`, `chains`, `fallback`, `model` (provider → model id) and `providers` (provider → `{model, effort}`). `effort` is the one effort every provider shares, or `null` when they differ: read `providers` then. `problems` is the list of messages, and `problem_details` the same list as `{profile, provider, field, message}`, where `field` is `model`, `effort`, or `null` for a profile that isn't defined. Each `fallback` entry has its own `problems` and `problem_details`. |
| `GET /api/harnesses` | One entry per provider: `{id, label, executable, executable_found, efforts, models, capabilities}`. `executable_found` is whether the command is on `PATH` now. There is no `version`. |
| `GET /api/harnesses/providers` | Each provider's capability surface. A provider also lists `efforts` and `models`: the plain-word values it limits that option to, `[]` when it takes any string or a pattern. |

## Drafts

The Templates editor keeps unpublished edits on the server, as drafts. There
is one draft per area and key: area `chains` with a chain id as the key (the
file `chains/<id>.yaml`), or area `library` with the key `library` (the file
`library.yaml`). File names are relative to the config directory. An op
can join more files to a draft: `move_to_library` adds `library.yaml` to a
chain's, and renaming a library component adds each chain file it rewrites to
the library's. Each joined file records its own base, and a publish writes
them all. These are board routes, so they can change in any release.

The settings files have drafts too. The key is the area's own name, and a PUT
to a file outside the area's set answers `422`:

| Area and key | Files | Applied by a publish |
|---|---|---|
| `harnesses` | `harnesses.yaml`, `policy.yaml` | Reloads the policy only when `policy.yaml` is in the draft. |
| `repos` | `repos.yaml` | Nothing; `repos.yaml` is read when needed. |
| `policy` | `policy.yaml` | Reloads the policy, as `PUT /api/policy` does. |
| `intake` | `intake.yaml`, `policy.yaml` | Rereads `intake.yaml` and restarts the poller; reloads the policy when `policy.yaml` is in the draft. |

A settings draft's `problems` are every problem its files have, the same checks
the matching `PUT` route runs, so a draft with none is one that route would
accept. Two drafts may hold `policy.yaml`: the first publish wins and the
second answers `409`, which `rebase` resolves. A publish whose apply step fails
has already written its files: it answers `500`, keeps the draft, and tries
again on the next publish.

| Route | Answers |
|---|---|
| `GET /api/drafts` | Every open draft: `area`, `key`, `files` (names), `changes` and `problems` (counts as of its last write), `updated_at`. |
| `GET /api/drafts/{area}/{key}` | `{area, key, draft, files, base, published, updated_at, result}`. `published` holds the text of each file as it is on disk (`null` for one that does not exist yet): the left side of a diff. With no draft, `draft` is `false` and `files` are the published ones. A chain with neither a file nor a draft answers `404`. |
| `PUT /api/drafts/{area}/{key}/files/{file}` | Body `{text}`. Stores the text as typed, comments kept, and answers as `GET` does. The first write makes the draft. A write whose files parse to the published ones drops it. |
| `POST /api/drafts/{area}/{key}/ops` | Body `{ops: [{op, ...}]}`. Applies the [ops](#draft-ops) in order and answers as `GET` does, plus `ops: [{op, result?}]`, each op's own answer. All or nothing, and one request for undo. `?preview=1` answers the same without saving. |
| `POST /api/drafts/{area}/{key}/undo` | Undoes the last request and answers as `GET` does. PUTs to one file less than 4 seconds apart count as one request. `409` when there is nothing to undo. |
| `POST /api/drafts/{area}/{key}/publish` | No body. Writes each file, applies them (the templates are reloaded; a settings area applies as above) and drops the draft. Answers `{published: [files], changes, result}`: `changes` is what was published, as the draft's `result.changes` listed it, and `result` the state after, with no draft left. |
| `POST /api/drafts/{area}/{key}/rebase` | No body. Takes the published files as the draft's new base and keeps its text, so the next publish no longer answers `409`: the way out of a conflict when the draft should win. Pushes no undo entry. Answers as `GET` does, or `404` with no draft. |
| `GET /api/drafts/{area}/{key}/fragment?path=` | `{path, text}`: the YAML of the component at `path` (a task, a node, a policy block), from the draft when there is one, else from the published file. `400` with no `path`, `404` when nothing is there. The text is what `set_fragment` takes back. On a `repos` draft `path` is a repo's path and the answer is read-only (there is no `set_fragment` for it); the other settings areas have no fragments and answer `404`. |
| `GET /api/drafts/policy/{key}/preview?chain=` | A published chain's caps under the `policy` draft: `{chain, scopes: [{path, kind, level, caps}]}`, `kind` being `chain`, `node`, `step` or `task` (a gate waits for a person and has none). Each cap (`time_cap_minutes`, `total_time_cap_minutes`, `token_budget`, `budget_usd`) is `{value, source, maximum, exceeds}`: `source` is `chain`, `library:<section>.<name>`, `policy` or `default`, `maximum` the `{value, level}` bounding it at its level (`null`: no bound) and `exceeds` whether `value` is past it. A read; the draft is unchanged. `404` for a chain not in the library, `422` for a draft that does not load. |
| `DELETE /api/drafts/{area}/{key}` | Discards the draft for good: `204`, or `404` with no draft. |

An unknown area answers `404`, a key the area does not accept (a chain key
that is not a valid chain id) `400`, and a file that is not one of the key's
files `422`. A draft also takes a `PUT` of any file an op joined to it,
such as the new file of a chain the `rename` op moved, which keeps its old key.

`result` is the same on every route:

| Field | Holds |
|---|---|
| `model` | Per file, the mapping it parses to. For a file that does not parse, the newest earlier state that did, else the published file. |
| `resolved` | The chain with `extends` expanded, as `GET /api/templates/chains/{id}/resolved` shows it, or `null` when it does not resolve. |
| `problems` | `[{path, field, message, file, line, col}]`: everything a save would refuse, with every schema error listed. `path` is the component's canonical path (`implementation.main.implement`), `field` the key below it. On the library, everything `PUT /api/templates/library` would refuse, checked against every chain and repo, each problem adding `chain` or `repo` (the one it breaks, or both `null` for one in `library.yaml` itself, whose `path` is the component, `tasks.implementer`) and `component`, the library component it comes from, or `null`. A repo's problem is at `path` `steering` in `repos.yaml`. |
| `sources` | For a chain that resolves, `{path: {field: {value, source}}}` for each node, step, task and fix loop: its own fields, and each `policy.*` cap of its scope. `source` is `chain` (the file sets it at that path), `library:<section>.<name>` (the nearest library component it inherits it from, such as `library:tasks.implementer` or `library:nodes.verification`), `policy` (a cap no layer sets, at the value the scope runs under) or `default`. A subprocess, builtin or forge task leaves out `steering` and the agent-only caps unless it sets them; with an `on_failure` recovery it lists those caps with `recovery: true`, since the recovery runs under them. |
| `changes` | `[{path, kind, summary, fields?}]` against the published chain, `kind` being `add`, `change`, `remove` or `rename`. A reordered component is a `change` whose summary says `moved`. A chain-level key that differs (`description`, `policy`) is one `change` row at the chain's own path, `""`, its summary naming the keys. A chain the `rename` op moved to a new id is one `rename` row at `""`, with `from` and `to` the old and new ids. On the `policy` and `intake` areas each row is one dotted key of a file, `{path, kind, summary, file}`, `summary` reading "was → now" (`not set`, or `no bound` for a maximum); a list of mappings (`schedules:`) is keyed by index (`schedules.0.cron`). On the library, `path` is a component path (`tasks.implementer`, `nodes.verification.review.code_review`) and each change adds `reaches`, the ids of the chains that use the component, as published or as drafted. |
| `impact` | For a chain: `{running, repos}`, the items still running it and the repos whose default it is. For the library: `{chains, repos}`, the chains any change reaches and the repos whose `steering:` names a changed profile. |
| `warnings` | `[{file, message}]` for a file an edit rewrote whole, whose published text has comments a publish would drop. |
| `policy_values` | `{auto_escalate_delay_s, auto_review_attempts}`, the instance's values from `policy.yaml`. |
| `choices` | The closed sets the editors offer, by field: `ref` (a builtin task's actions), `target` (a forge task's targets), `inputs` (what an agent task can ask for) and `grants`. Each is a list of `{value, summary}`, and a `target` also has `waits`, true for one that runs as an external wait. |
| `yaml_error` | Only when a file does not parse: `{file, line, col, message}`. |

A publish checks each file against the one on disk when the file joined the
draft. If any changed since, for example through a save on the Settings
screens, it answers `409` and writes nothing:

```json
{"detail": "published since this draft began: chains/default.yaml",
 "files": {"chains/default.yaml": {"published": "…", "draft": "…", "diff": "--- published/chains/default.yaml\n+++ draft/chains/default.yaml\n…"}}}
```

A draft with a `yaml_error` or any problem answers `422`
`{detail, problems}` and writes nothing either.

### Draft ops

An op edits the chain's model rather than its text, so it writes the whole
file back: the file's comments are dropped, and `warnings` says so until a
`PUT` of that file. A path is a component's canonical path
(`draft_merge_request.open.open`, `verification.fix_loop.judge`), and a
container is a node or one of its handlers (`spec`, `spec.on_failure`).

On the `library` draft, a path starts with the component's section:
`nodes.<name>[.<step>[.<task>]]`, `steps.<name>[.<task>]`, `tasks.<name>`,
`steering.<name>`. Every op below but `add_node`, `new_chain`, `delete_chain`,
`move_to_library` and a chain `rename` applies there, plus `add_component`.
`rename` of a component (`path: tasks.implementer`) also rewrites every
`extends:` or `steering:` entry naming it, in the library and in each chain
file, which joins the draft, and answers `{updated: [{file, path, field}]}`.
`remove` of one leaves its uses as problems and answers them as
`{broken: [{file, path, field}]}`.

| Op | Fields | Does |
|---|---|---|
| `add_node` | `at, id, kind` | Inserts an `exec` or `gate` node at position `at`. An exec node starts with no step, a problem until it has one. |
| `add_step` | `container, at, id?` | Inserts an empty step. The default id is `step_<n>`; a container holding only `main` renames it `step_1` first. |
| `add_task` | `container, step, kind \| extends, id?` | Appends a task of a `kind`, or one extending a library task. The default id is the kind or the library name, made unique with `_2`, `_3`…. |
| `add_task` | `slot, node, kind \| extends` | Fills a named slot: `judge` (the node needs a fix loop), `escalation` or `auto_review`, with the id `judge`, `escalate` or `reviewer`. |
| `add_handler` | `path, kind` | Adds an `on_failure`, `fix_loop` or `on_conflict` handler holding one empty step `main`. |
| `remove_handler` | `path, kind` | Removes it: written `null` when the node's library base supplies one, deleted otherwise. |
| `move` | `path, to, to_step?` | Moves a node, a step, or a task (to `to_step` beside its own) to position `to`. |
| `remove` | `path` | Removes a node, gate, step, task, `fix_loop`, `judge`, `escalation` or `auto_review`. Answers `{broken: [{path, field}]}`, the `reject_to` and `restart_from` references left naming a removed node; they stay as problems. |
| `extend` | `node, base` | Makes the node extend library node `base`, dropping its own `kind`, steps, `on_failure` and `fix_loop`. Answers `{dropped}`. |
| `change_base` | `node, base` | Changes the base, keeping each override the new base can take. Answers `{kept, dropped: [{key, why}]}`; with `?preview=1`, what a change would drop. |
| `new_chain` | `from?` | Starts the key's chain, empty or as a copy of chain `from` under this id. Only for a key with no file and no draft. |
| `delete_chain` | none | Deletes the chain on publish. A repo whose default it is makes that a problem. |
| `set_field` | `path, field, value` | Sets one field (`path: ""` is the chain). `field` is dotted: `policy.max_attempts`, `on_base_changed.restart_from`, `wait.polling.initial_interval`. `null` or `""` removes the key, and so does a value equal to the one the component inherits. Setting `profile` removes `model` and `effort`, and setting either removes `profile`. An empty `on_base_changed.restart_from` removes `on_base_changed` (written `null` when inherited), an empty `artifact` removes `artifact_required` with it, and `artifact_required: false` removes it. `icon` is set like any other field. `id` is refused: use `rename`. |
| `reset_field` | `path, field?` | Removes the key so the inherited or default value applies. With no `field`, removes every override of a component that extends a library one except `id`, `extends`, `icon` and `on_failure`. |
| `rename` | `path, id` | A node or gate also rewrites every `reject_to` and `on_base_changed.restart_from` naming it, and answers `{updated: [{path, field}]}`. A step, task, judge, escalation or reviewer changes its id only. The chain (`path: ""`) moves to `chains/<id>.yaml`, its old file deleted on publish; a repo whose default is the old id makes that a problem. A gate's `artifact` names a document kind, not a node, so a rename never changes it. |
| `set_fragment` | `path, yaml` | Replaces the component at `path` with the YAML mapping, as the component's YAML tab writes it. |
| `move_to_library` | `path, name` | Moves the exec node or task at `path` into `library.yaml` as `nodes.<name>` or `tasks.<name>`, leaving `{id, extends: <name>}` in the chain. `library.yaml` joins the draft. A `name` its section already has is refused. Answers `{path}`, the component's. |
| `add_component` | `section, name, kind?` | Library only. Adds an empty component to `nodes` (an `exec` node with no step, or a `gate`), `steps`, `tasks` (of `kind`, when given) or `steering`, whose empty `instructions` are a problem until written. Answers `{path}`. |

An op that cannot apply (an id that is taken, reserved or malformed, a move that
puts a `reject_to` or `restart_from` target after the node naming it, or a gate
before the node producing its document, a task moved beside one of its name) answers `422`
`{detail, op}`, `op` being its index, and nothing is saved. A fragment that
changes its component's id answers "rename it with rename"; one that does not
parse adds `line` and `col`, counted in the fragment. A draft with a
`yaml_error` answers `409` "fix the YAML first".

### Harnesses ops

On the `harnesses` draft (`harnesses.yaml` and `policy.yaml`), each harness is
`available`, `override` or `never`. That is two `allowed_harnesses` lists in
`policy.yaml`: `available` is in `defaults` and `maxima`, `override` only in
`maxima`, `never` in neither. An absent list means no bound. A list is written
again only when one was there to begin with, or when it leaves a harness out.
A task that selects a `never` harness, or falls back to one, is a problem that
names it, so the draft cannot publish until the task or the state changes. An
`override` harness is allowed only for a task whose own `policy:` widens it.

| Op | Fields | Does |
|---|---|---|
| `set_access` | `harness, state` | Moves the harness to `available`, `override` or `never`. |
| `set_allowed_tools` | `tools` | `maxima.allowed_tools`, or removes it with `null`. |
| `set_escalation` | `harness, grants` | `defaults.escalation_harness` and `escalation_grants`; `null` removes each. |
| `set_harness` | `id, patch` | A harness's own fields in `harnesses.yaml`. `patch` may hold `enabled` (a boolean), `executable` (`null` clears it) and `defaults`, which merges per option (`null` or an empty text removes one). An option the provider does not accept is a problem, not a refusal. Any other key is `422`. |
| `add_profile` | `name, copy_from?` | A new agent profile, empty or a copy of another. |
| `rename_profile` | `name, to` | Renames it and retargets the `fallback:` entries of `harnesses.yaml` that name it. A library or chain task that names it is left dangling, a problem, and answers `{broken: [{chain, path}]}`. |
| `remove_profile` | `name` | `422` while a task or another profile's `fallback:` names it. |
| `set_profile` | `name, patch` | `patch` may hold `providers` (per provider `{model, effort?}`, `null` removes one, and an older profile becomes this shape), or `model` and `effort` for an older profile, and `fallback` (replaces the list, or `null`). Both shapes in one patch is `422`. |

The answer's `resolved` lists `harnesses` (`id`, `state`, `executable_found`,
and from `harnesses.yaml` its `provider`, `enabled`, `executable` and
`defaults`, plus `tasks`: the agent tasks that select it, `{chain, path,
profile, fallback: false}`, and those whose `fallback:` list lands on it, with
`fallback: true`), `allowed_tools`, `escalation` (what the file says),
`escalation_effective` (`{harness, set}`: the harness a launch uses, `claude`
when the key is unset) and `profiles` (their providers and the tasks that use
them); `impact` counts the tasks whose harness changed state. A problem about a
task of a chain carries that task's `path` where the message names one, and
escalation running on a `never` harness is a problem at
`defaults.escalation_harness` in `policy.yaml`.

### Repos ops

On the `repos` draft (`repos.yaml`). `PATCH /repos` is unchanged. `DELETE /repos?path=` answers `409`, naming the count, while a work item that has not ended (active, paused or needs_human) uses the repo, as `remove_repo` reports it as a problem.

| Op | Fields | Does |
|---|---|---|
| `add_repo` | `path, fields?` | A new entry, disabled and managed, with `fields` on top. The path is not probed; a path that is not a git repository is a problem. |
| `set_repo` | `path, patch` | Any entry field; `null` clears it. Like `PATCH /repos`, it marks the entry managed. |
| `remove_repo` | `path` | Drops the entry. A problem while the repo has items that have not ended. |
| `connect_detected` | `path` | A detected (`managed: false`) entry becomes `managed: true`. |

The answer's `resolved` has `repos` and `detected`. Each carries `resolved` and
`sources` for `steering`, `deny_tools`, `models` and each `policy` key. `steering`
is `repo` or `library` (the chains' steering), the rest are `repo` or `default`.
Problems name the repo: a `policy:` that relaxes the instance's safety layer
(the same refusal a run gives), a path that is not a git repository, and a
`default_chain` that is no chain. `impact.running` is the count of
items not ended, per repo path.

### Policy ops

On the `policy` draft (`policy.yaml`). `PUT /policy` is unchanged.

| Op | Fields | Does |
|---|---|---|
| `set_value` | `scope, key, value` | One setting, by dotted `key`: `limits` is `budget.work_item_usd`, `budget.daily_usd`, `defaults\|maxima.max_attempts`, `defaults\|maxima.timeout_minutes` and `defaults\|maxima.<level>.<cap>`; `escalation` and `retries` their named keys. `null` removes it and any section it leaves empty. The `loops` scope takes `default.attempts` and `default.wall_clock_s` (the `default:` block), the `housekeeping` scope `max_concurrent` and `archive.after_days`, and the `findings` scope `findings.loop_severities` (a list of `critical`, `important`, `minor`); each key is its dotted path in `policy.yaml`. Any other key, and the `harnesses` scope, is `422`. |
| `set_loop` | `key, max_attempts?, wall_clock_s?` | The `loops:` entry for a loop (`<node id>.fix_loop`), starting from `default:`. A key naming no loop is kept and shown as a problem. |
| `remove_loop` | `key` | Drops the entry. `422` when it is not there. |

The answer's `resolved` has `limits`, `loops`, `escalation`, `retries`,
`housekeeping` (`max_concurrent`, `archive_after_days`), `findings`
(`loop_severities`), `harnesses` (read-only) and `other` (read-only). Each value is
`{value, source}`: `policy` or `default`; a cap's `source` is the level
(`work_item`, `nodes`, `steps`, `tasks`) that sets it, and an unset maximum is
`{value: null, source: null}`. Each cap also has `below`: every scope of the
published library's chains that sets that cap itself, `{layer, chain, path, via,
value, exceeds}`, `layer` being `chain` (the chain file) or `library` (a
component it extends, named in `via`), `path` the scope's canonical path (the
chain's id for the chain itself) and `exceeds` whether `value` is past the
draft's maximum at that level; `[]` when nothing sets it. `limits.work_item_usd` also has `binding`, the
lower of the dollar caps (`budget.work_item_usd`, `maxima.work_item.budget_usd`,
`defaults.work_item.budget_usd`) and the key that sets it. `loops.live` lists every
fix loop in the library with its `attempts` and `wall_clock_s` and the layer that
wins (`loop`, `node`, `chain`, `defaults` or `maxima`, `loops`, `default`; a wall
clock has no `loop` layer). A work item's own override is not in it. Problems
carry `scope` (the group) and, for a cap, `level`; a `loops:` key naming no
loop in the library, and a limit a chain already exceeds (naming the `chain`),
are problems.

`GET /api/policy` also answers `active_count` (items running now), and its
`max_concurrent` is the value the loaded policy runs under. A body sent back
to `PUT /api/policy` may keep `active_count`; it is ignored.

### Intake ops

On the `intake` draft (`intake.yaml`, its `schedules:` included).
`GET /api/intake` and `PUT /api/intake` are unchanged.

| Op | Fields | Does |
|---|---|---|
| `set_intake` | `patch` | Any of `enabled`, `interval_s` (at least 30), `priority_ceiling` (0 to 4) and `repos`, written to `intake.yaml`, which gets its defaults for any key it did not have. Any other key is `422`; `max_concurrent` is the `policy` draft's. |
| `add_schedule` | `cron, repo, chain, title, description?` | Appends a `schedules:` entry. |
| `set_schedule` | `index, patch` | Changes fields of the entry at `index`. `422` for an index that is not there or a key that is no schedule field. |
| `remove_schedule` | `index` | Drops the entry. |

The answer's `resolved` is `{enabled, interval_s, priority_ceiling, repos, schedules}`,
each schedule `{index, cron, repo, chain, title, description}`. A schedule whose `repo` is not
connected or whose `chain` is not in the library is a problem carrying its `schedule` index. A
publish applies without a restart: the poller is replaced, and the new interval and
schedules are live.

`GET /api/intake/checks?limit=` answers what each recent poll found, newest first:
`[{id, at, ready, started, skipped}]`. `limit` defaults to 20 and is at most 100;
the newest 500 polls are kept. `ready` is how many beads were ready, `started` the
work item ids it filed, and `skipped` the beads it left alone, each
`{bead_id, reason}` with `reason` one of `above_priority_ceiling`, `already_item`, `epic`,
`max_concurrent`, `daily_budget` or `invalid_config`. A check is not a work item event.

### Item drafts

A work item's own chain has one draft too: a list of ops a person has not
applied yet, kept until it is applied or discarded. A worker cannot read or
change its own item's draft (`403`), and an ended item's answers `409`.

| Route | Answers |
|---|---|
| `GET /api/work-items/{id}/draft` | `{ops, problems, checks, nodes, base_seq, updated_at}`. With no draft, `ops` is `[]` and `nodes` is the item's chain. |
| `PUT /api/work-items/{id}/draft` | Body `{ops: [{op, ...}]}`. Replaces the whole list and answers as `GET` does. An empty list deletes the draft. A malformed op answers `422`. |
| `DELETE /api/work-items/{id}/draft` | Discards the draft: `204`, or `404` with no draft. |
| `POST /api/work-items/{id}/draft/apply` | No body. Applies every op at once, in one transaction, and answers as `GET` does with the draft gone. |

| Op | Fields | Does |
|---|---|---|
| `override` | `path, task_config?, policy?` | Sets what a retry's override may set at that path, within the same bounds: no structural field, policy only tightened or kept under the maxima, a harness inside `allowed_harnesses`. |
| `add_node` | `after, node` | Adds a node built from library components only, as a chain revision adds one: `node` is `{id, extends}`, or `{id, tasks}` or `{id, steps}` of library tasks. |
| `remove_node` | `node` | Takes the node out of the chain. A gate, a node that is not skippable, or a node that lands the merge request cannot be removed. |
| `skip` | `path` | Skips a step or a task: applying records it as `scope_skipped`, so the walk passes it. |

In the answer, each op carries `passed`: `true` once the item has reached the
node it acts on (for `add_node`, gone past the node it follows). A passed op is
not applied, and `nodes` (the chain in the `chain_definition` node shape) has
every other op applied. `problems` is `[{op, message}]`, `op` being the op's
index. `checks` is `{budget, added}`. `budget` is `{spent_usd, cap_usd}`, the item's
spend against its cap, as `budget_cap` on `GET /api/work-items/{id}` reports it.
`added` has one `{op, node, harnesses, estimate_usd, estimate_runs}` for each `add_node` that is
not passed and has no problem: `harnesses` are the harnesses its agent tasks run
on (one outside the policy's `allowed_harnesses` is a problem on that op, so these
are allowed), and `estimate_usd` is what a node of that id has cost per item, averaged over `estimate_runs` items of the
instance; both are `null` when none has run. The estimate is information and blocks nothing. An `override` outside its
policy maximum is a `problems` entry on its op whose message starts with the field.

An apply re-reads the item inside its transaction. If any op is passed by
then, it answers `409` and writes nothing:

```json
{"detail": "the item has moved past some of this draft's ops; remove them or move them after the current node",
 "passed": [0]}
```

Any problem answers `422` `{detail, problems}`. Otherwise the revised chain
replaces the item's, recorded as `chain_revised` with `source: "draft"`, each
`skip` is recorded, and the draft is deleted. On a running item it takes effect
at the next node boundary; the node running finishes as it started. Nothing is
moved for you: drop a passed op from the list, or change it to act after the
current node.

## Saved but not applied

`GET /api/apply` answers what is saved and not running yet:
`{restart: [{id, file, text}], reload: [{id, file, text, problem?}], managed}`, both lists empty when
nothing is pending. `managed` is true when a service manager started this server, the only case
`POST /api/apply/restart` can restart it.

- A `restart` item is `access.bind` or `access.port`: `access.yaml` names an address the server is not bound to.
  It is left out when `KRAFT_HOST` or `KRAFT_PORT` is set, since the environment wins and a restart would change nothing.
- A `reload` item is `disk:<file>` for `library.yaml`, `chains/*.yaml`, `policy.yaml` or `intake.yaml` whose bytes
  differ from the ones last loaded. A file rewritten with the same bytes is no change. `problem` is the first
  problem found in the file as it is on disk.

`POST /api/apply/reload` rereads the library, `policy.yaml` and `intake.yaml` (and replaces the intake poller),
and answers the new `GET /api/apply`. `POST /api/templates/reload` does the same. A policy or an
`intake.yaml` that does not load is refused and stays pending, with its `problem`, and the
running one is kept. `POST /api/templates/reload` answers `{valid, invalid_templates,
refused_policy, refused_intake}`, the last two each the refusal's reason or `null`; `kraft admin
reload` prints them and exits 1 on either.

`POST /api/apply/restart` restarts the server when a service manager started it (the
launchd or systemd unit `kraft admin install-service` writes). It answers `202` and runs
`kraft admin restart` detached. A server started from a terminal answers `409`
`{"detail": "started from a terminal: restart it there"}`. Nothing restarts the server
unless this is called. The restart ends the agent of every active item, and each stops as
failed until it is retried, as `kraft admin restart` warns: see
[A restart ends running agents](/get-started/install#a-restart-ends-running-agents). The web
UI counts the active items from `GET /api/work-items` (the rows whose `status` is `active`) and
shows the number in its confirmation.

The `apply_changed` live message says when this list changes.

## Update check

`GET /api/update?channel=` answers `{installed, latest, channel, python, behind, checked_at}`; `python` is the interpreter the server runs on, as `3.14`.
`channel` is one of `stable`, `rc`, `beta` and `alpha` (`400` otherwise) and defaults to
the installed version's own; it is not stored. The answer comes from the daily
cached check. `POST /api/update/check?channel=` skips the cache and asks the
release feed now, and answers the same shape.

When the feed cannot be reached, `latest` and `behind` are `null`: unknown, not "up
to date". `checked_at` is the time of the last check that succeeded on that channel
(`null` when there has been none), so it can be old while `latest` is `null`. Installing
the update is `kraft admin update`; the server never does it.

## Editors

`GET /api/editors` answers `{available, system, default}`: `available` lists
the editors (`code`, `cursor`, `zed`, `obsidian`) whose executable this
server's machine has on its `PATH`, or, on macOS, whose app is installed in
`/Applications` or `~/Applications` (it is then opened with `open -a`); `system` says whether the system opener
(`open`, `xdg-open`) is there, and `default` is `editor` from `theme.yaml`,
else `KRAFT_EDITOR`, else `null`. It is loopback only, as
`POST /api/documents/{id}/open` is: any other caller gets `403`. `POST /api/work-items/{id}/artifact/open` opens the pending gate's document in the item's worktree (`GET /api/work-items/{id}/artifact` carries its `absolute_path`), with the same rule. These routes and `POST /api/work-items/{id}/open-worktree` take `{editor}`: a name from `available`, `"system"` for the system opener, or `null` (or nothing) for the `default` above, else the system opener.

## The schema

FastAPI generates a schema of every route:

| Path | What it serves |
|---|---|
| `/openapi.json` | The OpenAPI schema, as JSON. Its `info` names Kraft and the installed version. |
| `/docs` | Swagger UI for that schema. |
| `/redoc` | ReDoc for that schema. |

```bash
curl -s http://127.0.0.1:8765/openapi.json | jq '.paths | keys'
```

These three paths need no login. Open `/docs` or `/redoc` in a browser to read
the API there. Both pages load their scripts from a public CDN, jsdelivr. Each
script is pinned to one exact release, and your browser refuses it unless it
matches the hash Kraft ships. Nothing else on either page comes from another
site: their policy lets an image load only from Kraft itself or inline, so
ReDoc's "Redocly" logo is not fetched. On a machine without internet access,
load `/openapi.json` into your own OpenAPI viewer.

## Who may call

| Caller | What it needs |
|---|---|
| A process on the same machine, while Kraft is bound to loopback | Nothing, as long as it addresses the server as `127.0.0.1`, `localhost` or `[::1]`. |
| Anyone, once Kraft is bound off loopback | A browser session from the login page, or the MCP bearer token in `$KRAFT_HOME/run/mcp-token`, sent as `Authorization: Bearer <token>`. |
| A trigger sender, once Kraft is bound off loopback | For `POST /api/triggers` only, the trigger token in `$KRAFT_HOME/run/trigger-token`, sent the same way. |
| A remote caller while no password is set | Nothing works. Kraft answers `403`. |

A request without valid credentials gets `401`. A request whose `Host` is not
an allowed name gets `403` ("unexpected Host for a server bound to …"). On a
loopback bind that is any request not addressed to `127.0.0.1`, `localhost` or
`[::1]`. Off loopback it is a browser request (one that sends `Sec-Fetch-Site`,
`Origin`, `Referer` or an HTML `Accept`) whose `Host` is neither a loopback
name nor in `allowed_hosts`; the CLI, MCP and `curl` need no entry there. A
browser opening a page (a `GET` outside `/api` with an HTML `Accept`) gets the
`403` as a short HTML page instead, naming the `Host` it sent and how to allow
it. A cross-site
write also gets `403`. The `/api/ws/events` WebSocket applies the same `Host`
rules, and refuses the handshake (`403`) when its `Origin` is another site's. The MCP bearer token is
a full-access credential. See [Security](/project/security) for the whole
model, and [Remote access](/guides/remote-access) to set a password.
