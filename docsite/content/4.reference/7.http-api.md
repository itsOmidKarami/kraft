title: HTTP API

The Kraft server serves its board, and the JSON API behind it, on one port
(`127.0.0.1:8765` by default). The `kraft` command and the MCP server are
clients of that API.

## Stable routes

Only two routes are meant for other programs, and only these keep their shape
between minor releases. See
[Versioning and stability](/project/status-and-support#versioning-and-stability).

| Route | Use |
|---|---|
| `POST /api/triggers` | File a work item from a webhook or script. See [Inbound triggers](/reference/triggers#post-apitriggers). |
| `GET /api/health` | Check that the server is up. Answers `status` (`ok` or `degraded`), the reasons it is degraded, and which instance this is (`run_dir`, `pid`, `bind`, `port`). Needs no login. |

Every other route under `/api/`, and the `/api/ws/events` WebSocket, exists
for the board and can change in any release. For those, prefer the `kraft`
command with `--json`, which is stable.

`POST /api/work-items`, the board's create route, files the item paused unless
the body sets `autostart: true`, like `kraft item create` without
`--autostart`. A body with no `chain_template` gets the repo's
`default_chain_template`. Every repo path you send must be absolute: the
server would read a relative one against its own directory, not yours.
`POST /api/repos`, `POST /api/work-items` and `POST /api/triggers` refuse it
with a `422`, and `PATCH` or `DELETE /api/repos?path=` answer `404`.

## Work item status

`GET /work-items` and `GET /work-items/{id}` both carry two read-only fields
on every item, computed on read rather than stored (see
[Displayed status](/concepts/how-a-work-item-runs#displayed-status)):

| Field | Meaning |
|---|---|
| `display_status` | The board's status badge: one of `archived`, `done`, `cancelled`, `paused`, `running`, `waiting`, `needs_you`, `escalated`, `failed`. |
| `stop` | `null` unless the item is `needs_human`, `waiting` or `rate_limited`. On the list, `{kind, node, resume_at, reason}`; on the detail, also `task`, `attempt` and `facts`. |

`stop.kind` is one of `gate`, `question`, `cap`, `budget`, `failed`,
`conflict`, `mr_closed`, `config`, `infra`, `stuck`, `wait`, `rate_limit` (see
[Events → work_item_needs_human](/reference/events#work_item_needs_human) for
what each means). A `rate_limit` stop's `facts` also carries `fallback` and
`fallback_allowed` -- the stopped task's declared fallback harnesses, and
which of those its resolved policy still allows.

## Cancelling

`GET /work-items/{id}/cancel-preview` shows what `POST /work-items/{id}/cancel`
would do, without doing it: `409` once the item has already ended, same as
`/cancel` itself.

```json
{
  "running": {"node": "mr_checks", "task": "mr_checks", "attempt": 1} | null,
  "kept": {"branch": "kraft/...", "worktree": "/path", "findings": 0, "threads": 1},
  "mr": {"ref": 54, "url": "https://...", "state": "open"} | null,
  "spend": {"spent_usd": 1.2, "cap_usd": 5.0}
}
```

`running` is the item's running session, if any; `kept` is what cancel leaves
behind (cancel never removes the worktree or the branch); `mr` is the item's
merge request and its live state, or `null` before one was ever opened.

`POST /work-items/{id}/cancel` takes an optional `close_mr: bool = false`.
When set and the item's merge request is open, cancel closes it on the forge
once the cancel itself has landed and the response gains `close_mr: {ok:
true}` (or `{ok: false, error}` when there was no open merge request or the
forge call failed -- a failed close never undoes the cancel). The key is
absent when `close_mr` was not asked for.

## Retrying, duplicating, acting in bulk

`POST /work-items/{id}/retry`'s response gains `attempt`: the attempt number
the task it relaunches will run as -- the count of that (item, node, task)'s
own sessions so far, plus one. A `path` naming one task counts only that
task's sessions; a `path`-less retry (the whole stopped node, or `restart`'s
whole chain) takes the highest next-attempt over all of the node's own tasks,
since a walk may enter at any one of them.

`POST /work-items/{id}/duplicate` files a fresh, paused item from `{id}`'s own
title, description, repo, chain template, workspace selection and
attachments (re-snapshotted under the new item's own id). Any source status is
accepted, archived and cancelled included. No run state, override, policy
override, budget or bead link carries over -- this is a fresh intake, not a
clone of the row.

```json
{"id": "...", "status": "paused", "duplicate_warning": "..."}
```

`duplicate_warning` is present only when another open item looks like a
duplicate, the same check `POST /work-items` makes. A source whose stored
attachment copy has gone missing answers `409` naming it, before anything is
filed.

`POST /work-items/bulk` applies one action to several items at once:

```json
{"action": "pause", "ids": ["...", "..."], "reason": "..."}
```

`action` is one of `pause`, `cancel`, `archive`, `restore` -- the same door
each one's own single-item route already has, called once per id, each in its
own write, in `ids` order. `reason` is required, and checked before anything
is touched, when `action` is `cancel` (`422` otherwise); the other three
ignore it. The response is one result per id, in order:

```json
{"results": [{"id": "...", "ok": true, "status": "paused"}, {"id": "...", "ok": false, "error": "..."}]}
```

An id whose action raises (an item in the wrong status, say) becomes `{id,
ok: false, error}` and the rest of the batch still runs; an id naming no work
item answers `{id, ok: false, error: "not found"}`. `status` is the item's
stored status after the action ran.

## MR closed externally

A poller checks every `waiting`/`needs_human` item parked at a merge-request
node against the forge every `policy.forge_poll_s` seconds (default 300). When
the merge request was closed there without merging, it stops the item with
`stop.kind: "mr_closed"` and `facts: {ref, url}` (see [Events →
work_item_needs_human](/reference/events#work_item_needs_human)).

`POST /work-items/{id}/reopen-mr` reopens that merge request on the forge and
retries the stopped node, the same as `POST /work-items/{id}/retry` with no
`path` -- it answers `409` unless the item is actually stopped with
`stop.kind: "mr_closed"`, and `502` with the forge's own message when the
forge call fails (the item stays stopped). Its response is `/retry`'s own
response shape. "Open a new MR" instead is `/retry` with the MR node's path;
cancelling the item instead is `/cancel`.

## Daily total and dry run

`GET /budget/today` answers the instance's spend since local midnight against
`policy.budget.daily_usd`:

```json
{"spent_usd": 3.4, "cap_usd": 20.0}
```

`cap_usd` is `null` when `policy.budget.daily_usd` is unset. `GET
/work-items/{id}`'s `budget_cap` gains the same two numbers under `daily`
(`{spent_usd, cap_usd}`); its three existing keys (`cap_usd`, `source`,
`spent_usd`) are unchanged and stay the item's own, all-time spend.

`POST /work-items?dry_run=1` runs every check `POST /work-items` runs, up to
and including validating `node_overrides`, then answers `200` without filing
anything -- no row, no bead, no attachment copy, no spawn. A body that would
answer `422` or `503` on an ordinary create answers the same on a dry run.

```json
{
  "dry_run": true,
  "nodes": [...],
  "skipped": [{"node": "spec", "why": "covered_by", "kind": "spec"}, {"node": "...", "why": "skip"}],
  "gates": ["spec_approval", "..."],
  "caps": {
    "budget_usd": 5.0,
    "budget_source": "item",
    "daily_usd": 20.0,
    "nodes": {"implement": {"attempts": 3, "wall_clock_s": 7200}}
  }
}
```

`nodes` is the chain that would be filed, in `chain_definition`'s own node
shape. `skipped` lists every node the attachments or `skip_nodes` dropped:
`covered_by` names the attachment kind that made it redundant, `skip` is an
operator's own choice. `gates` is the ids of the gate nodes left in the chain.
`caps.budget_usd`/`budget_source` mirror the create route's own cap
resolution (`"item"` for the body's own `budget_usd`, else `"policy"`);
`caps.nodes` is each fix-loop node's `attempts`/`wall_clock_s`, resolved the
same way the walk resolves them at run time -- the node's own `policy`,
`node_overrides` entry and any item-wide override each layered on in the same
order, so a node's own override and an item-wide value each show where they
apply.

## Events paging and the run summary

`GET /work-items/{id}/events` normally returns every event after `after_seq`
(`0` by default). `before_seq` pages backward instead: it returns the last
`limit` events with `seq < before_seq`, oldest first, in the same row shape --
100 when `before_seq` is given with no `limit`. `limit` alone bounds
`after_seq`'s own forward window to the first `limit` events after it (1-500;
outside that range, or passing both cursors at once, answers `422`). Every
event row carries a `node_id` (see [Events](/reference/events)).

`GET /work-items/{id}` adds `summary`, a run's progress at a glance:

```json
{"nodes_done": 3, "nodes_total": 8, "gates_passed": 1, "step": {"index": 2, "count": 2} | null}
```

`nodes_done`/`nodes_total` count against the frozen chain; `gates_passed` is
how many of the completed nodes were gates. `step` is the current node's step
(1-based) out of its own steps, read from its latest non-escalation session's
task, when the node declares more than one -- `null` otherwise.

`GET /api/work-items/{id}/diff` and `GET /api/work-items/{id}/compare` take an
optional `ignore_whitespace=true`, like `git diff -w`. A file whose only change
is whitespace then drops out of `files`, the per-file counts and `diff` together,
so the three never disagree; `touched_by` and `untracked` do not follow it. Both
answers carry `ignore_whitespace`, the value they used.

`GET /api/work-items/{id}` carries `fix_target` while a gate is pending: the
`node` a request-changes review restarts at, the nodes `then` that run before it
returns to the `gate`, and the `round` (`n` of `max`) a rejection now would start,
counted against the cap the gate's reject loop already snapshotted. It is `null`
with no gate pending. `GET /api/work-items/{id}/fix-target?node=&gate=` answers
for a target the reviewer picked; with no gate pending it gives what a gateless
`request_changes` would target, with `reason` one of `requested` (you named the
node), `threads on <path or node>`, `current node`, or `gate`. It answers `400`
for a node that is not before the gate, `409` for a gate that is not pending or an
ended item, and does git work per thread, so call it on demand.

A review submitted with `outcome: approve` takes an optional `digest`, passed to
the gate approval as `POST /gates/{gate}/approve` takes it. A chain revision gate
needs it (the one `GET /artifact` returned) and answers `409` without it or with a
stale one; any other gate ignores it.

`GET /api/work-items/{id}/compare` marks each file `viewed`. `PUT` and
`DELETE /api/work-items/{id}/viewed?file=<path>&to=<target>` set and clear the
mark and answer `{file, to, viewed}`; `to` is a compare target (default `latest`)
and `file` a repository-relative path. A mark belongs to the file's content at
`to`, not to the `from` side, so a file that has not changed since you ticked it
stays ticked in any other comparison and a new attempt that edits it clears the
tick. `DELETE` clears the mark on that content wherever it was made. The routes
answer `404` for a target the item does not have and `400` for a path outside the
repository.

## Chain templates

These board routes read the chains the Templates editor shows.

| Route | Answers |
|---|---|
| `GET /api/templates/chains` | Every chain: `id`, `description` (or `null`), `nodes`, `gates`, `error` and `uses`. A chain that does not resolve still has its `description`, with `nodes` empty and `error` saying why. |
| `GET /api/templates/chains/{id}/resolved` | `{id, chain, task_paths, steering, nodes, documents}`. `documents` maps each gate id to the document kinds the exec nodes before it produce, in chain order: what that gate's `artifact` can name. |
| `GET /api/templates/library` | `{file, text, components}`. Each component has `id` (`tasks.implementer`), `kind` (its section), `name`, `definition` as written, `issues`, `used_by` (the ids of the chains that use it) and `used_by_paths: [{chain, path, overrides, via?}]`: each component of a chain that extends or selects it. `path` is that component's canonical path, `overrides` whether it sets any key besides `id`, `extends` and `kind`, and `via` the library node it reaches the chain through, when it sits in that node's own definition (`{chain: "default", path: "verification.review.code_review", overrides: false, via: "verification"}`). |
| `GET /api/templates/steering/preview?chain=&task=&repo=` | `{sections: [{kind, source, text}]}`: what the agent task at canonical path `task` of chain `chain` reads at launch in the repository whose `name` or `path` is `repo`, section by section in launch order. `kind` is `contract`, `document` (`source` is the kind it produces), `review_package`, `skill` (`source` is the skill), `intent` (`source` is the repository's `intent_dir`), `steering` or `usage`. There is one `steering` section per profile: the repository's first, then the task's, with `source` `repo:<profile>` or `task:<profile>`. Joined, the texts are the launch's context. Per-launch values are placeholders (`<work item id>`, `<session id>`, `<title>`, `<task instruction>`), and nothing launches. An unknown chain, task or repository answers `404`, and a task that is not an agent task answers `422`, as does a task whose harness, skill or steering cannot resolve. A `repos.yaml` that does not load answers `503`. |

Each entry of `nodes` carries `icon`, the node's own [icon](/reference/chain-nodes#icons)
name, or `null` when it sets none (always for a gate).

## Drafts

The Templates editor keeps unpublished edits on the server, as drafts. There
is one draft per area and key: area `chains` with a chain id as the key (the
file `chains/<id>.yaml`), or area `library` with the key `library` (the file
`library.yaml`). File names are relative to the templates directory. An op
can join more files to a draft: `move_to_library` adds `library.yaml` to a
chain's, and renaming a library component adds each chain file it rewrites to
the library's. Each joined file records its own base, and a publish writes
them all. These are board routes, so they can change in any release.

| Route | Answers |
|---|---|
| `GET /api/drafts` | Every open draft: `area`, `key`, `files` (names), `changes` and `problems` (counts as of its last write), `updated_at`. |
| `GET /api/drafts/{area}/{key}` | `{area, key, draft, files, base, updated_at, result}`. With no draft, `draft` is `false` and `files` are the published ones. A chain with neither a file nor a draft answers `404`. |
| `PUT /api/drafts/{area}/{key}/files/{file}` | Body `{text}`. Stores the text as typed, comments kept, and answers as `GET` does. The first write makes the draft. A write whose files parse to the published ones drops it. |
| `POST /api/drafts/{area}/{key}/ops` | Body `{ops: [{op, ...}]}`. Applies the [ops](#draft-ops) in order and answers as `GET` does, plus `ops: [{op, result?}]`, each op's own answer. All or nothing, and one request for undo. `?preview=1` answers the same without saving. |
| `POST /api/drafts/{area}/{key}/undo` | Undoes the last request and answers as `GET` does. PUTs to one file less than 4 seconds apart count as one request. `409` when there is nothing to undo. |
| `POST /api/drafts/{area}/{key}/publish` | No body. Writes each file, reloads the templates and drops the draft. Answers `{published: [files], result}`. |
| `DELETE /api/drafts/{area}/{key}` | Discards the draft for good: `204`, or `404` with no draft. |

An unknown area answers `404`, a key the area does not accept (a chain key
that is not a valid chain id) `400`, and a file that is not one of the key's
files `422`. A draft also takes a `PUT` of any file an op joined to it,
such as the new file of a chain the `rename` op moved, which keeps its old key.

`result` is the same on every route:

| Field | Holds |
|---|---|
| `model` | Per file, the mapping it parses to. For a file that does not parse, the newest earlier state that did, else the published file. |
| `resolved` | The chain with `extends` expanded, as `GET /api/templates/chains/{id}/resolved` shows it, or `null` when it does not resolve. |
| `problems` | `[{path, field, message, file, line, col}]`: everything a save would refuse, with every schema error listed. `path` is the component's canonical path (`implementation.main.implement`), `field` the key below it. On the library, everything `PUT /api/templates/library` would refuse, checked against every chain and repo, each problem adding `chain` or `repo` (the one it breaks, or both `null` for one in `library.yaml` itself, whose `path` is the component, `tasks.implementer`) and `component`, the library component it comes from, or `null`. A repo's problem is at `path` `steering` in `repos.yaml`. |
| `sources` | For a chain that resolves, `{path: {field: {value, source}}}` for each node, step, task and fix loop: its own fields, and each `policy.*` cap of its scope. `source` is `chain` (the file sets it at that path), `library:<section>.<name>` (the nearest library component it inherits it from, such as `library:tasks.implementer` or `library:nodes.verification`), `policy` (a cap no layer sets, at the value the scope runs under) or `default`. |
| `changes` | `[{path, kind, summary, fields?}]` against the published chain, `kind` being `add`, `change` or `remove`. A reordered component is a `change` whose summary says `moved`. On the library, `path` is a component path (`tasks.implementer`, `nodes.verification.review.code_review`) and each change adds `reaches`, the ids of the chains that use the component, as published or as drafted. |
| `impact` | For a chain: `{running, repos}`, the items still running it and the repos whose default it is. For the library: `{chains, repos}`, the chains any change reaches and the repos whose `steering:` names a changed profile. |
| `warnings` | `[{file, message}]` for a file an edit rewrote whole, whose published text has comments a publish would drop. |
| `policy_values` | `{auto_escalate_delay_s, auto_review_attempts}`, the instance's values from `policy.yaml`. |
| `yaml_error` | Only when a file does not parse: `{file, line, col, message}`. |

A publish checks each file against the one on disk when the file joined the
draft. If any changed since, for example through a save on the Settings
screens, it answers `409` and writes nothing:

```json
{"detail": "published since this draft began: chains/default.yaml",
 "files": {"chains/default.yaml": {"published": "…", "draft": "…", "diff": "--- published/chains/default.yaml\n+++ draft/chains/default.yaml\n…"}}}
```

A draft with a `yaml_error` or any problem answers `422`
`{detail, problems}` and writes nothing either.

### Draft ops

An op edits the chain's model rather than its text, so it writes the whole
file back: the file's comments are dropped, and `warnings` says so until a
`PUT` of that file. A path is a component's canonical path
(`draft_merge_request.open.open`, `verification.fix_loop.judge`), and a
container is a node or one of its handlers (`spec`, `spec.on_failure`).

On the `library` draft, a path starts with the component's section:
`nodes.<name>[.<step>[.<task>]]`, `steps.<name>[.<task>]`, `tasks.<name>`,
`steering.<name>`. Every op below but `add_node`, `new_chain`, `delete_chain`,
`move_to_library` and a chain `rename` applies there, plus `add_component`.
`rename` of a component (`path: tasks.implementer`) also rewrites every
`extends:` or `steering:` entry naming it, in the library and in each chain
file, which joins the draft, and answers `{updated: [{file, path, field}]}`.
`remove` of one leaves its uses as problems and answers them as
`{broken: [{file, path, field}]}`.

| Op | Fields | Does |
|---|---|---|
| `add_node` | `at, id, kind` | Inserts an `exec` or `gate` node at position `at`. An exec node starts with no step, a problem until it has one. |
| `add_step` | `container, at, id?` | Inserts an empty step. The default id is `step_<n>`; a container holding only `main` renames it `step_1` first. |
| `add_task` | `container, step, kind \| extends, id?` | Appends a task of a `kind`, or one extending a library task. The default id is the kind or the library name, made unique with `_2`, `_3`…. |
| `add_task` | `slot, node, kind \| extends` | Fills a named slot: `judge` (the node needs a fix loop), `escalation` or `auto_review`, with the id `judge`, `escalate` or `reviewer`. |
| `add_handler` | `path, kind` | Adds an `on_failure`, `fix_loop` or `on_conflict` handler holding one empty step `main`. |
| `remove_handler` | `path, kind` | Removes it: written `null` when the node's library base supplies one, deleted otherwise. |
| `move` | `path, to, to_step?` | Moves a node, a step, or a task (to `to_step` beside its own) to position `to`. |
| `remove` | `path` | Removes a node, gate, step, task, `fix_loop`, `judge`, `escalation` or `auto_review`. Answers `{broken: [{path, field}]}`, the `reject_to` and `restart_from` references left naming a removed node; they stay as problems. |
| `extend` | `node, base` | Makes the node extend library node `base`, dropping its own `kind`, steps, `on_failure` and `fix_loop`. Answers `{dropped}`. |
| `change_base` | `node, base` | Changes the base, keeping each override the new base can take. Answers `{kept, dropped: [{key, why}]}`; with `?preview=1`, what a change would drop. |
| `new_chain` | `from?` | Starts the key's chain, empty or as a copy of chain `from` under this id. Only for a key with no file and no draft. |
| `delete_chain` | none | Deletes the chain on publish. A repo whose default it is makes that a problem. |
| `set_field` | `path, field, value` | Sets one field (`path: ""` is the chain). `field` is dotted: `policy.max_attempts`, `on_base_changed.restart_from`, `wait.polling.initial_interval`. `null` or `""` removes the key, and so does a value equal to the one the component inherits. Setting `profile` removes `model` and `effort`, and setting either removes `profile`. An empty `on_base_changed.restart_from` removes `on_base_changed` (written `null` when inherited), an empty `artifact` removes `artifact_required` with it, and `artifact_required: false` removes it. `icon` is set like any other field. `id` is refused: use `rename`. |
| `reset_field` | `path, field?` | Removes the key so the inherited or default value applies. With no `field`, removes every override of a component that extends a library one except `id`, `extends`, `icon` and `on_failure`. |
| `rename` | `path, id` | A node or gate also rewrites every `reject_to` and `on_base_changed.restart_from` naming it, and answers `{updated: [{path, field}]}`. A step, task, judge, escalation or reviewer changes its id only. The chain (`path: ""`) moves to `chains/<id>.yaml`, its old file deleted on publish; a repo whose default is the old id makes that a problem. A gate's `artifact` names a document kind, not a node, so a rename never changes it. |
| `set_fragment` | `path, yaml` | Replaces the component at `path` with the YAML mapping, as the component's YAML tab writes it. |
| `move_to_library` | `path, name` | Moves the exec node or task at `path` into `library.yaml` as `nodes.<name>` or `tasks.<name>`, leaving `{id, extends: <name>}` in the chain. `library.yaml` joins the draft. A `name` its section already has is refused. Answers `{path}`, the component's. |
| `add_component` | `section, name, kind?` | Library only. Adds an empty component to `nodes` (an `exec` node with no step, or a `gate`), `steps`, `tasks` (of `kind`, when given) or `steering`, whose empty `instructions` are a problem until written. Answers `{path}`. |

An op that cannot apply (an id that is taken, reserved or malformed, a move that
puts a `reject_to` or `restart_from` target after the node naming it, or a gate
before the node producing its document, a task moved beside one of its name) answers `422`
`{detail, op}`, `op` being its index, and nothing is saved. A fragment that
changes its component's id answers "rename it with rename"; one that does not
parse adds `line` and `col`, counted in the fragment. A draft with a
`yaml_error` answers `409` "fix the YAML first".

### Item drafts

A work item's own chain has one draft too: a list of ops a person has not
applied yet, kept until it is applied or discarded. A worker cannot read or
change its own item's draft (`403`), and an ended item's answers `409`.

| Route | Answers |
|---|---|
| `GET /api/work-items/{id}/draft` | `{ops, problems, checks, nodes, base_seq, updated_at}`. With no draft, `ops` is `[]` and `nodes` is the item's chain. |
| `PUT /api/work-items/{id}/draft` | Body `{ops: [{op, ...}]}`. Replaces the whole list and answers as `GET` does. An empty list deletes the draft. A malformed op answers `422`. |
| `DELETE /api/work-items/{id}/draft` | Discards the draft: `204`, or `404` with no draft. |
| `POST /api/work-items/{id}/draft/apply` | No body. Applies every op at once, in one transaction, and answers as `GET` does with the draft gone. |

| Op | Fields | Does |
|---|---|---|
| `override` | `path, task_config?, policy?` | Sets what a retry's override may set at that path, within the same bounds: no structural field, policy only tightened or kept under the maxima, a harness inside `allowed_harnesses`. |
| `add_node` | `after, node` | Adds a node built from library components only, as a chain revision adds one: `node` is `{id, extends}`, or `{id, tasks}` or `{id, steps}` of library tasks. |
| `remove_node` | `node` | Takes the node out of the chain. A gate, a node that is not skippable, or a node that lands the merge request cannot be removed. |
| `skip` | `path` | Skips a step or a task: applying records it as `scope_skipped`, so the walk passes it. |

In the answer, each op carries `passed`: `true` once the item has reached the
node it acts on (for `add_node`, gone past the node it follows). A passed op is
not applied, and `nodes` (the chain in the `chain_definition` node shape) has
every other op applied. `problems` is `[{op, message}]`, `op` being the op's
index. `checks` is `{budget: {spent_usd, cap_usd}}`, the item's spend against
its cap, as `budget_cap` on `GET /api/work-items/{id}` reports it.

An apply re-reads the item inside its transaction. If any op is passed by
then, it answers `409` and writes nothing:

```json
{"detail": "the item has moved past some of this draft's ops; remove them or move them after the current node",
 "passed": [0]}
```

Any problem answers `422` `{detail, problems}`. Otherwise the revised chain
replaces the item's, recorded as `chain_revised` with `source: "draft"`, each
`skip` is recorded, and the draft is deleted. Nothing is moved for you: drop a
passed op from the list, or change it to act after the current node.

## The schema

FastAPI generates a schema of every route:

| Path | What it serves |
|---|---|
| `/openapi.json` | The OpenAPI schema, as JSON. |
| `/docs` | Swagger UI for that schema. |
| `/redoc` | ReDoc for that schema. |

```bash
curl -s http://127.0.0.1:8765/openapi.json | jq '.paths | keys'
```

These three paths need no login. Open `/docs` or `/redoc` in a browser to read
the API there. Both pages load their scripts from a public CDN, so on a machine
without internet access, load `/openapi.json` into your own OpenAPI viewer.

## Who may call

| Caller | What it needs |
|---|---|
| A process on the same machine, while Kraft is bound to loopback | Nothing. |
| Anyone, once Kraft is bound off loopback | A browser session from the login page, or the MCP bearer token in `$KRAFT_HOME/run/mcp-token`, sent as `Authorization: Bearer <token>`. |
| A trigger sender, once Kraft is bound off loopback | For `POST /api/triggers` only, the trigger token in `$KRAFT_HOME/run/trigger-token`, sent the same way. |
| A remote caller while no password is set | Nothing works. Kraft answers `403`. |

A request without valid credentials gets `401`. A browser request whose `Host`
is not an allowed name, or a cross-site write, gets `403`. The MCP bearer token is
a full-access credential. See [Security](/project/security) for the whole
model, and [Remote access](/guides/remote-access) to set a password.
