title: Events
description: Every event type on a work item's timeline, its key payload fields, and the notification webhook that sends them.
---

Kraft records what happens to a work item as a list of events, its timeline.
Each event has a `seq` number, the `work_item_id`, a `type`, a JSON `payload`,
a `node_id` and a `created_at` time. `node_id` is the node the event is about,
or `null` for an item-level event (filing the item, a pause, a bulk action);
it defaults from the payload's own `node_id` or `node` key, so most event
types carry it for free, and a handful of node-scoped events that name their
node under a different key (a gate's own events, under `gate`) have it filled
in explicitly. A database upgraded from before this field existed had it
backfilled the same way, from whichever of each row's own `node_id`/`node`
payload keys was a string. Read them with:

```bash
kraft view events ID                     # the whole timeline
kraft view events ID --type gate_requested
kraft view events ID --after 120 -f      # later events, then follow
kraft view events ID --json              # the raw events
```

The tables list each type and the payload fields you are most likely to use.
A payload can carry more fields than these. Event types and payloads are not a
[stable interface](/project/status-and-support#versioning-and-stability): a
release can add, rename or reshape them.

## Work item

| Type | When | Key fields |
|---|---|---|
| `work_item_created` | The item is filed. | `title`, `repo`, `chain_template`; `source`, `bead_id`, `priority` when auto-intake filed it |
| `work_item_attachments` | The item is filed with a spec or plan. | `attachments` |
| `work_item_resumed` | A paused item starts or restarts. | `steer` |
| `pause_requested` | Someone pauses the item. | `sessions` |
| `work_item_blocked_by_dependency` | An open bead dependency paused the item before its next node. | `node_id`, `blocked_by` |
| `paused_by_broken_base` | Another item broke the base branch, so this one paused. | `broken_by`, `follow_up_bead` |
| `work_item_needs_human` | The item stopped for a person. See [below](#work_item_needs_human). | `node_id`, `reason`, `kind` |
| `work_item_waiting` | The item is parked on an external wait. | `node_id`, `retry_at` |
| `work_item_rate_limited` | The agent hit a rate limit; the item retries on its own. | `node_id`, `retry_at` |
| `work_item_retried` | Someone retried the item. | `node_id`, `steer`, `escalated` (an escalation turn retried it) |
| `work_item_completed` | The item finished, on its own or by hand. | none |
| `work_item_manually_completed` | Someone completed the item by hand. | `reason`, `node_id` |
| `work_item_cancelled` | Someone cancelled the item. | `reason`, `node_id` |
| `work_item_abandoned` | The item was cancelled or abandoned. | none |
| `work_item_archived` | The item left the Done column. | `by`: `you` or `auto`; `kept_branch` and `unpushed_commits` when the branch stayed because it has commits nowhere else; `rescued_branch` and `rescued_commits` when commits on a detached HEAD were kept on a new branch; `worktree_kept`, the reason, when that branch could not be made and the worktree stayed |
| `work_item_restored` | An archived item came back. | none |
| `work_item_title_edited` | The title changed. | `title` |
| `work_item_description_edited` | The description changed. | `description` |
| `plan_progress` | A worker started a plan task. | `node_id`, `task`, `total`, `title` |
| `steer_context_set` | A steer was stored for the next agent. | `steer` |
| `steer_undelivered` | A steer was stored but no agent received it. | `steer` |

### `work_item_needs_human`

This is the event behind `stop_reason` in `kraft view show --json`, and behind
"why did it stop" on the board. Its fields:

| Field | Meaning |
|---|---|
| `node_id` | The node the item stopped on. |
| `reason` | What stopped it, in words. A reason that starts `needs_context:` is a question from the agent. |
| `kind` | Why, as one of a fixed set: `question`, `cap`, `budget`, `failed`, `conflict`, `mr_closed`, `config`, `infra`, `stuck`. |
| `session_id` | The last session of that node, when it failed or asked a question. `kraft view logs` reads its log. |
| `capped` | `{cycles, attempts}` when a fix loop spent its attempts. |
| `budget` | `{scope, spent_usd, cap_usd}` when a spend cap stopped the item. |
| `stuck` | `true` when the item stopped in a way an escalation turn can answer. |
| `bundle` | What Kraft gathered about a stuck item when it gave up. |
| `suggested_action` | `{action, reason}`, the next step Kraft suggests. |
| `facts` | Kind-specific detail, when there is any. A `conflict` stop carries `resolved` and `unresolved`: the files the handler cleared and the ones still conflicted (`git diff --diff-filter=U` in the worktree). A closed MR's `facts` carries its ref and url. A `failed` stop on a red changed-test-scope run carries the first failed command's `command`, `scope`, `exit_code` and `session_id` (`area`, and `setup: true` for an area's setup), and every failed one under `failed_scopes` when more than one went red. |

[Troubleshooting](/get-started/troubleshooting#why-did-my-item-stop) maps each
reason to a fix.

## Chain and nodes

| Type | When | Key fields |
|---|---|---|
| `chain_loaded` | The chain was built for the item. | none |
| `worktree_prepared` | The worktree was created and set up. | `report` |
| `node_started` | A node began. | `node_id` |
| `node_completed` | A node finished. | `node_id` |
| `node_skipped` | A node or its gate was skipped. | `node_id`, `gate`, `note` |
| `scope_skipped` | A step or task inside a node was skipped. | `path`, `note` |
| `node_recovery_started` | Kraft reran a node's failed tasks. | `node_id`, `failed_tasks` |
| `run_forked` | A retry started a new run from part of the old one. | `path`, `scope`, `reopened` |
| `base_change_restart` | The base branch moved, so part of the chain reran. | `node_id`, `restart_from`, `nodes` |
| `worktree_rebase_verified` | A rebase reported by a worker matched the worktree. | `reported_head`, `worktree_head` |
| `read_only_violated` | A read-only node or step changed the worktree. | `node_id`, `scope`, `files` |
| `fix_cycle_started` | A fix loop started another attempt. | `node_id`, `cycle`, `failed_tasks` |
| `fix_cycle_refunded` | A fix attempt did not count, because the repair never ran. | `node_id`, `cycle`, `outcome` |
| `findings_measured` | A review or check produced findings. | `node_id`, `cycle`, `findings` |
| `judge_verdict` | A judge ruled on findings. | `node_id`, `cycle`, `verdict`, `reasoning` |
| `sweep_failed` | Kraft could not commit work an agent task left uncommitted: the commit failed, or the worktree was not on the item's branch, held a git operation Kraft did not start, or held a repository Kraft did not create. The work stays in the worktree. | `node_id`, `task`, `error` |
| `sweep_left_out` | After an agent task, Kraft committed the work it left, but not these paths: a lockfile the repo's setup command wrote and nobody changed since (`uv sync` in a repo that commits no `uv.lock`), and a virtualenv or `node_modules` the repo does not ignore (a `node_modules` the setup command made counts whatever is in it: bun leaves no marker). They are installs, not the agent's work. A lockfile the agent writes, or an edit it makes to the setup's, is committed, and so is a directory that only looks like an install: a `node_modules` the setup did not make with no package manager's marker in it (`.package-lock.json`, `.modules.yaml`, `.pnpm`, `.yarn-integrity`, `.yarn-state.yml`), even beside a `package.json`, or a `pyvenv.cfg` with no `python` beside it. Written when the set differs from what the item's last `sweep_left_out` named, not after every task. | `node_id`, `task`, `paths` |
| `bead_not_filed` | Intake could not file a bead. | `reason` |
| `beads_left_open` | The item completed but its beads stayed open. | `beads`, `reason` |

## Gates and review

| Type | When | Key fields |
|---|---|---|
| `gate_requested` | A gate is waiting for a decision. | `gate`, `node_id` |
| `gate_approved` | A gate was approved. | `gate`, `by` |
| `gate_rejected` | A gate was rejected. | `gate`, `note`, `node`, `by` |
| `gate_reopened` | An approved gate is open again. | `gate`, `reason` |
| `gate_auto_review_started` | A gate's review agent started. | `gate`, `session_id` |
| `gate_auto_review_skipped` | A gate's review agent did not run, or left the decision to a person. | `gate`, `reason`; `note` says why, when the review gave a reason |
| `gate_auto_review_discarded` | A review agent's verdict was not used. | `gate`, `verdict`, `reason` |
| `chain_revision_shown` | A person was shown a chain revision. | `gate`, `digest` |
| `chain_revision_unchanged` | A chain revision proposed no change, so its gate passed. | `gate`, `rationale` |
| `chain_revised` | An approved chain revision, or an applied item draft, replaced the chain. | `gate`, `changes`, `diff`; `source: "draft"` and `gate: null` for an item draft |
| `artifact_refused` | Kraft found a gate's document but would not serve it. | `path`, `reason` |
| `review_submitted` | A review was sent. | `review_id`, `gate`, `outcome` |
| `thread_updated` | A review thread was resolved or reopened. | `thread_id`, `state` |
| `rewind_requested` | A review asked for work to be redone. | `review_id`, `target`, `note` |
| `rewind_cancelled` | That request was withdrawn. | `review_id` |
| `reply_agent_wrote` | An agent answered review threads. | `gate`, `files` |
| `reply_agent_skipped` | No agent answered review threads. | `gate`, `reason` |
| `reply_agent_failed` | The reply agent failed. | `gate`, `error` |

`by` is `human` (the board or the `kraft` command), `assistant` (an agent
through the MCP server), `agent` (a Kraft worker, such as a gate's review
agent) or `kraft` (Kraft itself).

## Live messages

A WebSocket client that connects to `/api/ws/events?live=1` also receives messages
that are not events. They are `{"frame": "live", "type", "payload", "created_at"}`,
have no `seq`, are sent once to whoever is connected and are neither stored nor
replayed after a reconnect. A client that does not ask for them never sees one.

| Type | When | Key fields |
|---|---|---|
| `intake_checked` | An intake poll found a bead ready, started an item or left one alone. A poll that found nothing sends none. | `id`, `at`, `ready`, `started`, `skipped` |
| `apply_changed` | What is saved but not applied changed: a draft was published, a reload or an access save ran, or a file was edited on disk (checked every 5 seconds). Not sent when the pending items are the same. | `restart`, `reload` (how many of each; see `GET /api/apply`) |

## Notifications

`notify.yaml` sends an HTTP `POST` to a webhook when an event you name
happens. Set it on the Settings screen, or edit the file:

```yaml
enabled: true
url: https://hooks.example.com/abc123   # a secret; Kraft never shows it back
base_url: https://kraft.example.com     # where links in the message point
events: [gate_requested, work_item_needs_human]
```

| Field | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Nothing is sent while this is off, or while `url` is empty. |
| `url` | none | The webhook. |
| `base_url` | the address the server listens on | The start of the link in each message. |
| `events` | `[gate_requested, work_item_needs_human]` | Which event types send a message. Any type on this page works; Kraft does not check the names, so a typo sends nothing. |

The body is JSON:

```json
{
  "work_item_id": "<work-item-id>",
  "title": "Fix the flaky login test",
  "type": "gate_requested",
  "gate": "spec_approval",
  "url": "https://kraft.example.com/work-items/<work-item-id>"
}
```

`gate` is `null` for an event that is not about a gate.

- Kraft sends at most one message per work item every 10 seconds. A second
  matching event in that window sends nothing.
- A send that times out after 5 seconds, errors, or gets a status of 400 or
  more is tried once more after 2 seconds. If that fails too, Kraft records a
  `notification_failed` event on the item.
- Events that happen while the server is down send nothing when it comes back.
- The Settings screen's **Send a test** posts `"type": "test"` with a `null`
  `work_item_id` and `gate`.
