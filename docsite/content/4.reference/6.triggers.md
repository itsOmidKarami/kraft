---
title: Inbound triggers
description: The schedule fields in intake.yaml and the POST /api/triggers contract for starting a chain from a cron or a webhook.
---

A trigger files a work item from an event instead of `kraft item create`.
There are two kinds, a schedule in `intake.yaml` and an HTTP call. Both
always file the item `paused`, exactly like manual
[intake](/concepts/vocabulary#intake): an agent can't start work from a trigger
any more than from your own `kraft item create`. To set one up, see
[Schedule or webhook work](/guides/schedule-and-webhook-work).

## Schedules

Each entry in the `schedules:` list of `intake.yaml` has these fields:

| Field | Required | Meaning |
|---|---|---|
| `cron` | yes | Five fields: minute (0-59), hour (0-23), day of month (1-31), month (1-12), day of week (0-7; 0 and 7 are both Sunday). Each field is `*`, an integer, a range (`1-5`), a step (`*/15`, `10-40/10`, or `5/20`, meaning from 5 to the field's top), or a comma-separated list of those. Names (`MON`, `JAN`) aren't read. A day of month and a day of week must both match: `0 9 1 * 1` fires only on a 1st that is a Monday, not on every 1st and every Monday as some crons do. A value outside its field, a backwards range or a zero step is refused where `intake.yaml` is read: see below. |
| `repo` | yes | Path of a repo you connected with `kraft repo connect`. |
| `chain` | yes | A chain id from `config/chains/`. |
| `title` | yes | The work item's title. A title is one line: one with a line break is filed with its first line as the title and the rest at the top of the description, rather than skipped. A block scalar (`title: >` or `title: |`) ends in a line break unless written `>-` or `|-`; that trailing one is simply dropped. Control characters are dropped too, and a blank title takes the description's first line. |
| `description` | no | The work item's description. Defaults to `""`. |

Kraft evaluates the schedule in UTC, not in the server's local time zone. It
checks once a minute, and a minute missed while the server is down isn't
backfilled. The poller runs for the life of the server, so a trigger you add
later fires without a restart. `kraft admin reload` rereads `intake.yaml`,
and so does a publish from Settings › Auto-intake.

Before 2.0 the list was `triggers:` in `policy.yaml`. A file still holding it
keeps firing, and `kraft admin doctor` names the move; the Auto-intake screen
edits `intake.yaml` only.

Kraft skips an entry, logs a warning naming the reason, and still fires the
other entries due in the same tick, when:

- the `repo` is not connected (the warning names `kraft repo connect`);
- the `chain` id is unknown;
- the `title` and the `description` are both blank;
- the template library is invalid;
- its `cron` can't be read (a guard: an `intake.yaml` holding one does
  not load, see below).

A pre-2.0 `policy.yaml` trigger whose `cron` names a value outside its
field, such as `0 24 * * *` or `0 9 * * 8`, loaded in 1.4, which never ran
it. So did one with a number in digits other than 0-9 (`²`). Kraft skips
either when the file is read, logs a warning, and loads the rest of
`policy.yaml` and its other triggers; `kraft admin doctor`'s `moved keys`
row names it. Any other bad trigger `cron` (a word, the wrong number of
fields) refuses `policy.yaml`, as it did in 1.4.

An `intake.yaml` with a `cron` Kraft can't run, such as minute `61`, does
not load: Settings › Auto-intake shows the problem on that schedule and
won't publish it; `kraft admin reload` refuses the file and exits 1, the
running auto-intake and schedules kept, with `/api/health` degraded and
`intake_off` false; and a server starting on it runs with auto-intake off
and none of its schedules, with `/api/health` degraded, `intake_off` true and
`kraft admin doctor` naming the file. A trigger left in `policy.yaml` still
fires.

## `POST /api/triggers`

The HTTP twin of a schedule, for anything that can fire a webhook and can't
wait for the next minute tick. The request body is JSON:

| Field | Required | Meaning |
|---|---|---|
| `title` | yes | The work item's title. |
| `repo` | yes | Path of a connected repo. |
| `chain` | no | A chain id. Defaults to the repo's `default_chain`, else `default`. `chain_template`, the pre-2.0 name, is still read. |
| `description` | no | The work item's description. Defaults to `""`. |

| Caller | Authentication |
|---|---|
| The machine running Kraft, while it is bound to loopback | None, as long as it addresses the server as `127.0.0.1`, `localhost` or `[::1]`. |
| Any caller after a non-loopback bind, the same machine included | The trigger token in `$KRAFT_HOME/run/trigger-token`, sent as `Authorization: Bearer <token>`. The MCP bearer token in `$KRAFT_HOME/run/mcp-token` or a browser session cookie also works. See [Remote access](/guides/remote-access). |

| Status | Meaning |
|---|---|
| `201` | The item was filed. The body is the work item as JSON: `id` is the new item's id and `status` is `paused`. |
| `401` | Kraft is bound off loopback, and the request has no valid bearer token or session. |
| `403` | A remote caller while no password is set; on a loopback bind, any request not addressed to `127.0.0.1`, `localhost` or `[::1]`, one through a tunnel or reverse proxy that keeps its client's `Host` included (see [A proxy in front of a loopback bind](/guides/remote-access#a-proxy-in-front-of-a-loopback-bind)); off loopback, a browser request whose `Host` is neither a loopback name nor in `allowed_hosts`; or a cross-site browser write. |
| `422` | The body is not valid: `repo` or `title` is missing, or a field has the wrong type. |
| `422` | The `repo` is not connected. The message names `kraft repo connect`. |
| `422` | The `repo` path no longer exists. |
| `422` | `chain` (or `chain_template`) names no chain, or that chain does not resolve. |
| `422` | `chain` and `chain_template` are both sent and name different chains; the `detail` names both. |
| `422` | The `title` is empty or only whitespace (`title cannot be empty`). 1.4 filed such an item with no title. |
| `422` | The `title` is longer than 500 characters. |
| `422` | The `title` holds a line break, a trailing one included (`the title is one line`). Put the rest in `description`. A tab, an escape or another control character is refused too (`the title is plain text`). |
| `422` | `repos.yaml` cannot be read, or the repo's policy or steering is invalid. The message names the problem. |
| `502` | Filing failed after the checks passed. The message starts `intake failed:`. |
| `503` | `policy.yaml` or the template library is invalid, so Kraft refuses all new work. `kraft admin doctor` names the file. |

See [HTTP API](/reference/http-api) for the rest of the API.

```json
{"id": "<work-item-id>", "title": "Nightly dependency check", "status": "paused", "...": "..."}
```

::note
Give CI and webhook senders the trigger token. It passes the login check on
`POST /api/triggers` only, so its holder can file paused work and nothing else.
The MCP bearer token passes it on every route, so whoever holds that one can
also start, approve and cancel work and change settings. To rotate either, see
[The bearer token](/project/security#the-bearer-token).
::
