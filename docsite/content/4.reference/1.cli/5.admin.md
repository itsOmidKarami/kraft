---
title: Admin verbs
description: "The kraft admin verbs: start, stop, check, update, and configure this machine's server."
---

`kraft admin` runs this machine's Kraft server. Bare `kraft` is the same as `kraft admin start`.

```bash
kraft admin start --port 9000
kraft admin start --detach
kraft admin stop
kraft admin restart -y
kraft admin health
kraft admin doctor
kraft admin reindex --repo <path>
kraft admin reload
kraft admin update --restart -y
kraft admin install-service
kraft admin uninstall-service
kraft admin templates lint
kraft admin templates lint --dir PATH
kraft admin templates show ID
kraft admin templates show ID --resolved
kraft admin templates library
kraft admin templates library ID
kraft admin harnesses
kraft admin harnesses ID
kraft admin init --repo
kraft admin mcp
kraft admin permission-hook cursor --fail-closed
```

| Command | Effect |
|---|---|
| `start` | Runs the server in the foreground; the same as bare `kraft`. `--host` and `--port` override `KRAFT_HOST` and `KRAFT_PORT`, which override `access.yaml`. The flags are not saved: other commands still dial the host and port in `KRAFT_HOST`/`KRAFT_PORT` or `access.yaml`, so `start` prints the `KRAFT_HOST=H` or `KRAFT_PORT=N` they need when `--host` or `--port` differs (a wildcard `--host` such as `0.0.0.0` needs none). `--detach`/`-d` forks it into its own session and returns once it is up. If the server exits instead, it prints the error (such as `RuntimeError: database schema vN is newer than code vM`), the end of that start's output, and the path of `server.log`. |
| `stop` | Sends SIGTERM to the process in `run/kraft.pid`, once it has checked that the process is this Kraft server. A pidfile naming any other process is stale: `stop` removes it, says so, and signals nothing. Any agent the server is running stops with it, and its item stops when Kraft starts again. A repo's setup command that is running is ended too, with everything it started, so it never runs beside the next server's own run of it. A server that is killed (SIGKILL) cannot end it. It lists the active items first, without asking; a server that does not list them within 2 seconds is stopped anyway. Pause running items first (see [A restart ends running agents](/get-started/install#a-restart-ends-running-agents)). |
| `restart` | Stops, then starts again the same way it was running: through the service manager if one is installed, back into the background if it was detached. A server running attached to a terminal is stopped, with a note that only that terminal can bring it back, and `restart` exits 1, since no server is running after it. Like `stop`, it ends any running agent: pause running items first, and retry any item it stopped. It lists the active items first and, in a terminal, asks before going on; `-y` skips the question. Answering no exits 1 and says nothing was restarted. With no server running, it starts nothing: it says so and exits 1. Start one with `kraft admin start`. |
| `health` | Exits 1 when the server is degraded, with the reasons on stdout. It names the version the server runs, and, after an update it has not restarted for, the installed one with `restart pending`, which is not degraded. |
| `doctor` | Runs every check in one pass. Exits 1 if any fails. |
| `reindex` | Rescans documents into the search index. `--repo` limits it to one repo. |
| `reload` | Rereads the template library, `policy.yaml` and `intake.yaml` from disk, with no restart. A `policy.yaml` or `intake.yaml` that does not load is refused, the running one is kept, and reload names it and exits 1, as it does for a chain that does not resolve. |
| `update` | Installs the newest release with uv, keeping the `vector` extra and the Python it runs on, or runs `brew upgrade` if you installed with Homebrew. On a pipx or pip install, or a source checkout, it installs nothing and prints the command that updates that install. `--force` installs even when current. `--restart` also restarts a running server, which ends any running agent, as `restart` does; it lists the active items and asks before installing anything; answering no exits 1. `--channel rc\|beta\|alpha` takes pre-releases (`rc` only release candidates and finals, `beta` adds betas, `alpha` takes anything); without `--channel`, a release candidate install follows `rc`, a beta `beta`, an alpha `alpha`, and a final release `stable`, which never takes a pre-release. Homebrew installs only track stable. `-y` accepts the [template migration](#migrating-an-older-template-configuration) without asking, and skips `--restart`'s question. |
| `install-service`, `uninstall-service` | Register or remove Kraft as an OS service (a launchd agent on macOS, a systemd user unit on Linux) that restarts if it exits. Stop a running server first. |
| `templates lint` | Checks every chain in the library, including that `harnesses.yaml` can launch each agent task (a `profile:` with no model for its harness's provider is an error), and exits 1 on any error, printing each as `file:line:column: message`. `--dir PATH` checks that directory in-process, with no server and no `$KRAFT_HOME`. |
| `templates show ID` | One chain as written. `--resolved` expands its library components. It asks the running server: a chain file you just added shows only after `admin reload`, and `--resolved` expands the version the server last loaded. |
| `templates library [ID]` | Every library component, its kind and the chains using it. With an ID, one component's definition, users and lint issues (`tasks.implementer`, or a unique bare name; a bare name two sections share is refused with each full id). |
| `harnesses [ID]` | Every `harnesses.yaml` profile, its provider, and the library tasks and chains selecting it (a chain's own `harness:` on a task included). With an ID, one profile in detail. |
| `init [--repo]` | Registers the MCP server and skills with an agent. `--repo` installs into this repo, not your user config. See [Agent integration](/guides/agent-integration). |
| `mcp` | Serves the MCP tools over stdio. |
| `permission-hook HARNESS` | What a Cursor or Codex worker's pre-tool hook runs. You do not run it by hand. `--fail-closed` denies rather than giving no opinion when Kraft cannot answer. See [Permission gate](/reference/permissions). |

Kraft refuses to start on a non-loopback address without a password. It also
refuses a second start against the same run directory while the first is
alive. The foreground server stops on Ctrl-C. Use `kraft admin stop` for one
you started elsewhere.

`kraft admin doctor`'s `mcp server` row checks Kraft's registration with
Claude Code only, the one Claude workers need. It does not read Codex's,
Cursor's, OpenCode's, Amp's, Antigravity's or Gemini CLI's; see
[Agent integration](/guides/agent-integration) for each one's own check.

`kraft admin doctor` fails its `kraft on PATH` row when an older `kraft` sits
ahead of this one on `PATH`, and `kraft admin update` warns about it. Its
`embeddings` row fails when an installed embedder's model will not load. See
[Enable vector search](/get-started/install#enable-vector-search).
A sandboxed repository's `sandbox` row names the runtime it found (Docker or
Podman, rootless or not) and the resource limits it can enforce, and fails
when that runtime does not answer, when SELinux enforces and
[sandbox.yaml](/reference/configuration/sandbox) does not say how to get past
it, when `ca_bundle` cannot be used, when the sandbox sets a
[limit](/reference/configuration/repos#resource-limits) the runtime cannot
enforce, or when the sandbox image is not pulled. It reads `sandbox.yaml`
afresh each run. A `proxy` row warns when a proxy variable points at this
machine's loopback, which a container cannot reach, and a `ca` row when
`SSL_CERT_FILE` is set but cannot be used, so sandboxes ignore it. Those two
read doctor's own environment, not the daemon's.
For a repository whose sandbox is a [Kit](/reference/configuration/repos#kits),
doctor fetches and lowers the Kit first: the `sandbox` row fails naming the Kit
and why when it cannot, and otherwise it and the egress, proxy and credentials
rows check the sandbox the Kit lowers to. A `kit hosts` row warns about each
host a harness requires that the Kit does not allow, and a `kit credentials`
row about each credential service with no binding in `sandbox.yaml`. Doctor
fetches each Kit it has not cached; under Podman a single-manifest Kit is
pulled, which can take up to 10 minutes per repository the first time.

## Migrating an older template configuration

Since 1.0, a template configuration is a `library.yaml` plus `chains/*.yaml`.
The 0.x format had a `registry.yaml` and no `library.yaml`. A Kraft home that
still holds it is not converted or overwritten. The
server starts degraded and refuses new work until you run
`kraft admin update`. That command says what will change, asks, and then moves
the whole `config/` directory to a `config.pre-v1-<time>` backup beside
it and installs the bundled configuration.

- `-y` accepts without the question. With no terminal and no `-y`, it changes
  nothing.
- `access.yaml`, `notify.yaml`, `theme.yaml`, `repos.yaml`, `intake.yaml`,
  `steering/` and `harnesses/` carry across. The next start folds
  `steering/*.md` into `library.yaml` as
  [steering profiles](/reference/configuration/repos#repository-steering).
- `policy.yaml` starts from the bundled default and keeps your value for every
  key the current format still has. Kraft prints each key it drops, with its old value.
- Your old chains and registry stay only in the backup. There is no migration
  helper.

An update interrupted mid-swap is finished by the next start or the next
`kraft admin update`.
