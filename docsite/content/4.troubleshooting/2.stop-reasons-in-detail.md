The tables under [Find your reason](/troubleshooting/why-did-my-item-stop#find-your-reason) link here from each one.

## Forge authentication fails

The stop's `facts.cause` is `forge_auth`, and the card reads **Failed** with the fix under it.

On a `client: cli` account, Kraft holds no forge token. It runs `gh` (GitHub) or `glab` (GitLab), and git, as the user the server runs as, and the forge refused what they sent. Nothing in Settings › Repos can supply a token. A forge that is only rate limiting Kraft is not this: see [A forge rate limit](#a-forge-rate-limit).

1. On the machine the server runs on, sign the forge CLI in: `gh auth login`, or `glab auth login` for GitLab.
2. If git itself still cannot authenticate, check its credentials: `gh auth setup-git`, your SSH key or credential helper. `gh auth status` shows who the CLI is signed in as. `kraft admin doctor` checks only that the CLI is installed, not that it is signed in.
3. If the forge asks for single sign-on, authorize the CLI's token for the organization on the forge's website. When the forge sent the address of that page, `facts.sso_url` carries it, and the card ends its fix with the address as a link: open it, authorize, then retry. Kraft shows only a plain `https://` address.
4. Run `kraft item retry ID`.

## A forge rate limit
_Added in next_

The forge answered a call with `HTTP 429`, or with an `HTTP 403` that says it is a rate limit: GitHub's `X-RateLimit-Remaining: 0`, a `Retry-After`, or a message naming a rate limit, which is all GitHub's secondary limit may send.

The forge has not refused your credentials, so the item does not stop for you: its status is `rate_limited`, a `rate_limit_hit` event records when to come back, and Kraft starts the item again at that time. The time is the forge's `Retry-After` when it sent one, else when GitHub's spent quota resets (`X-RateLimit-Reset`), else a minute.

Nothing to do but wait. If the limit keeps coming back, the account the server's `gh` or `glab` is signed in as is spending its quota elsewhere; sign in with another account, or give the CLI a token with a higher limit. A `403` with none of these signs is still [Forge authentication fails](#forge-authentication-fails).

## `backend is not in this release`

_Added in next_

The repo's forge account says `client: api`, and this release has no API backend to run it. Kraft stops the item at its first forge node, and answers the item's forge reads, label and merge request calls with the same text. It never falls back to `gh` or `glab`: a repo does not switch between the CLI and the API from one run to the next.

1. Set `client: cli` on the account in [forges.yaml](/reference/configuration/forges), or use a release that ships the backend.
2. Run `kraft admin reload`, then a person's `kraft item retry ID`.

A file that does not load stops a new item the same way: `forges.yaml does not load (<why>)`, because the broken file may hold an API account for the host. Fix the file, reload, retry.

## `no forge is recorded for this repo`

The repo had no GitHub or GitLab `origin` when you connected it, so Kraft does not know which forge CLI to run.

1. Set `forge: github` or `forge: gitlab` on the repo in Settings › Repos, then **Review & publish** (or set it in `repos.yaml`).
2. Run `kraft item retry ID`.

## `declares neither test_scopes nor test_command`

The item stops at its test node (`verify` on `quick-task`, `verification` on `default`) because Kraft will not guess a test command.

1. Set `test_command` (or `test_scopes`) on the repo in Settings › Repos, then **Review & publish**, or set it in `repos.yaml`. For a repo with no tests, set `""`. `kraft repo connect PATH` again saves the command it now proposes.
2. Run `kraft item retry ID`.

## `nothing registers it for Claude Code`

No `kraft` MCP server is registered, so Kraft refused a Claude worker. The item stops at its first agent step with 0 tokens spent: `spec` on `default`, `implementation` on `quick-task`.

1. Install the Kraft plugin and run `/kraft:onboard`, or run `kraft admin init`.
2. Run `kraft item retry ID`.

`kraft admin doctor`'s `mcp server` row checks the same thing: see [The mcp server warning](/troubleshooting/doctor-failures#the-mcp-server-warning).

## `is not on the PATH the worker gets`

_Added in next_

A `kraft` MCP server is registered, but no entry Claude could start it from runs a command on the `PATH` a worker gets, or on the `PATH` the entry sets in its own `env`. So Claude cannot start the server, and Kraft refused the worker. The reason names each command and the file that registers it. The item stops at its first agent step with 0 tokens spent.

Your own Claude Code shows the same: `claude mcp list` or `/mcp` says the server failed to connect, with `Executable not found in $PATH` and a name: for example `"kraft"` for a server you registered, or `"stdio"` for the plugin's. It is usual when Kraft is installed only in a virtual environment, or runs as a service with a short `PATH`.

1. Do one of these:
   - Put `kraft` on `PATH`, as in [`kraft`: command not found](/troubleshooting/starting-and-reaching-kraft#kraft-command-not-found). In a checkout of Kraft, `just install` installs the command.
   - Register the server by its absolute path. If `kraft admin init` registered it at user scope already, run `claude mcp remove --scope user kraft` first, then `claude mcp add --scope user kraft -- /path/to/kraft admin mcp`. Claude takes a repo's local-scope or `.mcp.json` entry before that one, so fix a bare `kraft` there the same way.
   - Under a service, reinstall the service from a shell where `kraft` runs, so it keeps that `PATH`: see [The `kraft on PATH` doctor row](/troubleshooting/starting-and-reaching-kraft#the-kraft-on-path-doctor-row).
2. Run `kraft item retry ID`.

`kraft admin doctor`'s `mcp server` row fails on the same thing while the server runs, and only warns when no chain launches an unsandboxed Claude task. With no server it checks the shell's `PATH` instead, which may not be the server's, and only warns. It does not check a registration that only a repo has, in its `.mcp.json` or local scope.

## `stored model override is not a model id`

A model override on the item or a node holds text that is not a model id, such as `sonnet 4`. The reason ends with the stored text.

1. Run the command the reason names, `kraft item set-overrides ID --clear` or `kraft item set-node-override ID --node N --clear`, or set a valid model.
2. Run `kraft item retry ID`.

Before 2.0, an override could hold any text, so an old item can still carry one.

## `add-on ... could not be read`

_Added in 2.1_

A work item reads a [Kraft add-on](/concepts/vocabulary#add-on)'s skills and agent profiles from the version it was filed with. Before a launch, Kraft restores that version's files if they are missing, from the commit the item recorded. The reason ends with what failed:

- `locked commit <commit> could not be fetched (network: ...)` or `(auth: ...)`: the server could not reach the collection, or git has no login for it there. A server run as a service may lack the SSH agent or credential helper your shell has.
- `collection <name> is no longer in addons.yaml; add it again`: the collection was removed.
- `its files no longer match the locked digest`: what the collection holds for that version changed.
- `...; the store was changed after it was installed`: something edited, added or removed a file under `run/addons/store/` after Kraft wrote it. A skill read from the add-on stops the same way, as `skill: add-on '<namespace>' could not be read: ...`.

Before the `;` of that last reason is `<file> does not match its digest`, `<file> is not in its digest`, `<file> is missing` or `<file> is not a regular file`. For the store's manifest it is `.kraft-digest does not hash to the store's name`, `.kraft-digest is malformed` or `.kraft-digest cannot be read`.

1. Fix what the reason names: restore the server's access to the collection, or add the collection again with `kraft admin addon collection add`.
2. Run `kraft item retry ID`. A retry reads the same pinned version.

For an edited store:

1. Find out what wrote under `run/addons/store/`. `kraft admin doctor` names the add-on.
2. Delete that `store/<digest>/` directory. It is read-only, so run `chmod -R u+w` on it first. The next launch restores the pinned version from its commit.
3. Run `kraft item retry ID`.

`kraft admin addon install --re-install` repairs the store only while the collection still holds the same content, because it takes the newest commit.

[Restoring a store](/reference/configuration/addons#restoring-a-store) says where the files come from.

### `its parent ... is not loaded`

_Added in 2.3_

The reason reads `add-on <id> <version> could not be read: its parent <parent> is not loaded: ...`. The add-on [builds on another one](/guides/customize/publish-an-add-on#build-on-another-add-on), and Kraft never runs a child without the add-on it inherits from. The rest is the parent's own reason, and it can name a grandparent the same way, so the last reason in the line is the add-on that failed.

1. Fix that add-on as its own reason says: restore its store as above, enable it again with `kraft admin addon enable`, or install it again with `kraft admin addon install`.
2. Run `kraft item retry ID`.

### `a work item never mixes versions`

_Added in 2.3_

The reason reads `add-on <id> <version> could not be read: <id> <version> builds on <ancestor> <version>, and this work item runs <ancestor> <version>; a work item never mixes versions of one add-on tree`, or `... is installed under <namespace>, and this work item runs <id> <version>; a work item never mixes versions of one add-on`.

The task reads an add-on the item had not pinned, through a `harnesses.yaml` fallback written after the item was filed, and the installed version is built on another version of an add-on the item pinned, or is itself another version of one. Kraft will not run one add-on tree at two versions.

A retry does not fix this: the item keeps the versions it pinned.

1. Remove the fallback from `harnesses.yaml`, or point it at a profile the item already reads, then run `kraft item retry ID`.
2. Or file the item again. A new item pins the versions installed now.

## `no user.name configured`

The same stop names `user.email` when that is the missing one. git has no commit identity for the repo, so Kraft would not make the item's worktree: its commits would fail or carry an invented author.

1. Set both for the user Kraft runs as, for every repo:

   ```bash
   git config --global user.name "Your Name"
   git config --global user.email you@example.com
   ```

   To set them for one repo, run the same commands without `--global` inside it.
2. Run `kraft item retry ID`.

## `no setup_command declared`

The repo has no `setup_command`, and Kraft will not guess what to run in a fresh worktree. This is the usual first stop on a repo with no lockfile Kraft knows (see [How connect proposes commands](/reference/configuration/repos/connect-proposals)). The item stops at its first node.

1. Set **setup command** on the repo in Settings › Repos (or `setup_command` in `repos.yaml`). If the repo has nothing to install, turn **No setup needed** on there instead (`""` in `repos.yaml`).
2. In Settings, click **Review & publish**: until you do, the change is a draft and the retry stops again.
3. Run `kraft item retry ID`.

## Git would not start the rebase

Nothing was rebased. Most often the base now tracks a file the worktree has untracked, such as a note or a script the agent never committed, and git will not overwrite it.

1. `cd "$(kraft repo path ID)"`.
2. Look at the files git names, then move, delete or commit them.
3. Run `kraft item retry ID`.

A `uv.lock` the setup command wrote and nobody changed is not one of these: Kraft sets it aside for the rebase. One that an older release recorded without a digest is kept in place, in case the agent edited it: see [Upgrade from 1.4 or an older release](/guides/run/upgrade-from-0-x-or-a-release-candidate#upgrading-from-a-150-release-candidate).

## A git operation is in progress

The worktree holds a rebase, merge, cherry-pick, revert, bisect or autostash. A sandboxed worker can plant one to move one of your branches. A rebase of Kraft's own that was cut short (a server killed mid-rebase, or an abort that could not run) leaves one too.

1. Look at the named file first. If you did not leave it there yourself, delete it as the reason says.
2. If deleting it leaves `HEAD` detached, check the item's branch out again with `git checkout -f <branch>`, as the reason names it. The branch still has the item's commits.
3. Run `kraft item retry ID`.

Never run `git rebase --abort`, `git merge --abort` or `--continue` on it: that is what moves the branch.

## A policy budget or token cap refused the launch

A policy `budget_usd` or `token_budget` refused the next launch. The message names the scope: `the work item`, or a node, step or task path in backticks.

`raise-budget` is refused for a `token_budget` or a path, and the item's page offers **Retry** with no raise. [Raise a cap on a stopped item](/guides/day-to-day/raise-a-cap) has the fix for each scope: **Raise cap** or `kraft item raise-budget` for the item-wide `budget_usd`, `kraft item set-policy` for a `token_budget`, and for a cap the chain sets on a path, `kraft item skip` or a change to the chain.

The item's policy was fixed when it was filed, so editing `policy.yaml` or the chain reaches only items filed afterwards.

## A budget cap cannot be checked

A launch in that scope ran on a harness that reports tokens but no cost, on a model `prices.json` cannot price. Kraft cannot show the scope is under its `budget_usd` and will not count the launch as free. Which harnesses these are is on [Harnesses that report no cost](/reference/harnesses/cost-reporting#harnesses-that-report-no-cost).

Raising `budget_usd` does not help: the stop stays while any `budget_usd` applies to the scope.

1. Clear the item-wide cap with `kraft item set-policy ID --policy budget_usd=none`. Add `--policy token_budget=N` to keep a bound.
2. Run `kraft item retry ID`.

The `budget_usd=none` fix clears a cap from the chain's own `policy:`, `repos.yaml` or a `policy.yaml` default too, but is refused under a `maxima.work_item.budget_usd`, and does not lift a cap the chain set on a node, step or task. For those, skip that node with `kraft item skip`, or bound that harness's scopes with `token_budget` in place of `budget_usd` and file the item again.
