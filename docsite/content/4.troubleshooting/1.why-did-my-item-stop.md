title: Why did my item stop?
description: Find the reason a work item stopped and needs you, the fix for each, and what to do when an item waits on CI or a review.
---

Start here when a [work item](/concepts/vocabulary#work-item) appears under **Needs you**, or when one waits and nothing moves.
Find the text Kraft shows in the tables under [Find your reason](#find-your-reason): each row has the fix, or links to an entry that has it.
[Waiting on CI or a review](#waiting-on-ci-or-a-review) covers the two waits that need no stop.

An item waiting at a gate is not a stop either: [Escalation turns and things that are not a stop](#escalation-turns-and-things-that-are-not-a-stop) covers that, and what comes before a stop reaches you.

## Check the cause before you retry

A work item that needs you appears under **Needs you** on the board, and its
row shows the node it stopped at (`needs_human` is its status in `kraft view
list`). The reason is in the item's side panel and in `kraft view show ID`.
Find out why before you retry: a retry without the cause reruns the same
failure.

```bash
kraft view show ID                                  # the node it stopped on, and the reason
kraft view events ID --type work_item_needs_human   # the stop, with every field
kraft view logs ID                                  # the log of the session that stopped it
```

In Claude Code, `/kraft:triage` reads all three and suggests the next step.

Where a fix says **retry**, run `kraft item retry ID`, and add `--steer "..."`
to tell the agent what to do differently. A retry you run resets the node's
attempt counters.

The [events catalogue](/reference/events#work_item_needs_human) lists every
field of a stop.

## Find your reason

The first column is the text Kraft shows, in the item's side panel, in `kraft view show ID` and in the board's stop card. `...` stands for text that varies. A row either holds the whole fix, or links to an entry under [Stop reasons in detail](#stop-reasons-in-detail).

### Questions, failed tasks and logins

| The reason says | What happened | Fix |
|---|---|---|
| `needs_context: <question>` | The agent asked a question it could not answer from the repo. | Answer it: `kraft item resume ID --steer "<answer>"`. |
| `task failed in node <node>: ...` | An agent task or command failed. | Read `kraft view logs ID`, then retry with a steer that names the fix. |
| `task failed in node <node>: ...`, and the log shows an authentication or login error | The agent CLI is installed but not logged in. | Run the agent once in a terminal and log in (`claude` for the shipped chains), then `kraft item retry ID`. `kraft admin doctor` checks only that it is on `PATH`. |
| A [forge](/concepts/vocabulary#forge) task (opening, syncing or merging the merge request), or a git push or fetch, failed, and the log shows `HTTP 401`, `Bad credentials`, `Authentication failed`, `could not read Username`, `Permission denied (publickey)` or `gh auth login` | Kraft holds no forge token, and the forge refused what `gh`, `glab` or git sent. | See [Forge authentication fails](#forge-authentication-fails). |
| The log shows `Could not resolve host`, `Connection timed out` or `Connection refused` on a forge or git call. The stop's `facts.cause` is `forge_unreachable`. | The machine the server runs on could not reach the forge. | Check that machine's network, DNS and proxy settings, then `kraft item retry ID`. |

### A task Kraft would not launch

| The reason says | What happened | Fix |
|---|---|---|
| `could not start <task> in node <node>: ...` | Kraft refused the launch, and the rest of the reason says why. | Fix the named cause, often with `kraft admin doctor`, then retry. The rows below are the common causes. |
| `could not start ...` with `cannot run: backend: auto, but no forge is recorded for this repo` | The repo had no GitHub or GitLab `origin` when you connected it. | See [`no forge is recorded for this repo`](#no-forge-is-recorded-for-this-repo). |
| `could not start ...` with `declares neither test_scopes nor test_command in repos.yaml` | The repo has no test command, and Kraft will not guess one. | See [`declares neither test_scopes nor test_command`](#declares-neither-test_scopes-nor-test_command). |
| `could not start ...` with `stored model override is not a model id: clear it with ...` | A model override on the item or a node is not a model id, such as `sonnet 4`. | See [`stored model override is not a model id`](#stored-model-override-is-not-a-model-id). |
| `... nothing registers it for Claude Code: ...` | No `kraft` MCP server is registered, so Kraft refused a Claude worker. | See [`nothing registers it for Claude Code`](#nothing-registers-it-for-claude-code). |

### Setting up the worktree

| The reason says | What happened | Fix |
|---|---|---|
| `no user.name configured in <repo>; set it before Kraft can commit` (or `user.email`) | git has no commit identity for the repo, so Kraft would not make the item's [worktree](/concepts/vocabulary#worktree). | See [`no user.name configured`](#no-username-configured). |
| `no setup_command declared for <repo> in repos.yaml, so <id>'s worktree cannot be prepared. Declare one ...` | The repo has no `setup_command`, and Kraft will not guess what to run in a fresh worktree. | See [`no setup_command declared`](#no-setup_command-declared). |
| `setup command failed for <id>: '<command>': <output>` | The repo's `setup_command` ran in the new worktree and exited non-zero, and the reason ends with its output. | In the worktree (`cd "$(kraft repo path ID)"`), run the command yourself. Fix it, or the repo's `setup_command`, then `kraft item retry ID`. |

### Fix loops, gates and reviews

| The reason says | What happened | Fix |
|---|---|---|
| `<loop> exhausted after N fix cycle(s)` | A [fix loop](/concepts/vocabulary#fix-loop) spent its attempts without passing. | Read the findings (`kraft view events ID --type findings_measured`), then retry with a steer. |
| `<node>.on_base_changed exhausted after N restart(s) from '<node>'` | The [base branch](/concepts/vocabulary#base-branch) kept moving: each restart from the named node found it moved again, until the restarts ran out. | Retry once the base branch settles; a retry resets the count. To allow more restarts, raise that key under `loops:` in `policy.yaml`. The shipped chain restarts `merge_request_feedback` from `verification`. |
| `<gate> exhausted after N rejection(s)` | A gate was rejected as many times as its chain allows. | Retry with a steer, or rework the spec or plan yourself. |
| `stuck: ...` or `judge: ...` | A fix loop made no progress across cycles (`stuck`), or the loop's [judge](/concepts/vocabulary#judge) decided another repair attempt is not justified (`judge`). | Kraft has already tried an [escalation turn](/concepts/vocabulary#escalation-turn) on its own. Send a message with `kraft item escalate ID --message "..."`, or retry with a steer. |
| `the merge request was closed on the forge without merging` | Someone or something other than Kraft closed the item's merge request without merging it. | The board offers **Reopen !N**, **Open a new MR** (only when the item had opened one) and **Cancel item…**. See [MR closed externally](/reference/statuses#mr-closed-externally) (the stop's `stop.kind` is `mr_closed`). |
| `a repair in node <node> finished with concerns ...` | A repair ran, but its agent doubted the result. | Read the concerns in the reason, then retry with a steer, or `kraft item skip ID`. |
| `<scope> is read_only, but it changed the worktree: ...` | A read-only step edited files. | Look at the named files, then retry. |

### Git state of the worktree

| The reason says | What happened | Fix |
|---|---|---|
| `the conflict in node <node> cannot be resolved ...` | Rebasing onto the base branch hit a conflict nobody resolved. | Resolve it in the worktree (`cd "$(kraft repo path ID)"`), commit, then retry. |
| `untracked <paths> would be overwritten by the base branch; move or delete it, then retry`, or `git would not start the rebase onto the base branch ...` | Kraft went to rebase the item onto its base branch, and git refused to start, so nothing was rebased. | See [Git would not start the rebase](#git-would-not-start-the-rebase). |
| `<worktree> has a <name> in progress: inspect it, then delete ...` | The worktree holds a rebase, merge, cherry-pick, revert, bisect or autostash, so Kraft would not rebase or commit over it. | See [A git operation is in progress](#a-git-operation-is-in-progress). |
| `<worktree> is not on <branch>; check it out by hand, then retry` | The worktree's HEAD names another branch, so Kraft would not commit, rebase or push from it. | `cd "$(kraft repo path ID)"`, check that nothing of yours is on the named branch, `git checkout <branch>`, then retry. |
| `origin/<branch> is at <sha>, which Kraft did not push and this worktree does not have ...` | Someone pushed commits to the item's merge request branch, and Kraft's push would have overwritten them. | `cd "$(kraft repo path ID)"`, `git pull --rebase origin <branch>` to bring them in, then retry. |
| `origin no longer has <branch>, which Kraft pushed ...` | The item's branch was deleted from origin, usually with its merge request merged or closed, and Kraft will not recreate it. | To publish the work anyway, run the two `git update-ref -d` commands the reason names in the item's worktree, then retry. Otherwise abandon the item. |

### Caps and budgets

| The reason says | What happened | Fix |
|---|---|---|
| `budget cap reached: ... on this work item` | The item's own dollar cap refused the next launch. | Raise that cap and retry in one step: `kraft item raise-budget ID --usd N`, or **Raise cap** on the item. See [Raise a cap on a stopped item](/guides/day-to-day/raise-a-cap). |
| `budget_usd reached ...`, `token budget reached ...` | A policy `budget_usd` or `token_budget` refused the next launch. | See [A policy budget or token cap refused the launch](#a-policy-budget-or-token-cap-refused-the-launch). |
| `budget cap reached: ... today, across every work item` | The daily cap, which nothing on the item raises, refused the next launch. | Raise `budget.daily_usd` in `policy.yaml`, or wait for local midnight, then retry. `raise-budget` is refused, and the item's page offers **Retry** with no raise. |
| `budget_usd cannot be checked: N launch(es) in ... reported no cost, and unknown spend is never counted as free ...` | A launch ran on a [harness](/concepts/vocabulary#harness) that reports no cost, on a model Kraft cannot price, so it cannot show the scope is under its `budget_usd`. | See [A budget cap cannot be checked](#a-budget-cap-cannot-be-checked). |

### Time caps and waits

| The reason says | What happened | Fix |
|---|---|---|
| `<scope> hit its time cap of N minutes` | A time cap ran out. | Raise it for this item, then retry: `kraft item set-policy ID --policy time_cap_minutes=240`. See [Raise a cap on a stopped item](/guides/day-to-day/raise-a-cap). |
| `<scope> hit its total time cap of N minutes` | A scope's wall-clock cap, which waits and gates count toward, ran out. | Raise it for this item, then retry: `kraft item set-policy ID --policy total_time_cap_minutes=N`. A node or task needs its path in the key, such as `merge_request_feedback.ci.await_ci.total_time_cap_minutes=N`. |
| `gate <gate> waited past its timeout of N minutes` | Nobody decided a gate in time. | Retry to reopen the gate, then decide it. |
| `<task> timed out waiting ...` | An external wait (CI, a review) ran out. | See [Waiting on CI or a review](#waiting-on-ci-or-a-review). Retry once the outside is fixed. |
| `rate_limit retries exhausted after N attempt(s)` | The agent's provider kept refusing for a rate limit. | Wait for the limit to reset, then retry. |
| A CI or automated-review failure, with a suggested **retry** | CI failed for its own reasons, or a cancelled run has no successor. | Retry once CI has recovered. |

### Restarts and crashes

| The reason says | What happened | Fix |
|---|---|---|
| `... are executed by the running Kraft daemon ...` | A task that runs inside Kraft itself failed. | Update and restart Kraft with `kraft admin update --restart`, after [pausing running items](/guides/run/restart-kraft#a-restart-ends-running-agents), or skip the node. |
| `reattach: running session, PID identity unconfirmed, no result (pid N is not alive)` | Kraft was stopped or restarted (`kraft admin stop`, `restart`, `update --restart`, or the service) while the item's agent ran, and a clean stop ends every running agent. | The board shows the item as failed. Retry. Pause running items before your next restart: see [A restart ends running agents](/guides/run/restart-kraft#a-restart-ends-running-agents). |
| `reattach crashed: <error>` | Kraft started and found the item's agent session still running, and the code that takes a running session over failed with the error shown. The agent's sandbox, if it had one, was closed. | Retry. If it happens again, [open an issue](https://github.com/itsOmidKarami/kraft/issues) with the error. |
| `... claimed this item but could not start a walk`, or `... could not start a walk: <error>` | A resume, retry, skip, gate decision or wait put the item back to running, then failed before the executor took it over. The ending names the error, if one was raised. `facts.cause` is `stranded`. | Retry: `kraft item retry ID`. If it happens again, run `kraft admin doctor` and [open an issue](https://github.com/itsOmidKarami/kraft/issues) with the error. |
| `executor crashed: ...`, `resume: ...`, or a `reattach ...` reason other than the ones above | Kraft crashed while the item ran: it was killed, or the machine went down. A restart you asked for gives the `reattach` row above, not this one. | Retry. If it happens again, run `kraft admin doctor` and [open an issue](https://github.com/itsOmidKarami/kraft/issues). |

## Stop reasons in detail

The tables link here from the reasons that need more than one row.

### Forge authentication fails

The stop's `facts.cause` is `forge_auth`, and the card reads **Failed** with the fix under it.

Kraft holds no forge token. It runs `gh` (GitHub) or `glab` (GitLab), and git, as the user the server runs as, and the forge refused what they sent. Nothing in Settings › Repos can supply a token.

1. On the machine the server runs on, sign the forge CLI in: `gh auth login`, or `glab auth login` for GitLab.
2. If git itself still cannot authenticate, check its credentials: `gh auth setup-git`, your SSH key or credential helper. `gh auth status` shows who the CLI is signed in as. `kraft admin doctor` checks only that the CLI is installed, not that it is signed in.
3. Run `kraft item retry ID`.

### `no forge is recorded for this repo`

The repo had no GitHub or GitLab `origin` when you connected it, so Kraft does not know which forge CLI to run.

1. Set `forge: github` or `forge: gitlab` on the repo in Settings › Repos, then **Review & publish** (or set it in `repos.yaml`).
2. Run `kraft item retry ID`.

### `declares neither test_scopes nor test_command`

The item stops at its test node (`verify` on `quick-task`, `verification` on `default`) because Kraft will not guess a test command.

1. Set `test_command` (or `test_scopes`) on the repo in Settings › Repos, then **Review & publish**, or set it in `repos.yaml`. For a repo with no tests, set `""`. `kraft repo connect PATH` again saves the command it now proposes.
2. Run `kraft item retry ID`.

### `nothing registers it for Claude Code`

No `kraft` MCP server is registered, so Kraft refused a Claude worker. The item stops at its first agent step with 0 tokens spent: `spec` on `default`, `implementation` on `quick-task`.

1. Install the Kraft plugin and run `/kraft:onboard`, or run `kraft admin init`.
2. Run `kraft item retry ID`.

`kraft admin doctor`'s `mcp server` row checks the same thing: see [The mcp server warning](/troubleshooting/doctor-failures#the-mcp-server-warning).

### `stored model override is not a model id`

A model override on the item or a node holds text that is not a model id, such as `sonnet 4`. The reason ends with the stored text.

1. Run the command the reason names, `kraft item set-overrides ID --clear` or `kraft item set-node-override ID --node N --clear`, or set a valid model.
2. Run `kraft item retry ID`.

Before 2.0, an override could hold any text, so an old item can still carry one.

### `no user.name configured`

The same stop names `user.email` when that is the missing one. git has no commit identity for the repo, so Kraft would not make the item's worktree: its commits would fail or carry an invented author.

1. Set both for the user Kraft runs as, for every repo:

   ```bash
   git config --global user.name "Your Name"
   git config --global user.email you@example.com
   ```

   To set them for one repo, run the same commands without `--global` inside it.
2. Run `kraft item retry ID`.

### `no setup_command declared`

The repo has no `setup_command`, and Kraft will not guess what to run in a fresh worktree. This is the usual first stop on a repo with no lockfile Kraft knows (see [How connect proposes commands](/reference/configuration/repos/connect-proposals)). The item stops at its first node.

1. Set **setup command** on the repo in Settings › Repos (or `setup_command` in `repos.yaml`). If the repo has nothing to install, tick **No setup needed** there instead (`""` in `repos.yaml`).
2. In Settings, click **Review & publish**: until you do, the change is a draft and the retry stops again.
3. Run `kraft item retry ID`.

### Git would not start the rebase

Nothing was rebased. Most often the base now tracks a file the worktree has untracked, such as a note or a script the agent never committed, and git will not overwrite it.

1. `cd "$(kraft repo path ID)"`.
2. Look at the files git names, then move, delete or commit them.
3. Run `kraft item retry ID`.

A `uv.lock` the setup command wrote and nobody changed is not one of these: Kraft sets it aside for the rebase. One that an older release recorded without a digest is kept in place, in case the agent edited it: see [Upgrade from 1.4 or an older release](/guides/run/upgrade-from-1-4#upgrading-from-a-150-release-candidate).

### A git operation is in progress

The worktree holds a rebase, merge, cherry-pick, revert, bisect or autostash. A sandboxed worker can plant one to move one of your branches. A rebase of Kraft's own that was cut short (a server killed mid-rebase, or an abort that could not run) leaves one too.

1. Look at the named file first. If you did not leave it there yourself, delete it as the reason says.
2. If deleting it leaves `HEAD` detached, check the item's branch out again with `git checkout -f <branch>`, as the reason names it. The branch still has the item's commits.
3. Run `kraft item retry ID`.

Never run `git rebase --abort`, `git merge --abort` or `--continue` on it: that is what moves the branch.

### A policy budget or token cap refused the launch

A policy `budget_usd` or `token_budget` refused the next launch. The message names the scope: `the work item`, or a node, step or task path in backticks.

`raise-budget` is refused for a `token_budget` or a path, and the item's page offers **Retry** with no raise. [Raise a cap on a stopped item](/guides/day-to-day/raise-a-cap) has the fix for each scope: **Raise cap** or `kraft item raise-budget` for the item-wide `budget_usd`, `kraft item set-policy` for a `token_budget`, and for a cap the chain sets on a path, `kraft item skip` or a change to the chain.

The item's policy was fixed when it was filed, so editing `policy.yaml` or the chain reaches only items filed afterwards.

### A budget cap cannot be checked

A launch in that scope ran on a harness that reports tokens but no cost, on a model `prices.json` cannot price. Kraft cannot show the scope is under its `budget_usd` and will not count the launch as free. Which harnesses these are is on [Harnesses that report no cost](/reference/harnesses/cost-reporting#harnesses-that-report-no-cost).

Raising `budget_usd` does not help: the stop stays while any `budget_usd` applies to the scope.

1. Clear the item-wide cap with `kraft item set-policy ID --policy budget_usd=none`. Add `--policy token_budget=N` to keep a bound.
2. Run `kraft item retry ID`.

The `budget_usd=none` fix clears a cap from the chain's own `policy:`, `repos.yaml` or a `policy.yaml` default too, but is refused under a `maxima.work_item.budget_usd`, and does not lift a cap the chain set on a node, step or task. For those, skip that node with `kraft item skip`, or bound that harness's scopes with `token_budget` in place of `budget_usd` and file the item again.

## Escalation turns and things that are not a stop

Some stops reach you only after Kraft has tried an **escalation turn** on its
own, up to three times (`auto_escalate_stuck_cap` in `policy.yaml`): a task
that failed after its recovery, an exhausted fix loop, and a `stuck:` stop.
`kraft view logs ID` shows those turns. The other stops (a configuration or
forge problem, a budget or time cap, a wait that ran out) come to you at once.

Three things look like a stop and are not one, or need a different move:

- A pending gate is not a stop. It waits for your decision:
  `kraft item approve ID` or `kraft item reject ID --note "..."`.
- If the work is heading the wrong way rather than failing, pause it and
  resume it with a steer: `kraft item pause ID`, then
  `kraft item resume ID --steer "..."`.
- To move past a node without running it, use `kraft item skip ID`.

## Waiting on CI or a review

Kraft keeps checking on both waits. One that outlasts its timeout stops the item with `<task> timed out waiting`.

### `merge_request_feedback` waits on "no checks yet"

The pull request has no CI checks, so nothing will ever pass. Do one of these:

- Add CI that runs on pull requests.
- Set `ci_checks: false` on the repo's entry in [`repos.yaml`](/reference/configuration/repos), so both CI waits, before and after the merge, pass at once.
- File the item on the `quick-task` chain.

### `external_approval` keeps waiting

A branch rule on the forge requires an approving review. Have someone else approve the pull request, or remove the rule. Kraft checks again on its own.
