`kraft admin doctor` runs every check, one row per line, and exits 1 if any row fails. `kraft admin health` checks only the server.

Each row starts with a verdict: `ok`, `warn`, `FAIL` or `skip`. Only `FAIL` sets the exit code: a warning means the check ran and found something worth reading, and a skip means it didn't run. The last line counts them: `N of M checks failed`, or `all M checks passed` with `, W warned` when any row warned.

A row about one repository carries its name, such as `setup my-repo`; here `<repo>` stands for that name. Each heading below is a row's name as doctor prints it, with a table of its messages when it has several. The rarer rows of a group share one table. The sandbox rows are on [Sandbox and Kit stops](/troubleshooting/sandbox-and-kit-stops#doctor-rows-for-a-sandbox).

## The server and its files

### `server`

Nothing answers on the configured address. Run `kraft`, or `kraft admin start --detach`.

### `restart`

A warning. `kraft admin update` installed a new release, but the running server still runs the old one. Until it restarts, the board shows a page saying so instead of the interface. Run `kraft admin restart`.

### `health`

The row reports the server's own health, and a message follows its colon.

| The row says | What it means | Fix |
|---|---|---|
| `health`: `orphaned agent sessions` | After a restart, Kraft couldn't confirm some sessions, and stopped their items. A session leaves the list once its item is retried or has ended. | Run `kraft item retry ID` for each affected item. |
| `health`: `storage: ...` | Worktrees use more than `storage.worktrees.limit`, so starts that need a new worktree are queued. With `auto_cleanup` set, the row counts finished items too recent to clean up. | Archive finished items (that frees their step outputs too), finish or abandon live work, or raise the limit. See [Limit the disk worktrees use](/guides/run/free-disk-space#limit-the-disk-worktrees-use). |
| `health`: `index: ...` | The search index reported an error, and the row names it. | Fix the cause the row names. `kraft admin reindex` rescans documents into the index. |
| `health`: `forge account NAME` _Added in 2.5_ | An API account's token is `refused`, `forbidden`, `tls` or `no_token`, or expires within 7 days, so `/health` is degraded. | Fix the token as [`forge account NAME`](#forge-account-name) says. |
| `health`: `invalid policy` or `invalid template` | `policy.yaml` or a chain file doesn't load. Kraft refuses new work. | Fix the named file, then run `kraft admin reload`. `kraft admin templates lint` checks every chain. |
| `health`: `invalid intake.yaml, auto-intake and its schedules are off` | The server started on an `intake.yaml` that doesn't load: a key Kraft doesn't know, or a schedule's `cron` it can't run (minute `61`, say). Auto-intake is off and none of its schedules fires. | Fix the named field, then run `kraft admin reload`. Settings › Auto-intake shows the field on the schedule. A trigger left in `policy.yaml` still fires. |
| `health`: `invalid intake.yaml, not applied` | A reload refused an edited `intake.yaml` for the same reasons. The auto-intake and schedules that were running are kept. | Fix the named field, then run `kraft admin reload`. |

### `storage`

A warning. Worktrees use more than `storage.worktrees.quota` and are still under the limit. Archive finished items before the limit holds starts. When the limit is passed, the row is `health`: `storage: ...` above.

### `worktrees`

A [worktree](/concepts/vocabulary#worktree) has no [work item](/concepts/vocabulary#work-item), not even an ended or archived one. A cancelled item's worktree isn't flagged. Check it for work you want, then delete it.

### Rarer server rows

| Row | What it means | Fix |
|---|---|---|
| `home` (a warning) | No server has ever run on this `KRAFT_HOME`. `config`, `harnesses.yaml` and the tokens fail until one has. | Run `kraft` once, then `kraft admin doctor` again. |
| `embeddings` | An installed vector-search extra's model won't load. Search keeps working as full-text search. | See [Vector search](/reference/web-ui/sidebar-search-and-keyboard#vector-search). |
| `pidfile` | `run/kraft.pid` names a process that is gone, or one that isn't this Kraft server: its pid was reused, or the process belongs to another program or user. `kraft admin stop` and `restart` never signal such a process. | Nothing. The next `kraft admin start`, `stop` or `restart` clears it. |
| `mcp token`, `trigger token` | The token file is missing, or other users can read it. | Start the server once to write it, or run `chmod 600` on it. |
| `old documents` (a warning) | Some worktrees still hold a `.engineering/` folder: documents and session summaries written there before Kraft kept one folder per item. Kraft reads them where they are. | Nothing needs fixing. The count drops as those items are archived. |
| `spa bundle` | This install has no web UI. | Reinstall from a release. |
| `version` (a warning) | The install couldn't reach the release feed, so it can't say whether a newer release exists. | Nothing needs fixing. `KRAFT_NO_UPDATE_CHECK` skips the check. |

## Configuration files

### `config`

| The row says | What it means | Fix |
|---|---|---|
| `config` | The config directory doesn't exist: no server has started on this home. | Run `kraft` once to seed it. |
| `config` (a warning): `... both exist and only one is read` | Before 2.0 the config directory was `templates/`. The 2.0 first start moved into your `config/` only what it lacked, so what both held stayed in `templates/`, which Kraft doesn't read. | Merge what `templates/` holds into `config/`, keeping the copy you want of each, then remove `templates/`. [Coming from 1.4](/guides/run/coming-from-1-4#config-directory-and-files) has the steps. |
| `config` (a warning): `templates is a link to ..., which is not read: 2.0 reads ...` | `templates/` is a link to a directory other than the one 2.0 reads, so what that directory holds isn't read. Kraft doesn't move a linked directory. | Set `KRAFT_CONFIG_DIR` to the link's target, as the row says, to keep using it. |

### `moved keys`

A warning. A file still has a key under its name before 2.0, or in its old file: `policy.yaml`'s `triggers`, `intake.yaml`'s `max_concurrent`, a repo's `default_chain_template`, or `theme.yaml`'s `group_by: template`. Move or rename each key by hand, as [Coming from 1.4](/guides/run/coming-from-1-4#config-directory-and-files) lists.

Kraft still reads the old key, so nothing stops, except `intake.yaml`'s `max_concurrent`: the server ignores it, with a warning, until the next start moves it to `policy.yaml`. For `triggers`, the row says how many the next start moves, and for each that stays, the entry and key `schedules:` refuses (`triggers.0.enabled`, say). Fix that entry and restart; [Coming from 1.4](/guides/run/coming-from-1-4#config-directory-and-files) says which triggers are skipped.

### `add-ons`

| The row says | What it means | Fix |
|---|---|---|
| `add-ons` | An add-on's store is missing, it needs another Kraft major, or `addons.yaml` or `addons.lock` doesn't read. The row names each add-on and why. | Run `kraft admin reload` to restore a missing store, or `kraft admin addon update`. If the verb refuses, see [Add-on problems](/troubleshooting/addon-problems). |
| `add-ons`: `its files do not match the locked digest` | Something changed a file under `run/addons/store/` after Kraft wrote it. A reload restores only a missing store, so it doesn't repair this. | Follow the steps for an edited store under [`add-on ... could not be read`](/troubleshooting/addon-problems#add-on-could-not-be-read). |
| `add-ons` (a warning) | An add-on is listed and not installed, or locked and no longer listed. An alias, ref or collection URL change waits for `update`. A locked commit isn't in the local mirror. A collection is a local directory. | Run `kraft admin addon install` or `kraft admin addon update`. A directory collection is fine on one machine. If the verb refuses, see [Add-on problems](/troubleshooting/addon-problems). |
| `add-on updates` (a warning) | An auto-updating add-on's last update was held for you or failed, or nothing in `policy.yaml` bounds what an unattended update may change. | Read the review with `kraft admin addon update`, or set `maxima:` in `policy.yaml`. If the verb refuses, see [Add-on problems](/troubleshooting/addon-problems). |

### `repo libraries`

| The row says | What it means | Fix |
|---|---|---|
| `repo libraries` | An accepted [repo library](/reference/configuration/repo-libraries) doesn't load: its harness or agent profile is gone, or its files no longer match the lock. The row names each one. | Run `kraft repo library` to review the remote's version, or restore the harness. |
| `repo libraries`: `... is in <repo-id>'s repo library, visible only to items in <repo-id>` | One of your files names a repo library from outside its repository: another repository's `default_chain` or `steering`, your own chain or `library.yaml`, a `harnesses.yaml` fallback, or a schedule for another repository. The row names the file and key. | Change that reference, or move it to the repository's own entry or schedule. See [Who can name it](/reference/configuration/repo-libraries#who-can-name-it). |
| `repo libraries` (a warning) | A change on the remote is waiting for you, or the last check of the remote failed (`network` or `auth`). | Run `kraft repo library` to read and take the change. For a failed check, make `git ls-remote origin` work in the checkout without a prompt. |
| `repo libraries` (a warning): `a change is held` | A repo with `library_auto_update: true` has a change the server didn't apply: a Reach line, a chain changed beyond its text, or text a gate's reviewer reads. The row says which. | Run `kraft repo library` to read and take the change. |
| `repo libraries` (a warning): `auto-update(s) on an instance with no allowed_tools, sandbox or maxima` | A repo sets `library_auto_update: true` and nothing in `policy.yaml` bounds what an unattended update may change. | Set `maxima:`, `defaults.allowed_tools` or a sandbox in `policy.yaml`, or turn the key off. |

### `access.yaml`

| The row says | What it means | Fix |
|---|---|---|
| `access.yaml` | The file doesn't load. The row says why. | Fix the named field. |
| `access.yaml`: `allowed_hosts: '...' is not a host name or IP address` | An `allowed_hosts` entry, usually a wildcard such as `*.ts.net` written into the file by hand, isn't one host. No browser's `Host` ever matches it, so a device using that name gets a 403. | Replace it with the exact name each device uses, such as `mybox.tailnet-name.ts.net`, in `access.yaml` or on the Access screen. |
| `access.yaml` (a warning): `bound to ... with no allowed_hosts` | The server is bound off loopback and `allowed_hosts` is empty, so a browser on any other device gets a page saying the name it used isn't allowed. | Add each exact name the devices use on the Access screen (from this machine, at `http://127.0.0.1:PORT`), or to `allowed_hosts` in `access.yaml`. |

While the server is bound to loopback the `allowed_hosts` list isn't read, so the first row is only a warning there. After an upgrade from 1.4, a board that opened on another device can stop opening: see [Network access](/guides/run/coming-from-1-4#network-access).

### Rarer configuration rows

| Row | What it means | Fix |
|---|---|---|
| `forges.yaml` _Added in 2.5_ | The file doesn't parse, or an account in it is refused. Two accounts are `default_for_host` for one host, or an address is `http://`. | Fix the key the row names, then run `kraft admin reload`. A server that hasn't reloaded keeps the accounts it has. |
| `chains` | A chain in the library doesn't resolve. The row names it, with the resolver's message. | Fix the named chain, then run `kraft admin reload`. `kraft admin templates lint` checks every chain. |
| `detectors.yaml` | Your own [`detectors.yaml`](/reference/configuration/repos/detectors) doesn't load: a key Kraft doesn't know, an unknown task reader, or a regex that doesn't compile. `kraft repo connect` refuses to probe until it does. | Fix the named field, or delete the file to use the shipped detectors alone. Nothing needs reloading. |
| `notify.yaml` | [`notify.yaml`](/reference/configuration/notify) doesn't load, names an event type Kraft doesn't know, or is enabled with no webhook URL. No notification is sent. | Fix the named field by hand, then run `kraft admin restart`. |
| `workers.yaml` _Added in 2.4_ | [`workers.yaml`](/reference/configuration/workers) doesn't load. At startup no machine is connected; after `kraft admin reload` the machines already loaded are kept. The row says why. | Fix the named field, then run `kraft admin reload`. |
| `worker: <name>` (a warning) _Added in 2.4_ | A registered machine is offline, and the row gives the server's reason. For an `ssh` machine it is the server's own `ssh` attempt, not your shell's. | Fix what the reason names. See [When a machine is offline](/reference/configuration/workers#when-a-machine-is-offline). |

## Agents and registration

### `mcp server`

The row reads Claude Code's registration only, not Codex's, Cursor's, OpenCode's, Amp's, Antigravity's or Gemini CLI's. [Use Kraft from your agent](/guides/day-to-day/agent-integration) has each one's own check. The item's own stops are [`nothing registers it for Claude Code`](/troubleshooting/launch-and-setup-stops#nothing-registers-it-for-claude-code) and [`is not on the PATH the worker gets`](/troubleshooting/launch-and-setup-stops#is-not-on-the-path-the-worker-gets), which have the steps.

| The row says | What it means | Fix |
|---|---|---|
| `mcp server` fails | Nothing registers a `kraft` MCP server with Claude Code: not your user scope, and not any connected repo. Some chain launches an unsandboxed Claude task, so every Claude worker is refused. | Install the Kraft plugin, or run `kraft admin init`. |
| `mcp server`: `... is not on the server's PATH` _Added in 2.5_ | The registered `kraft` MCP server's command isn't on the server's `PATH`, so Claude can't start it. A warning when a repo sets its own `PATH` or `kraft` entry, no chain needs it, or no server runs. | Put `kraft` on `PATH`: see [`kraft on PATH`](#kraft-on-path). |
| `mcp server` (a warning) | A registration exists, but a connected repo has none of its own (often its committed `.claude/settings.json` turns the plugin off), or no chain launches an unsandboxed Claude task. | Run `kraft admin init --repo` for that repo, or ignore the warning if no unsandboxed Claude task runs there. |

A repo whose items run sandboxed or on another harness is unaffected by a missing repo registration.

### `agent: <profile>`

The agent CLI isn't on the `PATH` of the shell running `doctor`. The row names the chains that select that [harness profile](/concepts/vocabulary#harness-profile) and so can't run, or says no chain can run when every chain does. For the shipped chains the CLI is `claude`.

1. Install the agent CLI, and make sure it runs from the shell that starts `kraft`.
2. Run `kraft admin restart`.

Doctor doesn't read the server's `PATH`. Under a service, the unit's `PATH` is the one that counts when an item runs, and a restart keeps it: see [`kraft on PATH`](#kraft-on-path) for reinstalling it. The row passes whether or not the CLI is signed in. A login error shows up in an item's log instead: see [Failed tasks and fix loops](/troubleshooting/failed-tasks-and-fix-loops#questions-and-failed-tasks).

### `kraft on PATH`

The plugin, every MCP registration and the hooks run `kraft` by name, so they start nothing when it isn't found. Look here when a service can't find `kraft` too.

| The row says | What it means | Fix |
|---|---|---|
| `kraft on PATH`: `not on PATH` | The `kraft` command isn't on `PATH`, usually right after a uv install. | Run `uv tool update-shell`, then start `kraft` from a new terminal. See [`kraft`: command not found](/troubleshooting/starting-and-reaching-kraft#kraft-command-not-found). |
| `kraft on PATH`: `another install` | Another install of `kraft` comes first on `PATH`. The MCP server and hooks run it. | Uninstall the other one, or reorder `PATH`. |

A service keeps the `PATH` it was installed with, which is also what finds the agent CLI the `agent: <profile>` row checks. Reinstall it from the new terminal you started `kraft` from, a shell where `kraft` and the agent CLI both run:

```bash
kraft admin uninstall-service
kraft admin install-service
```

### Rarer agent rows

| Row | What it means | Fix |
|---|---|---|
| `harnesses.yaml` | `harnesses.yaml` doesn't load, or the config directory is missing. | Fix the field the row names, or run `kraft` once to seed it. |
| `harness: <id>` | A [harness](/concepts/vocabulary#harness) definition doesn't load. The row says why. | Fix the harness file the row names. See [Harness definition files](/reference/harnesses/harness-files). |
| `profile: <name>` | A task selects an [agent profile](/concepts/vocabulary#agent-profile) its launch would refuse: it isn't defined in `harnesses.yaml`, has no model for the harness's [provider](/concepts/vocabulary#provider), or the provider takes no such model or effort. The row names each chain and task. | Fix the agent profile or the task's choice of it, as the row names. See [Agent profiles](/reference/harnesses/agent-profiles). |
| `cost: <harness>` (a warning) | That harness reports no cost, and the chains launch it on a model `prices.json` can't price, or on no model (the CLI's default). | Give its tasks or agent profile a priced model, or bound them with `token_budget`. See [Harnesses that report no cost](/reference/harnesses/cost-reporting#harnesses-that-report-no-cost). |

## Connected repositories

### `setup <repo>`

The repo has no `setup_command` in `repos.yaml`, so its next work item stops at its first node. The row reads `no setup_command in repos.yaml — suggest: ...` and names a command when it found one. Kraft won't guess what to run in a fresh worktree.

Run `kraft repo connect <path>` again to save the suggested command. If the row names none, see [`no setup_command declared`](/troubleshooting/launch-and-setup-stops#no-setup_command-declared) for every way to fix it.

### `tests <repo>`

A warning. Either `test_command ""`, so the repo's work items pass verify without running a test, or the repo has no test command, so its items stop at their test node.

For `""`, nothing needs fixing if the repo really has no tests. A repo connected before 2.0 often has no test command where the probe now finds one, and the row then names it: run `kraft repo connect <path>` to save it. When the row names none, see [`declares neither test_scopes nor test_command`](/troubleshooting/launch-and-setup-stops#declares-neither-test_scopes-nor-test_command).

### `forge <repo>`

| The row says | What it means | Fix |
|---|---|---|
| `forge <repo>` fails _Added in 2.5_ | `gh` or `glab` is missing, the repo has no [forge](/concepts/vocabulary#forge) recorded, or its `forge_account` names no account in forges.yaml or one for another forge. | Install and sign in the forge CLI: see [Forge authentication fails](/troubleshooting/forge-stops#forge-authentication-fails). With no forge recorded, see [`no forge is recorded for this repo`](/troubleshooting/forge-stops#no-forge-is-recorded-for-this-repo). |
| `forge <repo>` (a warning) | The repo's forge is `fake`, which is for dev only: it opens, merges and pushes nothing. | Nothing on a dev instance. On any other, set `forge: github` or `forge: gitlab`. |

Doctor checks every connected repo while any chain runs a forge task. `quick-task` needs no forge, so on a repo with no remote that you use only with `quick-task`, this one row fails and doctor exits 1; every other row should pass.

The detail names the [forges.yaml](/reference/configuration/forges) account the repo uses, as `gitlab · glab · account corp-gl`. When the host's `default_for_host` account says another forge than the repo, the detail says that account was skipped, and the repo uses the CLI as before. A `forge_account` that names no account, or an account for another forge than the repo's, fails the row and names it.

A repo on a `client: api` account passes when the account's token sees the project; the detail says so. When the forge wants single sign-on for the token, the detail ends `· authorize it: ` and a link; open it, authorise the token, and run doctor again.

### `forge account NAME`
_Added in 2.5_

| The row says | What it means | Fix |
|---|---|---|
| `forge account NAME` | An API account's token is refused (`refused`), lacks rights (`forbidden`), has no value (`no_token`) or fails TLS (`tls`). When the forge wants single sign-on, the detail adds `authorize it:` and a link. | Open the link and authorise the token, or fix the token source and run `kraft admin forge test NAME`. A `tls` row needs the forge's CA in `ca_file`. |
| `forge account NAME` (a warning) | The API is `unreachable`, no probe has run yet, the token expires within 7 days, its prefix doesn't match its `kind`, or it comes from `GITLAB_TOKEN`, `GH_TOKEN` or `GITHUB_TOKEN`, which Kraft hides from its processes. | Check `api_url` and the network, run `kraft admin forge test NAME`, renew the token, or read it from a variable only Kraft uses. |

### Rarer repository rows

| Row | What it means | Fix |
|---|---|---|
| `repo <repo>` | A connected repo's path is gone or isn't a git repo. | Reconnect it, or run `kraft repo disconnect PATH`. |
| `keys <repo>` | The repo's entry in `repos.yaml` has keys nothing reads, such as a typo. The row lists them. | Remove them. A key an older Kraft wrote is a warning that names its replacement: see [`repos.yaml`](/reference/configuration/repos). |
| `steering <repo>` | The repo's `steering:` names a [steering profile](/concepts/vocabulary#steering-profile) the library doesn't define. | Define the steering profile in the library, or remove the name from the repo's `steering:`. |
| `duplicate <repo>` (a warning) | A repo you connected and a submodule checkout Kraft detected are one repository, usually a member you connected on its own and its root's submodule. A workspace member naming the second runs with none of the first's settings. | Point the workspace member at the entry you configured (`workspaces:` in `repos.yaml`), then run `kraft repo disconnect` on the other. |

## Rows that never fail

These rows report and never fail.

| Row | What it reports |
|---|---|
| `kraft-default` | What to know about Kraft's built-in chains and library; see [What `doctor` lists about kraft-default](/guides/run/upgrade-kraft#what-doctor-lists-about-kraft-default). _Added in next_ |
| `capabilities` | What this version can do that your seeded settings files (today `harnesses.yaml`) don't yet use, and how to adopt each. |
| `bd` | Whether the optional `bd` issue tracker is installed. |
| `shell completion` | Whether zsh's tab completion is set up. It skips on any other shell. |
| `repos` | `none connected` when no repo is connected. It skips when no server is up. |
| `review bots` | A warning when a review bot may not be reviewing at all. It skips when no server is up, or one too old to answer. _Added in 2.5_ |

### `review bots`
_Added in 2.5_

The row names a bot that has never posted in a repo, across three items or more. Some bots post nothing on clean code, but one that has never posted at all usually has its login in `automated_review` misspelt, or isn't installed on that project. Check both. The warning clears once the repo's next review waits for the corrected login. A bot that has posted there once isn't named, even if it later stops.
