The tables below hold every row that can fail or warn, and
[Rows that never fail](#rows-that-never-fail) the rest. Find the row's name in
the first column, then its fix. A row that needs more than a cell links to an
entry under [Doctor rows in detail](#doctor-rows-in-detail).

## Doctor rows

`kraft admin doctor` runs every check, one row per line, and exits 1 if any row fails. `kraft admin
health` checks only the server.

Each row starts with a verdict: `ok`, `warn`, `FAIL` or `skip`. Only `FAIL` sets the exit code: a warning means the check ran and found something worth reading, and a skip means it didn't run. The last line counts them: `N of M checks failed`, or `all M checks passed` with `, W warned` when any row warned.

A row about one repository carries its name, such as `setup my-repo`. In the tables, `<repo>` stands for that name.

### The server and its files

| Row | What it means | Fix |
|---|---|---|
| `home` (a warning) | No server has ever run on this `KRAFT_HOME`. `config`, `harnesses.yaml` and the tokens fail until one has. | Start `kraft` once, then run `doctor` again. |
| `server` | Nothing answers on the configured address. | Start it: `kraft`, or `kraft admin start --detach`. |
| `restart` (a warning) | `kraft admin update` installed a new release, but the running server still runs the old one. Until it restarts, the board shows a page saying so instead of the interface. | `kraft admin restart`. |
| `health`: `orphaned agent sessions` | After a restart, Kraft couldn't confirm some sessions, and stopped their items. A session leaves the list once its item is retried or has ended. | Retry the affected items. |
| `health`: `storage: ...` | Worktrees use more than `storage.worktrees.limit`, so starts that need a new worktree are queued. | Archive finished items (that frees their step outputs too), finish or abandon live work, or raise the limit. With `auto_cleanup` set, the row counts finished items too recent to clean up. See [Limit the disk worktrees use](/guides/run/logs-and-disk-space#limit-the-disk-worktrees-use). |
| `storage` (a warning) | Worktrees use more than `storage.worktrees.quota`, and are still under the limit. | Archive finished items before the limit holds starts. |
| `health`: `index: ...` | The search index reported an error, and the row names it. | Fix the cause the row names. `kraft admin reindex` rescans documents into the index. |
| `embeddings` | An installed vector-search extra's model won't load. Search keeps working as full-text search. | See [Vector search](/reference/web-ui/sidebar-search-and-keyboard#vector-search). |
| `pidfile` | `run/kraft.pid` names a process that is gone, or one that isn't this Kraft server: its pid was reused, or the process belongs to another program or user. `kraft admin stop` and `restart` never signal such a process. | Nothing. The next `kraft admin start`, `stop` or `restart` clears it. |
| `mcp token`, `trigger token` | The token file is missing, or other users can read it. | Start the server once to write it, or `chmod 600` it. |
| `worktrees` | A [worktree](/concepts/vocabulary#worktree) has no [work item](/concepts/vocabulary#work-item), not even an ended or archived one. A cancelled item's worktree isn't flagged. | Check it for work you want, then delete it. |
| `old documents` (a warning) | Some worktrees still hold a `.engineering/` folder: documents and session summaries written there before Kraft kept one folder per item. Kraft reads them where they are. | Nothing needs fixing. The count drops as those items are archived. |
| `spa bundle` | This install has no web UI. | Reinstall from a release. |
| `version` (a warning) | The install couldn't reach the release feed, so it can't say whether a newer release exists. | Nothing needs fixing. `KRAFT_NO_UPDATE_CHECK` skips the check. |

### Configuration files

| Row | What it means | Fix |
|---|---|---|
| `config` | The config directory doesn't exist: no server has started on this home. | Start `kraft` once to seed it. |
| `forges.yaml` | The file doesn't parse, or an account in it is refused. Two accounts are `default_for_host` for one host, or an address is `http://`. _Added in 2.5_ | Fix the key the row names, then `kraft admin reload`. A server that hasn't reloaded keeps the accounts it has. |
| `config` (a warning): `... both exist and only one is read` | Before 2.0 the config directory was `templates/`. One is still a directory of its own beside `config/`, not the link 2.0's first start leaves. | See [Both templates and config exist](#both-templates-and-config-exist). |
| `config` (a warning): `templates is a link to ..., which is not read: 2.0 reads ...` | `templates/` is a link to a directory other than the one 2.0 reads, so what that directory holds isn't read. Kraft doesn't move a linked directory. | Set `KRAFT_CONFIG_DIR` to the link's target, as the row says, to keep using it. |
| `moved keys` (a warning) | A file still has a key under its name before 2.0, or in its old file: `policy.yaml`'s `triggers`, `intake.yaml`'s `max_concurrent`, a repo's `default_chain_template`, or `theme.yaml`'s `group_by: template`. | See [Moved keys](#moved-keys). |
| `health`: `forge account NAME` | An API account's token is `refused`, `forbidden`, `tls` or `no_token`, or expires within 7 days, so `/health` is degraded. _Added in 2.5_ | Fix the token as its `forge account NAME` row below says. |
| `health`: `invalid policy` or `invalid template` | `policy.yaml` or a chain file doesn't load. Kraft refuses new work. | Fix the named file, then `kraft admin reload`. `kraft admin templates lint` checks every chain. |
| `health`: `invalid intake.yaml, auto-intake and its schedules are off` | The server started on an `intake.yaml` that doesn't load. Auto-intake is off and none of its schedules fires. | Fix the named field, then `kraft admin reload`. See [Invalid intake.yaml](#invalid-intakeyaml). |
| `health`: `invalid intake.yaml, not applied` | A reload refused an edited `intake.yaml` for the same reasons. The auto-intake and schedules that were running are kept. | Fix the named field, then `kraft admin reload`. |
| `chains` | A chain in the library doesn't resolve. The row names it, with the resolver's message. | Fix the named chain, then `kraft admin reload`. `kraft admin templates lint` checks every chain. |
| `add-ons` | An add-on's store is missing, it needs another Kraft major, or `addons.yaml` or `addons.lock` doesn't read. The row names each add-on and why. | Run `kraft admin reload` to restore a missing store, or `kraft admin addon update`. If the verb refuses, see [Add-on problems](/troubleshooting/addon-problems). |
| `add-ons`: `its files do not match the locked digest` | Something changed a file under `run/addons/store/` after Kraft wrote it. A reload restores only a missing store, so it doesn't repair this. | Follow the steps for an edited store under [`add-on ... could not be read`](/troubleshooting/stop-reasons-in-detail#add-on-could-not-be-read). |
| `add-ons` (a warning) | An add-on is listed and not installed, or locked and no longer listed. An alias, ref or collection URL change waits for `update`. A locked commit isn't in the local mirror. A collection is a local directory. | Run `kraft admin addon install` or `kraft admin addon update`. A directory collection is fine on one machine. If the verb refuses, see [Add-on problems](/troubleshooting/addon-problems). |
| `repo libraries` | An accepted [repo library](/reference/configuration/repo-libraries) doesn't load: its harness or agent profile is gone, or its files no longer match the lock. The row names each one. | Run `kraft repo library` to review the remote's version, or restore the harness. |
| `repo libraries`: `... is in <repo-id>'s repo library, visible only to items in <repo-id>` | One of your files names a repo library from outside its repository: another repository's `default_chain` or `steering`, your own chain or `library.yaml`, a `harnesses.yaml` fallback, or a schedule for another repository. The row names the file and key. | Change that reference, or move it to the repository's own entry or schedule. See [Who can name it](/reference/configuration/repo-libraries#who-can-name-it). |
| `repo libraries` (a warning) | A change on the remote is waiting for you, or the last check of the remote failed (`network` or `auth`). | Run `kraft repo library` to read and take the change. For a failed check, make `git ls-remote origin` work in the checkout without a prompt. |
| `repo libraries` (a warning): `a change is held` | A repo with `library_auto_update: true` has a change the server didn't apply: a Reach line, a chain changed beyond its text, or text a gate's reviewer reads. The row says which. | Run `kraft repo library` to read and take the change. |
| `repo libraries` (a warning): `auto-update(s) on an instance with no allowed_tools, sandbox or maxima` | A repo sets `library_auto_update: true` and nothing in `policy.yaml` bounds what an unattended update may change. | Set `maxima:`, `defaults.allowed_tools` or a sandbox in `policy.yaml`, or turn the key off. |
| `add-on updates` (a warning) | An auto-updating add-on's last update was held for you or failed, or nothing in `policy.yaml` bounds what an unattended update may change. | Read the review with `kraft admin addon update`, or set `maxima:` in `policy.yaml`. If the verb refuses, see [Add-on problems](/troubleshooting/addon-problems). |
| `detectors.yaml` | Your own [`detectors.yaml`](/reference/configuration/repos/detectors) doesn't load: a key Kraft doesn't know, an unknown task reader, or a regex that doesn't compile. `kraft repo connect` refuses to probe until it does. | Fix the named field, or delete the file to use the shipped detectors alone. Nothing needs reloading. |
| `notify.yaml` | [`notify.yaml`](/reference/configuration/notify) doesn't load, names an event type Kraft doesn't know, or is enabled with no webhook URL. No notification is sent. | Fix the named field by hand, then `kraft admin restart`. |
| `access.yaml` | The file doesn't load. The row says why. | Fix the named field. |
| `access.yaml`: `allowed_hosts: '...' is not a host name or IP address` | An `allowed_hosts` entry, usually a wildcard such as `*.ts.net` written into the file by hand, isn't one host. No browser's `Host` ever matches it, so a device using that name gets a 403. | Replace it with the exact name each device uses. See [Allowed hosts rows](#allowed-hosts-rows). |
| `access.yaml` (a warning): `bound to ... with no allowed_hosts` | The server is bound off loopback and `allowed_hosts` is empty, so a browser on any other device gets a page saying the name it used isn't allowed. | Add each exact name the devices use. See [Allowed hosts rows](#allowed-hosts-rows). |
| `workers.yaml` | [`workers.yaml`](/reference/configuration/workers) doesn't load. At startup no machine is connected; after `kraft admin reload` the machines already loaded are kept. The row says why. _Added in 2.4_ | Fix the named field, then `kraft admin reload`. |
| `worker: <name>` (a warning) | A registered machine is offline, and the row gives the server's reason. For an `ssh` machine it is the server's own `ssh` attempt, not your shell's. _Added in 2.4_ | Fix what the reason names. See [When a machine is offline](/reference/configuration/workers#when-a-machine-is-offline). |

### Agents and registration

| Row | What it means | Fix |
|---|---|---|
| `mcp server` | Nothing registers a `kraft` MCP server with Claude Code: not your user scope, and not any connected repo. Every Claude worker is refused. | Install the Kraft plugin, or run `kraft admin init`. See [The mcp server warning](#the-mcp-server-warning). |
| `mcp server`: `... is not on the server's PATH` | The registered `kraft` MCP server's command isn't on the server's `PATH`, so Claude can't start it. A warning when a repo sets its own `PATH` or `kraft` entry, no chain needs it, or no server runs. _Added in 2.5_ | See [`is not on the PATH the worker gets`](/troubleshooting/stop-reasons-in-detail#is-not-on-the-path-the-worker-gets). |
| `mcp server` (a warning) | A registration exists, but a connected repo has none of its own, or no chain launches an unsandboxed Claude task. | Register it for that repo (`kraft admin init --repo`), or ignore it. See [The mcp server warning](#the-mcp-server-warning). |
| `agent: <profile>` | The agent CLI isn't on the `PATH` of the shell running `doctor`. The row names the chains that select that [harness profile](/concepts/vocabulary#harness-profile) and so can't run, or says no chain can run when every chain does. | Install the CLI and put it on `PATH`. See [The agent row and the service PATH](#the-agent-row-and-the-service-path). |
| `acp: <id>` | A `kind: acp` harness a chain selects didn't start, didn't answer, or asked for a login. When it passes, the detail lists what the agent offers. _Added in next_ | Sign in once in a terminal, or fix the entry's `command`. See [The acp rows](#the-acp-rows). |
| `acp-cost: <id>` (a warning) | The entry's `reports` has no `cost`, so a dollar cap refuses its launches unless it reports tokens on a priced model. An ACP session with no cost is unknown spend, never $0. _Added in next_ | Add `cost` to `reports` if the agent sends one, or accept the refusal. See [ACP agents](/reference/harnesses/cost-reporting#acp-agents). |
| `harnesses.yaml` | `harnesses.yaml` doesn't load, or the config directory is missing. | Fix the field the row names, or start `kraft` once to seed it. |
| `harness: <id>` | A [harness](/concepts/vocabulary#harness) definition doesn't load. The row says why. | Fix the harness file the row names. See [Harness definition files](/reference/harnesses/harness-files). |
| `profile: <name>` | A task selects an [agent profile](/concepts/vocabulary#agent-profile) its launch would refuse: it isn't defined in `harnesses.yaml`, has no model for the harness's [provider](/concepts/vocabulary#provider), or the provider takes no such model or effort. The row names each chain and task. | Fix the agent profile or the task's choice of it, as the row names. See [Agent profiles](/reference/harnesses/agent-profiles). |
| `cost: <harness>` (a warning) | That harness reports no cost, and the chains launch it on a model `prices.json` can't price, or on no model (the CLI's default). | Give its tasks or agent profile a priced model, or bound them with `token_budget`. See [Harnesses that report no cost](/reference/harnesses/cost-reporting#harnesses-that-report-no-cost). |
| `kraft on PATH`: `not on PATH` | The `kraft` command isn't on `PATH`, usually right after a uv install. The plugin, every MCP registration and the hooks run it by name, so they start nothing. | Run `uv tool update-shell`, then start `kraft` from a new terminal. See [`kraft`: command not found](/troubleshooting/starting-and-reaching-kraft#kraft-command-not-found). |
| `kraft on PATH`: `another install` | Another install of `kraft` comes first on `PATH`. The MCP server and hooks run it. | Uninstall the other one, or reorder `PATH`. |

### Connected repositories

| Row | What it means | Fix |
|---|---|---|
| `repo <repo>` | A connected repo's path is gone or isn't a git repo. | Reconnect it, or `kraft repo disconnect PATH`. |
| `setup <repo>` | The repo has no `setup_command` in `repos.yaml`, so its next work item stops. The row names a command when it found one. | Run `kraft repo connect <path>` again to save the suggested command, or see [The setup row](#the-setup-row). |
| `tests <repo>` (a warning) | `test_command ""`: the repo's work items pass verify without running a test. Or the repo has no test command, so its items stop at their test node. | For `""`, nothing, if the repo really has no tests. Otherwise see [Older entries and the tests row](#older-entries-and-the-tests-row). |
| `keys <repo>` | The repo's entry in `repos.yaml` has keys nothing reads, such as a typo. The row lists them. | Remove them. A key an older Kraft wrote is a warning that names its replacement: see [`repos.yaml`](/reference/configuration/repos). |
| `steering <repo>` | The repo's `steering:` names a [steering profile](/concepts/vocabulary#steering-profile) the library doesn't define. | Define the steering profile in the library, or remove the name from the repo's `steering:`. |
| `forge <repo>` | `gh` or `glab` is missing, the repo has no [forge](/concepts/vocabulary#forge) recorded, or its `forge_account` names no account in forges.yaml or one for another forge. _Added in 2.5_ | See [The forge row](#the-forge-row). |
| `forge <repo>` (a warning) | The repo's forge is `fake`, which is for dev only: it opens, merges and pushes nothing. | Nothing on a dev instance. On any other, set `forge: github` or `forge: gitlab`. |
| `forge account NAME` | An API account's token is refused (`refused`), lacks rights (`forbidden`), has no value (`no_token`) or fails TLS (`tls`). When the forge wants single sign-on, the detail adds `authorize it:` and a link. _Added in 2.5_ | Open the link and authorise the token, or fix the token source and run `kraft admin forge test NAME`. A `tls` row needs the forge's CA in `ca_file`. |
| `forge account NAME` (a warning) | The API is `unreachable`, no probe has run yet, the token expires within 7 days, its prefix doesn't match its `kind`, or it comes from `GITLAB_TOKEN`, `GH_TOKEN` or `GITHUB_TOKEN`, which Kraft hides from its processes. _Added in 2.5_ | Check `api_url` and the network, run `kraft admin forge test NAME`, renew the token, or read it from a variable only Kraft uses. |
| `duplicate <repo>` (a warning) | A repo you connected and a submodule checkout Kraft detected are one repository, usually a member you connected on its own and its root's submodule. A workspace member naming the second runs with none of the first's settings. | Point the workspace member at the entry you configured (`workspaces:` in `repos.yaml`), then `kraft repo disconnect` the other. |

### The sandbox

These rows appear only for a repository that runs [sandboxed](/concepts/vocabulary#sandbox).

| Row | What it means | Fix |
|---|---|---|
| `sandbox <repo>` | The runtime doesn't answer, the image isn't pulled, or the sandbox sets something the runtime can't enforce. The row says which. | See [The sandbox row](#the-sandbox-row). |
| `sandbox <repo>` for a `kind: os` sandbox on Linux | The host can't run bubblewrap: a user-namespace `sysctl`, a missing or old `bwrap`, Kraft running as root, or an unsupported platform. The row passes as `bubblewrap <version>`. _Added in 2.3_ | Apply the fix the row's message names. See [A kind: os sandbox is refused](/troubleshooting/sandbox-and-kit-stops#a-kind-os-sandbox-is-refused). |
| `sandbox <repo>` for a `kind: os` sandbox on a Mac | The Mac can't run Seatbelt: an unsupported machine, Kraft running as root, `/usr/bin/sandbox-exec` missing, Kraft inside a sandbox, or a profile `sandbox-exec` rejects. The row passes as `Seatbelt (sandbox-exec), macOS <version>`. _Added in 2.3_ | Apply the fix the row's message names. See [A kind: os sandbox is refused](/troubleshooting/sandbox-and-kit-stops#a-kind-os-sandbox-is-refused). |
| `sandbox <repo>`: `the Kit <ref> is refused: ...` | The repository's [Kit](/reference/configuration/sandbox/kits) can't be fetched or won't run, so each item there stops. | See [A Kit is refused](/troubleshooting/sandbox-and-kit-stops#a-kit-is-refused). |
| `kit hosts <repo>` (a warning) | The Kit doesn't allow a host a harness requires, so that harness's sessions under it are refused the host. | Add the host to the Kit's `runtime` allow list and rebuild it, or run that harness elsewhere. |
| `kit credentials <repo>` (a warning) | An optional Kit credential has no binding in `sandbox.yaml`, so it is skipped. | Add `<service>: <DAEMON_ENV_NAME>` under `credentials` in [sandbox.yaml](/reference/configuration/sandbox/sandbox-yaml). |
| `egress <repo>` | The sandbox sets no `network:` and no `unrestricted_network: true`, so every agent launch into it is refused. With `unrestricted_network: true` it is a warning: tasks there reach any host, the cloud metadata address included, and gates aren't enforced. | Set `network:` in the sandbox policy to allow only the hosts they need. See [Network policy](/reference/configuration/sandbox/network-policy#without-a-network-policy). |
| `egress listener` | The server's TLS listener didn't answer, so a sandbox under `network:` on a runtime in a VM has no route out. The row appears when some sandbox sets `network:`. | Restart the server: `kraft admin restart`. |
| `proxy <repo>` (a warning) | A proxy variable points at this machine's loopback, which a container can't reach, so sandboxed tasks run without it. | Set `network:` in the sandbox policy to route them through Kraft's own proxy. See [Proxy](/reference/configuration/sandbox/sandbox-yaml#proxy). |
| `ca <repo>` for a `kind: os` sandbox | Always passes: the sandbox trusts the host's trust store plus the CA files the daemon's CA variables name, and `ca_bundle` isn't used. _Added in 2.3_ | None. |
| `ca <repo>` (a warning) | `SSL_CERT_FILE` is set but can't be used as the sandbox's extra CA, so sandboxed tasks trust only their image's roots. | Fix the file, or name a CA in `ca_bundle` in `sandbox.yaml`. See [CA certificates](/reference/configuration/sandbox/sandbox-yaml#ca-certificates). |
| `credentials <repo>` | A credential the sandbox's proxy manages has no value here, so the proxy refuses every request that should carry it. A name no harness declares how to inject only warns. | Give each name the row lists a value. See [Credentials](/reference/configuration/sandbox/credentials#where-the-value-is-kept). |

The `proxy`, `ca` and `credentials` rows read the environment of the `kraft admin doctor` process, not the running server's. They agree when both started from the same shell. If the server runs as a service with its own environment, check that one.

### Rows that never fail

Six rows report and never fail:

| Row | What it reports |
|---|---|
| `kraft-default` | What to know about Kraft's built-in chains and library; see [kraft-default](#kraft-default). _Added in next_ |
| `capabilities` | What this version can do that your seeded settings files (today `harnesses.yaml`) don't yet use, and how to adopt each. |

## Doctor rows in detail

The tables link here from the rows with more to say.

### Review bots
_Added in 2.5_

The row names a bot that has never posted in a repo, across three items or more. Some bots post nothing on clean code, but one that has never posted at all usually has its login in `automated_review` misspelt, or isn't installed on that project. Check both. The warning clears once the repo's next review waits for the corrected login. A bot that has posted there once isn't named, even if it later stops.

### kraft-default
_Added in next_

Kraft's own chains and library are the built-in add-on `kraft-default`, read from the installed Kraft, so they can't fall behind it. The row is always `ok`, and a warning when it has any of these lines:

| Line | Meaning | Fix |
|---|---|---|
| `the <version> update was held: ...` | An unattended update would break one of your overrides, or Kraft couldn't compare. | Run `kraft admin update`, accept with the break shown, then fix the override it names. See [What an update shows about kraft-default](/guides/run/upgrade-kraft#what-an-update-shows-about-kraft-default). After accepting, and until you fix the override, filing on `default` answers 422. |
| `<from> -> <to> changed kraft-default:` | An unattended update installed a release that changed it; the lines say how, including changes to how far a run goes. | None. It clears at the next update. |
| `chains/<file>.yaml is a full copy and hides kraft-default:<id>` | A home seeded before the built-in keeps its own copy, which Kraft never rewrites. | See [Move onto kraft-default](/guides/run/upgrade-your-configuration). |
| `kraft-default@<collection>: Kraft now ships kraft-default itself; ...` | An add-on copy installed from GitHub on 2.5 is left out in favour of the built-in. | `kraft admin addon update kraft-superpowers@kraft-sdlc`, then `kraft admin addon uninstall kraft-default@kraft-sdlc`. See [If you installed kraft-default from GitHub](/guides/customize/share-chains-with-addons#if-you-installed-kraft-default-from-github). |
| `harnesses.yaml lacks <names>; using the packaged ones` | Your file lacks a harness or profile `kraft-default` needs, and Kraft supplies it from the package. | None needed; define the name in `harnesses.yaml` to change it. See [Names from the package](/reference/configuration/harnesses-file#names-from-the-package). |
| `repository id kraft-default is kraft-default's namespace; rename it` | A `repos.yaml` entry uses the reserved ID. | Rename the repository. |
| `maxima: clamps kraft-default task(s): ...` | `policy.yaml`'s `maxima:` is below some built-in tasks' caps. They run clamped; the add-on stays. | Raise `maxima:`, or accept the clamp. |

The board shows the same lines in a banner, "Kraft's own chains need attention", and the webhook and a hidden browser tab are told once for each new state, so you need not run `doctor` to see it. **Hide until it changes** hides the banner in that browser. The fix for each line is the one in the table. The banner never makes `/api/health` `degraded`.

### Both templates and config exist

Before 2.0, the config directory was `templates/`. The 2.0 first start found a `config/` you had made and moved in only what it lacked; what both held stayed in `templates/`, and Kraft doesn't read it. Merge what `templates/` holds into `config/`, keeping the copy you want of each, and remove `templates/`: [Changes from 1.4 to 2.0](/reference/changes-from-1-4#config-directory-and-files) has the steps.

### Moved keys

Before 2.0, each key the row names lived in another file or under another name. Kraft still reads it, so nothing stops, except `intake.yaml`'s `max_concurrent`: the server ignores it, with a warning, until the next start moves it to `policy.yaml`. Move or rename each key by hand, as [Changes from 1.4 to 2.0](/reference/changes-from-1-4#config-directory-and-files) lists.

For `triggers`, the row says how many the next start moves, and for each that stays, the entry and key `schedules:` refuses (`triggers.0.enabled`, say). Fix that entry and restart; [Changes from 1.4 to 2.0](/reference/changes-from-1-4#config-directory-and-files) says which triggers are skipped.

### Invalid intake.yaml

The server started on an `intake.yaml` that doesn't load: a key Kraft doesn't know, or a schedule's `cron` it can't run (minute `61`, say). Settings › Auto-intake shows the field on the schedule. Fix it, then `kraft admin reload`.

A trigger left in `policy.yaml` still fires.

### The mcp server warning

The row reads Claude Code's registration only, not Codex's, Cursor's, OpenCode's, Amp's, Antigravity's or Gemini CLI's. [Use Kraft from your agent](/guides/day-to-day/agent-integration) has each one's own check.

The row fails when nothing registers a `kraft` MCP server and some chain launches an unsandboxed Claude task, so that worker would be refused. It is a warning instead when:

- a registration exists, but a connected repo has none of its own, often because its committed `.claude/settings.json` turns the plugin off. In that repo an unsandboxed task on the harness the row names is refused. A repo whose items run sandboxed or on another harness is unaffected.
- no chain launches an unsandboxed Claude task, for example when every repo is sandboxed or the library is Codex-only.

Register it for the repo with `kraft admin init --repo`, or ignore the warning if no unsandboxed Claude task runs there. The stop an item shows is [`nothing registers it for Claude Code`](/troubleshooting/stop-reasons-in-detail#nothing-registers-it-for-claude-code), which has the steps.

### The agent row and the service PATH

The `agent: <profile>` row, where `<profile>` is a harness profile, passes when the agent CLI is on the `PATH` of the shell running `doctor`. For the shipped chains the CLI is `claude`.

1. Install the agent CLI, and make sure it runs from the shell that starts `kraft`.
2. Restart Kraft with `kraft admin restart`.

Doctor doesn't read the server's `PATH`. Under a service, the unit's `PATH` is the one that counts when an item runs, and a restart keeps it: see [The `kraft on PATH` doctor row](/troubleshooting/starting-and-reaching-kraft#the-kraft-on-path-doctor-row) for reinstalling it.

The row passes whether or not the CLI is signed in. A login error shows up in an item's log instead: see [Why did my item stop?](/troubleshooting/why-did-my-item-stop#find-your-reason).

### The acp rows
_Added in next_

The `acp: <id>` row starts the agent itself, sends `initialize` and `session/new`, and ends it. It sends no prompt, so it spends nothing. It fails when the agent didn't start, didn't answer within 20 seconds, or answered `session/new` with an authentication error (`log in: the agent asked for authentication`). A pass reads `initialize ok: resume=yes load=yes system_prompt=no options=model,mode`. `kraft admin acp-probe` runs a real session and checks the entry's declarations.

The row is skipped when the agent's program isn't on `PATH`, since the `agent:` row already fails for it.

### The setup row

The row reads `no setup_command in repos.yaml — suggest: ...`, and names a command when it found one. Kraft won't guess what to run in a fresh worktree, so the repo's next work item stops at its first node. Running `kraft repo connect <path>` again saves the suggested command; [`no setup_command declared`](/troubleshooting/stop-reasons-in-detail#no-setup_command-declared) has every way to fix it.

### Older entries and the tests row

A repo connected before 2.0 often has no test command where the probe now finds one, and the row then names it: `kraft repo connect <path>` saves it. When the row names none, [`declares neither test_scopes nor test_command`](/troubleshooting/stop-reasons-in-detail#declares-neither-test_scopes-nor-test_command) has the steps.

### The forge row

The row fails when `gh` (GitHub) or `glab` (GitLab) is missing, or when no forge is recorded for the repo because it had no GitHub or GitLab `origin` when you connected it. For the second, [`no forge is recorded for this repo`](/troubleshooting/stop-reasons-in-detail#no-forge-is-recorded-for-this-repo) has the fix; for the first, install the forge CLI and sign it in: [Forge authentication fails](/troubleshooting/stop-reasons-in-detail#forge-authentication-fails) has the commands.

Doctor checks every connected repo while any chain runs a forge task. `quick-task` needs no forge, so on a repo with no remote that you use only with `quick-task`, this one row fails and doctor exits 1; every other row should pass.

The detail names the [forges.yaml](/reference/configuration/forges) account the repo uses, as `gitlab · glab · account corp-gl`. When the host's `default_for_host` account says another forge than the repo, the detail says that account was skipped, and the repo uses the CLI as before.

A `forge_account` that names no account, or an account for another forge than the repo's, fails the row and names it.

A repo on a `client: api` account, GitHub or GitLab, passes when the account's token sees the project; the detail says so. When the forge wants single sign-on for the token, the detail ends `· authorize it: ` and a link; open it, authorise the token, and run doctor again.

### The sandbox row

For a sandboxed repository, the row names the runtime it found (Docker or Podman, rootless or not) and the resource limits it can enforce. It reads `sandbox.yaml` afresh each run. It fails when:

- the runtime doesn't answer. Start the Docker or Podman daemon. Doctor can wait about a minute for a runtime that is slow to answer: see [A runtime that doesn't answer](/reference/configuration/sandbox/sandbox-yaml#a-runtime-that-doesnt-answer).
- SELinux enforces and [sandbox.yaml](/reference/configuration/sandbox/sandbox-yaml#selinux) doesn't say how to get past it. Set `selinux` there.
- `ca_bundle` can't be used. Fix the path, which must be an absolute path to a PEM file, or unset it. See [CA certificates](/reference/configuration/sandbox/sandbox-yaml#ca-certificates).
- the sandbox sets a [limit](/reference/configuration/sandbox/resource-limits#when-a-limit-cant-be-enforced) the runtime can't enforce. Remove the limit or change it.
- the sandbox image isn't pulled. Run the `pull` command the row names, such as `docker pull <image>`.
- with a `network:` policy, the egress relay image isn't pulled. Run the `pull` command the row names.
- with a `network:` policy, the channel to the relay can't be reached. See [It fails closed](/reference/configuration/sandbox/network-policy#it-fails-closed).

For a repository whose sandbox is a [Kit](/reference/configuration/sandbox/kits), doctor fetches and lowers the Kit first. The `sandbox` row fails naming the Kit and why when it can't, and otherwise it and the egress, proxy and credentials rows check the sandbox the Kit lowers to. Doctor fetches each Kit it hasn't cached; under Podman a single-manifest Kit is pulled, which can take up to 10 minutes per repository the first time.

### Allowed hosts rows

For the `allowed_hosts: '...' is not a host name or IP address` row: replace the entry with the exact name each device uses, such as `mybox.tailnet-name.ts.net`, in `access.yaml` or on the Access screen. While the server is bound to loopback the list isn't read, so the row is only a warning there.

For the `bound to ... with no allowed_hosts` row: add each exact name the devices use on the Access screen (from this machine, at `http://127.0.0.1:PORT`), or to `allowed_hosts` in `access.yaml`. After an upgrade from 1.4, a board that opened on another device can stop opening: see [Network access](/reference/changes-from-1-4#network-access).
