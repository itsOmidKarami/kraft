## What changed

Ten tasks, one mechanism, applied twice, plus two independent fixes:

- **Kraft-ko7j** (rejecting `human_review_approval` discarded the note and
  routed nowhere) — Tasks 1–3, 9–10. Chain nodes now declare a
  `reject_route` target (`templates.py`, `default.yaml`). Every gate
  rejection routes there and the routing is recorded (`api.py`,
  `store.py`). The rejection note outlives the launch that wrote it and
  `retry` clears the reject-loop counter (`store.py`). Task 9 stops the
  `Gate.tsx` UI from promising a stop it can't deliver; Task 10 threads the
  note's route through CLI (`cli.py`), client (`client.py`), and MCP
  (`mcp.py`).
- **Kraft-bol** (a plan gate could only be rejected, not edited) — Task 4.
  A steered re-run over a plan the chain already wrote is now treated as a
  revision (`executor.py`, `skills/plan/SKILL.md`) rather than a fresh
  plan from scratch, reusing the same reject-route mechanism ko7j
  introduced instead of a second one.
- **Kraft-xron** (merge failed on an already-merged MR) — Tasks 5–6.
  `forge.py` gained `find_mr` and both `open_mr` and `merge` ask the forge
  about the MR's state before acting, so a MR merged out-of-band (e.g. by
  auto-merge/MWPS) is treated as done instead of failing the node.
- **Kraft-nhps** (branch named by work-item UUID, unreadable on main) —
  Tasks 7–8. Branch name is computed once at intake from the work item's
  title, slugified and suffixed with a short id (`db.py`, `store.py`), and
  every consumer — worktree creation, forge, abandon — reads that one
  stored value (`api.py`, `builtins.py`, `executor.py`) instead of
  rebuilding it from the UUID.

One branch, one MR, as instructed. A test accompanies every bead's change

`test_executor.py`, `test_builtins.py`, `test_db.py`, `test_api.py`,
