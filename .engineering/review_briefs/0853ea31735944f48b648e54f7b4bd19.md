## What changed

`create_session` in `src/kraft/store.py` inserted `attempt` as the literal `1`
on every row. Now the INSERT computes it as `COUNT(*) + 1` over existing rows
for the same `(work_item_id, node_id, hook_point)`, scoped by Kraft's single
serialized write connection so there's no race. The computed value is then
read back and included in the `worker_session_created` event payload (it was
previously missing there), and also added to the `session_running` event's
row select/payload. `frontend/src/store.ts` now carries `attempt` through on
both the pending-row and running-row event handlers (`p.attempt ?? 1`).

A schema migration (`SCHEMA_VERSION` 13 → 14, `src/kraft/db.py`) backfills
existing rows: for each `(work_item_id, node_id, hook_point)` group it numbers
rows 1..N in `(created_at, id)` order — the tuple comparison is there
specifically so two sessions sharing a timestamp don't collide.

Tests: `tests/test_db.py` (migration/backfill correctness), `tests/test_store.py`
(attempt increments across sessions, event payload includes it),
`frontend/src/store.test.ts` (attempt threaded through both event handlers).

## What was deliberately left out

- No fix for historical event rows already persisted with `attempt` missing
  from their JSON payload (or with the old literal `1`) — the DB backfill
  migration corrects `worker_sessions.attempt`, but past `worker_session_created`
  / `session_running` event payloads in the event log are not rewritten. Only
  new events carry the correct value. This wasn't in scope per the ticket
  (which named the table column), but is worth a callout since dashboards
  reading historical events for `attempt` will still see stale/absent values.

## Unsure about
