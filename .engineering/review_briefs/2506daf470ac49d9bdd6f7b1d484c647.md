## What changed

All four beads (bxj8, ejj9, 79x3, 8mi8) land in one commit on `src/kraft/adapters/forge.py`, `tests/test_forge.py`, `tests/test_forge_git.py`:

- **Kraft-bxj8**: `ci_poll` and `merge` now call `forge.push(repo=repo, branch=branch)` before polling/merging. Previously the worker left commits local (it's told not to push, `adapters/agent.py:45`), so `ci_poll` kept re-polling the previous head's pipeline forever, and `merge` could hit `_assert_pushed`'s refusal. `push` is a no-op when already up to date, so this costs one extra `git push -u` call on the happy path.
- **Kraft-ejj9**: `CIStatus` now carries the forge's own `mergeable` field (GitLab `merge_status`/`detailed_merge_status` via `mr view -F json`, GitHub `mergeable`/`mergeStateStatus`). `ci_poll` fails the node when `mergeable is False` even if the pipeline is green — `is False` specifically, so an undecided (`None`) state doesn't block the gate. States that need a human (approvals, etc.) stay the gate's business, not this node's.
- **Kraft-79x3**: `merge` no longer trusts the CLI's exit code. After calling `forge.merge`, it polls the forge (`_poll_merged`) until the MR reads `merged`, and fails the node with the actual state (`open`, `closed`, `gone`) if it doesn't land within `merge_timeout`. Also folds in the existing "already merged" idempotency check (Kraft-xron) so a retry after a first successful merge is a no-op rather than an error.
- **Kraft-8mi8**: `tests/test_forge_git.py` adds real-git (no mocked subprocess) coverage for `_assert_clean` (dirty worktree, gitignored-only worktree) and `_assert_pushed` (unpushed head refused, pushed head accepted) — previously these two guards were only exercised against `FakeForge`.

Nothing exercises `open_mr → ci_poll → merge` end-to-end against a live GitLab/GitHub API.

## Unsure about

- Whether `merge_timeout`'s default is long enough for a merge-train or auto-merge-on-green setup, where "accepted into train" (Kraft-ejj9's own note) can sit `open` for a while before landing — the poll now handles this correctly (fails with "still open" rather than reporting a false completion), but a slow train could make `merge` fail a node that would have succeeded given more time. That's a tuning question, not a correctness one.
