## What changed

Implements Kraft-zr3s per spec/plan (`docs/superpowers/specs/2026-09-10-auto-escalate-gates-design.md`, `.../plans/2026-09-10-auto-escalate-gates.md`), in 7 commits:

- **`templates.py`**: `auto_escalate: true` on a chain node, validated to require a bool and a `gate_after`. `materialize()` carries it through.
- **`db.py`/`store.py`/`api.py`/`client.py`/`cli.py`**: new `work_items.auto_gate` column (migration 20, default 0), `kraft item create --auto-gate`. Deliberately **not** added to the MCP `create_work_item` tool — an agent can't arm its own item.
- **`executor.py`**: moved `_pending_gate`/`_gate_node_index`/`_gate_artifact`/`_reject_target` out of `api.py` into public `executor` functions (`ValueError` instead of `HTTPException`, since executor can't import FastAPI), plus new `apply_rejection()` used by both the human reject endpoint and the new agent path — so an agent rejection and a human rejection can't drift apart. `store.approve_gate`/`reject_gate` gain `by: "human"|"agent"` in their event payloads.
- **`adapters/subprocess.py`**: `read_verdict()`, deliberately outside `read_result_fields` (a verdict is read once in-process, never persisted to the DB — that asymmetry is what makes the crash path safe).
- **`gate_review.py`** (new) + packaged `gate-review` skill: dispatches the review as a **worker** (`identify_as_worker=True`), so `client._forbid_self_action` blocks it from approving/rejecting its own item — that's the entire enforcement mechanism, not a prompt convention. No `--resume`; fresh judgement each time. Collapses everything ambiguous (bad/missing verdict, `status: failed`/`needs_context`, empty-reason reject) to `undecided`.
- **`executor.py`** `_review_gates`: `run`/`resume` split into `_run_once`/`_resume_once` plus an outer loop that fires only when both `auto_gate` (item) AND `auto_escalate` (node) are set. Re-reads the pending gate after the agent returns and discards a stale verdict if a human already acted. `approve` advances past the gate; `reject`/`fixed` go through `apply_rejection` (bounded by the existing `<gate>_reject_loop` counter, so a `fixed`-approve loop can't run forever); `undecided` leaves the gate pending. Budget checked before dispatch (`gate_auto_review_skipped` if exhausted).
- Docs: `CLAUDE.md`/`AGENTS.md` CLI reference updated with `--auto-gate`.

## What was deliberately left out (by design, not by omission)

- **No gate ships `auto_escalate: true`.** `templates/default.yaml` is untouched. This feature is inert until a human edits a template *and* creates an item with `--auto-gate`. Confirmed via `git diff` — default.yaml has no changes in this branch.
- **No UI checkbox** for `--auto-gate` — CLI-only for now.
- **No per-gate skill override** — one `gate-review` skill serves every gate type, discriminated by prompt text only.
- Three follow-up beads filed as the plan specifies: Kraft-zr3s.1 (UI checkbox), Kraft-zr3s.2 (decide which gates ship `auto_escalate` in default.yaml — `human_review_approval` flagged as the hard case since approving it walks straight through `mr_sync` into `merge`), Kraft-zr3s.3 (surface gate-review concerns in `kraft view show`).
