## What changed

Two commits on this branch, `7960422` (the feature) and `52279f9` (a follow-up
fix for a rebase collision found while landing it).

- **`src/kraft/templates.py`** (Kraft-unk): extracted `validate_nodes(nodes,
  registry)` out of `load_templates` — shape check, `gate_after` membership in
  `GATE_NAMES`, `fix_loop`-needs-tasks, hook-set membership. `load_templates`
  now calls it for whole-template validation; error message text is unchanged
  so nothing downstream that parses those strings breaks. Confirmed by
  `tests/test_templates.py` still passing unchanged plus new direct tests of
  `validate_nodes`.
- **`src/kraft/api.py`** (Kraft-hm0): `templates/registry.yaml` rebinds
  `on.chain.review_ready` to the `chain-review` agent skill (was
  `builtin:noop`). New `_splice_chain_review()` reads the `chain_review`
  artifact on `chain_finalized` gate approval, parses its `{status,
  revised_chain_nodes, rationale}` envelope, runs `revised_chain_nodes`
  through `validate_nodes`, and on success replaces
  `chain_definition["nodes"]` from the node after `chain_finalized` onward.
  Any failure (missing artifact, unparseable envelope, `status: "error"`,
  invalid node list) routes to `needs_human` with a reason instead of
  advancing or splicing.
- **`src/kraft/api.py` / `store.py` / `executor.py` / `db.py`** (Kraft-cd47):
  `chain_template` on `NewWorkItem` defaults to `None`, not the string
  `"default"`; resolved to the `default` template only at lookup time.
  Migration 15 (renumbered to 16 in the fix commit, see below) drops the
  column's `NOT NULL` constraint so `None` can actually be stored and stays
  distinguishable from an item that named `chain_template: "default"`
  explicitly.
- **Kraft-ouo**: decision recorded, no source change — filed Kraft-ruik as the
  follow-up build for a seeded-templates-directory upgrade path.
- **`52279f9`**: while landing this, migration key 15 collided with another
  branch's `implements_beads` migration (same key, different line, so git's
  merge didn't flag it — a dict literal silently drops one migration on key
  collision). Renumbered this branch's migration to 16, carried
  `implements_beads` forward through its rebuild, and added an import-time
  `assert` that `_MIGRATIONS` keys stay contiguous, plus a regression test.

## What was deliberately left out (matches the plan, not a gap found late)

- The splice path (`_splice_chain_review`) validates a revised tail with only
  `validate_nodes`'s four rules (shape, `gate_after`, `fix_loop`-needs-tasks,
  hook membership) — it does **not** re-run `load_templates`'s other
  whole-template checks (`fix_loop` string-shape, `on_failure` list-shape, the
  "not both `fix_loop` and `on_failure`" rule, `reject_to` target validity).
  This is what the plan (step 1/3) specified as the splice tier's scope;
  Kraft-unk's own description names the same four rules. I did not go back
  and widen it — flagging it here rather than silently, since a future
  `revised_chain_nodes` payload could still slip through with a malformed
  `on_failure` or a `reject_to` pointing at a node that no longer exists in
  the spliced tail.
- Kraft-ouo is decision-only by design (plan step 5); Kraft-ruik carries the
  actual build.

## What I'm unsure about

- I did not manually drive a chain_review revision end-to-end through a real
  fake-claude-backed run (the plan's verification step 3's last bullet); I
  relied on the existing `tests/test_api.py` splice tests (added tail runs,
  unchanged tail round-trips, error/missing-artifact stop at needs_human,
  invalid tail rejected) instead. Same behavior, but not the same as watching
  it happen live.
- `reject_to` validity for a spliced tail: a node the revised tail's
  `reject_to` points at could reference something outside the new tail (e.g.
  a node from the discarded old tail, or nothing at all). `validate_nodes`
  doesn't check this, and neither does the splice path. No test exercises
  that specific edge case, so I don't know today whether it produces a clean
  error later or an obscure one at chain-execution time.
