## What changed

- `src/kraft/builtins.py`: new `_pin_identity(repo, worktree, work_item_id)`,
  called from `ensure_worktree` right after `git worktree add` succeeds.
  Reads `user.name`/`user.email` off `repo`'s config chain and writes them
  into the new worktree's own config, then repeats the write into every
  submodule's separate gitdir (via `git submodule foreach --recursive`,
  since a submodule's gitdir under `.git/worktrees/<id>/modules/...` doesn't
  inherit the worktree's config). If either key is unresolved, raises
  `RuntimeError` naming the missing key instead of letting the worktree
  silently exist with no identity.
- `_commit_paths`'s docstring updated to point at `_pin_identity` instead of
  the old (now-inaccurate) claim that the worktree just inherits the repo's
  config.
- `src/kraft/executor.py`: comment in `_dispatch` trimmed — `unset
  user.email` dropped from the list of failure modes the git-add sweep must
  tolerate, since that path is now foreclosed before any node runs.
- `tests/test_builtins.py`: new test,
  `test_ensure_worktree_raises_when_the_repo_has_no_commit_identity` — unsets
  `user.email` on a fixture repo and asserts `ensure_worktree` raises
  `RuntimeError` matching `user.email`, rather than succeeding and letting
  the failure surface later at commit time.
- `tests/conftest.py`: unrelated to the identity fix itself — a fix-cycle
  correction from the prior verify pass. The new test (and others not
  opting into the `app` ASGI fixture) fell through `client.base_url()` to a
  real HTTP call on the default port 8765; on a machine already running
  `kraft` for real that returned a live 401 instead of the expected
  `ConnectError`, making the suite flaky depending on what else was running
  locally. `_isolated_kraft_home` now binds an ephemeral port and sets
  `KRAFT_PORT` to it before each test.

## What was deliberately left out

- No general "does `repo` have a usable git identity" pre-flight outside
  `ensure_worktree` — the spec scopes the fix to worktree creation, not to
  validating the parent repo config at any other entry point.
- No attempt to auto-fill a fallback identity (e.g. a `kraft-bot@` default)
  when the repo has none — the spec's design is to fail loudly and name the
  missing key, not paper over it with an invented identity, which is exactly
  the failure mode this bead exists to close off.

## What I'm unsure about

- `_pin_identity` swallows the exit status of both `git config` writes via
  `subprocess.run(..., capture_output=True)` with no return-code check. If a
  write to a submodule's gitdir silently failed (permissions, detached
  gitdir, etc.) that submodule would still lack identity and the failure
  would only surface later as a commit error inside it — the same
  "surfaces late" shape this bead was filed to close, just narrowed to the
  submodule case. Not raised as a blocking finding since submodules aren't
  this repo's normal case and the spec didn't call out submodule-write
  failure handling, but worth a human's eyes.
