# Escalate to Kraft-Agent — implementation

Followed `docs/superpowers/plans/2026-09-10-escalate-to-kraft-agent.md` task by task (TDD, one commit per task):

1. **DB**: `work_items.escalation_session_id` column (migration 18, `SCHEMA_VERSION` 19) + `store.set_escalation_session`.
2. **`run_agent_task`**: three new keyword-only params — `resume_session_id`, `autocompact`, `identify_as_worker` (default `True`, unchanged behavior for every existing caller). `Profile` gained `resume`/`autocompact` flag tuples, `claude` profile wired to `--resume`/`--autocompact`.
3. **`src/kraft/escalate.py`**: new module, `dispatch()` — one escalation turn through `_agent.run_agent_task`, `identify_as_worker=False` so the launch resolves as a human session (the self-resume trick), `--resume`s the prior CLI session id if one is stored, extracts the CLI's own session id off the `system`/`init` stream-json line afterward and persists it.
4. **API**: `POST /work-items/{wid}/escalate` — 409 if not `needs_human` or a turn is already pending/running, 400 on empty message, otherwise spawns `escalate.dispatch` via the existing `_spawn`/`_guard` machinery.
5. **`client.escalate`**: thin wrapper via `_forbid_self_action` + `_act`, same shape as `client.retry`.
6. **CLI + MCP**: `kraft item escalate <id> --message "..."` and MCP tool `escalate_work_item`.

One deviation from the plan's test snippet: `test_no_resume_session_id_omits_resume_and_autocompact_flags` used a manual `_subprocess.run_task = ...` / `del` instead of `monkeypatch` — this permanently deleted the real attribute from the module for the rest of the test session (order-dependent breakage), which is exactly what the plan's own comment warned about. Rewrote it to use `monkeypatch.setattr`/`_capture_cmd` like every sibling test, dropping the manual variant.
