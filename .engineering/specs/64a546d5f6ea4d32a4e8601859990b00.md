# Attachments an agent can actually hand over

The design below was agreed with the user this session; this spec confirms it
against the code and settles the two details the trace turned up (where the
copy reads from, and how the commit runs). Beads: Kraft-82gz, Kraft-85wk,
Kraft-8iw6, Kraft-vwv, Kraft-xwen. One branch, one MR.

## The problem

`POST /work-items` already takes `attachments: list[Attachment]`
(`api.py:461`, `NewWorkItem.attachments`), stores them (`store.create`),
trims the gates they satisfy (`templates.materialize` +
`executor.ATTACHMENT_GATES`), names them in the agent prompt
(`executor._attachment_note`) and copies them into the fresh worktree
(`builtins._copy_attachments`). Only the browser (`IntakeModal.tsx:115`) can
reach it. Four gaps:

1. **Kraft-82gz — no door.** `client.create_work_item` (`client.py:474`)
   posts `title/repo/chain_template/autostart/description` and nothing else.
   `kraft item create` (`cli.py:644`) and the MCP `create_work_item` tool
   (`mcp.py:50`) both go through it, so neither can attach.

2. **Kraft-85wk — the wrong root.** `_validated_attachments` (`api.py:485`)
   resolves every path under `Path(repo).resolve()` — the registered main
   checkout. An agent that just wrote `.engineering/specs/x.md` in a Kraft
   worktree (or any other worktree of the same repo) fails `target.is_file()`
   and gets `422 attachment not found`. That is the exact handoff the feature
   exists for.

3. **Kraft-8iw6 — the copy is never committed.** `_copy_attachments`
   `shutil.copyfile`s the document into the new worktree and stops. When the
   attachment trims the spec/plan gates, no doc node ever runs, so nothing
   commits it. It is still untracked when `forge._assert_clean`
   (`adapters/forge.py:174`) runs ahead of `open_mr`, and the node fails with
   "1 uncommitted path(s) in the worktree".

4. **Kraft-vwv — undecided.** A cross-repo item has submodule worktrees; no
   one has said which tree an attachment belongs to.

Kraft-xwen wants doc nodes to stop shelling out to `git commit`; the commit
primitive #3 needs is that same primitive.

Order: 85wk first. Opening the CLI and MCP doors onto a validator that still
rejects worktree paths ships the bug to two more callers.

## The approach

### Kraft-85wk: a second, proven root

`NewWorkItem` gains `cwd: str | None = None`. `client.create_work_item` fills
it with `str(Path.cwd())`, but only when it is sending attachments — no cwd
on a call that has no path to resolve.

`_validated_attachments(repo, attachments, cwd)` builds a candidate root
list:

- `Path(repo).resolve()` — always, first, unchanged.
- the toplevel of `cwd` (`git -C cwd rev-parse --show-toplevel`), appended
  only when `git -C cwd rev-parse --git-common-dir`, resolved against `cwd`,
  equals the same value computed for `repo`. Same `.git`, or no second root.

Both git calls go through `config.git_read`, which never raises and returns
None on failure, so an unreadable or non-git `cwd` degrades to today's
single-root behaviour rather than 500ing.

A path is accepted at the first candidate root it both stays inside
(`is_relative_to`, unchanged escape check) and exists under. The stored dict
stays `{"kind", "path"}` with `path` relative to *that* root — for a worktree
of the same repo that is the same repo-relative document path, which is what
the prompt note, the UI badge and `index/service._attachment_docs` all read.

**The one extra field.** When the file was found under the cwd root rather
than under `repo`, the entry also carries `"source": <absolute path>`, and
`_copy_attachments` copies from `attachment.get("source")` when present
instead of `repo / path`. Without this the validator would accept the path
and the copy would then silently find nothing at `repo / path` (its
`src.is_file()` guard skips), leaving a trimmed spec gate and no spec — a
worse failure than the 422 it replaces. `source` is absent for every browser
call, so nothing else changes shape.

The trust boundary is deliberately unmoved for the browser: with no `cwd`,
the reachable set is exactly `repo`, as Kraft-7izl set it. `cwd` widens it
only to other working trees of the same repository, and the origin check in
the perimeter middleware (`api.py:450`) already refuses cross-site POSTs, so
the widened set is reachable only by a caller that is already local and
trusted. A `cwd` pointing at an unrelated repo, a submodule of this repo (its
`--git-common-dir` differs), or a non-repo directory adds no root.

**Rejected:** (a) resolving under `cwd` with no same-repo proof — turns
`cwd` into "read any file on this machine"; (b) dropping the root check for
CLI/MCP by having the client read the file and POST its bytes — a new API
surface and a second storage question, for a local caller that can already
name the file; (c) making the client rewrite worktree paths to main-checkout
paths — the file genuinely is not in the main checkout.

### Kraft-82gz: the two doors

- `client.create_work_item(..., attachments: list[dict] | None = None)`
  threads `attachments` and `cwd` into the existing POST body. No new
  endpoint.
- `kraft item create` gains `--spec PATH` and `--plan PATH`; `_cmd_create`
  turns whichever were given into `[{"kind": "spec", "path": PATH}, ...]`.
  The path is passed as typed (relative to the shell's cwd, or absolute) —
  the server resolves it against the candidate roots, and an absolute path
  under either root already works, because `root / <absolute>` is that
  absolute path.
- MCP `create_work_item` gains `attachments: list[dict] | None = None`,
  documented as `[{"kind": "spec"|"plan", "path": "..."}]`, passed straight
  through. Same shape as the API rather than a second `spec=`/`plan=`
  spelling, so there is one vocabulary to learn.

`--spec`/`--plan` rather than a repeatable `--attach kind=path`: there are
exactly two kinds, the server already refuses a duplicate kind, and two flags
document themselves in `--help`.

### Kraft-8iw6 + Kraft-xwen: `_commit_paths`

New in `builtins.py`:

```python
def _commit_paths(worktree: Path, paths: list[str], message: str) -> None
```

`git add -- <paths>` then `git commit -m <message>`, both `subprocess.run` in
`worktree`, both no-ops when there is nothing staged (an ignored or unchanged
path stages nothing; the commit is skipped rather than allowed to fail).
Failures log a warning and return — a document that failed to commit is a
dirty-tree failure at `open_mr` with git's own message in the log, which is
strictly better than crashing worktree creation.

Two decisions the trace forces:

- **`--no-verify`.** `_copy_attachments` runs before the `uv sync` at the end
  of `ensure_worktree`, so the repo's `pre-commit` hook cannot spawn yet
  (Kraft-i047 is the same failure from the other side). Kraft is committing a
  file it copied itself, unmodified, so there is nothing for the hook to
  catch.
- **Identity.** No `-c user.email` override: the worktree inherits the repo's
  git config, which is where every other commit on this branch gets its
  author from.

`_copy_attachments` collects the destinations it actually wrote and calls
`_commit_paths(worktree, written, "chore: attach <kinds> for <id>")` once
after the loop — one commit, not one per attachment, and no commit at all
when every copy was skipped.

Kraft-xwen's remaining half — rewriting the doc-node prompt
(`adapters/agent.py:44`) and the node templates so agents stop running
`git add`/`git commit` themselves — is **out of scope here** by explicit
agreement: build the primitive, prove it with 8iw6's test, then move the
callers in a follow-up.

### Kraft-vwv: the decision

**An intake attachment belongs to the item's root worktree only.** Submodule
worktrees do not get a copy. The stored path is relative to the registered
repo (or, via 85wk, to a working tree of that same repo, which is the same
repo-relative path), and `ensure_worktree` copies into the root worktree
only. A `cwd` inside a submodule contributes no root, because its
`--git-common-dir` is the submodule's, not the superproject's — so the rule
is enforced, not merely documented. A spec is one document about one change;
duplicating it into every submodule tree would put N copies in the MR and
leave N places for it to drift. This is a recorded decision, not a scope cut:
if a submodule-local spec is ever wanted, it is new work with its own bead.

## Out of scope

- Rewriting doc-node templates/prompts to call `_commit_paths` (Kraft-xwen's
  second half) — follow-up.
- Any new attachment kind beyond `spec`/`plan`.
- Attaching to an existing work item; attachments stay an intake-time input.
- Indexing an attachment that only exists on the Kraft branch — `scan_repo`
  still lists via `git ls-files` in the main checkout, unchanged.
- The browser's path resolution and the IntakeModal UI.

## Verification

One test per bead, all in the existing suite:

- `tests/test_api.py::test_intake_accepts_an_attachment_from_another_worktree_of_the_repo`
  — file written only in a linked worktree, `cwd` set to it; 201, and the
  stored attachment carries the repo-relative path.
- `tests/test_api.py::test_intake_without_a_cwd_still_scopes_attachments_to_the_repo`
  — same file, no `cwd`; still 422. The browser boundary is unmoved.
- `tests/test_api.py::test_intake_ignores_a_cwd_in_a_different_repo` — `cwd`
  is an unrelated git repo holding the named file; 422.
- `tests/test_cli_verbs.py::test_create_attaches_a_spec_from_the_flag` — CLI
  round-trip: `kraft item create --spec ...` produces an item whose
  `attachments` name it.
- `tests/test_cli_verbs.py::test_create_through_the_mcp_door_attaches` — the
  MCP tool, same round-trip.
- `tests/test_builtins.py::test_an_attached_document_is_committed_in_the_worktree`
  — after `ensure_worktree`, `git status --porcelain` in the worktree is
  empty and the file is in `HEAD`.
- `tests/test_builtins.py::test_commit_paths_stages_and_commits_only_the_named_paths`
  — the helper alone: named path committed, an unrelated dirty file left
  alone, and a second call with nothing to stage is a no-op rather than a
  failure (Kraft-xwen).
- `tests/test_forge_git.py::test_open_mr_accepts_a_worktree_whose_attachment_was_copied_in`
  — the 8iw6 symptom against real git: `_assert_clean` passes and `glab` is
  reached.

Kraft-vwv gets no test: it is a decision about behaviour that already exists,
and the submodule half is enforced by the `--git-common-dir` check that
85wk's third test covers.

`just test tests/test_api.py tests/test_cli_verbs.py tests/test_builtins.py
tests/test_forge_git.py tests/test_client_write.py tests/test_mcp.py` is the
targeted run; `just lint` for format.
