## 1 — Kraft-97e: `probe_repo` connects a worktree as its own repo

**Problem.** `config.probe_repo` (`src/kraft/config.py:202`) takes the repo root
from `git rev-parse --show-toplevel`, which inside a linked worktree returns the
worktree, not the checkout it belongs to. Every door — `POST /repos/probe`,
`POST /repos`, the `ensure_repo` MCP tool, `kraft connect` — routes through it,
so an agent following `/kraft:handoff` (agents run in worktrees, and the skill
says to call `ensure_repo()` every time) registers its own worktree as a repo.
Observed live: `bridge-cse_013CvRHKKKBZQwhRNz7oCwBd` sits in `repos.yaml`
alongside Kraft.

**Approach.** Resolve the main checkout from the common git dir, in `probe_repo`
only:

```python
common = git_read(
    p, "rev-parse", "--path-format=absolute", "--git-common-dir", expected_failure=True
)
root = Path(common).parent if common and Path(common).name == ".git" else Path(toplevel)
```

In an ordinary checkout `--git-common-dir` is `<repo>/.git`, whose parent is the
toplevel — so there is no worktree special case and the existing probe tests
must pass unchanged. That is the point of the shape.

**Deviation from the bead, deliberate.** The bead's snippet is
`Path(common).parent if common else Path(toplevel)`. Taken literally it breaks
submodules: verified by hand, inside `super/libs/sub` git reports
`toplevel=…/super/libs/sub` but `common=…/super/.git/modules/libs/sub`, so
`.parent` would register `…/super/.git/modules` as the repo. The
`Path(common).name == ".git"` guard keeps a submodule (and any checkout whose
git dir is relocated by `GIT_DIR` or a `.git` file) on today's behaviour, which
is the bead's stated floor: "keep the fallback so probe never gets worse than
today".

Rejected: patching the four callers (the bead names this and rejects it — four
copies of one rule); rejecting a worktree path with an error instead of
resolving it (the caller is an agent that cannot do anything with the refusal —
its cwd *is* a worktree); teaching `POST /repos` to de-duplicate afterwards
(fixes the symptom in one door, leaves `probe` lying to the Settings screen).

**Tests** (`tests/test_settings_api.py`, beside the other probe tests):
- `test_probe_from_a_worktree_reports_the_main_checkout` — `make_repo`, then
  `git worktree add`, then `probe_repo(worktree)["path"] == str(repo.resolve())`.
- `test_probe_of_a_submodule_stays_the_submodule` — pins the guard above.

## 2 — Kraft-sws6: `kraft disconnect`

**Problem.** `DELETE /repos?path=…` exists and works
(`src/kraft/api.py:1781`: drops the entry from `repos.yaml`, then
`indexer.purge_repo`). The CLI exposes only `connect`, so undoing a wrong
connect — the exact thing §1 caused — needs raw `curl` and a hand-dug bearer
token.

**Approach.** `client.disconnect_repo(path)` plus a `disconnect` verb beside
`connect` in `cli.py`, `PATH` defaulting to cwd. No server change.

The client needs a `_delete` alongside `_get`/`_post` (four lines, same
`_send` and same `kraft {status}: {detail}` error string), because the route
answers 204 with no body and 404 on an unknown path — the 404 must read as a
sentence, like every other verb.

**One decision the bead did not foresee.** After §1, `POST /repos` stores the
main checkout, so `kraft disconnect` run from inside a worktree of a connected
repo would send the worktree path and 404 — `api._connected` matches the raw
path or its `resolve()`, and knows nothing about worktrees. `disconnect_repo`
therefore resolves through `POST /repos/probe` first and deletes the path the
probe returns, falling back to the path as given if the probe fails (not a git
directory, say). This is the pattern `ensure_repo` already uses for its 409
branch, it keeps the fix in one place, and it keeps `connect` and `disconnect`
symmetric: both are "the repo I am standing in".

Rejected: teaching `api._connected` the same resolution (correct for every door,
but it is a server change the bead ruled out, and no other door is reached with
a worktree path); sending the raw cwd and living with the 404 (leaves the
common case — an agent in a worktree — broken).

No confirmation prompt: disconnecting touches no repo file and no work item (the
API comment notes a repo with work items is simply re-ingested by the next
rescan).

**Tests** (`tests/test_cli_repos.py`):
- `test_disconnect_removes_the_connected_repo` — connect, `cli.main(["disconnect",
  path])`, `client.repos() == []`.
- `test_disconnect_of_an_unconnected_path_is_a_readable_404` — the message, not a
  traceback.

## 3 — Kraft-5lpl: `kraft retry`

**Problem.** `POST /work-items/{id}/retry` is the only door back onto a
`needs_human` stop (`resume` wants `paused`, `pause` wants `running`,
approve/reject want a pending gate). It has no CLI verb, so an operator in a
terminal reaches for `curl`.

**Approach.** `client.retry(steer=None, work_item_id=None)` — `_forbid_self_action`
then `_act(f"/work-items/{target}/retry", payload)`, byte-for-byte the shape of
`client.resume` — a `kraft retry [ID] [--steer TEXT]` verb beside `resume`, and
an MCP `retry_work_item` tool beside `resume_work_item` (the bead asks for it:
an agent that handed work off hits the same wall). `_forbid_self_action` rather
than `_target`, because retry restarts the node that is running you.

No server change.

**Tests:**
- `tests/test_client_act.py::test_retry_on_an_item_that_is_not_stopped_is_a_readable_409`
  — a 409 proves the route resolved; a wrong URL gives 404.
- `tests/test_cli_verbs.py::test_retry_passes_the_id_and_steer_through` — the
  dispatch table, which is what that file tests.

## 4 — Kraft-owea: `events -f` reprints the header per event

**Problem.** `_cmd_events`'s follow loop calls `emit([ev], render.event_line, …)`
once per streamed event, and `render.table` (`src/kraft/render.py:86`) always
prepends its header row, so a human sees `SEQ WHEN TYPE DETAIL` above every
single line.

**Approach.** `table(rows, columns, width=None, headers=True)` and
`event_line(rows, headers=True)`, both passing through; the follow loop renders
with `headers=False`. This is the bead's preferred option ("smaller change, and
useful to the next streaming verb").

**Accepted limitation, stated because a reviewer will notice it.** `table`
computes column widths from the rows it is given, so a streamed row's columns
are not guaranteed to line up with the backlog table above it — each column is
still at least as wide as its header, so the drift is bounded to the `TYPE`
column. Fixing it properly means carrying the backlog's widths into the stream,
which is a parameter and a state variable for cosmetics on a live tail. Not
doing it.

**Test** (`tests/test_render_widths.py`): `test_a_headerless_table_is_the_row_alone`
— `table(rows, cols, headers=False)` has one line and no `SEQ`. Plus, in
`tests/test_cli_watching.py`, the existing follow test gains
`assert out.count("SEQ") == 1`, which is the bug as a human meets it.

## 5 — Kraft-tom2: `events -f --json` emits arrays, not NDJSON

**Problem.** The same `emit([ev], …)` call does `json.dumps(value, indent=2)` on
a *list*, so a followed stream is a sequence of pretty-printed JSON arrays.
`kraft logs -f --json` is NDJSON and CLAUDE.md documents that contract; anything
line-oriented (`read -r`, `split("\n")`, a log shipper) breaks on the difference.

**Approach.** A `_print_event(event, as_json)` beside `_print_log`, used by the
follow loop only:

```python
print(json.dumps(event) if as_json else render.event_line([event], headers=False), flush=True)
```

One compact object per line, and `flush=True` — a followed stream through a pipe
is block-buffered otherwise, which `_print_log` already knew and `emit` does
not. This carries §4 as well; the two beads are one three-line function.

The one-shot backlog keeps `emit` and stays a single indented array: it is a
finite read, and the bead explicitly leaves it alone.

**Test** (`tests/test_cli_watching.py`):
`test_events_follow_json_is_one_object_per_line` — every line after the backlog
parses as an object with `json.loads`.

## 6 — Kraft-t5s9: `cli.py` calls `client._target`

**Problem.** `_cmd_events` needs the resolved work item id twice (once for the
events call, once to filter the instance-wide bus by `work_item_id`), so it
reaches into `client._target`. Every other caller of `_target` is inside
`client.py`, which owns "what a missing id means"; `cli.py` is the module the
design says must never become a second definition of a work item.

**Approach.** Rename `_target` to `resolve_work_item` — eight call sites inside
`client.py`, one in `cli.py`. No alias: `cli.py` is the only outside caller.

Rejected: having `client.events()` return `(id, rows)` (changes a public
signature for one caller's convenience, and every other `_target` caller would
still be reaching for something private that stayed private).

**Test** (`tests/test_client_context.py`):
`test_resolve_work_item_returns_the_standing_item` — the promoted function under
its public name, explicit id and `KRAFT_WORK_ITEM_ID` alike.

**Residual, filed not fixed.** `_cmd_watch` also calls `client._get("/work-items")`
directly. Out of scope here (the bead is about `_target`), filed as Kraft-8okl
so it is not lost — closing it means a shape decision (a `client.board()`
returning items *and* the event cursor `_cmd_watch` needs), not a rename.

## 7 — Kraft-ldeq: BudgetCard hides retry on a loopless node

**Problem.** `BudgetCard.tsx:31` computes `canRetry = !!node?.fix_loop`, and the
comment above it (lines 17-23) justifies the gate with "`/retry` 409s without a
fix loop". Kraft-bzwi removed that 409 — `retry_work_item` now accepts any
`needs_human` node — so the reason is gone while the behaviour, and three tests,
remain.

**Decision: open the retry, delete the gate.** The bead offers both, so here is
the argument. A budget stop leaves the item `needs_human` on a node with no fix
loop; `resume` wants `paused`, `pause` wants `running`, approve/reject want a
gate. Retry is the only door — the same stranding Kraft-bzwi fixed for a task
failure, reached from the budget side. The "retrying re-breaches" worry is real
but is not a reason to hide the control: the operator who *has* raised the cap in
Settings → Policy has no other way back, and the card already carries the warning
("this stops again at the next agent task unless the cap is raised or cleared
first"). Keeping the gate would also mean the card keeps telling that operator
"raising the cap will not restart this item", which after Kraft-bzwi is simply
false.

So: drop `canRetry` and the `node` lookup, always render the button and the
re-breach hint, and always say "Raise or clear the cap in Settings → Policy, then
retry." The doc comment loses its two `/retry` 409 paragraphs and keeps the one
that matters — the cap refused to *start* the next task and did not interrupt a
running one.

**Tests** (`frontend/src/components/BudgetCard.test.tsx`): the three tests that
pin the removed branch (`offers no retry on a node with no fix loop…`, `does not
tell a no-retry node that raising the cap will restart it`, and the fix-loop half
of `tells a fix-loop node to raise the cap and then retry`) are replaced by
`offers retry on a node with no fix loop, and warns it will re-breach`. The
`fixLoop` parameter of the `item()` helper goes with them. `calls retryWorkItem
with the item id when retried` stays and now runs on a loopless node.

## 8 — Kraft-9rs: `/kraft:status` skill

**Problem.** After a handoff an agent has no cheap way to say where the work got
to, and no way to end the turn "watching it" — so a human asks for an update
later. `kraft show ID --json` cannot answer it either: `client.get_work_item`
trims the payload to nine keys and `chain_definition` is not one of them, so
nothing in the CLI's output says what node comes *next*.

**Approach, two parts.**

**(a) One derived field.** `client.get_work_item` computes `next_node_id` from
the untrimmed item's `chain_definition.nodes` (the node after
`current_node_id`, `None` at the end of the chain) and adds it to the trimmed
dict. One string, so the trim keeps doing its job — the whole point of that
trim is not spending an agent's context on the chain — and both doors (CLI and
MCP) get it, so the CLI stays a renderer and not a second definition.
`_render_show` is a `kv` over whatever keys are present, so the human output
follows for free.

Rejected: putting `chain_definition` back in the keep list (undoes a deliberate
trim to save the skill one jq expression); computing the next node in the skill
from a second `--json` call against a raw endpoint (needs the bearer token the
CLI exists to hide).

**(b) A fifth entry in `init.SKILLS`.** `SKILLS` is a dict of SKILL.md bodies
written by `kraft init` under a plugin manifest, which is what makes them
`/kraft:status`. The body says two things:

- The phase line:
  `kraft show ID --json | jq -r '"\(.status): \(.current_node_id) → next \(.next_node_id // "done")\(if .pending_gate then " · gate \(.pending_gate)" else "" end)"'`
- The follow: arm a Monitor on `kraft events ID -f`, unfiltered. Unfiltered is
  the point — `-f` already ends itself on `work_item_completed` /
  `work_item_abandoned`, so the monitor disarms on its own, and a `--type`
  filter would go silent through exactly the escalation the human needs to hear
  about. A chain emits tens of events, not thousands.

`kraft events -f` is what §4 and §5 make fit to be read a line at a time, which
is why this item is last in the branch.

**Tests:**
- `tests/test_client_read.py::test_get_work_item_names_the_next_node` — and that
  it is `None` on the last node.
- `tests/test_init.py::test_the_status_skill_carries_the_phase_line_and_a_bounded_follow`
  — the body names `next_node_id` and `kraft events` with `-f`. The existing
  `SKILL_NAMES` loops (installed, self-named, description long enough) pick the
  new skill up for free.
