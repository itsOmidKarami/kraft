# Stream the worker's output, stop hanging on SIGTERM, and grant permissions per node

Six beads, three independent parts.

- **Part 1 — Kraft-77z, Kraft-54dk, Kraft-2r8s.** One change:
  `--output-format json` → `--output-format stream-json --verbose`. Live log,
  live token counts, a real model name.
- **Part 2 — Kraft-9oab.** The server never exits on SIGTERM when a browser has
  the board open. Root cause found and reproduced.
- **Part 3 — Kraft-3tw then Kraft-oor.** Permission grants become per-node
  registry keys, and those keys become the policy Kraft answers the worker's
  permission prompts from.

Every claim of fact below was measured on this machine against
`claude 2.1.260`; the commands are named where it matters.

---

## Part 1 — the worker stops being a black box

### The problem, in this repo's terms

`adapters/agent.py:97` pins `output_json=("--output-format", "json")` for the
`claude` profile, and `run_agent_task` (line 316) puts it on every agent
command line. In that mode the CLI prints **one JSON object at exit and nothing
before it**. Verified on a real finished session:

```
$ wc -l -c ~/.kraft/run/logs/9de7fa99d7d34b29b95df246ff002dea.log
       1   28442
```

One line, 28 KB, written at the end. Three beads fall out of that single fact:

- **Kraft-77z** — the log file is 0 bytes for the whole node. `kraft view logs
  -f` streams nothing, the log modal is empty, and the only way to tell a
  working opus node from a wedged one is `ps -o time`. Nodes now run 6–10
  minutes (`effort: high`), so this is the normal experience.
- **Kraft-54dk** — usage is harvested once, in `subprocess.run_task:214`
  (`_usage.read` → `store.session_exited`). While a node is live its
  `worker_sessions` row holds NULL tokens, so `store.usage_rollup`'s `by_node`
  entry for `current_node_id` is 0 and `WorkItemDetail.tsx:45` renders
  `0 tokens this node`. By the time the row has numbers, `current_node_id` has
  moved on. The counter is never right, in either state.
- **Kraft-2r8s** — `usage.from_envelope:63` reads `envelope.get("model")`. The
  envelope has no such key. Measured on the same log:

  ```
  keys:        [... 'modelUsage', ... 'total_cost_usd', 'usage', 'uuid']
  modelUsage:  ['claude-opus-5']
  ```

  So `worker_sessions.model` is NULL on every row ever written.

### The approach

Switch the `claude` profile to `output_json=("--output-format", "stream-json",
"--verbose")` (`--verbose` is mandatory: without it the CLI exits 1 with
`Error: When using --print, --output-format=stream-json requires --verbose` —
measured). The CLI then writes NDJSON, one object per line, as it works. A real
run produced:

```
0-7   system/hook_started, system/hook_response
8     system/init      model=claude-haiku-4-5-20251001  permissionMode=default  tools=[...]
9-10  system/thinking_tokens
11-12 assistant        message.model, message.usage{input,output,cache_*}, request_id, timestamp
13    rate_limit_event
14    result           usage{...}  modelUsage{...}  total_cost_usd  permission_denials
```

That one change answers all three beads:

- 77z: the log fills as the worker works. The follow endpoint
  (`api.py:1392`, `format=jsonl&follow=true`) and `kraft view logs -f` already
  exist and already tail the file — they have simply had nothing to tail.
- 54dk: `assistant` lines carry per-request `message.usage`, so tokens are
  knowable mid-run.
- 2r8s: the `system/init` line carries `model` on **line 8**, before the first
  token is spent.

The final line is still `{"type":"result",...}`, so `agent._envelope_is_error`
and `usage.read_envelope` keep reading `lines[-1]` unchanged.

Rejected: **a heartbeat event** (77z option 1) — gives liveness but neither
usage nor a transcript, and leaves 54dk needing its own answer. Rejected:
**tail `~/.claude/projects/<slug>/<uuid>.jsonl`** (the comment on 77z) — Kraft
would have to glob a vendor-private directory by mtime because the agent's own
session uuid is not `KRAFT_SESSION_ID`, and it puts a Claude-Code-specific path
inside a vendor-neutral adapter. Rejected: **drop the "this node" clause from
the usage line** (54dk option 1) — deletes the question instead of answering it,
and 77z forces the same change anyway.

### What has to change with it

**`adapters/subprocess.py` — stdin.** In stream-json mode the CLI waits on
stdin before starting:

```
Warning: no stdin data received in 3s, proceeding without it.
```

`Popen` at line 148 does not set `stdin`, so the child inherits the server's.
Add `stdin=subprocess.DEVNULL`. Measured: with `< /dev/null` the warning is gone
and the run starts immediately. This applies to `run_task` as a whole, which is
right — no hook should be reading the server's stdin.

**`adapters/subprocess.py:76` — `_watch_log` must stop re-reading the world.**
It calls `log_path.read_text().splitlines()` every 0.2 s purely to count lines.
Against a 0-byte log that is free; against a multi-megabyte streaming log it is
tens of MB/s per running worker. Make it incremental: keep a byte offset, read
only what is new, and count only lines terminated by `\n`, holding a trailing
partial back until it completes.

That changes the numbering contract the function's docstring pins ("counts
lines exactly the way `logs.jsonl` reads them back"), because `str.splitlines()`
also splits on `\r`, `\v`, `\x1c` and U+2028 while an incremental `\n` reader
cannot. Resolve it by moving both sides onto one rule: add
`logs.split_lines(text)` (a plain `split("\n")`, dropping a trailing empty
element) and use it in `logs.jsonl:64`, in `_watch_log`, and in
`builtins.py:150`. Writer and reader stay in lockstep by construction, and a
raw `\r` inside a line stops inventing a phantom line.

**`logs.py:22` — `classify`.** It looks for `type in ("tool_use","tool_result")`
at the top level. Stream-json nests those in `message.content[]` under
`type: "assistant"` / `"user"`, so every line would classify as `agent` and the
modal's `tool` filter would select nothing. Extend `classify` to look one level
into `message.content[0].type`. `system` and `result` lines classify as `sys`.

**`logs.py:64` — line size.** `jsonl` returns each raw line as `text`; a
`tool_result` for a large file read is tens of KB, and the modal renders every
line. Truncate `text` at 2000 characters with a trailing `…` in the `jsonl`
rows only. The copy button reads the plain-text endpoint (`FileResponse`), which
stays whole.

**`logs.py` — `summary`.** A wall of raw JSON is not the readable log 77z asks
for. `jsonl` rows gain a `summary` field: `Read(src/kraft/api.py)` for a
tool_use, the first line of the text block for an assistant message, `init
claude-opus-5` for the init line, `result: success` for the envelope, and the
raw line for anything unrecognised. `cli._print_log` prints `summary` in human
mode (`--json` keeps emitting the row unchanged), and the log modal prefers
`row.summary` over `row.text` — a one-line frontend change.

### Live usage (Kraft-54dk)

`run_task` already polls the child every 0.05 s (line 195). Give that loop a
second job, every 5 s: read the log forward from its own byte offset, decode the
new lines, and accumulate usage.

Counting rule: sum `message.usage` across **distinct `request_id`s** — the
stream emits several `assistant` lines per API request (measured: two lines,
identical usage, one request), so a naive sum double-counts. The sum converges
on the envelope's own number: the real 46-turn session reported
`cache_read_input_tokens: 1780049` at the top level against a single 78 657
iteration entry, i.e. the envelope's `usage` is itself the sum over requests.

New in `usage.py`:

```python
def from_stream(lines: Iterable[str], seen: dict[str, Usage]) -> Usage | None
```

— folds new NDJSON lines into a `request_id -> Usage` map owned by the caller
and returns the running total plus the model (from `system/init`, else from an
`assistant` line's `message.model`). No cost: cost is only ever the agent's own
number (`usage.py`'s module docstring), and no per-request cost is reported, so
a live row keeps `cost_usd = NULL` until the envelope lands.

New in `store.py`, beside `session_exited:403`:

```python
def session_progress(conn, session_id, usage: Usage) -> None
```

— `UPDATE worker_sessions SET model = ?, tokens_in = ?, tokens_out = ?` for a
row still `running`, and **no event**. Emitting one every 5 s per worker would
flood the WebSocket, the indexer and the notifier fan-out for a number nobody
subscribes to. `session_exited` still writes the authoritative final numbers, so
any live drift is corrected at the end.

`store.usage_rollup:486` already sums every session row regardless of status, so
the API and `WorkItemDetail.tsx` need no change at all — "tokens this node"
starts being true the moment the row does. The detail view reloads on a 60 s
interval (`WorkItemDetail.tsx:225`), so the number ticks about once a minute:
enough to answer "is this thing alive", which is what was asked.

**Model (Kraft-2r8s), both paths.** Live: `system/init`. At exit:
`usage.from_envelope` falls back to the first `modelUsage` key when there is no
top-level `model`. Both are needed — the envelope path is also what a result
file and `reattach` go through.

**The fakes.** `fixtures/fake-claude.sh` and `tests/support/fake_agent.py` each
print one envelope line today. Both must emit a small stream: a `system/init`
line with a model, one or two `assistant` lines with `request_id` and
`message.usage`, then the `result` envelope — otherwise no test exercises the
inputs the real adapter now parses. `fake-claude.sh` gains a
`KRAFT_FAKE_CLAUDE_STREAM_DELAY` so a test can assert the log is non-empty
*while the child is still running*.

## Part 2 — Kraft-9oab: SIGTERM

### The problem

Reproduced, minimally and decisively. A FastAPI app whose WebSocket handler only
ever *sends* (a `while True` loop with a 1 s timeout — exactly the shape of
`api.py:1569 ws_events`), one connected client, one SIGTERM:

```
STILL RUNNING after 30s -> hang reproduced
```

The same app with a handler that also awaits `websocket.receive()`:

```
EXITED after 0.2s rc=-15
```

Uvicorn's graceful shutdown closes the listening socket, then waits for open
connections to finish — which matches the bead's observation that port 8765 was
released within a second while the process stayed resident. It asks the
WebSocket to close; Starlette surfaces that as a `websocket.disconnect` message
delivered to `receive()`. `ws_events` never calls `receive()`. It sits in its
`asyncio.wait_for(client.queue.get(), timeout=1.0)` loop forever, uvicorn waits
for it forever, and lifespan shutdown never even runs. Nothing to do with the
executor, the reattach scanner or a non-daemon thread — the three the bead asked
to rule out. The existing `test_sigterm_shuts_down_cleanly_mid_task` passes
because it opens no WebSocket; a human with the board open in a browser hits it
every time.

### The fix

In `ws_events`, start one `asyncio.ensure_future(websocket.receive())` after
`accept()` and treat its completion as "the connection is going away": return
from the loop, cancel it in the `finally` beside `bc.unregister(client)`. This
is also the correct fix for a browser tab closed without a close frame, which
today leaks a `Client` in the broadcaster's set until the send fails.

Two supporting changes, neither a substitute for the above:

- `cli.py:119` — `uvicorn.run(..., timeout_graceful_shutdown=10)`. A backstop for
  the next endpoint that forgets, and for an in-flight HTTP request that hangs.
  10 s is comfortably above the slowest ordinary request (a forge call).
- `cli.py:162 _cmd_stop` — wait 15 s, not 5, so the poll cannot expire before
  the backstop it is waiting on. The message on expiry stays a failure.

Not doing: **escalating to SIGKILL** after the poll. The bead flags it as a
separate decision that risks a half-written run directory, and with the cause
fixed it has nothing left to rescue.

Noted, not fixed: uvicorn re-raises the captured signal after a graceful
shutdown (measured — the probe exited `rc=-15`), so `_serve`'s
`finally: pid_path.unlink()` never runs under SIGTERM. Harmless today, because
`_read_pid` detects and clears a stale pidfile itself. Filed as a follow-up
rather than smuggled in here.

## Part 3 — permissions, in the order 3tw then oor

### The order, and why

**Kraft-3tw first, Kraft-oor second, both in this MR.** oor's permission-prompt
tool has to answer *from* something, and the thing it answers from is a per-node
grant — which is exactly what 3tw adds. Building oor first would hardcode one
global policy and then re-plumb it a week later. Note also what oor's own
correction comment says: `--permission-mode auto` is the whole functional fix
(Kraft-8pe, already shipped), and a prompt tool buys an audit trail and a policy
hook, not an unblocking. So oor is built as observability with teeth, not as a
rescue.

### Kraft-3tw — the grant becomes a per-node registry key

Today `run_agent_task` appends `--permission-mode auto` unconditionally
(`agent.py:97-122`) and `--disallowed-tools` from a repo∪hook union. There is no
way to say anything narrower for one node.

Add two agent-hook keys, both hook-level only:

```yaml
on.spec.requested:
  { kind: agent, command: claude, skill: spec, artifact: spec,
    allowed_tools: [Read, Glob, Grep, Write, Edit, Bash], permission_mode: auto }
```

- `Profile` gains `allowed_tools=("--allowedTools",)` and
  `permission_mode_flag=("--permission-mode",)`; the existing
  `permission_mode=("--permission-mode","auto")` tuple becomes the *default*
  the binding overrides.
- `Invocation` gains `allowed_tools: tuple[str, ...]` and
  `permission_mode: str | None`; `resolve_invocation` reads them from the
  binding only. **Not repo-level**, unlike `deny_tools`: unioning two allowlists
  *widens* the narrower one, which is the opposite of what an allowlist is for,
  and the same argument `effort` is already hook-only for.
- `templates.py:159` — both join `agent_only`; `allowed_tools` validates as a
  list of strings beside `deny_tools`, `permission_mode` against a
  `_PERMISSION_MODES` set (`default`, `auto`, `acceptEdits`, `plan`,
  `bypassPermissions`) the way `_EFFORT_LEVELS` already does at line 46. A typo
  in a permission grant must fail at config load, not at dispatch.

**A correction to the bead's premise, which the reviewer should see.** Kraft-3tw
proposes `spec, plan, review-brief -> Write,Edit and NO Bash`. That is not
achievable today: `agent._ARTIFACT` — the contract every one of those three
nodes runs under — ends with *"Before you exit, `git add` that file and commit
it"*, and a spec worker also has to read the code it is designing against. All
three need a shell. So **no shipped node drops Bash in this change**, and
`registry.yaml`'s defaults keep today's effective grant. What ships is the
*mechanism* plus a `permission_mode`/`allowed_tools` an operator can narrow per
node, and the honest statement in the bead that the unbounded half is closed
only by OS-level isolation (Kraft-rki), not by a flag. Denying Bash to the
document nodes would need the artifact commit moved into Kraft (a builtin that
commits `agent.artifact_path()` after the node) — a real design, out of scope
here, filed as a follow-up.

### Kraft-oor — Kraft answers the prompts

`--permission-prompt-tool mcp__<server>__<tool>` names an MCP tool the CLI calls
instead of prompting a human, whenever `--permission-mode auto` decides it wants
to ask. Kraft already ships that MCP server (`kraft admin mcp`, registered at
user scope by `kraft admin init`), the worker already inherits it, and
`client.resolve_context()` already keys off `KRAFT_WORK_ITEM_ID`, which
`run_agent_task` already puts in the child's environment. The pieces exist.

- `mcp.py` gains one tool, `permission_request(tool_name, input, tool_use_id)`,
  which forwards to `client.permission_request(...)` →
  `POST /worker-sessions/{sid}/permission` with `sid` from `KRAFT_SESSION_ID`.
  It returns the CLI's contract shape: `{"behavior": "allow", "updatedInput":
  input}` or `{"behavior": "deny", "message": "..."}`.
- The API resolves the session → its `hook_point` → the registry binding → the
  binding's `allowed_tools`. **A binding with no `allowed_tools` allows
  everything.** That is deliberate: today `auto` resolves those asks silently by
  itself, and a default that denied would turn a pure-observability change into
  a behaviour change on every node at once. A binding that *does* declare
  `allowed_tools` is taken at its word, and a tool outside it is denied with a
  message naming the node — which is what makes 3tw's key load-bearing rather
  than decorative.
- Every decision appends a `permission_decision` event
  (`{session_id, node_id, tool, decision, reason}`). This is the whole point:
  it is the only way the orchestrator ever learns what a worker decided it was
  allowed to do.
- `Profile` gains `permission_prompt_tool=("--permission-prompt-tool",)` and
  `run_agent_task` passes `mcp__kraft__permission_request` for every agent task.
- **Fail closed.** If the API is unreachable (a Kraft restart while an adopted
  worker runs on), the tool returns `deny`. That is exactly today's behaviour
  for an unanswered ask, so it regresses nothing, and failing open would make
  Kraft's outage a permission grant.
- On an install where `kraft admin init` was never run, the flag names a tool
  that does not exist. Measured: `claude -p ... --permission-prompt-tool
  mcp__nosuch__tool` exits 0 and completes normally. So the degradation is back
  to today's behaviour, not a crash — which is why no `--mcp-config` is passed.
  Kraft does not own the operator's agent configuration, and a doctor check for
  the registration is a better answer than writing config on every launch
  (filed as a follow-up).

Not doing: **escalating an out-of-policy ask to a human gate**, which oor floats.
Gates are chain-level and answered in hours; a worker blocked mid-tool-call for
hours is worse than a denial it can route around. Revisit when there is a
sub-minute answer channel.

## Out of scope

- **Kraft-rki** (container isolation). Part 3 makes the grant expressible per
  node; it does not make `Bash` bounded, and this spec says so rather than
  implying otherwise.
- Log rotation or a size cap on the new streaming logs. They grow from 0 bytes
  to a few MB per node; disk pressure is a real question but not this work item's.
- `reattach._exit_from_file` recording usage for an adopted session (it passes no
  `usage` today, so a session that outlives a restart keeps NULL tokens).
- Per-work-item model/effort overrides (Kraft-4k6l), which Kraft-2r8s is a test
  instrument for.
- Any change to how `deny_tools` merges across repo and hook.
- Backfilling `model` on existing `worker_sessions` rows.
