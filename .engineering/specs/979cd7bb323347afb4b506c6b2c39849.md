# The chain must land the code it writes

One branch, one merge request, four beads: **Kraft-f3mv**, **Kraft-brq**
(**Kraft-fhd1** closed against it), **Kraft-nh5m**, **Kraft-i47n**.

Today the chain can reach `human_review_approval` over a merge request holding
the spec and the plan and none of the work. Nothing else on the board is
falsifiable until this lands: a green run is indistinguishable from a run whose
code was dropped with the worktree.

This spec was previously written as three merge requests. The steer narrowed it
to the first one; the beads that were MR2 and MR3 are listed under Out of scope
and stay open for their own work items.

---

## The problem, in this repo

`templates/default.yaml` runs `implementation → verify → open_mr → mr_checks →
human_review → merge` with `gate_after: null` on everything between
implementation and the merge gate. Nothing in that stretch commits, and nothing
after `open_mr` pushes.

* The only "commit your work" sentence Kraft injects is `_ARTIFACT`
  (`src/kraft/adapters/agent.py:60`), appended in `run_agent_task` only when a
  binding declares `artifact:` (`agent.py:277`). `on.implementation.start`
  (`templates/registry.yaml:5`) declares none, so the implementation worker is
  never told to commit. Whether it commits is left to the model's habits, which
  is not a property a chain can rest on — the registry pins implementation to a
  different model than spec and plan (Kraft-brq).
* The repo's own `CLAUDE.md` tells it the opposite. "Agent Context Profiles",
  `CLAUDE.md:31`: *Conservative (default) … Do not run git commits, git pushes,
  or Dolt remote sync unless explicitly asked.* `AGENTS.md:76` carries the same
  line. The implementation node is a bare `claude` agent in that repo, so it
  reads that and correctly leaves everything uncommitted (Kraft-f3mv).
* `GlabCli.open_mr` (`adapters/forge.py:181`) and `GhCli.open_mr`
  (`forge.py:232`) each `git push -u origin <branch>` exactly once. `update_mr`
  only rewrites the description; `merge` shells `glab mr merge --yes` against
  the remote. Every commit made after `open_mr` is local only and dies with the
  worktree. Observed on MR !65 and MR !66, both `[ahead 2]`, both pushed by hand
  before approval (Kraft-nh5m; Kraft-wzax was its duplicate and is closed).
* `_ARTIFACT`'s justification — "an uncommitted file is invisible to them" — is
  false. `_gate_artifact` (`api.py:620`) resolves the path and
  `GET /work-items/{wid}/artifact` reads the file off disk from the worktree,
  which its docstring says it does deliberately (Kraft-i47n).

Net effect: a merge gate over a merge request containing documents and no code.

## Kraft-brq vs Kraft-fhd1: pick the shape first

**Kraft-brq's shape wins — a commit *instruction* in the injected context, not a
commit *step* in the chain.** A chain step means the executor running
`git add -A && git commit` on the worker's behalf: it cannot write a message
that means anything, and `-A` sweeps whatever scratch the agent left into the
branch. The agent is the only party that knows what it changed and why.

Kraft-fhd1's second suggestion — "a hard precondition on `open_mr` that fails a
dirty tree instead of merging silently" — is kept, as §3. It is the same
suggestion as Kraft-brq's option 2, and it is what makes the instruction's
failure loud instead of plausible.

So: **Kraft-brq carries the fix; Kraft-fhd1 is closed as a duplicate against
it**, with a close reason naming the shape decision and the fact that its
precondition half shipped here.

f3mv lands with it, as both beads require: the injected instruction and the repo
file must not say opposite things to the same agent.

# The approach

## 1. One commit contract, injected for every agent node (Kraft-brq)

Move the commit sentence out of `_ARTIFACT` and into `_CTX` in
`adapters/agent.py`, so every agent launch gets it, artifact or not:

> You are working in a git worktree cut for this work item, on its own branch.
> Commit everything you change before you exit — `git add` and `git commit`, in
> this worktree. Work left uncommitted never reaches the merge request this
> chain opens, and is destroyed with the worktree. Do not push and do not merge:
> Kraft pushes the branch and opens, updates and merges the merge request
> itself.

It goes after the result-file paragraph and before `_ARTIFACT`, so an artifact
node reads the general contract then the specific one. The "do not push" half is
load-bearing: §4 makes Kraft the only pusher, and a worker that pushes on its
own defeats §3's dirty-tree gate on the next node.

## 2. The repo stops contradicting it (Kraft-f3mv)

Add a Kraft-worker carve-out to `CLAUDE.md` and `AGENTS.md`:

> ## Kraft Workers
>
> A session with `$KRAFT_WORK_ITEM_ID` set is a Kraft worker, running in a
> throwaway git worktree on its own branch. It commits everything it changes
> before it exits — uncommitted work never reaches the merge request and is
> destroyed with the worktree. This overrides the Conservative profile's
> "do not run git commits" for commits only: a worker still does not push,
> merge, sync Dolt, or close beads. Kraft does those itself.

`KRAFT_WORK_ITEM_ID` is really set for every agent launch (`agent.py:346`), so
the condition is checkable by the agent reading it.

**Outside the managed block, not inside it.** Both files carry
`<!-- BEGIN BEADS INTEGRATION v:1 profile:minimal hash:6cd5cc61 -->` …
`<!-- END BEADS INTEGRATION -->` (`CLAUDE.md:5-58`, `AGENTS.md:50-103`), and the
Conservative-profile line lives inside it. Editing inside a hashed generated
block invites `bd` to regenerate it and silently drop the carve-out, so the new
section is appended after the end marker in each file, and says which profile
line it overrides.

Kraft's injected context stays the authority — the 00_overview glossary bans
repo files as a context channel, and this does not make them one. It only stops
the repo arguing with the channel that is sanctioned.

## 3. `open_mr` refuses a dirty worktree (Kraft-fhd1's precondition half)

New module-level helper in `forge.py`, called at the top of `GlabCli.open_mr`
and `GhCli.open_mr`:

```python
async def _assert_clean(repo: Path) -> None
    # git status --porcelain; non-empty output -> ForgeError listing the first few paths
```

In the CLI backends rather than in `run_task` so `FakeForge` stays a pure
in-memory double with no git repo behind it — every existing `FakeForge` test
keeps passing, and the guard is tested directly against a stubbed `git`.

Ignored files are excluded by git itself, so `.pytest_cache/` and
`.engineering/sessions/` do not trip it. Untracked files are **not** excluded:
new source and test files are exactly what went missing on work item 5163dd1b.
The node fails, the item stops for a human, and the failure names the files
instead of opening a document-only MR.

## 4. Push before the merge, and never merge a stale branch (Kraft-nh5m)

* `Forge` gains `async def push(self, *, repo, branch) -> None`. `GlabCli` and
  `GhCli` implement it as `git push -u origin <branch>` — the line their
  `open_mr` already runs, now called through the method. `FakeForge.push`
  appends to a `pushed: list[str]`, so the push is assertable through
  `run_task` without a network or a git remote.
* `run_task`'s `sync_mr` case calls `forge.push(...)` before
  `forge.update_mr(...)`: the description and the branch the reviewer's forge
  shows then describe the same head.
* `merge` refuses a branch ahead of its remote. A second module-level helper,
  called at the top of both CLI backends' `merge`:

  ```python
  async def _assert_pushed(repo: Path, branch: str) -> None
      # git rev-list --count origin/<branch>..HEAD; non-zero -> ForgeError
      # "local branch is ahead of origin/<branch> by N commit(s)"
  ```

  If `origin/<branch>` does not exist, `_run` already raises `ForgeError` and
  the node fails loudly, which is the right answer for a merge with no pushed
  branch.

§5's push makes the refusal unreachable on the ordinary path. It stays because
it is the half that works on an operator's existing `$KRAFT_HOME/templates/`
(§6), and because the case that produced Kraft-nh5m must not be able to merge
silently again.

## 5. `on.mr.sync` gets its own node, after the gate

`human_review` is `tasks: [on.mr.sync, on.human_review.requested]`, and
`_measure_node` runs a node's tasks concurrently (`asyncio.gather`,
`executor.py:389`). So today's sync can push before the review brief is written,
and after §4 that push is the thing merge is checked against.

The sync node goes **after** the gate, not before it:

```yaml
  - id: human_review
    tasks: [on.human_review.requested]
    gate_after: human_review_approval
  - id: mr_sync
    tasks: [on.mr.sync]
    gate_after: null
  - id: merge
    tasks: [on.merge]
    gate_after: null
```

Why after and not before: `_gate_artifact` (`api.py:620`) finds the document a
pending gate is about by scanning **the gate node's own tasks** for a binding
with `artifact:`. Leaving the gate on a node whose only task is `on.mr.sync`
would leave the human_review gate with no review brief to show. Keeping the gate
on `human_review` keeps that resolution untouched, and pushing after approval
means the head that gets merged includes the brief commit and anything the human
committed while reviewing.

What the human reviews is unaffected: the gate's diff and artifact views read the
worktree off disk (`review.py`, `_gate_artifact`), not the forge. The stretch
between the CI poll and the merge gains only the review brief, which is
documentation and changes no CI outcome.

Nothing keys on the node id `human_review` — gates resolve by name
(`_gate_node_index`, `api.py:616`), the SPA renders the gate name — so the only
other edits are the two tests that enumerate the default chain's node ids
(`tests/test_templates.py:118`, `tests/test_analytics.py:30`).

## 6. Existing `$KRAFT_HOME` templates

`cli.seed_home` only ever creates (`cli.py:39`), so an operator's
`$KRAFT_HOME/templates/default.yaml` will not gain §5's split, and
`chain_definition` is materialized per work item, so in-flight items keep the
old chain either way. On such a home the sync still races the brief exactly as
today — and then §4's ahead-of-origin refusal stops the merge and names the
reason, instead of the work being dropped. That is why both halves ship. The MR
description says to copy the new `default.yaml` into `$KRAFT_HOME/templates/`;
no `doctor` check is added, because the merge refusal already reports the
condition at the moment it matters.

## 7. The artifact contract stops claiming something false (Kraft-i47n)

`_ARTIFACT` keeps only the artifact-specific half — where the file goes, its
front matter, revise-in-place — and loses both the now-redundant commit sentence
and its false justification. Kraft-i47n's fix is that deletion, not a new claim:
§1 already tells every worker to commit everything, so the artifact needs no
rule of its own.

**`.engineering/` stays tracked.** `.engineering/sessions/` is already
gitignored (`.gitignore:54`), so the per-session prose that motivated
Kraft-i47n's "or drop it entirely" branch is already out of the diff, and specs,
plans and review briefs are the documents the MR reviewer is being asked to
approve. Kraft-5fx's public-repo split can revisit `docs/` and `.engineering/`
together; this branch does not pre-empt it.

# Rejected

* **Have the executor commit for the agent** (`git add -A` after every agent
  node) — Kraft-fhd1's shape. See the shape decision above.
* **Push after every node.** More pushes and more CI runs for the same outcome
  as pushing once before the merge.
* **Have `merge` push what it finds ahead, instead of refusing.** It would merge
  a head CI has never seen, and quietly. A stop a human reads beats a green
  merge of untested code.
* **Put the sync node before the gate and teach `_gate_artifact` to scan
  backwards.** It would silently give `chain_finalized` — whose node is a
  `noop` — the plan's artifact, changing an unrelated gate to buy an ordering
  that §5 gets for free.
* **Steering instead of a repo edit for Kraft-f3mv.** Steering is per-item text
  a human writes; the contradiction is permanent and belongs where the agent
  reads it.
* **Drop `.engineering/` from git and gitignore it** — Kraft-i47n's other
  branch. See §7.
