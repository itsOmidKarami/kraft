## Problem

Everything that shapes how a work item runs — which chain it follows, what
model and effort its nodes get — is chosen once, at intake, by
`executor.intake` (`src/kraft/executor.py:151` calls
`templates.materialize(template, ...)` and `store.create_work_item` writes the
result into two columns, `chain_template` and `chain_definition`) and is
otherwise immutable and instance-wide:

- **Chain template.** There is no PATCH route for `chain_template` or
  `chain_definition`. `WorkItemPatch` (`src/kraft/api.py:1032`) only accepts
  `title` and `description`. A work item filed on the wrong template (a
  one-line fix filed on a template with spec+plan gates, or the reverse) has
  no fix short of delete-and-refile, which loses the description, attachments
  and bead link already set. (Kraft-gwn6)
- **Model and effort.** `adapters.agent.resolve_invocation`
  (`src/kraft/adapters/agent.py:175`) resolves `model` as
  `escalate_model or model or repo.default_model` and `effort` as
  `binding.get("effort")`, both read only from `templates/registry.yaml` and
  `repos.yaml` — shared by every work item on the instance. A one-line typo
  fix and a chain-integrity rewrite run their spec and plan nodes at the same
  model and the same effort; the per-item budget cap in `policy.yaml` can only
  stop an expensive item, never right-size it up front. (Kraft-4k6l)
- **Where `.engineering/` artifacts live.** Raised separately
  (Kraft-dqwr) at the human-review gate of an unrelated work item, where
  `.engineering/` was 77% of an MR's diff. Decided below, as a decision, not
  code (see "Decision: Kraft-dqwr" — no file in this repo changes for it in
  this branch).

All three are instances of one question: what belongs to the chain template
(shared, chosen once) versus the work item (one item's own knobs). This spec
answers it for all three: the chain and its knobs (node list, gates, agent
bindings) belong to the template; a live item may only override values inside
a fixed, validated set — never structure — and even that only where the
override provably cannot invalidate work already done.

## Approach

For gwn6 and 4k6l: extend the existing `PATCH /work-items/{wid}` route
(`WorkItemPatch` / `update_work_item`, `src/kraft/api.py:1032-1059`) with two
more optional fields, `chain_template` and `agent_overrides`, following the
same "field omitted ⇒ untouched" convention `title`/`description` already
use, and expose both through `client.py`, a `kraft item` CLI verb, and an MCP
tool — the parity gwn6 asks for explicitly, and the same gap Kraft-hbsv and
Kraft-82gz already name for `title`.

Rejected alternatives:
- **A general "revise the chain" endpoint** that accepts an arbitrary new
  `chain_definition`, reusing the chain-review splice path
  (`store.splice_chain`, Kraft-hm0). Rejected: that path exists to let a
  *running* chain's own agent revise its own tail during a gate; grafting
  arbitrary external chain edits onto it would let a template swap smuggle in
  node/gate changes no template file was ever validated against. Switching
  template must produce exactly what `executor.intake` would have produced
  had the item been filed on the new template to begin with — so it calls
  `templates.materialize` directly, the same function intake calls, not the
  splice path.
- **Per-node-id overrides** for model/effort (a map keyed by node id).
  Rejected as unrequested scope: nothing in Kraft-4k6l or the motivating
  cases ("a bigger model", "make a small item cheap") asks for one node to
  run hot and another cold within the same item — the ask is the whole item
  should cost more or less. One override object per item, applied to every
  agent-kind dispatch for that item, is the smaller surface and is what both
  the bead's design notes and its precedence rule ("escalate_model > item
  override > binding model > repo.default_model") assume.
- **Snapshotting the override into `chain_definition` at set-time** the way
  intake snapshots nodes. Rejected per the bead's own recommendation:
  resolving at dispatch (not intake) lets a paused, stuck item be made
  cheaper or stronger before its next retry, which is the actual use case.

## Kraft-gwn6: switch chain template before the chain has started

**Boundary.** "Not yet started" is `current_node_id IS NULL` — the same
boundary `client.py:212` already documents ("A NULL `current_node_id` is a
work item nobody has started"), not `status`, because a `paused` item can
also be paused mid-chain (Kraft-zpfb) and switching its template out from
under a live `current_node_id` would orphan whatever node that id names, plus
any attachment-gate trimming already baked into the current
`chain_definition`.

**API.** Add `chain_template: str | None = None` to `WorkItemPatch`. In
`update_work_item`, when it is set:
1. 404 if `chain_template` names no valid template
   (`st.templates.valid.get(chain_template)` is `None`) — same lookup
   `_start` in `intake.py:115` already does.
2. 409 if `current_node_id` on the row is not `NULL` — "work item has
   already started; template is fixed for its life".
3. Otherwise, recompute `satisfied = frozenset(templates.ATTACHMENT_GATES[a["kind"]] for a in executor._attachments(row))`
   (the exact expression `executor.intake` uses today) against the item's
   *existing* attachments — do not require re-attaching — and call
   `templates.materialize(new_template, satisfied_gates=satisfied)`.
4. Write both `chain_template` and `chain_definition` in the same
   transaction as any `title`/`description` fields also present in the body.

**Store.** New `store.set_chain_template(conn, work_item_id, template_id,
chain_definition)`, mirroring `set_description`'s shape: one `UPDATE`, one
event. New event type `chain_template_changed`, payload
`{"from": old_template_id, "to": new_template_id}` — its own type, not
folded into `chain_spliced` (that event means the *chain-review* path
touched the row; this means intake's own materialization ran again against a
different template, which is a different question to answer from the
timeline).

**Surfaces.** `client.py` gets a thin wrapper that PATCHes the route; `kraft
item set-chain --id ID --template NAME` in `cli.py` (parallel to the existing
`mr-label` verb's `--id`-not-positional shape only where a second positional
would be ambiguous — here there is only one positional-shaped argument, so
`id` stays a plain optional positional like `pause`/`resume`/`retry`); an MCP
tool `set_chain_template(work_item_id, template)` in `mcp.py`, docstringed
the way `create_work_item`'s already is. The SPA's existing detail-screen
patch surface (already wired to `PATCH /work-items/{wid}`) picks up the new
field for free once the API accepts it, but no new UI is required by the
brief and none is a bead here — out of scope beyond the API accepting the
field the frontend can then send.

**Out of scope.** Switching template on a started item (409, by design —
that is Kraft-zpfb's territory, not this one's, if it is ever wanted at
all). Editing `chain_definition` directly (that is the chain-review splice
path, untouched).

**Tests** (`tests/test_api.py`, alongside the existing `test_patch_*`
tests):
- `test_patch_switches_chain_template_before_the_chain_starts` — a work item
  created with `current_node_id` NULL, PATCH `chain_template` to a second
  valid template on disk, assert the row's `chain_template` and
  `chain_definition` both reflect the new template's nodes and a
  `chain_template_changed` event was recorded.
- `test_patch_refuses_chain_template_once_started` — same item, with
  `current_node_id` set (e.g. after `store.node_started`), PATCH
  `chain_template` → 409, row unchanged.
- `test_patch_refuses_an_unknown_chain_template` → 404, row unchanged.
- `test_patch_switching_chain_template_preserves_attachment_gate_trim` — an
  item with a `spec` attachment (so its materialized chain already skips the
  `spec_approval` gate), switched to a second template that also has a
  `spec_approval` gate, asserting the new `chain_definition` still has that
  node trimmed without re-attaching anything.

## Kraft-4k6l: per-item model/effort override

**What can be overridden.** `model`, `escalate_model`, `effort` only — the
three fields the bead scopes this to. Not `profile`, `deny_tools`,
`steering`, `skill`, `artifact`: those change what an agent is *allowed* to
do or *must produce*, which is a permission surface (Kraft-3tw, Kraft-oor
territory), not a cost/capability dial.

**Storage.** New column `work_items.agent_overrides TEXT` (migration 20,
`ALTER TABLE work_items ADD COLUMN agent_overrides TEXT`, following the
`ALTER TABLE ... ADD COLUMN` pattern every prior single-column migration in
`db.py` already uses), JSON object with up to those three keys, `NULL` when
unset. Read fresh at every dispatch (not snapshotted into
`chain_definition`), because `SELECT * FROM work_items` (the query
`_dispatch`'s `work_item_row` already comes from, `executor.py:1108`/`1292`)
picks up the new column automatically — no new query to write.

**Validation.** New `templates.validate_agent_overrides(overrides: dict) ->
list[str]`, next to `validate_nodes`, checking exactly what `load_registry`
already checks for an agent hook's own `model`/`escalate_model`/`effort`
(`templates.py:188-195`): keys are a subset of `{"model", "escalate_model",
"effort"}`; `model` and `escalate_model` are strings or `None`; `effort` is
in `templates._EFFORT_LEVELS` (exported alongside the new function so the API
layer does not reach for a private name). One rule set, two readers
(`load_registry` for hook bindings, the new API path for item overrides) —
the same "validate in one place" reasoning `validate_nodes`'s own docstring
already gives for its own two callers avoids repeating Kraft-unk, where
`revised_chain_nodes` shipped a second, unvalidated path.

**Precedence**, in `adapters.agent.resolve_invocation`: add a keyword-only
`item_override: dict | None = None` parameter (default treated as `{}`).
Compute, before the existing model/effort lines:

```python
io = item_override or {}
eff_model = io.get("model") if io.get("model") is not None else binding.get("model")
eff_escalate = (
    io.get("escalate_model")
    if io.get("escalate_model") is not None
    else binding.get("escalate_model")
)
...
model = ((eff_escalate if escalate else None) or eff_model or repo.get("default_model"),)
...
effort = (io.get("effort") if io.get("effort") is not None else binding.get("effort"),)
```

This gives: while escalating, an escalate model — the item's own override if
it set one, else the binding's — always wins over any plain `model`, item or
binding (the bead's "escalate_model must still win while escalating, or a
cheap override quietly disables the escalation valve"). While not
escalating, the item's plain `model` override wins over the binding's, which
wins over `repo.default_model`. `effort` has no escalate variant, so the
item's override simply wins over the binding's when set.

`_dispatch` (`executor.py:466-476`) parses
`json.loads(work_item_row["agent_overrides"]) if work_item_row["agent_overrides"] else None`
and passes it through as `item_override=`.

**API.** Add `agent_overrides: dict | None = None` to `WorkItemPatch`, same
route. When present (even `{}`): run `templates.validate_agent_overrides`,
422 on any error; otherwise `store.set_agent_overrides(conn, wid, json.dumps(body.agent_overrides) if body.agent_overrides else None)`,
mirroring `set_description`'s own empty-clears-it convention (`{}` clears all
three fields back to template defaults; a partial object like
`{"model": "opus"}` *replaces* the whole stored object, it does not merge —
the same all-or-nothing shape `title`/`description` already have, and
simpler than field-level merge semantics nothing has asked for). New event
`agent_overrides_changed`, payload `{"overrides": body.agent_overrides}` —
its own type for the same reason `set_description`'s docstring gives:
downstream cost changes have to be answerable from `events`, not inferred.
No `current_node_id` restriction: unlike the chain shape, a model/effort
dial can change mid-chain, including on a paused item, which is the point
(make a stuck item cheaper before its next retry).

**Surfaces.** `client.py` wrapper, `kraft item set-overrides --id ID
[--model NAME] [--escalate-model NAME] [--effort LEVEL] [--clear]` in
`cli.py` (`--clear` sends `{}`; naming any of the three value flags sends an
object with only those keys — clearing one field alone is not supported,
matching the all-or-nothing store semantics above), and an MCP tool
`set_agent_overrides(work_item_id, model=None, escalate_model=None,
effort=None, clear=False)` in `mcp.py`.

**Explicitly out of scope / follow-up.** End-to-end confirmation that an
override actually reached the dispatched CLI invocation is blocked on
Kraft-2r8s (`worker_sessions.model` is always `NULL` today because
`usage.from_envelope` reads a `model` key the Claude Code envelope does not
have) — that bead is already filed and is not part of this work item. This
spec verifies the override at the two levels that do not depend on it:
`resolve_invocation`'s precedence (unit-testable today) and the stored value
round-tripping through the API. Overriding `profile`, `deny_tools`,
`steering`, `skill`, or `artifact` per item is explicitly deferred to
whatever design Kraft-3tw/Kraft-oor settle on.

**Tests:**
- `tests/test_adapters_agent.py`:
  - `test_item_override_model_beats_binding_model`
  - `test_item_override_escalate_model_beats_binding_escalate_model_while_escalating`
  - `test_binding_escalate_model_beats_item_plain_model_override_while_escalating`
    (the exact case the bead calls out: a cheap item override must not
    suppress the escalation valve)
  - `test_item_override_effort_beats_binding_effort`
  - `test_no_item_override_falls_through_to_binding_and_repo_default`
    (existing behavior unchanged when `item_override` is `None`)
- `tests/test_templates.py`:
  - `test_validate_agent_overrides_rejects_unknown_effort`
  - `test_validate_agent_overrides_rejects_non_string_model`
  - `test_validate_agent_overrides_accepts_a_partial_object`
- `tests/test_api.py`:
  - `test_patch_sets_agent_overrides_and_records_an_event`
  - `test_patch_clears_agent_overrides_with_an_empty_object`
  - `test_patch_rejects_invalid_agent_overrides_with_422`
  - `test_patch_accepts_agent_overrides_on_a_started_or_paused_item` (no
    `current_node_id` restriction, unlike `chain_template`)

## Decision: Kraft-dqwr — where `.engineering/` artifacts live

**Decision** (recorded as Kraft-fbau, `related` to Kraft-dqwr, Kraft-gwn6,
Kraft-4k6l): `.engineering/` artifacts belong to the work item, not the
chain template, and are not committed — `.engineering/` is gitignored in
full. The durable record of a spec, plan, or review is the merge request the
chain opens (its description and gate history), readable with no checkout;
the on-disk files under `.engineering/` are a working copy for the duration
of the run, the same lifetime as the worktree that holds them.

This is the same item-versus-template question the other two beads answer,
on a third axis: a template's `artifact: <kind>` binding
(`templates.py:216-222`) already fixes *what kind of document* a hook must
produce, per node, which is correctly template-owned. *Where that document
physically lives* has never been template or per-item configuration — both
the write side (the prompt `_ARTIFACT` template in `adapters/agent.py`) and
the read side (`GET /work-items/{wid}/artifact`, `kraft view artifact`)
derive the path from `(kind, work_item_id)` alone via
`agent.artifact_path`, with nothing stored on the row, "so nothing to
migrate, nothing to go stale" per that function's own docstring. Committing
UUID-named, auto-written, ~1500-line-per-item prose into the public repo
(1496 of 1930 lines, 77%, on the MR that raised this bead) turns every merge
into a documentation diff a human has to scroll past to find the code, and
duplicates what the MR description already carries.

Alternatives considered and rejected (full rationale in Kraft-fbau):
keeping the interim state MR !59 left (only `.engineering/sessions/`
gitignored, specs/plans/review_briefs still tracked) is the state that
raised the question, not an answer to it; moving `.engineering/` into the
Kraft-5fx private-docs layer does not work because that layer's symlink
mechanism does not reach a `git worktree add` checkout; and making the
artifact root itself a per-item or per-template override is unneeded scope —
nothing asks for a *different location on disk*, only for the document to
survive the run somewhere the gate and the MR can both reach, which
gitignoring the whole directory already gives.

**Out of scope for this branch.** This is a decision, not code — it blocks
neither gwn6 nor 4k6l, and no file changes for it land here. Actually
gitignoring `.engineering/` (extending the current
`.engineering/sessions/`-only entry to the whole directory) and reconciling
MR !59's interim state is follow-up work the decision unblocks, tracked on
Kraft-fbau, not this work item.
