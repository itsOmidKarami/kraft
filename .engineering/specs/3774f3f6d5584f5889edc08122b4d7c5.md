# Gates and terminal states with no way out

One branch, one merge request, four beads: **Kraft-ko7j**, **Kraft-bol**,
**Kraft-xron**, **Kraft-nhps**.

Each is a state a human cannot get the chain out of without editing the
database or abandoning the item. Two of them (ko7j, bol) are the same missing
thing seen from two gates, so they get one mechanism and two applications. The
other two are independent: a forge node that reads a finished job as a failure,
and a branch name that makes `main`'s history unreadable.

---

## The problem, in this repo

### 1. Rejecting the last gate discards the note and routes nowhere (Kraft-ko7j)

`api.py:1081` declares `TERMINAL_REJECT_GATES = {"human_review_approval"}`.
In `reject_gate` (`api.py:1085`) that makes `replan` False, so:

* `store.reject_gate(..., reopen=False)` (`store.py:321`) runs a literal
  `SET status = status` and appends a `gate_rejected` event carrying the note;
* the `mark_needs_human` branch below is skipped, because it is itself guarded
  by `gate not in TERMINAL_REJECT_GATES`;
* the handler returns without spawning anything.

The item sits in `needs_human` on `human_review`. Two separate failures on one
code path:

* **The note is write-only.** Every other gate turns it into the next agent's
  steer (`executor.run(..., steer=body.note)` → `_STEER_PROMPT`,
  `executor.py:58`). Here it lands in an event payload that nothing reads.
  `retry_work_item` (`api.py:1311`) takes `body.steer` and never looks at the
  last rejection, so a human who typed a reason must retype it to make it
  count.
* **There is no route back to the code.** `retry` restarts at
  `current_node_id`, still `human_review`, which re-runs
  `on.human_review.requested` and regenerates the review brief against an
  unchanged diff. Every other door is shut by design: `resume` wants `paused`,
  `pause` wants `running`, `approve`/`reject` want a pending gate and the gate
  stops being pending the moment it is rejected. The real options after
  rejecting are abandon, or approve the thing you just rejected.

### 2. A plan can only be rejected, not edited, at its gate (Kraft-bol)

`plan_approval` does re-run its producer with the note as a steer, so the note
is not lost the way ko7j's is. What is lost is everything the plan got right.
The re-run dispatch is built in `_dispatch_task` (`executor.py:317-346`) as
`_STEER_PROMPT + _brief(work_item_row) + _BEAD_NOTE`: the *brief*, exactly what
the first pass got, plus a one-line steer. Nothing in the dispatch says "you
have already written `.engineering/plans/<id>.md`, and the human objected to
one paragraph of it". `plan/SKILL.md` has no revision clause at all (the spec
method has one — "If you are revising" — and it is the only reason a rejected
spec is ever edited rather than rewritten). So one bad line costs a full
re-plan and a whole session's tokens.

### 3. Merge fails on an already-merged MR (Kraft-xron)

Work item af0fb78e: MR !62 was auto-merged at 15:32:42 when its pipeline went
green; Kraft's `merge` node ran at 15:40:52 and recorded

```
on.merge failed: glab mr merge --yes failed: ERROR
No open merge request available for "kraft/af0fb78ef85c474f9ea11c1ec1f1010c".
```

`GlabCli.merge` (`adapters/forge.py:266`) and `GhCli.merge` (`forge.py:311`)
shell out and let `_run` (`forge.py:101`) turn any non-zero exit into a
`ForgeError`, which `run_task` records as a failed node. "Someone merged it
first" and "the merge was refused" are indistinguishable. `merge` is the last
node in `default.yaml`, so the item stops at `needs_human` with the work
already on `main`, and retry re-runs the same doomed command forever.
`open_mr` has the same blind spot from the other side: it runs
`glab mr create` unconditionally and fails if an MR for the branch is already
open.

### 4. The branch name is the work item UUID (Kraft-nhps)

Three places build it and none of them share a line:
`builtins.py:93` (`branch = f"kraft/{work_item_id}"`, the worktree),
`executor.py:379` (`branch=f"kraft/{work_item_row['id']}"`, every forge node),
and `api.py:1183` (`git branch -D f"kraft/{wid}"`, abandon). The UUID then
lands in the permanent record:

```
Merge branch 'kraft/f98af3e59e704ed69ad1064ed48acf59' into 'main'
Merge branch 'kraft/af0fb78ef85c474f9ea11c1ec1f1010c' into 'main'
```

`git log --oneline main` is a wall of hex, and so is every branch picker in the
forge UI.

## The approach

### A. One mechanism for ko7j and bol: a rejection is addressed, and its note travels with it

Today a rejection is "re-run the node that produced this artifact, with a note
that lives for exactly one launch". Both beads want the same two properties
that description is missing: **the rejection names where the chain goes next**,
and **the note is still there when the next agent reads it**.

**A1. Chain nodes declare where their gate's rejection goes.**
`templates/default.yaml` gains `reject_to: implementation` on the
`human_review` node. `templates.py` validates it (a string naming a node of the
same template, at an index at or before the declaring node) and `materialize`
copies it alongside `gate_after` and `fix_loop`. Absent means today's
behaviour: the gate's own node.

The routing lives in the chain template because that is where chain shape
lives; hard-coding `"implementation"` in `api.py` would make the one
configurable thing in the system carry a rule about a node it need not have.

**A2. `TERMINAL_REJECT_GATES` is deleted.** `POST
/work-items/{wid}/gates/{gate}/reject` gains an optional `node` in its body.
The target resolves as: `body.node`, else the gate node's `reject_to`, else the
gate node itself. It must name a node in *this item's* chain at an index at or
before the gate node — a chain whose `reject_to` node was dropped by
`materialize` (an intake attachment satisfied that gate) falls back to the gate
node rather than 500-ing; an out-of-range or unknown `node` in the request body
is a 400. Every gate then follows one path: bump `<gate>_reject_loop`,
`reject_gate(..., reopen=True)`, spawn `executor.run(start_index=<target>,
steer=note)`. The cap-exhausted branch — `mark_needs_human` with
`"<gate>_reject_loop exhausted after n rejection(s)"` — stops being
gate-specific and now applies to `human_review_approval` too, which is the only
thing that should ever park an item at a rejected gate.

**A3. The note survives past its one launch.** `store.reject_gate` records the
target node in the `gate_rejected` payload, and a new
`store.last_rejection(conn, wid)` reads the newest `gate_rejected` event back.
`retry_work_item` uses it as the steer when the request carries none. Nothing
is stored twice: the events table is already append-only and already holds the
note; it just had no reader.

**A4. Retry is the human's cap override.** `retry_after_cap` also clears
`<gate>_reject_loop` for the current node's `gate_after`, when it has one.
Without this, A2's cap turns into a new dead end one step further out: the
counter is spent, the gate re-opens after every retry, and each rejection is
refused forever.

**A5. A steered re-run over an existing artifact is framed as a revision.** In
`_dispatch_task`, when a steer note is taken *and* the binding declares
`artifact:` *and* `agent.artifact_path(kind, wid)` already exists in the
worktree, the prompt prefix becomes a revision instruction naming that path
instead of the bare `_STEER_PROMPT`:

```python
_REVISE_PROMPT = (
    "A human read {path} and sent it back with this note: {steer}\n"
    "Revise that document in place: change what the note objects to, and "
    "leave the rest of it alone.\n\n"
)
```

This is bol's fix. It is one branch in the one place every agent dispatch is
built, it needs no knowledge of which gate was rejected, and it applies to the
spec gate for free. `plan/SKILL.md` gains the revision paragraph `spec/SKILL.md`
already has, so the method and the dispatch say the same thing.

**How the mechanism reads at each gate afterwards.** `plan_approval`: reject
with a note → the plan node re-runs, told to edit the document it already
wrote. `human_review_approval`: reject with a note → the chain re-enters at
`implementation` with the note as the implementer's steer, walks
`verify → open_mr → mr_checks → human_review`, and re-opens the same gate over
a changed diff. Both bounded by `<gate>_reject_loop`; both leaving the note
readable in the events table for anything that comes after.

**Consequence that must ship with A2:** re-entering at `implementation` walks
back through `open_mr` on a branch that already has an open MR, which today
fails the node. Fixed in B, with the same helper xron needs — this is one bug
("a forge node assumes it is the only actor on its MR") reached from two
directions, so it is fixed once.

### B. Kraft-xron: the forge is asked about the MR before it is told to act

One new method on the `Forge` protocol:

```python
async def find_mr(self, *, repo: Path, branch: str) -> MRRef | None: ...
```

returning `MRRef(number, url, state)` with `state` in `{"open", "merged",
"closed"}`, or `None` when the branch has no merge request at all. Flags
confirmed against the installed CLIs (glab 1.117.0, gh):

* glab — `glab mr list --all --source-branch <branch> -F json -P 5`; rows carry
  `iid`, `state` (`opened`/`merged`/`closed`/`locked`), `web_url`.
* gh — `gh pr list --head <branch> --state all --json number,url,state -L 5`;
  `state` is `OPEN`/`MERGED`/`CLOSED`.

Both list forms, not `view`: an empty list is an unambiguous "no MR", where
`view`'s non-zero exit would force the caller to swallow real errors to read
the same fact. Pick the first row whose state is open, else the first row.
`FakeForge` grows the same method over its existing `opened`/`merged` lists.

Then, in `run_task`:

* `merge` — call `find_mr` first. `merged` → status `done` with
  `"already merged (!<n>); nothing to do"` in the session log. `open` → merge as
  today. `closed` or `None` → `ForgeError` as today. A genuine refusal
  (conflicts, unmet approval rules) still fails the node, because it fails
  inside `forge.merge` with the MR open.
* `open_mr` — an `open` MR for this branch means push, rewrite the description
  from the branch head (the `sync_mr` body, already built in `run_task`) and
  record `"reusing !<n>"` as `done`, instead of creating a second one. This is
  what makes A2's re-entry work, and it also fixes a `retry` of an `open_mr`
  node that crashed after the create.

Whether a merge node *should* silently finish a work item merged out of band —
`xron` asks — is answered yes: the node's stated end state is "this branch is
in `main`", auto-merge/MWPS makes another actor reaching it first an ordinary
event rather than an anomaly, and the log line plus the `gate_approved` event
already record that a human approved the merge. Failing here asks a human to
resolve a situation that is already resolved.

### C. Kraft-nhps: the branch is computed once, at intake, and stored

New nullable `branch` column on `work_items` (migration 13,
`SCHEMA_VERSION` 13 → 14). `store.create_work_item` fills it:

```python
_SLUG_MAX = 40


def branch_name(title: str, work_item_id: str) -> str:
    head = (title or "").strip().splitlines()[0].lower() if (title or "").strip() else ""
    slug = re.sub(r"[^a-z0-9]+", "-", head).strip("-")[:_SLUG_MAX].strip("-")
    return f"kraft/{slug}-{work_item_id[:8]}" if slug else f"kraft/{work_item_id}"
```

and `store.branch_for(row)` returns `row["branch"] or f"kraft/{row['id']}"`.
The three call sites (`builtins.ensure_worktree`, which already reads the row
for `base_ref` and extends that SELECT; `executor._dispatch_task`'s forge
branch; `api._remove_worktree`, whose signature takes the branch instead of
rebuilding it from `wid`) all go through `branch_for`. That answers the bead's
"the two call sites must agree exactly" the only way that cannot drift: they do
not each derive it, they read the one value that was written once.

Constraints, each discharged:

* *Uniqueness* — the `-<id[:8]>` suffix. Two uuid4s sharing an eight-hex prefix
  is not a case worth a collision check; `git worktree add -b` fails loudly if
  it ever happens.
* *Invalid refs* — the charset is `[a-z0-9]` joined by `-`, clipped, with
  leading and trailing `-` stripped after clipping. Every ref rule git enforces
  (`..`, `@{`, trailing `.lock`, leading dot, control characters, spaces) is
  unreachable by construction rather than by a blocklist.
* *Length* — 40 characters of slug, the same shape of clip `mr_title`
  (`forge.py:191`) already applies to titles.
* *In-flight items* — their `branch` is NULL and `branch_for` returns the old
  `kraft/<uuid>`, so their worktree, their open MR and their merge keep
  working. No backfill, no rename of a branch a forge already knows.

The worktree directory stays `~/.kraft/run/worktrees/<uuid>`. It is machine
state, every path that resolves a worktree resolves it from the id
(`_gate_artifact`, the diff endpoint, abandon), and renaming it would buy
legibility in a directory nobody reads at the cost of touching all of them.

## Approaches rejected

* **ko7j: make `retry` inherit the note and stop there** (the bead's one-line
  option). It stops the note being discarded but leaves the route missing —
  retry still restarts at `human_review` and regenerates a brief over an
  unchanged diff. It is A3 without A1/A2, and A3 alone does not open the door.
* **ko7j: keep the gate terminal and put an abandon button on it**
  (Kraft-aayj's shape). Honest, but it makes "the reviewer wants one thing
  changed" cost the whole item. Kraft-aayj stays open for the affordance
  itself.
* **bol: a writable artifact viewer** — `PUT /work-items/{wid}/artifact`, a
  textarea in `ArtifactModal`, the edit committed as the approved plan. This is
  bol's literal ask and it is the better product answer eventually, but it is a
  new write path into a worktree an agent may be running in, a new commit
  author, and a frontend editor — several times the size of everything else
  here, and it does not help ko7j at all. A5 gets most of the token saving for
  one branch in one function. Out of scope, bead stays open.
* **Carrying the rejection note in a file (`.engineering/rejections/<id>.md`)
  rather than in the events table.** A second copy of a fact the append-only
  event log already stores durably, plus a write into the worktree from the API
  process. `store.last_rejection` reads the copy that already exists.
* **xron: parse the CLI's error text for "already merged".** Message-shaped,
  per-CLI, per-locale, and it would still leave `open_mr` blind. Asking for
  state is the same number of calls and answers both.
* **nhps: derive the slug at each call site from the title** — explicitly what
  the bead warns against; two derivations of one string is a branch mismatch
  waiting to happen, and it cannot represent in-flight items whose branch is
  already `kraft/<uuid>`.

## Surfaces that change with the mechanism

* `client.reject_gate(note, gate, work_item_id, node=None)` and
  `POST .../reject` body `{note, node?}`; `kraft item reject --node <node-id>`;
  the MCP `reject_gate` tool gains the same optional argument. One optional
  parameter on the three surfaces that already carry the note.
* `Gate.tsx:24` — `rejectLabel` returns "Reject and stop" for
  `human_review_approval`, which is no longer true. It becomes "Reject and send
  back", with the sub-line naming the target node the item will re-enter at.
* `tests/test_api.py:469`, `test_human_review_reject_stops_the_item`, pins the
  behaviour this spec removes. It is rewritten, not deleted: same walk, now
  asserting the item goes back to `active` at `implementation` with the note as
  the steer.

## Out of scope

* The writable plan editor / inline annotations (Kraft-bol's literal ask) — see
  above; the bead stays open.
* An abandon affordance at a gate (Kraft-aayj).
* Renaming worktree directories, and backfilling `branch` for existing items.
* `retry --node`: with A1–A4 a rejection routes and a retry clears the cap, so
  a second way to choose a restart point has no case left.
* Teaching Kraft about auto-merge/MWPS as a *strategy* (asking the forge to
  merge when the pipeline goes green). B only makes Kraft tolerate someone else
  having done it.
* Detecting a merge that happened by direct push rather than through an MR.
  `find_mr` returns `None` there and the node fails, as it does today.

## How it will be verified

Every test names its bead. `tests/test_gates.py` and `tests/test_api.py` for
the mechanism, `tests/test_forge.py` for the forge, `tests/test_store.py` and
`tests/test_builtins.py` for the branch.

**Kraft-ko7j**

* `test_rejecting_the_final_gate_re_enters_at_implementation` — walk the
  default chain to `human_review_approval` with the fake agent, reject with a
  note, assert the item is `active`, the `gate_rejected` payload carries
  `node: "implementation"`, and the re-run dispatches
  `on.implementation.start` with the note in its instruction.
* `test_a_rejection_note_is_the_default_steer_for_the_next_retry` — reject
  until `<gate>_reject_loop` is exhausted (item → `needs_human`), then `POST
  /retry` with no steer; the `work_item_retried` event carries the last
  rejection's note.
* `test_retry_clears_the_gate_reject_counter` — after that retry, the gate
  re-opens and can be rejected again (A4).
* `test_reject_refuses_a_node_after_its_gate` — `{"node": "merge"}` on
  `plan_approval` is a 400 and nothing is spawned.

**Kraft-bol**

* `test_a_rejected_plan_rerun_is_framed_as_a_revision` — with
  `.engineering/plans/<id>.md` on disk, the re-run's task instruction names
  that path and the word "revise", and does not begin with the bare
  `_STEER_PROMPT`.
* `test_a_steered_node_with_no_artifact_yet_keeps_the_plain_steer_prompt` —
  the branch in A5 fires on the artifact's existence, not on any gate name.
* `test_templates.py::test_reject_to_must_name_an_earlier_node_of_the_same_template`
  — a template with `reject_to: merge` on the `plan` node lands in
  `TemplateSet.invalid`.

**Kraft-xron**

* `test_merge_treats_an_already_merged_mr_as_done` — stubbed `glab` returning
  `[{"iid":54,"state":"merged",...}]`; `run_task(handler="merge")` finishes
  `done`, the log names the MR, and `glab mr merge` is never invoked. Twin for
  `gh` with `"state":"MERGED"`.
* `test_merge_still_fails_on_a_closed_mr` and
  `test_merge_still_fails_when_the_forge_refuses` — the fix must not swallow a
  real refusal.
* `test_open_mr_reuses_an_open_mr_for_the_branch` — `mr create` is not called,
  the description is rewritten, the node is `done`.

**Kraft-nhps**

* `test_branch_name_slugs_the_title_and_suffixes_the_id` — including a
  360-character title, a title of punctuation only (falls back to
  `kraft/<uuid>`), and a clip that would otherwise leave a trailing `-`; every
  output passes `git check-ref-format --branch`.
* `test_an_item_with_no_stored_branch_keeps_its_uuid_branch` — `branch_for` on
  a row with `branch = NULL`.
* `test_the_worktree_and_the_forge_agree_on_the_branch` — end to end through
  `ensure_worktree` and a forge node: the branch git created is the branch the
  forge adapter was handed, and abandon deletes that one.
