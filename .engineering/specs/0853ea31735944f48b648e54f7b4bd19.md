# Problem

`store.create_session` (`src/kraft/store.py:332-360`) writes the literal `1` into the
`attempt` column for every worker session:

```sql
INSERT INTO worker_sessions (..., status, attempt, created_at, exited_at, round)
VALUES (?, ?, ?, ?, NULL, NULL, ?, ?, 'pending', 1, ?, NULL, ?)
```

The function takes no `attempt` parameter, and neither caller
(`builtins.start_session` at `src/kraft/builtins.py:143`,
`adapters.subprocess.run_task` at `src/kraft/adapters/subprocess.py:179`) computes
one. Every re-run of the same node/hook point — a resumed pause, a retry, each
`on.ci.poll` pass of `mr_checks` — gets a fresh row with `attempt = 1`.

The column is served straight to the SPA (`api.py:791-799` selects `*` from
`worker_sessions` and dicts every column), and the SPA reads it as a real counter:

- `frontend/src/components/CurrentNodePanel.tsx:32` renders `attempt ${s.attempt}` —
  observed on `b63d95be41884b6e83a423c114a97ce3`, where `mr_checks` ran `on.ci.poll`
  three times and all three rows read "attempt 1".
- `frontend/src/components/PausedCard.tsx:25` computes the *next* attempt as
  `paused[0].attempt + 1`, so "relaunches … as attempt 2" is the only sentence that
  card can ever produce.

There is a second, narrower leak on the live path. The `worker_session_created` and
`worker_session_started` events (`store.py:353-360`, `store.py:387-397`) carry
`node_id`, `hook_point` and `round` but not `attempt`, so `store.ts:128-152` builds the
row from `blankSession`, whose `attempt` is a hardcoded `1` (`frontend/src/store.ts:275`).
Even with the DB fixed, a live board would show "attempt 1" until the next hydrate.

# Approach

Compute the attempt in the INSERT itself, scoped to
`(work_item_id, node_id, hook_point)` — the same scope `PausedCard` and
`CurrentNodePanel` already assume:

```sql
INSERT INTO worker_sessions (...)
VALUES (?, ?, ?, ?, NULL, NULL, ?, ?, 'pending',
        (SELECT COUNT(*) + 1 FROM worker_sessions
          WHERE work_item_id = ? AND node_id = ? AND hook_point = ?),
        ?, NULL, ?)
```

`create_session`'s signature is unchanged: no caller has better information than the
table does, and adding an `attempt=` parameter would mean two callers each
re-implementing the same count. All writes go through `Database.write`, which
serialises them on one connection, so the read-then-insert is not racy.

`COUNT(*) + 1` over `MAX(attempt) + 1`: nothing deletes from `worker_sessions` in
production code (the only `DELETE FROM worker_sessions` in the tree is
`tests/test_resume.py:122`, simulating a lost row), so the two agree, and the count
is the definition the bead and the UI state.

Three pieces follow from it:

1. **The events.** Add `attempt` to the `worker_session_created` payload (read back
   from the row just inserted, in the same `create_session` call) and to
   `worker_session_started` — `session_running` already does a `SELECT node_id,
   hook_point, round`, so `attempt` joins that select list. In the SPA, both cases in
   `store.ts` take `attempt: p.attempt ?? 1`, matching the existing `round: p.round ?? 0`
   idiom.
2. **A backfill migration**, `_MIGRATIONS[13]`, with `SCHEMA_VERSION` bumped to 14. Data
   only, no schema change:

   ```sql
   UPDATE worker_sessions SET attempt = (
     SELECT COUNT(*) FROM worker_sessions p
      WHERE p.work_item_id = worker_sessions.work_item_id
        AND p.node_id      = worker_sessions.node_id
        AND p.hook_point   = worker_sessions.hook_point
        AND (p.created_at, p.id) <= (worker_sessions.created_at, worker_sessions.id))
   ```

   Without it every historical row keeps `attempt = 1` and the already-observed items
   stay wrong for the life of the database. The `(created_at, id)` row-value comparison
   breaks the tie when two rows share a timestamp, so the numbering has no duplicates
   and no gaps.
3. **Nothing else.** `mark_sessions_capped_out`, `sessions_for_round`, the fix-loop
   round accounting and the loop caps (`policy.LoopCap.attempts`, a separate counter on
   `loop_state`) all key off `round`/`status` and never read `attempt`.

## Rejected

- **Pass `attempt` in from the callers.** Both callers would have to run the same query
  first; two call sites, one truth, and a third caller added later gets it wrong.
- **Drop the column and derive `attempt` in the API or the SPA.** Larger diff for the
  same number: the API would need a window function over the session list, and the
  live-event path would still have nothing to show until a hydrate.
- **Scope the count to `(work_item_id, node_id)`, ignoring the hook point.** A node
  runs more than one hook point — `verify` runs `on.test.run` and
  `on.implementation.start` — and lumping them makes `CurrentNodePanel`'s per-row
  "attempt N" jump by the sibling's count.
- **Backfill with `ROW_NUMBER() OVER (...)`.** Needs the 12-step table rebuild to write
  the result back in SQLite; the correlated `COUNT(*)` is one statement on a table of
  this size.

# Out of scope

- The `attempt` semantics across a `kraft item retry`: the counter keeps climbing over
  the item's whole life rather than resetting per chain run. That is what "attempt N of
  this node" should mean, and no UI shows it otherwise.
- Any index for the new subquery. `worker_sessions` carries only
  `idx_worker_sessions_status`; the count runs once per session launch on a table with
  tens of rows per work item. Add one when a profile says so.
- `PausedCard`'s `paused[0].attempt + 1` arithmetic and `CurrentNodePanel`'s copy: both
  become correct once the value is, and neither changes.
- The fix-loop's `round` column and the loop-cap counters.

# Verification

Backend (`tests/test_store.py`, `tests/test_db.py`):

- `test_create_session_numbers_attempts_per_hook_point` — three sessions on the same
  `(w1, verify, on.test.run)` come back `attempt` 1, 2, 3.
- `test_create_session_attempts_are_scoped_to_node_and_hook_point` — a session on
  `(w1, verify, on.implementation.start)` and one on `(w2, verify, on.test.run)` are
  each `attempt = 1` while `(w1, verify, on.test.run)` is on its third.
- `test_worker_session_events_carry_the_attempt` — the `worker_session_created` payload
  of the second session has `attempt == 2`, and `session_running` puts the same number
  on `worker_session_started`.
- `test_migration_13_backfills_worker_session_attempts` — open a v12 database, insert
  three sessions on one `(work_item, node, hook_point)` and one on another, run
  `migrate`, assert `1, 2, 3` and `1`, following the existing migration-test shape in
  `tests/test_db.py`.

Frontend (`frontend/src/store.test.ts`):

- `worker_session_created carries the attempt` — an event with `attempt: 3` produces a
  row reading 3, and one without the field still reads 1.

`frontend/src/components/PausedCard.test.tsx:21` ("as attempt 2" from a fixture with
`attempt: 1`) and `CurrentNodePanel.test.tsx` stay as they are — they already pin the
arithmetic this change feeds.
