# Problem

All three bugs live in `src/kraft/adapters/forge.py`, in the `merge`/`ci_poll`
forge handlers dispatched by `_run_one` (default chain: `open_mr` → `mr_checks`
(`on.ci.poll`) → `human_review` (gate) → `mr_sync` (`on.mr.sync`) → `merge`
(`on.merge`), `templates/default.yaml:22-49`).

## Kraft-266b / Kraft-x10m: the merge node trusts a pipeline result that predates the head it merges

`mr_checks` runs `ci_poll`, which pushes and polls CI to green for the branch's
*then*-current head (`_run_one`, `case "ci_poll"`, forge.py:902-933). `human_review`
runs after it, as an ordinary agent-kind node: it gets the same "commit everything
you change before you exit" contract every worker gets
(`adapters/agent.py:43-48`), and its `review-brief` skill writes and commits
`.engineering/review_briefs/<id>.md` — a new commit, local only at that point.
`mr_sync` runs after the gate specifically so this commit (and anything a person
committed while reviewing) reaches origin before merge
(forge.py:40-43, "the merged head includes the brief commit and anything the
human committed while reviewing"). Its handler (`case "sync_mr"`, forge.py:934-944)
pushes unconditionally.

That push is the bug's trigger: it can move the branch's head past the SHA
`mr_checks` validated. On a project that requires a green pipeline before merge,
the new head has no pipeline yet — GitLab re-evaluates `detailed_merge_status`
for the new SHA, and `glab mr merge --yes` either refuses outright or (the
already-known Kraft-79x3 shape) schedules "merge when pipeline succeeds" for a
pipeline `mr_checks` never watched. Either way `on.merge` meets a result nothing
upstream validated (Kraft-266b).

The `merge` node's own read-back (`_poll_merged`, forge.py:825-848) waits
`MERGE_VERIFY_TIMEOUT` — 300s, deliberately short, on the stated assumption that
"the pipeline was already green at mr_checks, so a merge that has not landed by
now is waiting on something a person has to see" (forge.py:32-38). Once
`mr_sync`'s push can re-arm the pipeline requirement, that assumption is false:
the wait is for a pipeline that may take as long as any other pipeline in this
repo, up to `DEFAULT_POLL_TIMEOUT` (1800s) — six times the window `merge` gives
it (Kraft-x10m). `test_merge_fails_when_the_mr_is_still_open_afterwards`
(`tests/test_forge.py:1312`) already covers the case this 300s window is
*correctly* sized for (an already-green pipeline, `mr merge` lied about
landing); there is no coverage for a pipeline recreated after `mr_checks`.

## Kraft-v6ci: `_merge_state` errors instead of reading an out-of-band merge

`GlabCli._merge_state` (forge.py:482-494) runs `glab mr view -F json` and reads
`detailed_merge_status`/`merge_status` for `ci_status`'s conflict check
(Kraft-ejj9). If the merge request is merged out-of-band — a person merges it
in the GitLab UI while `mr_checks` is still polling — the lookup either errors
(the reported symptom) or, in the shape captured by `GLAB_MR_VIEW`/
`GLAB_MR_VIEW_CONFLICT` (`tests/test_forge.py:52-89`), comes back with
`"state":"merged"` and no `merge_status`/`detailed_merge_status` describing that
as a conflict. `_mergeable()` (forge.py:425-444) has no vocabulary for
`"merged"` in either `_MERGEABLE` or `_UNMERGEABLE`, so a bare `"merged"` state
falls through as `None` (undecided) at best, or the underlying CLI call raises
`ForgeError` (propagated through `ci_status` → `_poll_ci` → the `ci_poll`
handler → the outer `except ForgeError` in `run_task`) at worst — `mr_checks`
fails a node for a branch that already landed, needlessly stopping the chain.

# Approach

## Kraft-266b / Kraft-x10m: give `merge` its own CI gate, reusing `mr_checks`' wait budget

Before `merge` calls `forge.merge()`, it polls CI to a result the same way
`ci_poll` does — same `_poll_ci`, same `poll_timeout`/`poll_interval` (already
threaded into `run_task` for every forge node, `executor.py:567-568`, defaulting
to `DEFAULT_POLL_TIMEOUT`/`DEFAULT_POLL_INTERVAL` when a registry entry doesn't
override them, which `on.merge`'s entry in `templates/registry.yaml:22` does
not). Extract the shared "poll, then render the log line and the
mergeable/red-pipeline verdict" logic out of the `ci_poll` case into one
function, `_wait_for_ci`, and call it from both `case "ci_poll"` and the
`existing.state == "open"` branch of `case "merge"`. If it reports not-ok, the
node fails on that log — a red or still-pending pipeline, or a conflict — and
`forge.merge()` is never called. If it reports ok, `merge` proceeds exactly as
today: call `forge.merge()`, then `_poll_merged` with the existing
`MERGE_VERIFY_TIMEOUT`/`MERGE_VERIFY_INTERVAL`. That 300s window's original
assumption — the head about to be merged already has a validated green
pipeline — is restored, because `merge` itself is now what most recently
validated it, not a `mr_checks` result three nodes and one push old. Update the
comment at forge.py:32-38 to say so.

When nothing changed since `mr_checks` (the ordinary case — `human_review`
approved with no new commit, or a project with no required-pipeline rule), this
costs one extra `ci_status` round trip that returns immediately: `_poll_ci`'s
first check already short-circuits on a non-pending result, no sleep involved.

Rejected:

- **Move `mr_sync`'s push earlier, before `mr_checks`, so nothing lands after
  the pipeline is validated.** `mr_sync` runs after the gate on purpose — a
  merged head has to include the review brief and anything a human committed
  while reviewing (forge.py:40-43). Moving it earlier drops that guarantee to
  fix a different node; a bigger, riskier chain-topology change for what is a
  bug in `merge`'s own assumption.
- **Just raise `MERGE_VERIFY_TIMEOUT`.** Doesn't fix Kraft-266b (`merge` would
  still call `forge.merge()` against a head nothing has validated, and still
  fail loudly on a project that refuses the command outright rather than
  scheduling an async merge) — it only makes the Kraft-x10m symptom slower to
  surface, and blurs the two waits the existing docstring is explicit about
  keeping separate: "waiting for CI" and "waiting for the forge's own merge
  machinery," which have different natural durations.
- **Track the SHA (or pipeline id) `mr_checks` validated and only re-check CI
  in `merge` when the head has moved.** Extra state to persist and thread
  across nodes/sessions for a check that costs nothing extra when it isn't
  needed (`_poll_ci`'s first read is a single round trip either way) — YAGNI.

## Kraft-v6ci: read `state: "merged"`, don't let it surface as an error

`GlabCli._merge_state` gains a `branch` parameter (`ci_status` already has one
to pass through) and two changes:

1. When `glab mr view -F json` succeeds, check `data.get("state")` first: if
   it's `"merged"`, return the sentinel `"merged"` regardless of what
   `merge_status`/`detailed_merge_status` say (a merged MR may not carry either).
2. When the call itself raises `ForgeError` (the reported failure mode — the
   branch resolves to nothing when GitLab is asked for its current view, e.g.
   because the state changed under it), fall back to `find_mr`, the same
   `--all` lookup `merge`'s own "already merged" shortcut already trusts
   (Kraft-xron, `_run_one`'s `case "merge"`, forge.py:952-955). If that says
   `state == "merged"`, return `"merged"` too. Otherwise re-raise — a `glab`
   that is genuinely unreachable, or a real auth failure, must still fail the
   node loudly rather than being read as "someone merged it."

`GlabCli.ci_status` checks for that sentinel before doing anything else: on
`"merged"`, return `CIStatus(state="success", url="", jobs=("merge request
already merged",), mergeable=True, merge_detail="merged")` without calling
`glab ci list` (a deleted source branch's pipeline list is not a fact this node
needs once the MR has already landed). `_run_one`'s `case "ci_poll"` already
treats `state == "success"` as `status = "done"` — no handler change needed
there.

Rejected:

- **Catch any `ForgeError` from `_merge_state` and assume merged.** Would turn
  a real outage or auth failure into a false "done," hiding real breakage from
  the human_review gate that follows. The fallback must confirm via `find_mr`,
  not guess from the shape of the failure.
- **Fix this in `GhCli` too.** The ticket and the reported symptom name
  `_merge_state`, a `GlabCli`-only method — `GhCli.ci_status` reads
  `mergeable`/`mergeStateStatus` off one `gh pr view` call with no separate
  branch-scoped lookup to fail the same way. Left alone; file a follow-up if
  the same symptom is ever seen against GitHub.

# Out of scope

- What happens to `human_review`/`mr_sync` when a branch is merged out-of-band
  mid-chain (the gate reviewing, or the sync pushing to, a branch already on
  `main`). Kraft-v6ci is scoped to `_merge_state` not erroring; the rest of
  that race is pre-existing and untouched.
- The narrow window between `merge`'s own top-of-handler `find_mr` check and
  the new CI gate/merge call, where an out-of-band merge could land in between.
  Same class of race Kraft-xron already narrows, not widens or fixed further
  here.
- Any change to `MERGE_VERIFY_TIMEOUT`/`MERGE_VERIFY_INTERVAL`'s values, or to
  making them registry-tunable — untouched, and still not asked for.

# Verification

New tests in `tests/test_forge.py`, alongside the existing `ci_poll`/`merge`
coverage:

- `merge` waits out a pipeline recreated after `mr_checks` (`FakeForge` with
  `ci_states=["pending", "pending", "success"]`, `poll_interval=0`, run through
  the `"merge"` handler directly): asserts the node ends `done` and
  `fake.merged == [1]` — proving `merge` now polls rather than either failing
  immediately or racing the old 300s window.
- `merge` fails fast, without calling `forge.merge()`, when the CI gate reports
  unmergeable (`mergeable=False, merge_detail="conflict"`): asserts `status ==
  "failed"`, `"not mergeable: conflict"` in the log, and `fake.merged == []`.
- `merge` times out on a pipeline that never settles, using `poll_timeout`
  rather than `merge_timeout` (`ci_states=["pending"]`, `poll_timeout=0`):
  asserts `status == "failed"`, the log names the timeout, and `fake.merged ==
  []`.
- The existing `test_merge_is_done_only_when_the_forge_reports_merged`,
  `test_merge_pushes_before_it_merges`, `test_merge_fails_when_the_mr_is_still_
  open_afterwards`, `test_merge_treats_an_already_merged_mr_as_done`, and
  `test_merge_fails_when_the_mr_was_closed_rather_than_merged` continue to pass
  unmodified — they run against `FakeForge`'s default `ci_states=["success"]`,
  so the new CI gate resolves on its first, non-sleeping check.
- `GlabCli._merge_state`/`ci_status` reads `"state":"merged"` from a successful
  `glab mr view -F json` without erroring, and returns a `CIStatus` with
  `state="success"`, `mergeable=True`.
- `GlabCli._merge_state` falls back to `find_mr` and reads `"merged"` when
  `glab mr view -F json` itself raises `ForgeError` for a branch whose MR
  `find_mr` reports merged.
- `GlabCli._merge_state` still raises when `glab mr view -F json` fails and
  `find_mr` reports no MR (or a non-merged one) for the branch — the fallback
  must not swallow a genuine failure.

`just test -k test_forge` covers all of the above alongside the existing suite.
