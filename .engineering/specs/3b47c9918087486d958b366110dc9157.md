# Work item detail page is unreadable

The screen a human uses to approve or reject a gate. Six defects, two of which
corrupt the decision rather than slow it down.

## The problem, per bead

### Kraft-nceo — the diff mixes the chain's own committed docs into the change

`GET /work-items/{wid}/diff` (`src/kraft/api.py:1055`) calls
`review.read_change(worktree, base)` (`src/kraft/review.py:38`), which runs
`git diff <base>` — the working tree against `base_ref`. That single range folds
together two things a reviewer must keep apart:

- what earlier nodes **committed** (`spec` commits `.engineering/specs/…`,
  `plan` commits `.engineering/plans/…`, `env_setup` commits attachments), and
- what the current node has **written but not committed** — the change actually
  under review.

Measured on `f98af3e59e704ed69ad1064ed48acf59`: 1042 lines of plan doc plus 333
of spec doc ahead of the 531-line code change. `DiffModal`'s open-budget
(`MAX_OPEN_LINES = 600`, `frontend/src/components/DiffModal.tsx:32`) is spent on
docs before the code is reached, so the code arrives collapsed and the reviewer
scrolls past the chain's own paperwork to find the change.

The split is already in git and costs one extra read:

```
base_ref..HEAD   landed   — what earlier nodes finished and committed
HEAD..worktree   in-flight — what the current node is doing right now
```

### Kraft-yytk — no way to read the session summary before approve/reject

`human_review`'s task is `on.human_review.requested`, bound in
`templates/registry.yaml:18` to `skill: review-brief, artifact: review_brief`.
The skill writes the one page a human is meant to read before merging (CI
result, local findings including the minor ones, what was left out, what the
agent is unsure of). `_gate_artifact` (`src/kraft/api.py:735`) resolves it, the
detail payload carries it as `gate_artifact`, and
`GET /work-items/{wid}/artifact` serves it.

The UI throws it away. `WorkItemDetail.tsx` (~line 395):

```tsx
artifact={
  gate === "human_review_approval" ? (
    <button …>Review changes</button>          // diff — always this branch
  ) : item.gate_artifact ? (
    <button …>{gate === "spec_approval" ? "Review spec" : "Review plan"}</button>
  ) : undefined
}
```

`human_review_approval` short-circuits to the diff, so the brief that the
`review-brief` skill spent a session writing has no button anywhere. The reviewer
approves the last gate before merge with the raw diff as their only evidence.
Every other gate shows its artifact; this one — the one that matters most —
does not.

The bead calls it "the session summary". The artifact bound to that node is the
**review brief**; that is the evidence the gate is about, and it is what this
change surfaces. Session summaries for every node remain reachable through the
Documents tab (`LinkedDocuments`, ingested via `index/service.ingest_session_summary`).

### Kraft-39un — markdown tables render as raw pipes

**Already fixed.** Commit `2bd5d59` ("Readable merge records: branch slugs and
GFM tables") added `remark-gfm@^4.0.1` to `frontend/package.json` and passes
`remarkPlugins={[remarkGfm]}` in both renderers
(`DocumentModal.tsx:203`, `ArtifactModal.tsx:49`). Those are the only two
`react-markdown` call sites in the frontend (`grep -rn react-markdown frontend/src`),
and both already have a regression test:

- `DocumentModal.test.tsx:98` — "renders a GFM pipe table as an actual table, not a paragraph of pipes"
- `ArtifactModal.test.tsx:26` — "renders a GFM pipe table as a table"

No code change. The implementation node verifies those two tests still pass and
that no third markdown renderer has appeared; if one has, it gets the plugin and
a test. Nothing is invented to satisfy "a test per bead" — the tests exist.

### Kraft-n9gw — Tasks tab is scoped to the current node, always one row

`CurrentNodePanel` filters `sessions.filter(s => s.node_id === item.current_node_id)`.
Almost every node runs one task, so the tab is one row; between nodes
`current_node_id` names a node with no sessions yet and the tab reads "no tasks
running on this node". The detail payload already carries **every**
`worker_session` with `node_id`, `hook_point`, `status`, `attempt`, `round`,
`tokens_in/out`, `cost_usd`, `wall_ms`, `model` (`frontend/src/types.ts:103`).
Nothing is missing from the API; the component discards it.

### Kraft-zxu4 — Timeline shows raw event types

`EventTimeline.tsx` renders `<span className="etype">{e.type}</span>` and
`detailOf()` returns `null` for every `worker_session_*` event unless it carries
`concerns`. A verify node reads as eight identical grey rows:

```
worker_session_created  {session_id: 560b…, hook_point: on.test.run, round: 0}
worker_session_created  {session_id: 451d…, hook_point: on.review.local.run, round: 0}
worker_session_started  {session_id: 560b…, hook_point: on.test.run, pid: 41952}
worker_session_exited   {session_id: 451d…, status: done, wall_ms: 6}
worker_session_exited   {session_id: 560b…, status: done, wall_ms: 272309}
findings_measured       {node_id: verify, cycle: 0, findings: []}
```

Nothing says which task is which, that one ran 4m32s and the other 6ms, that
both passed, or that findings came back empty. `hook_point` is in the
created/started payloads and never rendered; `worker_session_exited` carries no
`hook_point` at all, so an exit row cannot name itself without a join.

### Kraft-d2sq — no link to the MR from the MR-related nodes

`forge.run_task`'s `open_mr` case (`src/kraft/adapters/forge.py:843`) has the URL
— `MR(number=int(data["iid"]), url=str(data["web_url"]))`, `forge.py:411` — and
writes it into the **session log text** and nowhere else:

```python
log, status = f"opened {mr.url}\n", "done"
…
log, status = f"reusing !{existing.number}: {existing.url}\n", "done"
```

Traced the write path as the bead asked: it is not on the work item row, not in
an event, not in the session result. **Persisting it is in scope.** Past
`open_mr` there is no way to reach the MR but to open the forge and search for
the branch.

## The approach

### 1. nceo — two ranges from `read_change`, two sections in `DiffModal`

Give `read_change` an optional `head`:

```python
def read_change(
    worktree: Path, base: str, *, head: str | None = None, context: int | None = None
) -> Change | None:
    diff_args = [
        "diff",
        *([f"-U{context}"] if context is not None else []),
        base,
        *([head] if head else []),
    ]
```

`git status --porcelain` is only meaningful for the working tree, so `untracked`
is `[]` when `head` is set.

`get_work_item_diff` then makes two calls:

| call | range | meaning |
|---|---|---|
| `read_change(worktree, base, head="HEAD")` | `base..HEAD` | landed — committed by earlier nodes |
| `read_change(worktree, "HEAD")` | `HEAD`..worktree | in-flight — the change under review |

Response shape: the existing top-level `files` / `diff` / `untracked` /
`truncated` become **in-flight**, and a new `landed` object carries
`{commits, files, diff, truncated}`. `base_ref`, `diff_max_bytes` and
`worktree_path` are unchanged.

Top-level is redefined rather than kept as the combined diff and a third field
added: the combined diff is exactly the thing that is wrong, and shipping it
alongside would double a payload already capped at `DIFF_MAX_BYTES`. Each of the
two diffs is truncated against `DIFF_MAX_BYTES` independently with its own
`truncated` flag — the in-flight change gets the full budget it deserves, and
the landed docs, which arrive collapsed, get their own.

Degrades correctly: if `implementation` starts committing mid-run, its commits
join `landed` and the in-flight section shows only what is still uncommitted. On
a fresh worktree with no commits, `landed` is empty and the page looks exactly as
it does today.

`DiffModal` renders in-flight first, expanded, with the existing per-file
collapse budget applied to it alone; then a `Landed` section — `N commits
already on this branch` — with every file collapsed. The `rows` `useMemo` is
extracted into a plain `rowsOf(diff, files, untracked, truncated, allClosed)`
helper and called twice; no new component. The header totals stay the in-flight
totals, because that is what the reviewer is deciding about, with the landed
counts on a second line.

`write_package` is **not** changed. The review agent is handed the same combined
`base..working tree` package it gets today, deliberately: an agent reading a
file has no collapse to be defeated by, and changing what a reviewer agent sees
is a different decision from changing what a human sees.

`render.diff_stat` / `render.diff_body` (`src/kraft/render.py:247`) are updated
so `kraft view diff` prints the landed section under a header ahead of the
in-flight one. Not doing this would silently drop committed work from the CLI —
the same class of bug as nceo, from the other side.

Rejected:
- **A per-node attribution table with a snapshot sha per node.** More storage,
  a migration, and a new failure mode, for a distinction git already draws for
  free.
- **Path-based filtering — hide `.engineering/**` from the diff.** Hides real
  changes when the work item's subject *is* a doc, and treats the symptom
  (docs are noisy) instead of the cause (two ranges shown as one).
- **Filter client-side in `DiffModal` by commit membership.** The browser does
  not know which chunk came from which commit; only git does.

### 2. yytk — both buttons at `human_review_approval`

Replace the short-circuit with: at `human_review_approval`, render **Review brief**
(→ `ArtifactModal`, when `item.gate_artifact` is set) *and* **Review changes**
(→ `DiffModal`). Both, not one — the bead's first option. The brief is the
agent's argument; the diff is the evidence; a reviewer needs to check one
against the other.

The artifact label is currently a two-way ternary on `gate`; it becomes a small
`Record<string, string>` beside `PROMPTS` in `Gate.tsx`
(`spec_approval → "Review spec"`, `plan_approval → "Review plan"`,
`chain_finalized → "Review chain"`, `human_review_approval → "Review brief"`)
with a `"Review document"` fallback, so a new artifact-carrying gate is not a
new branch.

When `gate_artifact` is null — the agent reported done without honouring the
contract, which `agent.py:259`'s `post_resolve` already turns into a failed
node, so this is rare — only "Review changes" renders. The gate stays answerable.

The `!== "human_review_approval"` guard on the standalone "Review changes"
control row below the gate card stays: the button now lives on the gate card at
that gate, so duplicating it is noise.

Rejected:
- **One combined modal, brief above diff.** The brief is markdown and the diff
  is monospace with its own collapse state; one scroll container fighting two
  renderers is how the current page got unreadable.
- **Surfacing the raw session summary from `.engineering/sessions/` instead.**
  It is the worker's log of its own run, not the artifact the gate is bound to,
  and it is already one click away in the Documents tab.

### 3. n9gw — Tasks tab shows every session, grouped by node in chain order

`CurrentNodePanel` (name kept; it is no longer only the current node, but a
rename is churn across imports and tests for no reader benefit — the component's
docstring is updated to say what it now shows) groups all sessions by `node_id`,
ordered by `item.chain_definition.nodes`, with any node not in the chain
appended in first-seen order. One `<details>` per node — the current node
`open`, the rest closed — the same zero-state `<details>` interaction
`DiffModal` already uses.

Each row keeps its `StatusGlyph` / `hook_point` / attempt / `RowState` /
`view log`, and gains a metrics line built from the helpers that already exist:
`tokens(tokens_in + tokens_out)`, `usd(cost_usd)`, `elapsed(wall_ms)`
(`frontend/src/format.ts`), each omitted when null. This puts per-node usage
where the numbers actually are, and makes `view log` reachable for finished
nodes — today a finished node's log is unreachable from this tab.

The tab count in `WorkItemDetail`'s `Tabs` changes from `nodeSessions.length` to
`sessions.length` to match what the tab shows. `usageLine`'s task count stays
scoped to the current node: it sits on the *control row*, next to "running 6s",
and is a statement about now.

Rejected:
- **A flat, ungrouped list of every session.** On a fixed-up item that is a
  dozen rows with no structure; the node is the unit a reader thinks in.
- **A new "All tasks" tab beside the existing one.** Two tabs where one is
  always a subset of the other.

### 4. zxu4 — name the task, show the outcome

Three fixes in `EventTimeline.tsx`, all client-side. `EventTimeline` takes a new
`sessions: WorkerSession[]` prop (`WorkItemDetail` already has them in hand) and
builds a `Map<session_id, hook_point>`.

1. **Title.** A row whose payload has `hook_point`, or whose `session_id`
   resolves through the map, is titled `"<hook_point> <verb>"` — `created`,
   `started`, `exited` — with `e.type` demoted to the muted `.etype` position it
   occupies now. Everything else keeps `e.type` as the title, so an unknown
   event type never renders blank.
2. **The unnamed exit.** `worker_session_exited` carries only
   `session_id`/`status`/`wall_ms`. Resolved client-side through the map rather
   than by widening `store.session_exited`'s payload: the sessions are already
   in the detail payload, and adding a field to the event fixes only events
   written after the change while leaving every existing item unreadable. If the
   map misses (a session pruned from the payload), the row falls back to the raw
   type — the behaviour today.
3. **The outcome.** `detailOf` gains: `worker_session_exited` →
   `"<status> · <elapsed(wall_ms)>"` (keeping the existing `concerns` text after
   it when present), and `findings_measured` → `"<n> findings"` / `"no findings"`.
   A `done` and a `failed` exit stop looking identical, and the 6ms
   noop-handler exit becomes visible for what it is.

Split with n9gw: **Tasks answers "what ran and what did it cost"**, **Timeline
answers "what happened, in order"**. Timeline gets no token or cost columns.

Rejected:
- **A human-readable label table for all ~20 event types.** A table that goes
  stale the first time an event is added, to solve a problem that is really "the
  payload is not rendered".
- **Adding `hook_point` and `node_id` to the `worker_session_exited` payload.**
  Fixes only future events; leaves every item already in the database unreadable.

### 5. d2sq — persist the MR, then link it

Backend: `forge.run_task`'s `open_mr` case appends an event on both paths — the
create and the reuse:

```python
await db.write(
    lambda c: events.append(c, work_item_id, "mr_opened", {"number": mr.number, "url": mr.url})
)
```

An event, not a work-item column: no migration, it is already replicated to the
UI by the existing event stream and `hydrateItem`, and it is timestamped, which
a column is not. The reuse path emits it too, so an item whose `open_mr` is
re-entered after a rejected review still has a current record.

Frontend: `WorkItemDetail` scans `events` for the last `mr_opened` and, when one
exists, renders `!<number>` as an external link in the `detail-meta` header
beside the repo and chain name — `target="_blank" rel="noreferrer"`.

Keyed on the event existing rather than on
`current_node_id ∈ {open_mr, mr_checks, human_review, merge}` as the bead
proposed: the link is correct exactly when an MR exists, it survives a
rejection walking the item back to `implementation`, and it is one condition
instead of a set to keep in step with the chain template. Deliberate deviation
from the bead's wording, same intent.

Items whose `open_mr` ran before this change have no event and show no link. Not
backfilled: `find_mr` would have to be called per work item from the API, and
the link reappears on the next `open_mr` or `sync_mr` run.

Rejected:
- **A `mr_url` column on `work_items`.** A migration for something an event
  records better.
- **Deriving the URL from repo remote + branch.** Guesses a forge's URL scheme;
  the forge already told us the real one.

## Out of scope

- **`write_package` / the review agent's package.** Unchanged; see §1.
- **Any change to `remark-gfm`** — already shipped in `2bd5d59` (§Kraft-39un).
- **The board (`Board.tsx`), Analytics, Settings.** Detail page only.
- **Backfilling `mr_opened` for existing work items.**
- **New backend fields for `n9gw`, `zxu4` or `d2sq`'s UI** beyond the one
  `mr_opened` event — everything else is already in the detail payload.
- **Renaming `CurrentNodePanel`.**
- **Per-file collapse in `DiffModal`** — already present
  (`MAX_FILE_LINES` / `MAX_OPEN_LINES`); nceo rides on it.
- **`usageLine`'s task count** — stays current-node scoped (§3).
- **Kraft-ri1y** (the `on.review.local.run` noop handler). zxu4 makes the 6ms
  noop *visible*; fixing the handler is a different work item.

## How it will be verified

One test per bead, plus the CLI regression the diff split implies.

**Backend — `tests/test_diff_api.py`** (extends the existing module; its
`_make_client` harness and `make_repo` support already build a real git
worktree):

- `test_diff_splits_landed_commits_from_in_flight_work` — commit a doc in the
  worktree, then write an uncommitted code file. Assert the top-level `diff`
  contains the code file and **not** the doc, and `landed.diff` contains the doc
  and **not** the code file; assert `landed.commits` names the commit.
- `test_diff_landed_is_empty_when_nothing_is_committed` — a worktree at
  `base_ref` with only uncommitted work returns `landed.files == []`,
  `landed.diff == ""`, and the in-flight side unchanged from today.
- `test_diff_landed_and_in_flight_truncate_independently` — each side over
  `DIFF_MAX_BYTES` carries its own `truncated: true`.

**Backend — `tests/test_review_package.py`**:
