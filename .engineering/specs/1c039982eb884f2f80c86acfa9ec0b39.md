# The problem

`templates/registry.yaml` binds four hooks to a hardcoded backend:

```yaml
on.mr.open:  { kind: forge, handler: open_mr, backend: glab }
on.ci.poll:  { kind: forge, handler: ci_poll, backend: glab }
on.mr.sync:  { kind: forge, handler: sync_mr, backend: glab }
on.merge:    { kind: forge, handler: merge,   backend: glab }
```

`glab` because *this* repo's origin is gitlab.com. `executor._dispatch`
(`src/kraft/executor.py:374`) passes `binding["backend"]` straight to
`adapters.forge.run_task`, which calls `forge.resolve(name)` and gets a
`GlabCli`. On a GitHub repo the first back-half node runs `glab mr create`,
`_run` raises `ForgeError`, and the item lands in `needs_human` — every time,
for every item. `templates/` is seeded once and never overwritten
(`cli.seed_home`), so a user who installs today keeps that binding forever
unless they find and edit the file.

The hardcoding is not just wrong for GitHub: it is wrong for any install with
repos on both forges, because the registry is per-install and the forge is a
property of the repo. One backend name in one file cannot be right for
`kraft repo connect` twice.

The answer is already in the repo and unused. `config.probe_repo`
(`src/kraft/config.py:202`) reads origin and returns `forge: "gitlab" | "github"
| None`; `POST /repos` stores it on the repo's `repos.yaml` entry
(`src/kraft/api.py:1714`), `PATCH /repos` lets a human correct it, Settings
shows it ("no forge remote detected", `frontend/src/views/Settings.tsx:229`),
and `_FORGES` already documents that self-hosted hosts are "set by hand in
repos.yaml instead". Nothing reads that field. Meanwhile `executor._dispatch`
already holds the repo entry as `launch.repo_entry` and passes it to agent
dispatches only.

# The approach

Ship `backend: auto` in the four forge bindings, and resolve `auto` at dispatch
against the repo entry's existing `forge` field.

Four small pieces:

1. **`templates/registry.yaml`** — the four bindings become `backend: auto`,
   and the comment about "changing these three lines is the whole migration"
   goes away: after the v0.1.0 split the shipped file needs no migration at all.

2. **`templates.py`** — `"auto"` joins `_FORGE_BACKENDS`. The comment tying that
   set to `forge.resolve` stays accurate: `resolve` never sees `auto`.

3. **`adapters/forge.py`** — one map and one function:

   ```python
   #: repos.yaml's `forge` (config._FORGES) -> the CLI that talks to it.
   _FORGE_CLI = {"gitlab": "glab", "github": "gh"}


   def backend_for(backend: str, repo_forge: str | None) -> str:
       """`auto` means the forge recorded for this repo; any other name is itself."""
   ```

   `backend_for("auto", None)` raises `ForgeError` naming the fix: no forge is
   recorded for this repo, set `forge: gitlab` or `forge: github` on it in
   Settings → Repos (or `repos.yaml`), or pin a `backend:` in `registry.yaml`.
   That is the self-hosted GitLab / GitHub Enterprise path, and it is the same
   escape hatch `config._FORGES` already documents.

   `run_task` grows a `repo_forge: str | None = None` parameter and moves its
   `forge = resolve(backend)` line *inside* the existing `try`, becoming
   `forge = resolve(backend_for(backend, repo_forge))`. The move is load-bearing:
   resolution can now fail at runtime, and outside the `try` that exception
   escapes past `finish_session`, leaving a started session row with no result
   and no log. Inside, an unresolvable backend is a failed node with a readable
   line in the log — the same shape as any other `ForgeError`.

   `resolve(name)` itself is untouched, so
   `monkeypatch.setattr(forge, "resolve", lambda name: fake)`, which every
   executor-level forge test uses, keeps working.

4. **`executor.py`** — the forge branch of `_dispatch` adds one argument:

   ```text
   repo_forge=(launch.repo_entry or {}).get("forge") if launch else None,
   ```

   Every path that reaches a forge node already threads `launch`
   (`api.py:160,544,1071,1149,1288,1351`, `intake.py:162`), so there is no path
   where the entry is silently missing for a reason other than "not connected"
   or "`repos.yaml` is malformed" — both of which `_launch` already logs and both
   of which land on the error message above.

## Why this and not the bead's three options

- **Resolve at intake and store on the work item** (bead option 1): a new
  `work_items` column, a migration, and a second copy of an answer `repos.yaml`
  already holds — which then goes stale for in-flight items if a repo moves
  forge. The work item does not need to remember it; the repo entry is read at
  dispatch for free.
- **Ship `builtin: noop`, make the forge bindings opt-in** (option 2): gives
  every new user a chain that reports "done" without opening anything, and
  `templates/` being seeded once means they stay noop forever. It un-ships
  Kraft-33j for everyone to protect the users it would have broken.
- **Ship `gh`, keep `glab` as the local override** (option 3): one line, but
  still wrong for one repo in every mixed install, and it permanently forks this
  repo's own dogfooding registry from the shipped one — the same drift that
  produced this bug pointing the other way.
- **Probe which CLI is installed at dispatch**: explicitly rejected by
  `forge.resolve`'s contract, and rightly — the same item would take different
  paths on a laptop and in a container. `auto` is still *named*, and it resolves
  against recorded configuration, not against the environment.

## Doctor

A GitHub user with `auto` and no `gh` installed still fails at `open_mr` — later,
and inside a work item. `doctor._repo_checks` already loops the connected repos,
so it gains one check per repo, emitted only when the live registry actually
binds a forge hook to `auto`:

- no `forge` recorded → fail, same wording as the runtime error;
- forge recorded, CLI not on PATH → fail, `` `gh` is not on PATH ``;
- otherwise ok, `gitlab · glab`.

Unlike `_hooks_check`, this one fails rather than passing with detail: an
operator who does not want these hooks has bound them to something else, so
`auto` in the live registry means they do intend to run them.

# Out of scope

- **kraft-lite.** Kraft-rje is closed: `kl.py:_forge` already picks the CI client
  from origin's host and writes `kind: prompt` when it cannot. That is the same
  decision as this one — detect per repo, record it, let a human override —
  so nothing in `plugins/kraft-lite/` changes. The two detectors stay separate
  (kl.py is deliberately standalone); they agree on the rule, not on the code.
- **`_FORGES` gaining self-hosted hostname patterns.** Hand-set in `repos.yaml`
  stays the answer for self-hosted, as today.
- **Settings → Hooks rendering.** `adapterOf` shows a forge binding as its bare
  kind today; that is pre-existing and unrelated.
- **Backfilling `forge` into existing `repos.yaml` entries.** `_normalize_forge`
  leaves it `None` for pre-forge entries; those operators get the error message
  or the doctor check, and fix it once in Settings.
- **A direct-API forge backend.** Unchanged (Kraft-rki, Kraft-gzp).
