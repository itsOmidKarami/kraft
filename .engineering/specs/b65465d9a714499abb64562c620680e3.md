# Refresh worktree base on resume

## The problem

A work item's worktree branch forks from the source repo's `HEAD` exactly once
— in `ensure_worktree` (`src/kraft/builtins.py:166`), the first time the item
dispatches. `base_ref` is stamped from that same `HEAD` at
`builtins.py:207-215` and never revisited. From then on `ensure_worktree` is
deliberately idempotent: `if worktree.is_dir(): return worktree` (`builtins.py
:198-199`) — a design the docstring calls out as intentional so a
crashed-and-retried run never re-pins to a moved `HEAD`.

That guarantee is right for crash recovery (`executor.resume`, used to
reconcile a server restart mid-node) but wrong for the two doors a human uses
to un-stick a stopped item:

- `POST /work-items/{wid}/resume` (`src/kraft/api.py:1577`), the only way off
  `paused`.
- `POST /work-items/{wid}/retry` (`src/kraft/api.py:1645`), the only way off
  `needs_human`.

Both call `executor.run(..., start_index=...)` (`executor.py:1081`), which
calls `ensure_worktree` before dispatching — and since the worktree directory
already exists, that call is a no-op. An item that sat paused or stopped for
days keeps working on top of the commit `repo` was at when it first launched,
however far `repo`'s default branch has moved since. The staleness is
invisible until `open_mr`/`ci_status` reports `need_rebase` or a conflict
(`src/kraft/adapters/forge.py:357`) — by which point the agent has already
built commits on a base nobody will merge cleanly, and the `landed` diff shown
at the gate (`api.py:1111-1168`, `base_ref..HEAD`) has been quietly wrong
the whole time.

## The approach

Add one step, run only from the two human-initiated resume doors, immediately
after each endpoint's existing status/concurrency checks and before it writes
the row to `active`/re-armed and spawns the session: rebase the worktree's
branch onto `repo`'s current `HEAD`, and advance `base_ref` to match when that
rebase actually moves anything.

New builtin, next to `ensure_worktree` in `src/kraft/builtins.py`:

```python
async def refresh_worktree_base(worktree: Path, repo: Path, branch: str) -> str | None:
    """Rebase `worktree`'s branch onto `repo`'s current HEAD, so a paused or
    retried item's next commit lands on top of whatever landed on `repo`
    while the item sat stopped, not the commit it forked from.

    Returns the new HEAD sha when the rebase moved the branch (the caller
    stores it as the item's `base_ref`), or None when there was nothing to
    do: no worktree yet, `repo`'s HEAD unreadable, the branch already
    contains that HEAD, the branch already has an `origin` remote-tracking
    ref, or the worktree has uncommitted changes -- all four are best-effort
    skips (logged), same posture as `ensure_worktree`'s other git steps.
    The dirty-tree case comes from a pause via SIGTERM (`api.py:_terminate`)
    catching an agent mid-edit with nothing committed yet, and `git rebase`
    itself refuses a dirty tree; the pushed-branch case is covered below.

    Raises RuntimeError, with the rebase already aborted (`git rebase
    --abort`), on a conflict -- that is for a human to resolve, not to
    dispatch an agent into.
    """
```

Implementation, using `git_read` (`config.py:141`) for the read-only checks
and a `subprocess.run(["git", "-C", str(worktree), ...])` pair for the
rebase/abort, matching the style already in this file (`_commit_paths`,
`_pin_identity`):

1. `if not worktree.is_dir(): return None` — nothing to refresh; `resume`
   only reaches this when a worktree exists already for every item past its
   first dispatch, but a pathological one (the very first `ensure_worktree`
   call raised before creating anything) has no worktree, and `ensure_worktree`
   itself will build one fresh off current `HEAD` a moment later.
2. `head = git_read(repo, "rev-parse", "HEAD")`; `if not head: return None`
   (logged) — an unreadable `repo` is not this step's problem to raise on;
   `ensure_worktree` re-derives the same value right after and already has a
   warning for it.
3. Skip, logged, if `git_read(worktree, "rev-parse", "--verify", "--quiet",
   f"refs/remotes/origin/{branch}", expected_failure=True)` resolves — the
   branch has already been pushed past a prior `open_mr` gate. Kraft's push
   is a plain `git push -u` with no `--force` (`adapters/forge.py:416`), so
   rebasing here would rewrite history the next `mr_sync` push cannot
   fast-forward onto; an item paused mid `mr_checks`-fix-loop and then
   resumed hits exactly this. This check runs before the merge-base check
   below since it is the cheaper, purely local ref lookup and makes the
   same call moot either way.
4. Skip if already up to date: `git_read(worktree, "merge-base",
   "--is-ancestor", head, "HEAD", expected_failure=True) is not None` (exit 0
   means `head` is already an ancestor of the branch tip). No fetch needed —
   the worktree shares `repo`'s object database (`git worktree add`), so
   `repo`'s `HEAD` commit is always present in it.
5. Skip, logged, if `git_read(worktree, "status", "--porcelain")` is
   non-empty.
6. Run `git -C worktree rebase <head>`. Non-zero exit: run `git -C worktree
   rebase --abort`, then raise `RuntimeError` with git's stderr. Zero exit:
   return `head`.

Call sites, both after the existing `409`/validation checks and before the
row is written back to a running state:

```python
# api.py resume_work_item, before store.resume_work_item / _spawn
worktree = st.run_dirs.worktrees / wid
try:
    new_base = await builtins_mod.refresh_worktree_base(
        worktree, Path(row["repo"]), store.branch_for(row)
    )
except RuntimeError as exc:
    await st.db.write(lambda c: store.mark_needs_human(c, wid, row["current_node_id"], str(exc)))
    return {k: v for k, v in dict(_work_item_row(st, wid)).items()}
if new_base:
    await st.db.write(lambda c: store.set_base_ref(c, wid, new_base))
```

Same shape in `retry_work_item`, inserted after the `row["status"] !=
"needs_human"` check and before `store.retry_after_cap`. `retry_work_item`'s
`node_id` for the `mark_needs_human` call is the `node_id` it already resolved
a few lines above.

`api.py` gains `from kraft import builtins as builtins_mod` (the module has no
existing import of it; `executor.py:12` already aliases it as `_builtins` for
the same reason — the name `builtins` shadows the Python builtin module).

A conflict leaves the item exactly where `ensure_worktree`'s own git failures
leave it — `needs_human`, reason naming the git error, no session spawned —
so a human sees a merge conflict at resume time instead of discovering it
later at `open_mr`. This is a status change on what was a same-status
`resume`/`retry` call; that is intended, not a side effect to suppress: the
alternative (silently proceeding on the stale base) is the exact staleness
this item exists to fix.

### Rejected alternatives

- **Do it inside `ensure_worktree` itself.** Simplest diff, but that function
  is also the crash-recovery path (`executor.resume`, called on server
  restart to reconcile an in-flight node) and the very-first-dispatch path
  (`executor.run` at `start_index=0`) — rebasing there would also fire on
  every crash reconnect, which is exactly the case the docstring says must
  *not* re-pin, and firing at first dispatch would rebase a branch that has
  no commits yet, for no reason.
- **Always rebase, conflict or not, forcing through with `-X theirs`/`-X
  ours`.** Silently picks a side of a real conflict an agent or a human
  needs to see; wrong on any node that already produced a spec/plan/commit
  worth keeping.
- **Fetch + rebase against a remote tracking ref instead of `repo`'s local
  `HEAD`.** `repo` here is the local checkout Kraft manages, not a remote;
  every existing worktree read (`ensure_worktree`'s own `rev-parse HEAD`)
  already treats `repo`'s `HEAD` as the source of truth, and the worktree
  already shares its object database, so a fetch would add a network step
  for objects already on disk.
- **Stash-and-pop the dirty tree ourselves (or `git rebase --autostash`)
  instead of skipping.** `refs/stash` is shared across every worktree of a
  repo (same as the shared stash stack this very session was warned about),
  so an autostash from the server competing with, say, a human's own `git
  stash` in that worktree is a hazard with no matching payoff — a paused
  item almost always has a clean tree already, since every node commits
  before its session ends; the rare mid-edit SIGTERM is the case worth
  degrading gracefully on, not engineering around.

## Out of scope

- `reject_gate` (`api.py:1360`) also relaunches via `executor.run` onto an
  existing worktree, but the work item names only "paused/retried items."
  Left as-is; worth a follow-up bead if the same staleness is confirmed to
  bite there.
- `executor.resume`'s crash-recovery path (`executor.py:1268`) is unchanged —
  see "Rejected alternatives" above.
- No change to how `open_mr`/`ci_status` detect or report `need_rebase`
  (`forge.py:356-357`); this only removes one common cause of hitting it.
- No backfill or one-time rebase for items already sitting paused/stopped
  before this ships — the new code path runs the next time each one is
  resumed or retried, same as any other behavior change in this endpoint.
- No UI change. The existing diff/gate views already read `base_ref` off the
  row (`api.py:1123`); they show the refreshed range automatically once it is
  stored.

tests/test_api_retry_open_log.py tests/test_builtins.py`):

  (as the existing `test_pause_then_resume_with_a_steer_relaunches_the_task`
  does), commit a new file straight to `repo`'s default branch while paused,
  `resume`, then assert the worktree's branch contains that commit
  (`git log --oneline` in the worktree, or the file exists on disk) and that
  `GET /work-items/{wid}` reports the new commit as `base_ref`.
- `test_retry_rebases_the_worktree_onto_a_moved_head` — same shape, driving a
  `needs_human` item through `/retry` instead of `/resume`.
- `test_resume_skips_rebase_when_worktree_is_dirty` — pause with an uncommitted
  file left in the worktree, advance `repo`, resume, assert the item still
  reaches its next state (not stuck) and the dirty file survives untouched —
  pinning the "skip, don't stash" choice.
- `test_resume_marks_needs_human_on_a_rebase_conflict` — pause an item that has
  a commit touching a file, commit a conflicting change to the same lines on
  `repo`'s default branch, resume, assert the response reflects `needs_human`,
  the reason event names a rebase conflict, no new worker session was spawned,
  and the worktree is clean (`git status --porcelain` empty — proving the
  abort ran).
- `test_resume_skips_rebase_when_branch_already_pushed` — pause an item,
  push its branch to `origin` (as a prior `open_mr` gate would have),
  advance `repo`'s default branch, resume, assert the worktree's branch
  HEAD is unchanged (no rebase happened) and `base_ref` is unchanged —
  pinning the already-pushed guard.
- Add `tests/test_builtins.py::test_refresh_worktree_base_*` for the unit-level
  cases directly: no worktree yet (`None`), already up to date (`None`, no
  git calls that would fail on a missing branch), branch has an
  `origin` remote-tracking ref (`None`, skipped before the merge-base check
  even runs), a real rebase (returns the new head sha), and a conflict
  (raises, worktree left clean after abort).
