# Fix three arithmetic errors in the board's cost and usage numbers

Three independent defects, one branch, one MR, one test each. They are grouped
because they are all "the number a human reads to decide whether a chain was
worth running is wrong", not because they share code — the three live in
`src/kraft/analytics.py` + `frontend/src/views/Analytics.tsx`,
`src/kraft/reattach.py`, and `plugins/kraft-lite/kl.py`.

## The problem

### 1. Cost per work item divides by items that never ran (Kraft-g2pi)

`frontend/src/views/Analytics.tsx:182` renders the Cost tile's subtitle as
`usd(t.cost_usd / t.work_items)` labelled "per work item". `totals.work_items`
is `len(items)` (`src/kraft/analytics.py:96`) — every work item in the range,
including ones sitting paused that have never started a node.

The numerator is a sum over `worker_sessions`; the denominator counts items with
no `worker_sessions` row at all. The average is diluted by exactly the items
that spent nothing, and the error grows with the backlog. Measured on
`~/.kraft/run/orchestrator.db` on 2026-09-08: 28 items, 9 of them with any
session, $50.97 spent — the board says $1.82, the truth is $5.66, understated
3.1x.

The By repo table (`Analytics.tsx:250-265`) shows items, MRs, tokens and cost as
raw columns with no division, so it is unaffected. This is the one tile.

### 2. An adopted session records no usage (Kraft-7co4)

`reattach._exit_from_file` (`src/kraft/reattach.py:47-66`) calls
`store.session_exited(c, session_id, status, summary_ref, concerns=…,
question=…)` and never passes the `usage` positional. `adapters/subprocess.py`'s
`run_task` at the same moment passes `_usage.read(log_path, result_path)`
(`subprocess.py:275-286`).

`store.session_exited` (`store.py:603-616`) only writes `model`, `tokens_in`,
`tokens_out`, `cost_usd` when `usage is not None`, so a worker that outlives a
Kraft restart — adopted by `_adopt`, or resolved from its result file by the
`reattach` loop — keeps all four NULL forever. Consequences: its node drops out
of `store.usage_rollup` (`store.py:646`), out of the analytics rollups, and out
of the budget spend query at `store.py:843-860`, which sums `cost_usd` over
`worker_sessions`. A restart therefore makes a run look cheaper than it was in
every place Kraft reports money.

### 3. kraft-lite `since()` bills a node the whole run on a tied stamp (Kraft-ao6)

`plugins/kraft-lite/kl.py:530-538`:

```python
events = sorted(x for x in (_at(r) for r in records) if x)


def since(record: dict) -> str | None:
    closed_at = _at(record)
    earlier = [e for e in events if e < closed_at] if closed_at else []
    return earlier[-1] if earlier else _at(epic)
```

Stamps have one-second granularity (`BD_TIME = "%Y-%m-%dT%H:%M:%SZ"`). Two nodes
closed inside the same second get the same stamp, so the strict `<` finds no
earlier event for the second one and it falls back to `_at(epic)` — the run's
start. Reproduced: nodes `a` and `b` both stamped `10:05:00Z` on a chain started
at `10:00:00Z` yield `[{'a': 300}, {'b': 300}]`; `b` is billed the entire run
instead of ~0. `summary()`'s docstring claims the sub-second ceiling "reports
zeros"; it does the opposite and inflates, and `skills/next/SKILL.md` tells the
agent to render this table to a human as the run's cost breakdown.

## The approach

### 1. A second denominator, computed for free, and a label that matches it

`analytics.compute` already builds `item_node_rounds`, a dict keyed by
`work_item_id` over the session rows (`analytics.py:139,164`). Add

```python
totals["work_items_run"] = len(item_node_rounds)
```

after that loop, seed it as `0` in the `totals` literal so the empty-range early
return keeps the same shape, and divide by it in the tile. The tile's label
becomes "per work item run", so the Cost subtitle and the "Work items" KPI are
visibly counting different populations rather than silently doing so.

`work_items` keeps meaning "every item": the Work items KPI and `by_status` both
need it. That is why this is a new field rather than a redefinition, as the bead
asks.

**Decision — a still-running item counts in the denominator.** It has spent
money. It is also already handled: a running session has tokens written by
`store.session_progress` and `cost_usd` NULL, so `analytics.py:158-161` flips
`cost_complete` to `False`, and `Analytics.tsx:179-180` then replaces the
subtitle entirely with "a floor — some runs reported no cost". The average is
not shown at all while a run is in flight, so no extra rule is needed for it.
Rejected: filtering the denominator to sessions with a non-NULL cost — it would
make the denominator disagree with `cost_complete`'s own definition of the
problem and add a second, quieter caveat for the same fact.

Touches: `src/kraft/analytics.py`, `frontend/src/types.ts` (add
`work_items_run: number` to `Analytics["totals"]`),
`frontend/src/views/Analytics.tsx`, and the fixture in
`frontend/src/views/Analytics.test.tsx`. The endpoint
(`api.py:1795-1808`) returns the dict untyped, so it needs no change.

Rejected alternatives:
- *Divide in the backend and ship `cost_per_item`* — the view already formats
  every other derived figure; one more number on the wire for one tile.
- *Drop the subtitle* — the per-item figure is the number the tile exists to
  support; the bug is the divisor, not the idea.
- *Count only completed items* — would exclude an item that ran, spent, and was
  abandoned, which is money genuinely spent.

### 2. `_exit_from_file` reads usage the same way `run_task` does

Give `_exit_from_file` a `log_path` and pass `usage.read(log_path, result_path)`
as `session_exited`'s `usage` argument. Both call sites already have the value:
the `reattach` loop does `SELECT *` (`reattach.py:82-84`) so `r["log_path"]` is
in hand, and `_adopt`'s own `SELECT result_path` (`reattach.py:72-76`) grows to
`SELECT log_path, result_path`.

`usage.read` prefers a `usage` block in the result file and falls back to the
agent envelope on the log's last line, which is where a Claude Code worker's
tokens and cost actually are — so an adopted agent session needs the log path,
not just the result path. It returns `None` when neither carries usage, and
`session_exited` already treats `None` as "leave the columns alone", so a
non-agent task that reports nothing behaves exactly as it does today.

Rejected alternatives:
- *Have `session_exited` read the files itself* — it takes a connection, not
  paths, and would put disk I/O inside a write transaction.
- *Re-read usage lazily when the rollups run* — the log and result files are
  reapable; the row is the record.

### 3. `since()` orders tied stamps by their place in the walk

Carry each stamp with the record's position in the walk, and compare the pair
rather than the stamp alone:

```python
order = {r["id"]: i for i, r in enumerate([epic, *walk])}
events = sorted((x, order.get(r["id"], -1)) for r in records if (x := _at(r)))


def since(record: dict) -> str | None:
    closed_at = _at(record)
    if not closed_at:
        return _at(epic)
    key = (closed_at, order.get(record["id"], -1))
    earlier = [e for e in events if e < key]
    return earlier[-1][0] if earlier else _at(epic)
```

Two records stamped in the same second now order against each other by walk
position, so a node whose predecessor shares its stamp is timed from that
predecessor — zero seconds, the truth floored to the second — instead of falling
through to the epic. The record's own key is never `< key`, so it excludes
itself without a separate id test.

The obvious smaller edit — keep one flat list of stamps and relax `<` to `<=`,
excluding the record's own — is wrong, and I built it before this one to find
out: for the bead's own reproduction it returns `[{'a': 0}, {'b': 0}]`. Node `a`
matches `b`'s equal stamp even though `b` ran afterwards, so the first node
loses its 300 seconds. Ordering the tie is the whole fix; only the pair does it.

Verified against the current tests by applying the patch above to a scratch copy
of `kl.py`: all 148 tests under `plugins/kraft-lite/tests/` pass, and the bead's
reproduction (`a` and `b` both at `10:05:00Z`, chain started `10:00:00Z`) goes
from `[300, 300]` to `[300, 0]`.

Every record has a unique `id` (`materialize`, `kl.py:70-97`). Untied stamps
behave exactly as before, since a strictly earlier stamp compares less whatever
the positions are — including after a rewind, where the epic fallback still only
fires for a record with nothing before it at all.

The `ponytail:` note in `summary()`'s docstring is corrected in the same edit: a
chain walked faster than a second now does report zeros, as it claims.

`kl.py` must stay stdlib-only (enforced by
`test_the_shipped_helper_imports_nothing_beyond_the_stdlib`); this change adds
no import.

Rejected alternatives:
- *Sub-second stamps* — `BD_TIME` is the format bd records carry; changing it
  breaks every existing chain's records for a resolution nothing else needs.
- *Fall back to the previous row in walk order outright* — that is what the
  ordered `events` list deliberately replaced, and it charges a redone node for
  the whole first pass
  (`test_a_redone_node_is_timed_from_the_rewind_not_from_the_first_pass`). Walk
  position is used here only to break ties, never to pick the predecessor.
- *Deduplicate `events` and keep `<`* — a tie would still fall through to the
  epic; the tie is the case being fixed.

## The fixture

The brief expects one shared fixture — "a run with known usage to assert
against". It does not survive contact with the code, and I am not building it:
`plugins/kraft-lite/kl.py` imports nothing outside the stdlib and is tested from
`plugins/kraft-lite/tests/`, which cannot see `kraft` at all, so bug 3 shares
nothing with the other two. Bugs 1 and 2 sit on opposite sides of the write:
`tests/test_analytics.py` seeds `worker_sessions` rows directly through its
existing `_session(conn, sid, wid, node, u=Usage(...))` helper, while bug 2 is
about writing those columns at all and asserts on the row after
`reattach.reattach`. Each test therefore extends the fixture already in its own
file rather than importing a new shared one.

## Out of scope

- The By repo table and the by-node bars: raw columns, no division, not wrong.
- `store.usage_rollup`, the budget spend query, and the detail view's usage
  strip: they read the columns bug 2 fixes and are correct once the columns are
  written.
- Cost estimation of any kind. `usage.py`'s docstring is explicit that cost is
  only ever the agent's own number; nothing here computes a cost from tokens.
- `session_progress` and live in-flight usage.
- The sub-second and rewind ceilings in `kl.summary` beyond the tied-stamp case,
  and `duration_seconds`/`finished`, which do not use `since()`.
- Any change to `totals.work_items`, `by_status`, or the analytics API's shape
  beyond the one added key.
- Backfilling usage for sessions already in a database with NULL columns: their
  logs may have been reaped, and a migration that guesses is the thing
  `usage.py` refuses to do.

## Verification

Backend, `just test tests/test_analytics.py tests/test_reattach.py`:

- `tests/test_analytics.py::test_cost_per_item_counts_only_items_that_ran` —
  three items, sessions on one of them with a known `Usage`; asserts
  `totals["work_items"] == 3`, `totals["work_items_run"] == 1`, and that
  `cost_usd / work_items_run` is the session's own cost.
- `tests/test_analytics.py::test_work_items_run_is_zero_when_nothing_ran` —
  items with no sessions, and the empty-range early return: both return
  `work_items_run == 0` rather than omitting the key.
- `tests/test_reattach.py::test_a_session_resolved_from_file_records_its_usage` —
  a dead pid, a result file and a log whose last line is an agent envelope with
  known tokens and `total_cost_usd`; asserts `model`, `tokens_in`, `tokens_out`
  and `cost_usd` on the `worker_sessions` row after `reattach.reattach`, and
  that the `worker_session_exited` event payload carries them.
- `tests/test_reattach.py::test_an_adopted_session_records_its_usage` — the
  `_adopt` path (live pid that then exits), same assertions; this is the path
  whose `SELECT` has to grow a column, so the file-resolved test alone would not
