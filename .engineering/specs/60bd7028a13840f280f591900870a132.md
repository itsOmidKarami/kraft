# bd workspace resolution and the bd dependency

Covers Kraft-ibwj (P1) and Kraft-7gy. Kraft-3cz is **closed as a duplicate of
Kraft-ibwj** — same defect, same line, and ibwj carries the live repro, the full
call-site list, the recurrence note, and 3cz's second half (the 502 swallows bd's
stderr). One bead survives; both are designed here.

## The problem

### 1. The bd workspace is the server's cwd (Kraft-ibwj)

`_bd_cwd()` in `src/kraft/api.py:81` is the whole resolution:

    return os.environ.get("KRAFT_BD_CWD") or None

`None` means "inherit the server process's cwd". Every bd call site passes it
(`api.py:158, 513, 538, 1049, 1126, 1265, 1328, 1422`). A daemon's cwd is an
accident of how it was launched — launchd, a login item, `kraft serve` typed in
`$HOME` — and nothing records it. So on the installed daemon with `KRAFT_BD_CWD`
unset, `POST /work-items` runs `bd create` in `$HOME`, bd answers `Error: no
beads database found`, and the user gets:

    kraft: kraft 502: bd intake failed: Command '['bd','create',...]' returned non-zero exit status 1

The one line that explains it never reaches the body, because
`CalledProcessError`'s message names the argv and the exit status and not
`proc.stderr`. `api.py:520` interpolates that message and nothing else. Reported
as having blocked the user repeatedly, most recently while handing off a batch.

`create_work_item` already has `body.repo` in hand two lines above the call
(`api.py:503`). `executor.intake` has `repo` as a required argument
(`executor.py:116`). The repo was never consulted.

There is already a per-item column for this: `work_items.bead_cwd` (`db.py:42`,
migration 10 at `db.py:169`), which the auto-intake poller sets to the repo path
(`intake.py:143`) so an adopted bead is closed in the `.beads` it came from.
`beads.complete` is called as `cwd=row["bead_cwd"] or bd_cwd`
(`executor.py:829, 986, 1033`). Manual intake leaves the column NULL, so a
manually-filed item is closed in whatever `KRAFT_BD_CWD` says *at close time* —
which is a second, quieter version of the same bug: change the env var between
filing and merging and the close goes to the wrong workspace.

Repo-less bd calls have the same defect with a different shape: `GET
/beads/search` (`api.py:1422`) passes only `_bd_cwd()`, so on a daemon started
outside a beads workspace the search overlay's bead strip is permanently empty.
It degrades quietly (`adapters/beads.py` `search` returns `[]` on any failure),
so nobody has filed it as a bug — it just never works.

### 2. bd is a hard dependency of intake (Kraft-7gy)

`adapters/beads.py` shells out to a `bd` binary, and README's Requirements
(line 208) lists it alongside git and Python. Of the four adapter functions,
three already degrade — `search` and `ready` swallow everything and answer `[]`,
`complete` is wrapped in `try/except` and logged at three call sites. Exactly one
is load-bearing: `intake` runs with `check=True` (`adapters/beads.py:25`), and
`executor.intake` will not create a work item without a bead id
(`executor.py:129`).

So the entire product is gated on a tracker a newcomer has never heard of. No
`bd` on PATH, or a connected repo that has never been `bd init`ed, and Kraft
cannot file work at all. Nothing else about a work item needs the bead: the chain
definition, the gates, the worktree and the diff all live in Kraft's own SQLite,
and the SPA already renders a null bead id as nothing at all
(`Board.tsx:159`, `WorkItemDetail.tsx:202`, `types.ts:35` types it
`string | null`).

## The approach

Five changes, none of them large.

### A. `executor.intake` resolves the bd workspace from the repo, and records it

In `executor.intake`, before filing:

    cwd = bd_cwd or repo

and pass `bead_cwd=bead_cwd or cwd` to `store.create_work_item`.

That is the whole fix for Kraft-ibwj's main half. It lands in the executor rather
than in `api.py` because the executor is the one funnel both doors go through —
`api.create_work_item` and `intake._start` — and because the other seven
`_bd_cwd()` call sites feed only the `row["bead_cwd"] or bd_cwd` close fallback,
which is already per-item and correct.

**`KRAFT_BD_CWD` keeps winning over the repo.** It is documented as the
instance-wide workspace, `just dev` sets it (`justfile:22`), the e2e harness sets
it (`frontend/e2e/serve.py:144`), and an operator who set it as the workaround
for this very bug must not silently start filing into per-repo trackers on
upgrade. Repo becomes the *default*, not the winner.

Recording the effective cwd on the row also closes the quieter half: a bead is
closed where it was filed, whatever the env says months later. Old rows keep NULL
and keep the old meaning, so the `or bd_cwd` fallback and the `db.py:42` column
comment both stay — the comment gains a sentence saying new rows always set it.

### B. `beads.intake` raises with bd's stderr in the message

Replace `check=True` with an explicit non-zero check that raises `RuntimeError`
naming the exit status and `proc.stderr` (falling back to stdout when stderr is
empty). This fixes the swallowing at the source rather than at the one call site
that currently formats the exception, so the log line, the event payload and any
future caller all get the cause. `test_intake_raises_on_bd_failure` changes from
`CalledProcessError` to `RuntimeError`; `beads.intake`'s only caller is
`executor.intake`.

### C. Intake degrades: no bd, no workspace, no bead — but still a work item

In `executor.intake`, wrap the `beads.intake` call:

- Success: as today.
- `OSError` (bd not on PATH, cwd gone): reason `"bd is not installed"` /
  the OS error.
- Any other exception: reason is the message from B, which now carries bd's own
  words (`no beads database found in <cwd>`).

On any failure the work item is created with `bead_id = NULL`, a
`bead_not_filed` event is appended in the same `db.write` as
`store.create_work_item`, and a warning is logged. Intake never fails on bd
again.

The rule is deliberately "any bd failure", not "only the two failures we can
name": distinguishing "no workspace" from "dolt is wedged" means string-matching
bd's stderr, and the honest reading is that the bead is a tracking side-effect
while Kraft's own DB is the source of truth for running the chain. What makes
this a degrade rather than a silent swallow is that the reason is recorded in
three places a human already looks:

1. the `bead_not_filed` event, visible in `kraft events <id>` and the item
   timeline;
2. `POST /work-items`, which gains a `bead_warning` field — present only when
   the bead was not filed — read back from that event by a four-line
   `_bead_warning(st, wid)` helper in `api.py`, and returned on both the paused
   and the autostart response bodies. `client.create_work_item` passes it
   through, so `kraft create` prints one extra line (`_render_action` already
   renders every key it is given);
3. `kraft doctor` (E).

`executor.py`'s three `beads.complete` calls get an `if row["bead_id"]` guard.
Without it a bead-less item reaching `mark_completed` runs `bd close None` and
raises `TypeError` inside the `except Exception` — harmless but logged as a
failure that did not happen.

`executor.intake`'s return type stays `str`. Returning the reason to the caller
instead of writing an event would touch its ~30 call sites across
`test_executor.py`, `test_budget.py` and `test_findings_loop.py` to deliver a
value one caller wants, and the event is wanted anyway — it is the durable half.

### D. `GET /beads/search` fans out over connected repos

When `_bd_cwd()` is set, unchanged. When it is not, `asyncio.gather` a
`beads.search` per connected repo whose path contains a `.beads` directory,
merge, dedupe by bead id, cap at `limit`. The `.beads` test is what keeps this
from spawning a bd per keystroke per repo for nothing; the overlay debounces, and
an instance has a handful of repos, not hundreds.

The bead strip is the only repo-less bd caller, and there is no repo to scope it
to — `SearchOverlay` is global and `api.ts:225` sends only `q`.

### E. bd becomes optional, and says so

- `doctor.py` gains a `bd` check next to `_agent_check`: found → the path;
  missing → **`ok=True`** with `not installed — work items will run without
  beads`. Not a failure: `_check(ok=False)` sets `kraft doctor`'s exit code, and
  a deliberately bd-less install is not broken.
- `_repo_checks` appends `no .beads: work items here file no bead` to a
  connected repo that lacks the directory. It already loops the repos and stats
  their paths.
- README moves `bd` out of Requirements into a sentence saying work-graph intake
  is optional and Kraft files work without it.

Settings already shows `.beads/ present` / `no .beads/ yet` per repo at connect
time (`Settings.tsx:185`), so the SPA's half of the story is told.

## Alternatives rejected

- **Resolve the cwd in `api.py` at each `_bd_cwd()` call site.** Eight sites,
  seven of which would need a repo lookup to feed a fallback that
  `row["bead_cwd"]` already outranks. The executor is one place.
- **Make the repo win over `KRAFT_BD_CWD`.** Cleaner rule, silently repoints
  every existing single-tracker install on upgrade, including `just dev`.
- **A work-graph plugin interface with a null backend** (Kraft-7gy's first
  option). An interface with one real implementation plus a null object, to
  replace four lines in one function. The plugin contract in
  `docs/consolidated/03_plugin_adapters.md` §5 stays a document until a second
  work-graph exists to write against it.
- **Refuse to connect a repo without `.beads`, or 422 with "run bd init".** A
  clearer error for the same hard dependency Kraft-7gy asks to remove.
- **The hydration hub (`bd -C <hub>`) for search**, designed in
  `06_cross_repo_federation.md` §5. Real design, much larger, and a fan-out over
  a handful of repos is enough for a footer strip.
- **Return the failure reason from `executor.intake`.** ~30 call sites edited to
  deliver a value one caller reads.

## Out of scope

- Backfilling a bead for an item created while bd was down. It stays bead-less
  for life; `Kraft-dr3n` tracks it.
- Persisting `chain_template` into the bead's own metadata
  (`03_plugin_adapters.md` §5, still TBD there).
- The hydration hub, and any cross-repo bead read other than the search strip.
- Making the *test suite* run without bd: `support/harness.isolated_bd` shells
  out to `bd init` and most fixtures set `KRAFT_BD_CWD`. Tests keep requiring bd;
  the degrade tests below fake its absence with `PATH`.
- Any SPA change. The intake modal does not surface `bead_warning`; add it when
  someone files bead-less through the browser and asks where the bead id went.

## Verification

Targeted files: `tests/test_adapters_beads.py`, `tests/test_bd_workspace.py`
(new), `tests/test_search_api.py`, `tests/test_cli_doctor.py`, plus `just lint`.
Every new test must clear `KRAFT_BD_CWD` explicitly — `conftest.py:48` sets it
for the whole suite, which is why none of this was caught.

1. `test_adapters_beads.py::test_intake_error_carries_bd_stderr` — a `bd` stub
   on `PATH` that writes a known line to stderr and exits 1; assert the raised
   `RuntimeError` message contains that line. The stub-on-PATH pattern is already
   in this file (`test_ready_is_best_effort_when_bd_emits_undecodable_bytes`).
   Replaces `test_intake_raises_on_bd_failure`.
2. `test_bd_workspace.py::test_intake_files_the_bead_in_the_work_items_repo` —
   `KRAFT_BD_CWD` deleted, `repo = isolated_bd(tmp_path)`; after
   `executor.intake`, `bd show <bead_id>` run in the repo finds it and the row's
   `bead_cwd` equals the repo path.
3. `::test_kraft_bd_cwd_still_overrides_the_repo` — env set to one
   `isolated_bd`, `repo` a second one (`isolated_bd(tmp_path, name=...)`); the
   bead lands in the env's workspace and `bead_cwd` records that, not the repo.
4. `::test_a_repo_with_no_beads_workspace_still_files_a_work_item` —
   `KRAFT_BD_CWD` deleted, repo is a plain git dir: `POST /work-items` returns
   201, `bead_id` is NULL, `bead_warning` quotes bd's own "no beads database"
   wording, and a `bead_not_filed` event exists on the item. This is the
   Kraft-ibwj repro inverted — it must not be a 502.
5. `::test_no_bd_on_path_still_files_a_work_item` — `PATH` emptied inside the
   test body (after the fixtures, which need real bd): 201, NULL bead id,
   `bead_warning` says bd is not installed.
6. `::test_a_bead_less_item_completes_without_calling_bd` — an item with
   `bead_id` NULL driven to `completed` on the fake agent, asserting no
   `bead close failed` warning is logged. Pins the `if row["bead_id"]` guard;
   without it the log carries a `TypeError` for a call that should never have
   been made.
7. `test_search_api.py::test_the_bead_strip_searches_connected_repos_when_no_override`
   — two connected `isolated_bd` repos with one bead each, `KRAFT_BD_CWD`
   deleted; `GET /beads/search` returns both.
8. `test_cli_doctor.py::test_doctor_reports_a_missing_bd_without_failing` — no
   `bd` on `PATH`: the `bd` line is present and says it is not installed, and
   `kraft doctor`'s exit code is unchanged.

Tests 2, 4 and 7 fail on `main` for the reason in the bead — 2 and 4 with a bd
error, 7 with an empty list — so each must be seen red before the fix, not merely
green after it.

No schema migration: `bead_cwd` exists since migration 10.
