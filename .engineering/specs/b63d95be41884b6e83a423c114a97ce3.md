# Readable merge records: branch slugs and GFM tables

Two unrelated, mechanical fixes to what Kraft leaves behind: the branch name in
git history (Kraft-nhps) and the rendering of markdown tables in the two doc
modals (Kraft-39un). One branch, one MR, one test per item.

## 1 — Branch name is the work item UUID (Kraft-nhps)

### The problem

The branch string is built from the work item id, by hand, at three places:

- `src/kraft/builtins.py:93` — `branch = f"kraft/{work_item_id}"`, the only site
  that *creates* the branch (`git worktree add -b`).
- `src/kraft/executor.py:379` — `branch=f"kraft/{work_item_row['id']}"`, handed
  to every forge node (`push`, `open_mr`, `ci_status`, `merge`).
- `src/kraft/api.py:1183` — `git branch -D kraft/{wid}` in `_remove_worktree`,
  the abandon path.

So merge commits on `main` read `Merge branch
'kraft/f98af3e59e704ed69ad1064ed48acf59' into 'main'`, and `git log --oneline`
on main is a wall of hex. The MR *title* is already readable —
`forge.mr_title` (`src/kraft/adapters/forge.py:150`) clips the work item title
to 72 characters — only the branch is not.

### The approach: persist the branch on the row, derive it once at intake

Add a nullable `branch` column to `work_items`, filled by
`store.create_work_item` from the title at INSERT, and read at all three sites
through one helper.

```python
# src/kraft/store.py
def branch_name(title: str, work_item_id: str) -> str:
    """`kraft/<slug>-<id[:8]>` — readable, unique, always a legal git ref."""


def branch_for(row) -> str:
    """The branch a work item's worktree lives on. The row is the truth."""
    return row["branch"] or f"kraft/{row['id']}"
```

`branch_name` rules, in order: first line of the title, lowercased; every run of
characters outside `[a-z0-9]` collapsed to `-`; leading and trailing `-`
stripped; clipped to 48 characters and re-stripped of a trailing `-`; then
`-{id[:8]}` appended. A title that slugs to nothing (a wholly non-ASCII title,
or an empty one) yields `kraft/{id}` — the current behaviour, which is ugly but
always valid. The `[a-z0-9-]` charset is what makes the result a legal ref by
construction: no `..`, no `@{`, no `.lock` suffix, no control characters, no
trailing dot. This is the same shape of decision `mr_title` already makes for
titles, kept next to the other `work_items` accessors because all three call
sites already import `store`.

Uniqueness comes from the id suffix, not from the title. Two items with the
same title collide only if their ids share a 8-hex prefix; if that ever happens
`git worktree add -b` fails loudly and `env_setup` already raises with git's
stderr (`builtins.py:110`).

Why persisted rather than re-derived at each site:

- The bead's own constraint — the two (three) sites must agree exactly. A
  column is agreement by construction; three copies of a slug function are the
  "bug waiting to happen" the bead names.
- In-flight items are not stranded. Rows written before this change have
  `branch IS NULL`, so `branch_for` returns `kraft/{id}` and their existing
  worktree, branch, MR and abandon path keep working untouched. No rename, no
  backfill.
- It survives a title edit. Nothing edits `work_items.title` today, but a
  derived-on-read name would silently point at a branch that does not exist the
  day something does.
- The row is already in hand everywhere: `executor._dispatch` has
  `work_item_row`, `api.abandon_work_item` has `row` from `_work_item_row`
  (`SELECT *`). Unlike `base_ref` — which `_review_package` re-reads because
  `env_setup` stamps it mid-chain (`executor.py:259-261`) — `branch` is written
  at INSERT and never changes, so the row the executor opened with is correct.

Rejected:

- **Pure derivation from title + id at each site.** No migration, but three
  copies of the rule, and every in-flight item is stranded on a branch nobody
  looks for any more unless each site also probes `refs/heads/kraft/<id>`.
- **Ask git**: `git rev-parse --abbrev-ref HEAD` in the worktree. One source of
  truth while the worktree exists — but a rejected gate deletes the worktree and
  keeps the branch, so abandon would have nothing left to read and would leak
  branches.
- **Rename on the fly** (`git branch -m`) in `env_setup`. `env_setup` returns
  early when the worktree directory exists, so in-flight items would never reach
  the rename and the forge nodes would then look for a branch that does not
  exist.

### Changes

| File | Change |
|---|---|
| `src/kraft/db.py` | `work_items.branch TEXT` in `SCHEMA_SQL` (commented as the item's git branch, NULL on pre-migration rows); `_MIGRATIONS[13] = ["ALTER TABLE work_items ADD COLUMN branch TEXT"]`; `SCHEMA_VERSION = 14`. |
| `src/kraft/store.py` | `branch_name`, `branch_for`; `create_work_item` writes `branch_name(title, id)` into the INSERT. |
| `src/kraft/builtins.py` | `env_setup`'s existing read becomes `SELECT base_ref, branch, id FROM work_items ...`; `branch = store.branch_for(row) if row else f"kraft/{work_item_id}"`. The `row is None` arm stays because the function is reachable with no row (tests, and a worktree asked for before intake committed). |
| `src/kraft/executor.py` | `branch=store.branch_for(work_item_row)`. |
| `src/kraft/api.py` | `_remove_worktree` takes `branch` instead of building it from `wid`; `abandon_work_item` passes `store.branch_for(row)`. |

Docstrings that spell `kraft/<id>` (`builtins.py:71`, `api.py:1172`) get updated
to say the branch comes from the row.

### Out of scope

- **The worktree directory stays UUID-named** (`run_dirs.worktrees / wid`). It
  is machine state, not history: `api`, `reattach` and `executor` all resolve it
  by id, and renaming it buys nothing on `main` while costing a lookup path and
  a migration for existing directories.
- No backfill of `branch` for existing rows, and no rename of existing branches
  or open MRs.
- `mr_title` / `mr_body` are unchanged.

## 2 — Markdown tables render as raw text (Kraft-39un)

### The problem

`DocumentModal.tsx:202` and `ArtifactModal.tsx:48` both render
`<Markdown>{doc.content}</Markdown>` with no plugins. react-markdown v10 is
CommonMark-only, so a GFM pipe table falls through as a paragraph of pipes;
`remark-gfm` is not in `frontend/package.json`. Every spec and plan with a table
— this one included — is unreadable at the gate.

### The approach

`npm i remark-gfm` (v4, the version matched to react-markdown v10), then
`remarkPlugins={[remarkGfm]}` in both components. Two identical two-line edits
rather than a shared `<Md>` wrapper: two call sites do not earn a component, and
the wrapper would be the third file to keep in step.

Tables also need somewhere to land. `.doc-modal-body` (`styles.css:491`) styles
`h1`–`h3`, `p`, `ul`/`ol`, `code`, `pre` but not `table`; react-markdown emits a
bare `<table>` with no class, so the existing `.table` rules do not apply. Add a
small block next to the others, borrowing the same tokens:

```css
.doc-modal-body table { width: 100%; border-collapse: collapse; margin: 0 0 12px; font-size: 12.5px; }
.doc-modal-body th, .doc-modal-body td { border: 1px solid var(--color-neutral-800); padding: 5px 9px; text-align: left; }
.doc-modal-body th { color: var(--color-text); font-weight: 500; background: var(--color-neutral-900); }
```

Both modals use the `.doc-modal-body` class, so one block covers both. (If
`--color-neutral-800` is not a defined token, use the nearest one the file
already uses for borders.)

Strikethrough, task lists and autolinks come along with the plugin; no extra CSS
for them.

### Out of scope

`remark-gfm` only. No syntax highlighting, no `rehype-raw`/HTML passthrough
(untrusted-ish agent output rendered as HTML is a separate decision), no
markdown rendering added anywhere it is not already.

- `tests/test_builtins.py::test_env_setup_branch_is_a_title_slug` — create a
  work item titled e.g. `Readable merge records: branch slugs & GFM tables!`,
  run `env_setup`, assert the worktree's HEAD is
  `kraft/readable-merge-records-branch-slugs-gfm-tab-<id[:8]>` (exact string
  fixed once the clip is implemented) and that `git branch --list` shows it.
- `tests/test_builtins.py::test_env_setup_keeps_the_legacy_uuid_branch` — a
  `work_items` row with `branch` NULL still gets `kraft/<id>`. This is the
  no-stranding guarantee.
- `tests/test_builtins.py::test_branch_name_slugs` — `store.branch_name` over a
  360-character title (clipped, no trailing `-`), a punctuation-only/non-ASCII
  title (falls back to `kraft/<id>`), and a title with characters git refuses
  (`~`, `^`, `:`, spaces, `..`) — every result passes
  `git check-ref-format --branch`.
- Migration coverage is generic in `tests/test_db.py` (each test asserts
  `user_version == SCHEMA_VERSION` after `migrate`); the new step rides along.
  Add an assertion in the existing old-database test that a row migrated from
  the previous version has `branch IS NULL`.

  is a pipe table, assert `.doc-modal-body table th` has the header text (the
  same shape as the existing `.doc-modal-body h1` assertion at line 95). Without
  `remark-gfm` this fails: the pipes render inside a `<p>` and the query returns
  null.
- `frontend/src/components/ArtifactModal.test.tsx` — the same assertion for the
  gate artifact, so the second call site cannot drift.
