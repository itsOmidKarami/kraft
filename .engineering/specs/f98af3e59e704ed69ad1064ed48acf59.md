# Per-file collapse in the diff modal, and a log modal that stops lying

Two beads, two independent components, one work item.

- **Kraft-bo98** (P1, feature) — `DiffModal` renders every file's hunks in one
  flat scroll; wanted: collapsible per-file sections like a GitLab MR.
- **Kraft-29a0** (P1, bug) — `LogModal` shows `Failed to fetch` / `0 lines` on a
  live session while simultaneously claiming to be following it.

They share no code and can be implemented in either order.

---

## Part 1 — Kraft-bo98: per-file collapse in the diff modal

### The problem, in this repo's terms

`frontend/src/components/DiffModal.tsx` renders the response of
`GET /work-items/{wid}/diff` (`src/kraft/api.py:859`, backed by
`review.read_change`) as three disconnected blocks:

| lines | what it renders | from |
|---|---|---|
| 80–90 | `.diff-files` — a static list of paths with `+n −n` | `change.files` (git `--numstat`) |
| 92–100 | `.diff-body` — `diff.diff.split("\n")` mapped through `lineClass`, one flat `<pre>` | git `diff <base>` |
| 109–120 | `.diff-untracked` — "New files (content not shown)" | git `status --porcelain -uall` |

Nothing connects the three. The file list is not clickable, the body has no
structure past per-line colouring, and a reviewer looking for `hull.py` scrolls
until they see its `+++` header go past. On the item that triggered the bead
(+127/−9 across 6 files, three tasks into a thirteen-task plan) that is already
tedious; at merge it is unreviewable.

### Approach

Split the diff body into per-file chunks **in the component**, and render one
`<details>`/`<summary>` per file inside the existing `.diff-files` list. The
untracked list folds into that same list as body-less rows, so a reviewer has
one list of "what changed" instead of two.

`<details>` is the whole interaction: no React state, no toggle handlers, no
expand/collapse bookkeeping, keyboard-accessible for free. The only thing the
component decides is the initial `open` attribute.

**Rejected:**

- *Return per-file patches from the backend* (`files: [{path, …, patch}]`) — a
  cleaner join, but it changes a response shape that `kraft diff`, the review
  package (`review.render_package`) and `tests/test_diff_api.py` all read, to
  buy something 15 lines of frontend splitting already gives.
- *A diff-parsing dependency* (`parse-diff`, `react-diff-view`) — a new
  dependency to find `diff --git` boundaries that `src/kraft/api.py:831`
  already splits on with two lines of string work.
- *Controlled React state per file plus "expand all / collapse all"* — state to
  reimplement what `<details>` does natively, for a control nobody asked for.

### Chunking, and how rows are built

Split on a lookahead so each chunk keeps its own header:

```ts
const chunks = diff.diff ? diff.diff.split(/\n(?=diff --git )/) : [];
```

This is safe against the backend's truncation: `_truncate_at_file_boundary`
(`src/kraft/api.py:831`) only ever cuts on a `diff --git` boundary, except for
the single-oversized-file case, which yields one partial chunk — still one
chunk, still headed.

A chunk's path is read from, in order: `rename to <path>`, `+++ b/<path>`,
`--- a/<path>`. Not from the `diff --git a/x b/x` line: it names the path twice
with no separator that survives a path containing a space. A chunk that matches
none of the three (a pure mode change) is labelled by its first line.

Rows, in this order:

1. **One row per chunk.** `+n −n` comes from the matching `--numstat` entry in
   `diff.files`; if no entry matches the chunk's path, the counts are derived
   from the chunk (`+`/`-` lines, excluding `+++`/`---`).
2. **Files in `diff.files` with no chunk — only when `diff.truncated`** — as
   body-less rows marked *not shown — diff truncated*.
3. **`diff.untracked`** — body-less rows marked *new file — content not shown*.
   No counts: `--numstat` never sees an untracked file.

Rule 2 is conditional on purpose. Under rename detection (git's default),
`--numstat` reports a rename as `old => new` while the chunk reports `new`, so
an unconditional rule would print a spurious "truncated" row for every renamed
file. Gating on `truncated` costs nothing in the normal case; in the rare
truncated-and-renamed case a reviewer sees one extra row that says the diff was
cut, which it was.

The header total keeps summing `diff.files` (`--numstat`), not the rendered
chunks — a truncated body must not silently shrink the total. It gains a file
count: `6 files · +127 −9`.

### What starts open

One budget, walked over the rows in order:

```ts
const MAX_FILE_LINES = 300;  // a single file bigger than this starts closed
const MAX_OPEN_LINES = 600;  // total lines open on arrival
```

A row opens when its own body is at most `MAX_FILE_LINES` *and* the running
total of already-opened lines plus its own is at most `MAX_OPEN_LINES`. Only
opened rows consume budget.

This is one rule for both defaults the bead asked for: a small diff arrives
fully expanded, a large one arrives with the first files open and the rest
collapsed, and a generated or vendored file is collapsed on its own size
wherever it sits. No file-count threshold and no byte threshold — a line budget
is what "how much scrolling did I just inherit" actually means.

`open` is passed as a plain attribute (`<details open={row.open}>`). React
re-applies it only when the value changes, and `diff` is fetched once, so a
reader's own toggling is never fought.

### CSS

`frontend/src/styles.css:940–955`. The scroll container moves from `.diff-body`
to `.diff-files` (the list is now the whole body); `.diff-files` loses its
`border-bottom`; a `<summary>` gets `cursor: pointer` and holds a flex `<span>`
rather than being flex itself, so the native disclosure marker survives.

`.diff-body > div { white-space: pre; }` and its `@media (max-width: 640px)`
`pre-wrap` override are pinned verbatim by `frontend/src/styles.order.test.ts`
and must not be reworded or reordered. The phone block at line 858 keeps
overriding padding for `.diff-files` and `.diff-body`, which still exist.

### Out of scope (Part 1)

- Side-by-side view, word-level intra-line highlighting, syntax colouring.
- "Expand all" / "collapse all" / per-file "viewed" checkboxes.
- Showing untracked file *contents* — the backend does not send them, and
  `--numstat` does not count them.
- Raising `DIFF_MAX_BYTES`, or surfacing `diff_max_bytes` / `worktree_path`
  (both already in the response, both absent from `WorkItemDiff` in
  `frontend/src/types.ts`).
- Persisting collapse state across reopens of the modal.

## Part 2 — Kraft-29a0: `Failed to fetch` on a live log

### What the code does today

`frontend/src/components/LogModal.tsx` opens two connections for one log:

- **51–62** — `api.getLogLines(sessionId)`, a one-shot snapshot
  (`GET …/log?format=jsonl`).
- **64–75** — an `EventSource` on `…/log?format=jsonl&follow=1`, when
  `follow` is on (`follow` initialises to `session?.status === "running"`).

The server's tail (`_tail`, `src/kraft/api.py:1350`) starts at `sent = 0` and
yields **every** structured line before it starts following. So while
`follow` is on, the snapshot fetch is a second copy of data the stream is
already sending — `merge()` (line 26) exists precisely to absorb the overlap.
That redundant request is the *only* thing on screen that can produce the
reported banner: the SSE path calls `es.close()` in `onerror` and sets no
message.

Four defects, all visible in that code:

1. **The error is never cleared.** No `setError(null)` anywhere. Clicking a
   second session in `EventTimeline` changes the `sessionId` prop without
   remounting, so one session's failure stays on screen over the next session's
   lines — an error banner and a healthy log, together.
2. **A redundant request is the only failure path.** For a followed session the
   snapshot can only duplicate the stream or fail; it has no third outcome.
3. **The stream dies silently.** `es.onerror = () => es.close()` discards
   `EventSource`'s own reconnection — the browser signals a *retrying* error
   with `readyState === CONNECTING` and a *terminal* one with `CLOSED`, and
   this treats both as terminal. After that the `.log-following` strip keeps
   saying "following · new lines appear here" forever. The same lie appears on
   the clean path: the `end` event closes the stream and leaves `follow` true.
4. **`Failed to fetch` is the browser's string, not ours.** Every call in the
   app goes through `req()` (`frontend/src/api.ts:29`), which handles non-OK
   responses but lets a transport-level `TypeError` through verbatim. A
   reviewer is told nothing about which server, which URL, or that the request
   never left.

### What was ruled out, and what was not

The bead's leading hypothesis is HTTP/1.1's six-connection cap being exhausted
by persistent SSE streams. Checked, and it is weaker than it looks: `LogModal`
is the app's only `EventSource` (the board uses a WebSocket, `frontend/src/ws.ts`),
and at most two log modals can be open at once (`CappedCard`, plus whichever of
`CurrentNodePanel` / `EventTimeline` the visible tab mounts — switching tabs
unmounts the other and closes its stream). Nothing else polls. Six concurrent
connections needs several browser tabs.

The standing suspect for *slow* responses while a log is followed is
**Kraft-21jy** (filed today): `_tail` re-reads the entire log file plus its
`.times.jsonl` sidecar, and does a synchronous SQLite read, every 0.4 s per
stream, on the event loop. That explains stalls, not a `TypeError`.

**So the mechanism is not reproduced, and this design does not claim it.** What
it does is remove the request that failed (for a followed session there is now
nothing to fail), stop the UI asserting things that are not true, and make the
message name the server if it happens again. If `Failed to fetch` is ever seen
again with follow *off*, the connection-cap investigation is the next step and
serving the API over HTTP/2 is the fix that would end it.

### Approach

Six changes, smallest first.

1. **`frontend/src/api.ts`, `req()`** — wrap the `fetch` call so a transport
   `TypeError` is rethrown as a message that names the server and the path,
   e.g. `could not reach the Kraft server (GET /worker-sessions/…/log) — it may
   have stopped`. One place, every caller. Non-`TypeError` rejections rethrow
   untouched.

2. **Skip the snapshot while following.** The first effect becomes
   `if (follow) return;` with `follow` added to its dependencies. A followed
   session gets exactly one connection; switching follow off fetches the
   snapshot then, which also refreshes anything the stream missed. `merge()`
   stays — it is still what reconciles a snapshot taken after a partial stream.

3. **Clear the error on entry** — `setError(null)` at the top of that effect,
   so an error belongs to the session and follow-state it came from.

4. **`end` stops the claim** — the `end` listener closes the stream *and* sets
   `follow(false)`, so a session that finishes while the modal is open drops the
   "following" strip and the button's pressed state, and (via change 2) pulls a
   final snapshot.

5. **`onerror` respects the browser's own retry** —
   `if (es.readyState === EventSource.CLOSED) { setFollow(false); setNote("log
   stream stopped — press Follow to retry"); }` and otherwise leave the
   `EventSource` alone to reconnect, with the strip reading "reconnecting…".
   A reconnect replays the log from line 0 and `merge()` drops the duplicates,
   so replay is correct; it also costs the server no more than one ordinary
   0.4 s poll already costs (Kraft-21jy), which is why no `?after=` resume
   parameter is being added.

6. **`pending` counts as live.** `_tail` currently reads
   `status == "running"`, so a stream opened on a session in `pending` sends
   one poll's worth and closes; `LogModal` likewise initialises `follow` from
   `"running"` alone, so a log opened a beat early never follows. Both become
   *not finished* (`pending` or `running`). Two lines, one on each side.
   Flagged separately here because it is adjacent to the reported bug rather
   than part of it, and is cheap to cut.

Plus one empty state: while a session is live with no lines yet, the body says
*no output yet — an agent running with `--output-format json` writes its log
when it exits*. That is the exact screen the reporter was looking at, and it is
correct behaviour (`adapters/subprocess.py:148`), not a fault.

### Out of scope (Part 2)

- Kraft-21jy itself (the per-poll full-file read) — filed, not fixed here.
- Serving the API over HTTP/2, or moving the log tail onto the existing
  `/ws/events` WebSocket.
- Per-line timestamps for adopted sessions (already noted in `logs.py`).
- Log search, download, or a byte-range resume parameter on the follow endpoint.
- The dev-only missing vite proxy entries found while reading this code — filed
  as its own bead, Kraft-9r4q (`/steering`, `/intake`, `/notify` absent from
  `frontend/vite.config.ts`).
