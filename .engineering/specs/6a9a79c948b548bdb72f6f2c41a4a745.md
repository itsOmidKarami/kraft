# CLI and UI polish

Thirteen independent beads, one branch, one MR, one test per bead. Nothing here
changes a chain's control flow; every item is a hole that makes a routine action
awkward. The batch epic Kraft-bwp9 lists seven siblings (97e, sws6, 5lpl, owea,
tom2, t5s9, ldeq) that already landed — they are the reason two of these beads
exist at all (Kraft-7qgb is the composition gap sws6+97e left, Kraft-8okl is the
half t5s9 named out of scope), and they are not re-touched here.

Order below is the implementation order. `tmsv` first because the chain-template
screen cannot be judged before it; the three steering beads together because
they are one file; `3e6e` last, because it is the only one that gains from
everything else being in place.

## 1. Kraft-tmsv — the chain-template textarea is 90px

**Problem.** `frontend/src/styles.css:806` is `.template-yaml { min-height:
320px; ... }`. The element is `<textarea class="input mono template-yaml">`
(`Settings.tsx:391-396`, and the steering editor at `Settings.tsx:779-784` uses
the same class). `frontend/src/nocturne.css:177` is `textarea.input {
min-height: 90px; resize: vertical; }` — one element + one class beats one
class, so 90px wins regardless of import order. The two sibling rules that do
work (`styles.css:314` `.gate-reject textarea.input`, `:731` `.paused-card
textarea.input`) both qualify with the element.

**Approach.** `textarea.template-yaml`, and raise 320px to 420px: the default
template is 10 nodes pretty-printed, and both editors that use this class hold
documents, not one-liners. `resize: vertical` from the base rule stays, so a
human can still drag it.

Rejected: raising specificity with `!important` (a landmine for the next
override); moving the rule into `nocturne.css` after the base rule (nocturne is
the design system, `.template-yaml` is a screen).

**Verification.** `frontend/src/styles.order.test.ts` gains
`it("qualifies .template-yaml with the element so textarea.input cannot outrank
it")`: read `styles.css`, assert the min-height rule for that class matches
`/textarea\.template-yaml/`. A source assertion, not a computed style — jsdom's
cascade is not a thing to build a regression test on, and the failure mode here
is exactly a selector that lost on specificity. The comment in that file already
explains why source-text assertions live there.

## 2. Kraft-9r4q — dev vite proxy is missing routes

**Problem.** `frontend/vite.config.ts:7-23` lists API prefixes to forward to
`127.0.0.1:8765`. Missing: `/steering`, `/intake`, `/notify` — and, traced
while writing this, **`/theme`** (`api.ts:223-224`, real routes at
`api.py:2334`/`:2340`). Under `just dev` those requests hit vite's SPA fallback
and return `index.html` with a 200, so `api.req()` dies in `res.json()` with a
SyntaxError about `<`. Four Settings screens are broken in dev only.

**Approach.** Add the four prefixes. Then close the recurrence: this list has
now drifted at least twice, so add
`frontend/src/vite.proxy.test.ts` — read `api.ts`, collect every

first set is a subset of the second. Cheaper than a route registry, and it fails
on the next route added without a proxy entry.

Rejected: a wildcard `^/(?!src|@|node_modules)` proxy (breaks the SPA's own
routes, which are also path-shaped); generating the list from the OpenAPI schema
at build time (a python dependency in the vite config for a 20-line array).

**Verification.** The new proxy test, plus the four literals present in the
config.

## 4. Kraft-hbsv — a work item's title is not editable

**Problem.** `store.set_description` (`store.py:802`) exists and emits
`work_item_description_edited`; `WorkItemPatch` (`api.py:999-1002`) documents
description as "the only editable field". A title typed at intake is permanent —
retitling seven items on 2026-09-08 was done with `sqlite3 UPDATE` against
`orchestrator.db`, bypassing the API and emitting no event.

**Approach.**

- `store.set_title(conn, work_item_id, title)`, mirroring `set_description`:
  same `UPDATE ... updated_at` shape, emitting `work_item_title_edited`. A
  separate event type rather than a shared `work_item_edited`, because the two
  edits mean different things — the description is prepended to every agent
  instruction, the title is a label.
- `WorkItemPatch` becomes `title: str | None = None` / `description: str | None
  = None`, with a rejection when both are None ("nothing to patch") and a
  rejection of an empty/whitespace title. Absent means untouched: a UI that
  patches only the title must not blank the brief. The route applies each
  provided field in one `db.write` and returns the fields it set.
- UI: `WorkItemDetail.tsx:315` (`<h2 className="detail-title">`) gets the same
  read-then-edit treatment the `Description` component already implements
  (`WorkItemDetail.tsx:113-179`) — an `Edit` button, an `<input className="input">`,
  Save/Cancel, `hydrateItem` after save. Same shape, one field, no shared
  abstraction for two callers.
- `api.ts:93` `updateWorkItem(id, description)` becomes
  `updateWorkItem(id, patch: { title?: string; description?: string })`. Two
  call sites (the description editor and the new title editor), both in
  `WorkItemDetail.tsx`.

Not changed, deliberately: the worktree branch name, which is derived from the
title at intake — a live branch cannot be renamed under a running chain, and
`base_ref`/MR already point at it. Nothing else derives from the title: search
indexes documents, not work-item rows (`index/ingest.py`), so no reindex.

Rejected: a general `PATCH` that accepts any column (this route is deliberately
not a table editor); a `kraft item retitle` CLI verb (the bead asks for the
detail header, and the CLI door is `--json` PATCH away if it is ever wanted).

**Verification.**
- `tests/test_store.py::test_set_title_records_an_event`
- `tests/test_api.py::test_patch_sets_the_title_without_clobbering_the_description`
  (and the reverse), plus a 422 for `{}` and for a blank title.
- `WorkItemDetail.test.tsx::it("edits the title and re-reads the item")`.

## 5. Kraft-cy30 — `item create` on a long title

**Problem.** `bd` refuses a title over 500 characters. `adapters/beads.intake`
(`adapters/beads.py:8-39`) shells out with the raw title.

Half of this bead is already fixed and must not be re-fixed: `beads.intake`
raises bd's own stderr (Kraft-ibwj), and `executor.intake:203-217` catches every
bd failure into a `bead_warning` rather than a 502 (Kraft-7gy). So the reported
`kraft 502: bd intake failed: Command [...]` no longer happens. What is left is
worse in a quiet way: a 711-character title now *succeeds*, and the work item is
created with no bead and a warning line the caller may not read.

**Approach.** Guard the length where the title enters, in `create_work_item`
(`api.py:591`), before `executor.intake`:

```python
if len(body.title) > beads.MAX_TITLE:
    raise HTTPException(
        422, f"title is {len(body.title)} characters; the tracker's limit is {beads.MAX_TITLE}"
    )
```

with `MAX_TITLE = 500` defined in `adapters/beads.py` next to the `bd create`
call, so the constant lives with the reason for it. An explicit check rather
than `Field(max_length=...)`: pydantic's 422 body is a list of error dicts, and
`kraft item create` prints `detail` straight through — one sentence is the
contract every other CLI error keeps.

The offending title is not echoed back, which is the third complaint in the
bead: the length and the limit are the actionable part.

Rejected: truncating the title for bd and keeping the full one in Kraft (two
different titles for one item is a worse bug than the one being fixed); asking
bd for its limit (a subprocess round trip to learn a constant).

**Verification.** `tests/test_api.py::test_a_title_over_the_tracker_limit_is_refused_before_bd`
— 422, the number 500 in the detail, the long title absent from the detail, and
no row written.

## 6. Kraft-8okl — `_cmd_watch` calls `client._get`

**Problem.** `cli.py:516` does `await client._get("/work-items")` to get the
board *and* the event cursor the stream must start from;
`client.list_work_items` (`client.py:153-168`) returns trimmed items and drops
the cursor. Same class as Kraft-t5s9, which promoted `client._target`.

**Approach.** The shape decision the bead names, decided: a second public
function, not a cursor grafted onto `list_work_items`.

```python
async def board(status=None, *, include_abandoned=False) -> tuple[list[dict], int]:
    """The trimmed rows and the event cursor they reflect."""
```

`list_work_items` becomes `(await board(status, ...))[0]`, so there is still one
definition of what a board row is (`trim_work_items` already exists for exactly
that reason). `_cmd_watch`'s `frame()` calls `client.board()`. A tuple return
rather than a `Board` dataclass: two fields, one caller that needs both.

Rejected: `list_work_items(..., with_cursor=True)` returning two different types
by flag; making the cursor a module-global the stream reads (invisible coupling).

**Verification.** `tests/test_cli_watching.py::test_watch_reads_the_board_through_the_public_client`
— monkeypatch `client.board`, assert `watch` draws from it and never touches
`client._get`; the existing
`test_watch_draws_a_frame_per_event_and_starts_at_the_live_cursor` keeps the
cursor behaviour honest.

## 7. Kraft-7qgb — disconnect cannot remove a worktree-path entry

**Problem.** `client.disconnect_repo` (`client.py:579-594`) probes the path
first, so from inside a worktree it deletes the repo the worktree belongs to.
Right for the common case; wrong for the case the verb was added for. An entry
written before Kraft-97e is keyed by a *worktree* path, and every CLI door now
probes, so no door can address it — removing one needed a raw
`curl -X DELETE /repos?path=...`.

**Approach.** Prefer the exact match over the resolved one:

```python
path = path or os.getcwd()
if path not in {r["path"] for r in await repos()}:
    status, probed = await _post("/repos/probe", {"path": path})
    if status < 400:
        path = probed["path"]
await _delete("/repos", path=path)
return {"path": path}
```

One extra `GET /repos` — `client.repos()`, already the sanctioned reader (spec D
§4) — and the probe only runs when the literal path is not itself connected.
Server-side `_connected` (`api.py:2109`) still handles the symlink-resolved
case, so a path that differs only by `/var` → `/private/var` behaves as before.
The 404 message when neither is connected is unchanged.

Rejected: a `--exact` / `--no-probe` flag (a flag for a case the tool can decide
itself, and the operator hitting this does not know which kind of entry they
have); doing the preference server-side in `DELETE /repos` (the server is handed
one path and cannot know a probe happened).

**Verification.** `tests/test_cli_repos.py::test_disconnect_removes_an_entry_registered_under_a_worktree_path`
— connect the main checkout, hand-write a second `repos.yaml` entry for a
worktree path, `kraft repo disconnect <worktree>`, assert the worktree entry is
gone and the main entry stays. The existing
`test_disconnect_from_inside_a_worktree_disconnects_the_repo` pins the other
direction and must keep passing.

## 8. Steering: Kraft-e9a, Kraft-oah, Kraft-17p

One file each side (`api.py`'s steering block, `Settings.tsx`'s `SteeringPage`),

### 8a. Kraft-e9a — blocking directory I/O in an async handler

`_check_steering_change` (`api.py:2358-2401`) copies every `*.md` from
`$KRAFT_HOME/templates/steering/` into a `TemporaryDirectory` with
`shutil.copy2`, then runs `load_registry` and `load_repos` over the copy — all
synchronous, inside `async def put_steering` / `delete_steering`.

The bead offers "measure and document" or "move it off the loop". Decision:
move it, `await asyncio.to_thread(_check_steering_change, st, name, body.body)`
at both call sites (`api.py:2445`, `:2462`). Two lines, no measurement to go
stale, and `HTTPException` raised inside the thread propagates unchanged. A
docstring number describing a directory whose size an operator controls is the
kind of comment that is wrong a year later.

The real write (`config_mod.write_text`) and `path.unlink()` stay on the loop:
one file, one syscall — moving those would be cargo.

**Verification.** `tests/test_settings_api.py::test_the_steering_validation_runs_off_the_event_loop`
— monkeypatch `_check_steering_change` to record `threading.current_thread()`,
PUT and DELETE, assert neither ran on the main thread.

### 8b. Kraft-oah — no DELETE-side reload test

`test_saving_steering_reloads_nothing` (`tests/test_settings_api.py:1210`) pins
`_reload_templates` is not called on PUT. `delete_steering` has no equivalent.

**Approach.** Add `test_deleting_steering_reloads_nothing`, the same monkeypatch
against `api_mod._reload_templates`, asserting an empty call list after a
successful DELETE. It is a change-detector on an implementation detail, and
that is the point: the reason the call is absent (no `app.state` holds steering
bodies; dispatch reads them off disk) is non-obvious enough that someone adds it
back. The test's docstring carries that reason.

### 8c. Kraft-17p — diff and revert

**Problem.** Sub-project C's spec says steering files are "edited by a Settings
screen like every other file under `templates/`, diffable and revertable for the
same reasons"
(`docs/superpowers/specs/2026-09-04-sub-project-c-agent-invocation-contract-design.md:163`).
The shipped editor is a textarea with Save and Delete. It already holds the last
saved body in `loaded` (`Settings.tsx:672`) and uses it only to disable Save.

**The family question the bead asks, answered.** The requirement belongs to the
family, not to steering alone — and the gap across the family is smaller than it
looks. The chain-template editor already has Discard
(`Settings.tsx:417-419`, reverting `draft` to `original`); the steering editor
has no revert at all. So: build one small diff view, use it on both screens, and
add Discard to steering. No supersede bead is needed, because both members of
the family end up covered by this work item; the policy statement ("every
`templates/` editor shows its unsaved change and can drop it") goes in the
docstring of the shared component so the next screen inherits it.

**Approach.**

- `frontend/src/diff.ts`: `lineDiff(before: string, after: string):
  {tag: " " | "+" | "-", text: string}[]` — a plain LCS table over lines, ~25
  lines, no dependency (`package.json` has no diff library and one is not worth
  adding for two textareas). `// ponytail: O(n·m) LCS; these are ≤8 KB steering
  files and a 10-node template — switch to Myers if a real document lands here.`
- `frontend/src/components/DraftDiff.tsx`: `<DraftDiff before={...}
  after={...} />` renders `lineDiff` into the classes DiffModal already styles
  (`.diff-body`, `.diff-add`, `.diff-del`, `.diff-ctx` — `styles.css:997-1002`),
  and renders "no unsaved changes" when the two are equal. No modal, no
  fetching: both strings are already in the component's state.
- `SteeringPage`: a `Changes` toggle button beside Save that shows
  `<DraftDiff before={loaded} after={draft} />`, and a `Discard` button
  (disabled while `draft === loaded`, and while `busy`) that sets `draft` back
  to `loaded`. A brand-new unsaved file has `loaded === ""`, so its diff is all
  additions, which is honest.
- `TemplatesPage`: the same `Changes` toggle against `original`. Its existing
  Discard stays as is.

Rejected: server-side `difflib.unified_diff` behind a new route (a round trip
per toggle to diff two strings the browser already has, plus a route and a
client function to test); storing history/versions of steering files (the
acceptance criterion is "against its last saved version", and git is where
history belongs — `templates/` is versioned YAML by design); a `<DiffModal>`
reuse (it is built around fetched `git diff` text and per-file `<details>`
rows).

**Verification.**
- `frontend/src/diff.test.ts` — an insertion, a deletion, a modified line, and
  identical inputs (empty change list).
- `Settings.test.tsx::it("shows the unsaved steering change and discards it back
  to the saved body")` — type into the body, open Changes, assert an added line
  is marked, click Discard, assert the textarea holds the saved body again and
  Save is disabled.
- `Settings.test.tsx::it("shows the unsaved template change")` — the same
  toggle on the templates screen.

## 9. Kraft-lqzx — doctor does not check the MCP server is registered

**Problem.** Every worker launch passes `--permission-prompt-tool
mcp__kraft__permission_request` (`adapters/agent.py:147,153`). On an install
where `kraft admin init` was never run the tool does not exist, the CLI exits 0
and ignores the flag, and permission asks silently go unanswered again. Nothing
reports it.

**Approach.** A new `doctor._mcp_check`, appended next to `_agent_check` (they
answer the same question — can this machine actually launch a worker):

1. User scope: `~/.claude.json` → `mcpServers.kraft` present → ok, naming the
   file. This is what `init.install` produces via `claude mcp add --scope user`
   (`init.py:122`).
2. Repo scope: any connected repo with a `.mcp.json` whose `mcpServers` names
   `kraft` → ok, naming the repo. This is what `kraft admin init --repo` writes
   (`init.py:100-109`). The repo list comes from `client.repos()`, so the check
   is async and joins the server-up branch of `run_checks`; with the server
   down it reports `skipped: no server` after the user-scope test fails, like
   every other server-dependent check.
3. Otherwise `ok=False`: "no kraft MCP server registered — workers' permission
   prompts go unanswered; run `kraft admin init`".

A real failure, not an advisory like `bd` or shell completion: unlike those,
this one silently breaks a running chain's ability to ask for permission.

Rejected (as the bead records): passing `--mcp-config` on every launch, which
makes Kraft write the operator's agent config. Also rejected: shelling out to
`claude mcp list` (a subprocess whose output format is not ours, when the file
it reads is right there).

**Verification.** `tests/test_cli_doctor.py`:
`test_mcp_check_passes_on_a_user_scope_registration` (a fake `$HOME` with a
`.claude.json`), `test_mcp_check_passes_on_a_repo_scope_mcp_json`, and
`test_mcp_check_fails_when_nothing_registers_kraft` (asserting `ok is False` and
`kraft admin init` in the detail). `test_doctor_on_a_live_instance_reaches_every_check`
gains the new name.

## 10. Kraft-map — the fake writes its artifact whatever it reports

**Problem.** `fixtures/fake-claude.sh:88-108` writes
`.engineering/{spec,plan}s/<item>.md` from the injected `Hook point`, before and
regardless of the status it is about to report. A real worker that stops to ask
a question has written nothing, and `agent._resolve_status`
(`adapters/agent.py:258-280`) holds only a *claim of success* to the artifact —
so the fake masks exactly the regressions that guard exists to catch. The
needs_context downgrade bug in MR !58 passed every needs_context test for this
reason. `tests/support/fake_agent.py` already honours the contract and has
`KRAFT_FAKE_AGENT_SKIP_ARTIFACT`.

**Approach.** Mirror the python fake:

- Write the artifact only when the reported `status` is `done` or
  `done_with_concerns` (the `_ADVANCING` set — `executor.py:95`). The status is
  already resolved before that block runs, including the `on.chain.review_ready`
  override at `fake-claude.sh:85`, so this is a guard, not a reordering.
- Honour `KRAFT_FAKE_CLAUDE_SKIP_ARTIFACT=1` for a test that wants the
  empty-gate failure on purpose, matching `KRAFT_FAKE_AGENT_SKIP_ARTIFACT`.
- The session summary keeps being written on every status: a stopped worker is
  still told to write one, and `run_agent_task` reads it back the same way.

No existing test drives fake-claude through a planning hook with a non-`done`
status — `harness.fake_templates_dir` binds `on.spec.requested` /
`on.plan.requested` to `builtin: noop` unless `planning_hooks=True`, which no
test currently passes — so this is behaviour-preserving for the suite it ships
with, and only changes what a *new* test can catch.

**Verification.** `tests/test_fixtures.py::test_a_needs_context_report_writes_no_artifact`
— run the script with a spec `Hook point` in the injected context and
`KRAFT_FAKE_CLAUDE_STATUS=needs_context`, assert `.engineering/specs/<id>.md`
does not exist while the result file and the session summary do; and
`test_the_skip_knob_suppresses_the_artifact_on_a_done_report`.

## 11. Kraft-3e6e — no visual validator for a chain template

**Problem.** `Settings.tsx:361-420` edits a chain as raw JSON in a textarea, and
the validator's whole output is `valid` / an error string plus one
"resolvable / unresolvable" line per repo (`Settings.tsx:398-407`). Neither
question a human has at that screen is answered: *what is this chain* (node
order, which nodes gate, where the fix loops are), and *where exactly is it
broken* ("unresolvable" names a repo, not a node or a task).

Worth recording while tracing: `_validate_template`'s `by_repo.resolvable`
(`api.py:2226-2232`) is `all(h in st.registry.hooks for h in hooks)` — the same
value for every repo, computed without consulting the repo at all, despite the
comment above it. It is one bit of information repeated N times. It is replaced,
not repaired.

**Approach**, reusing what exists rather than adding a component:

1. **Loosen `ChainBar`** (`components/ui.tsx:96-130`). Today it takes a
   `WorkItem` and reads three things off it. Change the props to
   `{ nodes, currentNodeId?, done?, invalid?, size, paused? }`; the two existing
   call sites (`Board.tsx:257`, `WorkItemDetail.tsx:338`) pass
   `nodes={item.chain_definition.nodes} currentNodeId={item.current_node_id}
   done={item.completedNodes}`. Explicit props rather than an optional `nodes`
   override beside `item`, so there is one way to call it. It already draws one
   segment per node, marks `gate_after` with `.chain-gate`, and labels nodes at
   `lg`.
2. **Draw the draft.** `TemplatesPage` renders `<ChainBar nodes={parsed}
   size="lg" />` above the textarea whenever `parsed` is non-null — so the
   diagram tracks what is typed, and vanishes into the existing "not valid JSON"
   line when it is not. No graph library, no new component.
3. **Report per node.** `_validate_template` returns
   `"unresolved": [{"node": <id>, "task": <hook>}]` — every node task not in
   `st.registry.hooks` — and drops `by_repo`. `TemplateValidation` in
   `types.ts:316-321` follows. The screen lists the unresolved pairs under the
   bar, and passes their node ids as `invalid` to `ChainBar`, which sets
   `data-state="invalid"` on those segments (precedence: invalid over current
   over done over todo; in the editor nothing is current). `styles.css` gets one
   `.chain-seg[data-state="invalid"] .chain-fill { background: var(--color-accent-2); }`
   beside the existing state rules — `--color-accent-2` is what `.diff-del`
   already uses for the "wrong" colour.
4. Keep what is already right: the "not valid JSON — nothing will be saved"
   line and the Save button disabled off `parsed`.

Rejected: a real graph/DAG rendering of fix loops and concurrent tasks
(`ChainBar`'s own docstring says fix cycles are deliberately not drawn there,
and a chain is a list with gates, not a graph); keeping `by_repo` alongside
`unresolved` (two answers to one question, one of them wrong); doing the
per-node analysis in the browser from `/registry` (a second definition of what
resolves, in a second language).

**Verification.**
- `tests/test_settings_api.py::test_validate_names_the_node_and_task_that_do_not_resolve`
  — a two-node draft with one bad hook; assert `unresolved == [{"node": "x",
  "task": "on.does.not.exist"}]` and that a fully-bound draft reports `[]`.
- `components/ui.test.tsx::it("draws a node list with no work item behind it")`
  and `it("marks an unresolved segment")`.
- `Settings.test.tsx::it("draws the parsed draft as a chain bar and marks the
  node that does not resolve")` — replaces the `"/repo-a: unresolvable"`
  assertion at `Settings.test.tsx:194`.
