# The chain can report a merge that never happened

## The problem

Everything below is in `src/kraft/adapters/forge.py`, in `run_task` and the two
production backends `GlabCli` / `GhCli`.

**Kraft-79x3 — the merge node trusts an exit code.** `run_task`'s `merge` case
calls `forge.merge(...)` and immediately writes `log, status = "merged\n",
"done"`. `GlabCli.merge` runs `glab mr merge --yes` through `_run`, which only
inspects the subprocess return code. GitLab treats `mr merge` as *async*: when
the head commit's pipeline is still running it enables "merge when all merge
checks pass", exits 0, and merges nothing. That happened live on work item
`0853ea31…` / MR !76: Kraft logged `merged`, marked the node done, and completed
the work item; the pipeline then failed, the auto-merge never fired, and the MR
is still open with `detailed_merge_status=conflict`. The item is terminal, so
there is no retry path back onto it. `GhCli.merge` has the same shape.

**Kraft-ejj9 — the check node never asks whether the MR can merge.** The
`ci_poll` case polls `forge.ci_status`, which reads pipeline state only:
`GlabCli.ci_status` reads `glab ci list -F json -P 1 --ref <branch>`,
`GhCli.ci_status` reads `statusCheckRollup`. Neither reads the merge request's
own mergeable state (`merge_status` / `detailed_merge_status` on GitLab,
`mergeable` / `mergeStateStatus` on GitHub). A branch with a green pipeline and
a real conflict against `main` passes `mr_checks` as `done`, walks through the
human_review gate, and only meets the conflict at the merge node — which, per
Kraft-79x3, reports success anyway.

**Kraft-bxj8 — nothing pushes before the check node polls.** Only `open_mr` and
`sync_mr` push. A commit made in the worktree after `open_mr` (a doc fix, a
re-run of implementation, a review-brief commit on a retry) is local until
`mr_sync`, which runs *after* human review. So `on.ci.poll` polls the pipeline
for the previously pushed commit — the same pipeline id every retry, green or
red, forever, because no new commit exists on the MR to trigger a new one. Work
items `b63d95be…` and `1c039982…` both hit this in one session; the fix each
time was a manual `git push` in the worktree. The merge node has the mirror
symptom: `_assert_pushed` correctly refuses a head the remote has never seen,
but it fails the node three times rather than pushing, and a retry of `merge`
alone never re-runs `mr_sync`, so it can never clear itself.

**Kraft-8mi8 — the two git guards have no real-git test.** `_assert_clean` and
`_assert_pushed` are exercised only through stub `git` binaries on PATH
(`tests/test_forge.py::_stub`) and through `FakeForge`. Nothing drives them
against a real `git` process with a real remote, and they are the two guards
standing between a chain and landing an empty or stale MR.

## The approach

One idea at four sites: **a forge node's stated end state must be read back off
the forge, and a forge node owns pushing.** The worker agents are told not to
push (`adapters/agent.py:45`); the nodes that talk to the forge already hold
`forge.push`, so the push belongs there and nowhere else.

### 1. Push before polling and before merging (Kraft-bxj8)

In `run_task`, `await forge.push(repo=repo, branch=branch)` at the top of the
`ci_poll` case and at the top of the `merge` case, the same single line
`sync_mr` already carries. `git push -u origin <branch>` is a no-op when the
branch is up to date, so this costs one git call per node. `_assert_pushed`
inside `GlabCli.merge` / `GhCli.merge` stays: after the push it is an invariant
that should never trip, and it is the tripwire if it ever does.

Pushing at the merge node is safe in this chain's order: `mr_sync` already
pushes post-approval commits by design, and after fix 3 below a merge deferred
by a fresh pipeline fails the node loudly instead of reporting success.

### 2. A pipeline that is not for this head is not a result (Kraft-bxj8)

Pushing exposes a second race: for a few seconds after the push, `glab ci list
-P 1 --ref <branch>` still returns the *previous* commit's pipeline, which may
be green. `GlabCli.ci_status` therefore compares the row's `sha` against `git
rev-parse HEAD` and returns `pending` with `jobs=("no pipeline for <sha7>
yet",)` when they differ — the same answer it already gives for no pipeline at
all. `GhCli` needs nothing here: `gh pr view --json statusCheckRollup` is
already scoped to the PR's head commit.

### 3. The check node reads the MR's mergeable state (Kraft-ejj9)

`CIStatus` gains two fields, both defaulted so `FakeForge` and existing tests
are unaffected:

```python
mergeable: bool | None = None  # None: the forge has not decided, or does not say
merge_detail: str = ""  # the raw state, for the log line
```

- `GlabCli.ci_status` makes one extra call, `glab mr view -F json` (already used
  in `open_mr`), and reads `detailed_merge_status`, falling back to
  `merge_status`.
- `GhCli.ci_status` adds `mergeable,mergeStateStatus` to the `--json` field list
  of the `gh pr view` call it already makes. No extra process.

Mapping, deliberately narrow: `conflict`, `need_rebase`, `broken_status`,
`cannot_be_merged`, GitHub `CONFLICTING` / `DIRTY` → `mergeable=False`.
`mergeable` / `can_be_merged` / `MERGEABLE` → `True`. **Everything else,
including `not_approved`, `ci_still_running`, `discussions_not_resolved`,
`draft_status`, `checking`, `unchecked` and `UNKNOWN` → `None`.**

That is the opposite of the "unknown means failed" convention the
`_GLAB_STATES` table uses, and it is on purpose: `mr_checks` runs *before* the
human_review gate, so `not_approved` and `ci_still_running` are the normal
state of a healthy MR at this node, and mapping them to failure would fail
every repo with approval rules. Only states that need a code change to clear
fail the node. States that need a *person* are the gate's business, and after
fix 4 the merge node no longer lets them through silently.

`_poll_ci` returns as soon as `ci.mergeable is False`, rather than waiting out
the pipeline: a conflict will not resolve itself in thirty minutes. `run_task`'s
`ci_poll` case fails the node when `ci.mergeable is False`, whatever the
pipeline colour, with a log line naming the state
(`merge request is not mergeable: conflict`).

### 4. The merge node reads the MR back until it says merged (Kraft-79x3)

A new `_poll_merged(forge, *, repo, branch, timeout, interval)` in `forge.py`,
mirroring `_poll_ci`: call `find_mr` on the same backoff until the `MRRef` state
leaves `open`, or the deadline passes. `run_task`'s `merge` case, after
`forge.merge` returns, polls it and decides from the state actually read:

- `merged` → `done`, logging the MR number.
- `closed` → `failed` (the merge did not land and the MR is gone).
- still `open` at the deadline → `failed`, with the state read and a line saying
  the forge may have scheduled an auto-merge, so the human knows where to look.

Two new module constants, `MERGE_VERIFY_TIMEOUT = 300.0` and
`MERGE_VERIFY_INTERVAL = 5.0`, exposed as `merge_timeout` / `merge_interval`
keyword arguments on `run_task` so tests can run them at zero. Five minutes,
not `DEFAULT_POLL_TIMEOUT`'s thirty: by this node the pipeline was already
green at `mr_checks`, so a merge that has not landed in five minutes is a merge
that is waiting on something a person has to see.

They are **not** added to the registry schema (`templates.py`'s
`poll_timeout`/`poll_interval` validation stays `ci_poll`-only). Nothing has
asked to tune them, and the constants are one edit away if something does.

### 5. A real-git test for the two guards (Kraft-8mi8)

A new `tests/test_forge_git.py` with a helper that builds a real repo and a real
`git init --bare` origin in `tmp_path`, commits, and pushes — no network, no
stubbing of `git`. Only the forge CLI is stubbed. This is also the fixture
Kraft-ejj9's and Kraft-bxj8's tests need: a branch that is genuinely pushed, and
a HEAD that a stale pipeline sha can be compared against.

### Rejected

- **A separate `mr_mergeable()` on the `Forge` protocol, or a new node for it.**
  More protocol surface and another CLI round trip for a fact the check node has
  to know at exactly the moment it already reads CI.
- **Making the worker agent push its own commits.** Puts the remote and its
  credentials into every agent session and races Kraft's own push; the forge
  adapter already owns push, and one fix there covers every node.
- **Verifying the merge inside `GlabCli.merge` / `GhCli.merge`.** Duplicates the
  poll in both backends and leaves `FakeForge` unable to script the failure, so
  the bug would stay untestable without a live forge. `run_task` is where the
  other merge-state reasoning (`find_mr`, the already-merged short circuit from
  Kraft-xron) already lives.
- **Failing the merge node immediately if the MR is still open after the CLI
  returns.** GitLab merges asynchronously even in the good case; a bounded poll
  is the shape `ci_poll` already uses for exactly this.
- **`ci_poll` pushing only when `git rev-list` says it is ahead.** An
  unconditional `git push` is already a no-op when up to date, and the extra
  branch is a second thing to get wrong.

## Out of scope

- Merge trains and GitHub merge queues beyond "poll until it is really merged".
- Automatic rebase or conflict resolution when `mergeable` is false: the node
  fails and the fix loop or a human takes it.
- Any route back onto a work item that already reached `work_item_completed`
  (Kraft-xron's family) — this work stops the false completion, it does not
  recover the one that already happened.
- Registry-configurable merge verification timeouts.
- Notifications, UI surfacing of the new failure reasons, and the `mr_checks`
  fix loop (`fix_loop` is unset on that node in `templates/default.yaml`; the
  node failing is enough for this change).
- `GhCli` sha checking: `statusCheckRollup` is head-scoped already.

## Verification

`just test tests/test_forge.py tests/test_forge_git.py`, plus `just lint`.

Kraft-bxj8:
- `test_ci_poll_pushes_before_it_polls` — FakeForge records `pushed` before the
  first `ci_status`.
- `test_merge_pushes_before_it_merges` — same, for the merge case.
- `test_glab_ci_status_ignores_a_pipeline_for_an_older_commit` — stub `glab`
  returning a green pipeline with a different sha than the real repo's HEAD;
  state is `pending`, not `success`.

Kraft-ejj9:
- `test_glab_ci_status_reads_the_mr_merge_state` — stub `glab` with
  `detailed_merge_status: "conflict"`; `mergeable is False`.
- `test_gh_ci_status_reads_mergeable_from_the_same_pr_view` — asserts
  `mergeable,mergeStateStatus` are in the recorded argv and `CONFLICTING` maps
  to False.
- `test_ci_poll_fails_when_the_mr_cannot_be_merged` — FakeForge with a green
  pipeline and `mergeable=False`; node status `failed`, log names `conflict`.
- `test_ci_poll_does_not_fail_on_an_undecided_merge_state` — `mergeable=None`
  with a green pipeline is still `done`.
- `test_poll_returns_early_on_a_conflict_rather_than_waiting_out_the_pipeline` —
  pending pipeline + `mergeable=False` returns without sleeping to the deadline.

Kraft-79x3:

  and the timeout.
- `test_merge_fails_when_the_mr_was_closed_rather_than_merged`.
- The existing `test_a_forge_error_fails_the_node_rather_than_escaping` and the

Kraft-8mi8 (`tests/test_forge_git.py`, real `git`, bare origin, stubbed forge
CLI):
- `test_open_mr_refuses_a_dirty_worktree_against_real_git` — an untracked file
  makes `GlabCli.open_mr` raise `ForgeError` naming the path, and no `glab mr

- `test_open_mr_ignores_gitignored_paths_against_real_git` — a `.gitignore`d

- `test_merge_accepts_a_pushed_head_against_real_git` — after a real push to the
  bare origin, `merge` runs the CLI.
