```python
async def _exit_from_file(
    db, session_id: str, log_path: Path, result_path: Path, status: str
) -> None:
    """Record a session exit from what it left on disk, carrying every field
    `adapters.subprocess.run_task` carries — `concerns` and `question` reach the
    gate and the needs_context stop only through this event, so a restart that
    dropped them would lose what the worker reported. Usage is the same story
    (Kraft-7co4): a session adopted across a restart used to write NULL tokens
    and NULL cost, dropping the node out of every rollup that sums them.

    `read_result_fields` is the one place that field list is spelled out
    (Kraft-k3d) — this and `adapters.subprocess.run_task` both call it rather
    than each enumerating the fields by hand."""
    fields = read_result_fields(result_path)
    seen = _usage.read(log_path, result_path)
    await db.write(
        lambda c: store.session_exited(
            c,
            session_id,
            status,
            fields["summary_ref"],
            seen,
            concerns=fields["concerns"],
            question=fields["question"],
        )
    )
```

is where a Claude Code worker's tokens and cost actually are — so the log path
is needed, not just the result path. It returns `None` when neither carries
usage, and `session_exited` already treats `None` as "leave the columns alone",
so a non-agent task that reports nothing behaves exactly as it does today.

```python
def test_two_nodes_closed_in_the_same_second_are_not_billed_the_whole_run(chain):
    """`BD_TIME` has one-second granularity, so two nodes closed inside the same
    second carry the same stamp. Compared with a strict `<` the second finds no
    earlier event at all and falls back to the epic — billing a node that took
    no measurable time for the entire run (Kraft-ao6)."""
    count = len(chain["nodes"])
    # epic at 10:00, the first two nodes both at 10:05, then a minute each
    stamps = [stamp(0), stamp(5), stamp(5)] + [stamp(m) for m in range(6, 6 + count - 2)]
    records = walked(chain, stamps)

    out = kl.summary(records, chain)
    seconds = [n["seconds"] for n in out["nodes"]]
    # the first node genuinely took the five minutes since the chain started
    assert seconds[0] == 300, out["nodes"]
    # the second shared its second, so its truth floored to the second is zero —
    # not the 300 it reports today, and not the 0 the first would wrongly report
    # if ties were merely allowed to match without being ordered
    assert seconds[1] == 0, out["nodes"]
    assert seconds[2] == 60, out["nodes"]
```

Today this fails on `assert seconds[1] == 0` with `seconds == [300, 300, 60,
…]`. Both halves of the assertion matter: the obvious smaller edit — one flat
list of stamps with `<` relaxed to `<=` and the record's own excluded —
produces `[0, 0, 60, …]` and fails the *first* assertion instead. The spec
built that version to find out; ordering the tie is the whole fix.

### Implementation

`plugins/kraft-lite/kl.py`, replacing lines 529–538 (fenced as text, not
python, so the repo's `ruff format` pre-commit hook does not dedent it — it is
indented one level, inside `summary()`):

```text
    #: Every stamp the chain carries, so a node can be timed from whatever happened
    #: last before it closed rather than from its predecessor's close. After a
    #: rewind those differ: the predecessor still holds its stamp from the first
    #: pass, and timing from it charges the redo for the whole walk in between.
    #: Each stamp is paired with its record's position in the walk, because
    #: `BD_TIME` resolves to the second and two nodes closed inside one second
    #: are otherwise indistinguishable — the later of the two then finds nothing
    #: earlier and falls all the way back to the epic (Kraft-ao6). Position
    #: breaks ties only; it never picks the predecessor.
    order = {r["id"]: i for i, r in enumerate([epic, *walk])}
    events = sorted((x, order.get(r["id"], -1)) for r in records if (x := _at(r)))

    def since(record: dict) -> str | None:
        closed_at = _at(record)
        if not closed_at:
            return _at(epic)
        key = (closed_at, order.get(record["id"], -1))
        # `< key` excludes the record's own entry without a separate id test.
        earlier = [e for e in events if e < key]
        return earlier[-1][0] if earlier else _at(epic)
```

`epic` and `walk` are both already bound above this point (`kl.py:511-512`).
Every record has a unique `id` (`materialize`, `kl.py:70-97`). A record that is
neither the epic nor on the walk sorts at position `-1`, below everything else
sharing its stamp — such a record is not timed by `since()`, only used as a
possible predecessor, and putting it first among equals is the conservative
choice.

Untied stamps behave exactly as before: a strictly earlier stamp compares less
whatever the positions are.

Same edit, the `ponytail:` note in `summary()`'s docstring at lines 503–504.
It currently claims the sub-second ceiling reports zeros while the code
inflated instead; after this fix the claim is true, so state it as a fact
rather than leaving the caveat reading like a known bug:

```python
    ponytail: one second is the granularity of every stamp here, so a chain walked
    faster than that reports zeros, including two nodes that closed inside the same
    second. Nothing sub-second is recoverable.
```

Not doing, and why (spec's rejected alternatives): sub-second stamps —
`BD_TIME` is the format bd records carry and changing it breaks every existing
chain's records. Falling back to the previous row in walk order outright — that
is what the ordered `events` list deliberately replaced, and it charges a
redone node for the whole first pass. Deduplicating `events` and keeping `<` —
a tie would still fall through to the epic, and the tie is the case being
fixed.
