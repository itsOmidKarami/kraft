# UI

> Component 4 of the decomposition (`01_conceptual_model.md` §12): the **UI** — a
> local web app: cross-repo work item board, unified search,
> spec/plan/session-summary viewer, approval gates (scheduled + ad hoc pause/steer),
> live worker status. Builds entirely against the API surface from
> `02_orchestrator_core.md`, `03_plugin_adapters.md`, `04_indexer_search.md`, and
> `06_cross_repo_federation.md`.

## 0. Purpose

A single local SPA over the orchestrator's API. No new mechanism or schema decisions
live here — those are in the component docs this one consumes.

---

## 1. Stack

- **React**, no meta-framework (no Next.js — a single local SPA served by one
  process, not a multi-route server app).
- Build output is static assets served directly by the orchestrator's FastAPI/uvicorn
  process (`02` §2) — one process, one port. A build step (Vite or equivalent) is
  dev-time only; no separate frontend dev server in the shipped app.
- No component library assumed — plain CSS/utility classes, kept lightweight given
  solo use and no design-system requirement.

---

## 2. Client State & Sync Model

- **One global WebSocket connection** (`WS /ws/events`, subscribed to all work items)
  opened at app load, not per-view. At this scale per-view subscriptions add
  complexity for no benefit.
- **Normalized client store**, keyed by `work_item_id`. Every inbound event reduces
  into the relevant work item's slice — `node_started` / `node_completed`,
  `worker_session_launched` / `completed` / `paused`, `chain_loaded`,
  `involved_repos_resolved`, `fix_cycle_started`, gate events (including
  `chain_finalized`, which is a *value* of the generic
  `gate_requested`/`gate_approved`/`gate_rejected` events, not a distinct type — it
  reduces the same way spec/plan/human-review gate events do),
  `pause_requested`/`resume_requested`, `steer_context_set`.
- **REST is the bootstrap and reconciliation path, not the primary sync path.**
  `GET /work-items` populates the store on load; after that the WS feed is
  authoritative. A periodic (~60s) background refetch of the currently-viewed work
  item guards against a silently missed event.
- **Reconnect:** on WS drop, the client tracks the last `seq` per work item it has
  seen and resubscribes with `after_seq` (`02` §5) — no data loss, no full refetch.
  A small "reconnecting…" indicator, not a blocking overlay.

---

## 3. Auth Flow

- App boots by attempting a lightweight authenticated call (`GET /health`):
  - **200** → straight to the board. The common case: bound to `127.0.0.1`, auth
    middleware skipped entirely (`02` §9).
  - **401** → login screen. The LAN-bound case, where auth is enforced.
- Login screen: password field → `POST /login`. Cookie (`HttpOnly`, `SameSite=Lax`)
  set server-side; the client never touches the token, just retries the boot call
  after a successful login.
- Any subsequent 401 mid-session (revoked/expired token) bounces back to the login
  screen, store intact — no state loss on expiry.
- Logout button → `POST /logout`, clears local store, returns to login.

## 4. Views

### 4.1 Board (`/`)

- **Flat card list**, not kanban columns keyed by node. Different work items run
  different chain templates, so a shared column axis doesn't line up across cards; a
  flat list with per-card chain graphs is the honest representation.
- Each card:
  - Repo tag (or repo cluster, below), title, overall `work_items.status` badge
    (`active` / `paused` / `needs_human` / `completed`).
  - **Full chain graph strip** — every node in `chain_definition` rendered as a
    segment in order, current node highlighted, gate markers (⚑) on nodes with
    `gate_after` set. Concurrent-task nodes (`verify`, `mr_checks`) render as one
    segment with a small task-count badge (e.g. "2") when active — the badge bumps
    during a fix cycle.
  - Requires `GET /work-items` (list) to include each item's `chain_definition` and
    `chain_template` — both already-materialized columns, cheap at this scale (`02`
    §10.1).
- **Repo cluster:** when an item's `involved_repos` (from `GET /work-items`) has more
  than one entry, the single repo tag becomes a cluster — root repo plus a "+N"
  badge.
- Filters (client-side, the full list is small): repo, status, `chain_template`, and
  `involved_repo` (matches any work item that touches the chosen repo, not just its
  root). `chain_template` is the dedicated `work_items.chain_template` column, not
  something parsed out of `chain_definition`.
- **"New Work Item" button** — opens the intake modal (§4.1a).

### 4.1a New Work Item (modal, launched from the Board)

`POST /work-items` is the only path by which a work item comes into existence (no
passive bead-watching), so the UI must be able to call it.

- Small modal, not a separate route — a quick, infrequent action.
- Fields: **repo** (dropdown, connected-repo set), **title** (free text), **chain
  template** (dropdown, defaults to the target repo's `default_chain_template`;
  options come from templates the Chain Validator's startup tier marked resolvable
  (`02` §12), so a broken template can't be selected).
- **"Advanced / cross-repo" disclosure** (collapsed by default): **submodules**
  (multi-select, populated from the target repo's `.gitmodules`, fetched once the
  root repo is chosen) and **root merge policy** (radio: Bump / Skip / Bump-no-MR,
  default Bump). Both map to the optional `submodules` / `root_merge_policy` body
  fields, sent only when set. Single-repo intake stays one line.
- Submit → `POST /work-items { repo, title, chain_template?, submodules?,
  root_merge_policy? }`. `chain_template` sent only if changed from the repo default.
- On success: close the modal, navigate to the new Work Item Detail (`/work-items/:id`
  — the response includes the id). The store also picks up the resulting
  `chain_loaded` event over WS, so the Board stays consistent without a manual
  refetch.
- On failure (e.g. Chain Validator's resolution tier rejects the template against
  this repo's plugin config): show the error inline, keep the modal open with input
  intact.

### 4.2 Work Item Detail (`/work-items/:id`)

- **Repos panel** — rendered above the chain stepper (it's cross-cutting, not
  per-node). One row per `work_item_repos` entry from `GET /work-items/{id}`: repo,
  role, a `merge_state` chip (`pending` / `mr_open` / `checks_green` / `merged` /
  `skipped`), MR link. During the `merge` node this is the live view of the ordered
  `merge_rank` walk. Shown only when `work_item_repos` has more than one entry; a
  single-repo item hides it.
- **Chain stepper** across the top — same full-chain representation as the board
  card, larger: every node as a step, current highlighted, past nodes collapsed to a
  status icon (clean / capped-out), gates shown inline at the node they belong to.
- **Current node panel** — one row per task in the current node (from the
  node-scoped `worker_sessions` array `GET /work-items/{id}` returns — every task
  regardless of state, not filtered to running-only, since this panel renders
  terminal-state chips too). Status chips:
  - `running` (pulsing), `completed` (clean), `failed`, `capped_out` (distinct from
    `failed` — the loop hit its cap but siblings ran to completion, `02` §7.1),
    `paused`, `unknown` (crash-reattach couldn't confirm, `02` §8).
  - A fix task (backward-motion) renders as a row here, badged (e.g. "fix · cycle N").
    It is steerable (`on.implementation.start` → HeadlessAgentInvocation).
  - A node whose tasks are all in a *terminal-clean* state, with `gate_after` set and
    no next-node session yet, is inferred to be **awaiting gate approval** — derived
    client-side from `chain_definition` + `current_node_id` + `worker_sessions`, not
    a separate API field. This inference depends on terminal-state rows still being
    present in the response.
- **Pause / Resume / Steer controls** — on the current node panel:
  - **Pause** — always available while `status = active`. Calls `POST /pause`; UI
    shows a pending state until the `worker_session_paused` event(s) land — not
    assumed synchronous.
  - **Steer** — a text box, active only once `status = paused`. Submits
    `POST /steer { text }`. Rendered only for nodes whose current task(s) map to a
    HeadlessAgentInvocation-backed hook (table below) — steering a GitLab poll or a
    beads CLI call is meaningless.
  - **Resume** — available once paused, with or without steer text. Calls
    `POST /resume`.
  - The steerable-hook mapping is a small hardcoded client table (not derivable from
    any API response today), mirroring the adapter kind each hook uses:

| Hook | Adapter | Steerable |
|---|---|---|
| `on.spec.requested` | HeadlessAgentInvocation | Yes |
| `on.plan.requested` | HeadlessAgentInvocation | Yes |
| `on.chain.review_ready` | HeadlessAgentInvocation | Yes |
| `on.implementation.start` | HeadlessAgentInvocation | Yes |
| `on.test.run` | HeadlessAgentInvocation (measurement-only) | Yes, technically — unusual in practice, flagged rather than excluded |
| `on.review.local.run` | HeadlessAgentInvocation (ponytail-review) | Yes |
| `on.intake` | SubprocessAdapter (beads CLI) | No |
| `on.env.prepare` | SubprocessAdapter (deterministic) | No |
| `on.mr.open`, `on.ci.poll`, `on.merge` | HttpClientAdapter (GitLab) | No |
| `on.review.mr.run` | SubprocessAdapter (remote-review CLI) | No |

  The multi-repo `open_mr` / `mr_checks` / `merge` tasks are still HttpClientAdapter /
  SubprocessAdapter and still not steerable. If this mapping ever needs to change with
  the plugin registry it'll silently go stale — worth eventually promoting to an
  `interactive: bool` field in the registry config, not urgent for v1.
- **Event timeline** — reverse-chronological feed of that work item's events
  (`GET /work-items/{id}/events`, live-appended via WS). Each `worker_session_*` event
  links to "view full log" → `GET /worker-sessions/{id}/log`, pull-based, opened in a
  modal — not a live tail.
- **Linked documents panel** — `GET /work-items/{id}/documents`:
  spec/plan/reviews/session-summaries linked to this work item, each opening the
  Document Viewer.

### 4.3 Search (global overlay, not a dedicated route)

- Accessible from any view (persistent affordance / keyboard shortcut).
- `GET /search?q=&mode=hybrid` by default; an "advanced" toggle exposes
  `source_kind` / `kind` / `repo` filters and the `fts` / `vector` / `hybrid` mode
  radio.
- Results list: title, `source_kind` / `kind` badge, repo, snippet (whatever
  `/search` returns — no full-content fetch at this stage).
- Click-through: `source_kind: 'artifact' | 'session_summary'` → Document Viewer
  (`GET /documents/{id}`), with a breadcrumb back to any linked work item(s) via
  `document_links`. `/search` no longer returns `source_kind: 'bead'` results.
- **Bead-scoped search box** — a separate box alongside artifact/summary search,
  backed by `GET /beads/search` (hub passthrough, live). Its results link to Work
  Item Detail via the bead's linked work item, or show the bead inline if unlinked.
- **Hard rule carried through from the Indexer:** nothing rendered from a `/search`
  result — status, gate state, retry counters — is ever treated as current. It's a
  lagging shadow (`04` §8). A search hit is used for text discovery and navigation
  only; landing on Work Item Detail always re-fetches live state from
  `/work-items/{id}`.

### 4.4 Document Viewer

- A **modal over the work item**, not a route (UI handoff spec §6, design 6a).
  Reading a plan is a glance mid-task; closing it must return the reader to the
  item they were on rather than to browser history. There is no `/documents/:id`.
- Rendered markdown (`react-markdown`), `GET /documents/{id}` for full `content`,
  with the metadata inline in the header: kind tag, source node, written-at, the
  repo-relative path, and how far behind git the index is.
- **Open in `<editor>`** — `POST /documents/{id}/open { editor? }` launches the
  editor server-side on the document's absolute path. A headless server answers
  501 and the UI falls back to a `vscode://file/…` URL, which the viewer's own
  machine can honour.
- No edit/save capability anywhere — there's no write path for documents in the API,
  and it would violate the git-native source-of-truth principle (`01` §1.3) for the
  UI to originate content.
- No bead documents exist (`04` §3/§4), so the viewer never renders one. Bead detail
  is the hydration-hub passthrough (`GET /beads/search` and the bead-inline view in
  §4.3), which is live, not a lagging shadow.

### 4.5 Gates

- Rendered inline on the chain stepper (§4.2), not a separate approvals page — a gate
  is a property of the node it's attached to.
- **Approve** → `POST /work-items/{id}/gates/{gate}/approve`.
- **Reject** → `POST /work-items/{id}/gates/{gate}/reject` with a **required**
  `{ note }` (a text field the UI must collect before enabling submit). Reject
  behavior is now defined (`02` §7.2 entry point B), and the UI can reflect it:
  - `spec_approval` / `plan_approval` / `chain_finalized` — the producing hook
    re-invokes with the note; the node's `gate_after` fires again and returns to the
    human. On the reject-loop counter breaching, `status` → `needs_human`.
  - `human_review_approval` — `status` → `needs_human`, no auto-re-invocation; the
    human drives the redo via pause/steer or a manual re-trigger.
  - The state is deterministic from the event stream; the UI reduces `gate_rejected`
    (with its `note` payload), `fix_cycle_started`, and subsequent
    `worker_session_launched` / `node_completed` events the same as any other update.

## 5. System Status

- Small persistent indicator (e.g. header bar) sourced from `GET /health` — surfaces
  Chain Validator problems (invalid templates, `02` §12) without a dig through logs.
  Not a dashboard, just a flag-if-something's-wrong affordance.
- **Manual reindex control** — a small "Rescan" action per repo, calling
  `POST /index/rescan?repo=<repo>` (`04` §2's manual escape hatch). Shows a brief
  pending/done state, not a progress bar — meant for the rare "I hand-edited a file
  and don't want to wait" case, not routine use.

---

## 6. What "Live" Means Here

"Live worker status" is **task/node state transitions delivered over the event bus**,
not a raw stdout tail. Concretely live:

- Node/task status transitions (`worker_session_launched` / `completed` / `paused`,
  `node_started` / `completed`, and status changes including `capped_out` surfaced
  via those same events).
- Gate lifecycle events; `fix_cycle_started`; `involved_repos_resolved`.
- Whatever the MCP status callback reports today (`usage_reported_json` — cost/token
  counts), as a secondary detail on a running task's chip.

**Not live in v1:** raw agent output. That stays a pull-based "view full log" action
(§4.2). If granular self-reported progress text ever gets a defined event shape, it's
a drop-in addition to the current-node panel — no UI architecture change.

## 7. API Surface Consumed

Auth (`/login`, `/logout`), `GET /health`, `WS /ws/events`; work-item creation
(`POST /work-items`), read (`GET /work-items`, `GET /work-items/{id}` — including
`chain_definition`, `chain_template`, `involved_repos`, `root_merge_policy`,
node-scoped `worker_sessions`, full `work_item_repos`), events
(`GET /work-items/{id}/events`), gates (`approve` / `reject { note }`), pause/resume/
steer; `GET /worker-sessions/{id}/log`; search (`GET /search`, `GET /beads/search`),
documents (`GET /documents/{id}`, `GET /work-items/{id}/documents`), index rescan
(`POST /index/rescan`).

This document assumes those land; it does not re-derive them.

## 8. Open Questions / Placeholders

Most of these are now **answered** by the UI handoff spec (`design/Kraft Handoff
Spec.dc.html`, screens in `design/Kraft Design.dc.html`):

- ~~Exact visual treatment for `capped_out` vs `failed` vs `unknown`~~ — **answered**
  (handoff spec §3). The palette is mono-accent, so states are told apart by glyph
  and tone, never by a second hue: `running` = circle-notch in the accent with a
  pulse, `done` = check, `failed` = x-circle, `capped_out` = prohibit *plus* the
  words "capped n/n", `paused` = pause, `unknown` = question. `needs_human` is the
  one solid accent fill in the interface. Fix cycles read as a `fix · cycle n`
  outline tag beside the current node, not as a badge on the chain bar.
- ~~Whether the steerable-hook-points table should move server-side~~ — **answered**
  (handoff spec §7): yes, `interactive: bool` in the plugin registry, replacing the
  client table. Steer is *hidden*, not disabled, for a hook that is not steerable.
- ~~Component library / CSS approach~~ — **answered**: the Nocturne design system,
  one stylesheet of tokens and component classes (`frontend/src/nocturne.css`), with
  Phosphor icons. Every value in `styles.css` comes from a token; no hex literals.
- ~~Mobile/phone layout~~ — **designed** (design 1n) but still v1.1: the same grouped
  rows at 44px touch targets, chain bar `sm` only, needs-you rows actionable and
  everything else read-only behind "Open on desktop".
- **Archive** is the one thing still open, and deliberately so — which states can be
  cancelled or archived, whether archive is a status or a flag on top of one, and
  what an archived item can still do. `archived_at` is reserved on work items and
  nothing else is built. Analytics counts archived items.

## 9. Build Order

1. **Auth + boot flow + WS connection + client store** (§2, §3) — nothing else
   renders without a live data path.
2. **Board** (§4.1) — first real screen, exercises `GET /work-items` with the
   `chain_definition` / `chain_template` shape.
3. **New Work Item flow** (§4.1a) — small, needed before there's any way to populate
   the Board beyond what exists.
4. **Work Item Detail — repos panel + chain stepper + current node panel** (§4.2,
   minus pause/steer) — the core "what's happening right now" view.
5. **Pause/Steer/Resume controls** (§4.2) — depends on the pause/steer mechanism
   (`02` §10.2) shipping first. Still true: nothing in `src/kraft` implements pause,
   steer or resume, so the detail control row renders them disabled.
6. **Event timeline + log viewer** (§4.2).
7. **Search overlay + Document Viewer** (§4.3, §4.4) — ✅ **shipped** (Effort
   4A-UI): global overlay (`Cmd/Ctrl-K` + header button), debounced
   `GET /search` (`fts` mode), advanced `source_kind` / `kind` / `repo`
   filters, results with `[..]` → `<mark>` highlighting, click-through to a
   document modal (`GET /documents/{id}`, raw-markdown `<pre>` body + metadata
   panel). Deferred: `mode` selector (Effort 4C), `document_links` breadcrumb
   + the `/work-items/{id}/documents` linked-docs panel (Effort 4B),
   bead-scoped search box (`06` §6.1), real markdown rendering.
8. **Gates** (§4.5) — can land any time after step 4.
9. **System status + manual reindex control** (§5) — low-stakes, whenever `GET
   /health` and `POST /index/rescan` are wired.

  Reject is now **defined** (`chain_backward_motion_addendum_v1.md` §4): required

  deterministic.
- **§2 / §6** — `fix_cycle_started`, `involved_repos_resolved`, `worker_session_paused`,
  and `steer_context_set` added to the events the client store reduces (the last two
  from `orchestrator_indexer_api_addendum_v1.md` §1.2).

- **UI redesign (Nocturne)** — §4.4 Document Viewer is a **modal, not a route**;
  §8's open questions on status iconography, the steerable-hook table, the CSS
  approach and the phone layout are answered from the handoff spec; §4.7-adjacent
  Settings screens now write YAML through the API (`02` §4.7, `01` §3.6 revised in
  step). New surfaces not in the original: an Analytics view (`GET /analytics`), a
  log modal with source filters and an SSE follow-tail, per-`worker_session` usage
  capture, and retry-after-cap carrying steer text.
- **Settings, Login and the phone view** — `/settings/{repos,templates,plugins,policy,access}`
  edit versioned YAML through the API; `/login` appears only off localhost, where
  auth is on (`02` §10.2-adjacent: scrypt password, HttpOnly session cookie whose
  token is stored only as a hash, and the websocket checks the session too because
  HTTP middleware does not run for it). The phone layout (design 1n) is CSS on the
  same rows: needs-you gates stay actionable, everything else says "Open on
  desktop". Cross-repo intake and the 3a repos panel are wired to `submodules` /
  `root_merge_policy` on the work item, ordered deepest-submodule-first.
- **Cost is never computed.** An earlier pass carried a per-model rate table and
  multiplied stored tokens by it whenever an agent reported no cost. That is gone:
  the agent knows what it was billed and Kraft does not, so `cost_usd` is only ever
  the agent's own figure and is NULL otherwise. Rollups carry `cost_complete`, and
  a sum missing an unreported cost renders with a trailing `+` — a floor, never a
  total. Tokens stay exact regardless, since those are measured.
